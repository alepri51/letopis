# Backlog

## Порт letopis на Python

**Статус:** идея / research
**Дата:** 2026-07-13

> **1.0:** разбор ниже писался для 0.21. В 1.0 целостность, id, права и проверка данных живут в базе, поэтому порт
> сводится к построителю цепочек, клиенту входа и валидатору. Опора для id — векторы v5
> `lib/test/vectors/v5.json`: они рассчитаны независимой реализацией на стандартном модуле `uuid` Python
> (генератор `lib/test/vectors/gen_v5.py`), и реализация на Python проверяется теми же векторами, что SQL и TypeScript.

### Вердикт

Полностью повторимо. ~80% ценности (append-only, tombstone-каскад, lineage, детерминированные
id, ACL-предикаты) живёт в БД — DDL + PL/pgSQL-триггеры переносятся дословно, язык клиента им
безразличен. Порт = переписать fluent-фасад + свапнуть драйверы. Идиоматичнее JS: `__getattr__`
чище `Proxy`.

### Маппинг JS → Python

| Летопис (JS) | Python |
|---|---|
| dot-цепочки через `Proxy` | `__getattr__` на классе цепочки |
| слоты `.Клиент.set()` без вызова | объект, который и callable, и держит `.set/.unset` |
| юникод-имена `db.Мастер` | `__getattr__` берёт строку — работает как есть |
| postgres.js | `asyncpg` |
| ioredis | `redis-py` (`redis.asyncio`) |
| fastest-validator | `pydantic` / `cerberus` |
| scrypt, sha256, uuidv5/v7 | `hashlib`, `uuid` (stdlib) |
| TOTP | `pyotp` |
| async/await | `asyncio` |

### Тонкие места

- **Смешанный синтаксис** `db.Услуга(x)` (вызов) + `.Клиент.set(x)` (атрибут без вызова).
  `__getattr__` возвращает объект: `__call__` = шаг-фильтр, атрибуты `.set/.unset` = слоты.
- **Ленивый план → терминал**: `await chain.rows()` ложится на `async def rows`.
- **v5-id детерминизм**: в 1.0 `uuid_v5(арендатор, '["класс", "значение", …]')` — имя собирается
  `json.dumps([класс, *значения], ensure_ascii=False, separators=(", ", ":"))`; совпадение проверяют векторы
  `lib/test/vectors/v5.json`. Идемпотентность и «двойная бронь мертва» сохраняются.
- **Reserved-слова**: `in`/`or`/`not`/`is` заняты → операторы `in_list`, `or_`, `not_`, `is_null`.
- **`class` reserved** → `row.class_` либо `row["class"]`.

### Отличия питон-API от JS

- Терминалы — `await` (`asyncio`).
- Dict-фильтр `{...}` как в JS; **плюс** kwargs-сахар `db.Услуга(name="X")`.
- Транзакция/сессия → `async with` (авто-rollback на исключении).
- Слоты `.Класс.set()` — идентично, через `__getattr__`.
- Row — `dataclass` или dict; поля `id/class/data/links/tags/account/owner/updated`.

### Как реализовать

#### Слои

```
┌─ приложение ─────────────────────────────┐
│ letopis (Python) — fluent-фасад          │  ← переписываем
├─ SQL: ddl.sql + триггеры + seed ─────────┤  ← ПЕРЕНОСИМ ДОСЛОВНО из JS-репо
└─ TimescaleDB + Redis ────────────────────┘
```

SQL (`lib/sql/*.sql`) не трогаем — копируем как есть. Вся тяжёлая логика (версии,
tombstone-каскад, `schema_lineage`, проверка концов LINK, FK) уже в БД и языко-независима.
Питон-часть = построитель плана + компилятор в SQL + драйверы.

#### Ядро: цепочка = неизменяемый план

Каждый `db.X()` / `.Y()` возвращает **новый** `Chain` с добавленным шагом (иммутабельно —
цепочку можно переиспользовать, как в JS). SQL уходит только на терминале.

```python
@dataclass(frozen=True)
class Step:
    cls: str                      # имя класса или алиас
    filter: Any = None            # id | list | dict | Op-dict | None
    verb: str | None = None       # None | 'create' | 'update' | 'delete' | 'anonymize'
    data: dict | None = None
    slots: tuple = ()             # (('Услуга', value|UNSET), …)
    alias: str | None = None
    pivot: bool = False

@dataclass(frozen=True)
class Chain:
    db: "EntityDb"
    steps: tuple[Step, ...] = ()
    mods: dict = field(default_factory=dict)   # limit/offset/sort/asOf/after/deep

    def __getattr__(self, name: str):
        if name in TERMINALS:  return partial(_run_terminal, self, name)   # await
        if name in MODIFIERS:  return partial(_add_mod, self, name)        # → Chain
        return ClassRef(self, name)   # класс схемы: шаг ИЛИ слот
```

#### `ClassRef` — один объект, три смысла

Ключевой трюк. Имя класса на цепочке (`chain.Услуга`) — это `ClassRef`, который:
- **вызван** `chain.Услуга(x)` → `__call__` → добавить шаг-фильтр;
- **`.set(x)`** → добавить слот (валиден только если у последнего шага есть глагол записи);
- **`.unset()`** → слот-снятие.

Так `db.Услуга(у)` (шаг) и `.Услуга.set(у)` (слот) различаются лишь `()` vs `.set` —
ровно как `Proxy` в JS, но явно.

```python
UNSET = object()

@dataclass(frozen=True)
class ClassRef:
    chain: Chain
    cls: str

    def __call__(self, filter=None, /, **kw) -> Chain:      # шаг
        f = kw or filter                                   # kwargs-сахар ⇒ dict
        return _append(self.chain, Step(cls=self.cls, filter=f))

    def set(self, value) -> Chain:                          # слот
        _require_write(self.chain, self.cls)               # иначе: link slot needs a write
        return _add_slot(self.chain, self.cls, value)

    def unset(self) -> Chain:
        _require_write(self.chain, self.cls)
        return _add_slot(self.chain, self.cls, UNSET)
```

`EntityDb.__getattr__` — то же, но резервные имена (`accounts/credentials/auth/acl/batch/
begin/watch/close/entity`) перехватываются ЯВНО до фолбэка в `ClassRef`.

#### Терминал → компиляция плана

`_run_terminal` разбирает `steps`:

1. **Резать на сегменты** по глаголам записи.
2. **Контекст-шаги** (до глагола) — каждый резолвится в РОВНО одну сущность: id-фильтр без
   запроса; уникальный фильтр — запрос (0 или >1 → ошибка). Дают `links` для create /
   containment-фильтр целей для update/delete.
3. **Чтение** → рекурсивный SELECT: на каждом hop `DISTINCT ON (id) … ORDER BY id, updated
   DESC` после сужения по class + GIN-кандидатам, перепроверка на latest. Переходы
   HUB→LINK (reverse), LINK→HUB (forward), pivot (возврат к узлу + AND-дофильтр).
4. **Запись** → INSERT новой версии, `links` = контекст + слоты, id по правилу схемы.
5. Есть запись → весь план в ОДНОЙ транзакции (`async with con.transaction()`).

Терминалы: `run/rows/first/ids/count/versions/sum/avg/min/max/countBy`.

#### Registry (на connect)

```python
class Registry:
    def load(self):
        rows = fetch("SELECT * FROM Schema WHERE partition='entity'")
        self.by_name = index(rows, key=('id','alias'))          # id и alias равноправны
        for cls in rows:
            self.attrs[cls] = merge_lineage(cls)                # потомок ПОВЕРХ предка
            self.validator[cls] = compile_validator(self.attrs[cls])
```

#### Валидация

`fastest-validator` DSL → питон. Два пути:
- **pydantic** `create_model` на класс (быстро, но strict-режим и «поле вне схемы = ошибка»
  надо доконфигурить: `model_config = ConfigDict(extra='forbid')`);
- **свой обходчик** DSL (точнее ложится на семантику: вложенные `props`, defaults, касты).

Рекомендация: свой — DSL простой, а совпадение поведения с БД-триггером критично (тесты
БД ловят те же ошибки, сверять по ним).

#### Драйверы и транзакции

- `asyncpg.create_pool(dsn)`.
- Чтения в автокоммите — ретрай deadlock `40P01` / serialization `40001` (3 попытки, backoff
  40–160 ms), как §10.12.
- `insertOne` — ретрай гонки `updated` (23505, мгновенно).
- `db.begin()` → `EntityTx` на удержанном соединении, тот же Chain-API; `async with` =
  commit на выходе / rollback на исключении.
- Redis — `redis.asyncio`, инжектится (не в зависимостях, как ioredis).

#### Фазы (порядок работ)

1. **registry + validate + ids** — без цепочек. Грузим схему, валидируем, считаем id.
   Тестируется автономно.
2. **чтение** — `Chain/ClassRef/__getattr__`, план→SELECT, hop-ы (HUB/LINK/pivot),
   терминалы `run/rows/first/ids/count`.
3. **запись** — глаголы `create/update/delete`, слоты, one-tx, каскад-превью.
4. **модификаторы** — `sort/limit/offset/asOf/after/deep` + агрегации.
5. **транзакции + батч**.
6. **auth + acl**.
7. **tables, watch, policies, gen-types**.

Каждая фаза проверяется теми же сценариями, что JS-тесты (`lib/bench/*`, README-примеры) —
БД одна и та же, ответы должны совпасть.

#### Риски

- **fastest-validator DSL** — самый муторный порт (nested props, custom rules, defaults,
  strict). Сверять по БД-триггеру: он бросает те же ошибки.
- **uuidv7** нет в stdlib < 3.13 — свой генератор.
- **Жадный матчинг концов LINK** (порядок объявления, союзы, optional) — воспроизвести
  байт-в-байт; БД-триггер `entity_check` ловит те же ошибки — эталон.
- **Коллизия имён**: класс с именем терминала/модификатора (напр. класс `count`) —
  `__getattr__` отдаст терминал, не шаг. Разрешение: терминалы/модификаторы приоритетны;
  такой класс — только через `db.entity()`. Задокументировать.

## Цена повторного наката `ddl.sql` (`upgrade: true`)

**Статус:** закрыт в 1.0 (этап 6)
**Дата:** 2026-07-31

> **Закрыто в 1.0.** `up()` выполняет `ANALYZE` только для таблиц без статистики (`lib/src/up.ts:up`, поле
> `analyzed` результата): на повторном накате он пуст, это проверяет тест `up`. Файла `ddl.sql` и внешних ключей
> `Entity` из 0.21 в 1.0 нет. Ниже — разбор 0.21, сохранённый для истории.

Пришло как внешнее предложение патча «letopis → 0.20.4». Техника верна, оценка эффекта в
предложении завышена на порядок. Здесь — что установлено замером, чтобы не разбирать заново.

### Дефект

`lib/sql/ddl.sql` (строки с `entity_account_fk` / `entity_owner_fk`) при каждом накате делает
`DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT … FOREIGN KEY`. `ADD` без `NOT VALID` проверяет
все существующие строки: полный проход по `Entity` со всеми чанками, дважды. Результат каждый
раз тот же FK. `lib/src/up.ts` при `upgrade: true` льёт файл целиком одной `sql.unsafe`, то
есть в одной транзакции — окна без FK не возникает, но и сканы идут всегда.

Замеры (dev-контейнер `letopis-timescale`, PG 17 + TimescaleDB):

| Полигон | Строк | Чанков | Размер | `DROP`+`ADD` двух FK |
|---|---|---|---|---|
| `v1.tenants` | 1 000 000 | 1 | 580 МБ | 22 + 337 + 7 + 256 = **~620 мс** |
| `v1.salondemo` | 980 328 | 13 | 954 МБ | 58 + 417 + 30 + 297 = **~800 мс** |

Блокировки (снято из `pg_locks` во время `ALTER`): `AccessExclusiveLock` на `Entity` **и на
каждом чанке**, плюс `ShareRowExclusive` + `AccessExclusive` на `Account`. Держатся до конца
транзакции, то есть весь накат. Цена линейна по истории — для append-only растёт всегда.

### Правка

Заменить четыре `ALTER TABLE` одним `DO $guard$ … END $guard$;` с проверкой
`NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = … AND conrelid = '"<SCHEMA-NAME>"."Entity"'::regclass)`
вокруг каждого `ADD CONSTRAINT`. Проверено на живой базе:

- повторный накат `ddl.sql`: **0.82 / 0.88 / 0.82 с** → **0.154 / 0.157 / 0.174 с** (×5.2);
- первый накат на свежей схеме не ломается: все три FK `convalidated = t`, штамп
  `letopis ddl_revision=1` на месте;
- `DO $guard$…$guard$` файл не рвёт: dollar-quoting в `ddl.sql` уже есть, `sql.unsafe` не
  режет текст на выражения;
- `checkDdlRevision` в `lib/scripts/check-docs.mjs` не страдает: проверка «штамп — последнее
  выражение» строит `tail` через `indexOf(stamp)` и смотрит только **после** штампа, а блок
  встаёт выше;
- `checkTestList` сверяет имена тест-файлов, не число тестов → README §16 править не нужно;
- ревизию бампать не нужно: результирующая схема та же, все три числа (`ddl.sql`,
  штамп `COMMENT`, `DDL_REVISION` в `lib/src/types.ts`) остаются 1.

Ограничение, которое появляется: определение FK «залипает» — guard старое не переопределит.
Будущая правка определения = смена имени констрейнта либо отдельный шаг апгрейда, привязанный
к `DDL_REVISION`.

### Почему одного этого мало

Рядом, в том же `applySchema`, стоит `ANALYZE "…"."Entity"` — и он дороже в 18 раз:

| Шаг `up({ upgrade: true })`, `v1.salondemo` | Время |
|---|---|
| весь `ddl.sql` | 0.82 с |
| — из них FK | ~0.70 с |
| `ANALYZE Entity` | **12.8 с** |
| **end-to-end** | **10.3 / 11.2 с** |

То есть guard снимает **6%** стоимости `upgrade`. «Повторный накат становится бесплатным» —
неверно: останется ~10 с на этом полигоне. `AccessExclusive` тоже не уходит — дальше в файле
`DROP TRIGGER IF EXISTS` + `CREATE TRIGGER` на `Entity` берут тот же лок; сокращается только
длительность окна.

Просто выкинуть `ANALYZE` из `upgrade` нельзя: схемы, накатанные либой до 0.20.2, статистики
не имеют, и `upgrade` для них единственный способ её получить (тот самый ×18 из README §14.1).
Нужен признак «статистика уже есть» — например `pg_stat_all_tables.last_analyze` по чанкам —
и `ANALYZE` только когда его нет либо когда прошлый накат был первым.

Ещё одна независимая линия: `ADD CONSTRAINT … NOT VALID` + отдельный `VALIDATE CONSTRAINT`
удешевляет уже **первый** накат на непустой базе. Замерено на `v1.salondemo`: `ADD NOT VALID`
37 мс + `VALIDATE` 281 мс против 417 мс прямого `ADD`. По времени выигрыш скромный, ценность в
том, что `VALIDATE` берёт `ShareUpdateExclusive` и не блокирует чтение и запись.

Системно: разделить `ddl.sql` на «структуру» (создаётся один раз) и «код» (функции и триггеры,
перекатываются дёшево), чтобы `upgrade` катал только вторую часть.

## Персональные данные: хранилище ПД и криптошреддинг

**Статус:** отложено владельцем — исключено из плана 1.1 решением от 2026-10-09
**Дата:** 2026-10-09

Пункт 3 раздела 13 плана 1.0. Полный разбор с источниками и тест-планом — редакция 2 плана
`reports/PLAN-LETOPIS-1.1.md` (§2.5, §7.6, коммит `45e7c4d`): `git show 45e7c4d:reports/PLAN-LETOPIS-1.1.md`.

### Что показало исследование

- Ни один регулятор не признаёт удаление ключа стиранием. EDPB Guidelines 02/2025 (версия 2.0 от 7 июля 2026):
  зашифрованные ПД остаются персональными данными, шифрование со временем устаревает, ПД не стоит записывать в
  неизменяемый журнал ни открытыми, ни зашифрованными, ни хэшированными (п. 50–52, 96, 103–104). ICO и CNIL — так же.
  NIST SP 800-88r2 не доверяет криптостиранию, пока неизвестно, где лежат копии ключа.
- Бэкапы PostgreSQL берутся по кластеру целиком: ключ в той же базе живёт в WAL и бэкапах до их истечения.
- pgcrypto для этого слаб: `encrypt()` без проверки целостности, `pgp_sym_encrypt` — AES-128 и SHA-1, ключ и открытый
  текст попадают в журнал сервера; CVE-2026-14663 (исправлена в 18.6).

### Предложенное устройство

- **Уровень 1 — хранилище ПД.** Опция класса `personal: { fields, subject }`. Значения персональных полей лежат не в
  `data`, а в строках `secret` вида `PD`; в `data` — обязательство `{"$pd": sha256(соль ‖ значение)}`. Журнал и
  цепочка хэшей не содержат ПД, `verify()` проверяет подлинность значений, пока они не стёрты. Чтение — функция
  владельца `pd_reveal(id, rev)` с проверкой видимости строки. `db.forget(субъект)` удаляет значения физически, пишет
  служебную запись `forget` и отдаёт квитанцию; `letopis forget --replay` повторяет стирания после восстановления
  из бэкапа.
- **Уровень 2 — криптошреддинг.** AES-256-GCM в Node, ключ субъекта обёрнут ключом приложения вне базы (переменная
  окружения или KMS); ротация этого ключа делает нечитаемыми старые бэкапы.
- **Структура:** частичные индексы `secret` по субъекту и по объекту (новая ревизия движка).

### Что учесть при возврате (из ревью редакции 2)

- Функции кредов (`auth_credentials`, `auth_revoke_credential`, `auth_set_flags`, `auth_kind_ok`) должны работать по
  белому списку видов, иначе пользователь увидит строки хранилища как свои креды и «отзовёт» их мимо `forget`.
- Поле ПД заменяется только целиком: `merge` не должен вливать патч внутрь обязательства.
- `rekey` и `reclass` перепривязывают строки хранилища; конец-субъект неизменяем.
- `personal` объявляется только у класса без строк и без версий в журнале.
- Уровень хранилища хранится в схеме, а не в опциях `up()`: иначе повторный `up()` его сбросит.
- Когда кэш работает только по сроку (без сигналов), классы с ПД не кэшируются.

### Первая заливка: ускорение подготовки строк

Цель плана 1.1 (§2.3) — первая заливка втрое быстрее обычного загрузчика на миллионе объектов. Достигнуто 2,19×:
77,2 с против 169,0 с на 1 073 580 объектах полигона salon (`docs/checkpoint-1.1.md`, раздел «Точка А: конвейер
первой заливки»). Конвейер в `lib/src/load.ts` готовит следующую пачку (`prepareBatch`), пока база пишет текущую
(`flushBatch`), и теперь скорость задаёт подготовка строк в Node: около 59 с процессорного времени из 77.

Что можно сделать:
- снять профиль `prepareBatch` на полном полигоне и ускорить саму подготовку: проверки, концы связей, id, строки
  `COPY`;
- готовить пачки в нескольких потоках (`worker_threads`): пачки независимы, а `COPY` остаётся одним, в той же
  транзакции;
- параллельный `COPY` в нескольких соединениях владелец на точке А отклонил в пользу конвейера: он требует нескольких
  транзакций, а первая заливка держится на одной транзакции и `FREEZE`.

### Подписка: дождаться начальной точки «now»

`db.watch({ from: 'now' })` возвращается сразу, а начальную точку (горизонт и снимок, `watch_head()`) берёт
асинхронно, из конструктора (`lib/src/watch.ts`, поле `start`). Запись, зафиксированная раньше снимка, считается
сделанной до подписки и в поток не попадает. README (раздел «Подписка») и шпаргалка («Грабли 1.0», п. 16) об этом
предупреждают, и пример README читает с `'start'`. Тесты ждут приватное поле (`lib/test/_engine.ts:watchStarted`):
из-за этой гонки CI выпуска 1.1.0 падал.

Что можно сделать: публичный `await sub.ready()` — обещание начальной точки; или асинхронный `await db.watch(…)`,
который отдаёт подписку уже с точкой (меняет API).

### Подписка: параллельные вызовы `next()`

`Subscription.next()` (`lib/src/watch.ts`) не рассчитан на параллельные вызовы: два вызова читают журнал с одной
позиции, и событие приходит дважды, либо событие достаётся вызову, который вызывающий уже бросил по таймауту.
`for await` зовёт `next()` по очереди, так что это задевает только ручной вызов с таймаутом через `Promise.race`, как в
тестах: `take` в `lib/test/watch.test.ts` теперь переиспользует незавершённый вызов.

Что можно сделать: ставить вызовы в очередь (следующий ждёт предыдущий) или отклонять параллельный вызов понятной
ошибкой.
