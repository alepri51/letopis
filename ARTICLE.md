# Letopis: хранилище, которое ничего не забывает

*Версионируемое entity-хранилище поверх TimescaleDB с запросами точками: `db.Сотрудник({name:'Вася'}).навык().Услуга().execute()`. Каждая запись — навсегда. Каждое изменение — новая строка. Каждый спор «а какая цена была на момент брони» решается одним вызовом.*

> Пакет: [`letopis`](https://www.npmjs.com/package/letopis) (ранее entity-chain). 86 автономных тестов, бенчмарки на 1.1M строк, статус — крепкая beta.

---

## 1. Проблема, из которой всё выросло

Любой бизнес на записях — салон, клиника, автосервис, аренда — живёт спорами о прошлом:

- «Мне называли другую цену» — а услугу трижды переоценивали.
- «Я не отменял запись» — а кто-то отменил. Кто? Когда?
- «Почему у мастера две брони на одно время?» — гонка двух администраторов.
- «Удалите мои данные» — GDPR, но бухгалтерии нужна история заказов.

Классический CRUD отвечает на всё это одинаково: *данные перезаписаны, история потеряна*. Дальше начинаются костыли: audit-таблицы на триггерах, поля `updated_by`, event-лог рядом с основной схемой — три источника правды, которые расходятся.

Letopis переворачивает постановку: **UPDATE и DELETE физически не существуют**. База умеет только INSERT. «Изменение» — новая версия строки. «Удаление» — надгробие (tombstone). История — не побочный журнал, а сама структура данных.

Это не новая идея — так работают Datomic, XTDB, event sourcing. Новое здесь — упаковка: обычный PostgreSQL/TimescaleDB, обычный TypeScript, одна таблица данных, и API, в котором граф связей читается и пишется точками.

## 2. Как устроено хранилище

### 2.1 Одна таблица на все сущности

Вся предметная область живёт в одной hypertable `Entity`:

| Колонка | Смысл |
|---|---|
| `partition` | пространство данных (`'entity'`) |
| `id` | id сущности |
| `class` | класс из таблицы `Schema` (FK) |
| `data` jsonb | атрибуты |
| `links` jsonb | связи: `{"Org": "id1", "Staff": "id2", …}` — сколько угодно на строку |
| `tags` text[] | метки |
| `account`, `owner` uuid NOT NULL | арендатор и владелец (FK → Account) |
| `updated` timestamptz | момент версии |
| `deleted` timestamptz | метка надгробия |

Ключевой трюк — первичный ключ **`(partition, class, id, updated)`**. Сущность — это *все строки с её id*; актуальное состояние — строка с максимальным `updated`, если она не tombstone. Партиционирование — только по времени (чанки по 30 дней): версии естественно ложатся в «свой» месяц, старые чанки сжимаются, новые пишутся.

### 2.2 CRUD живёт в самой базе

Три триггера делают семантику честной даже для того, кто пишет голый SQL мимо библиотеки:

```sql
-- UPDATE перехватывается: физического апдейта нет, вставляется НОВАЯ версия
UPDATE "booking"."Entity" SET data = data || '{"duration":45}'
 WHERE partition='entity' AND class='Service' AND id='…';

-- DELETE перехватывается: tombstone + РЕКУРСИВНЫЙ каскад по links на сервере
DELETE FROM "booking"."Entity"
 WHERE partition='entity' AND class='Booking' AND id='…';
```

- `entity_check` — INSERT-валидация: класс существует и не абстрактный, ключи `links` — реальные классы, у связей есть обязательные концы.
- `entity_update` — превращает UPDATE в INSERT версии с монотонным временем `GREATEST(clock, prev + 1µs)`; попытка изменить не-последнюю версию игнорируется — история неизменяема.
- `entity_delete` — вставляет tombstone и рекурсивно каскадирует по зависимым (`links ⊃ {класс: id}`) под advisory-lock. Повторный DELETE — no-op.

Библиотека добавляет поверх: строгую валидацию `data`, цепочки, транзакции, батчи. Но целостность не зависит от дисциплины клиента — она в БД.

### 2.3 Schema: классы как данные

Модель домена — строки таблицы `Schema`, а не миграции:

- **HUB** — сущности (Организация, Сотрудник, Услуга, Клиент, Окно, Запись…).
- **LINK** — связи с атрибутами (навык, смена, занятость, позиция). У LINK обязательные концы; конец `'Entity'` — полиморфный («что угодно»).
- `attributes` — схема полей в DSL [fastest-validator](https://github.com/icebob/fastest-validator): типы, enum, default-ы, `optional`. Валидация всегда строгая: лишнее поле — ошибка.
- Наследование: `ancestor` → триггер `schema_lineage` сам пересчитывает `ancestors`/`descendants` рекурсивными CTE.
- У каждого класса два равноправных имени: `Staff` и `Сотрудник`. API работает с обоими.

### 2.4 Чтение «актуального»

Паттерн каждого запроса: сузить по классу и GIN-кандидатам → взять последнюю версию `DISTINCT ON (id) … ORDER BY id, updated DESC` → перепроверить условия на актуальной версии. Важное следствие: фильтр истинен относительно *текущего* состояния — сущность со старым `name='Вася'` и новым `name='Петя'` под фильтр «Вася» не попадёт.

## 3. Тур по API на живом примере

Салон красоты: организация, мастера, услуги, календарь, брони.

### 3.1 Подключение и первые сущности

```ts
import { connect } from 'letopis'

const db = await connect({ dsn: 'postgres://…', schema: 'booking' })

const [org]  = await db.Организация().set({ name: 'BarberPro' })
const [вася] = await db.Организация(org).Сотрудник().set({ name: 'Вася', roles: ['owner','master'] })
const [маник] = await db.Организация(org).Услуга().set({ name: 'Маникюр', duration: 60, price: { RUB: 2000 } })
```

Первый принцип: **связи — только точками**. `db.Организация(org).Сотрудник().set({…})` означает «в контексте этой организации создай сотрудника» — строка получит `links: {Org: org.id}`. Никаких `{foreignKey: …}` в данных.

### 3.2 Запись: одна форма — четыре режима

Режим определяет *аргумент последнего шага*:

```ts
await db.Клиент().set({ name: 'Анна' })            // Класс()   → INSERT, id сгенерируется
await db.Клиент('uuid…').set({ name: 'Анна' })     // Класс(id) → UPSERT по id
await db.Клиент().set({ id: 'uuid…', name: '…' })  // id в data → тот же UPSERT
await db.Запись({ status: 'created' }).set({ status: 'confirmed' })  // объект → UPDATE найденных
await db.Клиент(анна).Запись({}).set({ status: 'cancelled' })        // {} → UPDATE ВСЕХ в контексте
```

Обновление — **deep-merge только указанных листьев**: `set({ price: { USD: 25 } })` добавит USD и сохранит RUB. Массивы и скаляры заменяются целиком.

Связи задаются тремя равнозначными формами:

```ts
// 1) контекст ДО set()
await db.Сотрудник(вася).Окно(w).Запись(b).занятость().set({ kind: 'booking' })
// 2) довес ПОСЛЕ set()
await db.Сотрудник(вася).занятость().set({ kind: 'booking' }).Окно(w).Запись(b)
// 3) z-форма: копим на переменной
const z = db.занятость().set({ kind: 'booking' })
z.Сотрудник(вася); z.Окно(w); z.Запись(b)
await z
```

`set()` возвращает ленивый thenable-билдер: связи довешиваются до первого `await`, исполняется **один INSERT**, промис кешируется (повторный `await` не плодит версий, довес после исполнения — ошибка).

### 3.3 Чтение: пути по графу

```ts
const пути = await db.Сотрудник({ name: 'Вася' }).навык().Услуга().execute()
// [{ Сотрудник: Row, навык: Row, Услуга: Row }, …] — узел на каждый шаг
```

Правила обходов выводятся из модели, объявлять «join-ы» не нужно:

| Переход | Механика |
|---|---|
| HUB → LINK | reverse: строки связи, содержащие этот hub в `links` |
| LINK → HUB | forward по `links->>'Hub'` — работает даже для не объявленного в схеме конца |
| HUB → HUB | forward, если класс-цель встраивается в текущий; иначе reverse; иначе понятная ошибка «no path» |
| HUB → тот же HUB | дети (`db.Папка(id).Папка()` — вложенные папки) |
| LINK → LINK | запрещено |

Терминалы на выбор: `execute()` (пути), `rows()` (уникальные сущности последнего шага), `first()`, `ids()`, `count()`.

### 3.4 Фильтры и 18 операторов

```ts
import { gte, between, ilike, has, or, not, exists } from 'letopis'

db.Услуга('uuid')                                  // по id
db.Услуга(['id1', 'id2'])                          // по списку
db.Услуга({ name: 'Маникюр', active: true })       // равенство → GIN containment
db.Услуга({ duration: between(30, 90) })           // операторы с кастом по типу из Schema
db.Услуга({ price: { RUB: gte(1000) } })           // вложенный путь record-поля
db.Сотрудник({ roles: has('master') })             // операторы массивов
db.Запись(or({ status: 'created' }, { status: 'confirmed' }))   // дизъюнкция
db.Услуга({ name: not(ilike('%тест%')), description: exists(false) })
```

Полный набор: `ne, gt, gte, lt, lte, between, inList, like, ilike, starts, ends, has, hasAny, hasAll, exists, isNull, not, or`. Касты берутся из Schema (`number → ::numeric`, `date → ::timestamptz`) — сравнение дат и чисел в jsonb корректно.

### 3.5 Модификаторы

```ts
await db.Запись().sort('updated', 'desc').limit(50).offset(0).rows()
await db.Клиент().tags(['vip']).rows()               // фильтр по колонке tags
await db.Запись().account(tenantId).count()          // фильтр по арендатору
await db.Организация(org).alias('салон').Услуга().execute()  // ключ шага в путях
```

Те же `.tags()/.account()/.owner()` перед `set()` задают **значения** колонок при вставке.

### 3.6 Удаление: сервер снимает всё дерево

```ts
const удалено = await db.Запись(bid).delete()
// [{class:'Booking', $deleted:true}, {class:'busy',…}, {class:'item',…}]
```

Один вызов: замыкание зависимых собирается CTE, один SQL `DELETE`, триггер каскадно тумбстоунит дерево. Возвращается **всё удалённое** с флагом `$deleted`. Повторный delete — `[]`. А `set()` по тому же id — воскрешение (историю никто не трогал).

### 3.7 Транзакции и гонка двойной брони

```ts
const tr = await db.begin()
await tr.lock('busy', staffId, slotId)              // advisory-lock до конца транзакции
const занято = await tr.занятость(busyId).first()   // перечитать ПОД локом
if (!занято) {
  await tr.Сотрудник(s).Окно(w).Запись(b).занятость(busyId).set({ kind: 'booking' })
  await tr.commit()
} else {
  await tr.rollback()                                // окно уже увели
}
```

`tr` — тот же API на выделенном соединении. Рецепт от двойной брони: лок на пару (мастер, окно) + детерминированный id занятости + перечитка под локом. В тестах это настоящая гонка двух параллельных транзакций — побеждает ровно одна.

### 3.8 Батчи

```ts
const b = db.batch('окна')
for (const { start, end } of сетка) b.Расписание(sch).Окно().set({ start, end })
const результаты = await b.execute()   // одна транзакция, Row[][] по порядку
```

Подряд идущие чистые INSERT одного класса склеиваются в один multi-VALUES. Любая ошибка (включая валидацию) откатывает весь батч.

### 3.9 Служебные таблицы

Аутентификация и ACL — обычные таблицы с обычным CRUD-фасадом: `db.accounts`, `db.credentials` (upsert по `(account, category, identifier)`, мягкое удаление, воскрешение), `db.resources`, `db.rules`. Связка с данными: `Entity.account/owner NOT NULL` с FK — аккаунт с историей физически неудаляем (RESTRICT), только `enabled: false`.

## 4. То, ради чего затевалась история

### 4.1 Машина времени

```ts
// спор о цене: что видел клиент 1 июля?
const тогда = await db.Услуга(id).asOf('2026-07-01T12:00:00Z').first()

// полная биография записи
const история = await db.Запись(bid).versions()
// created → confirmed → …, tombstone приходит с $deleted: true
```

`asOf` работает на **каждом шаге** цепочки и со всеми терминалами — «подграф, как он был». Никакого отдельного audit-механизма: это те же строки.

### 4.2 Realtime без поллинга

```ts
const stop = await db.watch('Запись', (e) => обновитьКалендарь(e.id))
```

Триггер шлёт лёгкий `pg_notify` на каждую версию (insert / update / tombstone); подписчик дочитывает данные обычной цепочкой.

### 4.3 Мультитенантность одной опцией

```ts
const db = await connect({ dsn, schema, account: tenantId, enforceAccount: true })
```

Все чтения автоматически фильтруются по арендатору, все записи пришпилены к нему; попытка указать чужой `account` — ошибка. Изоляцию гарантирует библиотека, а не внимательность разработчика.

### 4.4 GDPR при неизменяемой истории

```ts
await db.Клиент(id).anonymize(['name', 'contact'])   // '[erased]' + тег 'anonymized'
```

Честный компромисс, зафиксированный в документации: анонимизация создаёт новую версию, старые версии хранят PII до истечения retention-политики. Полное «право на забвение» = `anonymize()` сейчас + `--retain` потом:

```bash
node db/policies.mjs --dsn=… --schema=booking --compress-after=30d   # сжатие ~10-20×, история цела
node db/policies.mjs --dsn=… --schema=booking --retain=2y            # осознанный drop чанков старше 2 лет
```

### 4.5 Эволюция схемы без молчаливых поломок

```bash
node scripts/schema-sync.mjs --file=schema.v2.json --dsn=… --schema=booking
#  + Coupon (HUB · Купон) — новый класс
#  ~ Service — изменены: attributes
#  ! Service: 3/50 живых строк НЕ пройдут новую валидацию: brand — required
#  exit 1
```

Diff файла и таблицы Schema плюс прогон живых строк новой валидацией **до** применения. Инструмент окупился в первый же день: на тестовом прогоне он поймал баг деплой-скрипта, который подменял строку `"booking"` внутри jsonb-сидов.

### 4.6 Наблюдаемость, типы, прочее

```ts
const db = await connect({ dsn, schema, slowMs: 200,
  onQuery: (e) => log(e) })   // {mode:'rows', classes:['Staff','skill'], ms:4.2, rows:7, slow:false}
```

- `.deep()` — дерево папок любой глубины одним recursive-CTE, `$depth` на строках.
- `.after(cursorOf(row))` — keyset-пагинация, не деградирующая с ростом offset.
- `.sum/.avg/.min/.max/.countBy('data.total.RUB')` — агрегации в БД, включая record-пути.
- `scripts/gen-types.mjs` — TS-интерфейсы полей всех классов из живой Schema + типизированный фасад `TypedDb` (enum → union-литералы).
- `db/apply.mjs` — весь движок в любую PG-схему одной командой.

## 5. Производительность: измерено, не обещано

Docker TimescaleDB, локально. Датасет A: 105k строк (5k сущностей × 20 версий). Датасет B: **1 112 860 строк**, год истории, полный граф (250k броней × 2 версии, 250k занятостей, 250k позиций, 30k клиентов…).

| Операция (1.1M строк) | p50 | p95 |
|---|---|---|
| Точечное чтение по id | 2.4 ms | 4.4 ms |
| Вставка / новая версия | 3.1 / 6.7 ms | 4.7 / 10.7 ms |
| `versions()` сущности | 4.2 ms | 7.7 ms |
| `asOf().first()` | 2.2 ms | 3.8 ms |
| Фильтр по классу, limit 100 | 133 ms | 158 ms |
| Цепочка 3 хопа (пути) | 282 ms | 391 ms |
| `countBy` по 500k строк | 584 ms | 671 ms |
| Каскадное удаление дерева | 210 ms | 239 ms |

Отдельная история — выбор партиционирования. Исходный дизайн (унаследованный от legacy-системы) добавлял hash-размерности по partition/class/id. Бенчмарк на одинаковых данных показал: точечный доступ не ускоряется вовсе (PK-btree уже оптимален), простые фильтры выигрывают 10–20%, зато многошаговые LATERAL-цепочки проседают в **2–140 раз** (трёхшаговый count: 1 секунда против 150), а чанков становится 93/год вместо 14. Hash-размерности убрали; решение и цифры зафиксированы в `bench/dimensions.results.json`.

Слабое место, о котором честно: keyset-страница по *всему* классу в 500k строк стоит ~1.7 s — `DISTINCT ON` пересчитывает актуальные версии всех сущностей класса до сортировки. На отфильтрованных выборках проблемы нет.

## 6. Сравнение: на чьей поляне играем

Исследование 30+ систем (полное — в `RESEARCH.md` репозитория) не нашло прямого аналога связки «append-only entity store на TimescaleDB + dot-цепочки». Ближайшие соседи:

| Система | Что общего | Чем Letopis отличается |
|---|---|---|
| **Datomic / XTDB** | иммутабельность, `asOf`, история как первоклассная сущность | не JVM и не Clojure; обычный Postgres, обычный npm-пакет; нет Datalog — зато цепочки читаются без обучения |
| **Marten (event sourcing, .NET)** | события/версии в Postgres | нет разделения на события и проекции: версия и есть состояние; не нужно строить read-модели |
| **Prisma / Drizzle** | типизированный доступ из TS | это ORM поверх мутабельных таблиц: истории, asOf, watch, каскадов-в-БД у них нет |
| **EdgeDB (Gel)** | графовые связи, свой язык запросов | требует свой сервер и язык; Letopis — просто схема в вашем Postgres |
| **Hasura / Directus** | быстрый CRUD над Postgres | генерируют API над текущим состоянием; версионность — снова на плечах пользователя |
| **temporal_tables / periods (PG)** | системное время | история на таблицу, без графа связей, без каскадов, без клиентского API |

Суперсила против всех: **голый SQL остаётся полноценным клиентом**. UPDATE/DELETE в psql дают ту же семантику версий и каскадов — триггеры не дадут соврать. Интеграции, миграции, аварийные правки не ломают модель.

## 7. Где применять

- **Онлайн-запись и брони** (родной домен): салоны, клиники, сервисы, аренда. Гонки решены, «4 руки» (два мастера — одна запись) выражается моделью, переносы и отмены оставляют след.
- **CRM и заказы**, где споры о прошлом — норма: кто изменил сумму, когда подтвердили, что было в корзине.
- **Каталоги с историей цен** — аудит и «цена на дату» бесплатно.
- **Мультитенантные SaaS** малого/среднего масштаба — изоляция на уровне библиотеки.
- **Админки и внутренние инструменты**, где нужен «undo» и ответственность: каждая версия знает `owner`.
- **Комплаенс** — ретенция, анонимизация, полная трассируемость из коробки.

## 8. Где будет работать плохо

Честный список — записывался по мере набивания шишек:

1. **Высокочастотные обновления одной сущности** (счётчики, лайки, телеметрия): каждый инкремент — новая строка с полной копией `data`. Тысячи обновлений/сек одной записи раздуют историю и потеряют смысл.
2. **Крупные документы**: `data` больше ~2KB уходит в TOAST, deep-merge читает и переписывает документ целиком. Файлы и блобы — в объектное хранилище, здесь только ссылки.
3. **Аналитика по всему классу на лету**: `DISTINCT ON` актуальных версий 500k+ сущностей — сотни миллисекунд; сортировка всего класса или keyset без фильтра — секунды. Тяжёлый BI — выгружайте срез в витрину.
4. **Полнотекстовый поиск** — GIN по jsonb ищет равенство и containment, не релевантность. Нужен поиск — подключайте tsvector/внешний движок отдельно.
5. **Ссылочная целостность значений `links`** слабее реляционной: БД проверяет ключи (классы), но не существование целевого id — «висячая» ссылка возможна при ручной вставке. Библиотечные пути (контекст-шаги) резолвят цели и от этого защищают.
6. **Сложные инварианты между строками** — непересечение временных окон (EXCLUDE-констрейнты на hypertable невозможны), «сумма позиций = итог» — контролирует приложение (транзакции + локи в помощь).
7. **Не-JS клиенты**: готовый API — только TypeScript/JavaScript. Из других языков — голый SQL (семантика сохранится, удобство — нет).
8. **Жёсткое право на забвение** («стереть след полностью и немедленно») противоречит модели: только анонимизация + retention по расписанию. Если юристы требуют физического стирания точечно и сразу — это не сюда.

## 9. Статус и что дальше

Сегодня: движок (DDL + триггеры + FK) ~360 строк SQL, библиотека ~2.5k строк TypeScript без тяжёлых зависимостей (postgres.js + fastest-validator), 86 автономных тестов (включая сквозной чек-лист каждого публичного метода и 16 «живых» сцен дня салона), CI на живой БД, три бенчмарка, полный API reference. Из 16 пробелов, найденных при сравнении со зрелыми системами, закрыт 15 — остался row-level ACL поверх правил доступа, осознанно отложенный.

Кандидаты следующей волны: ускорение «широких» выборок класса (материализация latest-среза), полнотекст, клиенты вне JS.
