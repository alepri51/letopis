# M-WRITE — планы записи, транзакции, батч, загрузчик

**Инварианты и грабли**
- Причина изменения (план 1.1, этап 1): `opCall` перед глаголом ставит `letopis.reason` (`useReason`) — только если причина меняется (`WriteCtx.cur`); причина глагола — `op.reason`, иначе причина по умолчанию (`WriteCtx.reason`: батч или транзакция). После плана (`execPlan`) — обратно на причину по умолчанию, после батча (`execBatch`) — на причину транзакции (`txReason`): причина глагола не переходит на `db.sql` и следующие планы. В батче другая причина режет группу склеенных вставок, а конвейер вставок без ключа получает причину до отправки. `checkReason`: строка до 1000 символов без NUL.
- Библиотека пишет обычными операторами SQL (§2.5): `insert … returning`, `update … set data = merge(data, $patch)` (+ `inc(…)`, `links_patch(…)`), `insert … on conflict (id) do update` (upsert), `delete`; проверяют триггеры базы. Строка ответа — `rowJson()` того же вида, что `to_jsonb` у чтения.
- Всё, что проверяется без базы, — `precheckPlan` до отправки первого оператора (маркеры `inc`, `no_key`, фильтр у create, ранняя проверка данных create/upsert валидатором на TypeScript): такая ошибка не ломает `db.begin()`. Ошибки, найденные после первого запроса плана, — ломают.
- `inc()` — маркер `Symbol.for('letopis.inc')`, из JSON его не получить; `splitPatch` вынимает маркеры, объект, опустевший после изъятия, не подставляется. `{"$inc": 5}` — данные.
- Правило числа строк (§2.5): update/delete/anonymize затронули меньше, чем нашёл шаг → `explainMissing`: невидимые — `target_not_found`, видимые с другим `rev` в строгом режиме — `conflict`, остальные — `acl_denied`. `{ rev }` — только при одной цели (`rev_ambiguous`, `target_not_found`).
- Концы create из пути (`pathEnds`): шаг-роль — своей ролью; непосредственный предшественник, на которого создаваемая строка не ссылается (переход вперёд), пропускается; из нескольких ролей — без занятых слотами, затем роль с именем класса шага, иначе `invalid_query`; шаг по базовому классу выбирает роль по классу найденной строки.
- «Уже существует» — код `exists`, id вычисляет `idOf`, а не текст ошибки сервера.
- Результат `delete({ confirm })` — надгробия этой транзакции после метки (`log.tx = pg_current_xact_id()`, `seq > mark`; xid8eq leakproof — индекс `(tx, seq)` работает под RLS) плюс строки без журнала из `returning`; превью — `delete_preview()` (то же правило `ref_action`, что у триггера).
- Продолжение плана: create и upsert — по строке результата, остальные глаголы — от всех строк сразу (`fromRows`); после удаления — от удалённых строк класса цели.
- `runTx` (пул): своё зарезервированное соединение (`begin read committed`, служебные `set_config` и первый запрос — конвейером, `.execute()`), а не `sql.begin`: после гибели серверного процесса (FATAL) или обрыва сокета `rollback` не шлётся, а закрытое соединение не возвращается в пул (`release()` в tx.ts) — иначе postgres.js 3.4 роняет процесс необработанным `TypeError` в `nextWrite`. Повтор при 40P01, 40001, конфликте `log_id_rev`; обрыв после тела операции — `commit_unknown`, без повтора. Чтение `letopis.changed` и `COMMIT` уходят одним конвейером (и в `ExplicitTx.commit`): обрыв на любом из них — `commit_unknown`.
- `ExplicitTx` (db.begin): зарезервированное соединение; ошибка любого запроса ломает транзакцию — каждый следующий вызов и `commit()` бросают исходную ошибку (тот же объект), `rollback()` проходит; ответ ROLLBACK на COMMIT — `tx_rolled_back`; 40P01 — с подсказкой повторить блок. `commit` и `rollback` идемпотентны.
- Батч (`execBatch`): подряд простые create/upsert одного класса с ключом из полей данных — одна многострочная вставка (`jsonb_to_recordset`), create — `on conflict do nothing` (пропущенный id → `exists`), upsert — повтор id режет группу; create класса без ключа — `Promise.all` однострочных вставок (конвейер postgres.js).
- Сигналы: `letopis.changed` читается перед фиксацией и уходит в `Notifier` (решение 9 точки А) — и в пуле, и в `ExplicitTx.commit`.
- Контекст транзакции (этап 5): `letopis.tenant` (рабочий арендатор) и пропуск прав `letopis.acl` из `AclPasses` (ключ — токен, актор, арендатор; 60 с); пропуска нет — `set_config('letopis.acl', acl_token())` тем же конвейером, и его используют запросы той же транзакции.

- Загрузчик (`load.ts`, §2.6): только администраторское подключение (`set local role` владельца, иначе `admin_required`); режим доверия убран (решение 2 точки А, охранник `removed`). Проход 1 — классы, id (v5 от ключа, `$ext` или случайная часть), повторы (`duplicates`); проход 2 пачками — умолчания и валидатор на TypeScript, концы и ссылки (id, `$key`, `$ext`, у полиморфного — `$class`), цели внутри загрузки; `COPY` в `entity` и `log` с явными списками колонок (`ENTITY_COLS`, `LOG_COLS`): вне списка — только `seq` (identity: умолчание `nextval` PostgreSQL пакетной вставке не мешает) и генерируемые `hash` и `ends`, их значения даёт база; остальные колонки, включая `tx`, загрузчик передаёт сам. В конце порции — один запрос по целям вне загрузки с `for key share`, проверка арендатора, сигнал, `ANALYZE` (≥ 10 000 строк).
- Ошибка загрузчика (класс `Issues`, `ISSUES_LIMIT = 100`): код первого нарушения; `detail` — `rows` (первые 100), `total` (все найденные, без предела), `truncated`, `limit`, `complete`. Нарушения ищутся поэтапно — проход 1, права на классы, пачки, запросы в конце порции, `verifyRows`; отмена после первого этапа с нарушениями, `total` — нарушения этого этапа. Цель вне загрузки, владелец и невидимая цель — одно нарушение на id (строка — первая ссылка). Текст «(и ещё K)» — точное число; если проверены не все строки (`unchecked`: не последняя порция `commitEvery` — `laterUnchecked`, в т. ч. в `explainTaken`; пачка с нарушениями после пачки, уже проверенной условиями ACL, — `aclRan`; `verifyRows` вернул `ISSUES_LIMIT` строк), текст — «(и ещё не меньше K: причины)» или «(возможно, не единственная: причины)», `complete: false`. Тест — `load` («отчёт ошибки…»).
- `existing`: `error` — без запросов на пачку, отказ даёт первичный ключ или `log_id_rev`, затем `explainTaken` называет `exists`/`deleted`; `skip`/`update` — существование для всей порции выясняется до проверок (пропущенный объект для ссылок — вне загрузки), `update` — новая версия одним оператором из заблокированных строк, удалённые — воскрешение с продолжением цепочки.
- postgres.js 3.4 теряет ошибку `COPY`, пришедшую после конца потока: `copyLines` перехватывает `reject` запроса до начала потока — без этого промис висит.
- Глаголы этапа 6: `restore`, `purge` — над удалёнными объектами шага (сами читают с withDeleted; живые без удалённых — `not_deleted`), `rekey` — функция `rekey()` базы, занятый ключ — `exists`.
- `$tags` и `$owner` строки (этап 7, импорт): теги — в `entity` и `log` (литерал `text[]` для COPY — `pgArray`), в `update` — `coalesce(u.tags, e.tags)`; владелец — аккаунт, не с `{ as }`, сверяется запросом в конце (`for key share`, из загрузки — живой `Account`), отказ — `target_not_found` со строкой. Режим истории: `existing: 'skip'` пропускает объект со всей историей (есть строка или журнал), `'update'` — отказ.
- Режим истории: версии волнами (волна — одна вставка `insert … returning hash`, не COPY) (`$rev` подряд от 1, `$at`, `$op`), после волны база отдаёт хэши — они `prev_hash` следующей; концы прошлых версий не сверяются.
- `commitEvery`: порции по группам классов в порядке зависимостей (Тарьян), цикл и класс со ссылкой на себя — целиком.
- `load({ as })` (этап 5): `acl_subject(аккаунт, арендатор)` — арендатор доступен, планы READ/WRITE; класс без права — `acl_denied` на строку, условия ACL на новые (и в `update` — прежние) значения — запрос на пачку (`acl_row_ok`), видимость целей — запрос в конце (`row_visible`); владелец по `ownerDefault`, автор — пользователь; режим истории с `as` запрещён. Всегда: `Account` — только в System, у `member` конец `Tenant` = арендатор; строки прав — `acl_bump()`; ошибки базы — `fromDbError`.
