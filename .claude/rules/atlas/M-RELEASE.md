# M-RELEASE — CI, тег, релиз, check-docs, check-package, контракт API (этапы 0, 8)

**Инварианты и грабли**
- Контур: push dev → `ci.yml` (typecheck, check:docs с check:semver, check:package без живого прогона; у сайта — typecheck, ER, покрытие, нюансы; сборки сайта нет — он не разворачивается). Тестов в CI нет — решение владельца 01.11.2026: `npm test`, примеры со снимками, песочница, сценарии сервисов, быстрый долгий прогон (шаг `soak`, 15 минут, M-BENCH) и живой прогон пакета идут локально до выкатки одной командой `npm run prerelease` (`prerelease.mjs`) | merge в main → `tag.yml` (аннотированный тег `v` + version) | publish Release → `release.yml` (заметки, `check:semver --release`, npm, проверка из реестра). На каждое событие ровно одно действие; на PR и main тесты не гоняются — допуск даёт зелёный ci последнего push в dev. Трасса — `docs/atlas/F-RELEASE.md`.
- Шаг `npm test` в `prerelease.mjs` — команда `scripts.test` из package.json (`testCommands`; другой вид скрипта — отказ) со вторым репортёром `scripts/test-reporter.mjs`: события раннера построчно JSON в `<лог>.events.jsonl`, с кодом выхода процесса файла (spec его не печатает). Под Windows процесс тест-файла изредка падает за доли секунды без вывода (`'test failed'` у самого файла, тестов нет; код 0xC0000409 — fail-fast; отчёты WER в системе выключены). Воспроизводится без tsx и без postgres.js: процесс `node --test`, открывающий TCP-соединения к 15433 (`localhost`, `127.0.0.1`, без `autoSelectFamily` — одинаково), под нагрузкой падает в ~0,15 % запусков; без сокетов, с tsx и графом `src` — ни разу на тысячах запусков (02.11.2026). В коде проекта не устраняется. Если все отказы шага такие (`crashedFiles`), каждый файл перезапускается по одному один раз (`rerun` шага, подстановки `{file}` и `{report}`): зелёный повтор засчитан, в итоге шага и в таблице `docs/checkpoint-*.md` — «перезапущен: <файл> (код выхода N)»; есть красный тест или файл, где тесты шли, — не перезапускается ничего. Тест — `prerelease.test.ts` (план 2.0, 7.8 №3); вложенный `node --test` из теста — без `NODE_TEST_CONTEXT`, иначе он не запускает файлы.
- Таблица итогов `prerelease.mjs` в `docs/checkpoint-<x.y.z>.md` копится (`report`, `parseReport`): после падения повторяют упавший шаг и следующие (`--only`, `--skip`), поэтому строки шагов прогона заменяются, а строки остальных остаются из прежней таблицы с меткой своего прогона — колонка «Прогон»: дата UTC (до минуты) и коммит. Порядок строк — порядок шагов до `--only` и `--skip`; строки шагов, которых в списке больше нет, уходят. Шапка — прогоны, чьи строки остались, последний первым; таблица прежнего вида (одна строка «Прогон …», четыре колонки) читается как один прогон. Два прогона одной минуты на одном коммите неразличимы — в шапке остаётся последний. Прогон без шагов итог не пишет. С `--steps` таблица пишется только в файл `--report=<файл>` (так её проверяет тест «план 2.0, 7.8 №3: --only и --skip не затирают таблицу итогов»).
- Версия одна на трёх местах: `lib/package.json`, верхняя `## [x.y.z]` в `lib/CHANGELOG.md`, обе строки version в `lib/package-lock.json` — сверяет `check-docs.mjs:checkVersion`. Тег берётся из package.json; тег уже есть → `tag.yml` молча пропускает (забытый бамп = нет релиза).
- Правила версий — README, «Версии и совместимость» (план 2.0): патч — только исправления без новой ревизии и новых отказов; минор — новое API и новая ревизия; мажор — удаление, переименование, новые отказы. `check-semver.mjs` строит контракт (`contract.mjs:buildContract`) и `DDL_REVISION` из текущего дерева и из тега прошлого выпуска (`git show`, `git ls-tree`) одним кодом и сравнивает: исчезли точка входа, экспорт, метод, код ошибки, сменились engines → мажор; появилось, выросла ревизия → минор; тексты ошибок → патч. Прошлый выпуск — наибольший тег `v*` меньше версии; тег текущей версии уже есть (версию ещё не подняли) — контракт обязан совпасть с ним (`--release` всегда берёт прошлый). Смену сигнатуры при том же имени скрипт не видит. Нужна полная история с тегами: в CI `fetch-depth: 0`, иначе выход 2.
- Версия с дефисом уходит в npm под dist-tag `next` (`release.yml#«Publish to npm»`), без дефиса — `latest`. Выпуск — только по команде владельца.
- На событии release workflow берётся из коммита тега: правка `release.yml` действует только с новым тегом.
- `docs/api-contract.json` руками не править: генерирует `gen-api-contract.mjs`: экспорты всех точек входа из `exports`; методы цепочки, корня и батча — поля `chain`, `db`, `batch` из массивов `types.ts`; коды ошибок (`codes`: `LT_NAMES`, `new LetopisError('…'`, `fail('…',`, `lt_fail('…'`, поля `code: '…'` — и в записях каталога сообщений `src/messages/*.ts`, их `contract.mjs` читает вместе с `src/*.ts`; собранные из переменных не видны); тексты ошибок из `src/*.ts` и `sql/*.sql` (литералы с префиксом `letopis: `; шаблоны каталога в них не входят); порядок — по кодовым единицам. Сборка — `contract.mjs:buildContract`: её же зовёт `check-semver.mjs` для тега. Концы строк с диска не важны (рабочая копия Windows с `core.autocrlf=true` — CRLF): `--check` сравнивает по LF, запись — с концами строк самого файла; так же сравнивает по LF `guide/scripts/gen-api.ts --check` (страницы справочника сайта).
- `check-docs.mjs` ничего не правит, БД не нужна; 14 сверок: ops (план 2.0, этап 3, п. 5: `gen-ops-tables.mjs --check` через `node --import tsx` — таблицы операторов между метками `<!-- ops -->` в `lib/README.md`, `lib/AGENT-CHEATSHEET.md` и главе «Чтение» сайта (`guide/pages/read/index.md`, без колонки MCP) == реестр `OPERATORS`; концы строк не важны); messages (каталог сообщений `lib/src/messages` грузит дочерний `node --import tsx`: у записей непустой шаблон ru, у подсказок — непустой текст; у каждого кода контракта — запись `codes.<код>` и якорь `<a id="код"></a>` в разделе «Ошибки» README — на него ведёт `LetopisError.docs`; ключи `lt_fail`, `lt_raise`, `lt_text` в `lib/sql` — из разделов `sql-*`); literals (литеральные тексты в `new LetopisError(код, '…')`, `fail('…')`, помощниках `invalid` и `bad`, прежних `lt_fail(имя, текст)`, `lt_raise(код, имя, текст)`, в `lib/sql` — любой `raise` уровня exception (и без уровня) с текстом в кавычках без `lt_text`/`lt_fail`/`lt_raise` и литерал `'problem', '…'` или `'problem', format('…'` находки; исключения — механизм `15-errors.sql` и служебный `'шлюз пройден'`; комментарии SQL не сверяются — только в файлах `PENDING_LITERALS`, сейчас пустом; переведённый файл из списка убирают, файл в списке без литералов — тоже красный); version; links (ссылки и упоминания `ИМЯ.md` из корневых `*.md`, `docs/*.md`, документов пакета `lib/*.md` и `lib/llms.txt`, трасс, карточек, хедеров бенча; CHANGELOG — нет, это история; якоря `#…` — по слагам GitHub); text (нет управляющих символов: байт NUL делает файл «двоичным» для grep); paths (пути от корня в обратных кавычках в `docs/checkpoint-*.md` существуют, маски и `<…>` пропускаются); test-list (раздел «Тесты» `lib/README.md`); revision (`99-revision.sql` == `DDL_REVISION`); bench (`node --check`); api-contract; semver (`check-semver.mjs`); reserved (раздел «Зарезервированные имена» и case-метки Proxy); structure (разделы `## N.` README подряд и все в оглавлении). Разделы README ищутся по заголовку, не по номеру. Упоминание несуществующего `ИМЯ.md` в любой карточке или трассе — красный CI.
- Документация пакета — в `lib/`, только на русском (английский снят в 2.0.0): `README.md` (руководство по задачам), `AGENT-CHEATSHEET.md`, `llms.txt`, `CHANGELOG.md` — все в поле `files`. Примеры README, шпаргалки и корневого README исполняет тест `docs` (`lib/test/docs.test.ts`).
- `check-package.mjs` — один скрипт для dev (тарбол из `npm pack`) и релиза (`--registry=<v>`): основная точка входа грузится без peer-зависимостей (Zod нужен только `letopis/model`), каждый экспорт из контракта импортируется, установленная команда `letopis --help` печатает справку (`npm exec --no -- letopis`; на Linux это симлинк из `node_modules/.bin`), состав тарбола == поле `files` (обязательно README.md, CHANGELOG.md, LICENSE, AGENT-CHEATSHEET.md, llms.txt), без `test`, `scripts`, `bench`, `docker`, `src` и файлов тестов; живой прогон (`live`: `up`, вход сервисом, `load`, запись и чтение в свежей схеме `v2.pkgcheck_…`, затем схема удаляется) — строка — `ENTITY_DSN` (по умолчанию порт 15433); обязателен при `LETOPIS_PKG_LIVE=1`/`--live` (CI, release.yml — там свой сервис `postgres:18`), без переменной — пропуск с предупреждением, если база не отвечает; `=0`/`--no-live` — выключен.
- `--registry`: свежую версию `npm view` видит раньше, чем `npm install` (метаданные для установки) — установка повторяется при ETARGET/E404 до 20 раз через 15 с с `--prefer-online` (на 1.0.0 шаг `release.yml` упал ложно).
- Тело релиза — секция CHANGELOG текущей версии (`release-notes.mjs:section`), не описание PR: на release-событии `GITHUB_TOKEN` не видит PR-API. Относительные ссылки секции скрипт переписывает в абсолютные на `lib/` в main — на странице PR и релиза относительная ссылка мертва. Метки «Источник: …» у правок ядра (тест, пример, сервис, ревью, soak, внедрение) он считает и дописывает строку метрики стабилизации (план 2.0: цель — две версии подряд без правок ядра, найденных примерами и сервисами).

**Что ещё менять вместе**
- Изменились экспорты, методы цепочки, коды или тексты ошибок — `cd lib && npm run api:contract` в том же коммите; изменение требует шага версии по README «Версии и совместимость» — поднять версию (первая правка цикла открывает запись `x.y.z-alpha.0` в CHANGELOG), иначе красный `check:semver`.
- Меняется способ создавать ошибки — шаблоны `codesOf` в `contract.mjs`, иначе коды «исчезнут» и `check:semver` потребует мажор. Каталог сообщений (план 2.0, этап 3) уже учтён: место на `lerr('ключ')` берёт код из поля `code` записи в `src/messages/*.ts`. Каталог переехал из файлов — поправь `source.list('src/messages', …)` в `buildContract`.
- Перевели файл на ключи каталога — убрать его из `PENDING_LITERALS` в `check-docs.mjs` (своя строка раздела).
- Изменился реестр `OPERATORS` — `cd lib && npm run ops:tables` в том же коммите (таблицы операторов в README, шпаргалке и главе «Чтение» сайта), иначе красный `check:docs`.
- Новый тест-файл — строка в разделе «Тесты» `lib/README.md`; новый метод цепочки/корня — раздел «Зарезервированные имена» README и `types.ts` (`CHAIN_METHODS`, `DB_METHODS`, `BATCH_METHODS`).
- Изменили помеченный пример README или шпаргалки — тест `docs`, а обещанные в комментариях результаты — `*_EXPECT` в `docs.test.ts`.
- Новая проверка или шаг workflow — шапка скрипта/workflow, `docs/atlas/F-RELEASE.md`, раздел «Процессы» в `AGENTS.md`.
- Изменилось поле `files` или `exports` в package.json — `check-package.mjs` проверит; контракт перегенерировать.

**Проверка**
- `cd lib && npm run check:docs` — все сверки без БД.
- `cd lib && npm run check:semver` — шаг версии против прошлого выпуска; тест `semver` (план 2.0, 7.8 №1) проверяет сам скрипт на деревьях-копиях (`--base-dir`, `--current-dir`).
- `cd lib && npm run prerelease` — полная локальная проверка перед пушем и выпуском.
- `cd lib && npm run check:package` — тарбол как в CI.
- `cd lib && node scripts/release-notes.mjs` — тело будущего релиза.
- Workflows тестами не покрыты.

**Точки входа**
- `lib/scripts/check-docs.mjs:checkVersion` — версия, lock, LICENSE
- `lib/scripts/check-docs.mjs:checkLinks` — мёртвые ссылки и якоря в документах
- `lib/scripts/check-docs.mjs:checkMessages`, `:checkLiterals` — каталог сообщений и литеральные тексты ошибок
- `lib/scripts/check-package.mjs` — проверка пакета (dev и реестр)

- `lib/scripts/contract.mjs:buildContract` — сборка контракта из дерева (файлы или тег)
- `lib/scripts/check-semver.mjs` — шаг версии против прошлого выпуска
- `lib/scripts/prerelease.mjs` — полная локальная проверка; `:crashedFiles`, `:rerunCrashed` — повтор файла, упавшего до первого теста; `:report`, `:parseReport` — таблица итогов и её слияние с прежней

- `lib/scripts/release-notes.mjs:section` — секция CHANGELOG версии
- `.github/workflows/release.yml#«Publish to npm»` — dist-tag `next` для предрелизов
