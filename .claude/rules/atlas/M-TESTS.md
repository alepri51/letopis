# M-TESTS — тесты: обвязка, наборы, тестовые данные

**Инварианты и грабли**
- Подключение решает, что проверяет тест: `as()` — прикладная роль `letopis_test_app`, права и RLS как у приложения; `asAdmin` — администраторское подключение с сессией: триггеры срабатывают, RLS нет, `admin_role()` открывает все права `letopis.*`; `asOwner` — роль владельца: ни триггеров, ни RLS. Права и RLS проверяет только прикладная роль (`as()`, `hold()`, `connect` с `appDsn()`).
- `e.tenant()` выдаёт `sys_grant_all` — READ, WRITE, DELETE на строки арендатора, но не права `letopis.*`; тест прав — на `tenant(имя, { bare: true })` и помощниках `_access.ts`. Производный класс (`derivedBy`) — через `defineDerived`: `defineClass` от прикладной роли получит `acl_denied` (нужно право letopis.projector).
- Без пауз по времени. Гонка: `hold(token, шаг)` держит транзакцию A открытой, операцию B запускают промисом без await, `waitForLock(e.sql)` ждёт, пока B встанет на блокировку, затем `finish(true|false)`; порядок задаёт `waitForLock`, а не `Promise.all` (С15 в `scenario-real-life.test.ts`). Событие подписки — ожидание с таймаутом (`take` в `watch.test.ts`); у подписки `'now'` запись — только после `await sub.ready()`, иначе событие может не прийти. Замер времени — пары вперемешку и медианы (5.2 в `auth.test.ts`).
- `waitForLock` считает ожидающих блокировку во всей базе, а не в схеме файла: при параллельном прогоне файлов засчиталось бы чужое ожидание; прогон — по одному файлу (`--test-concurrency=1`).
- Пул прикладной роли — 16 соединений (`appSql(16)`): удерживаемая транзакция занимает соединение; при малом пуле B ждёт свободное соединение, а не блокировку, и `waitForLock` её не дождётся.
- postgres.js: объект в параметр `::jsonb` — как есть, без `JSON.stringify` (иначе двойное кодирование); скаляр (`true`, число) — `JSON.stringify` и `$1::text::jsonb`.
- Текст запроса с `${S}` не собирать на уровне модуля: схема известна только после `before`.
- `engine()` ставит схему с `allowReset: true`: без флага `reset()` и `maintain({ now })` отказывают (`reset_disabled`) — своя установка в тесте (`install`, `up`) для них тоже с флагом. `reset({ level: 'all' })` стирает данные и меняет ключ сервиса: сессии `e.tenant()` и `e.serviceKey` после него не действуют — такой тест ставят последним в файле или дают ему свою схему.
- Отказ проверяется конкретным исходом — `lt('имя')` или `lt('КОД05')`, а не любым исключением.
- Тест на исправление безопасности обязан падать без исправления — проверяют, отключив исправление (`docs/checkpoint-1.2.md`). В имени теста — номер кейса тест-плана или атаки (`№57`, `7.3 №12`, `С15`): на номера ссылаются планы и `docs/checkpoint-*.md`; новая атака в `engine-attacks.test.ts` — следующий номер, прежние не перенумеровывать.

**Что ещё менять вместе**
- Новый тестовый файл → строка `# <имя> — …` в разделе «Тесты» `lib/README.md` и «Tests» `lib/README.en.md` (сверяет `check-docs`).
- Новая миграция (`lib/sql/migrate/`, `DDL_REVISION`) → ожидания `upgrade.test.ts`: схему там ставят прежние пакеты (dev-зависимости `letopis-1`, `letopis-11`, `letopis-141`), тест сверяет их ревизию, список `migrations` и предупреждения `connect()`.
- Выпуск → в следующем цикле dev-зависимость `letopis-<версия>` (точная версия, `npm:letopis@x.y.z`) и сценарий «прошлый выпуск → текущая» в `upgrade.test.ts` (правило плана 2.0: каждый выпуск проверяет накат с предыдущего); у той же ревизии — обычный `up()` без миграций, предупреждение `connect()` о штампе — только если SQL менялся.

**Проверка**
- `cd lib && npm test` — весь набор; один файл — `cd lib && npx tsx --test --test-force-exit test/<файл>.test.ts`.
- `cd lib && npm run typecheck` (тесты входят) и `npm run check:docs` (список тестов в README).
