# M-TESTS — тесты: обвязка, наборы, тестовые данные

**Инварианты и грабли**
- Подключение решает, что проверяет тест: `as()` — прикладная роль `letopis_test_app`, права и RLS как у приложения; `asAdmin` — администраторское подключение с сессией: триггеры срабатывают, RLS нет, `admin_role()` открывает все права `letopis.*`; `asOwner` — роль владельца: ни триггеров, ни RLS. Права и RLS проверяет только прикладная роль (`as()`, `hold()`, `connect` с `appDsn()`).
- `e.tenant()` выдаёт `sys_grant_all` — READ, WRITE, DELETE на строки арендатора, но не права `letopis.*`; тест прав — на `tenant(имя, { bare: true })` и помощниках `_access.ts`.
- Без пауз по времени. Гонка: `hold(token, шаг)` держит транзакцию A открытой, операцию B запускают промисом без await, `waitForLock(e.sql)` ждёт, пока B встанет на блокировку, затем `finish(true|false)`; порядок задаёт `waitForLock`, а не `Promise.all` (С15 в `scenario-real-life.test.ts`). Событие подписки — ожидание с таймаутом (`take` в `watch.test.ts`); у подписки `'now'` запись — только после `await sub.ready()`, иначе событие может не прийти. Замер времени — пары вперемешку и медианы (5.2 в `auth.test.ts`).
- `waitForLock` считает ожидающих блокировку во всей базе, а не в схеме файла: при параллельном прогоне файлов засчиталось бы чужое ожидание; прогон — по одному файлу (`--test-concurrency=1`).
- Пул прикладной роли — 16 соединений (`appSql(16)`): удерживаемая транзакция занимает соединение; при малом пуле B ждёт свободное соединение, а не блокировку, и `waitForLock` её не дождётся.
- postgres.js: объект в параметр `::jsonb` — как есть, без `JSON.stringify` (иначе двойное кодирование); скаляр (`true`, число) — `JSON.stringify` и `$1::text::jsonb`.
- Текст запроса с `${S}` не собирать на уровне модуля: схема известна только после `before`.
- Вместо снятой в 2.0.0 проверки целостности базой журнал в тестах гонок и сценариях сверяет `lib/test/_engine.ts:journalIssues` (номера версий подряд с 1, строка `entity` — последняя версия у класса с журналом). Сброса установки нет: схема «заново» — `install(…, { fresh: true })` (образец — `emptyB` в `initial-load`).
- Отказ проверяется конкретным исходом — `lt('имя')` или `lt('КОД05')`, а не любым исключением.
- Тест на исправление безопасности обязан падать без исправления — проверяют, отключив исправление (`docs/checkpoint-1.2.md`). В имени теста — номер кейса тест-плана или атаки (`№56`, `7.3 №12`, `С15`): на номера ссылаются планы и `docs/checkpoint-*.md`; новая атака в `engine-attacks.test.ts` — следующий номер после наибольшего когда-либо занятого (№57; номера атак, снятых в 2.0.0 вместе с производными классами, агрегатами, проверкой целостности (№19) и сменой класса (№42), заново не занимают), прежние не перенумеровывать.

**Что ещё менять вместе**
- Новый тестовый файл → строка `# <имя> — …` в разделе «Тесты» `lib/README.md` (сверяет `check-docs`).
- Правило плана 2.0 «каждый выпуск проверяет накат с предыдущего» действует с 2.0: тест наката со схем 1.x снят в 2.0.0 вместе с совместимостью (схему 1.x 2.0 не обновляет — `up.test.ts`, «план 2.0, 7.10 №5»). Следующий выпуск 2.x проверяет накат с 2.0: в его цикле — dev-зависимость прошлого выпуска (точная версия, `npm:letopis@x.y.z`) и тест-файл со сценарием «прошлый выпуск → текущая»: схему ставит прежний пакет, данные пишет прежний движок, затем `up()` текущей версии; у той же ревизии — обычный `up()` без миграций, предупреждение `connect()` о штампе — только если SQL менялся; у новой ревизии — `up({ upgrade: true })`, тест сверяет ревизию, список `migrations` и предупреждения `connect()`. Дальше — так же на каждый выпуск.
- Новая миграция (`lib/sql/migrate/`, `DDL_REVISION`) → сценарий наката в этом тесте; механизм миграций без прежнего пакета проверяет `up.test.ts` («6.10 накат миграций 2.x»: `install()` с `migrateFrom`).
