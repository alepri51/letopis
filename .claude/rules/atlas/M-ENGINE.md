# M-ENGINE — таблицы, триггеры записи, классы, журнал, хэши, verify

**Инварианты и грабли**
- Ровно три таблицы: `entity`, `log`, `secret` (`10-core.sql`). Индекс журнала `log_ends` — GIN по выражению `link_ids(links)` (ревизия 5, срез по переходу — M-QUERY); выражение вычисляется пишущей ролью, как `entity.ends`. Колонки `ends` и `hash` генерируемые; `hash = sha256(prev_hash || snapshot(...))`. Генерируемые колонки вычисляются с правами пишущей роли — у `letopis_app` есть EXECUTE на `link_ids`, `snapshot`, `version_hash`; без него любая вставка приложения падает 42501.
- Триггеры `entity` — `when (current_user <> '<владелец>')` и `enable always`. Триггерные функции — `security definer`, поэтому всё, что они пишут сами (каскад, пересчёт потомков, `sys_update`, `move_row`), триггеры не перепроверяют: эти функции обязаны сами писать журнал (`log_version`) и сигнал (`signal`).
- Решение 2 точки А (этап 4): строковые триггеры BEFORE только разбирают концы (`links_shape`, без запросов к таблицам); цели проверяет и блокирует `for key share` триггер после оператора — `targets_bad()` один раз на цель за оператор, проверка идёт после блокировки по свежим строкам (удалённая или переведённая в чужой класс цель не пройдёт). Журнал пишут триггеры после оператора `entity_ai`/`entity_au` по переходным таблицам одной вставкой; пустая правка (тот же `rev`) версии не даёт. Надгробия каскада — одной вставкой на уровень. Переходные таблицы заполняются и для владельца (условие WHEN триггера после оператора на это не влияет) — замер: загрузчик не замедляется.
- `class_row(имя, арендатор)` ищет по частичному индексу `entity_class_name ((data->>'name'), tenant) where class = 'Class'`, без v5 (было 40 мкс на поиск, стало 11).
- Тест и сид пишут мимо триггеров только под `set role letopis_owner` (`asOwner()` в `_engine.ts`); суперпользователь без `set role` — тоже «не владелец», триггеры для него срабатывают.
- Пустая правка (`trg_entity_bu`) возвращает OLD, а не NULL: строка считается затронутой, версии и сигнала нет (AFTER-триггер сравнивает `rev`). На этом держится разбор `{ rev }` и правило числа затронутых строк этапа 4.
- Удаление — триггер ПОСЛЕ оператора с `old table as gone`; каскад по уровням (`delete … returning` в порядке id, затем поиск ссылок), `restrict` — один запрос по итогу (`delete_restricted`, LT017). Только `read committed` (статементный BEFORE-триггер). Действие со ссылающейся строкой решает `ref_action()` — общая с превью `delete_preview()` (функция владельца; цели и выдача — через `row_visible()`, как у `find_*`), поэтому превью не расходится с удалением.
- Права в записи (этап 5): `targets_bad(…, p_acl)` — цель видна актору (кроме `Account`); владелец — существующий аккаунт (разрешает ли — политика вставки); `trg_entity_ad` — `DELETE` на каждую строку каскада, `WRITE` на снятие конца, выход из членства — `owner_to_tenant` (индекс `entity_owner`), удаление аккаунта — `auth_kill` и удаление кредов; `trg_entity_au` — отключение аккаунта гасит сессии; `Account` — только в System, конец `Tenant` у `member` = арендатор строки; строки прав — `acl_bump()`; `verify` — право `letopis.verify` (правила System); `visible_detail` — по `row_visible`.
- Слоты концов — `links_patch(links, ops)` (set, unset, add, remove над свежей строкой); `merge`, `inc` и `links_patch` выданы приложению — сырой SQL пишет ими же.
- Блокировки семейства: `family_lock(корень, exclusive)` — форма advisory с двумя int4 (19540, hashtext), отдельное от пользовательского `lock()` (bigint) пространство. Писатели — разделяемая, ужесточение класса — исключительная; описание класса перечитывается после взятия блокировки.
- `fields` описания класса — `properties`, `required` и (этап 4) `anyOf`/`oneOf` — условия по нескольким полям; в `resolved.schema` они ложатся в корень, потомок заменяет их целиком (`class_resolve`).
- Строка `Class`: `class_admit` (system только у установки, имя не совпадает с системным, связь не называется методом цепочки, конец однозначен во всей схеме) + `class_prepare` (метасхема, ключ, unset, политика хранения). Пересчёт потомков и проверка строк семейства — `class_evolve` из триггера после оператора `entity_au`; «безопасность» изменения решает `class_change_safe`.
- Воскрешение: номер версии и `prev_hash` продолжаются от последней записи журнала, она берётся `for update` (этап 6: с `purge`, обрезкой и `restore` того же id); параллельные удаление и создание одного id сталкиваются на `log_id_rev` (23505) — повтор проходит.
- Смена класса: сырой `update set class` — только классы без ключа (иначе `use_reclass`); `reclass()` переносит строку на новый id через `move_row` (рекурсивно для ссылающихся строк, если конец входит в их ключ), журнал связывает id колонкой `moved`: первая версия нового id — вид `reclass`/`rekey` и `moved` = старый id, надгробие старого — всегда вид `delete` и `moved` = новый id (по `op = 'delete'` срез asOf и withDeleted отличают удалённый id).
- `reserved_names()` — текст функции с маркером `@RESERVED_NAMES@`: список подставляет установщик из `RESERVED_CLASS_NAMES` (`lib/src/types.ts`).
- Коды ошибок — только через `lt_fail(имя, …)` по `error_catalog()` (`15-errors.sql`); `merge` и `inc` выполняются от приложения и бросают ошибку напрямую (lt_raise приложению не выдан).
