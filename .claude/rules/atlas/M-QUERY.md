# M-QUERY — поиск id под RLS (find_*) и построитель чтения

**Инварианты и грабли**
- Видимость в `find_*` (этап 5): `row_visible(…, owner, tags, data, links, c_tenant, c_account, c_plan)` с планом `acl_actor('READ')` (пропуск `letopis.acl` или расчёт); подзапросы `find_*` выбирают эти колонки.
- Под RLS индексы GIN приложению недоступны (`@>` не leakproof). Шаг из двух частей: функции владельца `find_ids()`, `find_hop()`, `find_deep()` ищут id по индексам без RLS и сами применяют видимость `row_visible()` — копию условия политик `entity_select`/`log_select` (`50-acl.sql`); строки читаются по первичному ключу под RLS. Менять видимость — в обоих местах; расхождение ловит `find-ids-parity`.
- `find_hop`/`find_deep` пробуют `entity_ends` на каждый id через `lateral (… offset 0)`, а класс, видимость, data и роли проверяют после пробы. Без `offset 0` подзапрос поднимается в общий план, и планировщик по плохой оценке меняет пробы на перебор таблицы; пересечение пробы с индексами (class, tenant) или data перебирает весь класс (замер `bench/chain-read.mjs`).
- Срез журнала по переходу и deep (`asOf`, withDeleted; ревизия 5) — `log_refs_at(классы, источник, момент)`: кандидаты — версии, ссылавшиеся на источник (GIN `log_ends` по `link_ids(links)`), затем последняя версия каждого кандидата среди версий этих классов не позже момента (`log_id_rev`), ссылку проверяет она — та же семантика, что «последняя версия класса на момент, затем ссылка», но без перебора всех версий класса (бенч этапа 7: 3,37 с → 0,22 с). Ветка `find_ids` с условием на концы — от первой цели тем же помощником; без ссылки (только класс) срез по-прежнему перебирает версии класса (`log_class_at`).
- Узлы читаются через `lateral` по списку id (`entityByIds`), версии журнала — по паре (id, rev): так планировщик видит число строк и не переходит на перебор.
- Без возвратов к узлам (pivot) последний узел уже содержит ровно сущности полных путей — rows, ids, count, агрегаты и versions читают его без соединения путей; paths и цепочки с pivot соединяют `n0 ⋈ p1 ⋈ n1 …`.
- Значения — только параметрами (списки — одним массивом), неиспользованный параметр PostgreSQL не примет — параметры поиска ленивые. Текст запроса зависит только от формы цепочки → подготовленный оператор postgres.js (`prepare: true`).
- Записи журнала `purge`, `trim`, `reset` (этап 6) — не версии: срезы и withDeleted их пропускают. `versions({ follow: true })` — рекурсия по `moved` (индекс `log_moved`), порядок по времени.
- Переход: шаг-роль — своим концом (`resolveHop`); иначе концами всех классов обоих семейств без ограничения ролей — допустимость гарантирует целостность ссылок. Надгробие в журнале всегда `op = 'delete'` (по нему asOf и withDeleted отличают удалённый id).
- Время в ответе — UTC: `runTx` выставляет `TimeZone` на транзакцию; `asOf` и курсор по `at` передаются `::text::timestamptz` (Date в postgres.js режет микросекунды).
- Курсор `after()` проверяется до запроса (`sql.ts:cursorParams` по `SortSpec` из `sortSpec`: `field`, `type`, `nullable`; ожидания для текста ошибки — `CURSOR_EXPECT`): не объект, нет `v`, `id` не uuid или значение не того типа — `invalid_query`, а не ошибка приведения сервера (22P02, 22007, 42883) и не запрос, повисший на `undefined` в параметре. Типы: числовое — конечное число, `rev` — целое int4, логическое — `true`/`false`, текст — строка без `\0`, uuid и `id` — uuid, время и `at` — ISO с поясом, дата — `ГГГГ-ММ-ДД` (проверка календаря — `dateOk`), лист без описания (`jsonb`, сравнение текстом `->>`) — строка, число или логическое, уходит строкой; `null` — только у полей `data.*`. Курсор того же типа с другого поля не отличить.
- Известное ограничение keyset: строка с `null` в поле сортировки (или без поля) не проходит сравнение `(expr, id) > ($v, $id)` — `after()` её теряет, а курсор `null` даёт пустую страницу (README §18).
