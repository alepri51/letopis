# M-BENCH — замеры точки А, бенч против 0.21 и против 1.0.1 (этапы 1, 7; план 1.1, этап 0)

**Инварианты и грабли**
- Скрипты — через tsx (`cd lib && npx tsx bench/<имя>.mjs`): импортируют исходники `src/*.ts`; масштаб — `BENCH_SCALE` (0.1 — в десять раз меньше); итог — `bench/results/<имя>.json` (`save` в `_core.mjs`). Серии точки А (`core-*`, `chain-read`, `acl-cost`) — своя схема `v2.b_<имя>`, сводка — `docs/checkpoint-a.md`.
- 0.21 — пакет `letopis-0` на контейнере `letopis-timescale` (порт 15432, `LETOPIS_021_DSN`); `up()` 0.21 сам поднимает контейнер. 1.0 — `letopis-pg18` (порт 15433), поднимает обвязка тестов.
- Полигоны (этап 7): `salon-data.mjs` — дословный `makeRows` 0.21 и перевод строк в загрузку 1.0 на демо-домене (`toLoad10`: роли `Parent`, `Item`, `Part`; совпавшие старты записей мастера сдвигаются на минуты; явный null опускается); `seed-021.mjs` — засевка 0.21 сырыми вставками, как скрипты 0.21; `polygons.mjs` — 1.0 загрузчиком в арендаторах (правило «можно всё»), порциями ~100 тыс. строк по границам объектов (`loadChunks`: цели раньше ссылающихся — порядок генератора), клиенты tenants — по 50 тыс.; сверка объектов и версий по классам с генератором 0.21 (§7.9 №7.7).
- `import-salon.mjs` (`npm run test:import-salon`) — §7.9 №7.6: засевка 0.21, `up({ fresh })` 1.0, импорт с `--keyless booking` (полигон 0.21 писался мимо v5), сверка объектов и версий по классам и `verify()`, код 1 при расхождении. Импорт держит источник в памяти целиком (полный полигон — ~980 тыс. строк): при нехватке памяти процесс снимается.
- `compare.bench.mjs` — §7.9 №7.8: те же полигоны в обеих версиях, p50 после прогрева; таблица — `results/compare.md` (в README — раздел «Производительность», обе версии). В 0.21 нет `reclass`; там полигон salon — у System без изоляции (`enforceAccount: false`).
- `vs-101.bench.mjs` — бенч против 1.0.1 (план 1.1, этап 0, п. 4; точки А и Б): сторона 1.0.1 — пакет `letopis-1` (`npm:letopis@1.0.1`, версия закреплена точно), сторона текущей версии — исходники; полигон salon строит `polygons.mjs:seedSalon10` с параметром `lib` (`up` и `connect` стороны), схемы `v2.vs101_old` и `v2.vs101_new`. Перед замерами `vacuum (analyze)` обеих схем, порядок сторон чередуется от замера к замеру; `maintain` меряется фиксированным числом пачек: пачка прореживания берёт до 100 объектов, и полный проход по журналу полигона (около 540 тыс. объектов) слишком долог для бенча. Пока код не менялся, разница сторон — шум замера. Итог — `results/vs-101.{json,md}`, схемы удаляются (`BENCH_KEEP=1` — оставить).
- `history.bench.mjs` — `blame` и `diff` по 1000 и 10 000 версиям (план 1.1, этап 1, п. 5; решение о колонке изменённых путей): схема `v2.b_history` (`setup`), версии — циклом правок сырым SQL от приложения; итог — `results/history.json`, сводка — `docs/checkpoint-1.1.md`.
- Строки полигонов не держать между замерами (только число и время): память.
- `BENCH_REUSE=1` — бенч на уже засеянных полигонах (скорость загрузки — из `results/polygons.json` и прошлого `compare.json`); схемы старой ревизии — `up({ schema, upgrade: true })` перед замером.

**Что ещё менять вместе**
- Новый скрипт — `check-docs` проверяет только синтаксис (`node --check`) и мёртвые ссылки в шапке; импортируемые имена и типы не проверяются (у `tsconfig` нет `allowJs`), поэтому бенч надо хотя бы раз прогнать (`BENCH_SCALE=0.1`).
- Изменились цифры — раздел «Производительность» README (обе версии) и отчёт точки.
