# M-BENCH — бенчи и замеры

**Инварианты и грабли**
- Запуск — только через tsx (`cd lib && npx tsx bench/<скрипт>`): скрипты импортируют исходники `lib/src/*.ts`, а не сборку. Масштаб — `BENCH_SCALE` (0.1 — в десять раз меньше).
- Один замер на одном коде расходится между прогонами на десятки процентов (против 1.0.1: построчный `create` −7…+25 %, чтение по ключу −8…+39 % — `docs/checkpoint-1.2.md`, «Бенч против 1.0.1»). Разницу сравнивать с разбросом, а не с одним прогоном. Поэтому повторяемые замеры идут кругами `BENCH_ROUNDS`: порядок сторон или вариантов чередуется, в итоге — медиана; в `vs-101` перед замером стороны — `CHECKPOINT` (иначе контрольная точка базы доставалась одной стороне).
- Не гонять параллельно с тестами и другими бенчами: та же база, что у тестов (`ENTITY_DSN`, по умолчанию `letopis-pg18`, порт 15433; контейнер поднимает `ensureDatabase` обвязки). Первый прогон против 1.0.1 на точке Б шёл, по всей видимости, одновременно с тестами. Бенч в начале пересоздаёт свою схему: второй экземпляр того же бенча сносит данные первому.
- Быстрый прогон перезаписывает закоммиченный итог полного масштаба, на котором стоят цифры README и сводок, — такой итог не коммитить (масштаб — поле `scale` итога).
- Долгий прогон `soak.mjs` (план 2.0, этап 2; `npm run soak`): нагрузка и замеры — одним процессом, в конце критерии §7.7 и `verify({ data: true })`, код 1 — критерий нарушен. Ярус `all` не короче суток (`lib/sql/40-class.sql`), поэтому старую историю засевают загрузкой с `withHistory` (20 счётчиков × 500 версий за 10 дней) — иначе прореживать нечего. Heap — после принудительной сборки (`v8.setFlagsFromString('--expose-gc')`): без неё наклон за короткий прогон — шум сборщика. Вход по коду кончается выходом (`revokeAll`): сессия по коду живёт 7 дней, и без выхода SESSION росла бы весь прогон. Строки-замки удалённых классов считает тот же разбор имени, что в `maintain()` (`ORPHAN_LOCKS`; формат — `family_name`). Быстрый режим (`SOAK_HOURS=0.25`) — шаг `soak` prerelease с `SOAK_OUT` в каталоге логов: закоммиченный суточный итог не перезаписывается.
- `vs-101` «maintain: 20 пачек» меряет удаление по засеянной старой истории: 2000 клиентов по 12 версий четырёхлетней давности, ярус `all` — 3 года, длиннее возраста полигона salon (год истории до 2025-08-01). `thin_batch` берёт объекты по порядку id, до 100 за пачку, и только со старыми версиями — поэтому 20 пачек приходятся ровно на засеянные объекты. Без засева у объектов полигона нечего прореживать (первую и текущую версию прореживание не трогает): прежний замер давал 0 версий — мерил просмотр.
- Память: строки полигона не держать между замерами (только число и время), грузить порциями (`lib/bench/polygons.mjs:loadChunks`). `import-salon` держит источник 0.21 целиком (M-IMPORT): на полном полигоне процесс может быть снят по памяти.

**Что ещё менять вместе**
- Бенчи правят объекты базы по тексту и имени: `core-write` — `create or replace` функций `validate_data`, `targets_bad`, `trg_entity_ai`, `signal_raw` (вариант `noLog` — упрощённая копия `trg_entity_ai` без вставки в журнал); `core-concurrency` и `core-notify` — фрагменты `perform pg_notify` в `signal_raw` и `order by t.id for key share;` в `targets_bad`; `family-lock` — свои варианты `family_lock` на `family_name`, `lock_id`, `lock_row`; серия 4 `derived` — триггеры `entity_total_ai`, `_au`, `_ad`; `gencols` — сверка кандидатов с `link_ids` и `snapshot`. Сменились сигнатура, фрагмент, имя или шаги триггера в `lib/sql/` → поправить бенч. Пропажу фрагмента или имени видно только прогоном (`patchFunction` бросает «нет фрагмента»), а `create or replace` с новой сигнатурой в `core-write` молча заводит перегрузку — вариант ничего не отключает.
- Новый или изменённый скрипт: `check-docs` проверяет только синтаксис (`node --check`) и ссылки в шапке; имена и типы импортов не проверяет никто (`.mjs` без `allowJs` в `lib/tsconfig.json`) — прогнать хотя бы раз с `BENCH_SCALE=0.1`.
- Изменились цифры — раздел «Производительность» `lib/README.md` и `lib/README.en.md`, раздел бенча в `docs/checkpoint-*.md` (серии `core-*`, `chain-read`, `acl-cost` — `docs/checkpoint-a.md`).

**Состояние и побочки**
- Итог — `lib/bench/results/` (JSON с масштабом, версией сервера и `shared_buffers`). `BENCH_SERIES` у `derived` (серия 3 — только с 2) и `BENCH_RUNS` у `initial-load` пишут итог частичного прогона в отдельный файл, полный не трогают; `BENCH_ONLY` у `core-write` сливает снятые части с прежним итогом. Частичные итоги (derived-23, initial-load-regular-initial) и сводный vs-101-1.2.md, который бенч не пишет, цитируют сводки и CHANGELOG — не удалять.
- Схемы: серии — `v2.b_<имя>` (`gencols` и `initial-load` ставят свою сами), полигоны — `v2.salon` и `v2.tenants`, против 1.0.1 — `v2.vs101_old` (пакет `letopis-1`, `npm:letopis@1.0.1`, версия закреплена точно) и `v2.vs101_new`. 0.21 — пакет `letopis-0` на `letopis-timescale` (порт 15432, `LETOPIS_021_DSN`), контейнер поднимает `up()` 0.21.
- Схема удаляется в конце; `BENCH_KEEP=1` — оставить (где поддержано); `v2.b_soak` долгого прогона остаётся для разбора и пересоздаётся следующим прогоном. `BENCH_REUSE=1` у `compare` — на засеянных полигонах (скорость загрузки — из прошлых итогов `polygons` и `compare`); полигон старой ревизии — сначала `up({ schema, upgrade: true })`.

**Проверка**
- `cd lib && BENCH_SCALE=0.1 npx tsx bench/<скрипт>` доходит до итога; правильность, а не скорость, — `checks` в итоге `derived` (расхождений balance 0, `verify` чист) и `mismatches` в итоге `gencols` (нули). `cd lib && npm run check:docs` — синтаксис и ссылки шапок; `cd lib && npm run test:import-salon` — код 1 при расхождении импорта с полигоном 0.21.

**Точки входа**
- `lib/bench/_core.mjs:setup` — схема серии: установка, арендатор с сессией, классы
- `lib/bench/_core.mjs:save` — запись итога
- `lib/bench/polygons.mjs:seedSalon10` — полигон salon; `lib` — сторона бенча против 1.0.1
- `lib/bench/salon-data.mjs:toLoad10` — строки 0.21 → загрузка 1.x
- `lib/bench/core-concurrency.mjs:patchFunction` — подмена функции базы по фрагменту
- `lib/bench/vs-101.bench.mjs:measure` — круги, чередование сторон, медиана
- `lib/bench/soak.mjs` — долгий прогон: нагрузка, замер, критерии §7.7
