# M-BENCH — бенчи и замеры

**Инварианты и грабли**
- Запуск — только через tsx (`cd lib && npx tsx bench/<скрипт>`): скрипты импортируют исходники `lib/src/*.ts`, а не сборку. Масштаб — `BENCH_SCALE` (0.1 — в десять раз меньше).
- Один замер на одном коде расходится между прогонами на десятки процентов: разницу сравнивать с разбросом, а не с одним прогоном. Поэтому повторяемые замеры идут кругами `BENCH_ROUNDS`: порядок вариантов чередуется, в итоге — медиана; сравнивая варианты, перед замером каждого — `CHECKPOINT`, иначе контрольная точка базы достаётся одному из них.
- Не гонять параллельно с тестами и другими бенчами: та же база, что у тестов (`ENTITY_DSN`, по умолчанию `letopis-pg18`, порт 15433; контейнер поднимает `ensureDatabase` обвязки). Бенч в начале пересоздаёт свою схему: второй экземпляр того же бенча сносит данные первому.
- Быстрый прогон перезаписывает закоммиченный итог полного масштаба, на котором стоят цифры README и сводок, — такой итог не коммитить (масштаб — поле `scale` итога).
- Долгий прогон `soak.mjs` (план 2.0, этап 2; `npm run soak`): нагрузка и замеры — одним процессом, в конце сверка журнала запросом и критерии §7.7, код 1 — критерий нарушен. Heap — после принудительной сборки (`v8.setFlagsFromString('--expose-gc')`): без неё наклон за короткий прогон — шум сборщика. Вход по коду кончается выходом (`revokeAll`): сессия по коду живёт 7 дней, и без выхода SESSION росла бы весь прогон. Быстрый режим (`SOAK_HOURS=0.25`) — шаг `soak` prerelease с `SOAK_OUT` в каталоге логов: закоммиченный суточный итог не перезаписывается.
- p99 `read:latest` долгого прогона (`Order().sort('at', 'desc').limit(20)`) растёт с числом строк (`docs/checkpoint-2.0.0.md`) и в суточном прогоне может нарушить критерий 4: индекса по `at` у `entity` нет, а индекс `(class, at, id)` при фильтре построителя `class = any(…::text[])` план не берёт — нужна правка движка и построителя.
- Память: строки полигона не держать между замерами (только число и время), грузить порциями (`lib/bench/polygons.mjs:loadChunks`).

**Что ещё менять вместе**
- Бенчи правят объекты базы по тексту и имени: `core-write` — `create or replace` функций `validate_data`, `targets_bad`, `trg_entity_ai`, `signal_raw` (вариант `noLog` — упрощённая копия `trg_entity_ai` без вставки в журнал); `core-concurrency` и `core-notify` — фрагменты `perform pg_notify` в `signal_raw` и `order by t.id for key share;` в `targets_bad`; `family-lock` — свои варианты `family_lock` на `family_name`, `lock_id`, `lock_row`; `gencols` — сверка кандидата с `link_ids`. Сменились сигнатура, фрагмент, имя или шаги триггера в `lib/sql/` → поправить бенч. Пропажу фрагмента или имени видно только прогоном (`patchFunction` бросает «нет фрагмента»), а `create or replace` с новой сигнатурой в `core-write` молча заводит перегрузку — вариант ничего не отключает.
- `soak` держит копии SQL: `JOURNAL_ISSUES` — запрос `journalIssues` из `lib/test/_engine.ts` (обвязку тестов бенч не импортирует), `ORPHAN_LOCKS` — разбор имени строки-замка, как в `lib/sql/90-time.sql:maintain` (формат — `family_name`). Правишь оригинал → правь копию.
- Новый или изменённый скрипт: `check-docs` проверяет только синтаксис (`node --check`) и ссылки в шапке; имена и типы импортов не проверяет никто (`.mjs` без `allowJs` в `lib/tsconfig.json`) — прогнать хотя бы раз с `BENCH_SCALE=0.1`.
- Изменились цифры серий `core-*` и `chain-read` — раздел «Производительность» `lib/README.md`; любой серии — её раздел в `docs/checkpoint-*.md` (`core-*`, `chain-read`, `acl-cost` — `docs/checkpoint-a.md`).

**Состояние и побочки**
- Итог — `lib/bench/results/` (JSON с масштабом, версией сервера и `shared_buffers`). `BENCH_RUNS` у `initial-load` пишет итог частичного прогона в отдельный файл, полный не трогает; `BENCH_ONLY` у `core-write` сливает снятые части с прежним итогом. Частичный итог initial-load-regular-initial цитируют сводки `docs/checkpoint-*.md` — не удалять.
- Схемы: серии — `v2.b_<имя>` (`gencols`, `initial-load` и `soak` ставят свою сами), полигоны — `v2.salon` и `v2.tenants`.
- Схема удаляется в конце; `BENCH_KEEP=1` — оставить (где поддержано); `v2.b_soak` долгого прогона остаётся для разбора и пересоздаётся следующим прогоном.

**Проверка**
- `cd lib && BENCH_SCALE=0.1 npx tsx bench/<скрипт>` доходит до итога; правильность, а не скорость, — `mismatches` в итоге `gencols` (нули). `cd lib && npm run check:docs` — синтаксис и ссылки шапок.

**Точки входа**
- `lib/bench/_core.mjs:setup` — схема серии: установка, арендатор с сессией, классы
- `lib/bench/_core.mjs:save` — запись итога
- `lib/bench/polygons.mjs:seedSalon10` — полигон salon
- `lib/bench/salon-data.mjs:toLoad10` — строки генератора полигона → строки загрузчика
- `lib/bench/core-concurrency.mjs:patchFunction` — подмена функции базы по фрагменту
- `lib/bench/soak.mjs` — долгий прогон: нагрузка, замер, критерии §7.7
