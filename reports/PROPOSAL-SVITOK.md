# Предложение: «Свиток» — лёгкий типизированный слой моделей поверх обычного PostgreSQL

> Дата: 2026-10-06. Статус: предложение, к реализации не утверждено. «Свиток» — рабочее название: он легче летописи, но так же пишется только вперёд.
> Контекст: составлено после исследования letopis 0.21.0 (`reports/`, план 0.22.0) по запросу владельца: взять ключевые идеи библиотеки и предложить более лёгкую, но максимально удобную основу для построения моделей данных.

## 1. Что берём из letopis, а что выбрасываем

**Берём ключевые идеи:**
- история каждой записи бесплатно: путешествие во времени, аудит «кто и когда»;
- модели как данные: новый тип или поле не требуют миграций;
- граф: записи ссылаются друг на друга, навигация работает в обе стороны;
- естественные ключи: защита от дублей, например от двойной брони;
- арендатор как граница;
- поток изменений.

**Выбрасываем то, что создаёт боль** (именно отсюда выросло большинство находок исследования):
- Proxy-DSL с 52 зарезервированными именами и кириллическими alias;
- вычисление текущего состояния из всей истории через `DISTINCT ON`, откуда R2–R6 и ошибки 42P18;
- зависимость от TimescaleDB, Redis и Docker;
- auth и ACL-движок внутри ядра;
- v5-хитрости вместо настоящих уникальных ключей;
- типы через кодогенерацию.

## 2. Идея в одном абзаце

Модели описываются на TypeScript: поля, ссылки, ключи и правила. Из описания сразу выводятся статические типы (без кодогенерации), проверка данных и физические гарантии в БД.

Хранение — обычный PostgreSQL без расширений, три таблицы:
- `records` — текущее состояние;
- `history` — неизменяемый журнал версий;
- `models` — реестр моделей.

Инварианты держит сама база: частичные индексы, ограничения исключения и триггеры по каждой модели.

Что это даёт:
- модель сущностей, связей и ограничений собирается за минуты;
- история и поток изменений работают сразу;
- ядро укладывается примерно в 3 тыс. строк.

## 3. Как выглядит модель

```ts
import { model, f, ref } from 'svitok';

export const Client = model('Client', {
  label: 'Клиент',
  fields: {
    name:  f.text().min(1),
    phone: f.phone().pii({ search: 'exact' }),   // персональные данные — см. §6.5
    note:  f.text().optional(),
  },
  key: ['phone'],                 // уникален в пределах арендатора — уникальный индекс в БД
});

export const Master = model('Master', {
  label: 'Мастер',
  fields: { name: f.text(), skills: f.list(f.text()) },
});

export const Booking = model('Booking', {
  label: 'Запись',
  fields: {
    start:  f.datetime(),
    end:    f.datetime(),
    status: f.enum('planned', 'done', 'cancelled').default('planned'),
    price:  f.money('RUB'),
  },
  refs: {
    master: ref(Master).inverse('bookings').onDelete('restrict'),
    client: ref(Client).inverse('bookings').onDelete('cascade'),
  },
  rules:     [(b) => b.end > b.start || 'конец раньше начала'],
  noOverlap: { per: 'master', during: ['start', 'end'], unless: { status: 'cancelled' } },
  conflicts: { status: 'reject' },          // остальные поля сливаются автоматически
  index:     ['status', 'start'],
});

export type Booking = Infer<typeof Booking>;  // тип без кодогенерации
```

Одно описание даёт всё сразу:
- TS-типы и проверку данных;
- уникальный ключ клиента;
- запрет двойной брони силами БД;
- правила удаления;
- обратную навигацию `master.bookings`;
- индексы.

## 4. Хранение: три таблицы

```sql
CREATE TABLE models  (name text, version int, def jsonb, PRIMARY KEY (name, version));

CREATE TABLE records (                  -- ТЕКУЩЕЕ состояние, одна строка на запись
  tenant uuid, id uuid, type text, mv int, rev int,     -- mv = версия модели, rev = версия записи
  key text, owner uuid, data jsonb,
  created_at timestamptz, created_by uuid,
  updated_at timestamptz, updated_by uuid, deleted_at timestamptz,
  PRIMARY KEY (tenant, id));
CREATE UNIQUE INDEX ON records (tenant, type, key) WHERE key IS NOT NULL;

CREATE TABLE history (                  -- журнал версий, только дописывается
  seq bigint GENERATED ALWAYS AS IDENTITY, tx xid8 DEFAULT pg_current_xact_id(),
  tenant uuid, id uuid, type text, rev int, mv int, op text, data jsonb,
  at timestamptz DEFAULT clock_timestamp(), by uuid, reason text
) PARTITION BY RANGE (at);              -- партиции по времени — для retention
```

**Объекты на модель.** При синхронизации для каждой модели создаются, все `CONCURRENTLY`:
- частичные индексы `… WHERE type = 'Booking'`;
- индексы ссылок — для обратной навигации;
- ограничение исключения `EXCLUDE USING gist (tenant WITH =, (data->>'master') WITH =, range(start, end) WITH &&) WHERE type = 'Booking' AND …`.

**Триггеры:**
- пишут каждую версию в `history`;
- увеличивают `rev`;
- запрещают менять `tenant` и `owner`;
- ставят автора из `app.actor`.

У роли приложения нет прав `UPDATE` и `DELETE` на `history`.

**Почему так — структурное закрытие рисков letopis:**

| Риск letopis | Как закрыт здесь |
|---|---|
| R1 — перехват чужой записи | `PRIMARY KEY (tenant, id)`: чужую запись даже не адресовать; ссылки проверяются в пределах tenant |
| R2 — retention стирает текущее | retention режет только партиции `history`, текущее живёт в `records` |
| R3 — потерянные обновления | `rev` плюс атомарный `data \|\| patch` в одном UPDATE; для сложных правил — CAS-цикл (§6.1) |
| R4 / 42P18, R5, R6 | нет `DISTINCT ON` по истории: фильтр по текущему состоянию и частичным индексам, чанков нет |
| R9 — watch без изоляции | поток изменений читается из журнала в пределах tenant (§6.3) |
| R10 — обход append-only | автор в каждой версии, неизменность журнала обеспечена правами |
| R12 — v5-хитрости | настоящие уникальные ключи, проверяет БД |
| R13 — эволюция ломает данные | апкастеры (§6.2) |
| R14 — зависимость от TimescaleDB | любой PostgreSQL: RDS, Neon, Supabase, локальный |

## 5. Работа с данными

```ts
const db = await connect(DATABASE_URL, { models: [Client, Master, Booking] });
await db.sync();                                   // аддитивно сразу, ломающее — только с апкастером

const t = db.as({ tenant: acme, actor: bob });     // граница + автор; owner по умолчанию = actor

const anna = await t.Client.upsert({ name: 'Анна', phone: '+79990001122' });    // по ключу
const b    = await t.Booking.create({ master: m.id, client: anna.id, start, end, price: rub(2500) });
// вторая бронь на то же время → ошибка из БД (noOverlap), не из «надежды на v5»

const day = await t.Master.get(m.id).bookings
  .where({ start: { gte: dayStart, lt: dayEnd }, status: { ne: 'cancelled' } })
  .include({ client: ['name'] })                   // типы: Booking & { client: { name } }
  .orderBy('start').all();

await t.Booking.update(b.id, { status: 'done' });                    // безопасно при конкуренции
await t.Booking.update(b.id, { price: rub(3000) }, { expect: b.rev });   // строгий режим (ETag)
await t.Master.patch(m.id, (x) => x.inc('visits', 1).push('skills', 'окрашивание'));  // атомарно в SQL

await t.at('2026-09-01T00:00Z').Booking.get(b.id);   // состояние на дату
await t.Booking.history(b.id);                        // версии в форме текущей модели
await t.Booking.blame(b.id);                          // кто последним менял каждое поле
await t.Booking.diff(b.id, 3, 7);                     // что изменилось между версиями

await t.Folder.get(root).descendants('children', { depth: 5 });  // рекурсия по ссылкам
await t.Booking.where({ status: 'done' }).groupBy('master').sum('price');
```

Имена навигации (`bookings`, `client`) задаёт автор модели. Методы живут в своём пространстве имён, поэтому зарезервированных имён и коллизий нет.

## 6. Новые идеи

### 6.1. Конфликты объявляются в модели, а не ловятся вручную

Простой патч выполняется одним SQL-оператором:

```sql
UPDATE records SET data = data || $patch, rev = rev + 1 WHERE tenant = $1 AND id = $2
```

PostgreSQL сам применяет патч к свежей версии. Поэтому параллельные правки разных полей сливаются без потерь и без предварительного чтения.

Если правило требует всей записи, работает CAS-цикл: прочитать → проверить → записать с `WHERE rev = $rev` → при конфликте повторить.

Политика конфликтов задаётся на уровне поля:
- `merge` — по умолчанию;
- `reject` — ошибка, если кто-то успел поменять это же поле;
- `lww` — побеждает последний;
- своя функция слияния.

Атомарные операции `inc`, `push`, `remove` не конфликтуют вовсе.

### 6.2. Эволюция моделей без блокирующих миграций — апкастеры

Каждая строка хранит версию модели (`mv`). Ломающее изменение описывается рядом с моделью:

```ts
migrate: {
  2: { rename: { phone: 'mobile' } },
  3: (old) => ({ ...old, fullName: `${old.first} ${old.last}` }),
}
```

- **Декларативные шаги** (rename, default, split) компилируются в SQL. Фильтры работают и по ещё не переписанным строкам, а фоновая перезапись идёт пачками онлайн.
- **Произвольный JS-апкастер** вступает в силу после фонового прохода.
- **История** никогда не переписывается и при чтении поднимается до текущей формы.

Это приём event sourcing, перенесённый на текущее состояние.

### 6.3. Надёжный поток изменений из самого журнала

Отдельный outbox не нужен. `history` хранит `tx xid8`, и потребитель читает строки ниже горизонта завершённых транзакций:

```sql
… WHERE (tx, seq) > ($cursor) AND tx < pg_snapshot_xmin(pg_current_snapshot()) ORDER BY tx, seq
```

Такая выборка гарантирует, что:
- ни одно событие не проскакивает из-за разного порядка коммитов;
- после рестарта подписка продолжается с курсора;
- потерь нет.

`NOTIFY` служит только сигналом «проснись». В letopis события терялись при обрыве соединения.

### 6.4. Время — полноценное измерение

- `at(T)` — состояние на момент;
- `history()` — все версии;
- `diff()` — разница между версиями;
- `blame()` — кто последним менял каждое поле;
- `reason` — «почему изменено», передаётся из приложения;
- опционально бителемпоральность: время действия, а не только время записи. Например, `validFrom` и `validTo` для тарифов и договоров.

### 6.5. GDPR в неизменяемой истории — крипто-шреддинг

Поля с пометкой `.pii()` шифруются ключом субъекта: клиента или самой записи. `forget(subject)` удаляет ключ, и все версии в истории становятся нечитаемыми, а журнал остаётся нетронутым.

Для поиска по точному значению хранится слепой индекс (HMAC) — это `pii({ search: 'exact' })`.

### 6.6. Черновики и наборы изменений

`t.changeset()` собирает операции вместе с базовыми `rev`:
- `preview()` прогоняет их в транзакции с откатом и показывает результат и нарушения;
- `commit()` применяет атомарно с проверкой конфликтов.

Это для согласований, многошаговых форм и сценариев вида «а что, если переставить расписание».

### 6.7. Модели — сразу интерфейс для LLM-агентов

- `db.describe()` выдаёт машинно-читаемый граф моделей: поля, ссылки, ключи, ограничения, примеры.
- `db.describe({ format: 'llms.txt' })` выдаёт карточку для агента.
- `serveMcp(db)` поднимает MCP-сервер. Инструменты `Booking_find`, `Booking_create` и т. д. получают JSON Schema из моделей и политики доступа.

Руководство для агентов генерируется из модели, поэтому расходиться с кодом не может по построению.

### 6.8. Совместимость и лёгкость

- **Валидаторы.** Поля принимают любой валидатор стандарта Standard Schema: Zod, Valibot, ArkType.
- **Тесты без Docker.** Dev и тесты идут на PGlite (Postgres в WASM) через тот же драйверный адаптер — это полностью автономные тесты. Есть ли в PGlite нужные расширения, например `btree_gist` для `noOverlap`, надо проверить.
- **Схема как данные.** Модели можно задавать JSON на лету (`db.define(json)`) — идея letopis сохраняется для no-code сценариев.

## 7. Арендаторы, владение, права

| Поле | Смысл |
|---|---|
| `tenant` | граница; часть первичного ключа; неизменна |
| `owner` | владелец записи; неизменен (триггер) |
| `created_by` / `updated_by`, `history.by` | авторы версий |

Модель полей совпадает с решением владельца для letopis.

Политики пишутся кодом рядом с моделью:
- объектная форма компилируется в SQL-фильтр;
- функция проверяется в процессе.

```ts
policy(Booking, {
  read:   ({ user }) => user.role === 'admin' ? {} : { master: user.id },
  update: ({ user }, b) => b.owner === user.id || user.role === 'admin',
});
```

**Изоляция по `tenant`** обязательна и встроена; политики только сужают доступ внутри арендатора. Строгий режим `rls: true` дублирует границу политиками RLS PostgreSQL — вторая линия защиты. Без сжатия TimescaleDB RLS работает.

**Auth** — пароли, OTP, сессии — вынесен в отдельный необязательный пакет, ядру он не нужен.

## 8. Сравнение

| | letopis 0.21 | «Свиток» |
|---|---|---|
| Инфраструктура | PG17 + TimescaleDB + Redis + Docker | любой PostgreSQL; PGlite для dev и тестов |
| Типы | кодогенерация, «навесные» | выводятся из модели |
| Текущее состояние | вычисляется из истории (`DISTINCT ON`) | отдельная таблица, точечное чтение по PK |
| Уникальность | v5-хитрость | уникальный индекс + `noOverlap` в БД |
| Конкурентная запись | теряет обновления | атомарный patch, CAS, политики конфликтов |
| Эволюция | ломает старые строки | апкастеры, онлайн-перезапись |
| Поток изменений | NOTIFY, теряет события | журнал + курсор, без потерь |
| Права | ACL-движок в ядре | граница в ядре + политики кодом |
| Объём ядра | ~4,4 тыс. строк TS + 580 SQL + auth | оценка ~3 тыс. TS + ~300 SQL |
| Для LLM | ручная шпаргалка | `describe()`, `llms.txt`, MCP из модели |

**Чем отличаются аналоги:**
- Prisma и Drizzle дают типы и миграции, но без истории и потока изменений.
- Convex, InstantDB и Zero — это свои бэкенды и синхронизация.
- Marten (.NET), XTDB и Datomic дают историю, но требуют отдельного стека.

По моей оценке (специальным поиском не проверялось), одного лёгкого пакета с таким сочетанием нет: типизированные модели, текущее состояние плюс журнал, инварианты в БД, апкастеры, надёжный поток изменений и MCP — поверх обычного Postgres.

## 9. Честные ограничения

- **Универсальная таблица `records`.** На огромных объёмах одного типа частичных индексов может не хватить. Выход на будущее — `storage: 'table'`: та же модель и тот же API, но выделенная таблица.
- **Навигация вместо цепочек.** Пути произвольной длины с pivot через LINK, как в letopis, заменяются ссылками, `include` и `descendants`. Это проще, но менее «алгебраично».
- **`noOverlap`.** Нужна IMMUTABLE-функция разбора дат, поэтому библиотека обязана хранить даты в каноническом UTC.
- **Порядок разработки.** Самые сложные части — апкастеры, крипто-шреддинг и наборы изменений. Их стоит делать после ядра.

## 10. Путь

1. **Ядро (MVP):**
   - модели и типы, таблицы `records`, `history`, `models`;
   - CRUD с `rev`, ссылки и правила удаления;
   - запросы и `include`;
   - `as({ tenant, actor })`, `at()`, `history()`;
   - поток изменений, `sync` для аддитивных изменений;
   - тесты на PGlite.
2. **Инварианты и ключи:** `key`, `noOverlap`, правила, политики, `blame`, `diff`.
3. **Эволюция и модули:** апкастеры, крипто-шреддинг, наборы изменений.
4. **AI-слой:** `describe`, `llms.txt`, MCP.
5. **Импорт из letopis:**
   - версии `Entity` → `history` + `records`;
   - `Schema` → `models`;
   - links → ссылки.
