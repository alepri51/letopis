# План 2.0: зрелость letopis

> Дата: 2026-11-01, редакция 1. Статус: утверждён владельцем 1 ноября 2026 года.
> Основание: анализ зрелости letopis 1.4.1, присланный владельцем. Три оси: зрелость библиотеки, понятность для человека, пригодность для ИИ-агента. Владелец также поручил попутно искать ошибки в других местах.
> Выпуски: 1.4.2 (исправления), 1.5.0 (права, один процесс, ошибки, агент), 2.0.0 (строгий режим). Каждый — только по команде владельца.
> Тесты ссылаются на пункты §7 так: `test('план 2.0, 7.3 №1: …')`.

## 1. Контекст

Разведку на `2183d03` вели три разведчика и два ревьюера, главные находки перепроверены чтением кода. Что она показала:

- **Ошибок больше, чем думали.** Больше 40 находок, из них 28 в библиотеке (§7.1–7.5). Многие устроены одинаково: README обещает одно, код делает другое. Самые тяжёлые:
  - прореживание может безвозвратно стереть историю;
  - срез `asOf` показывает объект в прежнем классе;
  - `verify` не видит порчу надгробия;
  - два одинаковых `create` в батче проходят молча;
  - порядок ответа `reclass`, `restore` и `rekey` расходится с README;
  - подписка без событий опрашивает базу примерно 4 раза в секунду вместо одного.
- **Semver только объявлен** (`lib/CHANGELOG.md:3`).
  - Патч 1.4.1 поднял ревизию движка с 6 до 7, добавил миграцию, которая стирает строки, и новые отказы.
  - `gen-api-contract.mjs --check` сравнивает контракт только с закоммиченным файлом, а не с прошлым выпуском.
  - Теста наката с 1.2–1.4 нет.
- **Долгого прогона нет.** Есть 20 замеров скорости, но ни одного на часы. Рост `secret`, MultiXact, прореживание под записью и утечки подписок не измеряются.
- **API для записи прав нет.** Права — это строки системных классов `Resource`, `rule` и `member` с масками-строками вида `'{staff}'`. В `lib/src/acl.ts` есть только `check` и `checkData`.
- **Нужны два подключения.** У `connect()` нет второго пула. Роль приложения создаёт сам вызывающий, и во всех четырёх сервисах это склейка SQL из строки подключения.
- **Опечатки в типах не ловятся.** Опечатка в имени класса, перехода или роли компилируется: этому не мешают индексные сигнатуры в `typed.ts:83`, `index.ts:237,241` и `chain.ts:59,212`. Слот — это `set(value: unknown)`.
- **Агенту не хватает подсказок.**
  - У `LetopisError` нет `hint` и `docs`, а `similar` есть только в MCP.
  - Два диалекта фильтров без таблицы соответствия.
  - Описания MCP и тексты ошибок — только на русском.
  - В `describe()` нет примеров цепочек, а в `llms.txt` (33 строки) — ни ошибок, ни нюансов.
- **Сайт.**
  - Кнопка «Начать» ведёт в главу 1, а не на старт.
  - Аккаунт нигде не определён.
  - 78 нюансов идут одним списком.
  - Примеры не типизированы (`guide/kit/example.ts`), а `write/06` показывает пять идей сразу.

## 2. Решения владельца (1 ноября 2026)

| Вопрос | Решение |
|---|---|
| Тесты в CI | Оставить без тестов. В CI — только статические проверки, все тесты — локально до выкатки |
| Сайт | Оставить локальным, только на русском |
| Semver | Обычный semver с автопроверкой по прошлому тегу |
| PostgreSQL | Только 18 |
| Строгий режим | Сразу 2.0: строгие типы и новые отказы для всех |
| Примеры сайта | Один пример — одна идея (пересмотр решения «не дробить») |
| Тесты | Проверяют соответствие спецификации, unit-тестов не пишем. Спецификация — тест-план этого плана (§7), как у планов 1.0 и 1.1 |
| Английский для агента | Описания MCP, подсказки, `llms-full.txt` и все тексты ошибок, по опции `lang` |

## 3. Правила выполнения

- **Тесты.**
  - Каждое исправление и каждая возможность — пункт §7.
  - Тест в `lib/test` проверяет пункт через публичное API на настоящем PostgreSQL 18. Имя теста начинается с номера пункта.
  - Unit-тестов внутренностей нет. Тесты в `lib/test` — только по пунктам §7; разрешение на них — утверждение плана.
  - Тест исправления без исправления падает — это проверяется откатом.
- **Находки ревью.** Каждую сначала воспроизводят тестом. Если не воспроизвелась, её снимают с отметкой в отчёте.
- **Документы.** По правилам проекта одним коммитом идут код, карточка модуля, трасса, README (обе версии), раздел «Тесты» и контракт API.
- **Конец этапа.**
  - Команда `prerelease` (§5, этап 0) зелёная, затем пуш в `dev`, CI (статика) зелёный, короткий отчёт.
  - Длинные прогоны идут в фоне, их проверяют раз в минуту.
  - Тесты и примеры на одной базе не запускаются одновременно.
- **Выпуски — только по команде владельца:** 1.4.2 после этапа 1, 1.5.0 после этапа 3, 2.0.0 после этапов 4–5. Порядок деплоя: dev → PR → main → tag.yml → Release → release.yml.
- **Браузер.** Интерфейсы сервисов и сайт после правок проверяются в Chrome через chrome-devtools-mcp, с вводом паролей и кодов.

## 5. Этапы

### Этап 0. План, правила версий, проверка перед выпуском

1. **Документ плана** — этот файл. В `AGENTS.md` — строка в «Документах», исключение в «Не читать», паспорт.
2. **Правила версий.** Подраздел «Версии и совместимость» в `lib/README.md` и `lib/README.en.md` и шапка `lib/CHANGELOG.md`:
   - **патч** — только исправления. Ревизия движка та же (функции обновляет обычный `up()`), миграций нет, работающий код не получает новых отказов;
   - **минор** — новые возможности и изменения поведения. Новая ревизия движка накатывается через `up({ upgrade: true })`;
   - **мажор** — удаление, переименование, смена сигнатур и типов, новые отказы для всех.

   В секции 1.4.1 CHANGELOG отметить, какие её изменения по этим правилам должны были выйти минором.
3. **`check:semver`** — `lib/scripts/check-semver.mjs`, вызывается из `check:docs` и из `release.yml` до публикации.
   - Берёт `docs/api-contract.json` и `DDL_REVISION` из тега прошлого выпуска (`git show v<прошлая>:…`).
   - Классифицирует разницу:
     - удалено в `exports`, `chain`, `db`, `batch` или в кодах ошибок — мажор;
     - добавлено — минор;
     - выросла ревизия — не меньше минора;
     - изменились только тексты — патч.
   - Сверяет с шагом версии в `lib/package.json`.
   - Проверка статическая, поэтому идёт в CI. Нужен `fetch-depth: 0`.
4. **`prerelease`** — `lib/scripts/prerelease.mjs`, одна команда полной локальной проверки.
   - Шаги: typecheck, `check:docs`, весь `npm test`, примеры со снимками, песочница, покрытие, сценарии четырёх сервисов, `check:package` с живым прогоном.
   - Шаги идут строго по очереди, строка прогресса печатается раз в минуту.
   - Итог — таблица в `docs/checkpoint-<версия>.md`.
5. **Метрика стабилизации.**
   - У каждой правки ядра в CHANGELOG указан источник: тест, пример, сервис, ревью, soak или внедрение. `release-notes.mjs` считает их.
   - Цель из анализа — две версии подряд без правок ядра, найденных примерами и сервисами.
6. **Накат с прошлого выпуска.**
   - Dev-зависимость `letopis-141` (`npm:letopis@1.4.1`) по образцу `letopis-1` и `letopis-11`.
   - Тест `upgrade` «1.4.1 → текущая» (§7.8 №2).
   - Правило: каждый выпуск проверяет накат с предыдущего.
7. **Подготовка к внедрениям.**
   - `CONTRIBUTING.md` на русском и английском.
   - Шаблон issue: версии пакета и PostgreSQL, минимальная цепочка.
   - Форма отчёта о внедрении — `docs/adoption/TEMPLATE.md`.
8. **Мелочи.**
   - Комментарии `ci.yml` расходятся с делом, а сервис `postgres:18` в задании `test` не используется.
   - В `docs/checkpoint-guide.md` устарели версия 1.4.1-alpha.0, цифры (52 примера, 365, 70 нюансов) и строка «Осталось открытым».

### Этап 3. Выпуск 1.5.0: права, один процесс, ошибки, агент

1. **Обёртка над правами** (`lib/src/acl.ts`, M-ACCESS):
   ```ts
   await db.acl.grant({ role: 'staff', read: 'Product', write: 'Product' })
   await db.acl.deny({ role: 'staff', delete: 'Product' })
   await db.acl.grant({ role: 'client', read: { class: 'Ticket', owner: '$actor' } })
   await db.acl.grant({ role: 'manager', api: 'reports.*' })
   await db.acl.revoke({ role: 'staff', delete: 'Product' })
   await db.acl.roles(oleg, ['staff'])     // членство в текущем арендаторе
   await db.acl.list()                     // [{ role, op, target, permission, weight }]
   ```
   - Под капотом те же `Resource`, `rule` и `member`; права, как и прежде, проверяет база.
   - Alias детерминированные (`role:staff:ACCOUNT`, `class:Product:READ`), ключ правила `[Group, Object]` — поэтому повтор идемпотентен.
   - Вес по умолчанию 50: это сильнее правила «можно всё» с весом 10 от `createTenant`. При равном весе deny сильнее, как в базе.
   - helpdesk переходит на обёртку (`syncRules`).
   - Обновляются README о правах (обе версии), глава 8 сайта с примерами и `guide/pages/reference/acl.md`.
2. **Один процесс для малых приложений** (`index.ts`, `up.ts`; M-API, M-BOOTSTRAP).
   - `up({ login: { user, password } })` создаёт или обновляет роль приложения с логином и выдаёт ей `letopis_app`. Имя и пароль квотируются через `format('%I', '%L')`.
   - `connect({ dsn, admin, token | apiKey })` при первой надобности открывает второй пул (max 2).
     - Через него идут только администраторские методы: `load`, `projector`, `rebuildAggregates`, `syncModels`, `verify`, `maintain` — с тем же токеном сессии.
     - Цепочки всегда идут через пул приложения под RLS.
     - Без `admin` всё работает как сейчас.
   - Старт в 4 шага: `up({ schema, tenant, login })` → `connect({ dsn, admin, token })` → `syncModels` → цепочки.
   - README предупреждает: пароль администратора в процессе приложения — только для малых приложений.
   - Сервисы переходят на `up({ login })`.
3. **Каталог сообщений и английский** (`errors.ts`, новый каталог; вызовы `lt_fail` в `lib/sql`; M-API, M-ENGINE).
   - Каталог: ключ → шаблоны ru и en с параметрами. Каждый `fail()` и `new LetopisError()` в TS и каждый `lt_fail()` в SQL переходят на ключ с параметрами.
   - База кладёт ключ и параметры в DETAIL, а текст собирает библиотека на языке подключения. Для сырого SQL текст базы остаётся русским.
   - Опция `lang: 'ru' | 'en'` у `connect()`, `createMcpServer()` и CLI (`--lang`). По умолчанию `ru`, поведение не меняется.
   - По этой же опции переводятся описания инструментов MCP, их параметров и инструкция сервера.
   - `LetopisError.hint` — «что делать». Колонка из главы 16 переезжает в каталог, а страница сайта строится из него через `guide/scripts/gen-errors.ts`.
   - `LetopisError.docs` — ссылка на строку кода в разделе «Ошибки» README на GitHub по тегу версии.
   - `similar` становится общим: функция переезжает из `mcp.ts` в `errors.ts`. Охватывает неизвестный класс или роль в цепочке, поле в фильтре, `sort` или агрегате, имя опции. В 1.5 это предупреждение с похожими именами, в 2.0 — ошибка.
   - `check:docs` сверяет, что у каждого ключа есть ru и en и что в `fail`, `LetopisError` и `lt_fail` не осталось литеральных текстов.
4. **`llms-full.txt`** — генерирует `lib/scripts/gen-llms-full.mjs`, файл входит в `files` пакета.
   - Один файл на английском:
     - шпаргалка;
     - грамматика цепочки;
     - таблица «код — смысл — что делать»;
     - нюансы (у `guide/coverage/nuances.ts` появляется поле `en`);
     - зарезервированные имена;
     - операторы.
   - `check:docs` сверяет его свежесть, `check-package` — наличие в тарболе. `llms.txt` ссылается на него.
5. **Один словарь фильтров.** Реестр операторов в `ops.ts`: имя в TS, ключ MCP, описание ru/en. Из него строятся таблица `OPS` для MCP и таблицы соответствия в README (обе версии), шпаргалке, `llms-full` и справочнике сайта. `check:docs` сверяет их с реестром.
6. **Шпаргалка** (обе версии). Вместо абзацев — списки «условие → поведение». `c.before` описан таблицей «вид изменения → before».
7. **`describe()` с примерами.** У каждого класса появляется `examples`: рабочие цепочки «создать», «найти», «перейти к соседям», собранные из реестра (ключ, обязательные поля, концы). Их отдают и `describeText`, и `letopis_model` в MCP.
8. **Проверки до запуска.**
   - `letopis check <файлы> [--models модуль]` — статический разбор через TypeScript Compiler API (`typescript` — необязательная peer-зависимость, грузит её только эта команда). Ловит:
     - зарезервированные имена в `hub()` и `link()`;
     - `update()` и `delete({ confirm: true })` без фильтра;
     - `delete()` без `confirm`, чей результат не используется, — превью вместо удаления;
     - `upsert` у класса без ключа;
     - модификатор после глагола;
     - `forUpdate()` вне `db.begin()`;
     - неизвестные классы и роли с похожими именами.

     Вывод — текст или JSON, при ошибках код 1.
   - `letopis sync --check` возвращает код 1, если сухой прогон нашёл изменения.
9. **Агентский прогон** (`docs/agent-run.md`).

### Этап 4. Выпуск 2.0.0: строгий режим

1. **Типы** (`typed.ts`, `index.ts`, `chain.ts`, `model.ts`, `sync.ts`).
   - Индексные сигнатуры убираются из `TypedDb` и `TypedChain`. Шагом может быть только известный класс или алиас.
   - Системные классы (`Account`, `member`, `Resource`, `rule`, `Class` и другие) типизирует встроенный набор моделей.
   - Переходы выводятся из `ends`: от класса C — его роли и классы, чьи концы смотрят на C, как в `resolveHop` (`lib/src/sql.ts`).
   - Слоты:
     - только роли класса;
     - `set(id | Row | цепочка)`;
     - `add` и `remove` — только у `many`;
     - `unset` — только у необязательного конца.
   - Поля `sum`, `avg`, `min`, `max`, `countBy` и фильтр `or()` типизированы полями класса.
   - `letopis types` выдаёт и концы с классами-целями, поэтому строгие типы работают и без моделей Zod.
   - Для динамических имён — функция `loose(db)`, а не новое зарезервированное имя.
2. **Новые отказы.**
   - `update()` и `delete({ confirm: true })` дают `invalid_query`, если ни у одного шага нет фильтра, id или `limit`. Чтобы разрешить, нужно передать `{ all: true }`.
   - Зарезервированное имя хаба отклоняют `hub()`, `syncModels` и база; сейчас база отклоняет только связи. Существующие такие хабы `up({ upgrade })` оставляет и предупреждает о них.
   - Неизвестные опции `connect()`, `up()`, `load()`, проектора, `watch()` и `createMcpServer()` дают `invalid_data` с похожими именами.
   - `after()` у `count()`, агрегатов, `diff()` и `blame()` даёт `invalid_query`. В 1.4.2 курсор там не учитывается, и README это описывает: отказ — новый, поэтому только в мажоре (7.1 №4).
3. **Документы.**
   - В `lib/MIGRATION.md` — раздел «1.x → 2.0».
   - README, шпаргалка и `llms-full` переходят на строгий режим.
   - Нюансы, которые теперь ловит код, уходят из текста: в `nuances.ts` у них отметка «ловит код» и ссылка на ошибку.
4. **Примеры сайта — типизированные.** `guide/kit/example.ts` и раннер подключают модели примера через `connect({ models })`, `ctx.db` типизирован.
5. **Накат.** Тест `upgrade` «1.5.0 → 2.0.0».

### 7.7 Долгий прогон

1. `SESSION` и `OTP` ограничены после `maintain()`.
2. Строк-замков удалённых классов после `maintain()` нет: у живого корня семейства две строки (замок и шлюз), плюс служебные — обслуживание и проекторы. Редакция после пробного прогона: прежнее «не больше числа корней семейств» не учитывало шлюз и служебные строки.
3. Память и дескрипторы после прогрева не растут (наклон ≈ 0).
4. p99 последнего часа не больше чем вдвое хуже первого.
5. В конце `verify({ data: true })` даёт ok.
6. Неожиданных ошибок нет.
7. Отставание проектора ограничено.

Дефекты, найденные прогоном, получают номера с 8.

8. `maintain()` убирает строки-замки семейств, чей корень удалён: занятые — следующим вызовом, живые и служебные остаются, класс с тем же именем заводит их заново (пробный прогон; 1.4.2).
