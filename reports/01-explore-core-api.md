## О чём этот отчёт

Репозиторий лежит в `C:\projects\letopis`. Пакет `letopis` версии 0.21.0 — это append-only хранилище версионируемых сущностей поверх TimescaleDB с так называемым dot-chain API. «Append-only» означает, что данные никогда не меняются на месте: каждое изменение записывается новой строкой, а старые строки остаются как история. TimescaleDB — расширение PostgreSQL для больших таблиц с временным ключом; «dot-chain API» — стиль запросов, в котором путь по данным записывается цепочкой вызовов через точку, например `db.Класс().Связь().rows()`.

Ниже приведён фактический разбор ядра библиотеки: сигнатуры публичных методов, устройство модулей, найденные ограничения. Код не пересказывается, но каждое утверждение сопровождается ссылкой вида `файл:строка` на место в репозитории, где это можно проверить.

### 1.2 Методология моделирования домена

**Одна таблица на всё.** Хранилище — это одна append-only hypertable `Entity`. Hypertable — таблица TimescaleDB, автоматически разбитая на chunk'и (физические партиции) по времени; здесь партиционирование идёт по колонке `updated`, размер chunk'а — 30 дней. Каждая строка таблицы — это одна версия сущности, а сущность целиком — это все строки с одинаковой тройкой `(partition, class, id)`. Актуальной версией считается строка с максимальным `updated`; сущность считается живой, если у актуальной версии `deleted IS NULL` (см. `README.md:243-261`).

**Классы хранятся как данные.** Классы предметной области — это не TypeScript-классы, а строки служебной таблицы `Schema`. У класса есть `id` и `alias` (английское и русское имя, равноправные в API), `category`, `ancestor` (родительский класс для наследования), `attributes`, `links`, `meta` и `order`. Категория бывает двух видов: `HUB` описывает сущность, `LINK` — связь между сущностями с собственными атрибутами. Поле `attributes` — это описание полей на DSL библиотеки fastest-validator (декларативный язык правил валидации JS-объектов), `links` — концы связи (для LINK-классов; они не наследуются), `meta` — объект вида `{abstract?, history?, description?}`. Производные списки `ancestors` и `descendants` (все предки и все потомки) считает триггер БД `schema_lineage` (см. `README.md:298-338`).

**Наследование атрибутов.** Поля класса собираются по цепочке `ancestor`: правила потомка накладываются поверх правил предка. При этом переопределение поля означает замену правила целиком, а не слияние объектов (см. `README.md:413-418`, `lib/src/schema.ts:243-250`).

**Связи `Schema.links` версии 2.** Концы связи описываются массивом объектов `{class|classes, optional?, cardinality?}`. Вариант `classes: [...]` называется «союзом ролей» — конец связи занимает ровно один класс из перечисленных. Сопоставление переданных концов с объявленными идёт жадно, в порядке объявления. Поле `cardinality` зарезервировано, но не реализовано (см. `README.md:355`, `lib/src/types.ts:81`).

**Генерация идентификаторов.** Правило генерации id задаётся в `attributes.id`, и есть три варианта. UUID v4 — случайный, используется по умолчанию. UUID v7 (`{generate:7}`) кладёт unix-время в миллисекундах в старшие биты, поэтому новые id идут по возрастанию и вставки хорошо ложатся в btree-индекс. UUID v5 (`{generate:5, from:[...]}`) детерминированный: он вычисляется как `sha1(pgSchema:partition:class:значения from)`. Именно v5 даёт идемпотентный `create()` и позволяет знать id до записи, а значит двойная бронь одного и того же слота невозможна уже на уровне схемы — README называет это ключевым паттерном домена (см. `README.md:363-411`).

**Классы без истории (`meta.history: false`).** Эта возможность добавлена в 0.21.0 (DDL_REVISION 2 — вторая ревизия SQL-движка, см. отчёт 02). Класс с таким флагом хранит ровно одну актуальную строку на id: триггер `entity_collapse` типа AFTER INSERT физически удаляет более старые версии того же id сразу после вставки (см. `lib/sql/ddl.sql:574-624`). По умолчанию (`history` отсутствует или равен true) версии накапливаются как обычно. Режим даёт стоимость O(число активных сущностей) вместо O(вся история) на «статусных» сущностях вроде очередей и outbox-таблиц, но методы `.versions()` и `.asOf()` на таких классах теряют смысл — библиотека один раз на пару «класс + метод» выводит предупреждение через `console.warn` (см. `lib/src/chain.ts:296-310`). Уже накопленную историю можно схлопнуть один раз серверной SQL-функцией `compact()`.

**Полиморфизм чтения.** Шаг цепочки по родительскому классу возвращает объединение с потомками: например, `db.Контрагент()` отдаёт и Мастеров, и Клиентов. Модификатор `.exact()` отключает это для конкретного шага. Запись, напротив, не полиморфна: `create()` пишет строго в свой класс, а попытка создать сущность абстрактного класса — ошибка (см. `README.md:420-444`).

**Multi-tenancy (несколько арендаторов в одной схеме).** Арендатор (account) — это свойство вызова, а не подключения. Функция `connect()` не принимает `account`/`owner` (эти опции сняты в 0.20.0); вместо этого `db.as(account, {owner?})` возвращает дешёвый клон контекста на том же пуле соединений. Опция `enforceAccount` включена по умолчанию, поэтому чтение и запись с «безличного» корня `db` под изоляцией падают с ошибкой, в тексте которой есть подсказка вызвать `db.as()` (см. `README.md:1250-1300`; реализация — функция `guardScoped` в `lib/src/sql.ts:590-605`).

**Плейсхолдер имени схемы.** Все `.sql`-шаблоны (DDL и сиды — стартовые наборы данных) содержат маркер `<SCHEMA-NAME>`. Функция `up()` и скрипт `db/apply.mjs` перед накатом заменяют его на реальное имя PG-схемы вида `v<version>.<schema>` (см. `README.md:19-20, 1592-1596`).

### 1.3 Опции `connect(opts: ConnectOpts)`

В таблице перечислены все опции подключения: имя опции, её TypeScript-тип (знак `?` означает необязательность), значение по умолчанию и назначение.

| Опция | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `dsn` | string | — | строка подключения к PostgreSQL |
| `schema` | string | — | **полное** имя PG-схемы с версией (например `'v1.booking'`) — префикс версии не достраивается автоматически |
| `partition` | string? | `'entity'` | пространство данных внутри схемы |
| `max` | number? | `10` | размер пула соединений |
| `enforceAccount` | boolean? | **true** | жёсткая изоляция арендатора |
| `enforceAcl` | boolean? | **false** | ACL по таблицам Resource/Rule; opt-in, запрет по умолчанию (deny-by-default) |
| `onQuery` | fn? | — | хук на каждый SQL-запрос цепочки: `{mode, classes, ms, rows, slow}` |
| `slowMs` | number? | — | порог «медленного» запроса |

Два уточнения к таблице. Если `enforceAcl` выключен, библиотека один раз на процесс выводит предупреждение. Если задан `slowMs`, но не задан `onQuery`, медленные запросы уходят в `console.warn`.

### 1.4 `up(opts: UpOpts)` — bootstrap для разработки

`up()` — единая точка входа для локальной разработки, которая поднимает всё окружение за один вызов. Сначала она пробует подключиться к уже работающему PostgreSQL по `dsn`; если он отвечает, Docker пропускается. Если сервера нет, она поднимает Docker-контейнер (TimescaleDB на PostgreSQL 17 плюс Redis; образ собирается из `lib/docker/`) и ждёт готовности, опрашивая порт каждые 500 мс, но не дольше `waitTimeoutMs = 120000`. Затем она накатывает `ddl.sql` и сиды (по умолчанию — демо-домен booking; свои сиды передаются как `seeds: string[]`, а `seeds: false` отключает их), выполняет `ANALYZE Entity` и вызывает `connect()`.

Каждый шаг идемпотентен — повторный вызов ничего не ломает. Опция `fresh: true` делает `DROP SCHEMA CASCADE` перед накатом. Опция `upgrade: true` перекатывает только `ddl.sql` на существующую схему, не трогая данные, — это путь для аддитивных правок движка.

### 1.5 `db.watch()`, `onQuery` и порог медленных запросов

Метод `db.watch(cb, opts?)` или `db.watch(cls, cb, opts?)` возвращает `Promise<() => void>` (функцию отписки) и даёт realtime-уведомления через механизм `pg_notify`: триггер `entity_notify` публикует событие в канал, имя которого совпадает с именем PG-схемы. В полезной нагрузке события нет данных сущности — только `{partition, class, id, updated, deleted}`; данные при необходимости дочитываются отдельным запросом. Обрывы LISTEN-соединения клиент postgres.js переживает сам (переподключение с backoff и повторный LISTEN), а для обработки NOTIFY, пропущенных за время разрыва, предусмотрена точка `opts.onReconnect`. Если включён `enforceAcl`, события фильтруются до тех классов, для которых у аккаунта есть безусловное разрешение `allow`: проверить предикат-фильтр по одному payload невозможно.

`onQuery` и `slowMs` — единая точка телеметрии, реализованная в функции `runQuery` (см. `lib/src/sql.ts:130-169`). Событие приходит на каждый SQL-запрос цепочек — режимы paths, rows, ids, count, versions, agg, insert, delete. Служебные запросы (загрузка реестра, работа с таблицами, LISTEN) не инструментированы.

### 1.6 §11 API Reference — полный список публичных методов

Публичная поверхность библиотеки делится на несколько уровней: экспорты модуля, корневой объект `EntityDb`, цепочка `Chain`, транзакция `EntityTx`, батч `Batch`, фасады служебных таблиц, `db.auth`, `db.acl` и реестр `Registry`. Ниже они перечислены в том же порядке, что и в README §11.

**Экспорты модуля** (barrel-экспорты, то есть всё реэкспортируется из одной точки входа `lib/src/index.ts`):

- `connect(opts): Promise<EntityDb>` — подключение к существующей схеме;
- `up(opts): Promise<EntityDb>` — dev-bootstrap (см. §1.4);
- `cursorOf(row, field?): Cursor` — построение курсора для keyset-пагинации;
- `uuidv5(name, ns?)`, `uuidv7()`, константа `LETOPIS_NS`;
- `totpCode(secretBase32, atMs?)`;
- 18 операторов фильтров (см. ниже);
- классы `ValidationError` и `Registry`.

**EntityDb — корень (README §11.2).** Это объект, который возвращают `connect()`/`up()`. Он реализован как ES `Proxy` над реестром классов: обращение `db.<Класс>(filter?)` даёт цепочку `Chain` для любого класса из таблицы `Schema`. Остальные члены корня:

- `db.as(account, opts?): Promise<EntityDb>` — контекст арендатора;
- `db.begin(): Promise<EntityTx>`, `db.commit(tr)`, `db.rollback(tr)` — ручные транзакции;
- `db.watch(cb | cls, cb, opts?)` — подписка на события (см. §1.5);
- `db.close(): Promise<void>` — закрытие пула;
- `db.registry: Registry` — реестр классов;
- `db.sql` — «голый» клиент postgres.js;
- `db.reloadSchema(): Promise<void>` — перечитать реестр;
- `db.entity(x): Chain` — шаг по сущности без указания класса;
- `db.batch(name): Batch` — батч;
- фасады служебных таблиц `db.accounts`, `db.credentials`, `db.resources`, `db.rules`, `db.schema`, `db.auth`, `db.acl`.

**Chain — чтение (README §11.3).** Цепочка строится шагами `.<Класс>(filter?)` и завершается терминальным методом, который выполняет SQL. Терминалы: `.run(): Promise<Path[]>`, `.rows(): Promise<Row[]>`, `.first(): Promise<Row|null>`, `.ids(): Promise<string[]>`, `.count(): Promise<number>`, `.versions(): Promise<Row[]>`, а также агрегаты `.sum(field)`, `.avg(field)`, `.min(field)`, `.max(field)`, `.countBy(field)`. Модификаторы, не выполняющие запрос: `.limit(n)`, `.offset(n)`, `.sort(field, dir?)`, `.asOf(t)` (срез на момент времени), `.after(cursor)` в паре с модульным `cursorOf()`, `.exact()` (отключить полиморфизм шага), `.deep(max=32)` (рекурсивный обход self-связи), `.alias(name)`, `.tags(v)`, `.account(v)`, `.owner(v)`, `.withDeleted()` (включить удалённые).

**Операторы фильтров (README §11.4).** Всего 18 операторов плюс `or`: `ne`, `gt`, `gte`, `lt`, `lte`, `between`, `inList`, `like`, `ilike`, `starts`, `ends`, `has`, `hasAny`, `hasAll`, `exists`, `isNull`, `not`, `or`.

**Запись (README §11.5).** Операции записи — это звенья цепочки: `.create(data?)`, `.update(data?)`, слоты связей `.Класс.set(target)` и `.Класс.unset()`, `.delete(opts?: {confirm?})`, `.purge(opts?: {confirm?})`, `.anonymize(fields)`.

**EntityTx (README §11.6):** `tr.commit()`, `tr.rollback()`, `tr.lock(...keys): Promise<void>`.

**Batch (README §11.7):** `db.batch(name): Batch`, `batch.run(): Promise<Row[][]>`, `batch.discard(): void`, `batch.size(): number`.

**Служебные таблицы (README §11.8):** `db.accounts.{find, get, set, delete, purge}`, `db.credentials.{find, set, delete}`, `db.resources.{find, get, set, delete}`, `db.rules.{find, set, delete}`, `db.schema.define(def)`.

**db.auth (README §11.9):** `setPassword`, `verifyPassword`, `issueApiKey`, `verifyApiKey`, `issueKeySecret`, `verifyKeySecret`, `enrollTotp`, `verifyTotp`, `totpEnabled`, `issueOtp`, `verifyOtp`, `link`, `lookup`, а также `sessions(store): Sessions` с методами `start`, `check`, `revoke`, `revokeAll`.

**db.acl (README §11.10):** `check(account, endpoint): Promise<AclDecision>`, `checkData(account, className, op): Promise<AclDecision>`, `reload(): void`.

**Registry (README §11.11):** `resolve(name): ClassDef` (бросает ошибку, если класса нет), `find(name): ClassDef|undefined`, `has(name): boolean`, свойство `all: ClassDef[]`. Ошибка валидации — `ValidationError{message, issues}`.

Итого, по данным `docs/api-contract.json`, Proxy перехватывает имена на трёх уровнях: 52 на уровне chain, 2 на уровне batch и 18 на уровне db. Это соответствует таблице зарезервированных имён в README §3 — такие имена нельзя использовать как имена классов.

### 1.7 §12 — каталог ошибок

README §12 содержит около 35 записей (см. `README.md:3598-3637`). Они сгруппированы по категориям:

- **Класс и схема:** `unknown class "X"`, `ValidationError`, `class "X" is abstract`.
- **Концы LINK-связи:** `requires end`, `stray link(s)`, legacy-вариант `polymorphic end(s)`.
- **Построение цепочки:** `context step must resolve to exactly one entity`, `create() takes no filter`, `create() on a pivot step`, `no path X → Y`, `LINK → LINK …`.
- **Контракт детерминированного id (v5):** `class "X" computes id`, `needs end A|B`, `needs scalar data field`.
- **Слоты связей:** `is not a link end of`, `slot needs an owner step`, `link slot needs a write`, `link end is required — cannot unset`, `duplicate link slot`.
- **Миграционные охранники снесённых имён:** `set() split into create()/update() (0.16.0)`, `slot .delete() renamed to .unset() (0.16.0)`, `execute() renamed to run() (0.11.0)`.
- **Батч:** `plan is queued in the batch`.
- **Multi-tenancy и ACL:** `enforceAccount is on — call db.as(account)…`, `reads/writes are pinned to account X`, `db.as(account) requires an account id`, `enforceAcl is on — call db.as(account)…`.
- **Инфраструктура:** `Entity.account is NOT NULL…`, `violates foreign key constraint`, `lock() works only inside db.begin()`, `commit() needs a transaction`, `schema "X" has no "Schema" table`, `schema "X" has no classes for partition`.
- **Специфичные для `up()`:** `bad schema name`, `bad version`, `docker CLI not found`, `postgres/redis not ready`.

Машиночитаемая версия каталога — ключ `errors` в `docs/api-contract.json`: там 91 запись, то есть шире README, и каждая содержит точный текст сообщения с указанием модуля-источника.

## 2. AGENT-CHEATSHEET.md (246 строк)

Этот файл — однострочная замена 3500 строк README для ИИ-агента. Когда деталей не хватает, он отсылает к README §11 или к `docs/api-contract.json`.

**Минимальный рабочий цикл** описан в семи шагах (см. `AGENT-CHEATSHEET.md:59-113`):

1. Bootstrap: `up({schema, version, seeds})`.
2. Определить классы: `db.schema.define(...)` для каждого HUB/LINK-класса, затем `db.reloadSchema()`.
3. Назвать арендатора: найти системный аккаунт через `db.accounts.find({category:'System'})` и получить контекст `db.as(sys.id)`.
4. Писать: `t.Класс().create(data).rows()` и `t.Класс(id).update(data).rows()`.
5. Читать: атрибуты сущности лежат в `row.data`, а не в корне строки.
6. Удалять в два шага: `.delete()` показывает превью, `.delete({confirm:true})` удаляет.
7. Вызвать `db.close()` один раз на пул.

**22 «грабли»** — сконцентрированный список типовых ошибок (см. `AGENT-CHEATSHEET.md:155-237`). Приводим их полностью, потому что каждая отражает реальную особенность поведения библиотеки:

1. `up()` без опции `seeds` заливает демо-домен booking в любую схему.
2. `connect({schema})` требует полное имя схемы с версией.
3. Глаголы записи возвращают цепочку, а не Promise — нужен терминальный метод.
4. `.purge()` на живой (не удалённой) сущности возвращает `[]` без ошибки; это не значит «стёрто».
5. `.delete()` без `confirm` — только превью, ничего не удаляется.
6. Арендатор — свойство вызова (`db.as()`), а не подключения; `enforceAccount` включён по умолчанию, `enforceAcl` выключен по умолчанию.
7. Нужен System-аккаунт: массив `Account.categories` должен содержать `'System'` (колонка называется `categories`, не `category`).
8. В таблице `Schema` обязателен хотя бы один класс.
9. Чтение полиморфно (шаг по родителю отдаёт и потомков); для точного класса нужен `.exact()`.
10. Существует 52 зарезервированных имени классов — класс с таким именем недостижим как шаг цепочки.
11. Снесённые имена бросают ошибку с подсказкой: `execute→run` (0.11.0), `set→create/update` (0.16.0), слот `.delete→.unset` (0.16.0), `batch.execute→batch.run` (0.11.0); `.link()` снесён в 0.15.0.
12. Невалидный обход графа падает сразу при построении цепочки, а не на терминале; переход `LINK→LINK` запрещён.
13. `count()` считает пути, а не сущности.
14. v5-id детерминирован, поэтому порядок полей в `from` — часть контракта данных.
15. Есть два разных «reload»: `db.reloadSchema()` обновляет реестр и ACL-энфорсер, `db.acl.reload()` — только кэш фасада.
16. Цепочку нужно начинать с самого селективного шага.
17. После массовой заливки обязателен `ANALYZE`, иначе деградация на порядок (см. README §14.1).
18. Обновление npm-пакета не обновляет автоматически движок схемы (`ddl.sql`) — нужен `upgrade: true`.
19. `purge` сносит и связанные LINK-строки (замыкание по связям).
20. `Entity.links` ключуется по `id` класса, а слот-аксессор принимает любое имя (id или alias).
21. Ошибка внутри сида приходит как сырой `PostgresError` без префикса `letopis:`.
22. Полный каталог ошибок — README §12.

### 3.1 Как цепочка компилируется в SQL (обход графа)

Механика чтения сосредоточена в функции `buildRead` (см. `lib/src/sql.ts:607-913`). Важно, что для обычных переходов между классами она не использует рекурсивные CTE. Вместо этого каждый шаг цепочки превращается в подзапрос «последняя версия», и подзапросы соединяются через `JOIN LATERAL` — конструкцию PostgreSQL, которая позволяет правому подзапросу ссылаться на колонки левого, то есть выполняться заново для каждой внешней строки.

Конкретно, каждый шаг даёт блок вида `(SELECT * FROM (SELECT DISTINCT ON (id) e.* FROM Entity e WHERE ... ORDER BY id, updated DESC) t WHERE t.deleted IS NULL AND ...) hN`, и блоки соединяются через `JOIN LATERAL ... ON true` (см. `sql.ts:788-824`). Такая схема заменила «медленные view» прежнего движка.

**Направление обхода** определяет функция `resolveHop(prev, next)` (см. `sql.ts:531-545`). Переход HUB→LINK — это reverse-переход: связь ищется по вхождению (containment) в её колонке `links`. Переход LINK→HUB — forward-переход: id сущности берётся прямо из связи, условие `e.id = prevAlias.links->>'Класс'`, точное равенство без перепроверки. Переход HUB→HUB на тот же класс — reverse (поиск детей). Переход HUB→HUB на другой класс — forward, если `next` есть в `Schema.links` текущего класса, иначе reverse, иначе ошибка `no path`. Переход LINK→LINK — всегда ошибка (см. `sql.ts:544`).

**Кандидаты через GIN и перепроверка на актуальной версии.** GIN — инвертированный индекс PostgreSQL, который умеет быстро отвечать на вопрос «содержит ли jsonb-документ такой фрагмент» (оператор `@>`). Фильтры по вхождению (`data @>`, `links @>`, `tags @>`) сначала сужают множество кандидатов подзапросом `e.id IN (SELECT c.id FROM Entity c WHERE ...)`, использующим GIN-индексы с классом операторов `jsonb_path_ops`. Но GIN видит все версии, а не только последнюю, поэтому истинность условия проверяется повторно уже на выбранной актуальной строке (см. `sql.ts:775-784`).

**Pivot.** Так называется повтор LINK-класса в цепочке или вызов `entity()` для той же переменной. Pivot не создаёт новый блок JOIN, а дописывает AND-условия к уже материализованному узлу через карту `nodeKey → блок` (см. `sql.ts:624-656`, структуры `byNodeKey` и `real[]`).

**Полиморфизм.** Шаг по родительскому классу сопоставляет `class = ANY(id + descendants)` вместо равенства (это множество называется `family`). Уникальность сущности тогда определяется парой `(class, id)`, и вместо `DISTINCT ON (id)` используется `DISTINCT ON (class, id)` (см. `sql.ts:659-735, 786-787`). Модификатор `.exact()` снимает это на уровне конкретного шага.

**`.deep()`** — единственное место с явным `WITH RECURSIVE`. Это рекурсивный self-переход по тому же классу: `UNION ALL` с `JOIN LATERAL` вглубь, счётчик `$depth` инкрементируется, лимит глубины по умолчанию 32 (см. `sql.ts:794-822`). Работает только на self-переходах; максимум задаётся параметром.

**Замыкание удаления** — функция `closureSql` (см. `sql.ts:969-1001`). Это отдельный `WITH RECURSIVE`, который находит целевую сущность и все живые зависимые от неё по `links` рекурсивно, то есть ровно то множество, которое каскадно превратит в tombstone-версии серверный триггер `entity_delete` (tombstone — «надгробие», версия сущности с заполненным `deleted`).

Финальная форма SQL зависит от режима терминала — `paths`, `rows`, `ids`, `count`, `versions` или `agg`. Билдер `buildRead` единый, ветвление по режиму происходит в самом конце (см. `sql.ts:851-909`).

### 3.2 Как работают записи

**Только INSERT, никакого UPDATE.** Вызов `.update()`, как и `.create()` по уже известному id, всегда идёт через `insertOne`: выполняется `INSERT ... updated = GREATEST(clock_timestamp(), prevUpdated + 1µs)`, то есть новая версия получает время не раньше, чем предыдущая плюс микросекунда (см. `insertSql` в `sql.ts:922-932` и `write.ts:187-219`). Физического UPDATE строки не бывает никогда — это дополнительно форсирует триггер в БД (README §2.2).

**Оптимистичная конкуренция через ретрай, а не через столбец версии.** Если две записи одной сущности столкнулись по `updated` (код ошибки PostgreSQL 23505, нарушение уникальности), вставка немедленно повторяется с новым `clock_timestamp()` (см. `write.ts:201-217`). Явного поля для optimistic lock (вроде `version` или `etag`) в контракте нет: конкурентная запись просто создаёт следующую версию. Гонки на уникальность бизнес-данных снимаются иначе — детерминированным v5-id плюс `tr.lock()` (advisory lock — рекомендательная блокировка PostgreSQL по произвольному ключу; паттерн «двойная бронь» описан в README §7).

**Идемпотентность create.** Если вычисленный или явно переданный id уже существует в границах пути, вместо INSERT выполняется `versionRows()` (см. `write.ts:420-445`), то есть создаётся новая версия. Данные сливаются функцией `deepMerge` по листьям объекта `data` (см. `write.ts:106-118`): массивы и скаляры заменяются целиком, `links` домерживаются по ключам, конец-союз замещается целиком.

**Batch.** Функция `executeBatch` выполняет всю очередь батча в одной транзакции (см. `write.ts:892-930`). «Чистые» подряд идущие `create()` одного класса — без `data.id`, без слотов и не с v5-id — склеиваются в один `multiInsertSql` (INSERT с несколькими VALUES). Любой другой план идёт поштучно через обычный `runPlan`. Классы с v5-id никогда не склеиваются, потому что для вычисления id нужны конкретные концы связи.

**План (несколько операций в одной цепочке).** Функция `runPlan` (см. `write.ts:759-818`) режет шаги на сегменты по границам операций (`splitPlan`) и исполняет их по порядку. Продолжение после операции — это fan-out по строкам результата предыдущей операции (`virtualStep`); self-шаг (операция сразу после операции) пишет в те же строки. Хвост цепочки без операций читается тем же `buildRead` в конце той же транзакции.

**Retention и compression** (политики TimescaleDB по удалению старых chunk'ов и их сжатию) в коде библиотеки отсутствуют. Они настраиваются отдельным скриптом `db/policies.mjs`, который не входит в npm-пакет и вызывает `add_compression_policy`/`add_retention_policy`.

### 3.3 Транзакции (tx.ts, 90 строк)

Функция `beginTx(ctx)` резервирует соединение из пула через `sql.reserve()` и отправляет `BEGIN`. Функции `commit`/`rollback` отправляют `COMMIT`/`ROLLBACK` и освобождают соединение через `release()`; повторный вызов безопасен благодаря флагу `done`.

Функция `lock(ctx, ...keys)` выполняет `pg_advisory_xact_lock(hashtextextended(keys.join('|'), 0))` — берёт транзакционную advisory-блокировку по хэшу склеенных ключей. Она работает только внутри транзакции (иначе ошибка) и держится до её конца.

**Уровень изоляции.** Явного `SET TRANSACTION ISOLATION LEVEL` в коде нет нигде — используется уровень PostgreSQL по умолчанию, READ COMMITTED.

**Savepoints.** Публичного API нет: `tx.ts` не экспортирует ничего похожего на savepoint, и библиотека не предоставляет вложенные транзакции как возможность.

**Ретраи.** Константа RETRIES=3, задержка перед повтором `40*attempt + random(0..40)` мс (функция `retryDelay`, см. `sql.ts:117-118`). Транзиентными считаются коды `40P01` (deadlock) и `40001` (serialization failure) (функция `isTransient`, см. `sql.ts:103-106`). Чтения в режиме автокоммита повторяются до 3 раз. Внутренние транзакции записи — обёртка `inTransaction` (см. `write.ts:602-619`), которую используют `delOp`, `purgeOp`, `runPlan` и `executeBatch`, когда `!ctx.inTx`, — повторяют всю транзакцию целиком. Внутри пользовательской `db.begin()` ретрай невозможен семантически, потому что вся транзакция уже в состоянии aborted; ошибка сразу пробрасывается с дописанной подсказкой `hintTxRetry` (`retry the whole db.begin() block`, см. `sql.ts:108-114`).

### 3.4 Валидация (fastest-validator)

Схема класса берётся из `Schema.attributes` (DSL fastest-validator), собирается по цепочке `ancestor` функцией `buildDef` (см. `schema.ts:228-314`) и компилируется вызовом `new Validator({useNewCustomCheckerFunction:true}).compile({...attrs, $$strict:true})` (см. `schema.ts:41-45, 255-259`). Флаг `$$strict:true` означает, что валидация всегда строгая: поля, не описанные в схеме, запрещены.

Ключ `attributes.id` особый: помимо правила валидации он несёт спецификацию генерации id (`generate`/`from`), которую функция `parseIdGen` вырезает перед компиляцией валидатора (см. `schema.ts:189-218`).

Типы полей для SQL-приведений выводятся отдельно функцией `fieldTypeOf` (см. `schema.ts:84-138`), рекурсивно по `record`/`object`. Эти типы использует `sql.ts` для кастов `::numeric`, `::timestamptz` и `::boolean` в фильтрах, сортировке и агрегациях.

Ошибка валидации — класс `ValidationError extends Error` с полем `issues: {field, type, message}[]` (см. `write.ts:60-64`).

### 3.5 ACL-модель (acl.ts, 352 строки)

**Формат правил.** Таблица `Resource` (колонки `alias, category, pattern, meta`) описывает и субъектов, и объекты доступа; вид определяет `category`. `ACCOUNT` — шаблон группы аккаунтов по их `categories`. `API` — маска эндпоинта: сегменты через `.`, альтернативы `{a,b}`, подстановочный `*`. `READ`/`WRITE`/`DELETE` — шаблон строки Entity из реальных колонок и плейсхолдера `"$account"`, который подставляется рекурсивно функцией `substitute()` (см. `acl.ts:172-180`). Таблица `Rule` (`account → resource`, `permission: allow|deny`, `weight`, `enabled`) связывает субъект с объектом; оба конца правила — всегда alias ресурсов, никогда не конкретный аккаунт напрямую. Принадлежность аккаунта к субъекту вычисляется на лету из `Account.categories`.

**Точки применения.** Их две, и они независимы. Первая — справочный фасад `db.acl.check`/`checkData`: это рантайм-запрос по требованию, который каждый вызов ходит в SQL за категориями аккаунта. Вторая — энфорсер цепочек при `enforceAcl`, функция `compileEnforcer(src, account, cats, registry)` (см. `acl.ts:309-339`). Она возвращает синхронную функцию `(cls, op) → AclDecision` с memo-кэшем по ключу `"class op"` без аккаунта, поэтому один энфорсер строго соответствует одному субъекту; компилируется он при `db.as()` и `reloadSchema()`, а не при `connect()`. Внутри `buildRead` энфорсер вызывается на каждый шаг цепочки как READ; в `aclWrite` (write.ts) — на create/update как WRITE, а на delete — как DELETE по каждому классу каскада (см. `write.ts:643-652`).

**Принятие решения.** Побеждает ровно одно правило: с максимальным `weight`; при равном весе deny бьёт allow; при равных allow побеждает правило с меньшим `alias` ресурса (детерминированный tie-break). Если применимых правил нет — запрет по умолчанию (функция `decide`, см. `acl.ts:190-219`). У победившего allow остаточные ключи `pattern` (кроме `class`) становятся `filter` — предикатом строк, который вливается в SQL до сортировки и лимита, причём и в кандидатные GIN-подзапросы, и в перепроверку (см. `sql.ts:696-720`).

**Кэш источника правил.** Словарь Resource/Rule читается одним SELECT на всё подключение, а не на каждый `db.as()`: снимок `aclSource` кэшируется в `index.ts:connect()`. На уровне отдельного контекста арендатора остаётся только чтение своего аккаунта и сама компиляция резолвера.

### 3.6 Auth (auth.ts, 501 строка)

**Пароли.** Хэширование — scrypt из `node:crypto`, без внешних зависимостей, с параметрами `N=32768, r=8, p=1, keylen=32` и солью 16 байт. Формат хранения: `scrypt$N$r$p$saltB64$hashB64` (см. `auth.ts:45-62`). Сверка выполняется через `timingSafeEqual`. Если пользователь с таким identifier не найден, выполняется `dummyVerify` — тот же scrypt на нулевой соли, чтобы время ответа не выдавало, существует ли логин (см. `auth.ts:81-83, 304-313`). Legacy-хэши bcrypt (`$2b$...`) не верифицируются.

**API-ключи.** Формат `lts_<48hex>` (24 случайных байта). В БД хранится только `sha256(key)` как identifier плюс `prefix` для отображения в UI. **Пара key+secret:** `key` — 8 байт hex (открытый идентификатор пары), `secret` — 24 байта hex; в БД `sha256(secret)`, сравнение через `timingSafeEqual` по hex-строкам.

**TOTP** (одноразовые коды по времени, как в Google Authenticator). Реализация — RFC 6238 (HMAC-SHA1, 6 цифр, шаг 30 с) поверх ручной реализации HOTP (RFC 4226) и base32, без внешних библиотек (см. `auth.ts:100-176`). Для QR-кода формируется `otpauth://` URI. Повтор кода того же временного шага отбивается через `meta.lastStep`; фактор активируется первой успешной проверкой.

**OTP** (одноразовый код, например для входа по SMS/e-mail). В БД хранятся `sha256(code)`, срок `expires` и счётчик `attempts`; успешная проверка либо достижение `maxAttempts` (по умолчанию 5) сжигают учётные данные.

**JWT отсутствует.** Токены никогда не самоописывающиеся. Сессионный токен — 32 случайных байта в hex, в Redis хранится только `sha256(token)`. Для api-key и key-secret то же самое: в БД sha256, открытый текст отдаётся один раз при выпуске.

**Внешняя identity** (oauth/sso/telegram) — только связка через `link`/`lookup`. Проверку внешнего токена и сам OAuth-обмен библиотека сознательно оставляет приложению.

Единая точка инварианта — частичный уникальный индекс `credential_identity_udx`: один живой набор учётных данных на пару `(category, identifier)` во всей схеме. Уникальность обеспечивается на уровне БД, а не в JS.

### 3.7 Sessions (sessions.ts, 146 строк)

Redis-клиент не входит в зависимости пакета. Он инжектируется через минимальный интерфейс `SessionStore {set, get, del, sadd, srem, smembers, expire}`; ioredis подходит как есть.

Ключи в Redis: `sess:<sha256(token)>` хранит JSON `{account, meta, created}` с `EX ttlSec`; `sess:acc:<accountId>` — Set-индекс для группового отзыва, без TTL (протухшие хэши в нём безвредны).

TTL по умолчанию — 7 суток (`DEFAULT_TTL = 7*24*3600`, см. `sessions.ts:63`). `start()` отдаёт токен один раз; `revokeAll()` читает `smembers` индекса и удаляет все ключи разом.

### 3.8 uuid.ts (72 строки)

`uuidv5(name, ns=LETOPIS_NS)` реализует RFC 4122 v5: `sha1(nsBytes + name)`, берутся первые 16 байт дайджеста, биты версии и варианта выставляются вручную (`h[6] = (h[6]&0x0f)|0x50`, `h[8]=(h[8]&0x3f)|0x80`). Namespace библиотеки — константа `c7a2f9d4-3b61-4e8a-9f05-8d2c1e6b7a90`.

`uuidv7()` — самописная реализация RFC 9562 v7, не через сторонний пакет: 48 бит unix-времени в миллисекундах в 6 старших байтах (`writeUIntBE(Date.now(),0,6)`) плюс 10 случайных байт (`randomBytes(10)`); биты версии и варианта выставляются так же вручную.

UUID v4 генерируется не здесь, а в `write.ts:365` через `randomUUID()` из `node:crypto`.

### 3.9 ops.ts (92 строки) — операторы фильтра

Фабрика `op(name, ...args) → {[OP]: name, args}` создаёт узел оператора; ключ `OP` — это Symbol, поэтому узлы не пересекаются с пользовательскими данными. Экспортируемые операторы: `ne`, `gt`, `gte`, `lt`, `lte`, `between`, `inList`, `like`, `ilike`, `starts` (эквивалент `like(s+'%')`), `ends` (эквивалент `like('%'+s)`), `has`, `hasAny`, `hasAll`, `exists(yes=true)`, `isNull`, `not`, `or`. Все они — чистые фабрики; компиляция в SQL и приведение типов по типу листа выполняются в `compileOp` (см. `sql.ts:318-389`).

## 7. Типобезопасность и кодогенерация

Ядро библиотеки полностью динамическое. Объекты `EntityDb`, `Chain` и `Batch` — это ES `Proxy` над реестром классов, который загружается в рантайме из таблицы `Schema` (функции `makeChain`/`makeDb`, см. `chain.ts:430-984`). На уровне TypeScript без кодогенерации шаг класса типизирован индексной сигнатурой `[className: string]: StepProp`, то есть опечатка в имени класса компилируется без ошибки.

Типизированные запросы достигаются отдельным шагом кодогенерации — скриптом `scripts/gen-types.mjs`. Он подключается к реальной БД (по `dsn` и `schema`) и печатает статический `.d.ts` с конкретными интерфейсами `data`-полей на каждый класс (с учётом наследования `attributes`) и с конкретными методами-шагами вместо индексной сигнатуры. Используется это так: `const t = db as unknown as TypedDb`. Это приведение типа, а не структурная генерация самого клиента: рантайм-объект остаётся тем же Proxy, а тайпчек ловит только опечатки в статически известных путях.

Зарезервированные имена классов кодогенератор автоматически исключает из типизированных шагов — иначе тип предлагал бы метод, недостижимый в рантайме. `TypedDb` — строгий фасад: только шаги по классам, опечатка означает ошибку tsc. `TypedFullDb` включает `begin/batch/auth/acl/tables`, но опечатки в них не ловит.

Компиляция валидатора fastest-validator — тоже рантайм-шаг (см. `schema.ts:255`), никак не связанный с TS-типами. Поэтому расхождение между типами из `gen-types.mjs` и реальной схемой в рантайме статически не поймать; оно проявится только как `ValidationError` при записи.

## 8. Явные ограничения, TODO и известные границы

Комментариев `TODO`/`FIXME`/`HACK` в `lib/src/*.ts` не найдено — выполнен полный grep по всем 14 файлам. Вместо них обнаружены задокументированные архитектурные ограничения, перечисленные ниже.

**Обход `LINK → LINK` не поддерживается.** Это жёсткая ошибка при построении цепочки: `letopis: LINK → LINK traversal is not supported` (см. `lib/src/sql.ts:544`; дублируется в комментарии `sql.ts:528`). Обход через связку требует pivot — повтора имени связи.

**`cardinality` в `Schema.links` зарезервировано, но не реализовано.** DSL принимает это поле, но рантайм его не проверяет. Комментарий в типах гласит: «ЗАРЕЗЕРВИРОВАНО (не имплементировано): 0 — безлимит, N — точное число» (см. `README.md:355`, `lib/src/types.ts:81`). На практике множественность связи выражается отдельными LINK-строками, а не этим полем.

**Пересечения интервалов бронирования библиотека не проверяет.** EXCLUDE-constraint на hypertable невозможен. Двойная бронь одного и того же момента времени закрыта детерминированным v5-id, но частичное наложение разных интервалов — явная зона ответственности приложения (README §13 «Что контролирует приложение»).

**Бизнес-валидации домена вне библиотеки.** README §13 явно перечисляет как границу: соответствие навыка мастера услуге, попадание интервала записи в окно смены, суммирование стоимости по составу комплекса.

**Auth: часть механик «осознанно на приложении».** OAuth-обмен, проверка внешних токенов, rate-limit и блокировка после N неудачных попыток остаются приложению (см. `README.md:1050-1052`). Legacy-хэши bcrypt (`$2b$...` из дампа) библиотека не верифицирует — требуется `setPassword` заново.

**Нет изоляции транзакций выше READ COMMITTED и нет API savepoint.** В исходниках не найдено ни одного `SET TRANSACTION ISOLATION LEVEL` или `SAVEPOINT`. Конкурентные гонки закрываются паттерном `tr.lock()` плюс детерминированный id, а не уровнем изоляции БД.

**`up()` — явно dev-инструмент.** README прямо пишет, что пакетный образ из `docker/` (Redis без пароля и без персистентности) — «dev-удобство, не для прода» (см. `README.md:232`).

**Партиционирование только по времени.** Hash-размерности намеренно убраны; README оговаривает компромисс: точечный доступ не выигрывает, но обходы графа быстрее в разы (см. `README.md:260`; обоснование — `bench/dimensions.bench.mjs`).

**`.versions()`/`.asOf()` теряют смысл на классах с `meta.history:false`.** Это не ошибка, а предупреждение через `console.warn` (см. `lib/src/chain.ts:300-309`) — архитектурно осознанный компромисс: скорость фильтров против полноты истории.

**Эксплуатационные «known issues»** сосредоточены в README §10.12 («Устойчивость к сбоям») и §14.1 («ANALYZE обязателен»). Это не баги, а задокументированные операционные требования: без `ANALYZE` после массовой заливки чтения деградируют до ×126 (README §14.1, таблица с реальными замерами).
