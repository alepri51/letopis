# Предложение: «Свод» — лёгкое хранилище с цепочками, правами и целостностью, которую держит сама база данных

> Дата: 2026-10-06, редакция 3. Статус: предложение, к реализации не утверждено.
> Контекст: синтез трёх источников — текущей letopis 0.21.0 и двух предложений-преемников, «Свитка» (`reports/PROPOSAL-SVITOK.md`) и «Записи» (`reports/ZAPIS-CONCEPT.md`). Название выбрано по аналогии с летописным сводом, который собирает несколько летописей в одну.
> Редакция 2 учитывает замечания владельца: модели на Zod, регистр имён (хабы с заглавной буквы, связи со строчной), множественные концы, роли вместо `via`, переход сущности из класса в класс, полиморфные концы, механика имперсонации, назначение и инвалидация сессий, быстрый сброс. Добавлен полный перенос фич letopis (§15).
> Редакция 3: идентификатор v5 у всех классов — если естественного ключа нет, ключом служит `ref` (§7); хаб с несколькими именованными концами, включая ссылку на свой класс (§5).
> Ключевые утверждения о текущем поведении letopis сопровождаются ссылками на код. Всё, что касается «Свода», — проект; оценки объёма и стоимости помечены как оценки.

## 1. Идея в одном абзаце

«Свод» сохраняет всё, ради чего создавалась letopis: цепочки навигации по графу, хабы и связи с собственными данными в одной таблице, классы как данные, детерминированные идентификаторы v5, историю каждой записи, арендаторов, ACL и вход одного аккаунта через разные креды. У «Свитка» и «Записи» он берёт лёгкость: обычный PostgreSQL без TimescaleDB, Redis и Docker, таблицу текущего состояния рядом с журналом версий, номер ревизии против потерянных обновлений, надёжный поток событий по курсору и описание моделей стандартным валидатором вместо собственного языка. Главное новое свойство состоит в том, что все инварианты держит сама база данных. Проверка данных по описанию класса, ссылочная целостность, вычисление v5, неизменяемость журнала, изоляция арендаторов и ACL работают одинаково для библиотеки и для сырого SQL. Библиотека при этом превращается в тонкий клиент, который переводит цепочки в SQL.

### Что берётся у каждого из трёх проектов

**У letopis** — практически всё пользовательское: цепочки со всеми переходами, pivot, переменными-узлами, рекурсией, агрегатами и keyset-пагинацией; запись планами со слотами, вложенными цепочками и батчами; хабы и связи с данными; классы как данные с наследованием и полиморфным чтением; детерминированные идентификаторы v5, которые в «Своде» становятся единственным видом; полная история и срезы на момент времени; превью удаления и двухфазное физическое удаление; модель ACL; все виды кредов; оркестратор `up()`, ревизия движка, телеметрия и документация для агентов. Полная таблица переноса — в §15.

**У «Свитка»:** текущее состояние отдельно от истории; ревизия и атомарное слияние вместо потерянных обновлений; поток событий из журнала с горизонтом завершённых транзакций; автор и причина в каждой версии; RLS как барьер в самой базе; модели на стандартном валидаторе с выводом типов без кодогенерации.

**У «Записи»:** арендатор как пространство имён v5 и канонизация значений ключа; правило «голый SQL тоже попадает в историю»; журнал в роли надёжного outbox; единственная обязательная рантайм-зависимость — драйвер `postgres`.

**Чего нет ни у одного из трёх:** проверка данных по схеме внутри базы; ACL и сессии, которые действуют и на сырой SQL; полиморфные и множественные концы связей; переход сущности из класса в класс; схема и права как обычные сущности с историей; проверяемая цепочка хэшей в журнале; штатный быстрый сброс.

## 2. Шесть обязательных требований

| 6. Целостность даже против сырого SQL | частичная: дыры перечислены в §9.4 | триггеры и права на журнал | один триггер на журнал | данные, ссылки, ключи, журнал, арендаторы и права держит база (§9) |

## 3. Хранение

Нужен PostgreSQL 15 или новее и одно расширение — pgcrypto. Оно даёт SHA-1 для v5, HMAC для TOTP и криптостойкие случайные байты для токенов; pgcrypto относится к доверенным расширениям и доступно на всех распространённых управляемых PostgreSQL и в PGlite. TimescaleDB, Redis и Docker не нужны.

Данные лежат в двух таблицах, ещё две приватные таблицы обслуживают вход.

```sql
create extension if not exists pgcrypto;
create schema svod;

-- Текущее состояние: одна строка на идентификатор — хабы, связи и системные классы
create table svod.entity (
  id         uuid primary key,
  tenant     uuid not null references svod.entity (id),   -- арендатор: строка класса Account
  class      text not null,
  cv         int  not null,                  -- ревизия описания класса, по которой проверена строка
  rev        int  not null,                  -- ревизия самой строки
  links      jsonb not null default '{}',    -- {роль: id} или {роль: [id, …]} для множественных концов
  ends       uuid[] generated always as (svod.link_ids(links)) stored,  -- все цели плоским списком
  data       jsonb not null default '{}',
  tags       text[] not null default '{}',
  owner      uuid not null references svod.entity (id),
  created_at timestamptz not null,
  created_by uuid not null,
  updated_at timestamptz not null,
  updated_by uuid not null,
  hash       bytea not null                  -- хэш последней версии, голова цепочки
);
create index on svod.entity (class, tenant);
create index on svod.entity using gin (ends) with (fastupdate = off);
create index on svod.entity using gin (data jsonb_path_ops);

-- Журнал: полный снимок каждой версии; приложению разрешено только чтение
create table svod.log (
  seq    bigint generated always as identity,
  tx     xid8 not null default pg_current_xact_id(),
  at     timestamptz not null,               -- время версии, монотонное для каждого id
  tenant uuid not null,
  id     uuid not null,
  class  text not null,
  cv     int  not null,
  rev    int  not null,
  op     text not null,                      -- create, update, delete, restore, reclass, purge, reset
  links  jsonb,
  data   jsonb,
  tags   text[],
  owner  uuid,
  author uuid not null,                      -- от чьего имени сделана версия
  agent  uuid,                               -- сервис, если он действовал от имени пользователя
  reason text,                               -- причина изменения, если её передали
  moved  uuid,                               -- прежний id, если сущность сменила идентификатор (§8)
  hash   bytea not null                      -- sha256(хэш предыдущей версии || снимок)
) partition by range (at);
create index on svod.log (id, rev);
create index on svod.log (tx, seq);
```

Строка журнала устроена так же, как строка `Entity` в letopis сегодня: это полный снимок версии. Поэтому `versions()` и `asOf()` сохраняют прежний смысл, а текущее состояние больше не вычисляется из истории через `DISTINCT ON` (сейчас это делает каждый шаг чтения, `lib/src/sql.ts:684-688`).

Журнал разбит на месячные партиции: старую историю можно удалять целыми партициями, не задевая текущее состояние. Сейчас удаление старых чанков TimescaleDB (`db/policies.mjs:72-73`) уносит и сущности, которые давно не менялись, потому что их единственная версия лежит в старом чанке.

Идентичность сущности — один `id`. В letopis это пара `(class, id)` (`lib/sql/ddl.sql:102`), и сменить класс сущности нельзя; в «Своде» класс меняется штатной операцией (§8).

Приватные таблицы `svod.credential` и `svod.session` хранят креды и сессии (§11). У приложения к ним нет никакого доступа, только к функциям входа.

### Всё — сущность

Служебные данные хранятся строками той же таблицы `entity` под системным арендатором:

| Класс | Категория | Что хранит |
|---|---|---|
| `Class` | HUB | описание класса: поля в JSON Schema, концы, ключ, наследование, метаданные |
| `Account` | HUB | аккаунт: имя, категории, признак `enabled`; каждый аккаунт одновременно является арендатором для своих данных |
| `member` | LINK, роли `User` и `Tenant` | членство пользователя в чужом арендаторе вместе с ролями |
| `Resource` | HUB | ресурс ACL: категория и шаблон |
| `rule` | LINK, роли `Group` и `Object` | правило ACL: разрешение или запрет, вес, сообщение |

Отсюда бесплатно следуют история и аудит изменений схемы и прав, срезы на момент времени («у кого был доступ 1 сентября»), цепочки по служебным данным (`t.User(a).member().Tenant().rows()`) и единая точка проверки целостности. Записи о физическом удалении, обрезке истории и сбросе тоже попадают в тот же журнал.

Арендатор каждой строки — это строка класса `Account`; у системного аккаунта арендатором служит он сам. Внешние ключи `tenant` и `owner` не позволяют удалить аккаунт, пока у него есть данные, — как ограничения `RESTRICT` в letopis сегодня.

### Что уходит из letopis

Из letopis уходят колонка `partition` (отдельные пространства данных становятся отдельными схемами PostgreSQL), hypertable и сжатие TimescaleDB (их заменяют партиции журнала), GUC-переключатели вроде `letopis.purge`, функция `compact`, Redis, Docker в `up()`, флаги `enforceAccount` и `enforceAcl` (изоляция и ACL включены всегда) и валидатор fastest-validator — его место занимает Zod.

## 4. Модель на Zod

Поля классов описываются на Zod 4 — стандартном валидаторе экосистемы TypeScript. Концы, ключ и метаданные класса описываются рядом. Из одного описания получается:
- статический тип без генерации кода (`Infer<typeof X>`);
- проверка в библиотеке с понятными сообщениями ещё до обращения к базе;
- JSON Schema полей (`z.toJSONSchema()`), которая уходит в строку класса `Class` и по которой данные проверяет сама база.

```ts
import { z } from 'zod';
import { hub, link, one, many, type Infer } from 'svod';

export const Org = hub('Org', {                    // ключа нет — ключом служит ref (§7)
  alias: 'Организация',
  fields: z.object({
    name: z.string().min(1),
    timezone: z.string().default('Europe/Moscow'),
  }),
});

export const Person = hub('Person', {
  alias: 'Контрагент',
  abstract: true,
  ends: { Org },                                   // концы наследуются потомками
  fields: z.object({
    name: z.string().min(1),
    phone: z.string().meta({ trim: true }),        // нормализацию выполняет и база
  }),
});

export const Staff = hub('Staff', {
  alias: 'Мастер',
  extends: Person,
  fields: z.object({ specialization: z.string().optional() }),
});

export const Element = hub('Element', {
  alias: 'Элемент',
  abstract: true,
  ends: { Org },
  fields: z.object({ name: z.string().min(1) }),
  key: ['Org', 'name'],                            // v5: одно имя в организации; наследуется
});

export const Complex = hub('Complex', {
  alias: 'Комплекс',
  extends: Element,
  ends: { Items: many(Element) },                  // множественный конец: состав без своих данных
  fields: z.object({ cost: z.number().int().min(0) }),
});

export const skill = link('skill', {
  alias: 'навык',
  ends: { Staff, Service },                        // ключ по умолчанию — концы: одна связка на пару
  fields: z.object({
    level: z.enum(['basic', 'intermediate', 'advanced', 'expert']).default('intermediate'),
  }),
});

export const slot = link('slot', {
  alias: 'окно',
  ends: { Staff, Location, Schedule },
  fields: z.object({ start: z.iso.datetime(), end: z.iso.datetime() }),
  key: ['Staff', 'start'],                         // мастер не задваивает время
});

export const booking = link('booking', {
  alias: 'запись',
  extends: slot,                                   // наследует поля, концы и ключ окна
  ends: {
    Item: one(Element),                            // любой потомок Element: услуга, товар, комплекс
    Customer: one(Customer).optional(),            // ручная бронь — без клиента
  },
  fields: z.object({ notes: z.string().optional() }),
  onDelete: { Customer: 'unset' },                 // удалили клиента — запись остаётся без него
  meta: { description: 'Бронь мастера на элемент каталога', appearance: { icon: 'mdi:calendar-check' } },
});

export type Booking = Infer<typeof booking>;
```

Остальные классы демо-домена (`lib/sql/seed.booking.sql`) описываются так же. Имена следуют соглашению letopis: хабы — с заглавной буквы (`Staff`, `Мастер`), связи — со строчной (`booking`, `запись`).

### Почему Zod, а не собственный язык описаний

- Это стандарт де-факто: его знают, у него есть вывод типов, документация и инструменты. Не нужно поддерживать ни fastest-validator, ни свой язык описаний.
- Zod 4 сам отдаёт JSON Schema (`z.toJSONSchema()`, драфт 2020-12). JSON Schema становится общим языком с базой, с агентами (описания инструментов MCP — это JSON Schema) и с другими языками: будущий порт на Python из `BACKLOG.md` прочитает те же описания.
- Вместо Zod можно взять Valibot или ArkType: обе библиотеки тоже отдают JSON Schema по стандарту Standard JSON Schema.

У этого выбора есть границы, и их нужно знать заранее:
- `refine` и `superRefine` в JSON Schema не попадают — Zod их молча опускает. Такие правила работают только в библиотеке, и `svod sync` перечисляет их при синхронизации.
- `transform` и `z.date()` в JSON Schema непредставимы. Даты описываются строками `z.iso.datetime()` — так letopis их и хранит, чтобы не терять микросекунды.
- Нормализация, которую должна выполнять и база (`trim`, `lower`), задаётся через `.meta()`: произвольные ключи метаданных Zod переносит в JSON Schema.
- Вывод `toJSONSchema` слегка меняется между минорными версиями Zod, поэтому библиотека фиксирует версию и сохраняет в `Class` уже нормализованную схему.

База проверяет подмножество JSON Schema, которого хватает для всего, что сейчас описывает letopis, включая `record` и вложенные объекты: `type`, `enum`, `const`, `minLength`, `maxLength`, `pattern`, `format` (`email`, `uuid`, `date`, `date-time`), `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `items`, `minItems`, `maxItems`, `uniqueItems`, `properties`, `required`, `additionalProperties`, `propertyNames`, `anyOf`, `oneOf`, `default`. Описание с ключевым словом вне этого списка база не принимает, поэтому ни одно правило не будет молча проигнорировано.

### Та же модель — данными

Модели на TypeScript необязательны. Описание класса — это обычная строка, которую можно записать сырым SQL, например из админки или скрипта:

```sql
begin;
select set_config('svod.token', '<токен сессии администратора>', true);
insert into svod.entity (class, data) values ('Class', '{
  "id": "skill", "alias": "навык", "category": "LINK",
  "ends":   { "Staff": { "class": "Staff" }, "Service": { "class": "Service" } },
  "fields": { "type": "object", "additionalProperties": false,
              "properties": { "level": { "type": "string", "default": "intermediate",
                                         "enum": ["basic", "intermediate", "advanced", "expert"] } } }
}');
commit;
```

Арендатора, идентификатор, ревизии и авторство заполнит триггер. Он же проверит само описание, пересчитает цепочку наследования и сверит изменение с уже существующими данными (§8). Правка строки `Class` действует сразу, библиотека подхватывает её по подписке без переподключения — так же, как сейчас работают `schema.define()` и `reloadSchema()`. Команда `svod sync` превращает модели TypeScript в такие строки, а `svod types` делает обратное: генерирует объявления для классов, созданных данными.

Метаданные класса letopis сохраняются: `alias`, `description`, `appearance` (иконка и цвет), `order`, `abstract`, `history`. Сейчас `description` и `appearance` лежат только в сиде, и код их не читает (`lib/sql/seed.booking.sql:8`). В «Своде» база их тоже не проверяет, но они попадают в машинное описание модели (§14) и годятся для автоматического построения интерфейса.

## 5. Связи: роли, полиморфизм, множественность

**Концы.** Класс объявляет концы: имя конца (роль) и класс цели, по одному id на конец. Концов может быть сколько угодно, у хабов так же, как у связей, и база проверяет каждый. По умолчанию роль называется так же, как класс цели (`Staff`), поэтому форма данных letopis (`{"Staff": "<id>"}`) сохраняется.

Хаб может ссылаться сразу на несколько хабов, в том числе на хаб своего класса, и каждому концу можно дать собственное имя:

```ts
export const Customer = hub('Customer', {
  alias: 'Клиент',
  extends: Person,                                 // конец Org приходит от Person
  ends: {
    Master: one(Staff).optional(),                 // свой мастер
    Referal: one(Customer).optional(),             // клиент, который привёл этого
  },
  onDelete: { Master: 'unset', Referal: 'unset' },
  fields: z.object({ notes: z.string().optional() }),
});
```

Строка клиента хранит все три конца в одном `links`: `{"Org": "…", "Master": "…", "Referal": "…"}`. Каждый конец проверяется отдельно: цель существует, принадлежит тому же арендатору и относится к объявленному классу или его потомку. В цепочках имя конца работает как шаг в обе стороны (§6):

```ts
await t.Клиент(anna).Master().first();     // мастер Анны
await t.Мастер(vasya).Клиент().rows();     // клиенты, у которых Вася — свой мастер
await t.Клиент(anna).Referal().first();    // кто привёл Анну
await t.Referal(anna).Клиент().rows();     // кого привела Анна
```

В letopis хаб тоже может ссылаться на несколько хабов: так устроена папка со ссылками на организацию и на родительскую папку (`lib/sql/seed.booking.sql:52`). Но ключом конца там служит имя класса. Поэтому конец нельзя назвать (`Referal`) и на один класс нельзя сослаться дважды. Концы хабов не проверяет ни триггер, ни библиотека (`lib/sql/ddl.sql:189`, `lib/src/write.ts:96`). А родителя по ссылке на свой класс шагом цепочки не получить — только из `row.links` (`lib/test/core.test.ts:192`).

**Полиморфизм.** Конец, объявленный классом X, принимает X и всех его потомков, включая тех, что появятся позже; сам X может быть абстрактным. Конец `Item: one(Element)` принимает услугу, товар и комплекс. В letopis так нельзя: конец сопоставляется с ключом `links` только по точному имени класса (`lib/sql/ddl.sql:195-211`), поэтому потомков приходится перечислять союзом (`lib/sql/seed.booking.sql:68`), и новый потомок в союз сам не попадает. Союзы остаются: `one(Service, Product)` принимает потомков каждого из классов. Перенос класса в другое место иерархии база проверяет по существующим ссылкам.

**Множественность** — другое: это не несколько концов, а список целей в одном конце. `many(X, { min, max })` объявляет такой конец; `links` хранит для него массив идентификаторов. Так реализуется зарезервированная в letopis `cardinality` (`lib/src/types.ts:34`), которую нынешний формат `{класс: id}` выразить не может. Выбор между множественным концом и связью-классом такой:
- если нужен просто набор ссылок без собственных данных (состав комплекса, участники события), это множественный конец прямо в хабе;
- если у каждой пары есть свои данные или своя история (порядок и количество в составе, уровень навыка, бронь), это связь-класс, как сейчас.

Изменение списка — это новая версия строки. Добавление и удаление элемента выполняются атомарно, без предварительного чтения списка, поэтому параллельные правки не теряются.

**Имя конца** можно дать любому концу, а обязательно оно в одном случае: когда у класса два конца к одному и тому же классу. Примеры: перевод между счетами (`Отправитель` и `Получатель`, оба `Счёт`), правило ACL (`Group` и `Object`, оба `Resource`), родство (`Родитель` и `Ребёнок`, оба `Person`). В letopis такие классы невыразимы: ключ `links` — это класс, и второй конец того же класса занять нечем. Концы указывают на хабы, поэтому их имена пишутся с заглавной буквы. Как они используются в цепочках, показано в §6.

**Удаление цели.** Для каждой роли описание задаёт `restrict` (по умолчанию), `cascade` или `unset`. Для множественного конца `unset` убирает идентификатор из списка.

**Наследование концов.** Концы наследуются вместе с полями: `booking` получает концы `slot` и добавляет свои. В letopis `links` не наследуются (`lib/src/schema.ts:4-6`), и каждый потомок объявляет их заново.

## 6. Цепочки

### Имена

Как в letopis: хабы пишутся с заглавной буквы (`Мастер`, `Staff`), связи — со строчной (`навык`, `skill`), шаг можно назвать по id класса или по алиасу.

Методы цепочки — строчные латинские слова, поэтому совпасть с ними может только имя связи. Список методов один на всю библиотеку: он генерируется из кода, попадает в контракт API и проверяется при определении класса — и в библиотеке, и в базе. В letopis зарезервировано 52 имени, и список вручную продублирован в нескольких местах (`lib/src/types.ts:286-301`, `lib/scripts/gen-types.mjs`). В «Своде» из него уходят фасады `accounts`, `credentials`, `resources`, `rules` и `schema` (теперь это системные классы), остаются только методы цепочки и корня.

### Грамматика и переходы

Корень цепочки — область действия сессии `t = db.as(session)`, шаг — класс, алиас или роль с необязательным фильтром, в конце — терминал. Правила перехода те же, что сейчас (`lib/src/sql.ts:446-459`): из хаба в связь переход идёт в обратную сторону, из связи в хаб — в прямую, между двумя хабами — по объявленному концу, шаг к тому же классу хаба ведёт к его детям, а переход из связи в связь — ошибка. Повтор связи в читающем сегменте возвращает цепочку к уже введённому узлу (pivot, `lib/src/chain.ts:358`). Сохраняются переменные-узлы `entity()`, старт цепочки от готовой строки `db.entity(row)` и рекурсия `.deep()`.

Новое в переходах:
- шаг по базовому классу проходит через концы, объявленные любым классом семейства, — следствие полиморфных концов;
- переход через множественный конец разворачивает список: `t.Комплекс(c).Элемент()` вернёт весь состав, а `t.Услуга(s).Комплекс()` — все комплексы, в которые входит услуга.

### Роли в цепочке

Имя конца (роль) можно написать вместо имени класса. Оно означает тот же класс цели, но дополнительно говорит, по какому концу идёт переход. Если шаг-роль стоит после узла, у которого есть такой конец, переход идёт по нему вперёд, к цели. Если шаг-роль стоит перед узлом, у которого есть такой конец, переход идёт по нему назад — к тем, кто ссылается этим концом. Правило одинаково для связей и для хабов.

```ts
// у связи «перевод» два конца класса Счёт: роли Отправитель и Получатель
await t.Отправитель(a).перевод().Получатель().rows();   // кому переводил счёт a
await t.Получатель(a).перевод().Отправитель().rows();   // кто переводил на счёт a
await t.Счёт(a).перевод().rows();                       // все переводы счёта a, в любой роли

// концы хаба Клиент из §5: Master и Referal
await t.Клиент(anna).Referal().first();                 // вперёд: кто привёл Анну
await t.Referal(anna).Клиент().rows();                  // назад: кого привела Анна
```

Если конец не назван, он называется так же, как класс цели, и в цепочке достаточно имени класса. Имя конца однозначно указывает на класс во всей схеме, это проверяется при определении класса. Слоты тоже работают по именам концов: `.Получатель.set(b)`, `.Referal.set(boris)`.

### Что есть в цепочке

| Группа | Состав |
|---|---|
| Шаги | класс или алиас, роль, `entity(переменная)`, `db.entity(row)` |
| Фильтры | id, список id, готовая строка (Row), объект полей любой глубины с приведением по типу поля; 18 операторов letopis: `ne`, `gt`, `gte`, `lt`, `lte`, `between`, `inList`, `like`, `ilike`, `starts`, `ends`, `has`, `hasAny`, `hasAll`, `exists`, `isNull`, `not`, `or` |
| Модификаторы | `limit`, `offset`, `sort`, `after` (keyset-курсор, `cursorOf`), `asOf`, `withDeleted`, `deep(max)`, `exact`, `alias` (имя узла в путях), `tags`, `owner` |
| Терминалы | `rows`, `first`, `ids`, `count`, `paths`, `versions`, `sum`, `avg`, `min`, `max`, `countBy` |
| Запись | `create`, `update`, `delete`, `purge`, `anonymize`, `reclass`; слоты `.Роль.set()`, `.unset()`, для множественных концов ещё `.add()` и `.remove()` |
| Корень | `as`, `begin`, `batch`, `watch`, `sql`, `auth`, `acl`, `registry`, `close` |

Отличия от letopis сведены к минимуму:
- `count()` считает сущности, а не пути (в letopis это отдельная грабля шпаргалки); число путей — `count({ paths: true })`;
- терминал путей называется `paths()` вместо `run()`;
- появились шаги-роли, множественные концы и операция `reclass`.

### Примеры

Цепочки из тестов и README letopis в новом виде и несколько новых возможностей:

```ts
const t = db.as(session);

// многошаговое чтение через связь (было: db.Мастер({ name: 'Вася' }).навык().Услуга().run())
const paths = await t.Мастер({ name: 'Вася' }).навык().Услуга().paths();

// обратный и прямой переходы между хабами
const staff = await t.Организация(org.id).Мастер().rows();
const orgs  = await t.Мастер({ name: 'Вася' }).Организация().rows();

// pivot: звезда вокруг записи — клиент, услуга и мастер одной брони
const bookings = await t.Клиент(anna).запись().Услуга(haircut).запись().Мастер(vasya).запись().rows();

// создание: конец Staff берётся из пути, остальные — слотами
const [b] = await t.Мастер(vasya).запись()
  .create({ start: '2026-10-07T10:00:00.000Z', end: '2026-10-07T11:00:00.000Z' })
  .Location.set(hall).Schedule.set(october).Item.set(haircut).Customer.set(anna)
  .rows();

// создать и сразу добавить в состав одной цепочкой
await t.Комплекс(c).update()
  .Items.add(t.Организация(org).Услуга().create({ name: 'Укладка' }))
  .rows();

// правка с проверкой ревизии: если запись успели изменить, будет ошибка Conflict
await t.запись(b.id).update({ notes: 'перенос' }, { rev: b.rev }).rows();

// keyset-пагинация, агрегаты, дерево, история
const page    = await t.Услуга().sort('data.name').after(cursor).limit(50).rows();
const byLevel = await t.Мастер(vasya).навык().countBy('level');
const tree    = await t.Папка(root).Папка().deep(5).rows();          // у строк есть $depth
const before  = await t.цена(price.id).asOf('2026-09-01T00:00:00Z').first();
```

### Запись

Запись устроена как в letopis. Глаголы — звенья плана, а терминал исполняет весь план одной транзакцией. После операции цепочка продолжается от её результата, для каждой строки отдельно; операция после операции пишет в те же сущности.

`create` — идемпотентный PUT: по известному или вычисленному id он делает новую версию с глубоким слиянием и воскрешает удалённое. `update` никогда не создаёт. Концы берутся из предыдущих шагов пути и из слотов. Значением слота может быть вложенная цепочка — тогда цель создаётся и привязывается в той же транзакции. Каждая операция — один SQL-оператор над `entity`, сколько бы связей у строки ни было.

Батч `db.batch(имя)` копит планы и исполняет их одной транзакцией; подряд идущие простые вставки склеиваются в одну. `db.begin()` даёт транзакцию с тем же API и с `lock()`. Ретраи при взаимной блокировке и конфликте сериализации работают как в letopis, с подсказкой для пользовательских транзакций.

Главное отличие: слияние выполняется атомарно в SQL (`svod.merge(data, $patch)` над свежей версией строки), поэтому параллельные правки разных полей не теряются, а строгий режим `{ rev }` даёт отказ при любой чужой правке. В letopis один из параллельных патчей теряется (`lib/src/write.ts:337-361`).

### Во что превращается шаг

Каждый шаг — это обычная выборка текущих строк. Цепочка `t.Клиент(anna).запись().Мастер().rows()` превращается примерно в такой запрос:

```sql
select m.* from svod.entity m
where m.class = any ($1)                                    -- Staff и его потомки
  and m.id in (
    select (b.links ->> 'Staff')::uuid                      -- прямой переход по роли
    from svod.entity b
    join svod.entity c
      on b.ends @> array[c.id]                              -- обратный переход по GIN
     and b.links ->> 'Customer' = c.id::text
    where b.class = any ($2) and c.id = $3 and c.class = any ($4));
```

К каждому из трёх чтений `svod.entity` PostgreSQL сам добавит условие политики RLS: арендатора из сессии и решение ACL (§10). В библиотеке не остаётся ни `DISTINCT ON`, ни фильтра по арендатору, ни встроенного энфорсера ACL. Срез `asOf(T)` читает вместо `entity` функцию `svod.entity_at(T)`, которая восстанавливает состояние из журнала; исторические запросы стоят примерно как сегодня, а текущие становятся дешевле.

## 7. Идентификаторы: v5 у всех классов

В letopis три вида идентификаторов: v4 по умолчанию, v7 по объявлению и v5 по ключу (`lib/src/schema.ts:145-166`). v5 там стоит только у классов с естественным ключом, а корни демо-домена объявляют v7 (`lib/sql/seed.booking.sql:8`, `:56`): время в старших битах даёт вставку в правый край индекса (`lib/README.md:370`). Причина, по которой v5 не везде, одна — v5 нужен ключ, а у мастера, клиента или организации естественного неизменяемого ключа нет.

В «Своде» идентификатор всегда v5, и ключ есть у каждого класса:
- **естественный ключ**, если он есть: `(Org, name)` у элемента каталога, `(Staff, start)` у окна, концы у связи;
- **`ref`**, если естественного ключа нет: внешний идентификатор, который передаёт вызывающий, — номер в CRM, ключ идемпотентности запроса, id в другой системе. Класс без `key` получает ключ `ref` автоматически, а сам `ref` хранится в строке как неизменяемое поле. Если вызывающий `ref` не передал, его подставляет библиотека или триггер (случайное значение), и сущность просто получает уникальный id.

Что это даёт:
- любое создание можно сделать идемпотентным: повтор с тем же ключом или `ref` после сбоя сети вернёт ту же сущность, а не дубль;
- id любой сущности вычисляется заранее, офлайн и на любом языке;
- повторный импорт из внешней системы (`ref = 'crm:12345'`) не плодит копий;
- в тестах идентификаторы предсказуемы;
- база проверяет происхождение каждого id без исключений: он всегда равен v5 от хранимого ключа.

Чем за это платим:
- v5 — хэш, поэтому новые id ложатся в индекс первичного ключа вразброс, а не в правый край, как v7. На очень больших таблицах с интенсивной вставкой это больше разбиений страниц и больше записи в WAL; насколько это заметно, покажет бенч. Время создания при этом не теряется — оно хранится в `created_at`.
- Ключевые поля неизменяемы, поэтому в ключ кладут только то, что не меняется: внешний id, концы, момент времени. Телефон или email — плохой ключ: их уникальность задаётся отдельным правилом `unique`, которое держит база, а ключом служит `ref`.

### Формула

```
id = uuid_v5(пространство имён = арендатор, имя = '["booking", "<id мастера>", "2026-10-07T10:00:00.000Z"]')
id = uuid_v5(пространство имён = арендатор, имя = '["Person", "crm:12345"]')      -- ключ ref
```

Имя — канонический JSON-массив: класс и значения ключа в объявленном порядке, в формате вывода `jsonb::text` PostgreSQL. Этот формат легко воспроизвести в TypeScript и Python, и в нём нет неоднозначности разделителей.

| Тип значения | Каноническая форма |
|---|---|
| строка | нормализация NFC; `trim` и `lower`, если они объявлены у поля (применяются и к хранимому значению) |
| целое | число без ведущих нулей |
| логическое | `true` или `false` |
| `uuid` и концы связи | идентификатор строчными буквами |
| дата | `YYYY-MM-DD` |
| дата и время | UTC с миллисекундами, `2026-10-07T10:00:00.000Z`; в таком же виде значение и хранится |
| перечисление | строка значения |

Дробные числа, объекты, списки и множественные концы в ключ не допускаются.

Правила:
- Идентификатор вычисляет триггер базы. Если клиент передал другой — это ошибка; если не передал ничего — триггер подставит правильный, поэтому вставка сырым SQL без `id` тоже работает.
- Библиотека вычисляет тот же идентификатор офлайн: это нужно для ссылок до создания и для проверки «занято ли окно» без записи. Совпадение формул проверяет общий файл тестовых векторов, который прогоняют тесты TypeScript, тесты SQL и будущий порт на Python.
- Для естественного ключа в имя входит конкретный класс, как в letopis, поэтому окно и запись на одно и то же время не конфликтуют (`lib/sql/seed.booking.sql:68`); общим для семейства его делает опция `key.scope: 'family'`. Ключ `ref` общий для семейства по умолчанию: в имя входит класс, объявивший ключ (во втором примере — `Person`), поэтому при переходе между классами семейства, например когда клиент становится мастером, id не меняется (§8).
- В имя входит имя класса, зафиксированное при его создании, поэтому переименование класса или алиаса идентификаторы не меняет.
- У связи без явного ключа ключом служат её концы. Получается одна связка на пару: один навык на пару «мастер — услуга», одно правило на пару «группа — ресурс». Последнее в точности повторяет первичный ключ `Rule(account, resource)` в letopis. Если связей на одну пару может быть несколько (несколько переводов между теми же счетами), ключом объявляется `ref` или концы плюс момент времени.
- Ключевые поля нельзя поменять обычной правкой. Для смены ключа и класса есть отдельный механизм (§8).

Чем это отличается от letopis:

| | letopis 0.21 | «Свод» |
|---|---|---|
| У каких классов | только с правилом `generate: 5` и `from` (`lib/src/schema.ts:156-161`); остальные получают v4 или v7 | у всех |
| Где вычисляется | только в Node (`lib/src/write.ts:333`) | в базе и в библиотеке, одинаково |
| Пространство имён | константа `LETOPIS_NS` (`lib/src/uuid.ts:12`) плюс имя схемы и партиции | арендатор |
| Разделитель значений | двоеточие, которое встречается и внутри времени (`lib/README.md:390-392`) | JSON-массив |
| Канонизация значений | нет, время хэшируется в том виде, в каком передано | есть |
| Сырой SQL со случайным id | принимается (`lib/test/parity.test.ts:144-161`) | ошибка |
| Два одновременных `create` с одним ключом | две версии, вторая строится по устаревшему состоянию (`lib/README.md:380`, `lib/src/write.ts:337-361`) | одна вставка и атомарное слияние; одинаковые данные не создают версии |

## 8. Переход из класса в класс

В letopis класс — часть идентичности: первичный ключ включает `class` (`lib/sql/ddl.sql:102`), а API смены класса нет. Сырой `UPDATE … SET class = …` создаёт вторую живую сущность с тем же id в новом классе, а старая остаётся (`lib/sql/ddl.sql:243-259`). Окно и запись — разные сущности: бронь окно не меняет (`lib/test/integration.test.ts:207-210`), а перенос записи — это удаление и создание заново.

В «Своде» идентичность — только `id`, а смена класса — отдельная операция `reclass`:

```ts
// клиент становится мастером: тот же человек, тот же id, история продолжается
await t.Клиент(c).reclass('Мастер', { specialization: 'барбер' }).rows();

// окно превращается в запись, если по правилам бизнеса бронь должна занимать окно
await t.окно(s).reclass('запись', { notes: 'Анна' })
  .Item.set(haircut).Customer.set(anna)
  .rows();
```

Сырым SQL получается тот же эффект: `update svod.entity set class = 'Staff', data = … where id = …`. Смену класса обрабатывает триггер, поэтому гарантии одинаковы.

Что делает база:
1. Проверяет права: удаление в старом классе и запись в новом.
2. Проверяет данные и концы по описанию нового класса. Недостающие поля и концы передаются в той же операции.
3. Проверяет входящие ссылки. Каждая роль, которая ссылается на сущность, должна принимать новый класс. Если бронь ссылается на клиента ролью `Customer`, а клиент становится мастером, переход отклоняется с перечнем мешающих ссылок.
4. Пересчитывает идентификатор по ключу нового класса. Если ключ общий для семейства (так по умолчанию у `ref`), id не меняется, и строка просто меняет класс. Если меняется, строка получает новый id, а все ссылки на неё переписываются в той же транзакции; каждая переписанная ссылка становится версией ссылающейся строки. В журнале новая версия хранит прежний id в колонке `moved`, `versions({ follow: true })` проходит историю насквозь, и цепочка хэшей не рвётся.
5. Пишет в журнал версию с `op = 'reclass'`.

**Смена ключа класса** — та же операция для всех строк класса. Вызов `svod.rekey('booking', ['Staff', 'start', 'Location'])` создаёт новую ревизию описания с новым ключом и переводит строки пачками: пересчитывает id, переписывает ссылки и связывает историю. На время перевода запись в этот класс приостанавливается.

**Прочая эволюция классов** обходится без отдельных механизмов. Добавить поле или конец можно сразу. Сузить описание (сделать поле обязательным, ограничить диапазон, убрать поле) можно, только если все строки класса уже проходят новое описание, и база проверяет это сама. Большие изменения проводятся в три шага: расширить описание, перенести данные, сузить. В letopis похожую проверку живых строк делает CLI `schema-sync`, но только по выборке и только при запуске вручную (`lib/scripts/schema-sync.mjs`).

## 9. Целостность

### 9.1. Роли и права

- **`svod_owner`** — роль без входа. Ей принадлежат схема, таблицы и функции. Она нужна только при развёртывании: DDL, индексы из описаний классов, партиции журнала.
- **`svod_app`** — роль приложения. На `entity` у неё есть `select`, `delete`, `insert` только в колонки `id, tenant, class, links, data, tags, owner` и `update` только колонок `class, links, data, tags`; смену класса обрабатывает триггер как `reclass`. На `log` — только `select`, на партиции журнала и приватные таблицы — ничего. Прав `truncate`, `trigger` и `references` нет, создавать объекты в схемах (включая `public`) она не может.
- Все функции объявлены `security definer` с `set search_path = pg_catalog, svod, pg_temp` и обращаются к объектам по полным именам. Динамический SQL из данных не строится нигде: проверка JSON Schema и ACL — интерпретаторы, а не генераторы кода.
- Защитные триггеры включены в режиме `enable always`, поэтому продолжают работать и в режиме репликации.

### 9.2. Как работают триггеры

**Вставка и правка строки** проходят по шагам:
1. Контекст: актор и арендатор берутся из проверенной сессии (§11). Без сессии запись невозможна.
2. Неизменяемое: `tenant`, `owner`, `created_*`, а также `id` и ключевые поля вне операций `reclass` и `rekey`. Попытка их сменить — ошибка; для `tenant` и `owner` это вдобавок закрыто правами на колонки.
3. Описание класса: текущая ревизия, класс не абстрактный. Если класс меняется, дальше действуют правила §8.
4. Нормализация и умолчания, затем проверка `data` по JSON Schema класса.
5. Концы: роли объявлены, обязательные присутствуют, у множественных — без повторов и в пределах `min` и `max`. Каждая цель читается с блокировкой `for key share` и проверяется: существует, принадлежит тому же арендатору или системному, относится к объявленному классу или его потомку, видна актору.
6. Идентификатор: v5 по ключу класса; если ключ — `ref` и его не передали, триггер подставляет случайный `ref`.
7. Служебные колонки: `rev`, `cv`, `updated_*`, `hash` = sha256(хэш прошлой версии || снимок). Прошлый хэш берётся только из `OLD`: BEFORE-триггер получает строку уже под блокировкой и в самой свежей версии, поэтому параллельные писатели не разорвут цепочку.
8. Пустая правка: если `class`, `data`, `links` и `tags` не изменились, версия не создаётся.
9. После записи — строка журнала и сигнал `NOTIFY`, который служит только будильником. Журнал пишется в триггере `after`, то есть только для реально записанных строк: `on conflict do nothing` не оставит в истории фантомных версий.

**Удаление:**
1. Разрешено только в `read committed`, уровне изоляции PostgreSQL по умолчанию; в остальных уровнях триггер отказывает (почему — в §9.3).
2. Триггер `before delete` срабатывает, когда PostgreSQL уже взял на строку исключительную блокировку. Ссылающиеся строки находятся через индекс по `ends`, и для каждой роли применяется правило из описания: `restrict` — ошибка, `cascade` — удаление (цели упорядочены по `id`, каскад рекурсивен), `unset` — снятие необязательной роли или удаление id из списка.
3. Надгробная версия пишется в журнал в том же триггере.

Операции `truncate` над `entity` и любые `update`, `delete`, `truncate` над `log` отклоняются триггерами, даже если у роли каким-то образом окажутся права. Исключение составляют только функции физического удаления, обрезки истории и сброса: они выполняются от имени владельца, проверяют право вызывающего и оставляют о себе запись в журнале.

### 9.3. Тонкие места

- **Вставка ссылки и одновременное удаление цели.** Вставляющая транзакция держит на цели блокировку `for key share`. Удаляющая получает исключительную блокировку строки только после того, как вставившая завершится, и лишь затем запускает триггер; каждый запрос триггера в `read committed` видит свежий снимок — значит, видит и новую ссылку. Порядок «блокировка, затем BEFORE-триггер» подтверждается исходниками PostgreSQL (`GetTupleForTrigger` в `src/backend/commands/trigger.c`). Если первой успела удаляющая, вставляющая дождётся её фиксации и не найдёт цель. В `repeatable read` снимок удаляющей транзакции старый, и ссылка осталась бы висячей; поэтому удаление разрешено только в `read committed`. Вставка безопасна на любом уровне: если цель успели удалить, проверка либо не найдёт её (`read committed`), либо завершится ошибкой сериализации (более строгие уровни). Всё это обязаны подтвердить тесты гонок на двух соединениях.
- **Ужесточение класса и одновременная запись.** Новое обязательное поле или более узкий диапазон проверяются по всем строкам класса. Писатели держат разделяемую advisory-блокировку класса, правка описания — исключительную, поэтому строка, проверенная по старому описанию, не может проскочить мимо проверки. Если хоть одна строка не проходит, правка отклоняется. Отсюда следствие: любая строка всегда валидна относительно последней ревизии своего класса.
- **Одна и та же строка удалена и создана заново в одном операторе** (например, в writable CTE). Надгробие пишется в `before delete`, а не в `after`, поэтому повторное создание видит его и продолжает нумерацию ревизий и цепочку хэшей.
- **Смена класса с новым id** переписывает входящие ссылки в той же транзакции. Пока перевод не закончен, ссылающиеся строки заблокированы, и параллельная запись в них подождёт.
- **Классы без истории** (`history: false`) не ведут журнал и цепочку хэшей. Для системных классов (`Class`, `Account`, `member`, `Resource`, `rule`) это запрещено; режим предназначен для эфемерных данных вроде счётчиков и кэшей.
- **Взаимные блокировки каскада.** Цели каскада упорядочиваются по `id`, а библиотека повторяет операцию при `40P01` и `40001`.
- **Тексты ошибок** не раскрывают чужих данных: «цель не найдена» звучит одинаково для несуществующей сущности и для сущности чужого арендатора.

### 9.4. Что пробует сырой SQL и чем это кончается

| Попытка от роли приложения | letopis 0.21 | «Свод» |
|---|---|---|
| Записать `data`, не проходящие схему класса | принимается (`lib/test/parity.test.ts:182-203`) | ошибка проверки JSON Schema в триггере |
| Сослаться на несуществующую, чужую или не того класса сущность | принимается (`lib/test/parity.test.ts:144-161`) | ошибка: цель проверяется под блокировкой с учётом наследования |
| Записать хаб с произвольными концами | концы хабов не проверяются (`lib/sql/ddl.sql:189`) | концы хабов проверяются так же, как концы связей |
| Сменить арендатора или владельца | `UPDATE` вставляет версию с новыми значениями (`lib/sql/ddl.sql:253-257`) | запрещено правами на колонки и триггером |
| Сменить класс через `UPDATE … SET class` | вторая живая сущность с тем же id (`lib/sql/ddl.sql:243-259`) | проверенный переход `reclass` (§8) |
| Создать дубль естественного ключа или `id`, не равный v5 | принимается | идентификатор вычисляет база, дубль упирается в первичный ключ |
| Стереть историю через `SET letopis.purge = 'on'`, `compact` или `TRUNCATE` | возможно (`lib/sql/ddl.sql:311`, `lib/sql/ddl.sql:537-553`) | прав на `log` нет; физическое удаление — только функцией с проверкой права и записью в журнал |
| Воскресить удалённое через `UPDATE … SET deleted = NULL` или вставить надгробие в обход каскада | возможно (`lib/sql/ddl.sql:243-259`, `lib/sql/ddl.sql:158-160`) | в текущей таблице нет удалённых строк, надгробие пишет только триггер |

| Задеть каскадом удаления чужого арендатора | возможно: каскад идёт по `links` без учёта арендатора (`lib/sql/ddl.sql:297-300`) | ссылки существуют только внутри арендатора |
| Изменить описание класса так, что данные станут невалидными | возможно, данные не перепроверяются | ужесточение проверяет все строки класса |
| Записать без автора | колонки автора нет вовсе | без сессии записи нет, автор есть в каждой версии |
| Читать или писать чужого арендатора | возможно, RLS нет | RLS: арендатор берётся из сессии и закреплён в `with check` |
| Обойти ACL | ACL живёт только в Node и по умолчанию выключен | RLS с правилами из базы, включена всегда |
| Править креды, правила или аккаунты напрямую | возможно | креды в приватной таблице; правила и аккаунты — сущности под ACL |
| Подделать сессию или назваться другим аккаунтом | `db.as()` верит приложению (`lib/src/chain.ts:731-745`) | токен 256 бит, в базе только его sha256; имперсонация — только сервисом с правом (§11) |
| Потерять параллельное обновление | возможно (`lib/src/write.ts:337-361`) | атомарное слияние в `UPDATE`, строгий режим по `rev` |
| Получить чужие события | `watch` не знает арендатора (`lib/sql/ddl.sql:473-475`) | поток читается из журнала под RLS |
| Владелец схемы или суперпользователь отключает триггеры и правит журнал | возможно | тоже возможно, но `svod.verify()` обнаружит разрыв цепочки хэшей |

Последняя строка — честная граница. Владелец объектов и суперпользователь в PostgreSQL могут всё, и «Свод» этого не отменяет. Он делает такую правку обнаружимой и позволяет публиковать якорь — хэш всех голов цепочек на момент времени — вне базы.

## 10. ACL

Модель letopis переносится в базу без изменения смысла (`lib/src/acl.ts:142-161`).

- **Группа** — ресурс категории `ACCOUNT` с маской: `{A,B}` означает «есть любая из категорий», `!{A,B}` — «нет ни одной», отсутствие шаблона — «все». В «Своде» маска сравнивается с категориями аккаунта и с ролями его членства в текущем арендаторе.
- **Объект** — ресурс `API` (маска эндпоинта, шлюз приложения) либо `READ`, `WRITE` или `DELETE` (маска класса с учётом предков плюс предикат на строку).
- **Правило** — связь `rule` от группы к объекту: разрешение или запрет, вес, код и сообщение. Побеждает правило с наибольшим весом, при равенстве запрет сильнее разрешения, при отсутствии правил действует запрет.
- **Предикат** — конъюнкция равенств и включений по `data`, `links`, `tags`, `owner` и `id`. К переменной letopis `$account` добавляются `$actor` (кто действует) и `$tenant` (в чьих данных).
- **Решение принимается по конкретному классу строки**: запрет на потомке не обходится шагом по родителю — как в letopis.

Пример: перенос группы из сида `lib/sql/seed.auth.sql` и одно правило на данные — аутентифицированный пользователь видит только те записи, владельцем которых является.

```ts
const authenticated = await t.Resource().create({
  alias: 'authenticated:ACCOUNT', category: 'ACCOUNT',
  pattern: { categories: '!{Anonymous,Shadow}' },
}).first();

const ownBookings = await t.Resource().create({
  alias: 'booking.own:READ', category: 'READ',
  pattern: { class: 'booking', owner: '$actor' },
}).first();

await t.rule().create({ permission: 'allow', weight: 90 })
  .Group.set(authenticated).Object.set(ownBookings)
  .rows();

// какие объекты доступны группе — обычная цепочка с шагами-ролями
const granted = await t.Group(authenticated).rule().Object().rows();
```

Как правила применяются:
1. Правила, ресурсы и цепочки наследования классов сводятся в снимок — одну строку `jsonb`. Его пересчитывает отложенный триггер под блокировкой при каждом изменении правил. Ни генерации кода, ни DDL при этом не происходит.
2. В начале каждого запроса политика RLS один раз вычисляет решения для групп актора: для каждого класса это запрет, разрешение или разрешение с предикатом.
3. Для каждой строки остаётся дешёвая встроенная проверка предиката.

```sql
alter table svod.entity enable row level security;

create policy entity_read on svod.entity for select using (
  tenant in ((select svod.tenant()), svod.system_tenant())
  and svod.acl_ok((select svod.acl_plan('READ')), class, owner, links, data, tags));

create policy entity_insert on svod.entity for insert with check (
  tenant in ((select svod.tenant()), svod.system_tenant())
  and svod.acl_ok((select svod.acl_plan('WRITE')), class, owner, links, data, tags));

-- update и delete устроены так же; на svod.log действует такая же политика чтения по снимку версии
```

Обёртка `(select …)` превращает вычисление контекста и плана в однократное для всего запроса. Функция `svod.acl_ok` не помечается `leakproof`, чтобы планировщик не переносил чужие условия ниже барьера RLS.

Что из этого следует:
- ACL одинаково действует на библиотеку и на сырой SQL. Флага `enforceAcl` больше нет: права включены всегда, по умолчанию действует запрет, а режим «аутентифицированным можно всё» — это одно правило.
- Предикаты применяются до сортировки и лимита, поэтому пагинация, `count` и keyset честные — как сейчас в letopis, только силами самой базы.
- Шлюз `db.acl.check('booking.create')` возвращает `{ allow, rule, code, message }`, где код и сообщение берутся из запрещающего правила. `db.acl.checkData('booking', 'WRITE')` возвращает `{ allow, filter }`. Обе — функции базы на том же снимке.
- Изменения прав версионируются: `t.rule(r).versions()` показывает, кто и когда выдал право, а `asOf` отвечает на вопрос «у кого был доступ на дату».
- Функции, которые по своей природе работают мимо RLS (вход, физическое удаление, восстановление, сброс), проверяют права явно.

## 11. Auth и сессии

### Креды

Креды лежат в приватной таблице `svod.credential`: аккаунт, вид, идентификатор, секретный материал, служебные поля, признак подтверждения и мягкое удаление. Пара «вид, идентификатор» уникальна среди живых кредов, поэтому один и тот же email не может принадлежать двум аккаунтам, а у одного аккаунта может быть сколько угодно кредов. Это сохраняет поведение letopis.

| Вид | Как проверяется | Кто проверяет |
|---|---|---|
| `PASSWORD` | scrypt в формате letopis `scrypt$N$r$p$salt$hash` (`lib/src/auth.ts:23-46`), с выравниванием времени ответа для несуществующего идентификатора | сервис в Node; открыть сессию после проверки может только сервисный аккаунт |
| `APIKEY` | ключ с префиксом (`lts_…` в letopis), в базе — префикс и sha256 | база |
| `KEYSECRET` | открытый ключ и sha256 секрета | база |
| `OTP` | sha256 кода, срок, счётчик попыток; успех, истечение и перебор сжигают код | база, атомарно под блокировкой строки |
| `TOTP` | RFC 6238 (HMAC-SHA1 из pgcrypto); подключение отдаёт секрет и ссылку `otpauth://`, первая успешная проверка активирует фактор, повтор шага запрещён | база |
| Внешние: Telegram, Google, SSO | токен провайдера проверяет приложение, затем находит или привязывает identity (`link`, `lookup`) | сервис утверждает identity |

Признаки `confirmed` и `enabled` и опция `requireConfirmed` сохраняются. Для тестов остаётся `totpCode()`.

```ts
// сервер приложения подключается сервисным ключом — это его собственный кред APIKEY
const db = await connect(process.env.DATABASE_URL, {
  service: process.env.SVOD_SERVICE_KEY,
  models: [Org, Staff, Customer, Service, skill, slot, booking],
});

// один аккаунт — разные креды: любой из них открывает сессию того же Account
const s1 = await db.auth.login('PASSWORD', 'anna@salon.ru', password);
await db.auth.otp.issue('+79990001122', sendSms);          // код отправляет приложение
const s2 = await db.auth.login('OTP', '+79990001122', codeFromUser);

const t = db.as(s1);                                        // дальше всё — от имени Анны
await t.auth.attach('TOTP', { secret, code });              // второй фактор; нужен недавний вход
await t.auth.revokeAll();                                   // выйти на всех устройствах
```

Привязка нового креда требует недавнего входа существующим кредом, а ошибка привязки не сообщает, занят ли идентификатор кем-то другим.

### Зачем сессии в базе

В letopis база не знает, кто действует. Приложение проверяет токен в Redis (`sessions.check`) и само вызывает `db.as(accountId)`, а `db.as` ничего не проверяет: это просто клон контекста (`lib/src/chain.ts:731-745`). Для «Свода» так нельзя. Права (RLS), изоляция арендаторов и автор версии вычисляются в базе, а значит, база должна сама убедиться, что запрос пришёл от этого аккаунта. Иначе любой сырой SQL мог бы назваться кем угодно.

Самый простой надёжный якорь — таблица сессий. Токен знает только клиент, в базе лежит его sha256, а проверка — это поиск по первичному ключу один раз на запрос. Попутно уходит Redis, и появляется то, чего в letopis нет:
- сессии гаснут при отключении аккаунта;
- сессии гаснут при смене пароля;
- все сессии можно погасить разом.

Сейчас `check` не продлевает срок и не смотрит `enabled` (`lib/src/sessions.ts:57-60`), смена пароля сессии не трогает (`lib/src/auth.ts:212-220`), а перечислить и сбросить все сессии нельзя: у хранилища нет перебора ключей (`lib/src/sessions.ts:9-17`).

| Событие | Что происходит |
|---|---|
| Истёк срок | сессия не проходит проверку; срок по умолчанию 7 суток, как в letopis; можно включить продление при использовании (не чаще раза в минуту) |
| Выход | `revoke(token)` удаляет строку сессии |
| Выход на всех устройствах | `revokeAll()` удаляет все сессии аккаунта |
| Аккаунт отключён (`enabled = false`) | все его сессии перестают проходить проверку сразу, без отдельного вызова |
| Сменился пароль или удалён кред | сессии аккаунта гасятся автоматически, кроме текущей, если так настроено |
| Аккаунт удалён | сессии удаляются вместе с ним |
| Нужно выгнать всех | `svod.reset({ sessions: true })` — мгновенный `truncate` таблицы сессий (§13) |
| Уборка | `svod.maintain()` удаляет истёкшие строки |

Сессия хранит аккаунт, текущего арендатора, способы входа (пароль, код, второй фактор), сервис, если сессию выдал он, срок и метаданные (адрес, браузер). По замерам README letopis `sessions.check` в Redis стоит 0,4–1,7 мс; поиск сессии по первичному ключу внутри запроса должен стоить меньше, но это оценка, которую подтвердит бенч.

### Имперсонация

Имперсонация нужна серверному приложению, которое аутентифицирует пользователей само (свой OAuth, свой вход) и хочет работать в базе от их имени. Это нынешний `db.as(accountId)` letopis, только проверяемый базой.

1. У сервиса есть свой аккаунт категории `Service` и кред `APIKEY`. При подключении библиотека обменивает ключ на сессию сервиса.
2. `db.as(accountId)`, как и сейчас, ничего не запрашивает — это клон контекста. На каждую операцию библиотека первыми операторами транзакции выставляет `svod.token` (токен сервиса) и `svod.as` (id пользователя).
3. Функция контекста базы, один раз на запрос, находит сессию сервиса, видит `svod.as` и проверяет три вещи: у сервиса есть право `auth.impersonate` (обычное правило ACL на ресурс API); целевой аккаунт существует, включён и виден сервису по ACL — так ограничивается круг, например без System и владельцев; арендатор — собственный арендатор пользователя или тот, где у него есть членство.
4. Дальше всё вычисляется от имени пользователя: RLS, ACL, владелец новых строк. В журнале `author` — пользователь, `agent` — сервис.
5. Без валидного токена сервиса настройка `svod.as` игнорируется, поэтому подставить чужой id сырым SQL нельзя.

Если токен пользователя нужен другому процессу (агенту, воркеру), сервис с тем же правом выпускает обычную короткую сессию: `db.auth.sessionFor(accountId, { ttl: '15m' })`.

**Контекст в пуле.** Обе настройки ставятся через `set_config(…, true)` и живут до конца транзакции, поэтому соединение, вернувшееся в пул, не унесёт чужой токен. Любую настройку `svod.*` может выставить кто угодно, но произвольный токен не пройдёт сверку.

### Членство

Связь `member` от пользователя к арендатору с ролями решает задачу, которую letopis сейчас не выражает: сотрудники салона входят своими кредами и работают в данных салона, а их роли становятся группами ACL. Вызов `auth.switch(tenant)` переключает арендатора сессии, если членство есть.

Полезное следствие всей схемы: соединение с одним лишь паролем базы не видит и не пишет ничего, а соединение с токеном пользователя видит ровно то же, что этот пользователь. Аналитику или агенту можно выдать доступ на сырой SQL через пользовательскую сессию, не опасаясь за чужие данные.

## 12. Время, удаление, события

- `versions()` возвращает все версии из журнала, у каждой есть автор, время, ревизия, вид операции и причина; надгробия помечены `$deleted`. `versions({ follow: true })` проходит и через смену id (§8).
- `asOf(T)` работает на срезе журнала. Связи — это версионируемые строки, поэтому граф восстанавливается на любой момент времени. В «Записи» это невозможно: её таблица `edge` истории не хранит.
- `withDeleted()` читает последнюю версию вместе с надгробиями. Повторный `create` по тому же ключу воскрешает удалённое, как в letopis, а `restore()` возвращает последний снимок новой версией и заново проверяет его по текущему описанию класса.
- `delete()` без `confirm` показывает превью замыкания, с `confirm` удаляет строку и каскад и возвращает всё замыкание с пометкой `$deleted`.
- `purge({ confirm })` работает только для уже удалённого (двухфазность letopis), физически стирает версии из журнала и оставляет запись `op = 'purge'` с числом стёртых версий и последним хэшем.
- `anonymize(fields)` заменяет строковые поля на `'[erased]'` и ставит тег `anonymized`, история остаётся. Лестница «права на забвение» letopis сохраняется: `anonymize`, затем обрезка истории, затем `purge`; позже к ней добавится крипто-шреддинг.
- `accounts.purge` — функция базы с проверками letopis: вызывающий — владелец или система, нельзя удалить себя и последнего владельца.
- `svod.verify()` пересчитывает цепочки хэшей и учитывает записи о физическом удалении, обрезке истории и сбросе как законные разрывы.

Подписка надёжна и возобновляема:

```ts
for await (const ev of t.запись().watch({ from: cursor })) {
  await notifyClient(ev);        // ev: { cursor, op, id, class, data, author, at }
  cursor = ev.cursor;            // курсор сохраняется, после рестарта поток продолжится
}
```

Сервер читает журнал по курсору ниже горизонта завершённых транзакций:

```sql
select * from svod.log
where (tx, seq) > ($1, $2)
  and tx < pg_snapshot_xmin(pg_current_snapshot())
  and class = any ($3)
order by tx, seq
limit 500;
```

Такая выборка не пропускает события из-за разного порядка фиксации транзакций и не теряет их при обрыве соединения. `NOTIFY` только будит подписчика, его содержимому никто не доверяет. Изоляцию арендаторов и права обеспечивает RLS на журнале. В letopis события при обрыве соединения терялись (поэтому был нужен `onReconnect`), а сам канал не знал арендатора.

## 13. Сброс и эксплуатация

### Быстрый сброс

В letopis публичного «обнулить всё» нет. Есть `up({ fresh: true })`, который удаляет схему целиком (`lib/src/up.ts:179-182`), `TRUNCATE` в тестах и `accounts.purge` для арендатора, а сессии в Redis перечислить и сбросить разом нельзя (`lib/src/sessions.ts:9-17`). В «Своде» сброс — штатная операция с уровнями:

| Что сбрасывается | Вызов | Как и сколько стоит |
|---|---|---|
| Всё: данные, история, креды, сессии | `svod.reset({ all: true, confirm })` | `truncate` всех таблиц и повторная засевка системных строк (System, базовые классы и правила, при желании демо-домен); миллисекунды при любом объёме |
| Данные одного арендатора | `svod.reset({ tenant, confirm })` | удаление строк арендатора из `entity` и `log`, его членств и сессий; аккаунт остаётся; время пропорционально объёму арендатора |
| Все сессии | `svod.reset({ sessions: true })` | `truncate` таблицы сессий: все выходят мгновенно |
| Схема целиком | `up({ fresh: true })` | как в letopis: схема удаляется и создаётся заново |

Полный сброс и сброс арендатора разрушительны, поэтому у них три предохранителя:
- полный сброс разрешён только там, где при развёртывании включён флаг установки `allow_reset` (разработка, тесты, стенды); в продакшене флаг выключен, и функция отказывает даже системному аккаунту;
- нужны право `svod.reset` и подтверждение — строка с именем схемы;
- после сброса первой строкой журнала становится запись `op = 'reset'` с автором и временем, а проверка хэшей начинает цепочки заново.

В тестах это даёт полностью автономную изоляцию: `reset` между наборами вместо пересоздания схемы.

### Эксплуатация

- **`up()`** остаётся оркестратором letopis без Docker: проверяет доступность базы, создаёт её при необходимости, накатывает DDL и сиды (демо-домен booking и базовые правила), выполняет `ANALYZE` и подключается. Опции `fresh`, `upgrade`, `seeds` и `quiet` сохраняются. Для разработки без установленного PostgreSQL можно поднять встроенный PGlite (с ограничениями из §17).
- **Имя схемы `v<N>.<имя>` и ревизия движка** сохраняются: последний оператор DDL ставит штамп ревизии, а `connect()` предупреждает, если движок схемы отстал, и называет команду обновления.
- **`ANALYZE`** после наката и массовой заливки остаётся обязательным правилом.
- **`svod.maintain()`** заранее создаёт партиции журнала и убирает истёкшие сессии; обрезка истории удаляет старые партиции с записью в журнале.
- **Телеметрия**: хук `onQuery` получает режим, классы, длительность и число строк каждого запроса цепочки, `slowMs` без хука печатает предупреждение — как в letopis.
- **Ошибки**: каталог с префиксом `svod:`, `ValidationError.issues` по полям (из Zod и из проверки в базе), охранники снесённого API с версией и заменой.
- **`db.sql`** остаётся, но работает в контексте сессии и под RLS.

## 14. Документация и проверка для агентов

Практика letopis переносится целиком:
- шпаргалка с рабочим циклом и граблями, проверенная прогоном агента, который видит только её;
- `docs/api-contract.json`, генерируемый из кода: экспорты, методы цепочки, список зарезервированных имён, снесённый API с версиями, каталог ошибок;
- `check-docs` сверяет версии, ссылки, списки тестов, контракт и ревизию движка.

Новое: `db.describe()` отдаёт машинное описание модели — классы, концы, ключи, JSON Schema полей, алиасы, описания и иконки. Из него собираются `llms.txt` и, позже, инструменты MCP: их входные схемы — это те же JSON Schema.

Тесты:
- тест паритета letopis становится обращённым: каждая атака сырым SQL из §9.4 обязана завершиться ошибкой;
- EXPLAIN-тест (индексы в плане, ни одного последовательного сканирования при `enable_seqscan = off`) сохраняется;
- логику (цепочки, проверку данных, v5, триггеры, RLS под `SET ROLE`) можно гонять на PGlite, а гонки и границы безопасности — только на настоящем PostgreSQL, как сейчас в CI: PGlite держит одно соединение и не умеет параллельных транзакций, а его сессионный пользователь — суперпользователь;
- полигоны letopis salon и tenants используются для сравнительного бенча.

Выигрыш не столько в строках, сколько в расположении логики. Всё, что гарантирует целостность, живёт в базе, а клиент только переводит цепочки в SQL. Поэтому порт на Python сводится к построителю цепочек и клиенту входа.

## 17. Честные ограничения

1. **Запись дороже.** Каждая строка проходит проверку JSON Schema и ссылок, вычисление v5, хэширование, запись в журнал и RLS. Насколько это дороже простой вставки, покажет только бенч; ожидаю разницу в разы, а не в проценты.
2. **Удаление — только в `read committed`.** Это уровень PostgreSQL по умолчанию, но транзакции с более строгой изоляцией удалять не смогут.
3. **`COPY FROM` недоступен для таблиц под RLS** — так во всех версиях PostgreSQL; исключение — владелец таблицы, суперпользователь и роли с `BYPASSRLS`. Массовая загрузка идёт через `insert … select` или через инструмент импорта от роли владельца.
4. **Владелец схемы и суперпользователь** могут отключить триггеры. «Свод» это не предотвращает, а обнаруживает проверкой цепочки хэшей.
5. **В базе проверяется подмножество JSON Schema.** `refine`, `superRefine` и `transform` Zod работают только в библиотеке; описание с неподдерживаемым ключевым словом база не примет.
6. **Срезы `asOf`** восстанавливают состояние из журнала через `DISTINCT ON` по версиям — так же, как letopis сегодня. Дешёвым становится только текущее состояние.
7. **Горячие цели ссылок** — например, организация, на которую ссылается почти всё, — копят блокировки `for key share` и MultiXact, как при обычных внешних ключах. Это нужно мониторить.
8. **Ужесточение класса и `rekey`** приостанавливают запись в класс на время проверки или перевода; для больших классов изменения проводятся в три шага.
9. **Смена класса с новым id** переписывает все входящие ссылки, и её цена пропорциональна их числу.
10. **Обрезка журнала** укорачивает историю и цепочки хэшей; срез фиксируется записью в журнале.
11. **Имя связи может совпасть с именем метода.** Это проверяется при определении класса, но такое имя придётся выбрать другим.
12. **Это новый пакет, а не версия letopis.** API близок, но `count()`, `paths()`, роли, множественные концы и `reclass` ведут себя по-новому, а данные нужно импортировать.
13. **Сервисный ключ — корень доверия.** Его компрометация позволяет действовать от имени любого пользователя, которого сервис видит по ACL, — как сейчас позволяет вызов `db.as()`. Один пароль от базы при этом не даёт ничего.
14. **PGlite годится только для логики.** Он держит одно соединение и не исполняет транзакции параллельно, поэтому гонки на нём не воспроизвести; его сессионный пользователь — суперпользователь, поэтому RLS проверяется только под `SET ROLE`; поддержка партиционирования и `security definer` в нём не подтверждена. Сам PGlite пока в статусе alpha.
15. **Вывод `z.toJSONSchema()` меняется между минорными версиями Zod.** Версия Zod фиксируется, а в базе хранится уже нормализованная схема.
16. **v5 у всех классов распределяет новые id по индексу первичного ключа вразброс.** На очень больших таблицах с интенсивной вставкой это заметнее, чем с v7 у letopis; цену нужно замерить на полигоне.

## 18. Путь

1. **Ядро в базе.** Таблицы, роли и права, триггеры (проверка JSON Schema, концы с ролями, полиморфизмом и множественностью, v5 по ключу или `ref`, неизменяемость, журнал, хэши), `Class` как сущность, `reclass`. Первым делом пишется набор тестов «атаки сырым SQL»: каждая строка таблицы из §9.4 становится тестом, который обязан завершиться ошибкой. Рядом — сценарии гонок на двух соединениях настоящего PostgreSQL: вставка ссылки против удаления цели, ужесточение класса против записи, два создания с одним ключом, смена класса против записи в ссылающиеся строки.
2. **Цепочки.** Грамматика letopis на новом хранилище, шаги-роли, множественные концы, типы из моделей на Zod, планы записи, слоты, батчи, транзакции, строгий режим по ревизии.
3. **Доступ.** Сессии и контекст, имперсонация, RLS, снимок ACL, креды и вход, членство.
4. **Время, события, сброс.** `versions`, `asOf`, `withDeleted`, `restore`, подписка по курсору, физическое удаление, проверка хэшей, партиции и обрезка журнала, `reset` по уровням, `rekey`.
5. **Импорт из letopis 0.21 и бенч.**
   - Версии `Entity` переходят в `log`, вид операции определяется по порядку версий и надгробиям; последняя живая версия переходит в `entity`.
   - `Schema` переходит в строки `Class`; правила fastest-validator конвертируются в JSON Schema, неподдерживаемые помечаются.
   - Ключи-классы в `links` становятся ролями один к одному; союзы, перечисляющие всех потомков одного класса, заменяются полиморфным концом.
   - Все идентификаторы пересчитываются: v5 — по новой формуле, а старые v4 и v7 становятся `ref` и дают новый v5. Импорт строит таблицу соответствий старых и новых идентификаторов и переписывает ссылки.
   - `Account` переходит в сущности, `Credential` — в приватную таблицу: хэши scrypt и ключей переносятся как есть, одноразовые коды не переносятся. Таблицы `Resource` и `Rule` становятся сущностями классов `Resource` и `rule`.
   - Сессии из Redis не переносятся, пользователи входят заново.

   Бенч на полигоне salon против letopis: вставка, чтение по естественному ключу, цепочка из трёх шагов, двадцать параллельных писателей, запрос на дату, смена класса.
6. **Позже, по необходимости:** запрет пересечения интервалов через ограничение исключения (расширение btree_gist), инструменты MCP поверх `describe()`, крипто-шреддинг персональных данных, `diff` и `blame` по журналу, производные представления из журнала.
