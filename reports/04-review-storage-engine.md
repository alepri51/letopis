## Как читать этот отчёт

**Уровни систем (tier).** Каждая находка привязана к уровням T1–T4 — типам систем, для которых она значима:
- **T1** — прототип: один арендатор, меньше миллиона строк.
- **T2** — SaaS с несколькими арендаторами, 1–20 млн строк.
- **T3** — потоки событий, 100+ млн строк.
- **T4** — регулируемые отрасли: аудит, DR (disaster recovery — восстановление после катастрофы).

Запись «T2+» означает «T2 и все более требовательные уровни».

**Серьёзность (Severity).** Шкала Critical / High / Medium / Low — оценка аудитора, насколько находка опасна для систем указанного уровня.

**Базовые термины.** Hypertable — таблица TimescaleDB, которую расширение автоматически разбивает на физические партиции по значению временной колонки. Chunk — такая физическая партиция hypertable за интервал времени. Tombstone — специальная версия-строка, помечающая сущность удалённой. Advisory lock — блокировка PostgreSQL по произвольному числовому ключу, не привязанная к строке таблицы. Latest («актуальная версия») — последняя по времени строка сущности; в letopis это не свойство строки, а результат запроса. Арендатор (tenant, account) — клиент SaaS, чьи данные должны быть изолированы от данных других клиентов.

## (A) Верифицированное резюме архитектуры

### Таблица и индексы

Всё хранилище — одна hypertable `Entity(partition,id,class,data jsonb,updated,account,tags,owner,links jsonb,deleted)` с первичным ключом `(partition,class,id,updated)`. Партиционирование только по времени (time-only chunking) — по колонке `updated` с шагом 30 дней; шаг зашит в код (hardcoded) и не настраивается (см. `lib/sql/ddl.sql:151-156`).

Индексы: btree по `(partition,class,id,updated DESC)`; три GIN-индекса — по `data`, по `links` с классом операторов jsonb_path_ops и по `tags`; btree по `account` и по `owner` (см. `ddl.sql:160-165`). GIN — инвертированный индекс PostgreSQL для составных значений (jsonb, массивы), который ускоряет проверки вхождения вроде `@>`.

Внешних ключей (FK) три: `class` → таблица `Schema` (`RESTRICT` при удалении, `ON UPDATE CASCADE` при переименовании), `account` и `owner` → таблица `Account` (`RESTRICT`). Подробности: `ddl.sql:141-143, 478-483`.

### Версии, время, триггеры

Версия сущности — это строка. «Актуальная» версия вычисляется запросом `DISTINCT ON … ORDER BY updated DESC`: берётся последняя по `updated` строка для каждого ключа сущности. Удаление — tombstone-строка. Модель времени — только transaction-time (момент записи в БД): `asOf` работает по колонке `updated`. Valid-time (бизнес-время, когда факт действителен в реальном мире) отсутствует.

Row-триггеров (срабатывающих на каждую строку) пять:
- `entity_check` — BEFORE INSERT: проверяет класс, признак abstract и то, что ключи в `links` — имена классов; существование целевой сущности по ссылке НЕ проверяется.
- `entity_update` — BEFORE UPDATE: превращает обновление в INSERT новой версии, физический UPDATE отменяется.
- `entity_delete` — BEFORE DELETE: берёт advisory-lock, пишет tombstone и рекурсивно каскадирует удаление на зависимые сущности по условию `links @>`.
- `entity_notify` — AFTER INSERT: вызывает `pg_notify`, канал — имя схемы.
- `entity_collapse` — AFTER INSERT: для классов с `meta.history=false` физически удаляет (DELETE) старые версии.

Серверные функции: `purge_closure`/`purge` — двухфазное физическое стирание (hard-erase) под флагом `SET LOCAL letopis.purge`; `purge_account`; `compact`. Ревизия движка хранится в `COMMENT ON SCHEMA` (`DDL_REVISION=2`); `connect()` сверяет её и при расхождении только предупреждает (warn).

### Чтение

Построение читающих запросов находится в `lib/src/sql.ts:616-913`. На каждый hop (переход по связи между классами) строится подзапрос `DISTINCT ON` над классом — полиморфно, то есть `class IN (семья классов)`. GIN-индексы дают кандидатов (`e.id IN (SELECT c.id … WHERE c.data @> …)`), после чего все предикаты перепроверяются на latest-версии. Hop'ы соединяются через `JOIN LATERAL` (соединение, в котором правая часть может ссылаться на строки левой); `.deep()` (обход произвольной глубины) реализован через `WITH RECURSIVE`; пагинация — keyset по паре `(sort, id)`.

Изоляция арендатора: предикат по `account` попадает в кандидатный подзапрос и во внешнюю перепроверку, но не во внутренний `DISTINCT ON` (см. `sql.ts:689-695, 741-751`).

### Запись

Код записи — `lib/src/write.ts`. Любая запись — всегда INSERT; `updated = GREATEST(clock_timestamp(), prev+1µs)`, то есть не меньше текущего времени и строго больше предыдущей версии. `create()` с известным id (явным или детерминированным v5) работает как «новая версия, если сущность нашли, иначе INSERT». `update()` — это read-latest → `deepMerge` (рекурсивное слияние патча с текущими данными) → INSERT.

Все публичные пути записи идут через `inTransaction` — внутреннюю транзакцию с ретраем ошибок 40P01 (deadlock) и 40001 (serialization failure) до 3 раз (см. `write.ts:604-619, 768, 894`). Ручная транзакция — `reserve()` (выделение соединения из пула) плюс голый `BEGIN` без уровня изоляции и таймаутов (см. `lib/src/tx.ts:42-67`). Пул `postgres.js` создаётся с единственными опциями `max` и `types` (см. `lib/src/index.ts:90-93`).

## (C) Детали по находкам: Critical/High (F1–F8) и Medium/Low (F9–F20)

В исходном отчёте этот раздел содержал развёрнутые пояснения только по F1–F8; здесь по той же схеме разобраны все двадцать находок. Для F9–F20 источник — строки таблицы (B) исходника.

### F1 — Retention удаляет актуальное состояние неизменявшихся сущностей

**Severity:** Critical. **Tier:** T3, T4; T2 — при включённом retention.

**Что происходит.** Retention — политика TimescaleDB, которая по расписанию физически удаляет chunk'и старше заданного возраста через `drop_chunks`. Hypertable `Entity` партиционируется по `updated`, а `updated` меняется только тогда, когда записывается новая версия сущности: новая строка появляется только при изменении. Справочные сущности (услуги, организации, адреса) часто не меняются годами. Их единственная строка стареет в chunk'е, который политика `add_retention_policy(…, '2 years')` физически дропает (см. `db/policies.mjs:73`). После этого `DISTINCT ON` не находит ни одной строки — сущность исчезает из всех чтений вместе со своими связями; каскад удаления при этом, разумеется, не срабатывает.

Проблема нигде не задокументирована. Предупреждение в `policies.mjs:71` и README §10.8 говорит про «историю этих периодов», что читается как «старые версии», а не «текущее состояние»; `README.md:1327-1328` тоже говорит только про «историю». Механизма «carry-forward» или `touch` (принудительного переноса актуальной версии в свежий chunk) нет.

**Почему это важно и для каких систем.** Для T3 и T4 retention — обязательный инструмент (объём данных, GDPR), поэтому это ловушка с необратимой потерей данных. Для T2 находка актуальна, если retention включён.

**Где в коде.** Партиционирование только по `updated` — `ddl.sql:151-156`; политика retention — `db/policies.mjs:69-75`. Подробности: `write.ts:421-445` (новая строка только при изменении), `README.md:1327-1328`.

**Что можно сделать.** Аудит предлагает три варианта. (a) Retention только для классов с `history:false` или по классу через `drop_chunks` с предварительным «re-stamp» latest-версий — INSERT копии latest с новым `updated`; сам по себе он дорог и создаёт ложные версии. (b) Отдельная таблица `current` (материализованный latest) вне hypertable. (c) Документировать как «retention недопустим при наличии долгоживущих сущностей».

### F2 — Cross-tenant «захват id» под `enforceAccount`

**Severity:** High. **Tier:** T2 (SaaS).

**Что происходит.** `enforceAccount` — режим, при котором все чтения и записи фильтруются по аккаунту вызывающего. `createOp` при известном id проверяет существование сущности чтением, и это чтение под `enforceAccount` фильтруется по `account` вызывающего (см. `write.ts:506`, `sql.ts:689-695`). Чужая сущность оказывается «не найдена», и движок делает INSERT с `prevUpdated:null` и `account = B` (см. `write.ts:527-536`); триггер `entity_check` принадлежность не проверяет (см. `ddl.sql:189-275`).

Итог: latest-строка сущности теперь принадлежит арендатору B. Для A внутренний `DISTINCT ON` выбирает строку B, потому что фильтр по account стоит только в кандидатном подзапросе и во внешнем WHERE, а внешний предикат `t.account = A` эту строку отбрасывает — A видит «сущности нет» (см. `sql.ts:775-792`). B при вызове `.versions()` получает все версии сущности A: join истории `v … ON v.class = z.class AND v.id = z.id` сделан без account (см. `sql.ts:882-887`).

Предусловие — знать id. Для случайных UUID v4/v7 это нереалистично. Но для детерминированных v5-id, вычисляемых из пользовательских скаляров (`from:['phone']` — README §3.2 явно поощряет такой приём), это типовой сценарий SaaS: формула `uuidv5(pgSchema:partition:class:parts)` не включает account (см. `write.ts:417`). Под `enforceAcl` с `$account`-предикатом probe (предварительная проверка доступа) блокирует живую сущность — вызов тихо возвращает `[]`, — но не tombstone: probe выполняется без `withDeleted` и только при `aclFilter` (см. `write.ts:522`, `write.ts:512-524`). Значит, воскрешение удалённой сущности под чужим account возможно. Тест `acl.test.ts:227-229` покрывает только `enforceAcl` с предикатом.

**Почему это важно и для каких систем.** Это нарушение изоляции арендаторов — ключевого свойства T2 (SaaS). Арендатор B и лишает A сущности, и читает её историю.

**Где в коде.** Проверка существования под фильтром account — `write.ts:503-527`; v5-namespace без account — `write.ts:417`. Подробности: `sql.ts:775-792` (account не во внутреннем `DISTINCT ON`), `sql.ts:882-887` (`versions` join без account), `ddl.sql:189-275` (нет проверки принадлежности), `acl.test.ts:227-229`.

**Что можно сделать.** Исправление дешёвое: в `entity_check` проверять `account` latest-версии того же `(partition,class,id)`, а в v5-namespace добавить account (это breaking-изменение для существующих id).

### F3 — Lost update: нет compare-and-set

**Severity:** High. **Tier:** T2, T3; Critical для T4 без блокировок на уровне приложения.

**Что происходит.** Compare-and-set (CAS) — приём, при котором запись проходит только если данные не изменились с момента чтения. В letopis его нет. `versionRows` читает latest, делает `deepMerge` и вставляет новую строку (см. `write.ts:421-445`, `write.ts:195-219`). `prevUpdated` используется лишь в выражении `GREATEST(clock_timestamp(), prev+1µs)` — это гарантия монотонности `updated`, а не CAS (см. `sql.ts:923-932`, в частности `:928-929`).

Две конкурентные `update()` от одной версии V1 (с разных соединений пула или с двух инстансов приложения) дадут V2a и V2b с разными `clock_timestamp`. Обе успешны, latest — поздняя, а патч первой молча потерян, причём частично, потому что `deepMerge` сливает по листьям. Коллизия первичного ключа (ошибка 23505) ловит только совпадение микросекунды. Единственный рецепт — ручной `tr.lock()` (README §7), и он оформлен для сценария двойной брони, а не для «любого update». Никакого `expectedUpdated` или `WHERE NOT EXISTS newer` нет. Тестов на конкурентный `update()` нет — гонки покрыты только для `create` с v5-id.

**Почему это важно и для каких систем.** T2/T3 — счётчики, статусы, параллельные операторы. Для T4 — критично: аудит без CAS означает, что «что было записано» не равно «что хотели записать».

**Где в коде.** `write.ts:421-445` (read → `deepMerge` → INSERT), `write.ts:195-219`. Подробности: `sql.ts:923-932` (`prevUpdated` нужен лишь для монотонности).

**Что можно сделать.** Опциональный `expectedUpdated` с проверкой прямо в INSERT (`WHERE NOT EXISTS (… updated > $prev)`) либо advisory-lock в `versionRows`.

### F4 — GIN по всем версиям: неселективные фильтры по мутабельным полям

**Severity:** High. **Tier:** T3 (в конфликте с требованиями T4).

**Что происходит.** GIN-индексы построены по всем строкам, то есть по всей истории. Кандидатный подзапрос не умеет ограничиться latest-строками, потому что свойство «latest» не хранится в строке. Поэтому любой фильтр по мутабельному (меняющемуся) полю масштабируется объёмом истории, а не числом сущностей: `{status:'pending'}` матчит каждую сущность, когда-либо бывшую pending, — O(история).

Авторы это признают (CHANGELOG 0.21.0) и предлагают `history:false` — то есть для очередей и outbox-таблиц отказаться от истории вовсе. Штатное лечение — отказ от истории, а значит, аудит уровня T4 для тех же классов невозможен.

**Почему это важно и для каких систем.** Это фундаментальное противоречие одной таблицы «и аудит, и рабочее состояние»: T3 получает производительность ценой T4-требований.

**Где в коде.** GIN-индексы — `ddl.sql:161-163`; кандидатный подзапрос — `sql.ts:775-784`. Подробности: `README.md:3675-3678`, `ddl.sql:576-580` и CHANGELOG 0.21.0.

**Что можно сделать.** Индустриальный ответ — две таблицы (`current` + `history`) или хотя бы флаг `is_latest` с partial-GIN (частичным индексом только по актуальным строкам). Последнее несовместимо с append-only без UPDATE.

### F5 — Стоимость точечного доступа пропорциональна числу chunk'ов; шаг 30 дней зашит

**Severity:** High. **Tier:** T2+; Critical для T3.

**Что происходит.** Все обращения идут по ключу `(partition,class,id)`, а не по времени. Поэтому ни один read не может исключить chunk'и по времени (chunk exclusion — способность планировщика пропускать партиции, заведомо не содержащие нужных дат), и каждый точечный запрос заглядывает во все chunk'и. README §14 честно фиксирует это, включая модель стоимости «строки × чанки» и цифру 17.7 млн буферов (см. `README.md:3687-3698`). Интервал 30 дней зашит в `ddl.sql:153`, конфигурации нет.

При трёх годах данных получается 36 chunk'ов — примерно ×2.8 к полигону из 13 chunk'ов: traversal, занимающий 30 с, вырастет до ~80 с. Каждая индексная проба, каждый `JOIN LATERAL` и планирование растут линейно с возрастом базы, а не с её полезным объёмом. Планирование уже сейчас дороже исполнения на точечном чтении: в `lib/bench/dimensions.results.json` для `explain_point` planning 1.668 ms против execution 0.566 ms (аудит округляет это до «3× дороже»).

**Почему это важно и для каких систем.** Для T2+ стоимость всех чтений растёт каждые 30 дней. Для T1/T2 без compression и retention обычная таблица с теми же индексами была бы строго быстрее — hypertable для этого read-паттерна, по оценке аудита, чистый минус.

**Где в коде.** `ddl.sql:153` (шаг chunk'а), `README.md:3687-3698` (модель `строки × чанки`, 17.7 млн буферов). Подробности: `lib/bench/dimensions.results.json` (`explain_point`).

### F6 — На сжатых chunk'ах нет GIN

**Severity:** High. **Tier:** T2+.

**Что происходит.** Compression — сжатие старых chunk'ов TimescaleDB в колоночный формат; `segmentby` — ключ, по которому строки группируются в сегменты при сжатии. На сжатых chunk'ах Timescale создаёт только btree по `segmentby`-ключу; GIN-индексов по `data`/`links`/`tags` там нет. Значит, после `--compress-after=30d` любой containment-фильтр (проверка вхождения `@>`) и любой reverse-hop (обратный переход по ссылкам, `c.links @> …`), затрагивающий сжатые chunk'и, декомпрессирует сегменты всего класса.

Тест `wave4` проверяет только `first/versions/asOf` по id — это сегмент по `(partition,class,id)`, то есть быстрый случай (см. `lib/test/wave4.test.ts:56-63`). README обещает, что «чтение прозрачно» (см. `README.md:1324-1326`). Поведение фильтров по сжатым chunk'ам не измерено и не задокументировано.

**Почему это важно и для каких систем.** Для T2+ с включённым compression это скрытый обрыв производительности фильтров.

**Где в коде.** `policies.mjs:55-61` (политика compression), `lib/test/wave4.test.ts:56-63`. Подробности: `README.md:1324-1326`.

### F7 — Upgrade держит AccessExclusiveLock на Entity и всех chunk'ах; время растёт с историей

**Severity:** High. **Tier:** T2+.

**Что происходит.** `ddl.sql` идемпотентен (повторный накат не ломает базу), но не бесплатен. `DROP/CREATE TRIGGER` и `DROP/ADD CONSTRAINT` берут AccessExclusiveLock (самую строгую блокировку PostgreSQL, запрещающую даже чтение) на hypertable и на каждом chunk'е. `ADD CONSTRAINT` без `NOT VALID` (модификатора, который откладывает проверку существующих строк) сканирует все строки: BACKLOG замерил ~0.8 с на 1M строк и 13 chunk'ах, зависимость линейная. Затем идёт `ANALYZE` — 12.8 с. Всё выполняется одной транзакцией `sql.unsafe(text)` — весь файл одним вызовом (см. `up.ts:266-267`, `lib/src/up.ts:265-271`).

Дополнительно: `DDL_REVISION` — только предупреждение (см. `index.ts:66-86`); ledger миграций (журнал применённых миграций) отсутствует; down-миграций нет; инструмента переноса v1→v2 нет — несовместимая структура означает новую схему `v2` и ручной перенос данных «силами приложения».

**Почему это важно и для каких систем.** На T3-объёмах это минуты полной блокировки. Для T2+ отсутствие ledger'а и инструмента переноса — это отсутствие migration story.

**Где в коде.** `lib/src/up.ts:265-271` (весь файл одной `unsafe`), `BACKLOG.md:403-418, 444-461`. Подробности: `ddl.sql:277-280, 314-318, 365-372, 478-483, 569-572, 621-624` (места DROP/CREATE и DROP/ADD), `index.ts:66-86` (warn-only).

### F8 — Ручные транзакции без таймаутов; пул 10 без acquire-timeout

**Severity:** High. **Tier:** T2+.

**Что происходит.** `beginTx` резервирует соединение и шлёт голый `BEGIN` (см. `tx.ts:43-48`): уровень изоляции — READ COMMITTED, без `statement_timeout` (лимит на один запрос), `lock_timeout` (лимит ожидания блокировки) и `idle_in_transaction_session_timeout` (лимит простоя открытой транзакции). Пул — `max: 10` (см. `index.ts:90-93`); у postgres.js 3.4.9 по умолчанию `idle_timeout: null` и нет acquire-timeout (лимита ожидания свободного соединения из пула).

Следствия: при утечке `tr` — исключении между `begin()` и `rollback()` — слот пула теряется навсегда; 10 утечек — и все запросы висят. При исчерпании пула ожидание бесконечно и без ошибки. Долгие `DISTINCT ON`-сканы (5–30 с по README §14) без таймаута под нагрузкой блокируют пул. Ни одна из этих опций не пробрасывается через `ConnectOpts` (см. `lib/src/types.ts:293-331`).

**Почему это важно и для каких систем.** T2+ — любая многопользовательская нагрузка с долгими запросами или ошибками внутри транзакций.

**Где в коде.** `tx.ts:42-67`, `index.ts:90-93`. Подробности: `lib/src/types.ts:293-331` (`ConnectOpts`); дефолты postgres.js 3.4.9.

### F9 — Ретрай 23505 и transient-ошибок в `insertOne` недостижим из публичного API

**Severity:** Medium. **Tier:** T2, T3.

**Что происходит.** В `insertOne` есть ретрай на ошибку 23505 (нарушение уникальности) и на транзиентные ошибки, но он срабатывает только при `!ctx.inTx` — вне транзакции (см. `write.ts:208`). При этом все публичные пути записи идут через `inTransaction`, где `inTx:true` (см. `write.ts:768, 894`). Значит, ретрай недостижим. Случай 23505 — когда обе стороны получили одинаковый `prev+1µs` при откате часов — уходит приложению как ошибка. `README.md:1432` утверждает обратное: документация расходится с кодом.

**Почему это важно и для каких систем.** T2, T3 — конкурентная запись одной сущности.

**Где в коде.** `write.ts:208`, `write.ts:768, 894`. Подробности: `README.md:1432`.

### F10 — Каскад против конкурентной версии зависимого; ссылочной целостности `links` нет

**Severity:** Medium. **Tier:** T2, T3.

**Что происходит.** Каскад в `entity_delete` ищет зависимых по снимку (snapshot) DELETE-оператора, а проверку «latest уже tombstone» делает в новом снимке (см. `ddl.sql:343-347, 357-360`). Зависимая сущность, обновлённая параллельно с каскадом, остаётся живым «сиротой» — ссылается на уже удалённого родителя.

Вторая часть: ссылочной целостности для `links` нет. `entity_check` проверяет только, что ключ в `links` — существующий класс, но не существование целевой сущности (см. `ddl.sql:219-225`). Слот связи в API принимает сырую строку (см. `write.ts:345-346`), поэтому `set('любой-id')` создаёт висячую ссылку.

**Почему это важно и для каких систем.** T2, T3 — конкурентные удаления и обновления, а также любые данные, где важна целостность графа связей.

**Где в коде.** `ddl.sql:343-347, 357-360`; `ddl.sql:219-225`. Подробности: `write.ts:345-346`.

### F11 — `entity_collapse`: лок берётся после INSERT, `updated` вычисляется до

**Severity:** Medium. **Tier:** T3.

**Что происходит.** Для no-history классов (`meta.history=false`) триггер `entity_collapse` после вставки удаляет старые версии. Но advisory-lock берётся уже после INSERT, а значение `updated` вычисляется до него (см. `ddl.sql:607-616`, `ddl.sql:578-584`). Инверсия порядка приводит к гонке, при которой на один id остаются две строки; состояние самоизлечивается следующей вставкой. Кроме того, DELETE старых версий бьёт в старые и, возможно, сжатые chunk'и: там появляются dead tuples (мёртвые версии строк, требующие vacuum) и декомпрессия, тогда как Timescale ожидает, что старые chunk'и «холодные» и не меняются.

**Почему это важно и для каких систем.** T3 — очереди и потоки с высокой частотой записи в no-history классы.

**Где в коде.** `ddl.sql:607-616`, `ddl.sql:578-584`.

### F12 — Стоимость INSERT и лимиты батча

**Severity:** Medium. **Tier:** T3.

**Что происходит.** На каждую вставляемую строку выполняется Schema-lookup (запрос к таблице `Schema`) в двух триггерах (см. `ddl.sql:206-225, 599-603`), обновляются 7 индексов (из них 3 GIN), проверяются 3 FK и вызывается `pg_notify`. Fast-path для батча (ускоренный путь одной multi-row INSERT) работает только для чистых `create` без слотов связей и не для v5-id. Нарезки по лимиту 65535 параметров нет: больше 8191 строк в батче дают ошибку bind. Пути через COPY (массовая загрузка PostgreSQL) нет. Бенч: `insert_one` p50 6.2 ms.

**Почему это важно и для каких систем.** T3 — потоки событий с большим числом записей в секунду.

**Где в коде.** `ddl.sql:206-225, 599-603`; `write.ts:877-883, 900-921`. Подробности: `sql.ts:935-946`.

### F13 — Дуальная модель «схема `vN.name` плюс колонка account»

**Severity:** Medium. **Tier:** T2+.

**Что происходит.** В letopis два механизма разделения данных: отдельные схемы PostgreSQL с именем вида `vN.name` (версия движка плюс имя) и колонка `account` внутри одной схемы. Пул соединений создаётся на схему (см. `index.ts:88-95`); `db/apply.mjs:42` и `policies.mjs:42` обрабатывают по одной схеме за прогон. Ключ advisory-lock не включает имя схемы (см. `ddl.sql:340-341`).

Следствия: N схем — это N пулов, N×36 chunk'ов ×7 индексов в системном каталоге и N job'ов политик; cross-schema запросов нет; пространство advisory-lock'ов общее между схемами и `tr.lock()`.

**Почему это важно и для каких систем.** T2+ — при росте числа схем.

**Где в коде.** `index.ts:88-95`, `ddl.sql:340-341`. Подробности: `db/apply.mjs:42`, `policies.mjs:42`.

### F14 — Эволюция Schema против истории

**Severity:** Medium. **Tier:** T2+.

**Что происходит.** Валидация данных работает в режиме `$$strict` — неизвестные ключи отвергаются (см. `lib/src/schema.ts:255`). `deepMerge` при `update()` не удаляет ключи (см. `write.ts:106-118, 431-435`). Поэтому после удаления атрибута из схемы `update()` строк, где этот атрибут ещё есть, «кирпичится»: старые данные не проходят строгую валидацию. Вторая проблема — переименование класса. FK `class → Schema` объявлен с `ON UPDATE CASCADE` (см. `ddl.sql:141-143`), но каскадный UPDATE строк `Entity` проходит через триггер `entity_update`, который отменяет физический UPDATE (см. `ddl.sql:296-312`), — работать это не может; тестов нет.

**Почему это важно и для каких систем.** T2+ — любая система с долгой историей и меняющейся схемой.

**Где в коде.** `lib/src/schema.ts:255`; `write.ts:106-118, 431-435`. Подробности: `ddl.sql:141-143`, `ddl.sql:296-312`.

### F15 — Зависимость от TimescaleDB: лицензия, managed-cloud, пин образа

**Severity:** Medium. **Tier:** T2–T4.

**Что происходит.** Хранилище требует `CREATE EXTENSION` (см. `ddl.sql:36`); Docker-образ закреплён на `latest-pg17` (см. `lib/docker/Dockerfile:29`), и то же ограничение записано в `docs/technology.xml:19`. Managed-сервисы RDS и Aurora не поставляют TimescaleDB. `CREATE EXTENSION` требует привилегий. При этом единственное, ради чего нужен Timescale, — compression и retention.

**Почему это важно и для каких систем.** T2–T4 — при выборе хостинга и лицензионной модели.

**Где в коде.** `ddl.sql:36`, `lib/docker/Dockerfile:29`. Подробности: `docs/technology.xml:19`, `policies.mjs:64-65, 72-73`.

## (D) Потолок масштабирования по tier'ам

**T1 (прототип, <1M строк, один tenant).** Работает и достаточно быстро: catalog-запросы 4–20 ms, запись 6–25 ms. Первыми ломаются `ANALYZE` после заливки (деградация ×18–×126, README §14.1), traversal от широкого класса (30 с на 980k строк) и утечки `tr` без таймаутов. Timescale здесь — лишняя операционная зависимость (Docker-образ `latest-pg17`).

**T2 (SaaS, 1–20M строк, account-изоляция).** Первыми ломаются F2 (захват id при v5-из-данных — нарушение изоляции), F3 (lost update при нескольких инстансах), F8 (пул/таймауты) и F7 (upgrade — блокировка на минуты). При росте истории — F5 (каждые 30 дней +1 chunk к стоимости всех reads). Compression включать нельзя без замера F6. Вердикт: пригодно при условии патчей F2/F3/F8 и отказа от v5-id из пользовательских полей.

**T3 (100M+ строк, очереди/outbox, много писателей).** Не пригодно в текущем виде. F1 делает retention опасным; F4 требует `history:false` (потеря истории); F12 — 7 индексов, 3 триггера с Schema-lookup и NOTIFY на строку ограничивают single-writer примерно 100–150 rps, батч без COPY и с лимитом 8191 строк; F11 — collapse-DELETE в старых chunk'ах. Hot-chunk GIN pending-list (буфер отложенных вставок GIN-индекса в самом свежем chunk'е) — общая точка сериализации трёх GIN.

**T4 (regulated, DR/HA, bitemporal).** Не пригодно. F1 (необратимая потеря current state), F2 (изоляция), F3 (аудит без CAS — «что было записано» не равно «что хотели»), F17 (нет valid-time), F15 (TSL-лицензия, отсутствие managed-cloud), F16 (нет backup/DR-процедуры для hypertable; логическая репликация hypertable с ограничениями). Иммутабельность истории условна: `purge`/`compact`/`purge_account`/`entity_collapse` физически удаляют строки при наличии обычных прав.

## (E) Что сделано хорошо

- **Candidate + recheck.** GIN-индекс используется только для сужения множества кандидатов, а истина устанавливается перепроверкой всех предикатов на latest-версии (см. `sql.ts:775-792`). Поэтому фильтр, совпавший с устаревшей версией, не даёт ложных срабатываний. Полиморфизм через идентичность `(class,id)` и ACL-предикаты на каждый класс продуманы (см. `sql.ts:699-739`).
- **Серверный каскад с защитой от циклов и ромбов.** Проверка «latest уже tombstone» корректно гасит рекурсию (см. `ddl.sql:345-347`); advisory-lock берётся по ключу сущности; превью каскада строится тем же `closureSql`.
- **Двухфазный purge.** Флаг `SET LOCAL letopis.purge` проверяется в `WHEN`-условии триггера (см. `ddl.sql:371, 444-453`) — чисто, без ошибки TM_SelfModified (попытки изменить строку, уже изменённую той же командой), и флаг транзакционный.
- **Детерминированные v5-id как средство идемпотентности** (README §3.2, тесты `idgen.test.ts:134-184`) — сильный приём, испорченный лишь отсутствием account в namespace (см. F2).
- **Честность документации.** README §14 признаёт 30 с и объясняет модель стоимости; §14.1 — про ANALYZE; BACKLOG содержит замеры `pg_locks`; `schema-sync` выдаёт отчёт о ломающих изменениях.
- **Классификация ошибок и тесты устойчивости.** Реальный deadlock двух транзакций и `pg_terminate_backend` для LISTEN-соединения (см. `resilience.test.ts:72-119`); гонки двойной брони (см. `core.test.ts:484-519`, сцены C3/C7/C15 в `real-life.test.ts`).
- **Ревизия DDL в `COMMENT ON SCHEMA`** и мгновенный `db.schema.define()` + `reloadSchema` — прагматичная реализация «схема в БД».

## (F) Предлагаемая структура разделов отчёта

**«Схема БД и storage-модель»**
1. Единая hypertable и PK `(partition,class,id,updated)`: что это даёт и чего стоит (versioning = rows; latest — запрос, а не свойство строки).
2. Триггерный CRUD (`entity_check`/`entity_update`/`entity_delete`/`entity_notify`/`entity_collapse`): какие инварианты гарантирует БД, а какие оставлены клиенту — валидация `data`, существование целей `links`, принадлежность id (F2, F10).
3. Модель конкурентности: `clock_timestamp` + `GREATEST`, ошибка 23505 (F9), lost update (F3), advisory-lock как единственный CAS, гонка collapse (F11).
4. Изоляция арендаторов: где стоит предикат `account` в SQL и почему этого недостаточно (F2); дуальность «схема/account» (F13).
5. Время: только transaction-time, `asOf` через tombstone, отсутствие valid-time (F17); no-history как отказ от истории (F4).
6. Эволюция схемы: strict-валидация против исторических строк, rename/delete класса, ревизия DDL и стоимость upgrade (F7, F14).
7. Хранение истории: compression (F6) и retention (F1) — реальные последствия, а не «прозрачно».

**«Масштабируемость и эксплуатация»**
1. Модель стоимости чтений: `DISTINCT ON` на hop × `JOIN LATERAL` × число chunk'ов; зависимость от ANALYZE; полиморфизм ×20; таблица потолков по tier'ам (раздел D).
2. Модель стоимости записи: индексы, FK и триггеры на строку; batch fast-path и его лимиты; отсутствие COPY (F12); hot chunk и GIN pending list.
3. TimescaleDB: что реально используется (только compression/retention), лицензия TSL против Apache-2, managed-cloud (RDS/Aurora — нет), пин `latest-pg17`, необходимость `CREATE EXTENSION` (F15); сценарий «vanilla PG17 без hypertable» как рекомендация для T1/T2.
4. Транзакции и пул: reserved connection, таймауты, PgBouncer, LISTEN (F8, F16).
5. Наблюдаемость и DR: `onQuery`/`slowMs` как единственный сигнал; нет метрик, health и backup-процедуры; периодический ANALYZE родителя hypertable.
6. Рекомендации по приоритетам: (1) ownership-check в `entity_check` плюс account в v5-namespace; (2) `expectedUpdated`-CAS; (3) таймауты и опции пула в `ConnectOpts`; (4) документировать или запретить retention при долгоживущих сущностях; (5) разделить `ddl.sql` на структуру и код, `NOT VALID` + `VALIDATE`; (6) конфигурируемый chunk interval или режим без hypertable.
