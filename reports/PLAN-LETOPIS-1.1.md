## Словарь

| Слово | Что значит в этом плане |
|---|---|
| diff | различия между двумя версиями объекта: какие пути изменились, что было и что стало |
| blame | для каждого поля версии — какая версия, кто, когда и почему изменила его последней |
| путь | адрес поля в строке — массив сегментов: `["data", "price", "amount"]`, `["links", "Staff"]` |
| причина изменения | текст, который сохраняется в колонке журнала `reason`, например «отмена по просьбе клиента» |
| токен сигнала | первые 96 бит HMAC от имени класса или id арендатора на секретном ключе установки. Без ключа по токену не узнать, что за ним стоит |
| режим установки | настройка, которая действует на всю схему (здесь — режим сигналов). Хранится в самой схеме |
| первая заливка | загрузка в схему без данных: индексы и триггеры снимаются на время загрузки и строятся заново в конце |
| `COPY FREEZE` | вариант `COPY`, при котором строки сразу пишутся «замороженными», и последующий VACUUM их не переписывает |
| агрегат класса | поле, которое база сама держит равным сумме или числу строк другого класса. Пример: баланс кошелька — сумма операций |
| проектор | процесс, который читает журнал по курсору и строит из изменений строки производных классов |
| производный класс | класс, строки которого пишет только проектор, а приложение их только читает |
| чекпоинт проектора | курсор журнала вместе со снимком, до которого проектор обработал изменения. Хранится в `secret` и сдвигается в той же транзакции, что и запись результатов |
| MCP | Model Context Protocol — открытый протокол, по которому агент на языковой модели вызывает инструменты внешней системы |
| инструмент MCP | функция, которую агент вызывает по имени с аргументами, описанными JSON Schema |

### Что остаётся неизменным

- Ровно три таблицы. Новое — это виды строк `secret` и опции классов.
- Целостность держит база, и сырой SQL проходит те же проверки. Всё, что пишет мимо триггеров (функции владельца, загрузчик, проектор), проверяет само, и это закрыто тестами.
- Функции владельца — `security definer`, с фиксированным `search_path`, без динамического SQL. Новая функция владельца получает негативный тест (`roles` №4).
- Формула хэша версии и схема `v2` прежние.
- PostgreSQL 18 и новее. Рантайм-зависимость одна — `postgres`. Новые зависимости — только необязательные peer (SDK MCP).

**Совместимость с 1.0 не требуется** (решение владельца от 10 октября). Процессам 1.0 и новых версий не нужно работать с одной схемой, схемы 1.0.1 не обновляются на месте, а API 1.0 можно менять там, где это упрощает новое.

### Критерии готовности

1. Каждая возможность реализована по §2, её тест-план (§7) проходит в CI на `postgres:18`.
2. Повторный `up()` на схеме новой версии с данными сохраняет данные, хэши и режим сигналов, а `verify({ data: true })` после него чист.
3. Замеры сняты и приняты владельцем на контрольных точках (§6): цена режимов сигналов, ускорение первой заливки, `blame`, цена агрегатов и проекторов.
4. Проведены два ревью безопасности: на точке А (сигналы, первая заливка, история) и перед выпуском 1.2 (проекторы, агрегаты, MCP). Каждая находка закрыта тестом.
5. Документация соответствует коду: README и шпаргалка (обе версии), `llms.txt`, CHANGELOG, контракт API, карта atlas. `check-docs` проходит. Агент, видевший только README, решает новые задачи (§7.9).

## 2. Главные решения

### 2.1. `diff` и `blame` (п. 4)

**Зачем.** `versions()` в 1.0 отдаёт полные снимки версий, а что именно изменилось, приложение вычисляет само. `diff` отвечает на вопрос «что изменилось между двумя версиями или моментами», `blame` — «кто, когда и почему последним менял каждое поле».

**API.**

```ts
await t.Order(id).diff()                          // предыдущая версия → текущая
await t.Order(id).diff({ from: 3, to: 7 })        // по номерам версий
await t.Order(id).diff({ from: '2026-10-01' })    // состояние на момент → текущее
await t.Order(id).blame()                         // каждое поле текущей версии
await t.Order(id).blame({ at: '2026-10-01' })     // каждое поле версии на момент
```

Результат `diff` — по одному элементу на объект шага:

```ts
{ id, class,
  from: { rev, at } | null,
  to: { rev, at, deleted? } | null,
  changes: [
    { path: ['data', 'price', 'amount'], kind: 'changed', before: 100, after: 120 },
    { path: ['links', 'Services'], kind: 'added', after: '<id>' },
  ] }
```

Как сравниваются разделы строки:
- `kind` — `added`, `removed` или `changed`; `before` и `after` — значения JSON. У `added` нет `before`, у `removed` — `after`.
- Путь — массив сегментов, первый из них — раздел строки: `data`, `links`, `tags`, `owner`, `class`. Строка с точками не годится: точки и цифры в именах ключей делают её неоднозначной. С этим столкнулся MongoDB и в 6.1 добавил `disambiguatedPaths`.
- `data`: объекты сравниваются по ключам рекурсивно, массивы и скаляры — целиком. Так же сливает данные `merge` (массив заменяется целиком) и так же поступают аудит-системы (PaperTrail, django-simple-history). Поэлементное сравнение массивов (LCS, как в jsondiffpatch) по умолчанию не делается: его результат неоднозначен и неудобен агенту.
- Одиночный конец — `changed` со старым и новым id. Множественный конец — множество: `added` и `removed` по каждому id, как кардинальность many в Datomic и списки `set` в Kubernetes. Теги — тоже множество.
- Запись того же значения изменением не считается, как в Datomic. Пустая правка в letopis версии и так не пишет.

Какие версии сравниваются:
- `from` и `to` — номер версии или момент. Момент сводится к версии, действовавшей в него, по правилу среза `asOf`: последняя версия с `at ≤ T`, не надгробие.
- Если объекта на момент `from` не было, все его пути — `added`. Если на момент `to` объект удалён, ставится `to.deleted: true`, а изменения полей не перечисляются.
- `follow: true` — сравнение через смену id при `rekey` и `reclass` (по колонке `moved`), как в `versions({ follow: true })`.

Результат `blame` — тоже по объекту шага:

```ts
{ id, class, rev, complete: true,
  fields: [{ path: ['data', 'status'], rev: 12, at, author, agent, op, reason, exact: true }, …] }
```

Как считается:
- Для каждого листа версии (текущей или версии на момент `at`) находится последняя версия, где значение по этому пути отличалось от предыдущей. Лист — это скаляр, массив, роль одиночного конца, каждый id множественного конца, тег.
- Автор, агент, вид операции и причина принадлежат версии, а не полю. Так же устроены транзакции-сущности Datomic, ревизии Envers и `transaction_log` в pgMemento. Поэтому `blame` — это соединение «путь → версия».
- `exact: false` ставится, если до найденной версии история неполная: стёрта обрезкой (`trim`), прорежена политикой хранения или часть версий не видна актору. Настоящее изменение тогда могло быть раньше. `complete: true` значит, что у объекта таких пропусков нет. В git ту же роль играют пометки `?` и `*` при `--ignore-rev`.
- Версии видов `reclass` и `rekey` поля себе не «присваивают»: значения при них переносятся, а не меняются. Это как `--ignore-rev` для массовой правки форматирования.
- Удалённых полей в `blame` нет — их нет в версии. Где и кем поле удалено, показывает `diff`.

**Причина изменения.** В 1.0 колонку `reason` журнала заполняет только сырой SQL через настройку `letopis.reason`. В библиотеке способа её задать нет: `TxContext.reason` нигде не присваивается. Без причины `blame` отвечает только «кто и когда». Поэтому этап добавляет:
- опцию `reason` глаголам записи: `update(patch, { rev, reason })`, `create(data, { reason })`, `upsert(data, { reason })`, `delete({ confirm, reason })` и прочим;
- `db.begin({ reason })` и `db.batch(name, { reason })` — причину для всех операций блока.

Причина ставится настройкой `letopis.reason` перед оператором глагола, поэтому у разных глаголов одного плана или батча могут быть разные причины.

**Где считается.** В базе:
- функция `jsonb_changes(a, b)` — чистая, IMMUTABLE, обходит объекты по ключам;
- `version_changes(…)` сравнивает разделы строки;
- `diff_versions(id, from, to)` и `blame(id, rev, limit)` читают журнал с правами вызывающего (`security invoker`). Поэтому на них действует политика RLS журнала, и чужие или скрытые версии в расчёт не попадают.

Сырой SQL получает то же самое: `select * from "v2.shop".blame('<id>')`. Библиотека находит id шага и вызывает эти функции одним запросом на пачку объектов.

**Права.** История — это чтение. Актор видит те версии, которые разрешены ему текущими правами (политика `log_select`), как в Kinto, Directus и Databricks. Невидимая версия выпадает из расчёта, а соседние с пропуском результаты помечаются `exact: false`. Полевых прав в letopis нет, поэтому маскировать отдельные пути, как django-auditlog или Veeva, не нужно.

**Цена.** `blame` по снимкам стоит O(число версий × размер строки). По умолчанию просматривается не больше 1000 последних версий (`limit`), дальше ставится `complete: false`. Можно хранить у каждой версии список изменённых путей, как флаги `_MOD` в Envers или дельту в pgMemento. Но это новая колонка журнала (ревизия движка 6) и работа для загрузчика, поэтому замер делается в конце этапа 1, а решение владелец принимает до начала этапа 2: если `blame` по 1000 версиям дольше 100 мс, колонка добавляется.

**Как это устроено у других.**

| Система | Что даёт | Формат | Автор и причина |
|---|---|---|---|
| Dolt | `dolt_diff_<t>` по коммитам, `dolt_commit_diff_<t>` суммарно, `dolt_blame_<t>` по строке, `DOLT_JSON_DIFF` | колонки `from_*`/`to_*` и `diff_type`. В JSON — путь MySQL, массивы по индексам: вставка в середину даёт «изменено» на каждом сдвинутом индексе | коммит: автор, сообщение |
| git blame | последняя ревизия, менявшая строку; `--ignore-rev` | построчно; удалённые строки не показываются | автор коммита |
| TerminusDB | патч с проверкой старого значения (`SwapValue`) | дерево операций | — |
| Datomic | история фактов, `as-of`, `since` | `[e a v tx added]`; равное значение не записывается | транзакция — сущность с аннотациями |
| SQL Server, MariaDB, Oracle | временные таблицы, `VERSIONS BETWEEN` | версии строк; два момента — соединение двух `AS OF` | у Oracle — отдельным запросом к `FLASHBACK_TRANSACTION_QUERY` |
| Snowflake, BigQuery, Delta Lake | `CHANGES`, Change Data Feed | события изменений в окне хранения (у BigQuery — сутки) | — |

| Hibernate Envers | `withModifiedFlag` — «кто менял поле X» | флаг на свойство в каждой ревизии | ревизионная сущность |

Выводы:
1. Нужны две поверхности, как у Dolt. Пошаговая история уже есть (`versions()`), к ней добавляются суммарный `diff(a, b)` и `blame`.
2. Плоский список «путь → было/стало» с заголовком версии удобнее патч-форматов. В RFC 6902 у `replace` и `remove` нет старого значения, в RFC 7396 нельзя записать `null`, а jsondiffpatch кодирует операции «магическими числами».
3. Ссылки сравниваются как множества, массивы данных — целиком.
4. Автор и причина принадлежат версии.
5. Права — текущие права читателя; при неясности результат закрывается.

### 2.2. Сигналы: точность до арендатора и режимы без имён классов (п. 7 и п. 8)

**Как в 1.0.**
- Каждая запись посылает `NOTIFY` в канал схемы с именем изменённого класса. Отзыв сессии посылает `session:<16 hex>`, сброс — `*`.
- Транзакции библиотеки не шлют сигнал сами: функция `signal()` копит имена классов в настройке транзакции `letopis.changed`, библиотека читает её перед фиксацией, и после фиксации `Notifier` отправляет имена одним оператором. Сырой SQL шлёт сигнал при фиксации. Загрузчик и импорт вызывают `pg_notify` напрямую.
- По сигналу класса кэш результатов сбрасывает ответы, читавшие этот класс, во всех арендаторах сразу, а подписка `watch` просыпается. Сигнал `*` вдобавок перечитывает реестр классов и сбрасывает пропуска прав.
- Сигналы видит любая роль, которая может подключиться к базе. Прав на каналы в PostgreSQL нет, и запретить `LISTEN` нельзя ни правами, ни RLS, ни `pg_hba.conf`. По именам классов посторонний видит, когда и во что пишут.

**Режимы.** Режим выбирается опцией `up({ signals })` и хранится в схеме (§2.6): повторный `up()` без опции его не меняет.

| Режим | Нагрузка сигнала | Кэш | Что видит посторонний |
|---|---|---|---|
| `class` (по умолчанию, как в 1.0) | `Booking` | сброс класса во всех арендаторах | имена классов и время записи |
| `tenant` | `Booking@<токен арендатора>` | сброс класса только в этом арендаторе | имена классов, время, псевдонимы арендаторов |
| `opaque` | `<токен класса>@<токен арендатора>` | как у `tenant` | время записи и частоту по псевдонимам |
| `none` | сигналов нет | только по сроку (`ttlOnly`) или выключен; подписка опрашивает журнал | ничего, кроме нагрузки на базу |

Токены и нагрузка:
- **Токен** — первые 96 бит HMAC-SHA256 от «назначение ‖ значение» на секретном ключе установки, 24 строчных шестнадцатеричных символа. Ключ выводится из ключа строки `secret` с id System (`hmac('letopis:signals', ключ)`), поэтому новая строка не нужна, а `reset({ all })` вместе с ключом меняет и токены. Открытая соль не годится: имён классов мало, и их подобрали бы по словарю.
- **Нагрузка детерминирована** — без счётчиков и времени. PostgreSQL склеивает одинаковые сигналы транзакции, поэтому транзакция, записавшая тысячу броней одного арендатора, посылает один сигнал. Транзакция, задевшая N пар «класс, арендатор», посылает N сигналов.
- **Каналы не множатся по арендаторам и классам.** В PostgreSQL 18 любой `NOTIFY` будит всех слушателей базы, а поиск канала — линейный перебор. Избирательное будение появится только в PostgreSQL 19, и там остаётся общая для кластера блокировка при фиксации транзакции с `NOTIFY`. Канал во всех режимах один — имя схемы, как в 1.0.

Что сбрасывается:
- **Строки System** — классы, общие справочники — задевают все арендаторы. Сигнал с токеном System сбрасывает класс везде.
- **Классы прав** (`rule`, `Resource`, `member`, `Account`, `Class`) сбрасывают весь кэш и пропуска прав, как в 1.0. В режиме `opaque` библиотека узнаёт их по токенам.
- **Сессии** — сигнал `session:<16 hex>` во всех режимах, кроме `none`. Хэш токена сессии ничего не говорит ни о классе, ни об арендаторе.

Кто получает ключ:
- Функция владельца `signal_key()` отдаёт ключ сессии с правом `letopis.signals` (правило System). Системный сид выдаёт это право сервисам.
- Процесс без ключа — например, `connect({ token })` пользователя — работает «грубо». В режиме `tenant` он не узнаёт арендатора и сбрасывает класс во всех арендаторах, как в режиме `class`; в режиме `opaque` любой токен для него означает сброс всего кэша результатов. Реестр классов и пропуска прав он перечитывает не на каждый сигнал, а не чаще раза в 5 секунд — иначе каждая запись в базе, как и поддельный сигнал, заставляла бы его перечитывать реестр. Устаревших ответов кэша у такого процесса нет, только лишние запросы.
- То же ограничение частоты действует у всех процессов для `*` и незнакомых токенов: заливка канала поддельными сигналами не превращается в поток перечитываний реестра.

Что меняется у потребителей:
- **Триггеры** после оператора собирают пары «класс, арендатор» из переходных таблиц, а функция `signal()` строит из них нагрузку по режиму. Загрузчик и импорт перестают вызывать `pg_notify` напрямую и идут через ту же функцию.
- **Кэш** запоминает у ответа, кроме классов, токен арендатора запроса. Счётчики против гонки запроса и сигнала (`token()`/`set()`) ведутся по паре «класс, арендатор», а для сигналов System — по классу целиком.
- **Подписка** просыпается только от своих классов и своего арендатора, а без ключа — от любого сигнала, как сейчас. Потерь нет: сигнал только будит, события читаются из журнала.
- **Режим `none`** скрывает и время записи. Подписка опрашивает журнал (`pollMs`), кэш работает только по сроку или выключен — как сейчас за PgBouncer в режиме транзакций. Реестр классов раз в 5 секунд сверяет отпечаток классов (`class_stamp()`), пропуска прав живут по сроку (60 с), а ответы отозванной сессии уходят из кэша только по истечении срока.
- **Смена класса** сигналит и прежний, и новый класс. В 1.0.1 при смене класса без ключа сигнал шёл только по новому классу, и кэш прежнего класса в других процессах устаревал.
- **`Notifier`** возвращает в очередь сигналы, которые не удалось отправить; в 1.0.1 они терялись.

**Чего не скрыть.** Время и частота записи видны и без сигналов: представления `pg_stat_all_tables` и `pg_locks` открыты для PUBLIC. Режим `opaque` прячет «что», но не «когда». Детерминированный токен раскрывает частоту по псевдониму — на этом строятся частотные атаки на поисковое шифрование. Всё это записывается в «Ограничения». Настоящая защита от посторонних ролей — отдельная база для домена доверия: сигналы между базами не ходят.

**Совместимость с 1.0** не нужна (§1). Процессы 1.0 нагрузку режимов `tenant`, `opaque` и `none` не понимают, поэтому со схемой в этих режимах работают только процессы новой версии.

**Как это устроено у других.**

| Система | Точность | Как защищены метаданные |
|---|---|---|
| PostgreSQL LISTEN/NOTIFY | канал и нагрузка до 7999 байт; одинаковые сигналы транзакции склеиваются | никак: слушать может любая роль; при фиксации — блокировка кластера |
| Supabase Realtime | Postgres Changes — проверка RLS на каждого подписчика; Broadcast from Database — темы | права на темы — RLS таблицы `realtime.messages` |
| Hasura | мультиплексированный опрос; переменные сессии — параметры общего запроса | сигналов нет |
| Electric, PowerSync | формы и корзины, параметризованные сервером или JWT | изоляция на сервере синхронизации |
| Prisma Accelerate, Next.js, Fastly, Cloudflare | теги кэша | арендатор — граница пространства имён (сервис, зона, среда) |
| CipherSweet | «слепой индекс»: усечённый ключевой HMAC | усечение делает совпадение вероятностным |

Выводы:
1. `NOTIFY` — публичная, непостоянная и дорогая при фиксации подсказка. В нагрузке только токены, а права проверяются повторным чтением под RLS.
2. Нагрузка детерминирована, иначе пропадёт склейка.
3. Каналы не множатся по арендаторам.
4. Токен — ключевой HMAC, а не хэш с открытой солью.
5. На PostgreSQL 19 план не рассчитывает.

### 2.3. Режим первой заливки (п. 9)

**Зачем.** На точке А плана 1.0 `COPY` в копии таблиц без триггеров дал около 13,4 тысячи строк в секунду на миллионе строк, а прототип загрузчика (`bench/core-load.mjs`, без проверок данных) — около 10,8 тысячи: на 24 % медленнее. Потолок задают индексы GIN по `data` и `ends`, первичный ключ по uuid v5, который ложится в индекс вразброс, и генерируемый хэш. Ещё часть разницы даёт триггер BEFORE ROW на `entity`: из-за него `COPY` идёт построчно. При загрузке в пустую схему — импорт из 0.21, перенос из другой системы, засевка — индексы и триггеры во время загрузки не нужны: индексы быстрее построить один раз в конце, сортировкой, чем поддерживать на каждой строке.

**API.** `db.load(rows, { initial: true })`, `letopis load --initial`, `letopis import --initial`.

**Порядок** — всё в одной транзакции:
1. `lock table entity, log in access exclusive mode`. Блокировка берётся до проверки: строка, вставленная между проверкой и TRUNCATE, пропала бы молча. На время загрузки схема закрыта и для чтения, и для записи.
2. Проверка. Подключение должно быть администраторским, а в `entity` и `log` не должно быть строк, кроме строк системных классов — описаний классов, аккаунтов, членств, ресурсов, правил — и служебной записи `reset`. Иначе — `not_empty`, до любых изменений. С `commitEvery` режим несовместим: снятые индексы и TRUNCATE требуют одной транзакции.
3. Сохраняются в памяти процесса:
   - строки системных классов из `entity` и `log`, включая `seq` и `tx` журнала;
   - определения индексов, ограничений и всех триггеров `entity` из каталога (`pg_get_indexdef`, `pg_get_constraintdef`, `pg_get_triggerdef`) — так режим не дублирует `10-core.sql` и не разойдётся с ним;
   - режим включения каждого триггера (`pg_trigger.tgenabled`): `pg_get_triggerdef` его не передаёт, а триггеры `entity` включены в режиме `ENABLE ALWAYS`, чтобы работать и при `session_replication_role = replica`.
4. `truncate entity, log`. Затем удаляются вторичные индексы, первичный ключ, `log_id_rev` и все триггеры `entity`. Триггер BEFORE ROW нужно именно удалить: PostgreSQL выбирает построчный `COPY` по самому наличию такого триггера, не глядя ни на условие `WHEN`, ни на `DISABLE TRIGGER`. Триггеры после оператора тоже удаляются: их переходные таблицы на миллионе строк — лишняя память и запись.
5. Строки системных классов возвращаются оператором `insert … overriding system value` с прежними `seq` и `tx`: колонка `seq` журнала — `generated always`, и обычный `insert` явное значение в ней отклоняет.
6. `COPY … FREEZE` загружаемых строк. `FREEZE` разрешён, потому что таблицы опустошены в этой же транзакции. Сам `COPY` он не ускоряет, но ставит биты карты видимости: первый VACUUM не переписывает таблицу, а первое чтение не пишет hint bits. В PostgreSQL 18 контрольные суммы страниц включены по умолчанию, и запись hint bits попадает в WAL.
7. Индексы и ограничения строятся заново по сохранённым определениям: сначала первичный ключ и уникальные (дубликат обнаружит сортировка), затем GIN и B-tree. `set local maintenance_work_mem` и `max_parallel_maintenance_workers` — в пределах настроек сервера. PostgreSQL 18 строит GIN параллельно.
8. Триггеры возвращаются с прежним режимом включения (`alter table … enable always trigger …`).
9. Агрегаты классов (§2.4), если они есть в схеме, пересчитываются по загруженным строкам: их триггер во время загрузки был снят.
10. Обычный конец загрузки: запрос по целям вне загрузки (это строки системных классов), сигнал, `ANALYZE`. `ANALYZE` здесь обязателен: в PostgreSQL 18.0–18.5 параллельная сборка GIN могла оставить неверный `reltuples`.
11. Фиксация. Любая ошибка откатывает всё — и данные, и снятые индексы с триггерами: DDL в PostgreSQL транзакционен.

**Импорт.** `letopis import` вызывает загрузчик много раз — по арендаторам и группам классов. С `--initial` весь импорт идёт одной транзакцией: блокировка, TRUNCATE и снятие индексов делаются один раз в начале, а перестройка — один раз в конце. Иначе второй вызов загрузчика получил бы `not_empty`.

**Чего режим не делает.**
- Не пропускает WAL при обычном проде. WAL не пишется только при `wal_level = minimal`: тогда PostgreSQL сам не журналирует таблицу, опустошённую в этой транзакции. Обычный прод работает с `replica`, и режим рассчитан на выигрыш без пропуска WAL; `minimal` — бонус, о котором пишет README.
- Не переключает таблицы в `UNLOGGED` и обратно: `SET LOGGED` при `replica` переписывает и журналирует таблицу целиком.
- Не пишет из нескольких соединений. Параллельный `COPY` несовместим с `FREEZE` и одной транзакцией. В PostgreSQL 16 и новее без индексов он масштабируется, но это отдельный вариант — решение по замеру на точке А.
- Не использует двоичный формат `COPY`: для `jsonb` выигрыша нет.
- Почти не ускоряет режим истории (`withHistory`, импорт). Он пишет версии волнами `insert … returning hash`, потому что хэш следующей версии зависит от предыдущей, и выигрывает только от снятых индексов и триггеров.

**Цель** — в 3 раза быстрее обычного загрузчика на миллионе строк полигона salon без режима истории. Замер на точке А оценивает вклад триггеров, GIN, первичного ключа и `FREEZE` по отдельности; если `FREEZE` стоит больше, чем экономит, он убирается.

**Как это делают другие.**

| Инструмент | Порядок |
|---|---|
| `pg_restore` | pre-data (таблицы) → data (`COPY`) → post-data (индексы, ограничения, триггеры). `--jobs` распараллеливает. Сам делает `BEGIN; TRUNCATE; COPY; COMMIT`, чтобы при `minimal` пропустить WAL |
| pgloader | truncate, снятие индексов, отключение триггеров. Отключение, как сказано выше, построчный `COPY` не отменяет |
| pg_bulkload | прямая запись мимо буферов и WAL; нужен суперпользователь и своё восстановление после краха — для библиотеки не годится |
| timescaledb-parallel-copy | N соединений, пакеты по 5000 строк в отдельных транзакциях |

Замеры из рассылки PostgreSQL и блогов:
- перестройка индексов после загрузки — от 1,5 до 8 раз быстрее, в зависимости от схемы. Первичный ключ на миллионе строк: 4–6,7 с при вставке против 1,2–1,5 с, если строить его после;
- параллельная сборка GIN по `jsonb_path_ops` — около 1,2 раза;
- после `COPY FREEZE` первый VACUUM идёт примерно в 9 раз быстрее.

### 2.4. Производные представления (п. 5)

Под «производными представлениями» понимаются два разных механизма.
- **Агрегаты в базе** — синхронные, из текущего состояния. Нужны для сумм и счётчиков, которые обязаны совпадать с источником и для сырого SQL.
- **Проекторы** — асинхронные, из журнала. Нужны для сводок, денормализованных карточек и всего, что можно считать с отставанием.

Материализованные представления и расширение pg_ivm не подходят. Это дополнительные отношения, то есть нарушение принципа трёх таблиц. pg_ivm не работает с секционированными таблицами, его нет на AWS RDS, а у Neon он недоступен для новых установок.

**Агрегаты в базе.**

```ts
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0) }, {
  key: ['number'],
  aggregate: { balance: { sum: 'amount', of: 'Movement', via: 'Wallet' } },
})
```

Что делает база:
- Держит `balance` равным сумме `amount` живых строк `Movement`, чей конец `Wallet` указывает на этот кошелёк. Операции — `count` и `sum` по числовому полю. Условие `where` — JSON Schema над данными строки-источника.
- Пересчитывает приращением в отдельном триггере после оператора: по переходным таблицам, одним `update … set data = inc(…)` на каждый задетый объект за оператор, в порядке id. Правило `minimum: 0` проверяется над итогом и отклоняет операцию, которая увела бы баланс в минус.
- Этот триггер, в отличие от проверочных, срабатывает и для владельца (без условия `WHEN`). Поэтому один механизм учитывает всё: библиотеку, сырой SQL, каскад удаления, функции владельца (`move_row`, `restore`, удаление аккаунта) и загрузчик.
- Не даёт приложению писать агрегатное поле (`aggregate_field`). При создании объекта поле равно нулю.
- Пересчитывает поле целиком, когда меняется сама цель: `restore` кошелька берёт баланс не из надгробия, а из суммы живых операций; после `move_row` цели — тоже, чтобы приращения не применились дважды.
- Учитывает только строки того же арендатора, что и цель. Ссылка на строку System в агрегат не входит, иначе общий справочник считал бы данные всех арендаторов.
- Меняет цель от имени владельца. Это решение: чтобы изменить баланс операцией, достаточно права записи в `Movement`, право записи в кошелёк не нужно — как у счётчика `counter_cache` в Rails.

Добавить или изменить агрегат — ужесточение. Оно берёт исключительные блокировки семейства цели и семейств источников: иначе операция, зафиксированная во время пересчёта, потерялась бы. `db.rebuildAggregates(класс)` пересчитывает значения из текущих строк — для ремонта; версия пишется только там, где значение изменилось.

Цена — как у `inc` в 1.0: операции одного объекта идут друг за другом под блокировкой его строки, и каждая пишет версию цели. Строка-счётчик выстраивает писателей в очередь, поэтому для горячих счётчиков (тысячи записей в секунду на один объект) агрегат в базе не годится; для них нужен проектор со свёрткой пачкой. Делать ли агрегаты в 1.2, владелец решает на точке А (§6).

**Проекторы.**

```ts
const revenue = db.projector('daily-revenue', {
  from: ['Booking'],                 // классы-источники вместе с потомками
  into: ['DailyRevenue'],            // производные классы
  version: 1,                        // смена версии требует перестройки
  async handle(changes, out) {       // change: { id, class, tenant, op, rev, at, author, row, before? }
    for (const c of changes) out.upsert('DailyRevenue', { tenant: c.tenant, /* … */ })
  },
})
await revenue.run()          // догнать журнал и следовать за ним
await revenue.rebuild()      // перестроить с нуля
```

- **Это процесс администратора**, как загрузчик и `maintain`. Он работает на администраторском подключении, читает журнал всех арендаторов по курсору (без RLS) и записывает результаты тем же проверенным путём, что загрузчик: валидатор, концы, арендатор. Проектор — код приложения, которому доверяют, как миграциям.
- **Курсор** тот же, что у подписки: `(tx, seq)` ниже горизонта `pg_snapshot_xmin` вместе со снимком момента (как `~снимок` в курсоре подписки). Пачка и горизонт берутся одним оператором, без таймеров, пропускающих «дыры». Именно разные снимки и таймерные пропуски приводили к тихой потере событий в Marten до версии 9.16.1 (июль 2026 года).
- **Ровно один раз.**
  - Чекпоинт хранится в `secret` (вид `PROJECTOR`, идентификатор — имя проектора). Функции кредов этот вид не видят.
  - Он сдвигается условно, «курсор равен ожидаемому», в той же транзакции, что и запись результатов, — как `projection_versions` в Commanded и прогресс в Marten.
  - У проектора один писатель: транзакционная advisory-блокировка на каждую пачку, как у `maintain()`. Это работает и за PgBouncer.
- **Запись ограничена.**
  - `out.upsert` и `out.delete` пишут только в классы `into` и только в арендатора того изменения, которое обрабатывается.
  - Производные классы помечены `derivedBy: '<имя>'`. Приложение и сырой SQL их не пишут (ошибка `derived_class`).
  - Ссылаться на производные строки нельзя, поэтому у их удаления нет каскада.
  - Для производных классов рекомендуется `history: false`: иначе производные строки удваивают журнал, а проектор не должен читать собственные записи.
- **Изменение** — снимок новой версии (`row`), как событие подписки. Если проектор попросил `withBefore`, приходит и прошлая версия (`before`, по `(id, rev − 1)`). Служебные записи `purge`, `trim` и `reset` тоже приходят как изменения: проектор сам решает, что делать с производными строками стёртого объекта.
- **Порядок.** `(tx, seq)` — порядок первой записи транзакций, а не их фиксации. Для строк одного объекта проектор сравнивает `rev` и пропускает устаревшее, а для агрегатов по многим объектам берёт коммутативные операции — сумму или счётчик.
- **Перестройка** идёт с текущего состояния, а не с начала журнала: журнал прорежен политикой хранения и обрезан `purge`, и повтор с нуля дал бы не то.
  - Текущие строки источников читаются одним снимком — транзакцией `repeatable read`. Чекпоинт ставится на пару «горизонт этого снимка и сам снимок», а из хвоста журнала исключаются транзакции, видимые в снимке (`pg_visible_in_snapshot`). Иначе транзакции, зафиксированные между горизонтом и снимком, попали бы и в снимок, и в хвост — и сумма учла бы их дважды.
  - В атомарном варианте производные строки удаляются и строятся заново в одной транзакции, и до фиксации читатели видят прежние строки. Долгая транзакция держит горизонт и задерживает подписки всех процессов. Поэтому для больших проекций есть `rebuild({ chunked: true })`: перестройка пачками с состоянием `rebuilding`, и на это время читатели видят смесь старых и новых строк. Какой вариант брать по умолчанию — решается по замеру на точке Б.
- **Отставание** дольше яруса `all` политики хранения даёт `cursor_expired`, как у подписки. Опция `onExpired: 'rebuild'` перестраивает проекцию сама.

**Как это устроено у других.**

| Система | Синхронно | Асинхронно | Прогресс | Перестройка |
|---|---|---|---|---|
| Marten | inline, в той же транзакции | async-демон, high water mark | таблица прогресса, на арендатора | с нуля; новая версия проекции — новые таблицы |
| Kurrent | — | JS-проекции на лидере; движок V2 пишет чекпоинт и результат одной записью | поток чекпоинта | reset |

4. Перестройка идёт с текущего состояния плюс хвост журнала.
5. Дополнительные отношения противоречат принципу трёх таблиц.

### 2.5. Инструменты MCP (п. 2)

**Зачем.** Агент — Claude, Cursor или свой — получает доступ к данным letopis через инструменты MCP: узнать модель, прочитать данные цепочкой, посмотреть историю, а если разрешено — записать. Главное преимущество letopis перед MCP-серверами баз данных в том, что права проверяет сама база. Во всех разобранных провалах защита стояла вне базы:
- у Asana — ошибка в слое MCP открыла данные чужих организаций;
- в демонстрации на Supabase агент работал под `service_role`, который обходит RLS;
- у эталонного Postgres-сервера и у сервера AWS режим «только чтение» держался на разборе SQL и обходился оператором `COMMIT;`.

Поэтому слой MCP у letopis тонкий: каждый вызов идёт цепочкой под сессией пользователя.

**Поставка.**
- Подпуть `letopis/mcp` и команда `letopis mcp`.
- SDK — `@modelcontextprotocol/server` 2.x (Apache-2.0, Node ≥ 20, Zod ^4.2). Это необязательная peer-зависимость, как Zod для `letopis/model`: основная точка входа его не загружает.
- Целевая ревизия протокола — 2026-07-28: без состояния соединения, с `server/discover`. SDK обслуживает и прежнюю ревизию.
- Схемы инструментов задаются чистой JSON Schema (`fromJsonSchema`), без описания на Zod.
- `describe()` начинает отдавать условия `anyOf` и `oneOf` описания класса — сейчас их нет, а агенту они нужны.

**От чьего имени действует сервер.** Сервер MCP работает от имени одного пользователя и только с его правами.
- `letopis mcp` принимает только токен сессии пользователя (`--token` или `LETOPIS_TOKEN`), выпущенный приложением через `db.auth.sessionFor(пользователь, { ttl })`. Ключ сервиса командная строка не принимает: он даёт все права `auth.*` — имперсонацию любого видимого пользователя и выпуск сессий, — а лежал бы в окружении машины агента.
- `createMcpServer(db)` в приложении принимает сессию пользователя или фасад `db.as(пользователь)` — тогда ключ сервиса остаётся в процессе приложения, где он и так живёт. Подключение, которое обходит RLS, и корень сервиса без `as` отклоняются.
- Для stdio строку подключения и токен можно передать переменными окружения (`LETOPIS_DSN`, `LETOPIS_SCHEMA`, `LETOPIS_TOKEN`) — так их передают клиенты MCP.

**Инструменты** — немного и «по исходам», как советуют Anthropic и Phil Schmid (5–15 на сервер).

| Инструмент | Что делает | Аннотация |
|---|---|---|
| `letopis_model` | модель: классы, поля (JSON Schema), концы, ключи, алиасы; с `class` — подробно один класс | только чтение |
| `letopis_query` | чтение цепочкой, описанной в JSON: старт (класс и фильтр или id), шаги по связям и ролям, модификаторы (`asOf`, `withDeleted`, `sort`, `limit`, `after`), терминал (`rows`, `first`, `count`, `ids`, `sum`, `avg`, `min`, `max`, `countBy`) | только чтение |
| `letopis_history` | `versions`, `diff` или `blame` объекта | только чтение |
| `letopis_write` | `create`, `update`, `upsert`, `delete` — только при запуске с флагом `--write` | разрушительный |

Правила инструментов:
- **Без сырого SQL.** Цепочка из JSON собирается вызовами API библиотеки, без `eval`. Неизвестный класс или роль — ошибка с подсказкой похожих имён. Инструмента сырого SQL нет вообще.
- **Объём ответа.** Ответ — `structuredContent` и его текстовый дубль. По умолчанию не больше 100 строк и 50 КБ; дальше — курсор `after`. Курсор свой, потому что пагинация MCP есть только у списков. Claude Code переносит ответы больше 25 тысяч токенов в файл.
- **Данные — недоверенный ввод.** Всё, что пришло из базы, — данные строк, имена и описания классов, в том числе подсказки похожих имён в ошибках, — оборачивается в `<untrusted-data-…>` со случайным суффиксом и пояснением, что внутри не инструкции, как у Supabase и MongoDB. Это смягчение, а не защита.
- **Текст арендаторов не попадает в описания.** Метаданные классов (`meta`, названия, описания) пишут арендаторы. Поэтому в описания инструментов и в `instructions` сервера они не попадают — только в результаты, как данные. Иначе это канал «отравления инструментов». Описания инструментов — постоянный текст пакета.
- **Запись.**
  - `update` через MCP требует `rev`: агент сначала читает, поэтому потерянных обновлений нет.
  - `delete` без `confirm` возвращает превью. Само удаление требует подтверждения человека через elicitation — ответа пользователя в клиенте, привязанного к хэшу операции. Токен, который агент мог бы вернуть сам, подтверждением не считается. Если клиент не умеет elicitation, разрушительная операция не выполняется: в MongoDB и Supabase такой клиент получает выполнение без подтверждения, здесь — наоборот.
  - Каждая запись получает причину `mcp: <инструмент>` (§2.1), и `blame` показывает, что поле изменил агент.
- **Имена и схемы.** Имена инструментов — латиница, цифры и `_`: клиент Claude не принимает точки. Корень входной схемы — `type: object`, без `anyOf` и `oneOf`: Claude их разворачивает.

**HTTP.** Встроенного HTTP-сервера нет. `createMcpServer(db)` отдаёт сервер, который приложение подключает к своему HTTP-обработчику (`createMcpHandler` из SDK) со своей авторизацией OAuth 2.1, а токен запроса превращается в сессию letopis. Свой сервер авторизации в пакете (метаданные RFC 9728, проверка аудитории RFC 8707) дублировал бы то, что у приложения уже есть.

**Code mode** — когда агент пишет код против типизированного API, как в Cloudflare «Code Mode» или Anthropic «code execution with MCP», — в 1.2 не входит. Для него нужна песочница без сети, файловой системы и переменных окружения, а при четырёх инструментах выигрыш мал. Права и тогда проверяла бы база.

**Как это устроено у других.**

| Сервер | Запросы | Схема | Защита |
|---|---|---|---|
| Supabase | сырой SQL, `execute_sql` | инструмент `list_tables` | read-only роль, привязка к проекту, группы инструментов, обёртка `<untrusted-data-UUID>`, подтверждение разрушительного |
| Neon | `run_sql` | `describe_table_schema` | read-only по параметру или OAuth-scope |
| PlanetScale | раздельные чтение и запись | — | блокирует UPDATE и DELETE без WHERE, DDL — через подтверждение |
| MongoDB | инструменты коллекций | `collection-schema` | `readOnly`, `disabledTools`, подтверждение, до 100 документов и 16 МиБ |
| Google MCP Toolbox | параметризованный SQL из `tools.yaml` | — | параметры из claims токена |
| DBHub | `execute_sql`, `search_objects` | постепенное раскрытие | `max_rows`, таймаут |
| Convex | `runOneoffQuery` в песочнице, `run` | `tables` | прод по умолчанию закрыт |
| эталонный Postgres (в архиве) | `query` в транзакции READ ONLY | ресурсы схем | обходился `COMMIT;` |

Выводы:
1. Права проверяются только в базе, слой MCP тонкий.
2. Без сырого SQL и без ключа сервиса на машине агента.
3. По умолчанию — только чтение; запись — отдельной группой.
4. Всё, что пришло из базы, — недоверенный ввод.
5. Текст арендаторов не попадает в описания инструментов.
6. Без подтверждения человека разрушительная операция не выполняется.

### 2.6. Структура, режимы установки, совместимость

**Структура.** Обязательных структурных миграций нет: новое — виды строк `secret` (`PROJECTOR`), опции классов (`aggregate`, `derivedBy`) и функции, а функции накатываются при каждом `up()`. Если после этапа 1 владелец решит хранить у версий журнала список изменённых путей (§2.1), это будет ревизия движка 6 — миграция `lib/sql/migrate/0006-changed-paths.sql`. Механизм миграций есть с 1.0 (`up.ts:migrationFiles`); миграции идут до наката функций.

**Режим сигналов хранится в схеме.** В 1.0 опции `up()` — `allowReset`, политика истории — берутся из текущего вызова и подставляются в тексты функций, нигде не сохраняясь. Для режима сигналов так нельзя: обычный `up()` при старте приложения без опций вернул бы режим `class`, и имена классов снова стали бы видны. Поэтому:
- режим хранится в `meta` строки ключа `secret` с id System — там же, где курсор прореживания и метка политики по умолчанию;
- установщик читает его оттуда при каждом накате и подставляет в тексты функций;
- сменить режим можно только явной опцией `up({ signals })`; `reset({ all })` режим сохраняет: строку ключа заново создаёт `seed_system()`, и режим она берёт из подставленной константы.

**Описания классов.**
- Накат функций не пересчитывает `resolved` у старых строк `Class`. Новые опции (`aggregate`, `derivedBy`) появляются в `resolved` при правке класса, а код, читающий `resolved`, терпит их отсутствие.
- `class_change_safe` считает «безопасным» всё, чего не сравнивает. Поэтому любая правка `aggregate` и `derivedBy` в нём — ужесточение, с исключительной блокировкой и своей проверкой по правилам §2.4.
- Наследование: потомок получает `aggregate` и `derivedBy` предка; `aggregate` он может заменить своим, `derivedBy` — не менять.

**Зарезервированные имена.** Методы цепочки `diff` и `blame` и свойства корня `projector` и `rebuildAggregates` попадают в `RESERVED_CLASS_NAMES`. База отклоняет только связи с такими именами, а хаб с таким именем создать можно, но через цепочку он станет недостижим.

**Ревизия движка.** Проекторы отказываются работать на схеме, ревизия движка которой не равна их собственной.

## 3. Отличия от формулировок §13

| §13 плана 1.0 | В этом плане | Почему |
|---|---|---|
| `diff` и `blame` по журналу | плюс причина изменения в API | без причины `blame` отвечает только «кто и когда» |
| кэш с точностью до арендатора: сигнал с хэшем арендатора | режим `tenant`, токен — ключевой HMAC | без ключа хэш id арендатора сопоставит любой, кто знает id |
| сигналы без имени класса; кэш сбрасывается целиком | режим `opaque` сохраняет точность через токены; полный отказ от сигналов — режим `none` | точность и приватность одновременно |
| первая заливка: снятие индексов и перестройка | плюс удаление триггеров, TRUNCATE и `COPY FREEZE`, определения индексов и режимы триггеров из каталога | триггер BEFORE ROW сам по себе делает `COPY` построчным; `FREEZE` снимает последующий VACUUM |
| производные представления из журнала | проекторы из журнала плюс агрегаты в базе из текущего состояния | синхронная целостность для сырого SQL — отдельная задача от асинхронных сводок |
| инструменты MCP поверх `describe()` | плюс чтение цепочкой из JSON, история, запись по флагу; без сырого SQL, без ключа сервиса в командной строке и без встроенного HTTP-сервера | одного описания модели агенту мало; права уже проверяет база |

### Этап 0. Подготовка

1. Версия `1.1.0-alpha.0` в `dev`, верхняя запись CHANGELOG. Выпуска альфы нет; номер `1.1.0` выставляется перед выпуском.

4. Бенч против 1.0.1 (`bench/vs-101.bench.mjs`): запись, чтение, загрузка, `maintain` на полигоне salon. Опорный прогон — до изменений; тем же бенчем меряются точки А и Б.

### Этап 1. `diff` и `blame`

1. `75-history.sql`: `jsonb_changes`, `version_changes`, `diff_versions`, `blame` — `security invoker`, тела в стандартном синтаксисе SQL, где получается.

4. Зарезервированные имена `diff` и `blame`.
5. Замер `blame` по 1000 версиям; решение владельца о колонке изменённых путей — до начала этапа 2.

### Этап 2. Сигналы

1. Режим сигналов в `meta` строки ключа и опция `up({ signals })`; `reset({ all })` режим сохраняет.
2. `signal()` по парам «класс, арендатор» с нагрузкой по режиму и `signal_raw()` для сессий и сброса; триггеры, функции владельца, загрузчик и импорт — через них. Триггер правки сигналит и прежний класс при смене класса.
3. `signal_key()` и право `letopis.signals` в сиде.
4. Кэш: токены, счётчики по паре, грубый режим без ключа с ограничением частоты перечитывания реестра; подписка: фильтр по токенам; режим `none` с опросом журнала и сверкой отпечатка классов; `Notifier` повторяет неотправленное.
5. Предупреждение `up()` о PostgreSQL ниже 18.2: до 18.2 сервер мог усечь CLOG, который ещё нужен непрочитанным сигналам.

### Этап 3. Первая заливка

3. Замер на миллионе строк salon с раздельной оценкой триггеров, GIN, первичного ключа и `FREEZE` (точка А).

### 7.9. Проверка понятности

Агент, видевший только README, решает задачи:
1. найти, кто и почему изменил цену заказа;
2. настроить установку без имён классов в сигналах;

## 10. Порядок и правила работы

```
0 ─► 1 ─► (решение о колонке) ─► 2 ─► 3 ─► КТ А (ревью №1, выпуск 1.1.0) ─► 4 ─► 5 ─► 6 ─► КТ Б (выпуск 1.2.0)
```

- Каждый этап начинается только по команде владельца; на контрольных точках работа останавливается до его решения.
- Этапы идут последовательно: соседние этапы правят одни и те же файлы (этапы 1 и 2 — `tx.ts`; этапы 2, 3 и 4 — `60-write.sql`, `load.ts`). Параллельно можно готовить только тест-атаки и фикстуры следующего этапа.
- Внутри этапа сначала пишутся тест-атаки и гонки, затем код.
- Результат этапа фиксируется коммитами в `dev`. Пуш и выпуск — по команде владельца, по порядку деплоя: `dev` → PR → merge на GitHub → тег → Release.
- В одном коммите с кодом обновляются карточка модуля, трасса, раздел «Тесты» обоих README и контракт API.
- Проектирование, код и ревью выполняет основная модель или субагент без смены модели; поиск по коду — субагент `atlas-scout`.
