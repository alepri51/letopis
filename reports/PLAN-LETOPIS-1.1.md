**Коротко.** Восемь возможностей реализуются за девять этапов и выходят двумя выпусками.

Выпуск **1.1** — то, что меняет ядро немного и окупается сразу:
- `diff` и `blame` по журналу;
- запрет пересечения интервалов;
- сигналы с точностью до арендатора и режимы без имён классов;
- режим первой заливки.

Выпуск **1.2** — то, что требует отдельного ревью безопасности:
- хранилище персональных данных с криптошреддингом;
- производные представления: проекторы из журнала и агрегаты в базе;
- инструменты MCP.

Принципы 1.0 не меняются: три таблицы, целостность держит база (в том числе для сырого SQL), функции владельца без динамического SQL, прежняя формула хэша версии. Структуру таблиц меняют две миграции, по одной на выпуск:
- ревизия движка 6 (1.1) — две служебные колонки интервалов и одно ограничение исключения на `entity`;
- ревизия 7 (1.2) — индексы `secret` для хранилища ПД.

## Словарь

| Слово | Что значит в этом плане |
|---|---|
| ограничение исключения | правило PostgreSQL `EXCLUDE`: никакие две строки не совпадают по заданным операторам. Для интервалов — «тот же ресурс и пересекающееся время» |
| диапазон, `tstzrange` | тип PostgreSQL «интервал времени с поясом». `[a, b)` — начало включено, конец нет, поэтому соседние брони не пересекаются |
| btree_gist | расширение из поставки PostgreSQL: даёт индексу GiST сравнение на равенство для uuid и текста. Помечено доверенным и ставится без суперпользователя |
| служебные колонки интервала | `span` и `span_key` в `entity`: интервал строки и ключ её ресурса. Их заполняет триггер из описания класса |
| триггер-сторож | триггер после оператора на `entity`, который срабатывает и для владельца. Отклоняет строки, записанные мимо правил ревизии 6 — например, загрузчиком 1.0 |
| diff | различия между двумя версиями объекта: какие пути изменились, что было и что стало |
| blame | для каждого поля версии — какая версия, кто, когда и почему изменила его последней |
| путь | адрес поля в строке — массив сегментов: `["data", "price", "amount"]`, `["links", "Staff"]` |
| причина изменения | текст, который сохраняется в колонке журнала `reason`, например «отмена по просьбе клиента» |
| токен сигнала | первые 96 бит HMAC от имени класса или id арендатора на секретном ключе установки. Без ключа по токену не узнать, что за ним стоит |
| режим установки | настройка, которая действует на всю схему: режим сигналов, уровень хранилища ПД. Хранится в самой схеме |
| первая заливка | загрузка в схему без данных: индексы и триггеры снимаются на время загрузки и строятся заново в конце |
| `COPY FREEZE` | вариант `COPY`, при котором строки сразу пишутся «замороженными», и последующий VACUUM их не переписывает |
| персональные данные (ПД) | поля, помеченные в классе как персональные. Их значения лежат не в `data`, а в хранилище ПД |
| субъект | человек, к которому относятся ПД строки: сама строка (клиент) или объект на её конце (клиент брони) |
| хранилище ПД | строки `secret` вида `PD`, по одной на значение персонального поля. Журнал их не содержит, и они удаляются физически |
| обязательство | `{"$pd": "<64 hex>"}` в `data` вместо значения ПД: sha256 от случайной соли и значения. Пока соль и значение лежат в хранилище, по обязательству проверяется подлинность значения. Когда их удалили, обязательство ни с чем не связать |
| криптошреддинг | стирание шифрованием: значение хранится зашифрованным ключом субъекта, и удаление ключа делает нечитаемыми все копии шифротекста, включая бэкапы |
| ключ-обёртка (KEK) | ключ приложения, который хранится вне базы (переменная окружения, KMS) и шифрует ключи субъектов |
| агрегат класса | поле, которое база сама держит равным сумме или числу строк другого класса. Пример: баланс кошелька — сумма операций |
| проектор | процесс, который читает журнал по курсору и строит из изменений строки производных классов |
| производный класс | класс, строки которого пишет только проектор, а приложение их только читает |
| чекпоинт проектора | курсор журнала вместе со снимком, до которого проектор обработал изменения. Хранится в `secret` и сдвигается в той же транзакции, что и запись результатов |
| MCP | Model Context Protocol — открытый протокол, по которому агент на языковой модели вызывает инструменты внешней системы |
| инструмент MCP | функция, которую агент вызывает по имени с аргументами, описанными JSON Schema |
| ревизия движка | номер структуры таблиц схемы (`ddl_revision`). В 1.0 — ревизия 5, план поднимает её до 6, а затем до 7 |

### Что остаётся неизменным

- Ровно три таблицы. Новое — это колонки, индексы, виды строк `secret` и классы.
- Целостность держит база, и сырой SQL проходит те же проверки. Всё, что пишет мимо триггеров (функции владельца, загрузчик, проектор), проверяет само, и это закрыто тестами.
- Функции владельца — `security definer`, с фиксированным `search_path`, без динамического SQL. Новая функция владельца получает негативный тест (`roles` №4).
- Формула хэша версии и схема `v2` прежние. Служебные колонки интервалов в хэш не входят: они вычисляются из данных и описания класса.
- PostgreSQL 18 и новее. Рантайм-зависимость одна — `postgres`. Новые зависимости — только необязательные peer (SDK MCP).
- Обратная совместимость: код, написанный под 1.0, без правок работает на 1.1 и 1.2.

### Критерии готовности

1. Каждая возможность реализована по §2, её тест-план (§7) проходит в CI на `postgres:18`.
2. Миграции проверены на схемах с данными: 5 → 6 — на схеме 1.0.1, 6 → 7 — на схеме 1.1. После `up({ upgrade: true })` проверка `verify({ data: true })` чиста, процессы предыдущей и новой версии работают вместе — и читатели, и писатели.
3. Замеры сняты и приняты владельцем на контрольных точках (§6): цена ограничения интервалов на запись, цена режимов сигналов, ускорение первой заливки, цена хранилища ПД, агрегатов и проекторов.
4. Проведены три ревью безопасности: на точке А (интервалы, сигналы, первая заливка), после этапа 5 (ПД) и перед выпуском 1.2 (MCP, проекторы, итог). Каждая находка закрыта тестом.
5. Документация соответствует коду: README и шпаргалка (обе версии), `llms.txt`, CHANGELOG, контракт API, карта atlas. `check-docs` проходит. Агент, видевший только README, решает новые задачи (§7.11).

## 2. Главные решения

### 2.1. `diff` и `blame` (п. 4)

**Зачем.** `versions()` в 1.0 отдаёт полные снимки версий, а что именно изменилось, приложение вычисляет само. `diff` отвечает на вопрос «что изменилось между двумя версиями или моментами», `blame` — «кто, когда и почему последним менял каждое поле».

**API.**

```ts
await t.Order(id).diff()                          // предыдущая версия → текущая
await t.Order(id).diff({ from: 3, to: 7 })        // по номерам версий
await t.Order(id).diff({ from: '2026-10-01' })    // состояние на момент → текущее
await t.Order(id).blame()                         // каждое поле текущей версии
await t.Order(id).blame({ at: '2026-10-01' })     // каждое поле версии на момент
```

Результат `diff` — по одному элементу на объект шага:

```ts
{ id, class,
  from: { rev, at } | null,
  to: { rev, at, deleted? } | null,
  changes: [
    { path: ['data', 'price', 'amount'], kind: 'changed', before: 100, after: 120 },
    { path: ['links', 'Services'], kind: 'added', after: '<id>' },
  ] }
```

Как сравниваются разделы строки:
- `kind` — `added`, `removed` или `changed`; `before` и `after` — значения JSON. У `added` нет `before`, у `removed` — `after`.
- Путь — массив сегментов, первый из них — раздел строки: `data`, `links`, `tags`, `owner`, `class`. Строка с точками не годится: точки и цифры в именах ключей делают её неоднозначной. С этим столкнулся MongoDB и в 6.1 добавил `disambiguatedPaths`.
- `data`: объекты сравниваются по ключам рекурсивно, массивы и скаляры — целиком. Так же сливает данные `merge` (массив заменяется целиком) и так же поступают аудит-системы (PaperTrail, django-simple-history). Поэлементное сравнение массивов (LCS, как в jsondiffpatch) по умолчанию не делается: его результат неоднозначен и неудобен агенту.
- Одиночный конец — `changed` со старым и новым id. Множественный конец — множество: `added` и `removed` по каждому id, как кардинальность many в Datomic и списки `set` в Kubernetes. Теги — тоже множество.
- Запись того же значения изменением не считается, как в Datomic. Пустая правка в letopis версии и так не пишет.
- Поле ПД (§2.5) сравнивается по обязательству, а в результате приходит открытое значение, если оно не стёрто. Стёртое значение помечается `erased: true` без самого значения.

Какие версии сравниваются:
- `from` и `to` — номер версии или момент. Момент сводится к версии, действовавшей в него, по правилу среза `asOf`: последняя версия с `at ≤ T`, не надгробие.
- Если объекта на момент `from` не было, все его пути — `added`. Если на момент `to` объект удалён, ставится `to.deleted: true`, а изменения полей не перечисляются.
- `follow: true` — сравнение через смену id при `rekey` и `reclass` (по колонке `moved`), как в `versions({ follow: true })`.

Результат `blame` — тоже по объекту шага:

```ts
{ id, class, rev, complete: true,
  fields: [{ path: ['data', 'status'], rev: 12, at, author, agent, op, reason, exact: true }, …] }
```

Как считается:
- Для каждого листа версии (текущей или версии на момент `at`) находится последняя версия, где значение по этому пути отличалось от предыдущей. Лист — это скаляр, массив, роль одиночного конца, каждый id множественного конца, тег.
- Автор, агент, вид операции и причина принадлежат версии, а не полю. Так же устроены транзакции-сущности Datomic, ревизии Envers и `transaction_log` в pgMemento. Поэтому `blame` — это соединение «путь → версия».
- `exact: false` ставится, если до найденной версии история неполная: стёрта обрезкой (`trim`), прорежена политикой хранения или часть версий не видна актору. Настоящее изменение тогда могло быть раньше. `complete: true` значит, что у объекта таких пропусков нет. В git ту же роль играют пометки `?` и `*` при `--ignore-rev`.
- Версии видов `reclass` и `rekey` поля себе не «присваивают»: значения при них переносятся, а не меняются. Это как `--ignore-rev` для массовой правки форматирования.
- Удалённых полей в `blame` нет — их нет в версии. Где и кем поле удалено, показывает `diff`.

**Причина изменения.** В 1.0 колонку `reason` журнала заполняет только сырой SQL через настройку `letopis.reason`. В библиотеке способа её задать нет: `TxContext.reason` нигде не присваивается. Без причины `blame` отвечает только «кто и когда». Поэтому этап добавляет:
- опцию `reason` глаголам записи: `update(patch, { rev, reason })`, `create(data, { reason })`, `upsert(data, { reason })`, `delete({ confirm, reason })` и прочим;
- `db.begin({ reason })` и `db.batch(name, { reason })` — причину для всех операций блока.

Причина ставится настройкой `letopis.reason` перед оператором глагола, поэтому у разных глаголов одного плана или батча могут быть разные причины.

**Где считается.** В базе:
- функция `jsonb_changes(a, b)` — чистая, IMMUTABLE, обходит объекты по ключам;
- `version_changes(…)` сравнивает разделы строки;
- `diff_versions(id, from, to)` и `blame(id, rev, limit)` читают журнал с правами вызывающего (`security invoker`). Поэтому на них действует политика RLS журнала, и чужие или скрытые версии в расчёт не попадают.

Сырой SQL получает то же самое: `select * from "v2.shop".blame('<id>')`. Библиотека находит id шага и вызывает эти функции одним запросом на пачку объектов.

**Права.** История — это чтение. Актор видит те версии, которые разрешены ему текущими правами (политика `log_select`), как в Kinto, Directus и Databricks. Невидимая версия выпадает из расчёта, а соседние с пропуском результаты помечаются `exact: false`. Полевых прав в letopis нет, поэтому маскировать отдельные пути, как django-auditlog или Veeva, не нужно.

**Цена.** `blame` по снимкам стоит O(число версий × размер строки). По умолчанию просматривается не больше 1000 последних версий (`limit`), дальше ставится `complete: false`. Можно хранить у каждой версии список изменённых путей, как флаги `_MOD` в Envers или дельту в pgMemento. Но это новая колонка журнала и работа для загрузчика, поэтому замер делается в конце этапа 1, а решение владелец принимает до начала этапа 2: если `blame` по 1000 версиям дольше 100 мс, колонка входит в ревизию 6.

| git blame | последняя ревизия, менявшая строку; `--ignore-rev` | построчно; удалённые строки не показываются | автор коммита |
| TerminusDB | патч с проверкой старого значения (`SwapValue`) | дерево операций | — |
| Datomic | история фактов, `as-of`, `since` | `[e a v tx added]`; равное значение не записывается | транзакция — сущность с аннотациями |
| SQL Server, MariaDB, Oracle | временные таблицы, `VERSIONS BETWEEN` | версии строк; два момента — соединение двух `AS OF` | у Oracle — отдельным запросом к `FLASHBACK_TRANSACTION_QUERY` |
| Snowflake, BigQuery, Delta Lake | `CHANGES`, Change Data Feed | события изменений в окне хранения (у BigQuery — сутки) | — |
| PaperTrail, Audited, django-simple-history | `changeset`, `diff_against` | «поле → [было, стало]» | пользователь версии |
| Hibernate Envers | `withModifiedFlag` — «кто менял поле X» | флаг на свойство в каждой ревизии | ревизионная сущность |
| pgMemento | `row_log` хранит только изменённые колонки | `old_data` и `new_data` в jsonb | `transaction_log` |
| Kubernetes | `managedFields` — кто владеет каким путём | дерево путей `f:`, `k:`, `v:` | менеджер поля |

Выводы:
1. Нужны две поверхности, как у Dolt. Пошаговая история уже есть (`versions()`), к ней добавляются суммарный `diff(a, b)` и `blame`.
2. Плоский список «путь → было/стало» с заголовком версии удобнее патч-форматов. В RFC 6902 у `replace` и `remove` нет старого значения, в RFC 7396 нельзя записать `null`, а jsondiffpatch кодирует операции «магическими числами».
3. Ссылки сравниваются как множества, массивы данных — целиком.
4. Автор и причина принадлежат версии.
5. Права — текущие права читателя; при неясности результат закрывается.

### 2.2. Запрет пересечения интервалов (п. 1)

**Зачем.** Нужно правило класса «две строки одного ресурса не занимают пересекающееся время» — например, две брони одного мастера. В 1.0 его держит приложение через `forUpdate()` или `lock()` в явной транзакции, а сырой SQL и забывчивый код его нарушают. В 1.1 правило держит база — ограничением исключения PostgreSQL, как `EXCLUDE` в Django, Rails и Ecto.

**Описание в модели.**

```ts
const Booking = link('Booking', {
  Staff: one('Staff'),
  Client: one('Client'),
  start: z.iso.datetime({ offset: true }),
  end: z.iso.datetime({ offset: true }),
  status: z.enum(['booked', 'done', 'cancelled']).default('booked'),
}, {
  noOverlap: {
    by: ['Staff'],                                                   // чей ресурс
    range: ['start', 'end'],                                         // конец не включается
    when: { properties: { status: { enum: ['booked', 'done'] } } },  // кто занимает время
    group: 'staff-time',                                             // общее время классов
  },
})
```

- `range` — два обязательных поля формата `date-time` (с поясом) или оба формата `date`. Интервал полуоткрытый, `[начало, конец)`: бронь до 11:00 и бронь с 11:00 не пересекаются. Начало должно быть строго раньше конца, иначе `invalid_data`. Пустой интервал PostgreSQL не считает пересекающимся ни с чем, и без этой проверки через него правило обходилось бы.
- `by` — обязательные строковые поля и обязательные одиночные концы, как у ключа. Пустой `by` означает один ресурс на группу в арендаторе — например, единственную переговорную.
- `when` — условие на данные в виде JSON Schema того же подмножества, что у полей. Строка занимает время, только если её данные под него подходят: отменённая бронь время освобождает.
- `group` — общее время нескольких классов: бронь и выходной мастера с одной группой и одинаковым `by` тоже не пересекаются. По умолчанию группа — имя класса, объявившего правило, поэтому потомки, унаследовав правило, делят время с предком.
- У класса одно такое правило. Две независимые занятости одной строки (мастер и кабинет) выражаются двумя классами-связями, по одному на ресурс. Почему так — ниже, в части «Чего правило не даёт».

**Как устроено.**

У `entity` появляются две служебные колонки: `span tstzrange` и `span_key uuid`. Их вычисляет функция `span_of()` по описанию класса:
- `span` — интервал строки;
- `span_key` — v5 в пространстве арендатора от группы и значений `by`: `uuid_v5(арендатор, '["#span", "<группа>", "<значение 1>", …]')`.

У строк без правила и у строк, которые не подходят под `when`, обе колонки пустые.

Служебные колонки пересчитываются везде, где меняется строка:
- в триггерах вставки и правки;
- в функциях владельца, которые пишут строки сами: `move_row` (`rekey`, `reclass` с ключом), `sys_update` (через него идут перевод ссылок при `rekey` цели и смена класса без ключа), `restore`, пересчёт при эволюции класса;
- в загрузчике.

`move_row` вставляет строку с новым id раньше, чем удаляет старую. Если группа и значения `by` не изменились, обе строки получили бы одинаковый `span_key` и пересекающийся интервал, и `rekey` брони упал бы на конфликте с самой собой. Поэтому `move_row` сначала обнуляет служебные колонки старой строки. `rekey` мастера переводит ссылки броней через `sys_update`, и тот пересчитывает их `span_key` — иначе правило продолжало бы сравнивать брони по старому id мастера.

На всю таблицу ставится одно ограничение:

```sql
alter table entity add constraint entity_span_excl
  exclude using gist (span_key with =, span with &&) where (span_key is not null);
```

- Для него нужен btree_gist: без расширения у GiST нет равенства для uuid.
- Арендатор в ограничение отдельно не входит. `span_key` вычисляется в пространстве арендатора, поэтому строки разных арендаторов никогда не совпадают и друг друга не ждут.

Почему не своё ограничение на каждый класс (`… where (class = 'Booking')`), как обычно делают в Django и Rails:
1. Выражения ограничения обязаны быть IMMUTABLE, а разбор текста во время (`text::timestamptz`) помечен в PostgreSQL как STABLE — он зависит от `TimeZone` и `DateStyle`. Понадобилась бы IMMUTABLE-обёртка, корректность которой держится только на проверке формата. Служебные колонки заполняет триггер, а ему STABLE-функции разрешены.
2. PostgreSQL на каждом операторе открывает все индексы таблицы, а на каждой вставленной строке вычисляет предикат каждого частичного индекса. N классов с правилом — это N предикатов на каждую строку всей `entity`.
3. Создание ограничения — это DDL, который берёт `ACCESS EXCLUSIVE` на всю таблицу и делает второй проход по ней. Делать это при каждом определении класса значило бы останавливать запись, а функции владельца пришлось бы выполнять динамический SQL.

`PRIMARY KEY … WITHOUT OVERLAPS` из PostgreSQL 18 не подходит: он принимает только имена колонок без условия `WHERE` и не может быть целью `ON CONFLICT`.

Другие свойства схемы:
- Строки без правила в индекс не попадают, их вставка платит только проверку `span_key is not null`. Правка `data` и `links` и сейчас не идёт по пути HOT — у этих колонок есть индексы GIN, — так что новые колонки этого не ухудшают.
- Время разбирается однозначно. Формат `date-time` в letopis требует смещение пояса, поэтому результат не зависит от настроек сеанса. Даты (`date`) переводятся в интервал между полуночами UTC — для проверки пересечений этого достаточно.
- Служебные колонки производны от данных и описания класса, поэтому в хэш версии и в журнал они не входят, и формула хэша прежняя. `verify({ data: true })` пересчитывает их и сверяет.

**Конкурентность.** PostgreSQL проверяет ограничение исключения отдельным просмотром индекса «грязным» снимком. Если пересекающуюся строку вставляет незавершённая транзакция, вторая ждёт её: первая зафиксировалась — вторая получает отказ, откатилась — вторая проходит. Это работает на любом уровне изоляции и на любом пути записи — для библиотеки, сырого SQL, функций владельца и загрузчика — без блокировок в приложении. Две встречные вставки могут дождаться друг друга; тогда PostgreSQL снимает одну из них с `40P01`, библиотека повторяет её план, и повтор получает `overlap`: время уже заняла вторая транзакция.

**Ошибки.**
- Нарушение — это SQLSTATE `23P01`. Библиотека переводит его в код `overlap` и называет пересекающиеся строки, которые актор видит. Если среди пересекающихся есть невидимые, ставится пометка `hidden: true`, без их числа. Сырой SQL получает `23P01` как есть.
- Утечка через текст ошибки. Если на вызывающую роль не действует RLS, PostgreSQL кладёт в DETAIL значения чужой строки: её `span_key` и интервал. На приложение RLS действует, и DETAIL пуст. Но функции владельца (`restore`, `reclass`, `rekey`, пересчёт при эволюции класса) выполняются от владельца, на которого RLS не действует, и их ошибка дошла бы до приложения со временем чужой брони. Поэтому эти функции перехватывают `exclusion_violation` и бросают `overlap` сами, без значений. Это закрепляет тест-атака.
- `upsert` (`on conflict (id) do update`) нарушение не подавляет: цель конфликта — первичный ключ, а ограничение исключения проверяется как обычно.

**Эволюция класса.** Добавить правило или изменить `by`, `range`, `when` или `group` — ужесточение: под исключительной блокировкой семейства база пересчитывает служебные колонки всех строк семейства, и пересечения дают `tightening_conflict` со списком строк. Снять правило безопасно — колонки обнуляются. Эти обновления версий не пишут: служебных колонок нет в снимке версии. Правила совместимости описаний классов — §2.8.

**Чтение по интервалу.** Модификатор `during(от, до)` находит строки, которые занимают время в заданном интервале:

```ts
await t.Staff(id).Booking().during('2026-10-10T09:00Z', '2026-10-10T18:00Z').rows()
```

- Поиск идёт по служебному интервалу через `find_ids()` и индекс GiST, как поиск по `data`: под RLS операторы диапазонов индекс не используют — по той же причине, что и `@>`.
- Поэтому `during` находит только строки, которые занимают время: отменённые брони (вне `when`) он не видит. Для них есть обычный фильтр по полям `range`.
- Служебного интервала нет в журнале, поэтому `during` вместе с `asOf` — `invalid_query`.

**Загрузчик** вычисляет служебные колонки сам, тем же алгоритмом на TypeScript, и передаёт их в `COPY`, а ограничение проверяет вставку. Совпадение двух реализаций закрепляет дифференциальный тест. Защита от загрузчика 1.0, который о новых колонках не знает, описана в §2.8.

**Чего правило не даёт.**
- Одно правило на класс. У GiST одна запись индекса на строку и ограничение, поэтому вторая занятость одной строки потребовала бы второй пары колонок и второго ограничения. Это ограничение 1.1; вторая пара добавляется миграцией, если понадобится.
- Повторяющиеся брони («каждый вторник») — это строки на каждое занятие. Мультидиапазон в одной строке не подходит: PostgreSQL склеивает его части, и самопересечение внутри строки не ловится.
- Ошибка раскрывает, что время занято, так же как «уже существует» в 1.0 раскрывает занятость ключа.

**Требования к установке.**
- btree_gist входит в поставку PostgreSQL, помечен доверенным с версии 13 и ставится без суперпользователя (нужно право CREATE на базу). Версия 1.8 есть на AWS RDS, Google Cloud SQL, Azure Flexible Server и Neon; на Azure его сначала разрешают в `azure.extensions`. Установщик ставит btree_gist так же, как pgcrypto.
- Если расширения нет и поставить его нельзя (Azure без разрешения, PGlite без расширения), установка проходит без ограничения, а описание класса с `noOverlap` отклоняется с понятной ошибкой. Молча не действующего правила не бывает.

**Как это устроено у других.**

| Система | Как | Оговорки |
|---|---|---|
| PostgreSQL `EXCLUDE` | индекс GiST, оператор `&&`, частичность `WHERE`, `DEFERRABLE` | выражения только IMMUTABLE; добавление — `ACCESS EXCLUSIVE`, без `NOT VALID` |
| PostgreSQL 18 `WITHOUT OVERLAPS` | PK или UNIQUE по колонке-диапазону; внутри — то же ограничение исключения | только имена колонок, без `WHERE`; пустые диапазоны запрещены |
| Django | `ExclusionConstraint` с 3.0, `condition`, `deferrable` | нужен btree_gist |
| Rails | `add_exclusion_constraint` с 7.1 | — |
| Ecto | `exclusion_constraint` с 2.0 | — |
| Prisma | в схеме и миграциях нет | только сырым SQL |
| MariaDB | `UNIQUE (…, период WITHOUT OVERLAPS)` с 10.5 | — |
| Oracle | `CREATE ASSERTION` в 26ai | — |
| SQL Server, MySQL | декларативного аналога нет | триггеры и блокировки |
| CockroachDB, YugabyteDB | `EXCLUDE` не поддерживается | — |

Выводы:
1. Из встроенных средств PostgreSQL подходит только `EXCLUDE`.
2. Одно общее ограничение по служебным колонкам лучше частичного ограничения на каждый класс.
3. DETAIL безопасен, только когда на писателя действует RLS, поэтому функции владельца переводят ошибку сами.
4. `23P01` значит «занято», и повтор не нужен; `40P01` повторяется.
5. Пустой интервал отвергает валидатор.

### 2.3. Сигналы: точность до арендатора и режимы без имён классов (п. 7 и п. 8)

**Как в 1.0.**
- Каждая запись посылает `NOTIFY` в канал схемы с именем изменённого класса. Отзыв сессии посылает `session:<16 hex>`, сброс — `*`.
- Транзакции библиотеки не шлют сигнал сами: функция `signal()` копит имена классов в настройке транзакции `letopis.changed`, библиотека читает её перед фиксацией, и после фиксации `Notifier` отправляет имена одним оператором. Сырой SQL шлёт сигнал при фиксации. Загрузчик и импорт вызывают `pg_notify` напрямую.
- По сигналу класса кэш результатов сбрасывает ответы, читавшие этот класс, во всех арендаторах сразу, а подписка `watch` просыпается. Сигнал `*` вдобавок перечитывает реестр классов и сбрасывает пропуска прав.
- Сигналы видит любая роль, которая может подключиться к базе. Прав на каналы в PostgreSQL нет, и запретить `LISTEN` нельзя ни правами, ни RLS, ни `pg_hba.conf`. По именам классов посторонний видит, когда и во что пишут.

**Режимы.** Режим выбирается опцией `up({ signals })` и хранится в схеме (§2.8): повторный `up()` без опции его не меняет.

| Режим | Нагрузка сигнала | Кэш | Что видит посторонний |
|---|---|---|---|
| `class` (по умолчанию, как в 1.0) | `Booking` | сброс класса во всех арендаторах | имена классов и время записи |
| `tenant` | `Booking@<токен арендатора>` | сброс класса только в этом арендаторе | имена классов, время, псевдонимы арендаторов |
| `opaque` | `<токен класса>@<токен арендатора>` | как у `tenant` | время записи и частоту по псевдонимам |
| `none` | сигналов нет | только по сроку (`ttlOnly`) или выключен; подписка опрашивает журнал | ничего, кроме нагрузки на базу |

Токены и нагрузка:
- **Токен** — первые 96 бит HMAC-SHA256 от «назначение ‖ значение» на секретном ключе установки, 24 строчных шестнадцатеричных символа. Ключ выводится из ключа строки `secret` с id System (`hmac('letopis:signals', ключ)`), поэтому новая строка не нужна, а `reset({ all })` вместе с ключом меняет и токены. Открытая соль не годится: имён классов мало, и их подобрали бы по словарю.
- **Нагрузка детерминирована** — без счётчиков и времени. PostgreSQL склеивает одинаковые сигналы транзакции, поэтому транзакция, записавшая тысячу броней одного арендатора, посылает один сигнал. Транзакция, задевшая N пар «класс, арендатор», посылает N сигналов.
- **Каналы не множатся по арендаторам и классам.** В PostgreSQL 18 любой `NOTIFY` будит всех слушателей базы, а поиск канала — линейный перебор. Избирательное будение появится только в PostgreSQL 19, и там остаётся общая для кластера блокировка при фиксации транзакции с `NOTIFY`. В режимах `tenant` и `opaque` каналов два: точный `<схема>:2` и прежний канал схемы — на время перехода с 1.0 (ниже).

Что сбрасывается:
- **Строки System** — классы, общие справочники — задевают все арендаторы. Сигнал с токеном System сбрасывает класс везде.
- **Классы прав** (`rule`, `Resource`, `member`, `Account`, `Class`) сбрасывают весь кэш и пропуска прав, как в 1.0. В режиме `opaque` библиотека узнаёт их по токенам.
- **Сессии** — сигнал `session:<16 hex>` во всех режимах, кроме `none`. Хэш токена сессии ничего не говорит ни о классе, ни об арендаторе.

Кто получает ключ:
- Функция владельца `signal_key()` отдаёт ключ сессии с правом `letopis.signals` (правило System). Системный сид выдаёт это право сервисам.
- Процесс без ключа — например, `connect({ token })` пользователя — работает «грубо»: непонятный ему токен означает сброс кэша результатов. Реестр классов и пропуска прав он перечитывает не на каждый сигнал, а не чаще раза в 5 секунд — иначе каждая запись в базе, как и поддельный сигнал, заставляла бы его перечитывать реестр. Устаревших ответов кэша у такого процесса нет, только лишние запросы.

Что меняется у потребителей:
- **Триггеры** после оператора собирают пары «класс, арендатор» из переходных таблиц, а функция `signal()` строит из них нагрузку по режиму. Загрузчик и импорт перестают вызывать `pg_notify` напрямую и идут через ту же функцию.
- **Кэш** запоминает у ответа, кроме классов, токен арендатора запроса. Счётчики против гонки запроса и сигнала (`token()`/`set()`) ведутся по паре «класс, арендатор», а для сигналов System — по классу целиком.
- **Подписка** просыпается только от своих классов и своего арендатора, а без ключа — от любого сигнала, как сейчас. Потерь нет: сигнал только будит, события читаются из журнала.
- **Режим `none`** скрывает и время записи. Подписка опрашивает журнал (`pollMs`), кэш работает только по сроку или выключен — как сейчас за PgBouncer в режиме транзакций.
- **Классы с ПД** (§2.5) не кэшируются, когда кэш работает только по сроку — в режиме `none` или с `ttlOnly`: стёртое значение не должно жить в чужом кэше до конца срока.

**Чего не скрыть.** Время и частота записи видны и без сигналов: представления `pg_stat_all_tables` и `pg_locks` открыты для PUBLIC. Режим `opaque` прячет «что», но не «когда». Детерминированный токен раскрывает частоту по псевдониму — на этом строятся частотные атаки на поисковое шифрование. Всё это записывается в «Ограничения». Настоящая защита от посторонних ролей — отдельная база для домена доверия: сигналы между базами не ходят.

**Совместимость с процессами 1.0.** Процесс 1.0 разбирает нагрузку как имя класса и ничего не знает о втором канале. Поэтому в режимах `tenant` и `opaque`:
- `signal()` кладёт в `letopis.changed` не точную нагрузку, а `*`, а точную — в отдельную настройку `letopis.changed2`. Писатель 1.0 после фиксации посылает `*` в прежний канал и сам сбрасывает свой кэш целиком — дорого, но верно.
- Писатель 1.1 посылает точную нагрузку в `<схема>:2`, а пока включена опция `legacySignals` (по умолчанию включена) — ещё и `*` в прежний канал, для читателей 1.0.
- Читатель 1.1 слушает оба канала, пока включена `legacySignals`; всё непонятное в прежнем канале он считает `*`. Так он слышит и писателей 1.0.
- `legacySignals: false` выключают, когда процессов 1.0 не осталось.
- Загрузчик и импорт 1.0 по-прежнему шлют в прежний канал имена классов. Значит, режим `opaque` прячет имена, только когда все пишущие процессы — 1.1; `up({ signals: 'opaque' })` об этом предупреждает.
- В режиме `none` процессы 1.0 с включённым кэшем отдавали бы устаревшие ответы до конца срока (по умолчанию 60 с). Поэтому `up({ signals: 'none' })` требует подтверждения `confirm: 'no-1.0-cache'`, а README называет условие: все процессы — 1.1 или с выключенным кэшем.

**Как это устроено у других.**

| Система | Точность | Как защищены метаданные |
|---|---|---|
| PostgreSQL LISTEN/NOTIFY | канал и нагрузка до 7999 байт; одинаковые сигналы транзакции склеиваются | никак: слушать может любая роль; при фиксации — блокировка кластера |
| Supabase Realtime | Postgres Changes — проверка RLS на каждого подписчика; Broadcast from Database — темы | права на темы — RLS таблицы `realtime.messages` |
| Hasura | мультиплексированный опрос; переменные сессии — параметры общего запроса | сигналов нет |
| Electric, PowerSync | формы и корзины, параметризованные сервером или JWT | изоляция на сервере синхронизации |
| Prisma Accelerate, Next.js, Fastly, Cloudflare | теги кэша | арендатор — граница пространства имён (сервис, зона, среда) |
| CipherSweet | «слепой индекс»: усечённый ключевой HMAC | усечение делает совпадение вероятностным |

Выводы:
1. `NOTIFY` — публичная, непостоянная и дорогая при фиксации подсказка. В нагрузке только токены, а права проверяются повторным чтением под RLS.
2. Нагрузка детерминирована, иначе пропадёт склейка.
3. Каналы не множатся по арендаторам.
4. Токен — ключевой HMAC, а не хэш с открытой солью.
5. На PostgreSQL 19 план не рассчитывает.

### 2.4. Режим первой заливки (п. 9)

**Зачем.** На точке А `COPY` в копии таблиц без триггеров дал около 13,4 тысячи строк в секунду на миллионе строк, а загрузчик 1.0 — около 10,8 тысячи: на 24 % медленнее. Потолок задают индексы GIN по `data` и `ends`, первичный ключ по uuid v5, который ложится в индекс вразброс, и генерируемый хэш. Ещё часть разницы даёт триггер BEFORE ROW на `entity`: из-за него `COPY` идёт построчно. При загрузке в пустую схему — импорт из 0.21, перенос из другой системы, засевка — индексы и триггеры во время загрузки не нужны: индексы быстрее построить один раз в конце, сортировкой, чем поддерживать на каждой строке.

**API.** `db.load(rows, { initial: true })`, `letopis load --initial`, `letopis import --initial`.

**Порядок** — всё в одной транзакции:
1. `lock table entity, log in access exclusive mode`. Блокировка берётся до проверки: строка, вставленная между проверкой и TRUNCATE, пропала бы молча. На время загрузки схема закрыта и для чтения, и для записи.
2. Проверка. Подключение должно быть администраторским, а в `entity` и `log` не должно быть строк, кроме строк системных классов — описаний классов, аккаунтов, членств, ресурсов, правил — и служебной записи `reset`. Иначе — `not_empty`, до любых изменений. С `commitEvery` режим несовместим: снятые индексы и TRUNCATE требуют одной транзакции.
3. Сохраняются в памяти процесса:
   - строки системных классов из `entity` и `log`, включая `seq` и `tx` журнала;
   - определения индексов, ограничений и всех триггеров `entity` из каталога (`pg_get_indexdef`, `pg_get_constraintdef`, `pg_get_triggerdef`) — так режим не дублирует `10-core.sql` и не разойдётся с ним;
   - режим включения каждого триггера (`pg_trigger.tgenabled`): `pg_get_triggerdef` его не передаёт, а триггеры `entity` включены в режиме `ENABLE ALWAYS`, чтобы работать и при `session_replication_role = replica`.
4. `truncate entity, log`. Затем удаляются вторичные индексы, первичный ключ, `log_id_rev`, ограничение интервалов и все триггеры `entity`. Триггер BEFORE ROW нужно именно удалить: PostgreSQL выбирает построчный `COPY` по самому наличию такого триггера, не глядя ни на условие `WHEN`, ни на `DISABLE TRIGGER`. Триггеры после оператора тоже удаляются: их переходные таблицы на миллионе строк — лишняя память и запись.
5. Строки системных классов возвращаются оператором `insert … overriding system value` с прежними `seq` и `tx`: колонка `seq` журнала — `generated always`, и `COPY` её значения не принимает.
6. `COPY … FREEZE` загружаемых строк. `FREEZE` разрешён, потому что таблицы опустошены в этой же транзакции. Сам `COPY` он не ускоряет, но ставит биты карты видимости: первый VACUUM не переписывает таблицу, а первое чтение не пишет hint bits. В PostgreSQL 18 контрольные суммы страниц включены по умолчанию, и запись hint bits попадает в WAL.
7. Индексы и ограничения строятся заново по сохранённым определениям: сначала первичный ключ и уникальные (дубликат обнаружит сортировка), затем GIN и B-tree. `set local maintenance_work_mem` и `max_parallel_maintenance_workers` — в пределах настроек сервера. PostgreSQL 18 строит GIN параллельно.
8. Триггеры возвращаются с прежним режимом включения (`alter table … enable always trigger …`). Ограничение интервалов добавляется последним: пересечения в загрузке дают отказ со списком строк.
9. Проверки, которые делали бы удалённые триггеры после оператора, выполняются одним запросом: сторож ревизии 6 (§2.8) — по всем загруженным строкам сразу.
10. Обычный конец загрузки: запрос по целям вне загрузки (это строки системных классов), сигнал, `ANALYZE`. `ANALYZE` здесь обязателен: в PostgreSQL 18.0–18.5 параллельная сборка GIN могла оставить неверный `reltuples`.
11. Фиксация. Любая ошибка откатывает всё — и данные, и снятые индексы с триггерами: DDL в PostgreSQL транзакционен.

**Импорт.** `letopis import` вызывает загрузчик много раз — по арендаторам и группам классов. С `--initial` весь импорт идёт одной транзакцией: блокировка, TRUNCATE и снятие индексов делаются один раз в начале, а перестройка — один раз в конце. Иначе второй вызов загрузчика получил бы `not_empty`.

**Чего режим не делает.**
- Не пропускает WAL при обычном проде. WAL не пишется только при `wal_level = minimal`: тогда PostgreSQL сам не журналирует таблицу, опустошённую в этой транзакции. Обычный прод работает с `replica`, и режим рассчитан на выигрыш без пропуска WAL; `minimal` — бонус, о котором пишет README.
- Не переключает таблицы в `UNLOGGED` и обратно: `SET LOGGED` при `replica` переписывает и журналирует таблицу целиком.
- Не пишет из нескольких соединений. Параллельный `COPY` несовместим с `FREEZE` и одной транзакцией. В PostgreSQL 16 и новее без индексов он масштабируется, но это отдельный вариант — решение по замеру на точке А.
- Не использует двоичный формат `COPY`: для `jsonb` выигрыша нет.
- Почти не ускоряет режим истории (`withHistory`, импорт). Он пишет версии волнами `insert … returning hash`, потому что хэш следующей версии зависит от предыдущей, и выигрывает только от снятых индексов и триггеров.

**Цель** — в 3 раза быстрее обычного загрузчика на миллионе строк полигона salon без режима истории. Замер на точке А оценивает вклад триггеров, GIN, первичного ключа и `FREEZE` по отдельности; если `FREEZE` стоит больше, чем экономит, он убирается.

**Как это делают другие.**

| Инструмент | Порядок |
|---|---|
| `pg_restore` | pre-data (таблицы) → data (`COPY`) → post-data (индексы, ограничения, триггеры). `--jobs` распараллеливает. Сам делает `BEGIN; TRUNCATE; COPY; COMMIT`, чтобы при `minimal` пропустить WAL |
| pgloader | truncate, снятие индексов, отключение триггеров. Отключение, как сказано выше, построчный `COPY` не отменяет |
| pg_bulkload | прямая запись мимо буферов и WAL; нужен суперпользователь и своё восстановление после краха — для библиотеки не годится |
| timescaledb-parallel-copy | N соединений, пакеты по 5000 строк в отдельных транзакциях |

Замеры из рассылки PostgreSQL и блогов:
- перестройка индексов после загрузки — от 1,5 до 8 раз быстрее, в зависимости от схемы. Первичный ключ на миллионе строк: 4–6,7 с при вставке против 1,2–1,5 с, если строить его после;
- параллельная сборка GIN по `jsonb_path_ops` — около 1,2 раза;
- после `COPY FREEZE` первый VACUUM идёт примерно в 9 раз быстрее.

### 2.5. Персональные данные: хранилище и криптошреддинг (п. 3)

**Что говорит исследование.** Прежде чем выбирать устройство, изучено, что считают стиранием регуляторы и как стирают ПД другие хранилища с журналом.
- **Ни один регулятор не признаёт удаление ключа стиранием.** EDPB в руководстве 02/2025 о блокчейне (окончательная редакция — 7 июля 2026 года) пишет: после удаления ключа зашифрованные данные непонятны, но «зашифрованные персональные данные остаются персональными данными», и любое шифрование со временем устаревает (п. 51, 96). В том же руководстве: техническая невозможность стирания не оправдание (п. 50), а ПД лучше не записывать в неизменяемый журнал ни открытыми, ни зашифрованными, ни хэшированными (п. 103–104). ICO и CNIL называют шифрование способом «приблизиться к эффекту стирания», который нужно оценивать отдельно. Хэш без ключа или соли EDPB считает недостаточным (п. 52).
- **NIST SP 800-88r2** (сентябрь 2025 года) не доверяет криптостиранию, пока неизвестно, где лежат копии ключа, — в бэкапах и у эскроу.
- **Бэкапы PostgreSQL** берутся по кластеру целиком. Ключ, лежащий в той же базе, остаётся в WAL, на репликах и в бэкапах до их истечения — ровно как удалённые данные. MongoDB поэтому советует держать хранилище ключей в отдельном кластере, а Cratis Chronicle ведёт реестр стираний вне бэкапов и после восстановления повторяет стирания.
- **pgcrypto** для этой задачи слаб. `encrypt()` не проверяет целостность и по умолчанию берёт нулевой вектор инициализации. `pgp_sym_encrypt` по умолчанию — AES-128 с проверкой целостности на SHA-1. Ключ и открытый текст проходят через SQL и попадают в журнал сервера, если включено журналирование операторов или параметров. Вдобавок CVE-2026-14663 (исправлена в 18.6): при отключённых в OpenSSL шифрах `pgp_*` молча «шифровали» открытым текстом.

Отсюда решение в два уровня. Первый — стирание без шифрования: ПД вообще не попадают в журнал и удаляются физически. Второй, по желанию, — собственно криптошреддинг для копий вне досягаемости базы, то есть для бэкапов и дампов.

**Уровень 1 — хранилище ПД.**

```ts
const Client = hub('Client', { name: z.string(), phone: z.string(), email: z.email() }, {
  personal: { fields: ['name', 'phone', 'email'], subject: 'self' },
})
const Booking = link('Booking', { Client: one('Client'), note: z.string() }, {
  personal: { fields: ['note'], subject: 'Client' },           // субъект — клиент брони
})
```

Описание:
- Персональные поля — поля верхнего уровня. Субъект — `self` (сама строка) или роль одиночного обязательного конца. Конец-субъект после создания строки неизменяем: заметка о клиенте не может молча стать заметкой о другом клиенте.
- `personal` объявляется только у класса, у которого нет строк и нет версий в журнале: значения, уже записанные открытыми в `data`, лежат в журнале под цепочкой хэшей, и заменить их обязательствами нельзя. Для класса с данными путь — новый класс и перенос данных (загрузчиком или `reclass`), затем `trimHistory` старых версий.
- Поле нельзя убрать из `personal`, пока у класса есть строки. Потомки наследуют `personal` и могут добавить поля, но не убрать.
- Персональные поля не входят в ключ, в `noOverlap`, в условия правил ACL, в `anyOf` и `oneOf`, в агрегаты класса (`aggregate`), в фильтры, сортировку и агрегатные терминалы (`sum`, `avg`, `min`, `max`, `countBy`) и в `inc`. Описание с таким полем отклоняется, запрос — `invalid_query`.
- В типах TypeScript персональное поле — `T | null`: после стирания значения нет.

Как пишется:
- Значение персонального поля в `data` не хранится. Триггер вставки и правки проверяет данные целиком, с открытыми значениями, затем кладёт каждое новое значение в строку `secret` вида `PD` и оставляет в `data` обязательство `{"$pd": "<sha256(соль ‖ значение)>"}`. Соль — 256 случайных бит.
- Строка хранилища знает арендатора (колонка `account`), субъекта, объект и поле. Для поиска по субъекту (стирание) и по объекту (сопровождение) ревизия 7 добавляет два частичных индекса `secret`.
- Поле ПД заменяется только целиком. Объект, в котором рядом с `$pd` лежат другие ключи — так `merge` влил бы патч внутрь обязательства, — отклоняется (`invalid_data`). Библиотека всегда шлёт поле ПД целым значением.
- Неизменённое поле `merge` оставляет как было, обязательство вместе с ним, поэтому новой строки хранилища не появляется.
- Если пришло открытое значение, равное прежнему (`upsert` присылает объект целиком), триггер узнаёт это, посчитав хэш с солью прежнего значения, и оставляет прежнее обязательство. Поэтому `upsert` тех же данных по-прежнему отвечает `unchanged` и версии не пишет.
- Записать в поле чужое обязательство нельзя (`personal_ref`): принимается только обязательство, которое уже принадлежит этому объекту. Иначе приложение могло бы «одолжить» значение другого субъекта, подставив его обязательство.
- Журнал, снимки версий и цепочка хэшей содержат только обязательства. Хэш версии покрывает обязательство, а обязательство — значение, поэтому `verify({ data: true })` проверяет подлинность каждого значения, пока оно не стёрто.
- Проверка хранимых строк — в `restore`, `reclass`, `rekey`, при ужесточении класса, в `verify({ data: true })` и в проверке загрузчика — подчиняется одному правилу: обязательство удовлетворяет схеме своего поля. Значение проверялось открытым при записи. Правило одинаково в SQL и в валидаторе на TypeScript; совпадение закрепляет дифференциальный тест.
- После стирания обязательство остаётся в журнале и ни с чем не связывается. Подобрать значение по нему нельзя: соль стёрта вместе со значением. Это сильнее шифра — нет ключа, который однажды взломают.

Смена id:
- `rekey` и `reclass` объекта (`move_row`) перепривязывают строки хранилища к новому id объекта.
- `rekey` субъекта перепривязывает строки хранилища к новому id субъекта, поэтому `forget` нового id находит все значения.

Как читается:
- Функция владельца `pd_reveal(id, rev)` перечитывает строку или версию по id, проверяет её видимость актору (`row_visible`) и отдаёт открытые значения. Библиотека добавляет её везде, где строка уходит приложению: в `rows()`, `versions()`, `diff`/`blame`, события подписки и в результаты записи (`returning` глаголов).
- Стёртое поле приходит как `null` и перечисляется в служебном поле строки `$erased`.
- Сырой SQL видит обязательства и может вызвать `pd_reveal` сам.

**Строки хранилища и функции кредов.** Функции кредов (`auth_credentials`, `auth_revoke_credential`, `auth_set_flags`) сейчас отсекают только виды `SESSION` и `KEY`, а `auth_kind_ok` разрешает любой вид, кроме перечисленных. Со строками хранилища пользователь в личном арендаторе увидел бы их как свои «креды» и смог бы «отозвать» их мимо `forget` и его записи в журнале. Поэтому:
- функции кредов работают только с белым списком видов кредов;
- виды `PD`, `PDKEY` и `PROJECTOR` недоступны всем API кредов, в том числе созданию;
- удаление аккаунта и `reset({ tenant })` удаляют строки хранилища физически, а не помечают `deleted_at`.

**Стирание.** `db.forget(субъект, { confirm: true })`. Без `confirm` — превью: какие классы и сколько видимых строк задеты.
1. Удаляются все строки хранилища ПД субъекта — во всех классах и всех версиях, в арендаторе субъекта.
2. В журнал пишется служебная запись `forget` (субъект, автор, время) — след для аудита. id субъекта — суррогатный v5 и сам ПД не раскрывает. Запись учитывается там же, где `purge`, `trim` и `reset`: срезы её пропускают, прореживание не трогает.
3. Сигнал задетых классов сбрасывает кэши, где лежали открытые значения.
4. Новых версий живых строк стирание не пишет: в них и так только обязательства.

Что значит «удалено»:
- В живой базе и на репликах значения недоступны сразу после фиксации. Байты удалённых строк остаются в страницах таблицы до VACUUM, в WAL и в бэкапах до истечения их срока — как у любых удалённых данных PostgreSQL. Это записывается в «Ограничения», а против копий вне базы есть уровень 2.
- Вызывать `forget` могут системный администратор и роль с правом `letopis.forget` (правило System) — обычно это сервис, исполняющий запросы субъектов.
- Результат — квитанция: субъект, момент стирания и число стёртых значений. После восстановления базы из бэкапа, снятого до стирания, значения вернутся. Поэтому квитанции хранятся вне базы, а `letopis forget --replay <файл>` повторяет стирания до запуска приложения. Повтор удаляет только строки хранилища, созданные раньше момента из квитанции: новые данные вернувшегося клиента он не трогает. Так же поступает Cratis Chronicle, и этого ждёт EDPB («процедуры, чтобы исполнять запросы на стирание на восстановленных системах»).

**Сопровождение хранилища.**
- `purge`, `trim` и прореживание удаляют версии. Строки хранилища, на которые больше не ссылается ни одна версия объекта, удаляет тот же вызов по id объекта.
- `maintain()` подбирает потерянные строки, которые остались после сбоя.
- Загрузчик пишет строки хранилища и обязательства сам, тем же алгоритмом; это закрепляет дифференциальный тест.
- `letopis import` с опцией `--personal Класс.поле,…` переносит ПД из 0.21 сразу в хранилище.

**Уровень 2 — криптошреддинг.** Он защищает копии, до которых база не дотянется: бэкапы, PITR, дампы.
- Значения в хранилище шифрует библиотека — AES-256-GCM в Node, около 170 тысяч шифрований в секунду на ядро. Вектор инициализации случайный, 96 бит. Связанные данные — арендатор и id строки хранилища: шифротекст нельзя перенести в другую строку, а перепривязка при `rekey` и `reclass` (она меняет объект и субъект, но не строку хранилища) расшифровке не мешает.
- Ключ субъекта (DEK) случайный; в `secret` он лежит обёрнутым ключом приложения (KEK). KEK база не видит никогда: `connect({ personal: { kek } })` или адаптер KMS `{ wrap, unwrap }`.
- Обязательство считается от шифротекста. Поэтому `verify()` работает без ключей.
- Вектор инициализации случайный, поэтому триггер не узнает равное значение. `upsert` тех же данных сравнивает значения в библиотеке: она расшифровывает текущее и при совпадении оставляет прежнее обязательство.
- `forget` удаляет и строки хранилища, и ключ субъекта.
- Чтобы старые бэкапы стали нечитаемыми, KEK меняют по расписанию: `db.rotatePersonalKey()` переобёртывает ключи живых субъектов, а старую версию KEK уничтожают в KMS. Срок «не позже T» складывается из расписания ротации и задержки KMS: 7–30 суток у AWS, до 45 у Google. Цена: после уничтожения старого KEK из старых бэкапов не восстановить ПД ни одного субъекта, не только стёртых.
- База больше не видит открытых значений ПД. Их формат проверяет валидатор библиотеки, а база — только форму шифротекста. Сырой SQL писать ПД не может — у него нет KEK. Процесс без KEK (например, сервер MCP, которому KEK не дали) читает ПД как недоступные.
- Уровень 2 включается явно (`up({ personal: 'encrypted' })`), только целиком для установки, и хранится в схеме, как режим сигналов (§2.8).
- Ограничение AES-GCM — не больше 2^32 шифрований на один ключ субъекта. Ключ субъекта меняется для новых значений раньше этого предела; старые значения не перешифровываются.

**Чего хранилище не делает.**
- Не стирает копии в бэкапах на уровне 1 — они живут до истечения срока хранения бэкапов, как любые удалённые данные.
- Не ищет по ПД: поиск между субъектами требует общего ключа индекса, а общий ключ стирание субъекта переживёт. Вариант со «слепым индексом» в `secret` вынесен за план (§11).
- Не обещает юридической эквивалентности. README описывает, что именно удаляется и где копии остаются, а решение о соответствии GDPR — за ответственным за защиту данных.
- Не убирает ПД из журнала сервера PostgreSQL на уровне 1. Значения приходят в операторах `insert` и `update`, и журналирование операторов или параметров их запишет. README советует не журналировать параметры там, где есть ПД; на уровне 2 открытого значения в SQL нет.

**Как это устроено у других.**

| Система | Где ПД | Стирание | Бэкапы |
|---|---|---|---|
| Axon Data Protection | поле `@PersonalData` шифруется ключом `@DataSubjectId` | удаление ключа; проекции и снимки чистить отдельно | не описано |
| Kurrent / EventStoreDB, Dudycz | ключ на пользователя в Vault или KMS | удаление ключа | «когда алгоритм сломают, данные снова доступны» |
| Marten | маскирование событий (`ApplyEventDataMasking`) с перестройкой проекций | переписывание событий | — |
| Cratis Chronicle | `[PII]`, ключ на субъекта | удаление ключа и реестр стираний вне бэкапов | повтор стираний после восстановления |
| MongoDB CSFLE | ключ на пользователя в хранилище ключей | удаление ключа; кэш ключей — до 60 с | хранилище ключей — в отдельном кластере |
| Hyperledger Fabric | частные данные вне цепочки | purge, в цепочке остаётся хэш | — |
| Rails 7, Prisma | шифрование полей приложением | — | — |

Выводы:
1. Удаление ключа — не стирание, а смягчение для копий вне досягаемости. В своей базе letopis может удалить физически, значит, должен.
2. Журнал и хэш содержат только обязательство со случайной солью — не хэш открытого значения.
3. Шифрование — только в Node и только с ключом вне базы, иначе бэкапы не защищены.
4. Нужен реестр стираний вне базы и повтор после восстановления.
5. Поиск по ПД не обещается.

### 2.6. Производные представления (п. 5)

Под «производными представлениями» понимаются два разных механизма.
- **Агрегаты в базе** — синхронные, из текущего состояния. Нужны для сумм и счётчиков, которые обязаны совпадать с источником и для сырого SQL.
- **Проекторы** — асинхронные, из журнала. Нужны для сводок, денормализованных карточек и всего, что можно считать с отставанием.

Материализованные представления и расширение pg_ivm не подходят. Это дополнительные отношения, то есть нарушение принципа трёх таблиц. pg_ivm не работает с секционированными таблицами, его нет на AWS RDS, а у Neon он недоступен для новых установок.

**Агрегаты в базе.**

```ts
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0) }, {
  key: ['number'],
  aggregate: { balance: { sum: 'amount', of: 'Movement', via: 'Wallet' } },
})
```

Что делает база:
- Держит `balance` равным сумме `amount` живых строк `Movement`, чей конец `Wallet` указывает на этот кошелёк. Операции — `count` и `sum` по числовому полю. Условие `where` — JSON Schema над данными строки-источника.
- Пересчитывает приращением в триггерах после оператора: по переходным таблицам, одним `update … set data = inc(…)` на каждый задетый объект за оператор, в порядке id. Поэтому `Movement.create(…)` и сырой `insert` в `Movement` меняют баланс одинаково. Правило `minimum: 0` проверяется над итогом и отклоняет операцию, которая увела бы баланс в минус.
- Не даёт приложению писать агрегатное поле (`aggregate_field`). При создании объекта поле равно нулю.
- Применяет приращения и на путях записи мимо триггеров — в каскаде удаления, `move_row`, `restore`, загрузчике, удалении аккаунта — через тот же помощник `agg_apply`. На каждый путь есть свой тест.
- Пересчитывает поле целиком, когда меняется сама цель: `restore` кошелька берёт баланс не из надгробия, а из суммы живых операций; после `move_row` цели — тоже, чтобы приращения не применились дважды.
- Учитывает только строки того же арендатора, что и цель. Ссылка на строку System в агрегат не входит, иначе общий справочник считал бы данные всех арендаторов.
- Меняет цель от имени владельца. Это решение: чтобы изменить баланс операцией, достаточно права записи в `Movement`, право записи в кошелёк не нужно — как у счётчика `counter_cache` в Rails.

Добавить или изменить агрегат — ужесточение. Оно берёт исключительные блокировки семейства цели и семейств источников: иначе операция, зафиксированная во время пересчёта, потерялась бы. `db.rebuildAggregates(класс)` пересчитывает значения из текущих строк — для ремонта; версия пишется только там, где значение изменилось.

Цена — как у `inc` в 1.0: операции одного объекта идут друг за другом под блокировкой его строки, и каждая пишет версию цели. Строка-счётчик выстраивает писателей в очередь, поэтому для горячих счётчиков (тысячи записей в секунду на один объект) агрегат в базе не годится; для них нужен проектор со свёрткой пачкой. Механизм трогает все пути записи владельца, поэтому решение о нём принимается на точке Б (§6).

**Проекторы.**

```ts
const revenue = db.projector('daily-revenue', {
  from: ['Booking'],                 // классы-источники вместе с потомками
  into: ['DailyRevenue'],            // производные классы
  version: 1,                        // смена версии требует перестройки
  async handle(changes, out) {       // change: { id, class, tenant, op, rev, at, author, row, before? }
    for (const c of changes) out.upsert('DailyRevenue', { tenant: c.tenant, /* … */ })
  },
})
await revenue.run()          // догнать журнал и следовать за ним
await revenue.rebuild()      // перестроить с нуля
```

- **Это процесс администратора**, как загрузчик и `maintain`. Он работает на администраторском подключении, читает журнал всех арендаторов по курсору (без RLS) и записывает результаты тем же проверенным путём, что загрузчик: валидатор, концы, арендатор. Проектор — код приложения, которому доверяют, как миграциям.
- **Курсор** тот же, что у подписки: `(tx, seq)` ниже горизонта `pg_snapshot_xmin` вместе со снимком момента (как `~снимок` в курсоре подписки). Пачка и горизонт берутся одним оператором, без таймеров, пропускающих «дыры». Именно разные снимки и таймерные пропуски приводили к тихой потере событий в Marten до версии 9.16.1 (июль 2026 года).
- **Ровно один раз.**
  - Чекпоинт хранится в `secret` (вид `PROJECTOR`, идентификатор — имя проектора).
  - Он сдвигается условно, «курсор равен ожидаемому», в той же транзакции, что и запись результатов, — как `projection_versions` в Commanded и прогресс в Marten.
  - У проектора один писатель: транзакционная advisory-блокировка на каждую пачку, как у `maintain()`. Это работает и за PgBouncer.
- **Запись ограничена.**
  - `out.upsert` и `out.delete` пишут только в классы `into` и только в арендатора того изменения, которое обрабатывается.
  - Производные классы помечены `derivedBy: '<имя>'`. Приложение и сырой SQL их не пишут (ошибка `derived_class`).
  - Ссылаться на производные строки нельзя, поэтому у их удаления нет каскада.
  - Для производных классов рекомендуется `history: false`: иначе производные строки удваивают журнал, а проектор не должен читать собственные записи.
- **Изменение** — снимок новой версии (`row`), как событие подписки. Если проектор попросил `withBefore`, приходит и прошлая версия (`before`, по `(id, rev − 1)`). Служебные записи `purge`, `trim`, `reset` и `forget` тоже приходят как изменения: проектор сам решает, что делать с производными строками стёртого объекта.
- **Порядок.** `(tx, seq)` — порядок первой записи транзакций, а не их фиксации. Для строк одного объекта проектор сравнивает `rev` и пропускает устаревшее, а для агрегатов по многим объектам берёт коммутативные операции — сумму или счётчик.
- **Перестройка** идёт с текущего состояния, а не с начала журнала: журнал прорежен политикой хранения и обрезан `purge`, и повтор с нуля дал бы не то.
  - Текущие строки источников читаются одним снимком — транзакцией `repeatable read`. Чекпоинт ставится на пару «горизонт этого снимка и сам снимок», а из хвоста журнала исключаются транзакции, видимые в снимке (`pg_visible_in_snapshot`). Иначе транзакции, зафиксированные между горизонтом и снимком, попали бы и в снимок, и в хвост — и сумма учла бы их дважды.
  - В атомарном варианте производные строки удаляются и строятся заново в одной транзакции, и до фиксации читатели видят прежние строки. Долгая транзакция держит горизонт и задерживает подписки всех процессов. Поэтому для больших проекций есть `rebuild({ chunked: true })`: перестройка пачками с состоянием `rebuilding`, и на это время читатели видят смесь старых и новых строк. Какой вариант брать по умолчанию — решается по замеру на точке Б.
- **Отставание** дольше яруса `all` политики хранения даёт `cursor_expired`, как у подписки. Опция `onExpired: 'rebuild'` перестраивает проекцию сама.
- **ПД** в производных строках попадают в хранилище ПД, если производный класс объявил `personal` с субъектом (§2.5). Тогда `forget` стирает и их.

| Marten | inline, в той же транзакции | async-демон, high water mark | таблица прогресса, на арендатора | с нуля; новая версия проекции — новые таблицы |

3. Синхронно считается только то, что держит целостность; горячее сворачивается пачкой.
4. Перестройка идёт с текущего состояния плюс хвост журнала.
5. Дополнительные отношения противоречат принципу трёх таблиц.

### 2.7. Инструменты MCP (п. 2)

**Зачем.** Агент — Claude, Cursor или свой — получает доступ к данным letopis через инструменты MCP: узнать модель, прочитать данные цепочкой, посмотреть историю, а если разрешено — записать. Главное преимущество letopis перед MCP-серверами баз данных в том, что права проверяет сама база. Во всех разобранных провалах защита стояла вне базы:
- у Asana — ошибка в слое MCP открыла данные чужих организаций;
- в демонстрации на Supabase агент работал под `service_role`, который обходит RLS;
- у эталонного Postgres-сервера и у сервера AWS режим «только чтение» держался на разборе SQL и обходился оператором `COMMIT;`.

Поэтому слой MCP у letopis тонкий: каждый вызов идёт цепочкой под сессией пользователя.

**Поставка.**
- Подпуть `letopis/mcp` и команда `letopis mcp`.
- SDK — `@modelcontextprotocol/server` 2.x (Apache-2.0, Node ≥ 20, Zod ^4.2). Это необязательная peer-зависимость, как Zod для `letopis/model`: основная точка входа его не загружает.
- Целевая ревизия протокола — 2026-07-28: без состояния соединения, с `server/discover`. SDK обслуживает и прежнюю ревизию.
- Схемы инструментов задаются чистой JSON Schema (`fromJsonSchema`), без описания на Zod.

**От чьего имени действует сервер.** Сервер MCP работает от имени одного пользователя и только с его правами.
- `letopis mcp` принимает только токен сессии пользователя (`--token` или `LETOPIS_TOKEN`), выпущенный приложением через `db.auth.sessionFor(пользователь, { ttl })`. Ключ сервиса командная строка не принимает: он даёт все права `auth.*` — имперсонацию любого видимого пользователя и выпуск сессий, — а лежал бы в окружении машины агента.
- `createMcpServer(db)` в приложении принимает сессию пользователя или фасад `db.as(пользователь)` — тогда ключ сервиса остаётся в процессе приложения, где он и так живёт. Подключение, которое обходит RLS, и корень сервиса без `as` отклоняются.
- Для stdio строку подключения и токен можно передать переменными окружения (`LETOPIS_DSN`, `LETOPIS_SCHEMA`, `LETOPIS_TOKEN`) — так их передают клиенты MCP.

**Инструменты** — немного и «по исходам», как советуют Anthropic и Phil Schmid (5–15 на сервер).

| Инструмент | Что делает | Аннотация |
|---|---|---|
| `letopis_model` | модель: классы, поля (JSON Schema), концы, ключи, алиасы; с `class` — подробно один класс | только чтение |
| `letopis_query` | чтение цепочкой, описанной в JSON: старт (класс и фильтр или id), шаги по связям и ролям, модификаторы (`asOf`, `withDeleted`, `sort`, `limit`, `after`, `during`), терминал (`rows`, `first`, `count`, `ids`, `sum`, `avg`, `min`, `max`, `countBy`) | только чтение |
| `letopis_history` | `versions`, `diff` или `blame` объекта | только чтение |
| `letopis_write` | `create`, `update`, `upsert`, `delete` — только при запуске с флагом `--write` | разрушительный |

Правила инструментов:
- **Без сырого SQL.** Цепочка из JSON собирается вызовами API библиотеки, без `eval`. Неизвестный класс или роль — ошибка с подсказкой похожих имён. Инструмента сырого SQL нет вообще.
- **Объём ответа.** Ответ — `structuredContent` и его текстовый дубль. По умолчанию не больше 100 строк и 50 КБ; дальше — курсор `after`. Курсор свой, потому что пагинация MCP есть только у списков. Claude Code переносит ответы больше 25 тысяч токенов в файл.
- **Данные — недоверенный ввод.** Всё, что пришло из базы, — данные строк, имена и описания классов, в том числе подсказки похожих имён в ошибках, — оборачивается в `<untrusted-data-…>` со случайным суффиксом и пояснением, что внутри не инструкции, как у Supabase и MongoDB. Это смягчение, а не защита.
- **Текст арендаторов не попадает в описания.** Метаданные классов (`meta`, названия, описания) пишут арендаторы. Поэтому в описания инструментов и в `instructions` сервера они не попадают — только в результаты, как данные. Иначе это канал «отравления инструментов». Описания инструментов — постоянный текст пакета.
- **Запись.**
  - `update` через MCP требует `rev`: агент сначала читает, поэтому потерянных обновлений нет.
  - `delete` без `confirm` возвращает превью. Само удаление требует подтверждения человека через elicitation — ответа пользователя в клиенте, привязанного к хэшу операции. Токен, который агент мог бы вернуть сам, подтверждением не считается. Если клиент не умеет elicitation, разрушительная операция не выполняется: в MongoDB и Supabase такой клиент получает выполнение без подтверждения, здесь — наоборот.
  - Каждая запись получает причину `mcp: <инструмент>` (§2.1), и `blame` показывает, что поле изменил агент.
- **ПД** приходят открытыми, если пользователю разрешено их видеть. Флаг `--no-personal` отдаёт их как `null` с перечнем полей в служебном поле `$hidden` — для агентов, которым ПД не нужны.
- **Имена и схемы.** Имена инструментов — латиница, цифры и `_`: клиент Claude не принимает точки. Корень входной схемы — `type: object`, без `anyOf` и `oneOf`: Claude их разворачивает.

**HTTP.** Встроенного HTTP-сервера нет. `createMcpServer(db)` отдаёт сервер, который приложение подключает к своему HTTP-обработчику (`createMcpHandler` из SDK) со своей авторизацией OAuth 2.1, а токен запроса превращается в сессию letopis. Свой сервер авторизации в пакете (метаданные RFC 9728, проверка аудитории RFC 8707) дублировал бы то, что у приложения уже есть.

**Code mode** — когда агент пишет код против типизированного API, как в Cloudflare «Code Mode» или Anthropic «code execution with MCP», — в 1.2 не входит. Для него нужна песочница без сети, файловой системы и переменных окружения, а при четырёх инструментах выигрыш мал. Права и тогда проверяла бы база.

**Как это устроено у других.**

| Сервер | Запросы | Схема | Защита |
|---|---|---|---|
| Supabase | сырой SQL, `execute_sql` | инструмент `list_tables` | read-only роль, привязка к проекту, группы инструментов, обёртка `<untrusted-data-UUID>`, подтверждение разрушительного |
| Neon | `run_sql` | `describe_table_schema` | read-only по параметру или OAuth-scope |
| PlanetScale | раздельные чтение и запись | — | блокирует UPDATE и DELETE без WHERE, DDL — через подтверждение |
| MongoDB | инструменты коллекций | `collection-schema` | `readOnly`, `disabledTools`, подтверждение, до 100 документов и 16 МиБ |
| Google MCP Toolbox | параметризованный SQL из `tools.yaml` | — | параметры из claims токена |
| DBHub | `execute_sql`, `search_objects` | постепенное раскрытие | `max_rows`, таймаут |
| Convex | `runOneoffQuery` в песочнице, `run` | `tables` | прод по умолчанию закрыт |
| эталонный Postgres (в архиве) | `query` в транзакции READ ONLY | ресурсы схем | обходился `COMMIT;` |

Выводы:
1. Права проверяются только в базе, слой MCP тонкий.
2. Без сырого SQL и без ключа сервиса на машине агента.
3. По умолчанию — только чтение; запись — отдельной группой.
4. Всё, что пришло из базы, — недоверенный ввод.
5. Текст арендаторов не попадает в описания инструментов.
6. Без подтверждения человека разрушительная операция не выполняется.

### 2.8. Ревизия движка, режимы установки, совместимость

**Ревизии.**
- **Ревизия 6 (1.1) — миграция `0006-intervals.sql`**: колонки `span` и `span_key` и ограничение `entity_span_excl`. Это первая миграция в каталоге; сам механизм миграций есть с 1.0 (`up.ts:migrationFiles`). Миграции идут до наката функций, поэтому триггер-сторож и функция `span_of()` создаются обычными файлами (`60-write.sql`), а не миграцией. btree_gist установщик ставит до миграции, как pgcrypto.
  - Колонки добавляются мгновенно, без перезаписи таблицы. Ограничение строится по пустому множеству строк, но таблица просматривается под `ACCESS EXCLUSIVE` — на миллионах строк это секунды. README советует окно обслуживания.
- **Ревизия 7 (1.2) — миграция `0007-personal.sql`**: два частичных индекса `secret` для хранилища ПД — по субъекту и по объекту (§2.5). Индексы на `secret` строятся быстро: таблица до этого маленькая.
- **Остальные этапы структуру не меняют.** Они затрагивают функции (те накатываются при каждом `up()`), виды строк `secret` (`PD`, `PDKEY`, `PROJECTOR`) и метасхему классов. Если по замеру §2.1 понадобится колонка изменённых путей журнала, она войдёт в ревизию 6.

**Режимы установки хранятся в схеме.** В 1.0 опции `up()` — `allowReset`, политика истории — берутся из текущего вызова и подставляются в тексты функций, нигде не сохраняясь. Для режима сигналов и уровня хранилища ПД так нельзя: обычный `up()` при старте приложения без опций вернул бы режим `class` (имена классов снова видны, а процессы 1.1 на канале `<схема>:2` перестали бы получать сигналы) или выключил бы уровень 2 (сырой SQL снова смог бы писать открытые ПД). Поэтому:
- режимы хранятся в `meta` строки ключа `secret` с id System — там же, где курсор прореживания и метка политики по умолчанию;
- установщик читает их оттуда при каждом накате;
- сменить режим можно только явной опцией с подтверждением (`up({ signals: 'opaque', confirm: … })`);
- опустить уровень хранилища ПД со 2 на 1 нельзя, пока в хранилище есть шифротексты.

**Описания классов.**
- Накат функций не пересчитывает `resolved` у старых строк `Class`. Новые опции (`noOverlap`, `personal`, `aggregate`, `derivedBy`) появляются в `resolved` при правке класса, а код, читающий `resolved`, терпит их отсутствие.
- `class_change_safe` считает «безопасным» всё, чего не сравнивает. Поэтому любая правка `noOverlap`, `personal`, `aggregate` и `derivedBy` в нём — ужесточение, с исключительной блокировкой и своей проверкой строк по правилам §2.2, §2.5 и §2.6.
- `syncModels` 1.0 записывает описание класса целиком и о новых опциях не знает. Если бы отсутствие опции в описании значило «снять», процесс 1.0 с прежними моделями молча снял бы правило интервалов или пометку ПД. Поэтому для новых опций отсутствие ключа в присланном описании значит «оставить как было», а снять опцию можно только явным `null` — и только там, где это разрешено (`personal` со строками не снимается).
- Наследование: потомок получает `noOverlap`, `personal`, `aggregate` и `derivedBy` предка. `noOverlap` и `aggregate` он может заменить своими, `personal` — только расширить, `derivedBy` — не менять.

**Зарезервированные имена.** Методы цепочки `diff`, `blame`, `during` и свойства корня `forget`, `projector`, `rebuildAggregates`, `rotatePersonalKey` попадают в `RESERVED_CLASS_NAMES`. База отклоняет только связи с такими именами, а хаб с таким именем создать можно, но через цепочку он станет недостижим. Поэтому `up({ upgrade: true })` предупреждает о каждом существующем классе из полного списка новых имён.

**Процессы 1.0 на новых ревизиях.** `connect()` 1.0 предупреждает только об отставшей схеме, а на более новой работает молча.
- Чтение и запись через библиотеку 1.0 безопасны: служебные колонки и хранилище ПД обслуживают триггеры базы. Сигналы — §2.3.
- Опасен загрузчик 1.0: он пишет мимо триггеров и не знает ни интервалов, ни ПД. Поэтому ревизия 6 добавляет триггер-сторож после оператора вставки и правки без условия `WHEN`, то есть срабатывающий и для владельца. Строки классов с правилом интервалов без служебных колонок или с открытыми значениями ПД (с 1.2) он отклоняет с подсказкой обновить letopis. Для обычных писателей сторож выходит сразу, а его цену для загрузчика 1.1 показывает замер на точке А.
- Загрузчик 1.1 и проекторы отказываются работать на схеме, ревизия которой не равна их собственной.

## 3. Отличия от формулировок §13

| §13 плана 1.0 | В этом плане | Почему |
|---|---|---|
| запрет пересечения через ограничение исключения (btree_gist) | одно ограничение по служебным колонкам, которые заполняет триггер | выражения ограничения обязаны быть IMMUTABLE; частичные ограничения на каждый класс дорожают линейно; DDL при определении класса останавливал бы запись |
| инструменты MCP поверх `describe()` | плюс чтение цепочкой из JSON, история, запись по флагу; без сырого SQL, без ключа сервиса в командной строке и без встроенного HTTP-сервера | одного описания модели агенту мало; права уже проверяет база |

| `diff` и `blame` по журналу | плюс причина изменения в API | без причины `blame` отвечает только «кто и когда» |
| производные представления из журнала | проекторы из журнала плюс агрегаты в базе из текущего состояния | синхронная целостность для сырого SQL — отдельная задача от асинхронных сводок |
| кэш с точностью до арендатора: сигнал с хэшем арендатора | режим `tenant`, токен — ключевой HMAC | без ключа хэш id арендатора сопоставит любой, кто знает id |
| сигналы без имени класса; кэш сбрасывается целиком | режим `opaque` сохраняет точность через токены; полный отказ от сигналов — режим `none` | точность и приватность одновременно |
| первая заливка: снятие индексов и перестройка | плюс удаление триггеров, TRUNCATE и `COPY FREEZE`, определения индексов и режимы триггеров из каталога | триггер BEFORE ROW сам по себе делает `COPY` построчным; `FREEZE` снимает последующий VACUUM |

## 5. Этапы

Каждый этап начинается по команде владельца. Условие закрытия этапа — его тест-план из §7, пройденный в CI. Документация, карточки модулей и трассы обновляются в том же коммите, что и код.

### Этап 0. Подготовка

1. Версия `1.1.0-alpha.0` в `dev`, верхняя запись CHANGELOG. Выпуска альфы нет; номер `1.1.0` выставляется перед выпуском.
2. Проверка btree_gist в PGlite и на роли без суперпользователя.
3. Каталог `lib/sql/migrate/` и фикстура схемы ревизии 5 с данными, снятая с 1.0.1, — для тестов миграции на этапе 2.
4. `describe()` отдаёт `anyOf` и `oneOf` описания — сейчас их нет, а они нужны агенту и MCP.
5. Опорный бенч перед изменениями: запись, чтение, загрузка, `maintain` на полигоне salon. С ним сравниваются замеры точек А и Б.
6. Карта: заготовки карточек M-PERSONAL, M-DERIVED, M-MCP.

### Этап 1. `diff` и `blame`

1. `75-history.sql`: `jsonb_changes`, `version_changes`, `diff_versions`, `blame` — `security invoker`, тела в стандартном синтаксисе SQL, где получается.
2. Терминалы `diff()` и `blame()` в цепочке; `follow`, моменты, `limit`, `exact`, `complete`.
3. Опция `reason` глаголов, `db.begin({ reason })`, `db.batch(name, { reason })`.
4. Зарезервированные имена `diff`, `blame`; предупреждение `up({ upgrade })` о конфликтующих классах.
5. Замер `blame` по 1000 версиям; решение владельца о колонке изменённых путей — до начала этапа 2.

### Этап 2. Запрет пересечения интервалов

1. Миграция `0006-intervals.sql` и та же структура в `10-core.sql`; btree_gist в установщике (без расширения — установка без ограничения и отказ `noOverlap`); ревизия 6 в `99-revision.sql` и `DDL_REVISION`.

## 10. Порядок и правила работы

```
0 ─► 1 ─► (решение о колонке) ─► 2 ─► 3 ─► 4 ─► КТ А (ревью №1, выпуск 1.1.0) ─► 5 ─► КТ Б ─► 6 ─► 7 ─► 8 ─► КТ В (выпуск 1.2.0)
```

- Каждый этап начинается только по команде владельца; на контрольных точках работа останавливается до его решения.
- Этапы идут последовательно: соседние этапы правят одни и те же файлы (этапы 1 и 2 — `chain.ts`, `sql.ts`, `types.ts`; этапы 2, 3 и 5 — `60-write.sql`, `load.ts`). Параллельно можно готовить только тест-атаки и фикстуры следующего этапа.
- Внутри этапа сначала пишутся тест-атаки и гонки, затем код.
- Результат этапа фиксируется коммитами в `dev`. Пуш и выпуск — по команде владельца, по порядку деплоя: `dev` → PR → merge на GitHub → тег → Release.
- В одном коммите с кодом обновляются карточка модуля, трасса, раздел «Тесты» обоих README и контракт API.
- Проектирование, код и ревью выполняет основная модель или субагент без смены модели; поиск по коду — субагент `atlas-scout`.

## 11. Вне плана

- Партиции журнала по месяцам (п. 6 §13) и порт на Python (п. 10) — по решению владельца.
- Вторая пара служебных колонок для двух занятостей одной строки.
- Чтение по интервалу в прошлом (`during` вместе с `asOf`).
- Поиск по ПД через «слепой индекс» в `secret`.
- Добавление `personal` к классу с данными без переноса в новый класс.
- Полевые права (маскирование отдельных полей в чтении и истории).
- Встроенный HTTP-сервер MCP со своей авторизацией; code mode.
- Сигналы через логическую репликацию (`pg_logical_emit_message`): права на чтение сигнала, но ценой `wal_level = logical` и права REPLICATION.
- Матрица CI с PostgreSQL 19 — после его выхода, по плану 1.0.
