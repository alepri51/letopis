## О чём этот отчёт

Это промежуточный отчёт — приложение к итоговой оценке `reports/ASSESSMENT.md`, для которой он служит источником. Предыдущий статический анализ кода (чтение исходников без запуска) дал несколько критических находок. Здесь мы проверяем четыре из них эмпирически: пишем короткий сценарий — пробу, — прогоняем его на живой базе и смотрим, совпадает ли реальное поведение с тем, что предсказал анализ кода.

Нумерация проб (P1…P4) совпадает с исходным отчётом, поэтому ссылки вида «[08] P1» из итоговой оценки остаются верными.

## Как устроен прогон

Все четыре пробы выполнены в одном окружении.

- **Код.** Пакет `letopis` 0.21.0, ветка `dev`, HEAD `99a28e0`. Исходники `lib/src/*.ts` запускались напрямую через `tsx` — инструмент, который исполняет TypeScript без предварительной сборки.
- **База.** Dev-контейнер `letopis-timescale` (образ `letopis-db`, TimescaleDB на PostgreSQL 17).
- **Схема.** Для проб создана одноразовая схема `v1.auditprobe` вызовом `up({fresh:true})` с сидами по умолчанию (сиды — начальные данные демо-доменов booking и auth). Классы `Org` и `Folder`, на которых идут пробы, взяты из этого демо-домена.
- **Опции подключения** оставлены по умолчанию: `enforceAccount: true` и `enforceAcl: false`. Аккаунт (account) в letopis — это арендатор (tenant): несколько клиентов делят одну схему, и данные одного не должны быть видны другому. `enforceAccount` включает фильтрацию запросов по аккаунту текущего подключения; `enforceAcl` включает дополнительную проверку ACL — списков доступа на уровне отдельных сущностей.
- **Уборка.** После прогона схема удалена командой `DROP SCHEMA … CASCADE`.

## P1 — cross-tenant shadowing через `create()` с чужим id

Находка: R1 (SEC-01/F2) + SEC-02.

### Что проверяли

Гипотеза: арендатор B, зная id сущности арендатора A, может вызвать `Класс(idA).create()` и «перехватить» эту сущность. Такой приём называется cross-tenant shadowing — «затенение» между арендаторами: новая версия с чужим `account` перекрывает старую в выборке последнего состояния. Ожидаемые по анализу кода последствия: A перестаёт видеть свою сущность; B читает всю её историю через `.versions()`; каскадное удаление от B помечает данные A удалёнными. Удаление в letopis — это tombstone: хранилище append-only (данные не меняются на месте, только добавляются новые версии), поэтому вместо стирания строки записывается версия-пометка «удалено».

Бытовой пример. Два салона красоты, A и B, работают в одной установке letopis как разные арендаторы. У салона A есть организация (`Org`) и папка (`Folder`) внутри неё. Если администратор салона B узнает id организации A и вызовет `Org(idA).create({ name: '...' })`, то салон A перестанет видеть собственную организацию и папку, салон B увидит историю организации A вместе с её исходными данными, а удаление «своей» организации со стороны B пометит удалённой и папку салона A.

### Как проверяли

1. Создали два аккаунта — A (`f2efde63-…`) и B (`bff0067d-…`) — через `sys.accounts.set()` и получили два подключения: `tA = db.as(A)` и `tB = db.as(B)`.
2. От имени A создали `Org` с id `01a0d3c5-6588-7ce9-a911-beaed783a855` (`account=A`, `name=org-A`) и вложенную в неё `Folder` с id `01a0d3c5-65b3-…`.
3. Убедились, что B до «атаки» не видит `Org` арендатора A.
4. От имени B вызвали `tB.Org(orgA.id).create({ name: 'hijacked-by-B' })`.
5. Проверили, что видит A: свою `Org` по id и свою `Folder` через цепочку `Org → Folder`.
6. Проверили, что видит B: `Org` по id и её `.versions()`.
7. От имени B выполнили `delete()` — сначала превью без подтверждения, затем с `{ confirm: true }`.
8. Проверили состояние `Folder` арендатора A обычным чтением и через `.withDeleted()` (чтение с учётом удалённых версий).

### Что получили

```
=== P1: cross-tenant shadowing через create() с чужим id ===
P1: A created Org 01a0d3c5-6588-7ce9-a911-beaed783a855 (account=A) + Folder 01a0d3c5-65b3-…
P1: B sees A's Org before attack: 0 rows
P1: B .Org(idA).create() → 1 row(s), account=B, name=hijacked-by-B
P1: A now sees own Org by id: 0 rows  ← СУЩНОСТЬ ИСЧЕЗЛА ДЛЯ A
P1: A sees own Folder via Org chain: 0 rows
P1: B sees Org by id: 1 rows, name=hijacked-by-B
P1: B .versions() on that id: 2 rows, accounts=[A,B] names=[org-A,hijacked-by-B]  ← B ЧИТАЕТ ИСТОРИЮ A
P1: B delete() preview closure: 2 rows, of A: 1
P1: B delete({confirm}) → 2 rows tombstoned, of A: 1
P1: A's Folder alive after B's cascade: 0 rows; withDeleted: 1  ← ДАННЫЕ A ЗАТОМБСТОУНЕНЫ АРЕНДАТОРОМ B
```

### Что это значит

Изоляция арендаторов нарушается штатным API. Под конфигурацией по умолчанию (`enforceAccount:true`, ACL выключен) арендатор B, зная id сущности A, одним вызовом `create()` вставил новую версию с `account=B`. Дальше всё пошло по сценарию гипотезы. A получает пустой результат `[]` и по своему id, и по цепочке `Org → Folder`. B видит «свою» сущность. `.versions()` у B возвращает обе версии, включая строку с `account=A` и её данными (`name=org-A`). Превью удаления у B показало замыкание из двух строк (замыкание — полный набор сущностей, которые каскад затронет), и одна из них — `Folder` арендатора A; подтверждённый `delete()` пометил удалёнными обе. После каскада `tA.Folder(id).rows()` возвращает 0 строк, а `.withDeleted().rows()` — 1: последняя версия `Folder` арендатора A стала tombstone по инициативе B.

Механика ровно та, что описана в статическом анализе. Последняя версия сущности выбирается конструкцией `DISTINCT ON` (она оставляет одну строку на id) по всем строкам без учёта арендатора, и только потом применяется фильтр по `account`; поэтому версия B «затеняет» версию A (`lib/src/sql.ts:689-695`, `lib/src/sql.ts:787-792`). Проверка существования сущности перед записью (probe) выполняется только при включённом ACL-предикате (`lib/src/write.ts:512-524`). Join для `.versions()` не ограничен по account (`lib/src/sql.ts:885`). Каскад удаления в триггере `entity_delete` тоже не учитывает account (`lib/sql/ddl.sql:357-360`).

Замечание о предусловии: B должен знать id сущности A. Для идентификаторов v4/v7 (случайных или основанных на времени UUID) это либо IDOR (Insecure Direct Object Reference — доступ к чужому объекту по известному идентификатору), либо утечка через `watch()` — механизм подписки на изменения, чей payload не содержит account (`lib/sql/ddl.sql:563-565`). Для идентификаторов v5, которые детерминированно вычисляются из пользовательских полей, id можно вычислить из самих данных: namespace не включает account, то есть в идентификаторе нет привязки к арендатору (`lib/src/write.ts:417`).

## P2 — `.deep()` под `enforceAccount:true` (дефолт)

Находка: R4 (SEC-13).

### Что проверяли

Гипотеза: `.deep()` — рекурсивный обход вложенных сущностей на любую глубину (например, все подпапки папки, включая подпапки подпапок) — под конфигурацией по умолчанию (`enforceAccount:true`) падает с ошибкой PostgreSQL. Причина по анализу кода: в SQL-запрос добавляется плейсхолдер для account (позиционный параметр вида `$N`), который в тексте запроса нигде не используется; PostgreSQL не может вывести тип такого параметра и отвечает ошибкой.

Бытовой пример. Салон A хранит документы в дереве папок. Запрос «покажи все вложенные папки на любую глубину» через `.deep()` в конфигурации по умолчанию не возвращает ни результат, ни пустой список — он падает с исключением базы данных. Работает он только после отключения фильтрации по арендатору, то есть при отступлении от конфигурации, описанной в документации.

### Как проверяли

1. От имени A создали корневую папку `root` и дерево вложенных папок под ней.
2. Под конфигурацией по умолчанию вызвали `tA.Folder(root.id).Folder().deep().rows()`.
3. Контрольный прогон: тот же вызов на подключении с `enforceAccount:false`.

### Что получили

```
=== P2: .deep() под enforceAccount:true (дефолт) ===
P2: deep() with enforceAccount THREW: could not determine data type of parameter $5
P2 control (enforceAccount:false): 3 rows: a@1, a1@2, b@1
```

### Что это значит

`.deep()` не работает под конфигурацией по умолчанию. PostgreSQL отвечает ошибкой `could not determine data type of parameter $5`. Плейсхолдер для account аллоцируется в общей части построителя запросов (`lib/src/sql.ts:689-691`), а блок deep собирает SQL без `innerWhere` и `finalFrags` — фрагментов, куда этот плейсхолдер должен был попасть (`lib/src/sql.ts:795-821`). Контрольный прогон с `enforceAccount:false` отдаёт корректные 3 строки с полем `$depth` (глубина вложенности): папки `a` и `b` на глубине 1, `a1` на глубине 2.

Почему регрессию не поймали тесты: все тесты `deep` в репозитории идут с `enforceAccount:false`, а значение по умолчанию `enforceAccount:true` появилось в 0.20.0. Поведение здесь fail-closed — при сбое система выдаёт ошибку, а не утечку данных, — но функция недоступна тем, кто следует документации.

## P3 — два конкурентных `update()` от одной версии

Находка: R3 (F3).

### Что проверяли

Гипотеза: если два `update()` одной сущности выполняются одновременно и оба стартуют от одной и той же версии, один из патчей теряется. Это lost update — ситуация, когда одно из двух одновременных обновлений молча теряется. Защитой от неё служит compare-and-set — проверка перед записью, что версия, от которой стартовало обновление, всё ещё последняя; по анализу кода такой проверки в letopis нет.

Бытовой пример. Два администратора салона A одновременно правят карточку одной организации: первый меняет адрес (`address: 'a1'`), второй — телефон (`phone: 'p1'`). Обоим система сообщает об успехе. Но в актуальной карточке остаётся только новый адрес, а телефон — прежний `p0`: правка второго администратора пропала без какого-либо предупреждения.

### Как проверяли

1. От имени A создали `Org` с исходным телефоном `p0`.
2. Одновременно запустили два `update()` от одной версии: `Promise.all([tA.Org(x.id).update({ address: 'a1' }).rows(), tA.Org(x.id).update({ phone: 'p1' }).rows()])`.
3. Прочитали последнее состояние (`address`, `phone`) и число версий сущности.
4. Повторили сценарий 20 раз и посчитали среднее число версий на сущность.

### Что получили

```
=== P3: два конкурентных update() от одной версии ===
P3[0]: latest address=a1 phone=p1 versions=3 OK
P3[1]: latest address=a1 phone=p0 versions=3 ← LOST UPDATE
P3[2]: latest address=a1 phone=p0 versions=3 ← LOST UPDATE
… (полный список в probes.out.txt)
P3: lost updates 19/20; avg versions per entity 3.00 (expected 3 = create + 2 updates)
```

### Что это значит

Lost update воспроизводится в 19 попытках из 20. Каждая пара конкурентных `update()` вставляет по одной версии — на сущность приходится ровно 3 версии (создание плюс два обновления), то есть обе записи «успешны». Но итоговое последнее состояние содержит только один из двух патчей. Механика такая: `versionRows` читает последнюю версию, накладывает патч через `deepMerge` (рекурсивное слияние объектов) и вставляет результат новой версией (`lib/src/write.ts:421-445`). Значение `prevUpdated` используется только для монотонности `updated` — чтобы метка времени новой версии была строго больше предыдущей (`lib/src/sql.ts:922-932`); проверки «latest не изменился с момента чтения» нет. Оба обновления читают одну и ту же исходную версию, и тот, кто вставил вторым, затирает патч первого. В единственной удачной попытке (P3[0]) второй `update()` успел прочитать latest уже после вставки первого. История честно показывает обе версии, но актуальное состояние получено с молчаливой потерей данных.

## P4 — `drop_chunks` и неизменявшаяся сущность

Находка: R2 (F1).

### Что проверяли

Гипотеза: retention-политика уничтожает не только историю, но и актуальное состояние. Retention-политика — это автоматическое удаление старых chunk'ов TimescaleDB по возрасту; chunk — физический фрагмент hypertable (таблицы, которую TimescaleDB автоматически разбивает по времени). Внутри политики работает функция `drop_chunks`, которая удаляет все chunk'и старше заданного интервала. Если у сущности единственная версия старше порога — она давно создана и с тех пор не менялась, — эта версия исчезает вместе с chunk'ом, а с ней и сама сущность.

Бытовой пример. Салон A завёл свою организацию три года назад и с тех пор ни разу не менял её карточку — данные актуальны, просто стабильны. Администратор включает retention-политику «хранить два года», ожидая, что база забудет только старые правки. Вместо этого организация исчезает целиком: у неё не было версий моложе двух лет, и под «удаление истории» попало её текущее состояние.

### Как проверяли

1. Вставили напрямую SQL-ом в таблицу `"v1.auditprobe"."Entity"` единственную живую (не удалённую) версию `Org` с id `4ba4a3cd-…` и `updated = now() - interval '3 years'`.
2. Проверили через API, что сущность видна.
3. Посчитали chunk'и hypertable и вызвали `SELECT drop_chunks('"v1.auditprobe"."Entity"', INTERVAL '2 years')` — ровно то, что делает retention-политика с порогом два года.
4. Снова проверили видимость сущности через API и посчитали физические строки с этим id в таблице.

### Что получили

```
=== P4: drop_chunks и неизменявшаяся сущность ===
P4: inserted Org 4ba4a3cd-… with updated = now()-3y (единственная версия, живая)
P4: visible before drop_chunks: 1 rows
P4: chunks before=2; drop_chunks(older_than 2y) dropped: _timescaledb_internal._hyper_1004_2202_chunk
P4: visible after drop_chunks: 0 rows  ← АКТУАЛЬНОЕ СОСТОЯНИЕ ПОТЕРЯНО
P4: physical rows left for that id: 0
```

### Что это значит

Retention уничтожает актуальное состояние. Единственная живая строка сущности с `updated = now()-3y` ушла вместе с chunk'ом `_timescaledb_internal._hyper_1004_2202_chunk` при `drop_chunks(older_than 2 years)`. Это ровно та операция, которую регистрирует `add_retention_policy` из `db/policies.mjs`. Физических строк с этим id не осталось, чтение через API возвращает пустой результат. Документация (README §10.8, `policies.mjs:71`) говорит о потере «истории», а не текущего состояния сущностей, которые давно не менялись; то есть контракт, описанный в документации, не совпадает с фактическим поведением.

## Воспроизведение

Скрипт проб сохранён в scratchpad сессии под именем `probes.mts`; в репозиторий он не добавлялся. Последовательность действий скрипта:

1. `up({dsn, schema:'auditprobe', version:1, fresh:true})` — создание одноразовой схемы.
2. Два аккаунта через `sys.accounts.set()`.
3. Два подключения: `db.as(A)` и `db.as(B)`.
4. Сценарии P1–P4 на классах `Org`/`Folder` демо-домена.
5. `DROP SCHEMA` — удаление схемы.

Запуск: `cd lib && node_modules/.bin/tsx <путь>/probes.mts`. Требуется Docker: контейнер `letopis-timescale` поднимается вызовом `up()`.

Ключевые вызовы:

```ts
// P1
const [orgA] = await tA.Org().create({ name: 'org-A' }).rows();
await tB.Org(orgA.id).create({ name: 'hijacked-by-B' }).rows();   // проходит
await tA.Org(orgA.id).rows();                                      // []
await tB.Org(orgA.id).versions();                                  // версии A и B
await tB.Org(orgA.id).delete({ confirm: true }).rows();            // каскад по данным A
// P2
await tA.Folder(root.id).Folder().deep().rows();                   // PG: could not determine data type of parameter $5
// P3
await Promise.all([tA.Org(x.id).update({ address: 'a1' }).rows(), tA.Org(x.id).update({ phone: 'p1' }).rows()]);
// P4
INSERT INTO "v1.auditprobe"."Entity"(…, updated, …) VALUES (…, now() - interval '3 years', …);
SELECT drop_chunks('"v1.auditprobe"."Entity"', INTERVAL '2 years');
```
