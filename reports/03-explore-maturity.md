# 03 — Дайджест зрелости, позиционирования и ограничений `letopis`

> Отчёт 03 — «Дайджест зрелости, позиционирования и ограничений `letopis`». Дата: 2026-09-24. Пакет: `letopis` 0.21.0 (ветка `dev`, HEAD `99a28e0`).
> Читаемая версия; исходный текст субагента без правок — в `reports/raw/03-explore-maturity.md`.
> Метод исходника: read-only исследование репозитория `C:\projects\letopis` субагентом Explore (модель Sonnet). Все числа проверены грепом и подсчётом на момент дайджеста (2026-09-24); репозиторий на ветке `dev`, версия пакета — `0.21.0`. Статус: источник для `reports/ASSESSMENT.md`.

**Как читать.** `letopis` — темпоральное append-only хранилище сущностей поверх PostgreSQL 17 и TimescaleDB. «Append-only» означает, что строки никогда не изменяются на месте: каждое изменение сущности записывается новой строкой-версией, а прежние строки остаются как история. «Темпоральное» — что можно запросить состояние данных на любой момент в прошлом. Этот дайджест собирает факты о зрелости проекта: что заявляет его документация (разделы 1–5 и 14), как устроены тесты, бенчмарки, CI и публикация (6–9), какие есть сигналы по безопасности и эксплуатации (10–11), что говорят история git и известные ограничения (12–13). Итоговые наблюдения — в конце.

### BACKLOG.md

`BACKLOG.md` (27KB) состоит из двух разделов.

Первый раздел — «Порт letopis на Python» (статус: идея/research, 2026-07-13). Это детальный дизайн-документ порта; по оценке автора, ≈80% ценности живёт в SQL/PL-pgSQL и переносится дословно. Работа не начата.

Второй раздел — «Цена повторного наката `ddl.sql` (upgrade: true)» (статус: **«разобрано, замерено, не сделано»**, 2026-07-31). Это реальный, известный автору технический долг с цифрами. Речь о файле `lib/sql/ddl.sql` — определении схемы хранилища (DDL), которое движок повторно накатывает на базу при запуске с опцией `upgrade`. Дефект в том, что при каждом накате файл выполняет `DROP CONSTRAINT` и затем `ADD CONSTRAINT FOREIGN KEY` для двух внешних ключей (FK) без модификатора `NOT VALID`. Без `NOT VALID` PostgreSQL проверяет ограничение на всех существующих строках, то есть сканирует всю таблицу `Entity` — здесь дважды. На время операции накат удерживает `AccessExclusiveLock` (самую строгую блокировку PostgreSQL, запрещающую даже чтение) на таблице и на каждом chunk'е. Chunk — физическая партиция hypertable (таблицы TimescaleDB, автоматически разбитой по времени) за интервал времени.

Замер сделан на полигоне `v1.salondemo` (980 328 строк, 13 chunk'ов, 954 МБ). Текущий полный накат `upgrade` занимает **10.3–11.2 с** end-to-end, из них FK ≈0.70 с, а **`ANALYZE Entity` — 12.8 с (доминирующая статья расхода)**. `ANALYZE` — сбор статистики таблицы для планировщика запросов. Дайджест приводит обе цифры именно так и не поясняет, почему `ANALYZE` превышает полное время наката. Предложенный guard-фикс ускоряет только FK-часть (0.82→0.154 с, ×5.2), но снимает **всего 6% стоимости upgrade** в целом. Поэтому вывод автора бэклога «Повторный накат становится бесплатным» — **неверен**. Решение отложено; зафиксирован план работ: тест на `oid` FK в `lib/test/up.test.ts` и требование пройти через `codescribe-update`, так как файлы `lib/sql/*.sql` — governed (находятся под управлением документационной методологии codescribe; см. §13).

Пояснения к терминам таблицы: link-концы — стороны связи между сущностями; pivot — промежуточная сущность-связка; TOTP/OTP — одноразовые пароли (по времени и по коду); LISTEN/NOTIFY — встроенный механизм PostgreSQL для рассылки уведомлений подписчикам; батч — несколько операций записи одним вызовом.

**NonGoals.** Документ фиксирует четыре явных «не-цели», дословно (`docs/requirements.xml:145-148`):
1. «Not a code-first ORM: class definitions live in the DB Schema table, not as TS classes; there are no code migrations.»
2. «No arbitrary-SQL query builder beyond the chain DSL and the fixed auth/authz table APIs.»
3. «No admin UI for ACL — authorization is rule/weight based and configured as data.»
4. «Dev Redis sessions are ephemeral (no persistence/password in the dev container).»

**Constraints.** Ограничений четыре. Первое: обязателен PostgreSQL 17 с TimescaleDB (таблица `Entity` — hypertable) плюс Redis для сессий. Второе: только ESM (модульная система ECMAScript, без CommonJS), Node 20+, режим разрешения модулей NodeNext. Третье: колонка `Entity.account` объявлена `NOT NULL` — каждая запись требует аккаунт. Четвёртое: функция `up()` требует Docker, если строка подключения (dsn) не указывает на уже работающий PostgreSQL.

**Risks.** Рисков пять, дословно (`docs/requirements.xml:159-163`). Идентификаторы вида `M-DDL`, `M-WRITE`, `M-ACL` — это модули из графа знаний проекта (см. §5):
1. «Invariant duplication: entity validation and link-end rules live both in M-DDL triggers and in M-WRITE.validate — they can drift.»
2. «ACL (M-ACL) concentrates authorization logic and is compiled into a memoized per-connection enforcer, so a wrong rule/weight silently widens access…»
3. «Type-level import cycle M-SQL↔M-ACL↔M-TABLES and runtime ESM cycle M-CONNECT↔M-UP constrain refactoring.»
4. «Logic concentration in chain.ts / sql.ts / write.ts — most of the engine lives in three files, raising regression surface.»
5. «The demo booking schema is seeded by hand (lib/sql/seed.booking.sql) and is the source of truth for its classes, so a hand edit can silently diverge from the docs…»

**ResolvedQuestions.** Отдельно три записи `ResolvedQuestions` фиксируют осознанные архитектурные решения владельца по безопасности. `enforceAccount` — принудительная фильтрация всех операций по аккаунту-арендатору вызывающего — включён по умолчанию (`true`): изоляция тенанта обязательна. `enforceAcl` — применение правил ACL к чтению и записи — остаётся `false`, то есть включается явно (opt-in). Обоснование дословно: «Instead of inverting the default, connect() prints one warning per process… a noisy absence of authorization beats a quiet one.»

## 3. docs/technology.xml — рантайм, зависимости, наблюдаемость, поставка

**Рантайм и зависимости.** Node 20.x+, ESM/NodeNext, TypeScript 5.7.x в режиме `strict`. Фреймворков нет — это standalone-библиотека. **Рантайм-зависимостей две:** `postgres@^3.4.5` (драйвер porsager/postgres, он же postgres.js) и `fastest-validator@^1.19.0` (валидатор данных по схеме). Dev-зависимости: `typescript`, `tsx`, `@types/node` и `ioredis` (только для тестов и демо, в ядро не входит). Версионные ограничения жёсткие: PostgreSQL строго **17** (не диапазон), TimescaleDB — образ `latest-pg17`.

**Наблюдаемость.** Задокументирована как `<logger>none (no structured logger dependency)</logger>`: структурного логгера нет, используются только `console.log`/`console.warn` и хук `onQuery(QueryEvent)` — функция обратного вызова, которую приложение может подписать на каждый запрос. Явная политика редакции: пароли, API-секреты, TOTP-секреты, OTP-коды и токены сессий никогда не логируются в открытом виде.

**Тестирование.** Политика моков: `<mocking-policy>Integration-first… no in-process DB mocks.</mocking-policy>`. Важная оговорка самого документа: **`<test-scope-note>lib/test/** is OUTSIDE the documented scope: test files are referenced by path and by the npm test command only; their contents were not read or analyzed.</test-scope-note>`**. То есть официальный документационный слой сознательно не верифицировал содержимое тестов; их содержимое проверено отдельно в §6 этого дайджеста.

**Поставка.** npm-пакет `letopis`; публикуемые файлы — `dist/ scripts/ sql/ docker/ README.md CHANGELOG.md`; бандлер не используется.

## 5. docs/knowledge-graph.xml — граф модулей

Граф знаний описывает **23 модуля**, сгруппированных в 6 слоёв. В порядке от фундамента к инструментам:
- Layer 0, foundation: `M-TYPES`, `M-UUID`, `M-SESSIONS` — без внутренних зависимостей.
- Layer 1: `M-OPS`, `M-SCHEMA`.
- Auth/authz: `M-TABLES`, `M-ACL`, `M-AUTH`.
- Query/write engine: `M-SQL`, `M-WRITE`, `M-TX`.
- Public API: `M-CHAIN` — самый связанный узел, 8 зависимостей (TYPES/SQL/WRITE/TX/TABLES/AUTH/ACL/SCHEMA); `M-CONNECT`, `M-UP`.
- Storage engine SQL: `M-DDL`, `M-SEED-AUTH`, `M-SEED-BOOKING`.
- Tooling: `M-GEN-TYPES`, `M-SCHEMA-SYNC`, `M-GEN-API-CONTRACT`, `M-RELEASE-NOTES`, `M-CHECK-DOCS`, `M-DOCKER`.

Явно задокументированы два цикла зависимостей: на уровне типов `M-SQL↔M-ACL↔M-TABLES` и на уровне рантайма ESM `M-CONNECT↔M-UP`. Второй безопасен благодаря live bindings ESM (импортированные значения разрешаются при обращении, а не в момент импорта), но ограничивает рефакторинг — см. риск 3 в §2. `M-DDL` (файл `lib/sql/ddl.sql`) — движок хранения; его список зависимостей — `none`, однако он связан шестью CrossLink типа `runtime data-contract` с модулями, которые читают и пишут таблицы Entity/Schema напрямую через SQL.

Все 23 модуля имеют `STATUS="implemented"` — нет ни одного `planned` или `in-progress`. Для solo-проекта это необычно завершённо на уровне заявленной архитектуры.

## 10. Сигналы безопасности

**Пароли.** Хэширование — `scrypt` из `node:crypto`, без внешних зависимостей. Scrypt — функция получения ключа с настраиваемой стоимостью по памяти и времени, затрудняющая перебор. Параметры заданы в `lib/src/auth.ts:45`: `{ N: 32768, r: 8, p: 1, maxmem: 64*1024*1024 }`, `KEYLEN=32`; комментарий в коде — «OWASP-порядок стойкости». Формат хранения: `scrypt$N$r$p$saltB64$hashB64`, случайная соль на каждый пароль.

**Timing-safety.** Для всех сравнений хэшей используется `timingSafeEqual` из `node:crypto` — сравнение за постоянное время, не зависящее от того, в каком байте строки расходятся (`lib/src/auth.ts:78,89,95`). Если учётной записи нет, выполняется `dummyVerify` — холостой scrypt, чтобы время ответа не выдавало, существует ли пользователь; это защита от user-enumeration через тайминг (`lib/src/auth.ts:83`).

**Токены и ключи.** API-ключ формата `lts_<48hex>` выдаётся один раз, в БД хранится только его `sha256`. В схеме key+secret секрет также хранится только как sha256. OTP-код — sha256 плюс TTL плюс счётчик попыток (`maxAttempts`, дефолт **5**; `lib/src/auth.ts:238,469-470`), после превышения код сжигается. В коде есть явный дисклеймер (`lib/src/auth.ts:6`): «OAuth-танец, rate-limit, lockout — на приложении: здесь хранение и проверка». То есть **сетевого rate-limiting или lockout на уровне библиотеки нет** — только счётчик попыток OTP.

**SQL injection.** Запросы параметризуются через tagged-template драйвера `postgres` (шаблонные строки, в которых подстановки автоматически становятся параметрами) либо через `sql.unsafe(text, params)` с позиционными `$1…$N` (`lib/src/sql.ts:148`). Идентификаторы (имена схем и таблиц) экранируются отдельной функцией `escId`: `` `"${s.replace(/"/g, '""')}"` `` — двойные кавычки вокруг и удвоение внутренних кавычек (`lib/src/sql.ts:232`); для литералов есть `escLit` (`:233`). Прямых конкатенаций пользовательских значений в SQL-текст в проверенных местах не обнаружено.

**Сессии.** Токен хранится в Redis только как `sha256`-ключ (`sess:*`), TTL обязателен; `revokeAll` чистит все сессии аккаунта. В `docs/verification-plan.xml` (`GlobalPolicy/redaction`) есть явное требование не логировать секреты и токены.

**Секреты в репозитории.** В корне присутствует файл **`.env`** (3158 байт), но он **не отслеживается git**: `git ls-files` его не находит, `.env` есть в `.gitignore`. По содержанию файл принадлежит другому проекту на этой же машине (Nuxt/SaaS-инфраструктура — Cloudflare, YooKassa, VPS SSH и т.д.) и с letopis не связан. Файла-примера `.env.example`/`.env.sample` для самого letopis в репозитории нет; README упоминает только переопределение через переменные окружения `ENTITY_DSN`/`ENTITY_REDIS`. Отдельный операционный риск касается не letopis, а гигиены рабочей директории: `.env` лежит рядом с репозиторием и содержит незамаскированные учётные данные в комментариях — стоит убедиться, что он не будет случайно подхвачен при упаковке или архивации.

**Зависимости.** Две рантайм-зависимости, 44 пакета в lock-дереве. Признаков `npm audit` в CI не найдено — шага audit в `ci.yml` нет.

## 11. Observability / Ops

**Логирование.** Структурного логгера нет (`docs/technology.xml`: `<logger>none</logger>`). Есть только `console.warn`/`console.log` с префиксами `[letopis.up] …` (bootstrap) и `letopis: slow query <ms>ms — <mode> <classes>` (медленные чтения).

**Метрики и хук.** `onQuery(QueryEvent)` — единая точка телеметрии; событие содержит `{mode, classes, ms, rows, slow}`. Хук опционален; без него при превышении порога `slowMs` просто вызывается `console.warn`.

**Health endpoint.** Отсутствует — ожидаемо, поскольку это библиотека, а не сервер.

**Graceful shutdown.** Явных обработчиков `SIGTERM`/`SIGINT`/`process.on` в `lib/src/*.ts` не найдено (греп пуст). Пул закрывается только явным вызовом `db.close()`/`sql.end()`; в `lib/src/up.ts:193,218,293` он используется с `timeout:1` при разовых служебных подключениях.

**Connection pooling.** Пул создаётся как `postgres(opts.dsn, { max: opts.max ?? 10, types: {...} })` (`lib/src/index.ts:90-93`): дефолт — **10** соединений, настраивается через `ConnectOpts.max`. Служебные подключения в `up.ts` используют `max:1, connect_timeout:3`.

**Retries.** Транзиентные ошибки PostgreSQL — `40P01` (deadlock, взаимная блокировка) и `40001` (serialization failure, конфликт сериализации) — повторяются автоматически **до 3 попыток** (`const RETRIES = 3`, `lib/src/sql.ts:116`) с задержкой `40*attempt + random(40)` мс (`:117-118`). Но это работает **только для чтений в автокоммите**: внутри `db.begin()` ретрай невозможен по семантике PostgreSQL (после ошибки транзакция обречена), и ошибка уходит наружу с подсказкой «retry the whole db.begin() block» (README §10.12). `insertOne` отдельно и мгновенно ретраит гонку по `updated` (код 23505 — нарушение уникальности).

**Timeouts.** `waitTimeoutMs` (дефолт 120000 мс) — ожидание готовности контейнера в `up()`; `connect_timeout:3` — на служебных подключениях. Выделенного `statement_timeout`/`query_timeout` (ограничения времени выполнения одного запроса) на уровне клиентских запросов не найдено.

**Slow query hook.** Есть и встроен в единую точку `runQuery` (`lib/src/sql.ts:149-153`): либо `onQuery`, либо `console.warn`; порог задаётся `slowMs`.

**Критичная эксплуатационная оговорка (README §14.1).** После массовой заливки (`COPY`, миграция) обязателен ручной `ANALYZE`. Иначе планировщик берёт дефолтную оценку «200 уникальных id», и деградация достигает **×126** (1371мс→11мс на выборке 100 из 440k) и **×18** (57.6с→3.2с на `count()` под изоляцией тенанта). README называет это «самой дорогой ошибкой эксплуатации из всех, что есть в этом руководстве».

## Итоговые наблюдения для архитектора

**Зрелость продукта и зрелость процесса расходятся.**

Кодовая база («продукт») — честная early-alpha. Аргументы: 45 дней истории; один автор; 9 задокументированных BREAKING-изменений API; ни одного тега или релиза до 0.20.0; известный и не исправленный perf-дефект в `upgrade`-пути (в нём доминирует `ANALYZE` — 12.8с при ~11с всего наката); отсутствие lint-тулинга и dependency-audit в CI; отсутствие выделенных large-data/bulk-тестов (есть только бенчи без assertion).

При этом инженерный процесс («process») необычно строг для этой стадии: 23 модуля с явным графом зависимостей и `STATUS=implemented`; verification-plan с VF-потоками и пробелами покрытия по каждому модулю; CI с чётким разделением dev/main/release и смоук-тестом опубликованного тарбола; `check-docs.mjs` с 7 проверками против дрейфа документации; параметризованный SQL и явное экранирование идентификаторов; scrypt с OWASP-параметрами и timing-safe сравнения.

Сам COMPARISON.md — написанный автором о собственном проекте — приходит к тому же выводу: сильный дизайн, pre-production по совокупности метрик.
