## 1. Резюме

**Что это.** Append-only темпоральное хранилище сущностей поверх PostgreSQL 17 + TimescaleDB: одна hypertable `Entity` хранит все классы домена (строка = версия, tombstone = удаление), схема домена лежит в таблице `Schema` как данные, доступ — через Proxy-цепочки `db.Класс(фильтр).Другой().rows()`, где глаголы записи (`create/update/delete`) являются звеньями того же плана. В комплекте: аутентификация (scrypt/API-key/TOTP/OTP), ACL по правилам с весами, изоляция арендатора по колонке `account`, сессии в Redis, realtime через `LISTEN/NOTIFY`, codegen типов, dev-bootstrap с Docker. Две runtime-зависимости, MIT.

**Для кого.** Solo-разработчик или малая команда (в том числе работающая с LLM-агентами), строящая booking/CRM/каталог-подобный продукт на PostgreSQL, где важны «как было на T», граф связей и минимум инфраструктурного кода. Для этого профиля библиотека даёт заметно больше, чем ORM: история, каскады, идемпотентные id, auth/ACL «из коробки».

**Зрелость.** Pre-production, честно и самим автором (COMPARISON.md: зрелость 1/5). 45 дней истории, один автор, 27 релизов и 9 BREAKING за 6 недель, тесты только против Docker, нет lint/coverage/audit. Инженерный процесс при этом заметно выше среднего для такой стадии: 210 интеграционных тестов, CI со smoke-тестом опубликованного тарбола, гейт против дрейфа документации, слой codescribe для агентов, README на 26 тысяч слов с реальными таймингами.

**Главные риски (подтверждены прогоном, [08]).** (R1) Арендатор B штатным `create()` с чужим id перехватывает сущность арендатора A: A её теряет, B читает историю A через `.versions()`, каскадное удаление от B тумбстоунит данные A. (R2) Retention-политика TimescaleDB физически удаляет единственную строку неизменявшихся сущностей — потеря актуального состояния. (R3) Конкурентные `update()` теряют патчи (19 из 20 в пробе): compare-and-set отсутствует. (R4) `.deep()` под дефолтной конфигурацией падает ошибкой PostgreSQL.

**Вердикт по уровням.** T1 — пригоден (с оговорками: `.deep()` только при `enforceAccount:false`, TimescaleDB избыточен). T2 — не пригоден до закрытия R1/R3/R4/R8/R9/R11. T3 — не пригоден (R2/R5/R6/R12). T4 — не пригоден (R10, отсутствие актора, valid-time, DR-процедур, TSL-лицензия).

**Новизна: 3/5.** Все примитивы известны (triggered history, single-table jsonb с версиями, hash-key Data Vault, пути Gremlin/Cypher, schema-in-DB, ACL-предикаты в WHERE). Ново — композиция и поверхность API: план-цепочка с глаголами-звеньями в одной транзакции, слоты связей, pivot, v5-id как средство идемпотентной брони, purge поверх append-only, no-history классы в той же таблице, встроенные tenancy/auth/ACL в двух зависимостях.

## 2. Что такое letopis

Архитектура в десяти пунктах (детали: [01], [02]).

1. **Хранилище — одна hypertable `Entity`** `(partition, id, class, data jsonb, updated timestamptz, account uuid, tags text[], owner uuid, links jsonb, deleted timestamptz)`, PK `(partition, class, id, updated)`. Все HUB-сущности и LINK-связи всех классов — в ней (`lib/sql/ddl.sql:126-166`). Партиционирование только по времени `updated`, chunk 30 дней, жёстко в DDL (`ddl.sql:151-156`).
2. **Версия = строка.** Актуальная версия — `DISTINCT ON (id) ORDER BY updated DESC`; живая — `deleted IS NULL`. Физического UPDATE нет: триггер `entity_update` отменяет его и вставляет новую версию (`ddl.sql:296-318`); DELETE превращается в tombstone + рекурсивный каскад по `links` (`ddl.sql:336-372`).
3. **Схема — данные.** Таблица `Schema(partition, id, alias, category HUB|LINK, ancestor, attributes, links, meta, order, ancestors[], descendants[])` (`ddl.sql:45-58`); триггер `schema_lineage` считает наследование (`ddl.sql:74-118`). `attributes` — DSL fastest-validator, компилируется в клиенте со `$$strict:true` (`lib/src/schema.ts:255`). Классы правятся `db.schema.define()` + `reloadSchema()` без DDL.
4. **Связи — jsonb-карта `links {Класс: id}`.** HUB несёт контекст (например `{Org: …}`), LINK — все концы. Концы описаны в `Schema.links` v2 (союзы `classes:[…]`, `optional`, `cardinality` зарезервировано и не реализовано — `lib/src/types.ts:81`).
5. **Идентификаторы — три режима**: v4 (случайный), v7 (time-ordered, своя реализация RFC 9562, `lib/src/uuid.ts`), v5 (детерминированный из концов и полей: `uuidv5(pgSchema:partition:class:parts)`, `lib/src/write.ts:397-418`). v5 даёт идемпотентный `create()` и «двойная бронь невозможна по построению».
6. **Чтение — цепочка шагов → SQL.** Каждый шаг — подзапрос «latest по классу», шаги соединены `JOIN LATERAL`; containment-фильтры сначала сужают кандидатов через GIN (`jsonb_path_ops`), затем перепроверяются на актуальной строке (`lib/src/sql.ts:616-913`). Полиморфизм по иерархии классов, `.exact()` его снимает; `.deep()` — `WITH RECURSIVE` только для self-hop; keyset-пагинация; агрегаты; `asOf`/`versions`.
7. **Запись — план.** Глаголы `create/update/delete/purge/anonymize` и слоты `.Класс.set()/unset()` — звенья цепочки; терминал исполняет план одной транзакцией с fan-out по результатам (`lib/src/write.ts:759-818`). Батч склеивает «чистые» create одного класса в multi-VALUES INSERT.
8. **Арендатор — свойство вызова.** `db.as(account, {owner?})` клонирует контекст; `enforceAccount` включён по умолчанию и пришпиливает предикат `account` к каждому шагу (`sql.ts:681-695`). `enforceAcl` — opt-in: правила `Resource/Rule` с весами, deny-by-default, победивший allow может нести row-предикат, который вливается в SQL (`lib/src/acl.ts`).
9. **Auth и сессии.** scrypt-пароли, API-ключи и key+secret (в БД только sha256), TOTP/OTP собственной реализации, связка внешних identity; сессии в инжектируемом Redis-совместимом хранилище с TTL 7 суток (`lib/src/auth.ts`, `lib/src/sessions.ts`).
10. **Инструменты.** `up()` — dev-bootstrap (Docker-контейнер TimescaleDB+Redis, накат `ddl.sql` и сидов, `ANALYZE`, `connect`); `gen-types.mjs` — `.d.ts` из живой схемы; `schema-sync.mjs` — diff/apply схемы с проверкой совместимости; `check-docs.mjs` — CI-гейт против дрейфа документации; `docs/api-contract.json` — машиночитаемый контракт; codescribe-разметка в каждом governed-файле.

## 3. Схема БД и storage-модель

### 3.1 Что гарантирует БД, а что — клиент

| Инвариант | Где обеспечивается | Комментарий |
|---|---|---|
| Класс существует и не abstract; ключи `links` — реальные классы; концы LINK по `Schema.links` | триггер `entity_check` (`ddl.sql:189-280`) | Существование **целевой** сущности в `links` не проверяется — висячие и кросс-тенантные ссылки допустимы (`ddl.sql:218-229`, `write.ts:345-346`) |
| Нет физического UPDATE; версия монотонна по `updated` | `entity_update` + `GREATEST(clock_timestamp(), prev+1µs)` в INSERT (`sql.ts:922-932`) | Только transaction-time; valid-time (когда факт стал верен) в модели нет |
| Soft delete + каскад по `links`, защита от циклов | `entity_delete` (advisory lock по ключу сущности, `ddl.sql:336-372`) | Каскад не знает арендатора (`ddl.sql:357-360`) |
| Валидация `data` по `attributes` | **только клиент** (`schema.ts:255`, `write.ts`) | Сырой SQL и второй клиент (Python-порт из BACKLOG) обходят валидацию |
| Принадлежность сущности арендатору | **нигде на уровне БД** | PK без `account`; см. R1 |
| Уникальность бизнес-ключа | **только v5-id** (одно правило на класс) | `create()` по существующему id молча версионирует; второй уникальный ключ невозможен; на изменяемом поле id не пересчитывается (`write.ts:552-570`) |
| Хард-delete | функции `purge`/`purge_account`/`compact` под `SET LOCAL letopis.purge='on'` (`ddl.sql:395-455, 536-545, 641-657`) | Флаг доступен любой роли — append-only «по умолчанию», не по правам |

### 3.2 Индексы и их семантика

`entity_latest_idx (partition, class, id, updated DESC)`, три GIN (`data`, `links` — `jsonb_path_ops`; `tags`), btree по `account` и `owner` (`ddl.sql:160-165`). Ключевой факт: **GIN видит все версии**, а не только актуальные — свойство «latest» не хранится в строке. Поэтому фильтр по мутабельному полю (`{status:'pending'}`) матчит каждую сущность, когда-либо бывшую в этом статусе, и кандидатный набор растёт O(история) [04 F4]. Штатный ответ 0.21.0 — `meta.history:false` (триггер `entity_collapse` физически удаляет старые версии, `ddl.sql:593-624`), то есть отказ от истории для классов, где фильтры по статусу критичны.

### 3.3 Партиционирование и его цена

Hypertable по `updated` с шагом 30 дней. Все обращения идут по `(partition, class, id)` — исключение chunk'ов по времени невозможно, каждая индексная проба и каждый `JOIN LATERAL` обходят все chunk'и. README §14 честно даёт модель стоимости «строки внешнего шага × число chunk'ов» и измеренные 30 с на обход от широкого класса при 13 chunk'ах и 980k строк. Через три года эксплуатации chunk'ов 36 — стоимость всех чтений растёт линейно с возрастом базы, а не с полезным объёмом [04 F5]. Hash-размерности отвергнуты по замеру (`bench/dimensions.bench.mjs`): они ускоряют точечный доступ несущественно и замедляют цепочки в разы. Итог: для T1/T2 без compression/retention обычная таблица с теми же индексами была бы строго быстрее — TimescaleDB здесь не даёт ничего, кроме операционной зависимости.

### 3.4 Compression и retention

Обе политики выключены по умолчанию, включаются `db/policies.mjs` (TSL-функции, см. §6.3). Compression с `segmentby (partition, class, id)` даёт локальность версий одной сущности; но на сжатых chunk'ах нет GIN — containment-фильтры и обратные переходы по `links` декомпрессируют сегменты, README обещает «прозрачность» без замера [04 F6, 07 #14]. **Retention удаляет chunk целиком**: единственная строка сущности, не менявшейся дольше горизонта retention, исчезает вместе с актуальным состоянием — подтверждено пробой P4 ([08]): `drop_chunks(older_than 2 years)` → сущность не читается, физических строк 0. Документация говорит только об «истории» (README §10.8, `policies.mjs:71`).

### 3.5 Эволюция схемы

Аддитивные правки `ddl.sql` — через `up({upgrade:true})`/`apply.mjs --upgrade`, метка `DDL_REVISION` в `COMMENT ON SCHEMA` (`ddl.sql:670`), при расхождении `connect()` только предупреждает. Накат идёт одной транзакцией `sql.unsafe(text)` и берёт `AccessExclusiveLock` на hypertable и каждый chunk; FK пересоздаются без `NOT VALID` (BACKLOG.md: 10–11 с на 1M строк, доминирует `ANALYZE` 12.8 с) [04 F7]. Ломающие изменения структуры = новая PG-схема `v2.<name>` и перенос «силами приложения»; migration ledger и down-миграций нет. На уровне `Schema`: добавить атрибут — да (`optional`/`default`, `schema-sync` проверяет 200 latest-строк); удалить/переименовать атрибут — практически нет (`$$strict` + deepMerge не удаляет ключи → существующие сущности становятся необновляемыми, [06 A]); переименовать класс — нет (FK `ON UPDATE CASCADE` упирается в `entity_update`, ключи `links` не переименовываются). `Schema` не темпоральна: «как выглядела схема на T» не восстановить, `asOf` кастует старые данные текущими типами.

### 3.6 Модель конкурентности

- `updated = GREATEST(clock_timestamp(), prev+1µs)` — гарантия монотонности, не compare-and-set. `update()` = прочитать latest → deepMerge → INSERT (`write.ts:421-445`): два писателя от одной версии дают две успешные версии, latest — поздняя, патч первого частично теряется. Проба P3: **19 из 20** пар конкурентных `update()` потеряли один из патчей ([08]).
- Единственный CAS — ручной `tr.lock(...)` (advisory lock, `lib/src/tx.ts`) внутри `db.begin()`; рецепт в README §7 оформлен для двойной брони, не для «любого update».
- Изоляция транзакций — READ COMMITTED по умолчанию, `SET TRANSACTION`/savepoint в API нет. Ретрай 40P01/40001 ×3 только вне пользовательской транзакции; ретрай 23505 в `insertOne` из публичного API фактически недостижим (`write.ts:208` vs `inTransaction`) [04 F9].
- `entity_collapse` берёт advisory lock после INSERT, а `updated` вычислен до — при инверсии порядка временно две строки на id [04 F11].

## 4. Методология использования

### 4.1 Ментальная модель

Пять правил, которые нужно принять до проектирования: (1) строка = версия, сущность = все строки с одним `(class, id)`; (2) класс = строка `Schema`, а не TS-класс, — схема живёт в БД и перечитывается `reloadSchema()`; (3) HUB — узел, LINK — ребро с атрибутами; LINK ссылается только на HUB (`LINK → LINK` запрещён, `sql.ts:544`); (4) путь — закон и для чтения, и для записи: `create()` в конце цепочки получает концы из пройденных шагов; (5) арендатор — свойство вызова (`db.as`), все чтения/записи под ним пришпилены.

### 4.2 Проектирование домена — что выражается

| Потребность | Поддержка | Как / почему нет |
|---|---|---|
| Сущности с вложенными объектами, enum, record, defaults | да | fastest-validator DSL в `attributes` |
| Наследование полей и полиморфные выборки | да | `ancestor`; чтение по родителю включает потомков, `.exact()` для точного класса. Наследование ради переиспользования полей (`booking ⊂ slot`) смешивается с is-a — задокументированная ловушка (CHEATSHEET #9) |
| M:N и n-арные связи с атрибутами | да | LINK с 2…5 концами, союзы ролей, `optional` |
| Связь на связь (платёж → бронь) | **нет** | концы LINK только HUB → реифицированные отношения приходится делать HUB-ами, теряя v5 «из концов» [06 A] |
| Кардинальность | **нет** | `cardinality` принимается, не проверяется |
| Уникальность | частично | только v5-id из неизменяемых полей/концов; повтор → новая версия, не ошибка |
| Обязательный контекст HUB (Staff → Org) | **нет** | объявленный конец HUB-а не проверяется, `write.ts:138` |
| Ссылочная целостность значений `links` | **нет** | проверяется только класс ключа |
| Деревья | да, вниз | `.deep()` только self-hop вниз; вверх к корню — итерации |
| Вычисляемые поля, хуки, view | нет | всё в приложении |
| Кросс-сущностные инварианты (наложение интервалов) | приложение | EXCLUDE на hypertable невозможен; рецепт — `tr.lock()` + перечитка |
| Деньги/точность | осторожно | jsonb numeric, но `sum/avg` → `Number` (double); конвенции минорных единиц нет |
| FTS, geo, бинарные данные | нет | только `LIKE/ILIKE` без trigram, jsonb (TOAST >2 КБ) |
| Удалить поле из `data` | **нет** | deepMerge пропускает `undefined`, `null` — значение |
| Кириллические alias | да | `id`/`alias` равноправны; переносимость в иноязычную команду страдает |

### 4.3 Правила, которые не написаны в README, но следуют из кода

1. **v5 только на неизменяемых `from`.** `update()` не пересчитывает id → после смены поля-источника инвариант уникальности нарушен (`write.ts:552-570`). Даты в `from` берутся сырой строкой до нормализации: `10:00+03:00` и `07:00Z` — два разных id одного момента [06 A].
2. **В `from` v5 всегда должен быть tenant-scoped конец** (Org, Staff…), иначе id вычислим из пользовательских данных другого арендатора (namespace без account, `write.ts:417`).
3. **Всё, к чему будут цепляться связи, — HUB.** LINK нельзя сделать концом.
4. **`optional` вместо cardinality; «ровно один» ≠ «не более N».**
5. **`.exact()` там, где наследование — переиспользование полей, а не is-a.**
6. **`count()` считает пути, не сущности** (CHEATSHEET #13); полиморфный `count()` в 20 раз дороже точного (README §14).
7. **OR только на уровне всего фильтра шага и без GIN-кандидатов** (`sql.ts:426-435`) — полный `DISTINCT ON` по классу.
8. **Цепочку начинать с селективной стороны**: `db.запись(id).Мастер()` — 7.5 мс, `db.Мастер().запись()` в обратную сторону — 30 с (README §14).
9. **ANALYZE после любой массовой заливки** — иначе деградация ×18–×126 (README §14.1).
10. **`.deep()` работает только при `enforceAccount:false`** до исправления R4.

### 4.4 Арендаторы и права

`db.as(req.accountId)` на каждый запрос; `enforceAccount` держать включённым; `enforceAcl:true` + `Resource/Rule` с `$account`-паттернами для row-level предикатов. Принимать как факт: изоляция **клиентская** (RLS в БД нет; `db.sql` и любой SQL-клиент видят всё), а до закрытия R1/R9 — и дырявая штатным API. Admin-фасады (`db.accounts/rules/schema`) доступны на любом scoped-хендле без авторизации — разграничение на приложении.

### 4.5 Жизненный цикл

`seed.sql` или `db.schema.define()` → `up()` (dev) / `db/apply.mjs` (CI, prod-накат) → `schema-sync --apply` в CI с отчётом совместимости → `gen-types` → `TypedDb`-cast → `up({upgrade:true})` при смене `DDL_REVISION` (в проде — в окно обслуживания, см. §6) → `db/policies.mjs` для compression/retention (только после оценки §3.4) → `anonymize()` / `purge({confirm})` / `accounts.purge()` для забвения. Тесты потребителя — только против Docker (TimescaleDB + Redis), in-memory режима нет.

### 4.6 Анти-паттерны

22 «грабли» из AGENT-CHEATSHEET.md ([01 §2]) плюс найденные здесь: v5 на мутабельных полях; удаление атрибута из схемы после накопления данных; `OR` в горячем пути; `count()` по семейству; попытка удалить ключ из `data`; retention при наличии долгоживущих сущностей; `.deep()` под дефолтом; параллельные `update()` одной сущности без `tr.lock()`.

## 5. Рецепты по уровням сложности T1–T4

### T1 — прототип / внутренний инструмент, один арендатор
**Сборка.** `up({schema, version:1, seeds:['./domain.sql']})`; классы через `schema.define()`; один System-аккаунт, `connect({enforceAccount:false})` или один `db.as(sys)`; history по умолчанию; `gen-types` в `postinstall`; миграции — правка `Schema` + `reloadSchema()`.
**Что получаете.** Time-travel (`asOf`, `versions`), граф без JOIN-кода, каскады, идемпотентные id, auth — за один пакет. Тайминги на 980k строк: точечные чтения 4–20 мс, запись 6–25 мс.
**Где предел.** FTS/geo/файлы — внешние сервисы; полные сканы класса — секунды; `.deep()` только без `enforceAccount`.
**Вердикт: адекватен.** Самый сильный уровень для библиотеки. TimescaleDB здесь балласт — для T1 стоило бы иметь режим vanilla PG.

### T2 — SaaS, мультитенантность, auth/ACL
**Сборка.** Тенант = `Account`; `db.as()` на запрос; `enforceAcl:true`; v5 только с tenant-scoped концом; `tr.lock()` вокруг любых конкурентных обновлений; свой мигратор поверх `apply.mjs`; `onQuery` → метрики; ANALYZE по расписанию.
**Что ломается первым.** R1 (перехват id — нарушение изоляции штатным API), R3 (lost update при нескольких инстансах), R4 (`.deep()`), R8 (fail-open ACL-паттерн, отзыв прав без SLA), R9 (`watch()`/каскад без арендатора), R11 (пул без таймаутов), R7 (upgrade = минуты блокировки при росте истории).
**Вердикт: не адекватен сегодня.** Пригоден для booking-подобных доменов после патчей R1/R3/R4/R8/R9/R11 и при принятии клиентской изоляции.

### T3 — потоки событий/статусов, 100M+ строк
**Сборка.** Статус-классы с `meta.history:false`; `db.batch()` (multi-VALUES только для «чистых» create одного класса); `watch()` как best-effort сигнал, не как шина; compression через `policies.mjs`; retention — **нельзя** без ре-дизайна (R2).
**Что ломается.** R2 (retention стирает актуальное), R5 (GIN по истории → или `history:false`, или O(история)), R6 (chunk-налог на каждый read; сжатые chunk'и без GIN), R12 (7 индексов + 3 триггера с lookup `Schema` на строку + NOTIFY per row; батч без COPY, лимит ~8191 строк на INSERT), нет durable-подписок/outbox/CDC, single-writer оценочно 100–150 rps [04 D].
**Вердикт: не адекватен.** letopis не event store и не очередь: нет stream/aggregate-версии, exactly-once, consumer groups. Максимум — умеренные потоки (тысячи событий/мин) с `history:false` и внешней очередью.

### T4 — enterprise / regulated
**Что есть.** Append-only с `versions/asOf`, tombstone-каскады, три уровня забвения (`anonymize` → retention → `purge`), ACL-предикаты в SQL.
**Чего нет.** Актор и tx-id изменения (версия копирует `account/owner` оригинала, `write.ts:437-441`); commit-time (`clock_timestamp`, а не время фиксации — `asOf` не является консистентным снимком транзакции); valid-time/bitemporal; темпоральная `Schema`; tamper-evidence (bypass через GUC `letopis.purge`, `compact`, `DROP TRIGGER`); legal hold; RLS; DR/backup-процедуры для hypertable; LTS/второй мейнтейнер; TSL-лицензия и недоступность на managed PG.
**Вердикт: не адекватен.** Возможное место — «журнал версий» рядом с нормализованной системой записи, при добавлении `actor/tx_id` в собственной `v2`-схеме.

## 6. Масштабируемость и эксплуатация

### 6.1 Модель стоимости чтений
`DISTINCT ON` на каждом шаге × `JOIN LATERAL` × число chunk'ов. Измерено (README §14, полигон `v1.salondemo`, 980 328 строк, 13 chunk'ов): точечные 4–20 мс; `sort().limit()` по классу 5.4 с; обход от широкого класса 30 с (некоррелированный вариант — 561 с); полиморфный `count()` 1.6 с против 82 мс с `.exact()`; без `ANALYZE` — ×18 (57.6 с → 3.2 с) и ×126 (1371 мс → 11 мс). Планирование на точечном чтении уже дороже исполнения (`dimensions.results.json`: 1.67 мс vs 0.57 мс) и растёт с числом chunk'ов. Цифры README дрейфуют вместе с полигоном — сам README фиксирует случай устаревания в 5×.

### 6.2 Модель стоимости записи
На каждую строку: 7 индексов (3 GIN), 3 FK, два триггера с lookup в `Schema`, `pg_notify`. `insert_one` p50 6.2 мс (`dimensions.results.json`). Fast-path батча — только v4/v7-create без слотов; COPY-пути нет; нарезки по лимиту параметров протокола нет.

### 6.3 TimescaleDB как зависимость
Используется ради двух вещей — compression и retention (`policies.mjs`), и обе доступны только в Community Edition под Timescale/Tiger Data License, а не в Apache-2 [07 #3]. `timescaledb` отсутствует в официальном списке расширений Amazon RDS [07 #4], в Azure Flexible Server — только Apache-редакция без этих политик [07 #6]. Dev-контейнер и CI проекта работают на Community 2.19.0 (`timescaledb.license = timescale`) [07 #7]; образ `latest-pg17` не пришпилен; PostgreSQL зафиксирован строго 17. Следствие: на managed PG остаётся «hypertable без выгод», а on-prem — TSL-обязательства.

### 6.4 Транзакции, пул, таймауты
`beginTx` = `reserve()` + голый `BEGIN` (`tx.ts:42-67`); пул `max:10` без acquire-timeout; `statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout`/`ssl` через `ConnectOpts` не пробрасываются (`index.ts:90-93`, `types.ts:293-331`). Утечка `tr` без `rollback` навсегда забирает соединение; PgBouncer transaction-mode несовместим с `LISTEN`/`reserve`.

### 6.5 Наблюдаемость и DR
Единственный сигнал — `onQuery(QueryEvent)` / `slowMs` (`sql.ts:130-169`), служебные запросы не инструментированы; структурного логгера, метрик пула, health, graceful shutdown нет. Backup/PITR/restore для hypertable (`timescaledb_pre_restore` и т.д.) не описаны вовсе [02 §9]. Родитель hypertable не анализируется автовакуумом своевременно — нужен периодический ручной `ANALYZE`.

### 6.6 Потолки по уровням (что ломается первым)
| Уровень | Первый барьер | Далее |
|---|---|---|
| T1 | ANALYZE после заливки; traversal от широкого класса | утечки `tr` |
| T2 | R1, R3, R4, R11 | R7 (upgrade-окно), R6 (chunk-налог), compression без замера R5/R6 |
| T3 | R2 (retention), R5 (GIN по истории) | R12 (пропускная способность записи), collapse-DELETE в холодных chunk'ах |
| T4 | R10 (advisory immutability, нет актора), R2 | R14 (лицензия/облако), нет DR, нет valid-time |

## 7. Безопасность, мультитенантность, соответствие

### 7.1 Модель доверия
Субъект — то, что приложение передало в `db.as(account)`; библиотека не проверяет право приложения назвать этого субъекта и не различает пользователя и приложение (`chain.ts:866-880`). Доверенная граница — процесс приложения. Всё ниже (`db.sql`, admin-фасады) — плоскость без авторизации.

### 7.2 Изоляция арендатора — где рвётся
Реализация — единственный предикат `t.account = $n` в кандидатном подзапросе и внешнем WHERE, но **не** во внутреннем `DISTINCT ON` (`sql.ts:689-695, 787-792`); PK без `account` (`ddl.sql:137`); RLS нет.

- **R1 (Critical, T2) — перехват сущности.** Подтверждено пробой P1 ([08]): B делает `Org(idA).create()`, для A сущность исчезает (`[]` по id и по цепочкам), B видит её как свою, `.versions()` у B отдаёт версию A с данными (`sql.ts:885` — join без account), превью и подтверждённый `delete()` у B возвращают строки A, каскад тумбстоунит Folder арендатора A (`ddl.sql:357-360`). Под `enforceAcl` с `$account`-предикатом чтение защищено (ACL-предикат идёт до `DISTINCT ON`), но probe существования (`write.ts:512-524`) остаётся под account-фильтром и без `withDeleted` — запись и каскад проходят, воскрешение tombstone под чужим account возможно. Предусловие — знать id: IDOR, `watch()` (payload без account, `ddl.sql:563-565`) или v5 без tenant-scoped конца.
- **R9 (High, T2).** `closureSql`/`purge_closure`/триггер каскада не знают арендатора; `links` на чужой id создаются без проверки (`write.ts:307, 345`); `watch()` отдаёт события всех арендаторов (`chain.ts:923-938`).
- **R4 (High, функц.)** `.deep()` под дефолтом падает: `could not determine data type of parameter $5` (проба P2), fail-closed.
- Дуальность моделей: «PG-схема на группу арендаторов» (`vN.name`) + «колонка account» внутри — N пулов, N×chunk'ов в каталоге, cross-schema запросов нет, общее пространство advisory-lock'ов [04 F13].

### 7.3 ACL
Сильные стороны: deny-by-default, один победитель (max weight, tie → deny), row-предикат до сортировки/лимита, полиморфизм по классу (deny на потомке не обходится родителем), DELETE-проверка по всему замыканию с откатом, memo per-scope с тестом на утечку между scope. Слабые: **fail-open** при нестроковом `categories`/`class` в pattern — `{"categories":["Admin"]}` матчит всех (`acl.ts:62-64, 168-169`), `resources.set` не валидирует pattern; снимок `Resource/Rule` на подключение без межпроцессной инвалидации, `rules.set` не сбрасывает кэш, `db.as()` и `sessions.check` не смотрят `Account.enabled` — отзыв прав/бан без SLA до 7 суток (`index.ts:137-155`, `sessions.ts:105-108`); «широкий allow с большим весом побеждает узкий deny» — риск silent widening, признанный в `docs/requirements.xml` (Risk 2).

### 7.4 Auth и сессии
Хорошо: scrypt без внешних зависимостей, `timingSafeEqual`, `dummyVerify` против перечисления пользователей, ключи/секреты/токены только хэшем, `credential_identity_udx` (глобальная уникальность живого identifier), HOTP/base32 по RFC, replay-защита `lastStep`, три ворота `deleted/confirmed/enabled`, секреты не логируются. Слабее: scrypt `N=2^15, r=8, p=1` — memory cost в 4 раза ниже минимума OWASP (`2^17`) [07 #13], rehash-on-login/pepper/политики паролей нет; TOTP-секрет plaintext в БД; OTP `attempts` — read-modify-write без блокировки; `sess:acc:*` без TTL растёт бесконечно, ротации/sliding TTL нет; rate-limit/lockout/OAuth осознанно вынесены на приложение.

### 7.5 Аудит, неизменяемость, GDPR
Append-only — «по умолчанию», не по правам: `SET LOCAL letopis.purge='on'` доступен любой роли (`ddl.sql:369-372, 384`), `compact`/`purge_account`/`entity_collapse` удаляют физически; рекомендаций по ролям БД нет. Актор изменения не фиксируется, `owner` при create — любой существующий Account без проверки; hash-chain/WORM-экспорта нет. `anonymize()` переписывает только top-level string-поля и не трогает историю; полное забвение — `purge` поддерева (потеря бизнес-записей) или retention (потеря и живых строк, R2). Шифрование at rest/in transit — вне scope (`ssl` только через DSN).

### 7.6 Матрица готовности
| Область | Вердикт |
|---|---|
| Tenant isolation | **не готово** (R1, R9, R4; нет RLS и DB-инварианта) |
| GDPR erasure | частично (история с PII; забвение разрушительно или неполно) |
| Audit immutability | advisory (GUC-bypass, нет актора, нет hash-chain) |
| Least privilege | слабо (admin-фасады везде, ACL opt-in, fail-open pattern) |
| Secrets handling | хорошо/средне (scrypt ниже OWASP, TOTP plaintext) |
| Session management | средне (нет ротации, индекс без TTL, не связан с `enabled`) |
| DR/backup | отсутствует в документации |

## 9. Новизна и полезность

### 9.1 Декомпозиция новизны
**Известные примитивы:** triggered history (temporal_tables, pgMemento); single-table jsonb-хранилище с версиями; hash-key Data Vault → v5; пути Gremlin/Cypher; schema-in-DB (Directus/Strapi); ACL-предикаты в WHERE (Hasura); LISTEN/NOTIFY realtime; scrypt/TOTP по RFC.
**Новая композиция:** (1) dot-chain, в которой глагол записи — звено плана, а один терминал исполняет план транзакцией с fan-out (`chain.ts:536-544`, `write.ts:766-819`); (2) слоты связей `.Класс.set()/unset()` на той же версии; (3) pivot/`entity()` как возврат к узлу без нового JOIN; (4) v5-id как средство идемпотентной брони и «уникальности по построению»; (5) `.purge()` поверх append-only через `SET LOCAL`-гейт триггера; (6) no-history классы в той же таблице; (7) tenancy + auth + ACL в двух зависимостях; (8) документационный слой для LLM-агентов (cheatsheet, api-contract.json, codescribe) как часть продукта.
**Оценка: 3/5** — инженерно свежий «мини-платформенный» пакет, не новая модель данных.

### 9.2 Полезность
**Полезен:** solo/малым командам, особенно с LLM-агентами (стоимость входа заметно ниже благодаря шпаргалке, контракту и разметке); booking/CRM/каталог-подобным SaaS на PG, где история и связи важнее throughput, домен помещается в HUB/LINK без «связей на связи», приемлемы TimescaleDB + ESM + Node 20 + один автор; как референс-дизайн темпорального jsonb-хранилища и как учебный пример дисциплины документации.
**Не полезен:** T4/regulated; T3 с гарантиями доставки; командам с требованием сквозной type-safety (Drizzle/Kysely-уровень: типизация здесь — bolt-on cast, фильтры/sort/agg нетипизированы, `record` → `number`); доменам с FTS/geo/бинарными данными, аналитикой по всему классу, второй уникальностью, событийными цепочками (заказ → оплата → возврат); многоязычным командам (кириллица в цепочках).
