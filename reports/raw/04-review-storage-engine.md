## (A) Верифицированное резюме архитектуры

Хранилище — одна hypertable `Entity(partition,id,class,data jsonb,updated,account,tags,owner,links jsonb,deleted)` с PK `(partition,class,id,updated)`, time-only chunking по `updated` с шагом 30 дней, hardcoded (`lib/sql/ddl.sql:151-156`). Индексы: btree `(partition,class,id,updated DESC)`, три GIN (`data`, `links` jsonb_path_ops, `tags`), btree `account`/`owner` (`ddl.sql:160-165`). Три FK: класс → `Schema` (RESTRICT / ON UPDATE CASCADE), `account`/`owner` → `Account` (RESTRICT) (`ddl.sql:141-143, 478-483`).

Версия = строка; «актуальная» = `DISTINCT ON … ORDER BY updated DESC`; удаление = tombstone-строка. Только transaction-time (`asOf` по `updated`), valid-time нет. Пять row-триггеров: `entity_check` (BEFORE INSERT — класс/abstract/ключи links = классы, существование целевой сущности НЕ проверяется), `entity_update` (BEFORE UPDATE → INSERT новой версии, физический UPDATE отменён), `entity_delete` (BEFORE DELETE → advisory-lock, tombstone, рекурсивный каскад по `links @>`), `entity_notify` (AFTER INSERT → `pg_notify`, канал = имя схемы), `entity_collapse` (AFTER INSERT, `meta.history=false` → физический DELETE старых версий). Серверные функции `purge_closure`/`purge` (двухфазный hard-erase под `SET LOCAL letopis.purge`), `purge_account`, `compact`. Ревизия движка — `COMMENT ON SCHEMA` (`DDL_REVISION=2`), сверка в `connect()` только warn.

Чтение (`lib/src/sql.ts:616-913`): на каждый hop подзапрос `DISTINCT ON` над классом (полиморфно — `class IN (семья)`), GIN-кандидаты (`e.id IN (SELECT c.id … WHERE c.data @> …)`) + перепроверка всех предикатов на latest; hop’ы — `JOIN LATERAL`; `.deep()` — `WITH RECURSIVE`; keyset по `(sort, id)`. Изоляция арендатора: предикат `account` попадает в кандидатный подзапрос и во внешнюю перепроверку, но не во внутренний `DISTINCT ON` (`sql.ts:689-695, 741-751`).

Запись (`lib/src/write.ts`): всегда INSERT; `updated = GREATEST(clock_timestamp(), prev+1µs)`; `create()` с известным id (явным или v5) = «новая версия, если нашли, иначе INSERT»; `update()` = read-latest → `deepMerge` → INSERT. Все публичные write-пути идут через `inTransaction` (`write.ts:604-619, 768, 894`) — внутренняя tx с ретраем 40P01/40001 ×3. Ручная tx = `reserve()` + `BEGIN` без isolation/timeouts (`lib/src/tx.ts:42-67`). Пул `postgres.js` с единственными опциями `max` и `types` (`lib/src/index.ts:90-93`).

## (C) Детали по Critical/High

**F1. Retention стирает current state.** Hypertable партиционируется по `updated`, а `updated` меняется только при новой версии. Справочные сущности (услуги, организации, адреса) часто не меняются годами: их единственная строка стареет в chunk, который `add_retention_policy(…, '2 years')` (`db/policies.mjs:73`) физически дропает. После этого `DISTINCT ON` не находит ни одной строки — сущность исчезает вместе со своими связями (каскад, разумеется, не срабатывает). Предупреждение в `policies.mjs:71` и README §10.8 говорит про «историю этих периодов», что читается как «старые версии», а не «текущее состояние». Для T3/T4, где retention — обязательный инструмент (объём, GDPR), это ловушка с необратимой потерей данных. Варианты: (a) retention только для `history:false`-классов/по классу через `drop_chunks` с предварительным «re-stamp» latest-версий (INSERT копии latest с новым `updated` — сам по себе дорог и создаёт ложные версии); (b) отдельная таблица `current` (materialized latest) вне hypertable; (c) документировать как «retention недопустим при наличии долгоживущих сущностей».

**F2. Захват id между арендаторами.** `createOp` при известном id проверяет существование чтением, которое под `enforceAccount` фильтруется по `account` вызывающего (`write.ts:506`, `sql.ts:689-695`). Чужая сущность «не найдена» → идёт INSERT с `prevUpdated:null` и `account = B` (`write.ts:527-536`); `entity_check` принадлежность не проверяет. Итог: latest-строка теперь принадлежит B; для A внутренний `DISTINCT ON` выбирает строку B (фильтр account стоит только в кандидатном подзапросе и во внешнем WHERE), внешний `t.account = A` её отбрасывает — A видит «сущности нет». B при `.versions()` получает все версии A: join `v … ON v.class = z.class AND v.id = z.id` без account (`sql.ts:882-887`). Предусловие — знать id: для v4/v7 нереалистично, для v5 из пользовательских скаляров (`from:['phone']`, README §3.2 явно поощряет) — типовой сценарий SaaS, так как формула `uuidv5(pgSchema:partition:class:parts)` не включает account (`write.ts:417`). Под `enforceAcl` с `$account`-предикатом probe блокирует живую сущность (тихий `[]`), но не tombstone (probe без `withDeleted`, `write.ts:522`) — воскрешение под чужим account возможно. Исправление дешёвое: в `entity_check` проверять `account` latest-версии того же `(partition,class,id)`, а в v5-namespace добавить account (breaking для существующих id).

**F3. Lost update.** `versionRows` читает latest, делает `deepMerge`, вставляет; `prevUpdated` используется лишь для `GREATEST(clock_timestamp(), prev+1µs)` (`sql.ts:928-929`) — это гарантия монотонности, не CAS. Две конкурентные `update()` от одной V1 (разные соединения пула или два инстанса приложения) дадут V2a и V2b с разными `clock_timestamp`, обе успешны, latest — поздняя; патч первой молча потерян, причём частично (deepMerge по листьям). PK-коллизия (23505) ловит только совпадение микросекунды. Единственный рецепт — ручной `tr.lock()` (README §7), и он оформлен для двойной брони, а не для «любого update». Для T2/T3 (счётчики, статусы, параллельные операторы) нужен опциональный `expectedUpdated` с проверкой в INSERT (`WHERE NOT EXISTS (… updated > $prev)`) либо advisory-lock в `versionRows`.

**F4. GIN по всей истории.** Кандидатный подзапрос не умеет ограничиться latest-строками (свойство «latest» не хранится в строке), поэтому любой фильтр по мутабельному полю масштабируется объёмом истории, а не числом сущностей. Авторы это признают (CHANGELOG 0.21.0) и предлагают `history:false` — т.е. для очередей/outbox отказаться от истории вовсе. Это фундаментальное противоречие одной таблицы «и аудит, и рабочее состояние»: T3 получает производительность ценой T4-требований. Индустриальный ответ — две таблицы (`current` + `history`) или хотя бы `is_latest`-флаг с partial-GIN, что несовместимо с append-only без UPDATE.

**F5. Chunk’и как налог на каждый read.** Все обращения идут по `(partition,class,id)`; исключение chunk’ов по времени невозможно, что README §14 честно фиксирует, включая модель `строки × чанки`. Интервал 30 дней hardcoded в `ddl.sql:153`, конфигурации нет. При 3 годах данных — 36 chunk’ов: каждая индексная проба, каждый `JOIN LATERAL` и планирование (уже 3× дороже исполнения на точечном чтении по `dimensions.results.json`) растут линейно с возрастом базы, не с её полезным объёмом. Для T1/T2 без compression/retention обычная таблица с теми же индексами была бы строго быстрее — Timescale здесь не даёт ничего.

**F6. Сжатые chunk’и без GIN.** Timescale создаёт на сжатых chunk’ах только btree по `segmentby`-ключу; GIN по `data`/`links`/`tags` там нет. Значит после `--compress-after=30d` любой containment-фильтр и любой reverse-hop (`c.links @> …`), затрагивающий сжатые chunk’и, декомпрессирует сегменты всего класса. Тест `wave4` проверяет только `first/versions/asOf` по id (сегмент по `(partition,class,id)` — быстрый случай), README обещает «прозрачность». Для T2+ с compression это скрытый обрыв производительности фильтров.

**F7. Upgrade — окно недоступности, растущее с историей.** `ddl.sql` идемпотентен, но не бесплатен: `DROP/CREATE TRIGGER` и `DROP/ADD CONSTRAINT` берут AccessExclusiveLock на hypertable и каждый chunk, ADD без `NOT VALID` сканирует все строки (BACKLOG замерил ~0.8 с на 1M и 13 chunk’ах, линейно), потом `ANALYZE` (12.8 с). Всё — одной транзакцией `sql.unsafe(text)` (`up.ts:266-267`). На T3-объёмах это минуты полной блокировки. Плюс: `DDL_REVISION` — только warn; ledger миграций отсутствует; несовместимая структура = новая схема `v2` и ручной перенос данных — для T2+ это отсутствие migration story.

**F8. Транзакции и пул.** `beginTx` резервирует соединение и шлёт голый `BEGIN` (`tx.ts:43-48`): READ COMMITTED, без `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`. Пул `max: 10`, у postgres.js нет acquire-timeout — при утечке `tr` (исключение между `begin()` и `rollback()`) слот теряется навсегда, при исчерпании — бесконечное ожидание без ошибки. Долгие `DISTINCT ON`-сканы (5–30 с по README §14) без таймаута под нагрузкой блокируют пул. Ни одна из опций не пробрасывается через `ConnectOpts` (`lib/src/types.ts:293-331`).

## (D) Потолок масштабирования по tier’ам

- **T1 (прототип, <1M, один tenant).** Работает и достаточно быстро: catalog-запросы 4–20 ms, запись 6–25 ms. Ломается первым: `ANALYZE` после заливки (×18–×126, §14.1), traversal от широкого класса (30 с на 980k), утечки `tr` без таймаутов. Timescale — лишняя операционная зависимость (Docker-образ `latest-pg17`).
- **T2 (SaaS, 1–20M, account-изоляция).** Первыми ломаются F2 (захват id при v5-из-данных — нарушение изоляции), F3 (lost update при нескольких инстансах), F8 (пул/таймауты) и F7 (upgrade = блокировка минут). При росте истории — F5 (каждые 30 дней +1 chunk к стоимости всех reads). Compression включать нельзя без замера F6. Вердикт: пригодно при условии патчей F2/F3/F8 и отказе от v5 из пользовательских полей.
- **T3 (100M+, очереди/outbox, много писателей).** Не пригодно в текущем виде: F1 делает retention опасным, F4 требует `history:false` (потеря истории), F12 — 7 индексов + 3 триггера с Schema-lookup + NOTIFY на строку ограничивают single-writer ~100–150 rps, батч без COPY и с лимитом 8191 строк; F11 — collapse-DELETE в старых chunk’ах. Hot-chunk GIN pending-list — общая точка сериализации трёх GIN.
- **T4 (regulated, DR/HA, bitemporal).** Не пригодно: F1 (необратимая потеря current state), F2 (изоляция), F3 (аудит без CAS — «что было записано» не равно «что хотели»), F17 (нет valid-time), F15 (TSL-лицензия, отсутствие managed-cloud), F16 (нет backup/DR-процедуры для hypertable, логическая репликация hypertable с ограничениями). Immutability истории условна: `purge`/`compact`/`purge_account`/`entity_collapse` физически удаляют строки при наличии обычных прав.

## (E) Что сделано хорошо

- **Candidate + recheck** (`sql.ts:775-792`): GIN только сужает, истина — перепроверка на latest; фильтр по устаревшей версии не даёт ложных срабатываний. Полиморфизм через `(class,id)`-идентичность и per-class ACL-предикаты (`sql.ts:699-739`) продуманы.
- **Серверный каскад с защитой от циклов/ромбов** — проверка «latest уже tombstone» (`ddl.sql:345-347`) корректно гасит рекурсию; advisory-lock по ключу сущности; превью через тот же `closureSql`.
- **Двухфазный purge** с `SET LOCAL letopis.purge` в `WHEN`-условии триггера (`ddl.sql:371, 444-453`) — чисто, без TM_SelfModified, флаг транзакционный.
- **Детерминированные v5-id** как средство идемпотентности (README §3.2, тесты `idgen.test.ts:134-184`) — сильный приём, испорченный лишь отсутствием account в namespace.
- **Честность документации**: §14 признаёт 30 с и объясняет модель стоимости; §14.1 — ANALYZE; BACKLOG с замерами `pg_locks`; `schema-sync` с отчётом ломающих изменений.
- **Классификация ошибок и тесты устойчивости**: реальный deadlock двух tx, `pg_terminate_backend` LISTEN-соединения (`resilience.test.ts:72-119`), гонки двойной брони (`core.test.ts:484-519`, `real-life.test.ts` C3/C7/C15).
- **Ревизия DDL в `COMMENT ON SCHEMA`** и мгновенный `db.schema.define()` + `reloadSchema` — прагматичная схема-в-БД.

## (F) Предлагаемая структура разделов отчёта

**«Схема БД и storage-модель»**
1. Единая hypertable и PK `(partition,class,id,updated)` — что даёт и чего стоит (versioning = rows; latest как запрос, а не свойство).
2. Триггерный CRUD: `entity_check`/`entity_update`/`entity_delete`/`entity_notify`/`entity_collapse` — инварианты, гарантированные БД, и инварианты, оставленные клиенту (валидация `data`, существование целей `links`, принадлежность id — F2, F10).
3. Модель конкурентности: `clock_timestamp` + `GREATEST`, 23505 (F9), lost update (F3), advisory-lock как единственный CAS, collapse-гонка (F11).
4. Изоляция арендаторов: где стоит предикат `account` в SQL и почему этого недостаточно (F2); дуальность «схема/account» (F13).
5. Время: transaction-time only, `asOf` через tombstone, отсутствие valid-time (F17); no-history как отказ от истории (F4).
6. Эволюция схемы: strict-валидация против исторических строк, rename/delete класса, ревизия DDL и стоимость upgrade (F7, F14).
7. Хранение истории: compression (F6) и retention (F1) — реальные последствия, а не «прозрачно».

**«Масштабируемость и эксплуатация»**
1. Модель стоимости чтений: `DISTINCT ON` per hop × `JOIN LATERAL` × число chunk’ов; ANALYZE-зависимость; полиморфизм ×20; таблица потолков по tier’ам (раздел D).
2. Модель стоимости записи: индексы/FK/триггеры на строку, batch fast-path и его лимиты, отсутствие COPY (F12); hot chunk и GIN pending list.
3. TimescaleDB: что действительно используется (только compression/retention), лицензия TSL vs Apache-2, managed-cloud (RDS/Aurora — нет), пин `latest-pg17`, необходимость `CREATE EXTENSION` (F15); сценарий «vanilla PG17 без hypertable» как рекомендация для T1/T2.
4. Транзакции и пул: reserved connection, таймауты, PgBouncer, LISTEN (F8, F16).
5. Наблюдаемость и DR: `onQuery`/`slowMs` как единственный сигнал; нет метрик/health/backup-процедуры; периодический ANALYZE родителя hypertable.
6. Рекомендации по приоритетам: (1) ownership-check в `entity_check` + account в v5-namespace; (2) `expectedUpdated`-CAS; (3) таймауты и опции пула в `ConnectOpts`; (4) документировать/запретить retention при долгоживущих сущностях; (5) разделить `ddl.sql` на структуру и код, `NOT VALID`+`VALIDATE`; (6) конфигурируемый chunk interval или режим без hypertable.
