# Кошелёк и биллинг — сервис-пример letopis

Счета, пополнение тестовой картой, списания, переводы, выписка по месяцам. Деньги не списываются дважды: у каждой
операции ключ `[кошелёк, opId]`, и вторую операцию с тем же ключом база не создаст. Баланс — поле счёта: операция и
приращение баланса (`inc`) пишутся одним планом записи, одной транзакцией, а правило `min(0)` база проверяет над итогом.
Выписку по месяцам сервис считает обычным запросом при каждом показе.
Кошелёк — дом letopis (схема `v2.wallet`), компания «Копейка» — квартира в нём.
Интерфейс собран из блоков **shadcnblocks** (`login1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/wallet.

Панель «Под капотом» — как в салоне. Она показывает, что сделало действие: цепочки letopis (вызовы вида
`me.Wallet(…).Movement().create(…)`) и запросы к базе (`onQuery`), версии, которые оно записало, с изменёнными полями
(из журнала `log`), и сигналы об изменении классов, в которые оно записало (`flushSignals()`; только имя класса).
Перевод, например, записывает четыре версии: две операции `Movement` и `balance` обоих счетов. Код панели общий для
четырёх сервисов — `services/shared/`.

Демо-вход: `admin@kopeika.ru` / `Kopeika-2026!` — ключ оператора, он открывает квартиру «Копейка». Тестовые карты: `4242 4242 4242 4242`, `5555 5555 5555 4444`, срок и
CVC — любые. Номер карты проверяется алгоритмом Луна, хранятся только последние 4 цифры.

## Что умеет

- **Пополнение, списание, перевод** — операция `Movement` с ключом `[Wallet, opId]` и приращение баланса её счёта в том
  же плане: `me.Wallet(счёт).Movement().create({ opId, kind, amount }).Wallet().update({ balance: inc(amount) })`. План —
  одна транзакция. `inc` прибавляет внутри `UPDATE` над заблокированной строкой счёта, поэтому параллельные операции не
  теряются, а `min(0)` база проверяет над итогом: операцию, после которой баланс стал бы отрицательным, она отклоняет
  (`invalid_data`), и план откатывается целиком — нет ни операции, ни версии баланса. Нехватку средств сервис отличает от
  других ошибок данных по `e.issues`: поле `balance`, правило `minimum`.
  Флажок «потерять ответ»: операция проведена, но ответ до браузера не дошёл. Повтор с тем же `opId` база не записывает
  (`exists`), сервис сверяет вид и сумму и отвечает «уже было».
- **Обрыв связи с базой на COMMIT** (диалог пополнения) — обрыв настоящий. Для такой операции сервис открывает своего
  консьержа через TCP-прокси (`src/proxy.mjs`, как `examples/_shared/proxy.ts`): тот же пропуск, но с адресом прокси, и на
  нём корень оператора по токену её сессии (`resume`). Прокси рвёт связь до того, как
  COMMIT дошёл до базы, или после того, как база его выполнила. Библиотека отвечает `commit_unknown`: записалась ли
  операция, неизвестно. Сама она не повторяет — сервис повторяет ту же операцию с тем же `opId` обычным корнем
  сессии. Повтор провёл операцию («проведено») — значит, в первый раз она не записалась; получил `exists` («уже было») —
  записалась. При обрыве после COMMIT сигнал о записи не уходит. Другие вкладки узнают о ней из запасного опроса:
  подписка и без сигнала время от времени перечитывает журнал.
- **Перевод** — явная транзакция `db.begin()`: сервис блокирует оба счёта (`lock()`) в порядке id, поэтому встречные
  переводы не ждут друг друга по кругу. Затем две операции — каждая с `inc` баланса своего счёта — и `commit`. С
  флажком «без порядка блокировок» перевод блокирует сначала свой счёт и только через 2 с — счёт получателя. Встречный
  перевод из второй вкладки за это время блокирует свой, и возникает настоящая взаимная блокировка: PostgreSQL прерывает
  один из блоков (`40P01`). Внутри `db.begin()` библиотека не повторяет — сервис откатывает блок и повторяет его
  целиком, всего до трёх попыток. Повтор виден в «Под капотом».
- **Владелец** — `update({ owner }, { rev })`: правка по версии `rev`, прочитанной вместе со счётом. Если счёт за это
  время изменился (правка в другой вкладке или любая операция: баланс — тоже поле счёта), база отвечает `conflict`,
  сервис — 409, ничего не записано.
- **Удалить** — `delete({ confirm: true })`. У ссылки операции на счёт (конец `Wallet` у `Movement`) правило по
  умолчанию — `restrict`: счёт, на который ссылаются операции, база не удаляет (`delete_restricted`). Сервис отвечает
  409 и называет число мешающих операций. Счёт без операций удаляется.
- **Выписка по месяцам** — обычный запрос на чтение: операции, сведённые по счёту и месяцу (`group by`), в транзакции
  сессии (`db.transaction`) — под RLS, поэтому видны только операции своей квартиры — компании «Копейка». Отдельного класса и процесса нет: выписка считается при каждом показе и всегда совпадает с
  операциями. Пополнено — приходы (пополнения и входящие переводы), списано — расходы (списания и исходящие переводы).

## Модель, дом и вход

`src/models.mjs`: счёт `Wallet` (баланс `balance` — целые копейки, `min(0)`) и операция `Movement`.

- **Дом** строит мастер-ключ — строка подключения администратора PostgreSQL — один раз: `src/setup.mjs` вызывает
  `setup(ADMIN_DSN, 'wallet', { models: [Wallet, Movement] })`. Модель — общие классы дома: их пишет консьерж, повтор
  меняет только то, что изменилось, поэтому правка модели доходит до работающего дома при следующей подготовке.
  `setup()` отдаёт **пропуск** — строку, в которой дом и ключ консьержа; повтор отдаёт тот же пропуск.
- **Засев демо** — там же, в `src/setup.mjs`, один раз: консьерж заводит квартиру «Копейка» (`db.createTenant`) и зовёт
  оператора с ролью `owner` (`me.invite({ email }, ['owner'])`); ссылку получает почтальон-заглушка
  (`services/shared/postman.mjs`), и подготовка принимает приглашение за демо-оператора с известным паролем
  (`db.accept(token, { password, name })`, помощник `seedResident`). Это засев демо-данных, а не регистрация.
- **Сервис знает только пропуск** (`LETOPIS_PASS`): `connect(pass, { postman })` — консьерж. При старте он никого не
  зовёт, только заводит счета W-1 и W-2 консьержем в квартире (`await db.in('Копейка')`).
- **Вход** — ключом оператора: `db.open({ email, password })`. Токен сессии — в cookie (`HttpOnly`), каждый
  запрос открывает корень квартиры по нему (`db.resume(token)`), поэтому перезапуск сервиса вход не сбрасывает.
  «Выйти» — `me.close()`: сессия гаснет в базе.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build wallet      # http://127.0.0.1:8082
```

Вместе с кошельком поднимутся база `pg` и шаг подготовки `wallet-setup`: он строит дом мастер-ключом и кладёт пропуск
в том `passes`, откуда его берёт сервис.

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя — мастер-ключ в `ADMIN_DSN`.
2. `services/wallet/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, подготовит дом и
   запустит сервис с одним пропуском. PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..serviceswallet
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:LETOPIS_PASS = (node src/setup.mjs) -replace '^LETOPIS_PASS=', ''   # дом и пропуск
   Remove-Item Env:ADMIN_DSN                                                 # сервису мастер-ключ не нужен
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8082 (порт задаёт `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev`
   (порт 5182, запросы к API уходят к сервису на 8082).

## Проверки

`node services/wallet/scenario.mjs` — «день работы» через JSON API сервиса. С `LETOPIS_PASS` он работает в готовом доме
(каждый прогон — свои номера операций), с одним `ADMIN_DSN` строит свой дом `wallet_scenario` (имя — `HOUSE`) и в
конце сносит его. Сценарий проверяет:

- карту с ошибкой в номере, потерю ответа и повтор с тем же `opId`;
- списание больше баланса (`min(0)` над итогом `inc`, план откатывается целиком), перевод, историю баланса и два
  одновременных списания, которые вместе больше баланса;
- встречные переводы без порядка блокировок (`40P01` и повтор блока) и в порядке id;
- обрыв связи до и после COMMIT (`commit_unknown`);
- смену владельца из двух сессий (`conflict`) и удаление счёта с операциями (`delete_restricted`);
- выписку: пополнение в ней сразу, порядок строк, баланс каждого счёта равен сумме его операций;
- вход ключом оператора и сессию, которой сервис не знал (`db.resume`): операция по ней проходит; после выхода токен — 401.

Проверка в браузере — `CHECK.md`.
