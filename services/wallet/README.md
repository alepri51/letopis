# Кошелёк и биллинг — сервис-пример letopis

Счета, пополнение тестовой картой, списания, переводы, выписка по месяцам. Деньги не списываются дважды: у каждой
операции ключ `[кошелёк, opId]`, и вторую операцию с тем же ключом база не создаст. Баланс — агрегат, то есть поле,
которое считает сама база (здесь — сумма операций). Выписку пишет проектор — процесс, который по журналу версий (`log`)
заполняет производный класс.
Интерфейс собран из блоков **shadcnblocks** (`login1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/wallet.

Панель «Под капотом» — как в салоне. Она показывает, что сделало действие: цепочки letopis (вызовы вида
`db.Wallet(…).Movement().create(…)`) и запросы к базе (`onQuery`), версии, которые оно записало, с изменёнными полями
(из журнала `log`), и сигналы об изменении классов, в которые оно записало (`flushSignals()`; только имя класса).
Перевод, например, записывает четыре версии: две операции `Movement` и `balance` обоих счетов. Код панели общий для
четырёх сервисов — `services/shared/`.

Демо-вход: `admin@kopeika.ru` / `Kopeika-2026!`. Тестовые карты: `4242 4242 4242 4242`, `5555 5555 5555 4444`, срок и
CVC — любые. Номер карты проверяется алгоритмом Луна, хранятся только последние 4 цифры.

## Что умеет

- **Пополнение, списание, перевод** — операция `Movement` с ключом `[Wallet, opId]`. Баланс — агрегат
  `sum(Movement.amount)` с ограничением `min(0)`: операцию, после которой баланс стал бы отрицательным, база отклоняет.
  Флажок «потерять ответ»: операция проведена, но ответ до браузера не дошёл. Повтор с тем же `opId` база не записывает
  (`exists`), сервис сверяет вид и сумму и отвечает «уже было».
- **Обрыв связи с базой на COMMIT** (диалог пополнения) — обрыв настоящий. Для такой операции сервис открывает отдельное
  подключение letopis через свой TCP-прокси (`src/proxy.mjs`, как `guide/kit/proxy.ts`). Прокси рвёт связь до того, как
  COMMIT дошёл до базы, или после того, как база его выполнила. Библиотека отвечает `commit_unknown`: записалась ли
  операция, неизвестно. Сама она не повторяет — сервис повторяет ту же операцию с тем же `opId` обычным подключением
  сессии. Повтор провёл операцию («проведено») — значит, в первый раз она не записалась; получил `exists` («уже было») —
  записалась. При обрыве после COMMIT сигнал о записи не уходит. Другие вкладки узнают о ней из запасного опроса:
  подписка и без сигнала время от времени перечитывает журнал.
- **Перевод** — явная транзакция `db.begin()`: сервис блокирует оба счёта (`lock()`) в порядке id, поэтому встречные
  переводы не ждут друг друга по кругу. С флажком «без порядка блокировок» перевод блокирует сначала свой счёт и только
  через 2 с — счёт получателя. Встречный перевод из второй вкладки за это время блокирует свой, и возникает настоящая
  взаимная блокировка: PostgreSQL прерывает один из блоков (`40P01`). Внутри `db.begin()` библиотека не повторяет —
  сервис откатывает блок и повторяет его целиком, всего до трёх попыток. Повтор виден в «Под капотом».
- **Владелец** — `update({ owner }, { rev })`: правка по версии `rev`, прочитанной вместе со счётом. Если счёт за это
  время изменился (правка в другой вкладке или любая операция: баланс — тоже поле счёта), база отвечает `conflict`,
  сервис — 409, ничего не записано.
- **Удалить** — `delete({ confirm: true })`. У ссылки операции на счёт (конец `Wallet` у `Movement`) правило по
  умолчанию — `restrict`: счёт, на который ссылаются операции, база не удаляет (`delete_restricted`). Сервис отвечает
  409 и называет число мешающих операций. Счёт без операций удаляется.
- **Выписка по месяцам** — проектор `statement` (`adm.projector`) читает журнал операций пачками и пишет класс
  `Statement`. Опции — `lockTimeout: 1000` и `lockRetries: 3`. Если строку выписки держит чужая транзакция, пачка ждёт
  не дольше секунды, затем откатывается, и проход повторяется. После трёх таких проходов подряд арендатор (владелец
  данных, здесь — компания «Копейка») выбывает: проектор пропускает его изменения до перестройки (`status().failed`, код
  `55P03`). Блок выписки показывает `status()` — состояние, версию проектора, отставание, время прохода — и
  предупреждение, если арендатор выбыл. «Перестроить выписку» вызывает `rebuild({ tenant })` для выбывшего арендатора,
  иначе — `rebuild()` одной транзакцией.
- **Чужая транзакция: занять выписку** — проверка `lockTimeout` и `lockRetries` из интерфейса. Сервис открывает на
  отдельном подключении администратора транзакцию-«горизонт»: проектор читает журнал только до самой старой
  незавершённой транзакции и, пока она открыта, новых операций не видит. Следующее пополнение записывается, после него
  вторая транзакция берёт строку выписки этого счёта за месяц (`select … for update`), а горизонт закрывается. Пачка
  проектора доходит до пополнения и ждёт строку; через три прохода по секунде арендатор выбывает (`55P03`), и сервис сам
  закрывает чужую транзакцию. Горизонт задерживает подписки и проекторы всех сервисов этой базы, поэтому сервис держит
  его недолго: горизонт — до пополнения, но не дольше 30 с, строку — пока арендатор не выбыл, но не дольше 15 с.
  «Отпустить чужую транзакцию» закрывает её раньше.
- **Проверить целостность** — `adm.verify({ data: true })` сверяет цепочки хэшей журнала (хэш каждой версии включает
  хэш предыдущей), данные — с описаниями классов, агрегат `balance` каждого счёта — с суммой его операций. В отчёте —
  число проверенных версий, якорь (хэш голов цепочек, его хранят вне базы) и нарушения. «Испортить запись журнала»
  меняет баланс в промежуточной версии счёта прямым `UPDATE` от суперпользователя — как правка руками в SQL; `verify`
  находит её: хэш версии не совпадает с `prev_hash` следующей. «Вернуть как было» возвращает данные байт в байт.
  Подделать сам баланс в `entity` так не выйдет: триггеры `entity` включены и в режиме репликации (`enable always`).

## Модель

`src/models.mjs`: счёт `Wallet`, операция `Movement` и выписка `Statement` — классы арендатора «Копейка». `Statement` —
производный класс: его строки пишет проектор `statement`. При каждом запуске сервиса классы записывает `syncModels`
через администраторское подключение letopis (`ADMIN_DSN`, `allowBypassRls`: построчные правила доступа базы, RLS, на
него не действуют) в сессии оператора (демо-вход `admin@kopeika.ru`). Это же подключение ведёт проектор выписки и
`verify`. Веб-сессия пользователя модель не пишет: производный класс описывает только администратор. Классы лежат в
арендаторе сервиса, а не в System — системном арендаторе с общими классами установки. Классы System `syncModels`
пропускает: их пишет только установка (`up()` из сида, готового набора классов), а сид не меняет класс, который уже
есть. Будь классы в System, правка модели не дошла бы до уже работающей установки.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build wallet      # http://127.0.0.1:8082
```

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя через `ADMIN_DSN` и `APP_DSN`
   (роль приложения `wallet_app` сервис создаст сам).
2. `services/wallet/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, запустит сервер.
   PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\wallet
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://wallet_app:wallet-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8082 (порт задаёт `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev`
   (порт 5182, запросы к API уходят на сервер 8082).

## Проверки

`node services/wallet/scenario.mjs` — «день работы» через JSON API сервиса. Сценарий проверяет:

- карту с ошибкой в номере, потерю ответа и повтор с тем же `opId`;
- списание больше баланса, перевод, историю баланса и два одновременных списания, которые вместе больше баланса;
- встречные переводы без порядка блокировок (`40P01` и повтор блока) и в порядке id;
- обрыв связи до и после COMMIT (`commit_unknown`);
- смену владельца из двух сессий (`conflict`) и удаление счёта с операциями (`delete_restricted`);
- проектор: `status()`, `rebuild()`, выбывание арендатора по `lockRetries` и `rebuild({ tenant })`;
- `verify({ data: true })`.

Чужую транзакцию, которая держит строки выписки, сценарий открывает прямым подключением по `ADMIN_DSN`. Проверка в
браузере — `CHECK.md`.
