# Кошелёк и биллинг — сервис-пример letopis

Счета, пополнение тестовой картой, списания, переводы, выписка по месяцам. Деньги без двойного списания:
операция с ключом `[кошелёк, opId]`, баланс — агрегат базы (сумма операций), выписка — проектор из журнала.
Интерфейс собран из блоков **shadcnblocks** (`login1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/wallet.

Панель «Под капотом» — как в салоне: цепочки, запросы к базе (`onQuery`), записанные версии с изменёнными полями (у
перевода — две операции `Movement` и `balance` обоих счетов) и сигналы классов, которые записало действие; код общий
для четырёх сервисов — `services/shared/`.

Демо-вход: `admin@kopeika.ru` / `Kopeika-2026!`. Тестовые карты: `4242 4242 4242 4242`, `5555 5555 5555 4444`
(любой срок и CVC; номер проверяется алгоритмом Луна, хранятся только последние 4 цифры).

## Что умеет

- **Пополнение, списание, перевод** — операция `Movement` с ключом `[Wallet, opId]`, баланс — агрегат базы
  (`sum(Movement.amount)`, `min(0)`). «Потерять ответ» — операция проведена, ответ до браузера не дошёл; повтор с тем же
  `opId` — «уже было».
- **Обрыв связи с базой на COMMIT** (диалог пополнения) — на деле: на одну операцию своё подключение letopis через
  TCP-прокси (`src/proxy.mjs`, как `guide/kit/proxy.ts`), он рвёт связь до того, как COMMIT дошёл до базы, или после того,
  как база его выполнила. Библиотека отвечает `commit_unknown` и сама не повторяет; сервис повторяет ту же операцию с тем
  же `opId` обычным подключением: «проведено» — в первый раз не записалось, `exists` («уже было») — записалось. После
  обрыва «после COMMIT» сигнал записи не уходит: вкладки узнают о ней запасным опросом подписки.
- **Перевод** — `db.begin()`, `lock()` обоих счетов в порядке id: встречные переводы не ждут друг друга по кругу. Флажок
  «без порядка блокировок» — сначала свой счёт и пауза 2 с между замками: встречный перевод из второй вкладки ловит
  настоящую взаимную блокировку, PostgreSQL прерывает один блок (`40P01`). Повторов внутри `db.begin()` библиотека не
  делает — сервис откатывает и повторяет весь блок (до трёх попыток), повтор виден в «Под капотом».
- **Владелец** — `update({ owner }, { rev })` по версии, прочитанной вместе со счётом. Счёт успели изменить (другая
  вкладка или любая операция: баланс тоже поле счёта) — `conflict`, 409, ничего не записано.
- **Удалить** — `delete({ confirm: true })`. Конец `Wallet` у `Movement` — `restrict`, правило по умолчанию: счёт с
  операциями база не удаляет (`delete_restricted`, 409 с числом мешающих операций); без операций — удаляется.
- **Выписка по месяцам** — проектор `statement` (`adm.projector`) с `lockTimeout: 1000` и `lockRetries: 3`: чужую
  блокировку строки выписки пачка ждёт не дольше секунды (дольше — откат, проход пропущен), после трёх таких проходов
  подряд арендатор выбывает (`status().failed`, код `55P03`). Блок выписки показывает `status()` — состояние, версию,
  отставание, время прохода — и предупреждение о выбывшем; «Перестроить выписку» — `rebuild({ tenant })` для выбывшего,
  иначе `rebuild()` одной транзакцией.
- **Проверить целостность** — `adm.verify({ data: true })`: цепочки хэшей журнала, данные против описаний классов и
  агрегат `balance` каждого счёта против суммы его операций; отчёт — число версий, якорь, нарушения.

## Модель

`src/models.mjs`: счёт `Wallet`, операция `Movement`, выписка `Statement` — классы арендатора «Копейка». При каждом
запуске их пишет `syncModels` администраторского подключения (`ADMIN_DSN`, `allowBypassRls`) в сессии оператора — оно
же ведёт проектор выписки и `verify`; сессия пользователя модель не пишет. Классы не System: их `syncModels`
пропускает, а сид установки уже существующий класс не меняет — изменение модели до работающей установки так не дошло бы.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build wallet      # http://127.0.0.1:8082
```

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя через `ADMIN_DSN` и `APP_DSN`
   (роль приложения `wallet_app` сервис создаст сам).
2. `services/wallet/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, запустит сервер.
   PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\wallet
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://wallet_app:wallet-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8082 (порт — `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev` (5182).

## Проверки

`node services/wallet/scenario.mjs` — «день работы» через API: карта с ошибкой, «потерянный ответ» и повтор,
списание больше баланса, перевод, история баланса, гонка списаний; встречные переводы без порядка блокировок (`40P01`
и повтор блока) и в порядке id; обрыв связи до и после COMMIT (`commit_unknown`); смена владельца из двух сессий
(`conflict`); удаление счёта с операциями (`delete_restricted`); проектор — `status()`, `rebuild()`, выбывание по
`lockRetries` и `rebuild({ tenant })`; `verify({ data: true })`. Чужую транзакцию, которая держит строки выписки,
сценарий открывает прямым подключением по `ADMIN_DSN`. Проверка в браузере — `CHECK.md`.
