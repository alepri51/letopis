# Helpdesk — сервис-пример letopis

Служба поддержки для нескольких компаний. Helpdesk — дом letopis (схема `v2.helpdesk`), каждая компания — квартира в
нём: свои заявки, сотрудники и клиенты. Чужого не видно даже по прямому запросу. Роли — руководитель, агент поддержки и
клиент. Что кому можно, решает матрица квартиры, а проверяет её сама база. Вход — ключом: паролем или одноразовым
кодом из письма. Второй фактор — TOTP (код из приложения-аутентификатора): подключается по QR-коду, а отключается на
той же странице «Безопасность» действующим кодом. В компанию попадают только по приглашению: письмо со ссылкой
приходит на почту, по ссылке открывается страница приглашения, на ней его и принимают. Интеграции входят по ключу API. Очередь заявок обновляется сама: подписка `watch` следит
за изменениями, а события приходят в браузер потоком SSE. Помощник работает через MCP — протокол, по которому ИИ-агенты
вызывают инструменты. Тот же адрес `/mcp` подходит настоящему ИИ-агенту — по ключу API сотрудника, постоянному или
временному на 15 минут.
Интерфейс собран из блоков **shadcnblocks** (`login1`, `signup1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/helpdesk.

Панель «Под капотом» показывает, что сделало действие: цепочки letopis и запросы к базе (`onQuery`; дольше `slowMs` —
отмечены), версии, которые оно записало (из журнала `log`, с изменёнными полями), и сигналы об изменении классов, в
которые оно записало (`flushSignals()`; только имя класса, без токена квартиры). При работе от имени видны версии того,
от чьего имени работают, — под его правами. Вызовы ИИ-агента по временному ключу видны у вкладки, которая этот ключ
выдала. Данных чужой компании в панели нет. Код панели общий для четырёх сервисов — `services/shared/`.

Демо-входы (компания «Север»; агент работает ещё и в «Байкале»):

| Кто | Email | Как войти |
|---|---|---|
| руководитель | `boss@sever.ru` | пароль `Sever-2026!` |
| агент поддержки | `agent@sever.ru` | пароль `Agent-2026!`; если включили TOTP — ещё код из приложения |
| клиент | `client@sever.ru` | «Код на почту» → письмо в демо-почте http://127.0.0.1:8083/mail |

Руководитель «Байкала» — `boss@baikal.ru` / `Baikal-2026!`. Агент в «Байкале» — тот же `agent@sever.ru`, но со своим
паролем `Agent-Baikal-2026!`: ключ открывает ровно одну квартиру, и один пароль на две квартиры дом не примет. Свою
компанию можно зарегистрировать на странице входа.

## Дом, консьерж и вход

- **Дом** строит мастер-ключ — строка подключения администратора PostgreSQL — один раз: `src/setup.mjs` вызывает
  `setup(ADMIN_DSN, 'helpdesk', { models, signals: 'tenant' })`. Модель (`src/models.mjs`: `Desk`, `Counter`, `Profile`,
  `Ticket`, `Reply`, `Note`; `Profile` — справочник email людей компании, имена и роли сервис берёт из
  `me.acl.people()`) — общие классы дома: их пишет консьерж, повтор меняет только то, что изменилось. Режим
  сигналов `tenant`: подписчики и кэш одной компании не просыпаются от правок другой. `setup()` отдаёт **пропуск** —
  строку, в которой дом и ключ консьержа; повтор отдаёт тот же. `FRESH=1` — демо с нуля: подготовка сносит дом
  (`demolish`) и строит заново, прежний пропуск гаснет.
- **Засев демо** — там же, в `src/setup.mjs`, один раз: консьерж заводит «Север» и «Байкал» и зовёт их людей с ролями;
  ссылки получает почтальон-заглушка, и подготовка принимает приглашения за демо-людей (помощник `seedResident`):
  руководителю и агенту — с паролями, клиентам — без пароля (они входят кодом из письма). Это засев демо-данных, а не
  регистрация. Матрицу, счётчик и демо-заявки сервис пишет при запуске.
- **Сервис знает только пропуск** (`LETOPIS_PASS`): `connect(pass, { postman })` — консьерж. Он открывает дверь жильцам
  (`open`, `resume`, `invitation`, `accept`), выдаёт коды (`requestCode`), заводит квартиры и работает в них сам
  (`db.in`) или от имени жильца (`db.as`).
- **Почтальон** — функция сервиса из `connect(pass, { postman })`: библиотека выпускает и проверяет токен ссылки и код,
  а доставляет их почтальон. Здесь он заглушка (`services/shared/postman.mjs`): письмо ложится в «Демо-почту» (`/mail`,
  у приглашения — кнопка-ссылка) и одной строкой отмечается в логе сервиса. В настоящем сервисе на его месте — отправка
  письма или СМС; демо-почту выключает `DEMO_MAIL=0`.
- **Вход** — ключом: пароль (`db.open({ email, password, totp })`) или код из письма: `db.requestCode({ email })` —
  письмо с кодом почтальону; код доказывает email, а не открывает одну компанию: `db.tenantsOf({ email, code })` — его
  компании; одна — вход сразу, несколько — страница просит выбрать, и вход — `db.open({ email, code, tenant })`.
  Включён второй фактор — верный ключ без кода из приложения квартиру не открывает: `db.open` отвечает
  `api.totp_required`, страница входа просит код, и вход повторяется с ним (`{ email, password, totp }` или
  `{ email, code, tenant, totp }`; код письма при этом не сгорает, он ждёт на сервисе до пяти минут). Неверный пароль — просто «Неверный email или пароль». Токен сессии — в cookie (`HttpOnly`),
  каждый запрос открывает корень квартиры по нему (`db.resume(token)`): погашенный или истёкший токен — 401 и вход
  заново, перезапуск сервиса вход не сбрасывает.
- **Регистрация компании** — тоже приглашение: консьерж заводит квартиру (`db.createTenant`), пишет её матрицу и
  настройки и зовёт регистратора с ролью `owner`. Письмо со ссылкой `/invite/<токен>` уходит в демо-почту; страница
  приглашения показывает его, ничего не меняя (`db.invitation`), регистратор принимает его и задаёт пароль
  (`db.accept`). Название занято — 409; сбой посреди регистрации квартиру не оставляет: консьерж её
  удаляет (`me.deleteTenant()`), повтор начинает с нуля.
- **Команда.** Руководитель зовёт человека (`me.invite({ email }, [роль])` — звать можно с ролью, которую матрица
  разрешает выдать; руководителю — любую), письмо со ссылкой приходит в демо-почту, человек открывает её и принимает
  приглашение сам — новый аккаунт или прежний, если этот email уже работает в другой компании; пароль — по желанию
  (свой у каждой компании), без него вход кодом. Пока ссылку не открыли, приглашение видно в команде, его можно
  отменить (`me.revokeInvite`). «Удалить из компании» — выписка: ключи и сессии человека в квартире гаснут сразу. «Работать от
  имени» — `db.as(аккаунт, компания)`: права того человека, автор версий — он, исполнитель (`agent`) — сервис.
  «Закрыть компанию» — `me.deleteTenant()`: квартира стирается целиком.

## Матрица

Правило по умолчанию дома — «нельзя». Руководителю (роль `owner`) всё, в том числе выдачу любых ролей, разрешает
правило хозяина квартиры, которое заводит `createTenant`. Остальное — список `ACL` в `src/server.mjs`, вызовы обёртки `db.acl.grant`:

- агент (`agent`) читает компанию, справочник людей, прописки (`member` — чтобы `me.acl.people()` отдавал ему имена
  коллег), заявки, ответы и заметки, пишет заявки, ответы и заметки; удалять
  заявки и править компанию ему нечем — правил на это нет;
- клиент (`client`) читает название компании, свои заявки (условие `owner: '$actor'`), ответы на них (условие
  `data.client`) и свой профиль, пишет свои заявки и ответы; заметки и счётчик заявок ему не видны;
- интеграция (`integration`) читает заявки и справочник, пишет заявки — от имени клиентов;
- разделы приложения — действия API: агенту — `desk.{queue,assistant}`, руководителю — все.

В базе это строки `Resource` и `rule` квартиры с постоянными `alias` (`role:client:ACCOUNT`, `class:Ticket:READ`).
Правила пишет консьерж (`db.in(компания).acl.grant`) при каждом запуске — во всех компаниях, демо и зарегистрированных,
и при регистрации: изменение правил после перезапуска доходит до всех. Совпадающее не трогается, повтор версий не
пишет; снять правило консьержа руководитель не может. Номер заявки выдаёт сервис — консьерж в квартире (`db.in`): `inc`
в счётчике компании, поэтому клиенту счётчик не нужен.

## Ключи API и ИИ-агент

- **Ключ интеграции** («Интеграции») — у своего аккаунта с ролью `integration`: руководитель зовёт его на служебный
  адрес `…@helpdesk.local` — такое письмо почтальон в демо-почту не кладёт, ссылку забирает сам сервис и принимает
  приглашение за программу без пароля (программа входит ключом API), а затем выпускает ей ключ — `keys.issueApiKey`. «Отозвать» выписывает аккаунт интеграции: ключ и его сессии гаснут.
- **Ключ ИИ-агента** («Помощник» → «Выдать ключ для агента») — свой ключ сотрудника (`me.keys.issueApiKey`): агент
  работает с его правами. **Временный ключ** на 15 минут — `me.keys.issueApiKey({ ttl: 900 })`: истекает сам,
  «Отозвать» (`me.keys.revoke`) и «Выйти на всех устройствах» гасят его сразу. Свои ключи выдаются только в первые
  10 минут после входа паролем или кодом: позже — выйти и войти снова.
- MCP — всегда от имени жильца: `createMcpServer(корень)` вкладки (cookie) или корня по ключу (`db.open({ apiKey })`).
  Запись через MCP — только сотрудникам, клиенту и ключу интеграции — только чтение. Работая от имени, помощником
  пользоваться нельзя (корень консьержа MCP не принимает).

Подключить настоящего агента: войдите агентом → «Помощник» → «Выдать ключ для агента» или «Временный ключ на 15
минут». Страница покажет команду для Claude Code:

```sh
claude mcp add --transport http helpdesk "http://127.0.0.1:8083/mcp" --header "Authorization: Bearer <ключ>"
```

Агент получит инструменты `letopis_model`, `letopis_query`, `letopis_history`, `letopis_write` с правами того, кому
выдан ключ. Ключ открывает одну компанию, поэтому адрес — просто `/mcp`. Правка — только с номером прочитанной версии
`rev`; в журнале правки агента — от имени сотрудника, исполнителя нет. «Проверить доступ агента» вызывает `/mcp` с
ключом без cookie вкладки — так, как это сделает агент.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build helpdesk    # http://127.0.0.1:8083
```

Вместе с сервисом поднимутся база `pg` и шаг подготовки `helpdesk-setup`: он строит дом мастер-ключом и кладёт пропуск
в том `passes`, откуда его берёт сервис. Демо с нуля (дом сносится, данные теряются): `FRESH: '1'` в `environment`
шага `helpdesk-setup` в `services/compose.yaml` или при запуске руками.

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя — мастер-ключ в `ADMIN_DSN`.
2. `services/helpdesk/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, подготовит дом и
   запустит сервис с одним пропуском. PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\helpdesk
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:LETOPIS_PASS = (node src/setup.mjs) -replace '^LETOPIS_PASS=', ''   # дом и пропуск
   Remove-Item Env:ADMIN_DSN                                                 # сервису мастер-ключ не нужен
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8083 (порт — `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev` (5183).

Переменные сервиса: `LETOPIS_PASS` — пропуск, `PORT` (8083), `HOST` (127.0.0.1), `DEMO_MAIL=0` — выключить демо-почту.
Подготовки (`src/setup.mjs`): `ADMIN_DSN` — мастер-ключ, `HOUSE` — имя дома (по умолчанию `helpdesk`), `FRESH=1` — дом
с нуля.

**Демо-почта — только для своей машины.** `/mail` показывает коды входа и приглашений всем, кто её открыл, то есть
позволяет войти по коду за любого. Сервис слушает 127.0.0.1, а в контейнере порт открыт только на 127.0.0.1; наружу
стенд не публикуют. В настоящем сервисе `mail()` отдавал бы письмо почтовому шлюзу, а демо-почты не было бы.

## Проверки

- `ADMIN_DSN=… node services/helpdesk/scenario.mjs` — «день работы» через HTTP и настоящий клиент MCP. Дом свой
  (`helpdesk_scenario`, имя — `HOUSE`): сценарий строит его заново и в конце сносит. Сценарий проверяет:
  - вход ключом, второй фактор (паролем и кодом из письма без кода из приложения — `api.totp_required`, код
    одноразовый) и его отключение только верным кодом;
    вход по коду из письма; клиент видит только свои заявки — и через сервис, и своим корнем прямо в доме;
  - очередь по курсору, запрет удаления агенту, версию `rev`, ключ интеграции (выписка — отзыв) и MCP;
  - временный ключ ИИ-агента: срок, место среди своих ключей, у правок агента автор без исполнителя, после «Отозвать» и
    «Выйти на всех устройствах» — 401;
  - агента в двух компаниях — два ключа, два пароля; приглашение по ссылке (письмо в демо-почте, страница приглашения,
    принятие — ссылка одноразовая), работу от имени и удаление из компании (выписка гасит ключи и сессии);
  - регистрацию приглашением, сбой посреди неё, вторую компанию того же человека со своим паролем (пароль первой — 422)
    и закрытие компании.
- `services/helpdesk/CHECK.md` — проверка в браузере по шагам.
