# Helpdesk — сервис-пример letopis

Служба поддержки для нескольких компаний. Каждая компания — отдельный арендатор letopis: свои заявки, свои
сотрудники и клиенты, чужого не видно даже по прямому запросу. Роли — руководитель, агент, клиент; что кому можно,
решают правила доступа, а проверяет их сама база. Вход — по паролю или одноразовому коду из письма, второй фактор —
TOTP с QR-кодом. Интеграции входят по ключу API. Очередь заявок обновляется сама (подписка `watch` → SSE).
Помощник работает через MCP — тот же адрес `/mcp` подходит настоящему ИИ-агенту: по ключу API или по короткой
сессии, которую выпускает сервис (`auth.sessionFor`).
Интерфейс собран из блоков **shadcnblocks** (`login1`, `signup1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/helpdesk.

Панель «Под капотом»: вызовы letopis, запросы к базе (`onQuery`; дольше `slowMs` — отмечены), записанные версии с
изменёнными полями (при работе от имени — версии того, от чьего имени, под его правами; вызовы ИИ-агента по его
сессии — у вкладки, которая её выдала) и сигналы классов, которые записало действие (только имя класса, без токена
арендатора); чужой компании в панели нет. Код общий для четырёх сервисов — `services/shared/`.

Демо-входы (компания «Север»; агент работает ещё и в «Байкале»):

| Кто | Логин | Как войти |
|---|---|---|
| руководитель | `boss@sever.ru` | пароль `Sever-2026!` |
| агент | `agent@sever.ru` | пароль `Agent-2026!`; если включили TOTP — ещё код из приложения |
| клиент | `client@sever.ru` | «Код на почту» → письмо в демо-почте http://127.0.0.1:8083/mail |

Руководитель «Байкала» — `boss@baikal.ru` / `Baikal-2026!`. Свою компанию можно зарегистрировать на странице входа.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build helpdesk    # http://127.0.0.1:8083
```

Демо с нуля (схема пересоздаётся, данные теряются): `FRESH=1` в `environment` сервиса `helpdesk` в
`services/compose.yaml` или при запуске руками.

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя через `ADMIN_DSN` и `APP_DSN`
   (роль приложения `helpdesk_app` сервис создаст сам).
2. `services/helpdesk/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, запустит сервер.
   PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\helpdesk
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://helpdesk_app:helpdesk-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8083 (порт — `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev` (5183).

Переменные: `ADMIN_DSN`, `APP_DSN`, `SCHEMA` (по умолчанию `helpdesk`), `PORT` (8083), `HOST` (127.0.0.1),
`SIGNALS` — режим сигналов установки (`tenant`), `FRESH=1` — пересоздать схему, `DEMO_MAIL=0` — выключить демо-почту.

**Демо-почта — только для своей машины.** `/mail` показывает коды входа всем, кто её открыл, то есть позволяет
войти по коду за любого. Сервис слушает 127.0.0.1, а в контейнере порт открыт только на 127.0.0.1; наружу стенд не
публикуют. В настоящем сервисе `mail()` отдаёт письмо почтовому шлюзу, а демо-почты нет.

## Подключить настоящего ИИ-агента

Войдите агентом → «Помощник» → «Выдать ключ для агента» или «Сессия агента на 15 минут». Страница покажет команду
для Claude Code:

```sh
# ключ API
claude mcp add --transport http helpdesk "http://127.0.0.1:8083/mcp?tenant=<компания>" \
  --header "Authorization: Bearer <ключ>"
# короткая сессия: компанию она помнит сама
claude mcp add --transport http helpdesk "http://127.0.0.1:8083/mcp" \
  --header "Authorization: Bearer <токен сессии>"
```

Агент получит инструменты `letopis_model`, `letopis_query`, `letopis_history`, `letopis_write` с правами того,
кому выдан ключ или сессия. Правка — только с версией `rev`. «Проверить доступ агента» вызывает `/mcp` с токеном
сессии без cookie вкладки — так, как это сделает агент.

Чем сессия агента отличается от ключа и от «Работать от имени» (по коду `lib/src/auth.ts`, `lib/sql/80-auth.sql`,
`lib/sql/20-context.sql`):

| | ключ API | сессия агента | «Работать от имени» |
|---|---|---|---|
| вызовы | `auth.issueApiKey({ account })` | `auth.sessionFor(account, { ttl: 900 })`, `connect({ sql, token, refreshSession: false })`, `auth.switch(компания)` | `svc.as(account, { tenant })` |
| что в базе | кред `APIKEY`: он есть в `auth.credentials()` | сессия со способом входа `SERVICE`: это не кред, в `credentials()` её нет — выданные сессии помнит сервис | своей сессии нет: сервис в каждой транзакции называет актора (`letopis.account`, право `auth.impersonate`) |
| срок | пока не отзовут | 15 минут от выдачи: работа агента срок не продлевает | пока жива сессия сервиса |
| как закрыть | `revokeCredential` — гаснут сессии этого ключа | «Погасить» — `auth.revoke()` её подключением; выход вкладки, которая её выдала; «Выйти на всех устройствах» (`revokeAll`) | «Вернуться к себе» |
| компания | `?tenant=` в адресе | `auth.switch` при выдаче — база помнит её в сессии | `{ tenant }` в `as()`; `auth.switch` у такого фасада нет |
| журнал | автор — вы, исполнителя нет | автор — вы, исполнителя (`agent`) нет: что сессию выпустил сервис, видно только в `auth.session(token).methods` | автор — тот, от чьего имени, исполнитель (`agent`) — сервис |

Поэтому работа от имени в интерфейсе — `svc.as`: журнал называет сервис, а причина — руководителя. Сессию агента
сервис выдаёт только на себя: работая от имени, её не получить (409) — токен с чужими правами ушёл бы из сервиса.

## Проверки

- `node services/helpdesk/scenario.mjs` — «день работы» через HTTP и настоящий клиент MCP: вход с TOTP, код из
  письма, только свои заявки у клиента, очередь по курсору, запрет удаления, версия `rev`, ключи API, MCP,
  сессия ИИ-агента (`sessionFor`: способ входа, срок, нет в `credentials()`, автор версий без исполнителя, «Погасить»
  и «Выйти на всех устройствах» — 401), переход между компаниями, работа от имени, «завершить сеансы», удаление из
  компании, регистрация и закрытие компании. Схема своя (`helpdesk_scenario`) и каждый раз с нуля.
- `services/helpdesk/CHECK.md` — проверка в браузере по шагам.
