# Helpdesk — сервис-пример letopis

Служба поддержки для нескольких компаний. Каждая компания — отдельный арендатор letopis, то есть отдельный владелец
данных: свои заявки, сотрудники и клиенты. Чужого не видно даже по прямому запросу. Роли — руководитель, агент
поддержки и клиент. Что кому можно, решают правила доступа, а проверяет их сама база. Вход — по паролю или по
одноразовому коду из письма. Второй фактор — TOTP (код из приложения-аутентификатора), подключается по QR-коду, а
отключается на той же странице «Безопасность» действующим кодом (`auth.revokeCredential` его креда).
Интеграции входят по ключу API. Очередь заявок обновляется сама: подписка `watch` следит за изменениями, а события
приходят в браузер потоком SSE. Помощник работает через MCP — протокол, по которому ИИ-агенты вызывают инструменты.
Тот же адрес `/mcp` подходит настоящему ИИ-агенту: по ключу API или по короткой сессии, которую выпускает сервис
(`auth.sessionFor`).
Интерфейс собран из блоков **shadcnblocks** (`login1`, `signup1`, `navbar1`, `stats8`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/helpdesk.

Панель «Под капотом» показывает, что сделало действие: цепочки letopis и запросы к базе (`onQuery`; дольше `slowMs` —
отмечены), версии, которые оно записало (из журнала `log`, с изменёнными полями), и сигналы об изменении классов, в
которые оно записало (`flushSignals()`; только имя класса, без токена арендатора). При работе от имени видны версии
того, от чьего имени работают, — под его правами. Вызовы ИИ-агента по его сессии видны у вкладки, которая эту сессию
выдала. Данных чужой компании в панели нет. Код панели общий для четырёх сервисов — `services/shared/`.

Демо-входы (компания «Север»; агент работает ещё и в «Байкале»):

| Кто | Логин | Как войти |
|---|---|---|
| руководитель | `boss@sever.ru` | пароль `Sever-2026!` |
| агент поддержки | `agent@sever.ru` | пароль `Agent-2026!`; если включили TOTP — ещё код из приложения |
| клиент | `client@sever.ru` | «Код на почту» → письмо в демо-почте http://127.0.0.1:8083/mail |

Руководитель «Байкала» — `boss@baikal.ru` / `Baikal-2026!`. Свою компанию можно зарегистрировать на странице входа.

## Модель и правила доступа

`src/models.mjs` — классы каждой компании (арендатора): `Desk`, `Counter`, `Profile`, `Ticket`, `Reply`, `Note`.
Правила доступа — список `ACL` в `src/server.mjs`: вызовы обёртки прав `db.acl.grant` и `db.acl.deny` по ролям
(`owner` — руководитель, `agent`, `client`, `integration` — ключ формы на сайте). В базе это строки `Resource` и `rule`
арендатора с постоянными `alias` (`role:client:ACCOUNT`, `class:Note:READ`). Номер заявки выдаёт сервис от имени
руководителя: клиенту и ключу интеграции счётчик `Counter` закрыт правилом.

Классы и правила пишет администраторское подключение letopis (`ADMIN_DSN`, `allowBypassRls`: построчные правила
доступа базы, RLS, на него не действуют). Для записи сервис выпускает короткую сессию руководителя компании
(`auth.sessionFor`) и переводит её в компанию (`auth.switch`). Затем `syncModels` записывает классы, а сервис —
правила; после записи сессия гаснет (`auth.revoke()`). Так происходит при регистрации компании и при каждом запуске —
во всех компаниях, демо и зарегистрированных (это арендаторы со строкой `Desk`). Поэтому изменение модели или правил
после перезапуска доходит до всех.

`db.acl.grant` и `db.acl.deny` пишут ресурс и правило целиком по постоянному `alias` и паре `Group`–`Object`: чего
нет — создаётся, расходящееся с кодом приводится к нему, совпадающее не трогается, и повторный запуск версий не
пишет. Ресурсы прежних версий сервиса (`LEGACY_RESOURCES`) удаляются вместе со своими правилами; ресурсы с другими
`alias` остаются как есть. Сессии пользователей модели и правила не пишут, а администраторское подключение в
веб-сессии не попадает.

Классы лежат в арендаторе компании, а не в System — системном арендаторе с общими классами установки. Классы System
`syncModels` пропускает: их меняет только установка, а её сид (набор классов, который ставит `up()`) не трогает
класс, который уже есть. Правка модели не дошла бы до работающей установки.

Ещё три свойства сервиса. Записи через MCP видны в «Под капотом» вкладки — и её собственные (по cookie), и записи
ИИ-агента по сессии, которую она выдала. Сессии агента гаснут, когда эта вкладка выходит из сервиса. Если модель или
правила не записались хотя бы в одну компанию, сервис не запускается.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build helpdesk    # http://127.0.0.1:8083
```

Демо с нуля (схема пересоздаётся, данные теряются): `FRESH=1` в `environment` сервиса `helpdesk` в
`services/compose.yaml` или при запуске руками.

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя через `ADMIN_DSN` и `APP_DSN`
   (роль приложения `helpdesk_app` сервис создаст сам).
2. `services/helpdesk/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс, запустит сервер.
   PowerShell по шагам:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\helpdesk
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://helpdesk_app:helpdesk-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8083 (порт — `PORT`). Интерфейс с горячей перезагрузкой — `cd web && npm run dev` (5183).

Переменные: `ADMIN_DSN`, `APP_DSN`, `SCHEMA` (по умолчанию `helpdesk`), `PORT` (8083), `HOST` (127.0.0.1),
`SIGNALS` — режим сигналов установки (`tenant`), `FRESH=1` — пересоздать схему, `DEMO_MAIL=0` — выключить демо-почту.

**Демо-почта — только для своей машины.** `/mail` показывает коды входа всем, кто её открыл, то есть позволяет
войти по коду за любого. Сервис слушает 127.0.0.1, а в контейнере порт открыт только на 127.0.0.1; наружу стенд не
публикуют. В настоящем сервисе `mail()` отдавал бы письмо почтовому шлюзу, а демо-почты не было бы.

## Подключить настоящего ИИ-агента

Войдите агентом → «Помощник» → «Выдать ключ для агента» или «Сессия агента на 15 минут». Страница покажет команду
для Claude Code:

```sh
# ключ API
claude mcp add --transport http helpdesk "http://127.0.0.1:8083/mcp?tenant=<компания>" \
  --header "Authorization: Bearer <ключ>"
# короткая сессия: компанию она помнит сама
claude mcp add --transport http helpdesk "http://127.0.0.1:8083/mcp" \
  --header "Authorization: Bearer <токен сессии>"
```

Агент получит инструменты `letopis_model`, `letopis_query`, `letopis_history`, `letopis_write` с правами того,
кому выдан ключ или сессия. Правка — только с номером прочитанной версии `rev`. «Проверить доступ агента» вызывает
`/mcp` с токеном сессии без cookie вкладки — так, как это сделает агент.

Чем сессия агента отличается от ключа и от «Работать от имени» (по коду `lib/src/auth.ts`, `lib/sql/80-auth.sql`,
`lib/sql/20-context.sql`):

| | ключ API | сессия агента | «Работать от имени» |
|---|---|---|---|
| вызовы | `auth.issueApiKey({ account })` | `auth.sessionFor(account, { ttl: 900 })`, `connect({ sql, token, refreshSession: false })`, `auth.switch(компания)` | `svc.as(account, { tenant })` |
| что в базе | кред `APIKEY` (учётные данные для входа, как пароль): он есть в `auth.credentials()` | сессия со способом входа `SERVICE`. Это не кред: в `credentials()` её нет, выданные сессии помнит сервис | своей сессии нет: в каждой транзакции сервис называет базе учётную запись, от имени которой работает (`letopis.account`, право `auth.impersonate`) |
| срок | пока не отзовут | 15 минут от выдачи: работа агента срок не продлевает | пока жива сессия сервиса |
| как закрыть | `revokeCredential` — гаснут сессии этого ключа | «Погасить» — `auth.revoke()` её подключением; выход из вкладки, которая её выдала; «Выйти на всех устройствах» (`revokeAll`) | «Вернуться к себе» |
| компания | `?tenant=` в адресе | `auth.switch` при выдаче — база помнит компанию в сессии | `{ tenant }` в `as()`; у подключения `svc.as()` нет `auth.switch` |
| журнал | автор — вы, исполнителя нет | автор — вы, исполнителя (`agent`) нет: что сессию выпустил сервис, видно только в `auth.session(token).methods` | автор — тот, от чьего имени работают, исполнитель (`agent`) — сервис |

Поэтому «Работать от имени» в интерфейсе сделано на `svc.as`: журнал называет исполнителем сервис, а причина правки —
руководителя. Сессию агента сервис выдаёт только на себя: работая от имени, её не получить (409), иначе токен с
правами другого человека ушёл бы из сервиса.

## Проверки

- `node services/helpdesk/scenario.mjs` — «день работы» через HTTP и настоящий клиент MCP. Схема своя
  (`helpdesk_scenario`) и каждый раз создаётся с нуля. Сценарий проверяет:
  - вход с TOTP и по коду из письма, отключение TOTP только верным кодом; клиент видит только свои заявки;
  - очередь по курсору, запрет удаления, версию `rev`, ключи API и MCP;
  - сессию ИИ-агента (`sessionFor`): способ входа и срок; в `credentials()` её нет; у версий агента автор без
    исполнителя; после «Погасить» и «Выйти на всех устройствах» — 401;
  - переход между компаниями, работу от имени, «Завершить сеансы» и удаление из компании;
  - регистрацию (модель новой компании та же, что у «Севера») и закрытие компании.
- `services/helpdesk/CHECK.md` — проверка в браузере по шагам.
