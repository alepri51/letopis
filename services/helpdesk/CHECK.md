# Helpdesk — проверка в браузере (chrome-devtools-mcp)

Стенд: `docker compose -f services/compose.yaml up --build`, сервис — http://127.0.0.1:8083. Демо с нуля — `FRESH: '1'`
в `environment` шага подготовки `helpdesk-setup`. Проверка — на свежем стенде: `docker compose -f services/compose.yaml
down -v`, затем `up --build` (том базы один на все сервисы; на несвежем `guest@sever.ru` уже в команде — шаг 3 получит
409, у агента может остаться второй фактор прошлого прогона — шаг 5 откажет без кода, а новая заявка шага 9 уйдёт за
первую страницу очереди).
Проверка идёт без участия человека, через chrome-devtools-mcp. Пароли, коды из писем, коды приглашений и коды TOTP
вводятся в поля формы. Код TOTP вычисляется из секрета, который показывает страница «Безопасность», функцией
`totpCode(секрет)` из `letopis`.

| № | Шаг | Ожидаемо |
|---|---|---|
| 1 | Вход: `boss@sever.ru` и неверный пароль | «Неверный email или пароль», страница входа остаётся |
| 2 | Вход: `boss@sever.ru` / `Sever-2026!`, затем «Показать ещё» | очередь «Севера» по сроку ответа, показатели и панель «Под капотом»; «Показать ещё» догружает вторую страницу; пункта смены компании в меню нет — ключ открывает одну компанию |
| 3 | «Команда»: пригласить `Гость` / `guest@sever.ru` с ролью «клиент» | «Гость: приглашение отправлено»; приглашение — в таблице приглашённых (роль, срок ссылки, «Отменить»); в демо-почте — письмо со ссылкой «Открыть приглашение»; в логе сервиса — строка почтальона-заглушки. «Под капотом»: `me.invite(…)` |
| 4 | «Интеграции»: выдать ключ с назначением «форма на сайте» | окно с ключом (он показан один раз) и примером `curl`; ключ в списке, «действует». «Под капотом»: `me.invite` аккаунта интеграции, `db.accept(token)` сервисом, `robot.keys.issueApiKey` |
| 5 | Выйти; вход агентом `agent@sever.ru` / `Agent-2026!` | очередь «Севера» |
| 6 | «Безопасность» → «Подключить приложение-аутентификатор»; ввести неверный код, затем код из секрета | QR-код и секрет; неверный код — «Неверный код — фактор не включён»; верный — «Второй фактор включён…» |
| 7 | Выйти и снова войти агентом: пароль, затем код TOTP следующего 30-секундного интервала (код, которым включили фактор, второй раз не примут). Выйти и войти «Кодом на почту»: код из письма, выбрать «Север», затем код из приложения ещё не использованного интервала | после пароля — экран «Второй фактор» (letopis ответил `api.totp_required`: пароль верен, нужен код); с кодом — очередь. В письме — один код; после него — экран «Выберите компанию» («Север», «Байкал»: `db.tenantsOf`), после «Севера» — снова экран «Второй фактор», с кодом из приложения — очередь «Севера» |
| 7а | «Безопасность» → «Отключить второй фактор»: неверный код, затем код ещё не использованного интервала. Выйти и войти агентом по паролю | неверный код — «Неверный код — второй фактор не отключён»; верный — «Второй фактор отключён. Другие ваши сессии в компании закрыты, эта осталась»; вход — без кода из приложения |
| 8 | Вторая вкладка в отдельном контексте браузера (cookie у вкладок одного контекста общие): «Код на почту» для `client@sever.ru`, «Прислать код», код из демо-почты | в письме — код (`db.requestCode`, доставил почтальон-заглушка); компания у клиента одна — вход сразу в «Север»; клиент видит только свои обращения |
| 9 | Клиент: новое обращение — тема, текст, приоритет «высокий» | «Обращение HD-… создано»; во вкладке агента заявка появилась сама |
| 10 | Агент: открыть заявку с клавиатуры (Tab до строки очереди, Enter), «Взять себе», затем ответ клиенту и внутренняя заметка | у клиента — ответ и статус «ждёт клиента», заметки нет. В «Под капотом» агента — версии `Ticket` (изменены `status`, `assignee`…), `Reply` и `Note`, сигналы `Ticket`, `Reply`, `Note`: только имена классов, без токенов квартиры. После закрытия карточки (Esc) фокус — на строке заявки |
| 11 | Агент: «Удалить» | «Нет прав…» — отказ базы; заявка на месте |
| 12 | Агент: «История» | версии со статусами, авторами и причинами |
| 13 | Агент: «Помощник» → «открытые заявки», затем «ответь на HD-…: …» → «Разрешить» | вызовы MCP видны; перед записью — окно «Помощник просит разрешения»; ответ записан только после «Разрешить» |
| 14 | Третья вкладка в отдельном контексте: вход `agent@sever.ru` / `Agent-Baikal-2026!` | очередь «Байкала», заявок «Севера» нет: тот же email, другой пароль — ключ другой квартиры |
| 15 | В отдельном контексте браузера открыть ссылку из письма шага 3 («Открыть приглашение» в демо-почте): имя, пароль от 8 знаков (можно не задавать) | страница показывает компанию «Север», роль «клиент», кто зовёт и срок; после «Принять и войти» — вход клиентом «Севера»; у руководителя в «Команде» гость появился, приглашение из таблицы исчезло. Та же ссылка ещё раз — «Приглашение уже принято — попросите новое» |
| 16 | Руководитель: «Работать от имени» гостя, создать обращение, «Вернуться к себе» | баннер «Вы работаете от имени …»; в истории заявки автор — гость, исполнитель — сервис; в «Под капотом» — версия заявки, записанная от имени гостя |
| 17 | Руководитель: «Удалить из компании» у гостя | вкладка гостя при следующем действии возвращается ко входу; войти снова ему нечем — ни пароль, ни код на почту не подходят |
| 18 | Регистрация своей компании: название, имя, email → в демо-почте письмо → «Открыть приглашение» → страница приглашения: имя и пароль; затем «Команда» → «Закрыть компанию» → «Закрыть навсегда» | после регистрации — экран «Проверьте почту»; страница приглашения показывает компанию, роль «руководитель» и срок; после принятия — очередь новой компании, вы руководитель; «Компания закрыта: стёрто строк …», затем страница входа |
| 19 | Агент: «Помощник» → «Временный ключ на 15 минут», «Проверить доступ агента». Затем вызвать `/mcp` с этим ключом без cookie, как это сделает агент (`curl` или `fetch(…, { credentials: 'omit' })`): `letopis_write` меняет статус заявки с её `rev`. Открыть «История» заявки. «Отозвать» в списке и снова «Проверить доступ агента» | ключ до … (15 минут), команда `claude mcp add` с адресом `/mcp`; «агент видит открытых заявок: N». В «Под капотом» запись «Временный ключ для ИИ-агента» — `me.keys.issueApiKey({ name, ttl: 900 })` и `me.keys.list()`; запись «MCP агента: tools/call letopis_write» — версия `Ticket` (изменено `status`) и сигнал `Ticket`. В истории заявки автор — сам агент поддержки, исполнителя нет, причина `mcp: letopis_write`. После «Отозвать» — «401: ключ отозван или истёк…», в списке ключа нет |
| 20 | Консоль и сеть | ошибок JavaScript и ответов 5xx нет; ответы 4xx — только намеренные отказы (браузер пишет их в консоль как «Failed to load resource») |

Интерфейс — React и блоки shadcnblocks (`web/`), сервис отдаёт JSON API и `/mcp`. Сценарий `node scenario.mjs`
проверяет то же самое через HTTP и настоящий клиент MCP — и ещё сбой посреди регистрации, вторую компанию того же
человека со своим паролем и «Выйти на всех устройствах».

Прогона в браузере на нынешней версии ещё не было: сценарий `scenario.mjs` пройден целиком на PostgreSQL 18 (свой дом,
в конце снесён).
