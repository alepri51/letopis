# Helpdesk — проверка в браузере (chrome-devtools-mcp)

Стенд: `docker compose -f services/compose.yaml up --build`, сервис — http://127.0.0.1:8083. Демо с нуля — `FRESH=1`.
Проверка — на свежем стенде: `docker compose -f services/compose.yaml down -v`, затем `up --build` (том базы один на все
сервисы; на несвежем `guest@sever.ru` уже заведён — шаг 3 получит 409, у агента может остаться второй фактор прошлого
прогона — шаг 5 попросит код, а новая заявка шага 9 уйдёт за первую страницу очереди).
Проверка идёт без участия человека, через chrome-devtools-mcp. Пароли, коды из писем и коды TOTP вводятся в поля формы.
Код TOTP вычисляется из секрета, который показывает страница «Безопасность», функцией `totpCode(секрет)` из `letopis`.

## План 2.0: права через MCP

- Клиент (вход по коду) на странице помощника и через `/mcp` видит только инструменты чтения: `letopis_write` нет.
  Сотрудник и ключ API агента пишут; ключ интеграции — только читает, внутренние заметки и профили ему закрыты.

## План 2.0: правила обёрткой db.acl

- Правила компании пишет обёртка прав `db.acl` (список `ACL`), ресурсы прежних версий удаляются. Клиент не пишет в
  счётчик заявок и напрямую в базе (`acl_denied`), видит только свои заявки (условие `owner: '$actor'`); номер заявки
  выдаёт сервис от имени руководителя — клиент и ключ интеграции заявки создают (7.9 №2). Сценарий — 73 из 73.

## План 2.0: сбой посреди регистрации

- Регистрация компании прервалась после того, как компания и руководитель заведены (сценарий имитирует это
  переменной `HELPDESK_FAIL_REGISTER`): ответ 500, компания без строки Desk. Повтор с тем же названием, email и
  паролем достраивает её и входит руководителем; заявка в ней создаётся. Повтор с чужим паролем и то же название
  другим человеком — 409. Если человек успел включить TOTP, повтор регистрации — 409: сессию по одному паролю сервис не выдаёт, только вход с кодом.
