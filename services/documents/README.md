# Документы с аудитом — сервис-пример letopis

Договоры с полной историей: каждая правка — новая версия с автором и причиной. Что показывает сервис:

- черновик подписывают — он становится договором (`reclass`); номер можно сменить (`rekey`). Обе операции меняют id
  документа, но лента версий (`versions({ follow: true })`) идёт через обе смены;
- любые две версии можно сравнить (`diff`), узнать, кто последним менял поле (`blame`), и открыть документ на любой
  момент ползунком (`asOf`);
- удаление — с предпросмотром: `delete()` без подтверждения ничего не удаляет, а показывает, что удалится. Удалённое
  попадает в корзину: оттуда его можно вернуть (`restore`) или стереть навсегда (`purge`);
- персональные данные контрагента можно обезличить (`anonymize`);
- история хранится по ярусам: свежие версии — все, старше — по одной на день, неделю, месяц, год. Лишние версии
  удаляет прореживание (`maintain`), а историю документа можно обрезать до даты (`trimHistory`);
- архив старых договоров залит с историей первой заливкой — быстрой загрузкой в пустую схему
  (`db.load(…, { initial: true })`);
- целостность журнала (`log`, все версии всех объектов) проверяет `verify`: каждая версия хранит хэш предыдущей,
  поэтому правка в обход библиотеки видна. Проверить это можно кнопкой «Испортить запись журнала».

Интерфейс собран из блоков **shadcnblocks** (`login1`, `navbar1`, `stats8`, `changelog1`) и компонентов shadcn/ui.
Описание со схемами — http://127.0.0.1:8080/services/documents.

Панель «Под капотом» показывает, что сделало действие: цепочки letopis и запросы к базе (`onQuery`), версии, которые
оно записало (из журнала `log`: класс, номер документа, номер версии `rev`, вид операции `op`, причина, изменённые
поля), и сигналы об изменении классов, в которые оно записало (`flushSignals()`; только имя класса). У подписания и
смены номера там видны новая версия нового id и надгробие прежнего id — версия `delete`: объекта нет, история есть.
Код панели общий для четырёх сервисов — `services/shared/`.

## Модель

`src/models.mjs`: контрагент `Party` и семейство документов `Doc` с потомками `Draft` (черновик) и `Contract`
(договор). Классы принадлежат арендатору (владельцу данных) — фирме «Право и Дело». При каждом запуске их записывает
`syncModels` — через администраторское подключение letopis (`ADMIN_DSN`, `allowBypassRls`: построчные правила доступа
базы, RLS, на него не действуют), а не через сессию пользователя. Сессия руководителя у этого подключения — токен
`createTenant` только на эту запись: после неё сессия гаснет (`revoke`), подключение закрывается. Установку обслуживает
другое администраторское подключение — без сессии: `verify` и `maintain` пускает его роль, архив `load` пишет в
арендатора фирмы, названного явно (`tenant`). Обрезке истории (`trimHistory`) нужна живая сессия с правами READ и
DELETE на документ — роль подключения её не заменяет. Поэтому сессия руководителя выдаётся на каждую обрезку:
`svc.auth.sessionFor`, подключение с её токеном, `auth.switch` в фирму, после обрезки — `revoke`. Постоянного токена у
сервиса нет: прежний после простоя дольше срока сессии давал обрезке отказ `no_session`.

Будь классы в System (системном арендаторе с общими классами установки), правка модели не дошла бы до уже работающей
установки: классы System `syncModels` пропускает — их меняет только установка, а её сид (набор классов, который ставит
`up()`) не трогает класс, который уже есть.

## Запуск в Docker

```sh
docker compose -f services/compose.yaml up --build documents   # http://127.0.0.1:8084
```

## Запуск руками, без Docker

1. База: `docker compose -f services/compose.yaml up -d pg` или своя: `ADMIN_DSN` — подключение администратора,
   `APP_DSN` — роли приложения (роль `documents_app` сервис создаст сам).
2. `services/documents/run-local.sh` — соберёт библиотеку, поставит зависимости, соберёт интерфейс и запустит сервер.
   В PowerShell — те же шаги:
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\documents
   npm install; cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://documents_app:documents-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8084 (порт задаёт `PORT`). Интерфейс с горячей перезагрузкой: `cd web && npm run dev`,
   порт 5184.

Переменные: `ADMIN_DSN`, `APP_DSN`, `SCHEMA` (по умолчанию `documents`), `PORT` (8084), `HOST` (127.0.0.1),
`FRESH=1` — пересоздать схему (демо с нуля). Установка ставится с `allowReset: true` — флагом для тестовых баз: без
него `maintain({ now })` («как будто сейчас — через N дней») отказывает. В рабочей установке флаг не включают.

## Проверки

- `node services/documents/scenario.mjs` — «день работы» через JSON API: черновик, конфликт версии, подписание и
  смена номера, лента версий, сравнение, «кто менял», машина времени, корзина, обезличивание, обрезка истории (вторая —
  после простоя: срок сессий `createTenant` руководителя истекает в базе), порча журнала и `verify`, прореживание. Схема
  базы своя (`documents_scenario`) и каждый раз создаётся заново.
- `services/documents/CHECK.md` — проверка в браузере по шагам.
