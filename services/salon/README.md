# Салон записи — сервис-пример letopis

Расписание мастеров, запись клиента без двойной брони, перенос, отмена, возврат и история брони, прайс услуг, отчёт
дня, живое обновление открытых вкладок. Каждый салон — отдельный арендатор (владелец данных в letopis): данные
одного салона другому не видны.
Интерфейс собран из блоков **shadcnblocks** (`login1`, `navbar1`, `stats8`) и компонентов shadcn/ui. Сервер —
Express 5 с JSON API, данные хранит letopis в PostgreSQL 18. Описание со схемами — на сайте документации, страница
«Сервисы-примеры → Салон записи» (http://127.0.0.1:8080/services/salon).

Панель «Под капотом» показывает, что сделало каждое действие: цепочки letopis и запросы к базе (`onQuery`), версии,
которые оно записало (из журнала `log`), и сигналы об изменении классов, в которые оно записало (`flushSignals()`;
только имя класса) — см. `services/shared/trace.mjs`. Цепочка — запрос шагами, например
`db.Org(салон).Staff().rows()`. Журнал `log` хранит все версии всех объектов. Панель читает его под правами сессии и
показывает у версии класс, номер `rev`, операцию `op`, причину, изменённые поля и концы — ссылки на другие объекты.
Сигнал — короткое уведомление базы о том, что данные класса изменились. Журнал действий (`trace.mjs`), веб-сессии
(`sessions.mjs`), подписка `watch()` → SSE (`events.mjs`; SSE — поток событий от сервера в браузер) и сама панель
(`web/UnderHood.tsx`) общие для четырёх сервисов-примеров и лежат в `services/shared/`.

Демо-входы: `admin@lokony.ru` / `Lokony-2026!` (салон «Локоны»), `admin@lastochka.ru` / `Lastochka-2026!`
(салон «Ласточка»).

## Что умеет

- **Запись** — «Записать» у свободного слота. Бронь пишется одной транзакцией под блокировкой мастера
  (`db.begin()` + `lock()`), поэтому двойной брони не бывает. Занятый слот — ответ 409.
- **Перенос** — «Перенести» у брони: мастер и свободный час того же дня. id брони вычисляется из её ключа
  `[Staff, start_datetime]` — мастера и времени начала, а ключ правкой не меняется. Поэтому перенос — это новая бронь
  на новом слоте и удаление прежней одной транзакцией (`db.begin({ reason: 'перенос брони' })`: `create` и
  `delete`). Новая бронь получает новый id, те же концы (клиент, услуга, локация, расписание) и сдвинутое время
  конца — длительность прежняя. У прежнего слота остаётся надгробие (версия удаления: строки нет, история есть) с
  причиной «перенос брони». Это не отмена: в списке «Отменённые в этот день» его нет, вернуть его нельзя (409).
  Блокировка та же, что у записи, а при переносе к другому мастеру блокируются оба, в порядке id. Занятый слот — 409.
  История брони — версии одного id, то есть слота: у новой брони — история нового слота (последняя версия — создание
  с причиной «перенос брони»), а история прежнего слота остаётся у него.
- **Отмена и возврат** — «Отменить» вызывает `delete` с причиной, «Вернуть» — `restore`, и бронь возвращается с тем
  же id.
- **Прайс** (меню «Прайс»). Цена услуги — строка класса `price`. Класс входит в сид `booking` — готовую модель
  салона, которую ставит `up()`. Ключ строки — `[Item, note]`, то есть услуга и вариант цены. Вариант здесь один —
  «базовая», сумма — в рублях.
  «Сохранить» вызывает `upsert`: цены нет — она создаётся, есть — заменяется целиком; те же данные новой версии не
  дают.
  «Загрузить списком» принимает строки вида «услуга; цена», не больше 1000 строк по 200 знаков. Список пишет
  `db.load({ price }, { existing: 'update', as, tenant })` одной транзакцией, через `COPY` от роли владельца схемы.
  Загрузчику нужно администраторское подключение letopis (`allowBypassRls`: построчные правила доступа базы, RLS, на
  него не действуют). Оно одно на все салоны и работает без сессии: автора, арендатора и права загрузчик берёт из
  `as` и `tenant`, поэтому простой сервиса загрузке не мешает — истекать нечему. С `as` автор версий — вошедший; без
  `as` автором была бы служебная учётная запись System. Право
  вошедшего на запись в `price` и то, что услуги ему видны, проверяет сам загрузчик. С `as` арендатор строк по
  умолчанию — личный арендатор аккаунта, поэтому салон сессии передаётся явно, в `tenant`. Новая цена создаётся,
  изменённая получает новую версию, та же пропускается (`skipped`). Услуга не из каталога салона — ответ 422, ничего
  не записано.
- **Отчёт дня** (меню «Отчёт дня») — сколько броней у каждого мастера в выбранный день; считает функция сервиса
  `report()`.

## Запуск в Docker (одной командой)

Из корня репозитория:

```sh
docker compose -f services/compose.yaml up --build salon
```

Откройте http://127.0.0.1:8081. Вместе с салоном поднимется база `pg` (127.0.0.1:15440). Остановить —
`docker compose -f services/compose.yaml down`: данные базы останутся в томе Docker, а `down -v` удалит и их.

## Запуск руками, без Docker

Нужны Node 22+ и PostgreSQL 18 с ролью администратора (суперпользователь или `CREATEROLE`).

1. База. Проще всего поднять только базу стенда:
   ```sh
   docker compose -f services/compose.yaml up -d pg
   ```
   Своя база — задайте строки подключения (роль приложения `salon_app` сервис создаст сам):
   ```sh
   export ADMIN_DSN=postgres://postgres:ПАРОЛЬ@localhost:5432/letopis
   export APP_DSN=postgres://salon_app:salon-app-secret@localhost:5432/letopis
   ```
2. Скрипт делает всё остальное — собирает библиотеку, ставит зависимости, собирает интерфейс и запускает сервер:
   ```sh
   services/salon/run-local.sh            # Git Bash, Linux, macOS
   ```
   То же по шагам (PowerShell):
   ```powershell
   cd lib; npm ci; npm run build; cd ..\services\salon
   npm install
   cd web; npm ci; npm run build; cd ..
   $env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'
   $env:APP_DSN = 'postgres://salon_app:salon-app-secret@127.0.0.1:15440/letopis'
   node src/server.mjs
   ```
3. Откройте http://127.0.0.1:8081 (порт меняет `PORT`).

Разработка интерфейса с горячей перезагрузкой: запустите сервер (шаг 2), затем `cd services/salon/web && npm run dev`.
Интерфейс откроется на http://127.0.0.1:5181, а запросы `/api` уйдут на сервер.

## Проверки

- Сценарий «день работы» через API: `node services/salon/scenario.mjs` с теми же `ADMIN_DSN` и `APP_DSN`. Он
  проверяет вход, гонку двух броней, бронь, отмену, возврат, перенос и отказ 409, историю новой брони и прежнего
  слота, отказ 409 на возврат прежнего слота, отчёт дня, прайс (`upsert`, `db.load`, в том числе после простоя: срок
  сессий `createTenant` управляющей истекает в базе) и разделение салонов. Сценарий можно повторять: в конце он
  отменяет свои брони и возвращает прежние цены.
- Проверка в браузере по шагам — `CHECK.md`.

## Что при старте делает сервис

Сервис ставит схему `v2.salon` с моделью салона: `up({ seeds: ['booking'] })`, повторный запуск безопасен. Затем
создаёт роль приложения `salon_app`, два салона-арендатора (`createTenant`) и их справочники: мастера, услуги,
локация, расписание. Для загрузки прайса он открывает одно администраторское подключение letopis, без сессии. При
этом letopis печатает предупреждение «letopis: администраторское подключение — RLS не действует, данные всех
арендаторов видны» — так и должно быть. Токены, которые выдаёт `createTenant`, сервису не нужны: справочники он пишет от
имени управляющего (`svc.as`), а сессии `createTenant` гаснут через минуту. Цен при старте нет — их задают на экране
«Прайс».
