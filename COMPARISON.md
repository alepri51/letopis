# Letopis vs ORM/БД-системы: сравнительный анализ

> Дата: 2026-07-16 · Предмет: `lib/` (letopis 0.19.0) + движок `lib/sql/ddl.sql`
> Метод: разбор исходников и бенчмарков letopis, собственный конкурентный анализ автора (`RESEARCH.md`, 31 система) + веб-разведка состояния ORM/темпоральных БД на июль 2026.

> **Разделы 1–8 описывают 0.19–0.21.** Что изменилось в 1.0 — раздел 0 ниже; подробности — `lib/README.md` и `lib/CHANGELOG.md`.

## 0. Что изменилось в 1.0

letopis 1.0 — переписанный пакет на PostgreSQL 18 без TimescaleDB, Redis и Docker: три таблицы (`entity`, `log`,
`secret`), а целостность, изоляция и права перенесены в базу. Оценки разделов 4–5 ниже не пересчитаны.

| Что | 0.21 | 1.0 |
|---|---|---|
| Целостность | триггеры пишут версии, но id v5, проверку данных (fastest-validator) и права считает Node; сырой SQL их обходит | проверяет база: триггеры вычисляют id v5, проверяют данные по JSON Schema (скомпилированной в jsonpath), концы и их цели; сырой SQL от роли приложения проходит те же проверки; цепочка хэшей версий и `verify()` (сняты в 2.0.0) |

| Массовая запись | нет отдельного пути | загрузчик `db.load()` / `letopis load`: проверки в коде, `COPY` от роли владельца, один запрос по целям вне загрузки; полигон salon — 6 359 строк/с против 3 609 у сырых INSERT 0.21 |

## 1. Главный вывод (TL;DR)

**Letopis — не ORM.** Это темпоральное append-only хранилище сущностей поверх PostgreSQL 17 + TimescaleDB с graph-query API «точками», схемой-в-БД (модель HUB/LINK в духе Data Vault) и встроенными auth/ACL/сессиями. Весь CRUD реализован триггерами в самой БД; JS/TS-библиотека — тонкий клиент.

Вердикт по осям:
- **Инновационность — очень высокая.** Комбинация «append-only на Timescale-hypertable + схема-в-БД + fluent-обход графа jsonb + каскадные tombstone-триггеры + детерминированные id» действительно не имеет прямого аналога. Отдельные элементы есть у Datomic, XTDB, Gremlin, Directus, Data Vault — но не вместе и не в одном лёгком пакете.
- **Зрелость — очень низкая.** Версия 0.19.0, ~неделя разработки, один автор, один потребитель, 181 тест, ноль продовых пробегов, нестабильный API (десяток breaking-релизов за неделю). Это alpha/proof-of-concept, а не production-инструмент.
- **Быстродействие — бимодальное.** Селективные операции — единицы-десятки миллисекунд (отлично); полный скан класса без фильтра — **секунды** (6 с на 440k записей). Это врождённый «темпоральный налог» модели.

Итог: **сильная исследовательская работа и оригинальный дизайн, но не готов к продакшену и решает другую задачу, чем классические ORM.**

## 2. Что такое letopis и почему его трудно сравнивать «в лоб»

Классический ORM (Prisma, TypeORM, Sequelize, MikroORM) решает задачу: *отобразить реляционные таблицы на объекты языка, сгенерировать SQL, дать типы*. Схема живёт в коде, каждая сущность — своя таблица, история не хранится.

Letopis решает другую задачу: *хранить версионируемый граф сущностей, где каждое изменение — новая строка, а история первоклассна*. Ключевые архитектурные решения:

| Аспект | Классический ORM | Letopis |
|---|---|---|
| Где живёт схема | В коде (классы/DSL) | В БД (таблица `Schema`, HUB/LINK) |
| Хранение | Таблица на класс | Единая append-only hypertable `Entity` (jsonb) |
| Изменение данных | UPDATE строки на месте | INSERT новой версии (триггер), старая цела |
| Удаление | DELETE строки | Tombstone + рекурсивный каскад; физический `purge` отдельно |
| Где логика CRUD | В коде ORM | В БД (PL/pgSQL-триггеры) |
| Связи | FK + JOIN | `links: jsonb` + обход графа dot-цепочкой → один SQL с `JOIN LATERAL` |
| История | Нет (нужна аудит-таблица) | Встроена: `asOf`, `versions`, `watch` |
| Auth/ACL | Отдельные пакеты | Встроены в ту же библиотеку |

Поэтому корректнее сравнивать letopis **сразу в двух рамках**: (A) как альтернативу ORM для приложения — где он в основном проигрывает по зрелости и типам, но выигрывает по истории; (B) как облегчённый темпоральный/immutable-store — где его настоящие концептуальные родственники Datomic, XTDB, Dolt.

## 3. Референсный набор для сравнения

- **TS/JS ORM (2026):** Prisma 7.8 (47k★, ~10M/нед), Drizzle 0.45/1.0-beta (35k★, ~11M/нед), TypeORM 1.0 (36.6k★), MikroORM 7.1 (9.1k★, единственный с настоящими Unit of Work + Identity Map), Sequelize 6.37 (плато, v7 в alpha 4.5 года), Kysely/Knex (query builders).
- **Темпоральные/версионные БД:** Datomic (immutable, transaction-time, закрытый код, узкое место — единый transactor), XTDB v2 (open-source, настоящий **bitemporal** valid+system time, SQL:2011), Dolt (git для данных: branch/merge/diff), EventStoreDB/Kurrent (event sourcing).
- **Backend-as-data:** Hasura, PostgREST/Supabase, Directus (`directus_fields`/`relations` — прямой аналог схемы-в-БД letopis).
- **Граф:** Neo4j/Cypher, Gremlin/TinkerPop (`path()` — единственный аналог формата результата-путей letopis), ArangoDB.
- **Важный контекст:** PostgreSQL **не имеет** нативного system-versioning даже в PG18/19 (только application-time). То есть letopis реализует то, чего в ядре Postgres до сих пор нет.

## 4. Оценка по метрикам

### 4.1 Инновационность — 5/5

Самая сильная сторона. Оригинальные и грамотные решения:

- **UPDATE→INSERT через триггер** — не просто версионирование, а способ сделать мутабельные сущности совместимыми с read-only compressed chunks TimescaleDB. Timescale официально не рекомендуют для мутабельных «core entities»; letopis обходит это корректно. Как паттерн нигде не задокументирован.
- **Детерминированный id (UUID v5) по формуле из схемы** → `create` идемпотентен, id известен *до* вставки, двойная бронь убивается на уровне схемы (id брони = хеш от мастера+времени). Этого нет ни у одного ORM.
- **Формат результата-путей** `[{шаг: Row}]` — встречается только у Gremlin `path()`, среди ORM — ни у кого.
- **ACL как SQL-предикаты, вливаемые в WHERE до сортировки/лимита** — не постфильтрация в приложении, а сужение в БД.
- **Live schema reload** без реконнекта + **физический purge** (GDPR hard-erase) поверх append-only через временное отключение триггера (`SET LOCAL letopis.purge='on'`).

Оговорка: инновационность здесь — в *комбинации*. Отдельные кирпичи известны (temporal tables, Data Vault HUB/LINK, обход графа, схема-в-БД у Directus, RLS). Но собрать их в ~5.5k строк TS с **двумя** runtime-зависимостями (`postgres` + `fastest-validator`) — действительно ново. Собственный вывод автора «точного аналога нет» — правдоподобен.

### 4.2 Быстродействие — 3/5 (бимодальное)

Замеры на едином полигоне `v1.salondemo` (~980 000 строк, 440k записей ×2 версии):

**Быстро (селективные операции):**
| Операция | Время |
|---|---|
| Точечное чтение по id | 2–6 ms |
| Фильтр/`count` по каталогу (`gt`/`between`/`like`) | 5–8 ms |
| Агрегации `sum`/`avg`/`min`/`max` | 5–15 ms |
| Цепочка `навык→Услуга`, count 1260 путей | ~65 ms |
| Keyset-страница на суженном классе | 20–31 ms |
| Запись новой версии (в т.ч. со связями) | 8–21 ms |
| Каскадное удаление (серверное) | ~55 ms |

**Медленно (полный класс без фильтра):**
| Операция | Время |
|---|---|
| `count()` всех 440k записей | ~3.4 s |
| `sort('updated').limit()` без фильтра | ~6 s |
| `countBy` по 440k | ~3.3 s |
| Обход всего класса записей | ~6 s |

Причина «медленно» — `DISTINCT ON (id) ... ORDER BY id, updated DESC` по всем версиям класса, когда нет предварительного сужения по GIN-кандидатам. Это фундаментальный компромисс append-only: чтобы получить «срез актуального», надо продедуплицировать все версии. С селективным фильтром сначала — быстро; без него — секунды.

**В сравнении:**
- Обычный ORM на нормализованной таблице сделал бы `COUNT(*)` по 440k за ~50–100 ms, а `ORDER BY ... LIMIT` по индексу — за единицы ms. Здесь letopis платит реальный темпоральный налог. Но взамен даёт полную историю, которой у обычной схемы нет.
- Datomic/XTDB имеют аналогичный налог и **узкое место на записи** (единый transactor). Запись letopis (8–21 ms) на обычном Postgres-конкурентном пуле — в этом смысле здоровее.
- Оптимизации сделаны грамотно: GIN `jsonb_path_ops` для containment, time-only партиционирование (hash-размерности убраны после бенча — они давали цепочки ×2…×140 медленнее и 93 чанка/год против 14), Timescale-сжатие 10–20× для старых чанков.

Вывод: для селективного доступа (реальные пользовательские сценарии — «мои брони», «каталог услуг») — быстро. Для аналитики по всему классу — не инструмент; лечится фильтром/курсором или выносом в отдельный read-model.

### 4.3 Простота разработки (DX) — 4/5

**Сильно:**
- Крайне лаконичный API. Типовой CRUD — одна строка: `await db.Организация(org).Мастер().create({name:'Вася'}).rows()`. Создание брони с 4 связями — одна цепочка в 2 строки.
- Многошаговый план (`create().update().delete()`) автоматически = одна транзакция с откатом. Ручные `BEGIN/COMMIT` нужны только для advisory-lock.
- Русские и английские имена классов равноправны в рантайме (`db.Мастер` ≡ `db.Staff`).
- Ошибки построения цепочки (`no path X → Y`, `unknown class`) бросаются **синхронно**, до похода в БД — быстрый фидбэк.
- README на 3470 строк с **живыми таймингами** каждого метода на реальном полигоне — редкое качество документации для solo-проекта.

**Слабо:**
- **Типобезопасность — ядро динамическое** (`Row.data: Record<string, unknown>`). Типы — опциональная надстройка через кодоген (`db as unknown as TypedDb`), которая читает живую схему из БД. Это принципиально слабее сквозного вывода Prisma/Drizzle/Kysely, где невалидный запрос не компилируется. Для TS-библиотеки в 2026 — заметный минус.
- Новые концепции для освоения: HUB/LINK, pivot, слоты, формат путей, детерминированные id. Кривая входа выше, чем у «таблица→класс».
- Нет GUI/Studio/playground (у Prisma есть Studio, у Drizzle — Drizzle Studio).

### 4.4 Простота поддержки — 2.5/5

**За:**
- Append-only = полный аудит-след и time-travel-отладка бесплатно: можно спросить «как выглядела запись на момент T» (`asOf`). Обычный ORM для этого требует отдельной инфраструктуры аудита.
- `schema-sync` с dry-run: перед миграцией класса прогоняет новый валидатор по живым строкам и печатает, сколько записей сломается — до `--apply`.
- CRUD в БД → даже сырой SQL мимо библиотеки соблюдает те же правила (валидация дублирована в триггере `entity_check`).

**Против:**
- **Bus factor = 1.** Один автор, нет сообщества, нет сторонних мейнтейнеров. Для сравнения: даже «умирающий» Sequelize имеет 2.7M загрузок/нед и открыто ищет мейнтейнеров; у letopis экосистемы нет вообще.
- **API нестабилен**: 0.10–0.17 — сплошные BREAKING за неделю (`set()`→`create()/update()`, `link()` удалён, `execute()`→`run()`). Semver 0.x.
- Логика размазана между TS и PL/pgSQL — отлаживать триггеры сложнее, чем код приложения.
- Жёсткие ограничения окружения: **ESM-only**, только Node 20+, только PostgreSQL 17 + TimescaleDB, Redis для сессий.

### 4.5 Гибкость — 4/5

**За:**
- Схема-в-БД + `reloadSchema()` → можно менять модель данных **в рантайме** без реконнекта и без деплоя кода. Это гибче code-first ORM, где смена схемы = миграция + релиз.
- Граф HUB/LINK: союзы ролей (`{Service|Product|Complex}`), optional-концы, наследование атрибутов по иерархии, pivot для many-to-many без спец-синтаксиса.
- Мультитенантность встроена (`enforceAccount`, `partition`).

**Против:**
- **Только PostgreSQL + TimescaleDB.** Ноль портируемости на другие СУБД (Prisma/TypeORM/Drizzle поддерживают 5–8 движков).
- Осознанно нет произвольного SQL-query-builder за пределами chain-DSL. Нет shortest-path, ограниченная переменная глубина обхода (только `deep()` через recursive CTE). Фильтры в цепочке — преимущественно AND (есть оператор `or()`, но не полноценная булева алгебра как в Kysely).
- Только transaction-time, **не bitemporal** — нет оси valid-time (в отличие от XTDB), нельзя записать «этот факт был истинным с прошлого вторника».

### 4.6 Масштабируемость — 3/5

**За:**
- Наследует хорошо понятную модель масштабирования Postgres: пул соединений, GIN-индексы, time-партиционирование через hypertable, read-реплики.
- Timescale-сжатие старых чанков (10–20×) + опциональный retention — прямой ответ на рост хранилища.
- Ретраи deadlock/serialization, самопереподключение LISTEN.

**Против:**
- **Неограниченный рост хранилища** — каждое изменение это новая строка. Сжатие смягчает, но не отменяет.
- Деградация `DISTINCT ON` на полном классе с ростом объёма (проблема 6 с) — требует дисциплины: всегда начинать цепочку с самого селективного шага, использовать keyset.
- Единственный инстанс Postgres: вертикальное масштабирование + реплики, **нет встроенного шардинга/распределённости**. Datomic масштабирует чтение через peers, XTDB — колоночный Arrow-движок; letopis тут проще и ограниченнее, но зато без экзотики.

### 4.7 Дополнительные метрики

| Метрика | Оценка | Комментарий |
|---|---|---|
| **Типобезопасность** | 2/5 | Динамическое ядро + bolt-on кодоген. Слабее Prisma/Drizzle/Kysely/MikroORM. |
| **Зрелость / экосистема** | 1/5 | v0.19, ~1 неделя, 1 автор, 1 потребитель, 181 тест, 0 продовых пробегов, нет плагинов/интеграций/сообщества. Против Prisma 47k★/10M нед. |

| **Realtime** | 4/5 | `watch()` через `LISTEN/NOTIFY` с авто-переподключением и хуком дочитывания пропущенного. Встроено, в отличие от большинства ORM. |

## 6. Где letopis объективно сильнее / слабее

**Сильнее конкурентов:**
1. История как первоклассная возможность на обычном Postgres — то, чего нет ни в одном мейнстрим-ORM и даже в ядре PG18/19.
2. Идемпотентный `create` через детерминированные id — уникальное решение проблемы гонок/дублей.
3. Один SQL на обход графа любой длины (`JOIN LATERAL`), формат путей как у Gremlin.
4. Встроенный, интегрированный со слоем данных auth+ACL (ACL вливается в SQL до пагинации).
5. Схема меняется в рантайме без деплоя.

**Слабее:**
1. Зрелость: alpha одного автора против индустриальных инструментов с миллионами загрузок.
2. Типобезопасность: динамическое ядро в мире, где Drizzle/Prisma/Kysely дают сквозной вывод типов.
3. Полный скан класса — секунды (архитектурный налог append-only).
4. Привязка к одному стеку (PG17+TimescaleDB+Redis+ESM+Node20).
5. Нестабильный API и отсутствие сообщества/поддержки/аудита.

---

## 7. Кому подходит / не подходит

**Подходит (гипотетически, после дозревания):**
- Домены, где **история и аудит критичны by design**: бронирования, финансовые записи, медкарты, юридические/комплаенс-данные, где «как было на момент T» — требование, а не опция.
- Приложения на PostgreSQL, готовые принять TimescaleDB, где ценна схема-в-БД и рантайм-эволюция модели.
- Проекты, которым нужен встроенный auth/ACL/мультитенантность без сборки зоопарка пакетов.

**Не подходит:**
- Продакшен сегодня — из-за alpha-статуса, bus-factor 1 и нестабильного API.
- Аналитические нагрузки с частыми полными сканами классов.
- Мультибазовые/портируемые проекты, edge/serverless (там правит Drizzle), команды, которым нужен сквозной type-safety.
- Кто не может/не хочет TimescaleDB.

---

## 8. Итоговый вердикт

Letopis — **концептуально одна из самых оригинальных работ в нише за последнее время**: он берёт идеи Datomic/XTDB (immutable, time-travel), Data Vault (HUB/LINK), Gremlin (обход-пути) и Directus (схема-в-БД) и собирает их в лёгкую MIT-библиотеку на две зависимости, реализуя на Postgres то, чего в ядре Postgres нет. Дизайн-решения (детерминированные id, каскад в триггерах, ACL-в-SQL, live reload, purge поверх append-only) — грамотные и небанальные.

Но между «инновационным дизайном» и «инструментом, который можно взять в продакшен» — дистанция, которую letopis ещё не прошёл: одна неделя разработки, один автор, один потребитель, ноль продовых пробегов, слабая типобезопасность, нестабильный API и врождённая просадка на полных сканах. Классические ORM (Prisma, Drizzle) решают другую, более узкую задачу — но решают её зрело, типобезопасно и с огромной экосистемой. Ближайшие настоящие родственники (XTDB, Datomic, Dolt) — тяжелее и специализированнее, но проверены в бою; XTDB вдобавок богаче (bitemporal).

**Оценка: отличный R&D-проект и потенциально ценная ниша (темпоральный store на Postgres с graph-API), но по совокупности метрик — pre-production. Ценность сейчас — в идеях и дизайне, а не в готовности к эксплуатации.**
