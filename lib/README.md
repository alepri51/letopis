# letopis 1.0 — в разработке

> Эта ветка переписывает letopis по плану `reports/PLAN-LETOPIS-1.0.md`. Пакет 1.0 ещё не опубликован.
> Документация действующей версии 0.21 — в теге `v0.21.0`: `git show v0.21.0:lib/README.md`.

letopis 1.0 — хранилище версионированных сущностей на PostgreSQL 18. Целостность, история,
изоляция арендаторов и права проверяет сама база: триггеры и политики RLS действуют и для
библиотеки, и для сырого SQL. Поверх базы — цепочки вида `t.Мастер(vasya).запись().rows()`.

Разделы ниже заполняются по этапам плана; окончательный текст пишется на этапе 8.

## 1. Быстрый старт

Появится вместе с `up()` и `connect()` (этапы 1, 2 и 6).

## 2. Устройство

Три таблицы (`entity`, `log`, `secret`), две роли (`letopis_owner`, `letopis_app`), проверки в
триггерах и политиках RLS. Подробно — §2 плана.

## 3. Имена

Шаг цепочки называется именем класса, его алиасом или именем роли (конца): `db.Staff(…)`, `db.Мастер(…)`,
`db.Folder(f).Parent()`. Имена ниже Proxy разбирает раньше классов, поэтому класс с таким именем недостижим
как шаг, а связь с таким именем база не примет (`reserved_names()`; список подставляет установщик из
`RESERVED_CLASS_NAMES`, `lib/src/types.ts`).

- методы цепочки: `then`, `entity`, `paths`, `rows`, `first`, `ids`, `count`, `limit`, `offset`, `sort`, `asOf`,
  `withDeleted`, `deep`, `exact`, `sum`, `avg`, `min`, `max`, `countBy`, `after`, `versions`, `create`, `update`,
  `upsert`, `set`, `unset`, `add`, `remove`, `delete`, `anonymize`, `reclass`, `restore`, `purge`, `alias`, `tags`,
  `owner`, `forUpdate`, `cache`, `rekey`; охранники снесённого API — `run`, `execute`, `account`;
- корень `db`: `as`, `begin`, `commit`, `rollback`, `lock`, `batch`, `watch`, `close`, `registry`, `sql`, `load`,
  `verify`, `maintain`, `reset`, `describe`, `auth`, `acl`, `idOf`, `refresh`, `transaction`, `flushSignals`,
  `schema`, `token`, `tenant`, `trimHistory`, `rekeyClass`, `cache`; охранники — `reloadSchema`, `accounts`,
  `credentials`, `resources`, `rules`, `compact`;
- батч: `discard`, `size`.

## 11. API

Заполняется по этапам 2–6. Этап 3 — чтение цепочками:

```ts
const db = await connect({ dsn, schema: 'v2.salon', token, models: BOOKING })   // models — только для типов
await db.Org(org).Staff({ specialization: 'барбер' }).skill().Service().rows()  // хаб → хаб → связь → хаб
await db.Folder(f).Parent().rows()                 // шаг-роль: родительская папка
await db.Person(p).booking().count()               // базовый класс: записи, где p — мастер или клиент
await db.Staff(v).booking().Customer().booking().Item().paths()  // повтор связи — возврат к её узлу
await db.Folder(root).Folder().deep().rows()       // дети любой глубины, $depth
await db.Service(s).asOf('2026-10-07T10:00:00Z').first()        // срез по журналу
await db.Service().withDeleted().rows()            // с удалёнными ($deleted)
await db.Service().sort('data.duration', 'desc').after(cursorOf(last, 'data.duration')).limit(20).rows()
```

- Фильтр шага: id, список id, строка ответа, `or(…)`, объект полей любой глубины с операторами (`gt`, `between`,
  `inList`, `like`, `has`, `exists`, `not`, …) и роли концов: `{ Customer: id }`, `{ Customer: null }`.
- Модификаторы: `limit`, `offset`, `sort('at' | 'rev' | 'id' | 'data.<путь>', dir)`, `after(cursor)`, `asOf`,
  `withDeleted`, `deep(max)`, `exact`, `alias`, `tags`, `owner`, `entity(цепочка | строка)`.
- Терминалы: `rows`, `first`, `ids`, `count` (сущности; `{ paths: true }` — пути), `paths`, `versions`, `sum`, `avg`,
  `min`, `max`, `countBy`. Строка ответа: `id`, `class`, `rev`, `tenant`, `owner`, `links`, `data`, `tags`, `at`,
  `author`, `op` и, если есть, `agent`, `reason`, `moved`, `$deleted`, `$depth`.
- Переход: шаг-роль идёт своим концом; иначе — концами всех классов обоих семейств: в своём семействе — к детям,
  хаб → связь — назад, связь → хаб и хаб → хаб — вперёд. Под RLS id находят функции владельца `find_ids()`,
  `find_hop()`, `find_deep()` (индексы GIN), строки читаются по первичному ключу.

Этап 4 — запись цепочками, транзакции, батч, загрузчик:

```ts
await db.Org(org).Staff().create({ name: 'Вася', phone: '+7 900' }).rows()     // концы из пути: { Org }
await db.Staff(s).booking().create({ start_datetime, end_datetime })
  .Customer.set(c).Item.set(svc).Location.set(loc).Schedule.set(sch).rows()    // слоты концов
await db.Customer(c).booking({ notes: 'x' }).update({ notes: 'y' }).rows()     // слияние патча в базе
await db.Wallet(w).update({ balance: inc(-300) }).first()                       // приращение, без чтения
await db.Wallet(w).update({ balance: 700 }, { rev: 3 }).first()                 // строгий режим: conflict
await db.Service().upsert({ Org: org, name: 'Стрижка', duration: 45 } as never).first()  // $upsert
await db.Service(s).delete().rows()                // превью: $action delete | unset | restrict
await db.Service(s).delete({ confirm: true }).rows()                            // удалённое: $deleted
const tr = await db.begin()                        // явная транзакция read committed
await tr.Wallet(w).forUpdate().first()             // чтение с блокировкой
await tr.commit()
const b = db.batch('импорт'); b.Service().create({ … }); await b.run()          // одна транзакция
await adm.load({ Org: orgs, Staff: staff })        // загрузчик: администраторское подключение
```

- Глаголы — звенья плана: `create`, `update(patch, { rev })`, `upsert`, `delete({ confirm })`, `anonymize(поля)`,
  `reclass(класс, данные)`. Терминал исполняет весь план одной транзакцией; продолжение после глагола идёт от его
  результата (create и upsert — по строке, остальные — от всех строк), глагол сразу после глагола пишет в те же
  сущности; ошибка любого сегмента откатывает план. Модификаторы до глагола (`limit`, `sort`) сужают его цели.
- `create` только создаёт: занятый ключ — `exists` с id (вычисляет `idOf`); замена целиком — `upsert` (класс с ключом,
  иначе `no_key`); `update` никогда не создаёт; `data.id` — цель `update`, если у шага нет фильтра.
- Концы создаваемой строки — из пути (шаг, на который она ссылается) и слотов `.Роль.set/unset/add/remove`.
  Из нескольких подходящих ролей — без занятых слотами, затем роль с именем класса шага, иначе `invalid_query`.
- `inc(n, { start })` — маркер, который не получить из JSON; база прибавляет величину функцией `inc` внутри оператора.
  Поля нет — ошибка (или `start`); маркер в create, upsert, загрузчике и массиве — `invalid_data` до отправки.
- Если `update`, `delete` или `anonymize` затронули меньше строк, чем шаг нашёл, план откатывается: невидимые —
  `target_not_found`, видимые с другим `rev` в строгом режиме — `conflict`, остальные — `acl_denied`. `{ rev }` —
  только при одной цели (`rev_ambiguous`).
- `db.begin()`: ошибка любого запроса ломает транзакцию — каждый следующий вызов и `commit()` бросают исходную
  ошибку, `rollback()` проходит; `lock(...ключи)` — advisory до конца транзакции; 40P01 — с подсказкой повторить
  весь блок; обрыв связи во время `COMMIT` — `commit_unknown` (и в операциях из пула), без повтора.
- `forUpdate()` — только в `db.begin()` (`tx_required`), с `rows`, `first`, `ids` (`lock_unsupported`): блокировка
  `for no key update` в порядке id; строка, переставшая подходить под условия шага, в ответ не попадает.
- Батч: подряд простые `create`/`upsert` класса с ключом — одна многострочная вставка (повтор id в upsert режет
  группу), `create` класса без ключа — конвейер однострочных; терминал на плане из очереди — `invalid_query`.
- `db.as(аккаунт, { owner })` — тот же пул с `letopis.account` (имперсонацию проверяет база — этап 5) и владельцем
  новых строк.
- Загрузчик `db.load(вход, { duplicates, existing, commitEvery, withHistory, verify, class, tenant })` и
  `letopis load <файлы NDJSON…>`: только администраторское подключение (`allowBypassRls` и право стать владельцем,
  иначе `admin_required`); проверки в коде валидатором на TypeScript, `COPY` от роли владельца, один запрос по целям
  вне загрузки с `for key share`; строка — поля и роли на верхнем уровне, `$class`, `$ext`; ссылка — id,
  `{ $key: […] }` или `{ $ext }` (полиморфная — с `$class`). Ошибка — код первой проблемы и `detail.rows`
  (номер строки, код, нарушения). Режима доверия нет (решение 2 точки А).

### Доступ (этап 5)

```ts
const svc = await connect({ dsn, schema: 'v2.salon', apiKey: SERVICE_KEY })      // сервис: ключ → сессия
const r = await svc.auth.verifyPassword({ identifier: 'anna@salon.ru', password })  // { account, token } | null
const user = await svc.as(r.account, { tenant: org })     // имперсонация: база проверяет право auth.impersonate
await user.booking().create({ start }).rows()             // author — пользователь, agent — сервис
await user.acl.check('booking.create')                    // { allow, rule, code, message }
await user.acl.checkData('booking', 'READ')               // { allow, filter }
const tok = await svc.auth.sessionFor(r.account, { ttl: 600 })   // короткая сессия для другого процесса
```

- Права включены всегда и по умолчанию запрещают. Правила — строки `Resource` (группа `ACCOUNT` по категориям
  аккаунта или ролям членства, эндпоинт `API`, объект строк `READ`, `WRITE`, `DELETE` — маска класса с предками
  и условие на колонки `id`, `owner`, `tenant`, `tags`, `data`, `links`, значения `$actor` и `$tenant`) и `rule`
  (группа → объект, `allow` | `deny`, вес). Решение — ровно одно правило: наибольший вес, при равном запрет
  сильнее, из равных — объект с меньшим alias. Вес правила арендатора — не больше 999: правила System с весом от
  1000 — административный слой, который арендатор не перевесит. Правила арендатора действуют на его строки, правила System — везде;
  группа по ролям совпадает только в правилах того арендатора, где у пользователя роль.
- Строки видят и правят только по плану прав (политики RLS) — и библиотека, и сырой SQL; без права строка не
  видна, правка — пусто или `acl_denied`, новые значения вне условия — `acl_denied`. Каскад удаления требует
  права `DELETE` на каждую удаляемую строку, снятие конца — `WRITE`; цель ссылки должна быть видна.
- Аккаунты лежат в System, их категории правит только системный администратор (член System с ролью `admin`).
  Права `auth.*` (имперсонация, выпуск сессий, креды) и `letopis.*` (`verify`, `reset`, `maintain`) решают
  только правила System.
- `db.auth`: `setPassword`, `verifyPassword`, `issueApiKey`, `verifyApiKey`, `issueKeySecret`,
  `verifyKeySecret`, `enrollTotp`, `verifyTotp`, `totpEnabled`, `issueOtp`, `verifyOtp`, `link`, `lookup`,
  `credentials`, `revokeCredential`, `setFlags`, `sessionFor`, `refresh`, `revoke`, `revokeAll`, `switch`,
  `tenants`. Свои креды аккаунт привязывает сам только после недавнего интерактивного входа (10 минут; ключ API
  и сессия от сервиса не в счёт, при включённом TOTP — с пройденным TOTP) и не подтверждает их сам; креды
  System, сервисов и системных администраторов меняет только сам аккаунт или системный администратор.
  Вход по одноразовому коду и проверку TOTP вызывает сервис (права `auth.otp`, `auth.totp`): счётчики попыток
  транзакционные, частоту ограничивает сервис. Продление сессии — не дольше срока, выданного при входе.
- Пропуск прав: библиотека один раз берёт у базы подписанный план прав актора (`acl_token()`) и передаёт его в
  каждой транзакции (`letopis.acl`) — проверка прав стоит десятки микросекунд вместо сотен. Устаревший пропуск
  база не принимает и считает план сама.
- Загрузчик от имени пользователя: `db.load(rows, { as: account, tenant })` — право `WRITE` на класс, условия
  ACL на строки, видимость целей, владелец по `ownerDefault`, автор — пользователь.

### История, хранение, события, эксплуатация (этап 6)

```ts
await db.Note(id).withDeleted().versions({ follow: true })   // все версии и через смену id (reclass, rekey)
await db.Note(id).restore().rows()                           // удалённый — последним снимком, id прежний
await db.Note(id).purge().rows()                             // превью: $versions; purge({ confirm: true }) — стереть
await db.trimHistory('Note', '2026-01-01')                   // обрезка истории класса, id или строк до момента
await db.Master(id).rekey({ name: 'Василий' }).rows()        // новый ключ — новый id, ссылки переведены
await db.rekeyClass('Room', ['floor', 'code'])               // новый ключ класса для всех строк семейства
for await (const ev of db.watch({ from: cursor, classes: ['booking'] })) save(ev.cursor)
await db.Price().cache({ ttl: 300 }).rows()                  // кэш результатов; класс с cache в модели — без .cache()
await admin.verify({ data: true })                           // цепочки хэшей, якорь; данные, концы, арендаторы, id
await admin.maintain()                                       // сессии, коды, прореживание журнала, очередь сигналов
await admin.reset({ level: 'tenant', confirm: 'v2.salon', tenant })   // sessions | tenant | all
const r = await up({ dsn, schema: 'salon', seeds: ['booking'], history: { all: '1 day', daily: '1 month' } })
```

- У id, у которого в журнале есть запись, номер версии 1 всегда занят: `purge` и обрезка истории кладут на его
  место свою запись (`purge` — число стёртых версий и последний хэш; `trim` — время прежней версии 1). Эти записи
  видны в `versions()`, но не в срезах `asOf` и не в `withDeleted`. `purge` — только для удалённых
  (`not_deleted`), история системных классов не стирается и не обрезается.
- Политика хранения — `history: { all, daily, weekly, monthly, yearly, tz }` у класса (наследуется) или
  `up({ history })` для всех классов без своей: все версии моложе `all`, дальше — последняя версия периода
  (день, неделя с понедельника, месяц, год в поясе `tz`) текущего яруса или любого более крупного; ярус —
  календарно. Не удаляются версия 1, текущая и версии `create`, `delete`, `reclass`, `rekey`, `restore`,
  `purge`, `reset`, `trim`; история удалённого объекта, надгробие которого старше последнего яруса со сроком,
  стирается целиком. Прореживает `maintain()` пачками по 10 000 версий (каждая — своя транзакция).
- `maintain()` — системный администратор, роль с правом `letopis.maintain` или администраторское подключение;
  из нескольких процессов работает один (advisory-блокировка), `connect({ maintain: '1h' })` — по расписанию.
- Подписка `db.watch({ from: 'now' | 'start' | курсор, classes, pollMs })` — асинхронный итератор событий
  `{ cursor, row, id, class, op, rev, at }`: события ниже горизонта завершённых транзакций — без потерь и повторов,
  под RLS журнала; долгая пишущая транзакция задерживает поток (`sub.lag()`); курсор старше яруса `all` —
  `cursor_expired`. Без LISTEN (`connect({ listen: false })`) — опрос.
- Кэш результатов: ключ — запрос, параметры, сессия, актор и арендатор; свои записи сбрасывают ответы сразу
  после фиксации (с классами каскада), чужие — по сигналу базы; права, схема, `db.sql`-запись, погашенная сессия
  и переподключение слушателя — весь кэш или ответы сессии; срок по умолчанию 60 с; в `db.begin()` не работает;
  без LISTEN — выключен (`cache: { ttlOnly: true }` — по сроку). `db.cache.clear()`, `db.cache.stats()`.
- `reset`: флаг `up({ allowReset: true })` (по умолчанию выключен — `reset_disabled` даже для System), право
  `letopis.reset`, подтверждение именем схемы (`confirm_mismatch`); первая запись журнала после сброса — `reset`;
  `all` возвращает новый ключ сервиса.
- `db.verify({ data })` и `letopis verify [--data]` (код 1 при находках): законные разрывы — после записи `trim`
  (стык по её хэшу) и прореживание (пропуск после версии старше яруса `all` класса с политикой); якорь — хэш всех
  голов цепочек, его стоит хранить вне базы.
- `db.auth.purgeAccount(аккаунт)` — удаление аккаунта: системный администратор или владелец его арендатора;
  себя и последнего владельца арендатора нельзя; данные арендатора стираются, владение строками в чужих
  арендаторах переходит им.
- `up()`: ждёт и создаёт базу, проверяет PostgreSQL 18+ и UTF8, `fresh`, `upgrade` (миграции `sql/migrate/`),
  свои сиды (имена или пути), свой ключ сервиса, `ANALYZE` только без статистики; `up({ pglite: true })` —
  база для разработки без PostgreSQL (одно соединение: `connect({ dsn: r.pglite.dsn, listen: false, max: 1 })`).
  `connect()` предупреждает, если ревизия схемы отстала. `db.describe()` и `describeText()` (`letopis describe
  --format text` — llms.txt) — описание модели с метаданными.

## 12. Ошибки

Текст ошибки — `letopis: <код>: <сообщение>`, код — в `err.code`. Коды базы (SQLSTATE класса `LT`, детали — JSON):

| Код | Когда |
|---|---|
| `no_session` | нет действующей сессии (запись, функции владельца) |
| `target_not_found` | цель не найдена — одинаково для несуществующей, чужой и невидимой |
| `invalid_data` | данные не проходят описание класса; `err.issues` — путь, ключевое слово, сообщение |
| `undeclared_end` | конец не объявлен в классе |
| `tenant_denied` | чужой арендатор или нет членства |
| `acl_denied` | отказ по правилам доступа |
| `id_mismatch`, `id_from_db` | id не равен v5 от ключа; id класса без ключа выдаёт база |
| `immutable_key` | ключевое поле, id, арендатор, владелец не меняются (смена ключа — `rekey`) |
| `invalid_class` | описание класса отклонено, класс не найден или абстрактный |
| `use_reclass`, `reclass_denied` | класс с ключом меняется `reclass()`; роли ссылающихся строк не принимают класс |
| `tightening_conflict` | ужесточению описания мешают строки |
| `isolation_level` | удаление, смена класса и ключа — только в `read committed` |
| `recreated_in_statement` | id удалён и создан заново одним оператором |
| `delete_restricted` | удалению мешают ссылающиеся строки (`onDelete: restrict`) |
| `cursor_expired` | курсор подписки старше яруса `all` политики хранения |
| `not_deleted` | `restore` и `purge` — только для удалённых |
| `reset_disabled` | сброс выключен в установке (`allowReset`) |
| `confirm_mismatch` | подтверждение сброса не совпадает с именем схемы |

Коды библиотеки: `exists` (объект уже существует, `detail.id`), `conflict` (`{ rev }` разошёлся), `rev_ambiguous`,
`tx_required`, `lock_unsupported`, `commit_unknown`, `tx_rolled_back`, `no_key`, `admin_required`,
`class_not_loadable`, `invalid_query`, `bypass_rls`, `removed` (снесённое API 0.21 с заменой). Полный машинный
каталог — `docs/api-contract.json`.

## 15. Ограничения

Заполняется на этапе 8: пункты §17 предложения, ограничения из §2 плана и риски из §10. Уже известно:

- символ NUL (` `) в строках данных невозможен: PostgreSQL не хранит его в `jsonb`; такие данные
  отклоняются ещё при разборе JSON (официальный набор JSON-Schema-Test-Suite, группы «nul characters», пропущены).

- Пропуск прав открывает клиенту его собственный план (классы и условия правил, которые к нему применимы).
- Сырой SQL без пропуска прав платит за план прав на каждый запрос: 0,3–1,3 мс в зависимости от числа правил.
- Имена концов `User`, `Tenant` (членство), `Group`, `Object` (правило) заняты системными классами во всей схеме.
- Счётчики попыток OTP и TOTP откатываются вместе с транзакцией вызывающего: частоту попыток ограничивает сервис.
- Самостоятельная привязка занятого идентификатора отвечает `acl_denied` — пользователь с недавним входом так
  узнаёт, что идентификатор занят. Изменения прав во всех арендаторах упорядочены одной строкой счётчика.
- Число невидимых строк, мешающих удалению, и существование аккаунта по id (как цели ссылки) не скрываются.
- Прореженная часть журнала не доказывает ни полноты истории, ни подлинности старых версий: подмену версии
  старше яруса `all` у класса с политикой `verify()` не отличит от прореживания.
- Кэш результатов между процессами устаревает на время доставки сигнала (миллисекунды) и переподключения
  слушателя (десятки миллисекунд); срок `ttl` — предохранитель.
- Курсор подписки «с этого момента» несёт снимок момента подписки, пока не пройдёт его границу: такой
  курсор длиннее обычного.
- `rekeyClass` переносит строки одной транзакцией под исключительной блокировкой семейства, а не пачками:
  между пачками строки со старыми id нарушали бы правило «id — v5 от ключа».
- PGlite — одно соединение: без параллельных писателей и LISTEN; не замена `postgres:18` для гонок и CI.
