# letopis 1.4

**letopis** — библиотека для Node.js, хранилище версионированных сущностей на PostgreSQL 18. Каждое изменение
сохраняется версией в журнале. Поэтому у любого объекта есть история, состояние на любую дату и подписка на
изменения. Целостность данных, изоляцию арендаторов и права доступа проверяет сама база — триггерами и политиками
RLS. Правила одинаково действуют и для библиотеки, и для сырого SQL. Данные читают и пишут цепочками:
`db.Shop(shop).Product({ price: lt(1000) }).rows()`.

[English version](README.en.md) · [Шпаргалка для ИИ-агента](AGENT-CHEATSHEET.md) · [Переход с 0.21](MIGRATION.md) ·
[Изменения по версиям](CHANGELOG.md) · [llms.txt](llms.txt)

Что умеет letopis:

- **Модели на Zod** хранятся в базе как классы: хабы (объекты) и связи (отношения со своими данными) — [раздел 4](#4-модель-данных).
- **Запись цепочками**: `create`, `update` со слиянием, `upsert`, удаление с превью и каскадом, приращение `inc`
  для денег и счётчиков — [разделы 5](#5-запись), [7](#7-удаление-и-восстановление) и [8](#8-транзакции-батчи-и-деньги).
- **Чтение цепочками**: переходы по связям, фильтры, деревья, агрегаты, постраничный вывод — [раздел 6](#6-чтение).
- **История**: версии, срез на дату, что изменилось и кто (`diff`, `blame`), восстановление удалённого, политика
  хранения, проверка цепочки хэшей — [раздел 11](#11-история-и-срезы-на-дату).
- **Арендаторы, вход и права** — в самой базе: пароли, ключи API, одноразовые коды, TOTP, сессии, имперсонация,
  правила доступа — [раздел 10](#10-пользователи-вход-и-права).
- **Подписка на изменения** по курсору без потерь и **кэш результатов** — [раздел 12](#12-подписка-на-изменения-и-кэш).
- **Производные данные**: агрегаты в базе — суммы и счётчики, которые держит сама база, — и проекторы, которые строят
  сводки из журнала, — [разделы 4](#агрегаты-в-базе) и [12](#проекторы).
- **Агенты и MCP**: сервер MCP даёт ИИ-агенту модель, чтение, историю и, если разрешено, запись — с правами одного
  пользователя — [раздел 13](#агенты-и-mcp).
- **Массовая загрузка** миллионов строк и **импорт из 0.21** — [разделы 9](#9-массовая-загрузка) и [14](#14-переход-с-021).

Требования:

- PostgreSQL 18 или новее с расширением pgcrypto (оно входит в стандартную поставку), база в кодировке UTF8.
- Node.js 22 или новее; пакет — модуль ES.
- Рантайм-зависимость одна — `postgres`. Zod 4 — необязательная peer-зависимость: он нужен только подпути
  `letopis/model`, а `import { connect } from 'letopis'` работает и без него. Для разработки без PostgreSQL —
  необязательные `@electric-sql/pglite` и `@electric-sql/pglite-socket`. Серверу MCP (`letopis/mcp` и
  `letopis mcp`) нужна необязательная `@modelcontextprotocol/server` версии 2.4 или новее в линейке 2.

## 1. Быстрый старт

Нужен PostgreSQL 18 и роль администратора: суперпользователь или роль с правом `CREATEROLE`. Установите пакет:

```sh
npm install letopis zod postgres    # postgres — для createTenant и своих SQL-запросов
```

Приложение подключается к базе отдельной ролью, которая состоит в `letopis_app`. Её заводит сама установка: опция
`login` у `up()` создаёт роль с паролем (повтор только обновит пароль) и выдаёт ей `letopis_app`.

Пример ставит схему, заводит магазин с первым пользователем, описывает два класса и работает с ними:

<!-- run: quickstart -->
```ts
import { up, connect, syncModels, inc, gte } from 'letopis'
import { hub } from 'letopis/model'
import { z } from 'zod'

const ADMIN = 'postgres://postgres:secret@localhost:5432/shop'    // администратор: ставит схему
const APP = 'postgres://shop_app:app-secret@localhost:5432/shop'  // приложение: член letopis_app

// 1. Установка схемы v2.shop. login — роль приложения shop_app, tenant — первый арендатор (магазин) и его пользователь Анна.
const r = await up({ dsn: ADMIN, schema: 'shop', login: { user: 'shop_app', password: 'app-secret' },
  tenant: { name: 'Ромашка', user: { name: 'Анна', login: 'anna@shop.ru', password: 'Ромашка-2026!' } } })
// r.serviceKey — ключ сервиса приложения: выдаётся при первой установке, сохраните его

// 2. Сервис приложения входит по ключу, проверяет пароль Анны и работает от её имени в магазине.
const svc = await connect({ dsn: APP, schema: r.schema, apiKey: r.serviceKey! })
const login = await svc.auth.verifyPassword({ identifier: 'anna@shop.ru', password: 'Ромашка-2026!' })
const db = await svc.as(login!.account, { tenant: r.tenant!.tenant })

// 3. Модель: магазин и товар. syncModels записывает описания классов в базу.
const Shop = hub('Shop', { name: z.string() }, { key: ['name'] })
const Product = hub('Product', { sku: z.string(), title: z.string(), price: z.number().int().min(0) },
  { ends: { Shop }, key: ['Shop', 'sku'] })
await syncModels(db, [Shop, Product], { apply: true })

// 4. Запись и чтение цепочками.
const [shop] = await db.Shop().create({ name: 'Ромашка' }).rows()
const [kettle] = await db.Shop(shop).Product().create({ sku: 'K-1', title: 'Чайник', price: 2500 }).rows()
await db.Product(kettle).update({ price: inc(-500) }).rows()      // скидка: база вычитает внутри оператора
const expensive = await db.Shop(shop).Product({ price: gte(1000) }).rows()
const history = await db.Product(kettle).versions()               // две версии: создание и правка

await svc.close()
```

Что здесь произошло:

- `up()` поставил в базу схему `v2.shop`: три таблицы, триггеры, политики RLS, функции и системный сид. Опция
  `tenant` завела арендатора «Ромашка» с правилом «аутентифицированным можно всё» и пользователя Анну с ролью
  `owner` в нём.
- `connect({ apiKey })` обменял ключ сервиса на сессию. `verifyPassword` вернул `{ account, token }` (или `null`,
  если пароль неверный). `svc.as(account, { tenant })` — тот же пул соединений, но от имени Анны в магазине;
  право сервиса на это проверяет база.
- `hub('Product', поля, опции)` описал класс-объект. `ends: { Shop }` — обязательная ссылка на магазин.
  `key: ['Shop', 'sku']` — ключ: id товара вычисляется из магазина и артикула, а второй товар с тем же ключом база
  не примет.
- `db.Shop(shop).Product().create(…)` создал товар, и ссылку на магазин взял из пути цепочки. `inc(-500)`
  уменьшил цену внутри оператора `UPDATE`, без предварительного чтения. `versions()` прочитал историю из журнала.

Повторный вызов `up()` безопасен: он повторно накатывает ту же ревизию и данные не трогает, а ключ сервиса снова не
выдаёт, пока в установке есть хоть один ключ API, кроме отозванных. Дальше раздел 2 объясняет устройство, а разделы 3–13 разбирают задачи по порядку.

## 2. Как устроен letopis

### Основные понятия

| Понятие | Что это |
|---|---|
| установка | схема PostgreSQL `v2.<имя>` с таблицами и функциями letopis; в одной базе их может быть несколько |
| класс | тип данных: имя, поля (JSON Schema), концы и ключ. Описание класса — тоже строка в базе (класс `Class`) |
| хаб | класс-объект: магазин, товар, клиент |
| связь | класс-отношение между объектами со своими данными: строка заказа, навык мастера |
| конец (роль) | ссылка строки на другую строку. У конца есть имя — роль: `Shop`, `Parent`. Концы лежат в `row.links`, поля — в `row.data` |
| ключ | поля и концы, которые определяют объект внутри класса и арендатора. Из них вычисляется id, поэтому уникальность — это ключ |
| id | UUID версии 5: хэш от арендатора, класса и значений ключа; у класса без ключа — от случайной части |
| аккаунт | пользователь, сервис или организация — строка класса `Account` |
| арендатор | аккаунт, в чьих данных идёт работа. Данные разных арендаторов изолированы |
| членство | связь `member` «пользователь — арендатор» с ролями; даёт работать в чужом арендаторе |
| сессия | токен, по которому база узнаёт аккаунт и арендатора. Сервис получает её по ключу API, пользователь — входом |
| версия, журнал | каждое изменение строки — версия в журнале `log` с автором, временем и хэшем |
| надгробие | версия «удалено» с последним снимком объекта |
| цепочка | запрос вида `db.Shop(shop).Product().rows()`: шаги, модификаторы, глаголы записи и терминал |
| терминал | метод, который исполняет цепочку: `rows`, `first`, `ids`, `count`, `paths`, агрегаты |

### Что хранится в базе

Таблиц три. `entity` — текущее состояние: одна строка на каждую живую сущность, включая строки системных классов
(`Class`, `Account`, `Resource`, `member`, `rule`). `log` — журнал: полный снимок каждой версии с автором,
временем, видом операции и хэшем. `secret` — креды, сессии и чекпоинты проекторов: приложение не видит в ней ни
одной строки, с ней работают только функции входа и проекторов.

Классы — тоже сущности. Описание класса лежит в строке `Class`; там же база хранит развёрнутое описание с учётом
предков и скомпилированную проверку данных. Хэш версии — генерируемая колонка: sha256 от хэша прошлой версии и
снимка строки. Поэтому подмену версии выдаёт следующая версия, а у последней — якорь вне базы ([раздел 11](#11-история-и-срезы-на-дату)).

### Кто проверяет данные

Ролей две. `letopis_owner` владеет схемой, таблицами и функциями. `letopis_app` — роль приложения: его
LOGIN-роль состоит только в ней. Всё, что выполняет приложение, — и библиотека, и сырой SQL, — проходит через
триггеры и RLS.

- **Триггеры.** При вставке триггер вычисляет id, подставляет умолчания и проверяет данные по JSON Schema класса
  (схема скомпилирована в jsonpath). Он проверяет концы и их цели, заполняет служебные колонки и пишет версию в
  журнал. Правка сливает патч внутри оператора (`merge`, `inc`). После удаления триггер применяет правила
  `restrict`, `cascade` и `unset` и пишет надгробия.
- **RLS и права.** Политики изолируют арендаторов и применяют правила доступа. В начале запроса база один раз
  строит план прав актора (`acl_plan()`), а на каждую строку остаётся дешёвая проверка `acl_ok`.
- **Контекст запроса** — настройки транзакции: `letopis.token` (сессия), `letopis.tenant` и `letopis.account`
  (арендатор и имперсонация), `letopis.reason` (причина изменения) и `letopis.acl` (пропуск прав, см.
  [раздел 10](#10-пользователи-вход-и-права)). Сессию база ищет по sha256 токена, поэтому без настоящего токена
  настройки ничего не дают.
- **Обход проверок** есть только у кода от имени владельца: у функций владельца (`security definer` с
  фиксированным `search_path`) и у загрузчика на администраторском подключении. `connect()` отказывает роли,
  которая обходит RLS (суперпользователь, `BYPASSRLS`, член `letopis_owner`), если не указано
  `allowBypassRls: true`.

### Как идёт чтение

Под RLS индексы по `data` и по обратным ссылкам политике напрямую недоступны. Поэтому id для шагов цепочки
находят функции владельца `find_ids()`, `find_hop()` и `find_deep()`. Они применяют те же условия арендатора и
прав, что и политика. Сами строки затем читаются по первичному ключу под RLS. Срез на дату строится по журналу.

### Сигналы

Запись сообщает об изменениях через `NOTIFY`. Канал — полное имя схемы установки вместе с версией, например
`v2.shop`; из-за точки в SQL его имя берут в двойные кавычки: `LISTEN "v2.shop"`. Запись сырым SQL на своём
соединении шлёт сигнал из триггера, и PostgreSQL доставляет его при фиксации. Транзакции библиотеки, в том числе
`db.sql` и `db.transaction()`, шлют сигналы отложенно: нотификатор процесса отправляет их раз в 100 мс
(`notifyIntervalMs`), а неотправленные из-за ошибки — повторяет. Что несёт сигнал записи (его нагрузка, payload),
задаёт режим установки `up({ signals })`:

| Режим | Нагрузка сигнала записи | Что видит любая роль, которая может подключиться к базе |
|---|---|---|
| `class` (по умолчанию) | имя класса: `Booking` | имена классов и время записи |
| `tenant` | `Класс@токен арендатора`: `Booking@3f9c…` | ещё и псевдонимы арендаторов |
| `opaque` | `токен класса@токен арендатора`: `9a1e…@3f9c…` | только время и частоту записи по псевдонимам |
| `none` | сигналов нет | ничего |

Токен — 24 шестнадцатеричных знака ключевого HMAC: сопоставить псевдоним с именем может только процесс с ключом
сигналов, а ключ выдаётся сервисам (право `letopis.signals`). Кроме сигналов записи, есть служебные: погашенная
сессия шлёт `session:<16 hex>` (первые 16 шестнадцатеричных знаков sha256 её токена), сброс сессий — `session:*`,
сброс арендатора или всей установки — `*` (сброс всей установки шлёт ещё и `session:*`). В режиме `none` нет и их.
Ни id, ни данных в сигналах нет. По сигналам перечитывается реестр классов, сбрасывается кэш результатов и будится
подписка; что меняет режим для кэша и подписки — в [разделе 12](#12-подписка-на-изменения-и-кэш).

## 3. Установка и подключение

### Установка: `up()`

`up()` ждёт базу и создаёт её, если её нет. Он проверяет PostgreSQL 18 и кодировку UTF8, ставит роли
`letopis_owner` и `letopis_app`, расширение pgcrypto и схему `v2.<имя>` со всеми функциями и системным сидом.
При первой установке он выдаёт ключ сервиса. Вызывайте его от администраторской роли.

| Опция | Что делает |
|---|---|
| `dsn` или `sql` | администраторская строка подключения или готовый пул postgres.js |
| `schema` | имя установки: `'shop'` даёт схему `v2.shop`; можно сразу `'v2.shop'` |
| `tenant` | первый арендатор и его пользователь (см. ниже) |
| `seeds` | сиды после ядра: `'booking'` — демо-домен салона, или пути к своим файлам `.sql` |
| `history` | политика хранения истории для классов без своей ([раздел 11](#11-история-и-срезы-на-дату)) |
| `serviceKey` | свой ключ сервиса вместо случайного: `lts_` и 32–128 шестнадцатеричных знаков |
| `allowReset` | разрешить `db.reset()` ([раздел 13](#13-эксплуатация)); по умолчанию выключено |
| `signals` | режим сигналов: `'class'` (по умолчанию), `'tenant'`, `'opaque'` или `'none'` ([«Сигналы»](#сигналы)); режим хранится в схеме — `up()` без опции его не меняет |
| `fresh` | удалить схему и поставить заново — **данные схемы теряются** |
| `upgrade` | обновить схему старой ревизии: миграции и повторный накат |
| `pglite` | база для разработки без PostgreSQL (см. ниже) |
| `quiet`, `waitTimeoutMs` | без сообщений в консоль; сколько ждать базу (по умолчанию 60 000 мс) |
| `owner`, `app` | имена ролей владельца и приложения (по умолчанию `letopis_owner`, `letopis_app`) |

Результат: `schema` (полное имя), `serviceKey` (при первой установке и при накате, когда в установке не осталось ни
одного ключа API, кроме отозванных: истёкший или выключенный ключ тоже в счёт; иначе `null`), `created`,
`upgraded`, `revision`, `migrations`, `analyzed`, `owner`, `app`, `signals` (режим сигналов установки), `warnings`
(предупреждения, без `quiet` они печатаются), а также `tenant` и `pglite`, если их просили. На PostgreSQL ниже 18.2
`up()` предупреждает: такой сервер мог усечь CLOG, который ещё нужен непрочитанным сигналам, — обновите его.

Несколько экземпляров сервиса могут звать `up()` одной схемы одновременно: накат идёт под блокировкой схемы. Первый
`up()` ставит или обновляет её, остальные ждут и делают повторный накат по готовой (`created: false`,
`upgraded: false`); первого арендатора `tenant` заводит один из них, остальные находят его по имени. `up()` разных
схем одной базы друг друга не ждут.

Скрыть из сигналов имена классов — режим `opaque` (или `tenant`, если имена не секрет, а нужна точность кэша по
арендатору); после смены режима перезапустите процессы приложения — режим читается при подключении:

```ts
await up({ dsn: ADMIN, schema: 'shop', signals: 'opaque' })   // дальше up({ dsn, schema }) режим не меняет
```

<!-- run: guide -->
```ts
import { up, connect } from 'letopis'

const ADMIN = 'postgres://postgres:secret@localhost:5432/shop'
const APP = 'postgres://shop_app:app-secret@localhost:5432/shop'

const r = await up({ dsn: ADMIN, schema: 'shop',
  tenant: { name: 'Ромашка', user: { name: 'Анна', login: 'anna@shop.ru', password: 'Ромашка-2026!' } } })
const SHOP = r.tenant!.tenant      // арендатор — магазин «Ромашка»
const ANNA = r.tenant!.user!       // его первый пользователь
```

### Роль приложения

Приложение работает от LOGIN-роли, которая состоит только в `letopis_app`. Её заводит `up({ login: { user, password } })`:
имя и пароль квотирует база, повтор обновляет пароль, а привилегированную роль (суперпользователя, с `CREATEROLE`,
`BYPASSRLS`, роль-владельца или её члена) `up()` не трогает — `invalid_data`; строка подключения роли — `r.login.dsn`.
Вручную — `create role shop_app login password '…'; grant letopis_app to shop_app;`. На роль приложения действуют RLS и
триггеры, как и на любой сырой SQL от этой роли. Роль, которая обходит RLS, `connect()` отклоняет с ошибкой
`bypass_rls`. Администраторское подключение (`allowBypassRls: true`) нужно только загрузчику, проекторам, ремонту
агрегатов (`rebuildAggregates`), проверке и обслуживанию; держите его в отдельном процессе, а не в веб-приложении.
Малому приложению хватит одного процесса — [ниже](#один-процесс).

### Первый арендатор и пользователь

Права в letopis включены всегда и по умолчанию запрещают всё. Поэтому новому арендатору нужны правила. Опция
`up({ tenant })` и функция `createTenant(sql, schema, opts)` делают это одной транзакцией:

- арендатор — аккаунт в System с id из имени («tenant:<имя>»);
- правило «аутентифицированным можно всё» в этом арендаторе (`grantAll`, по умолчанию да, вес 10);
- пользователь (id из логина) с членством в арендаторе с ролями `user.roles` (по умолчанию `['owner']`), паролем и
  сессией в арендаторе.

Повтор с теми же именем и логином ничего не дублирует и пароль не меняет, только выдаёт новую сессию. Логин входит в
id как есть: `Anna@shop.ru` и `anna@shop.ru` дали бы два аккаунта, и у второго не было бы пароля, — пишите логин в
одном регистре. Поле `created` в ответе — создан ли арендатор этим вызовом: для существующего арендатора с новым
пользователем оно `false`. Роли задаёт `user.roles` — непустой список имён (не масок), иначе `invalid_data`. Вид
пароля `user.kind` (по умолчанию `PASSWORD`) подчиняется правилу вида креда, как у `auth.setPassword`
([«Справочник API»](#dbauth)), иначе — тоже `invalid_data`. Роли
уже существующего членства повтор не меняет: их меняет правка членства ([«Выдать право»](#выдать-право)).
Удалённое повтор не воскрешает: если арендатор, аккаунт пользователя или членство удалены (строки нет, а история в
журнале есть), `createTenant` отвечает `invalid_data` и не записывает ничего. Текст ошибки называет удалённое и
советует вернуть его `restore()`: аккаунт — `db.Account(id).restore()` от имени системного администратора,
членство — `db.member(id).restore()` в этом арендаторе; другой выход — другое имя или логин. Сессия
из `createTenant` — без способа входа, поэтому свой пароль по ней не сменить: для этого пользователь входит по
паролю. `createTenant` нужен администраторский пул postgres.js:

<!-- run: guide -->
```ts
import postgres from 'postgres'
import { createTenant } from 'letopis'

const pg = postgres(ADMIN)
const lutik = await createTenant(pg, r.schema, {
  name: 'Лютик', user: { name: 'Борис', login: 'boris@lutik.ru', password: 'Лютик-2026!' } })
await pg.end()
const BORIS = lutik.user!          // lutik: { tenant, user, token, created: true }
```

### Подключение: `connect()`

Подключение получает сессию одним из двух способов: по ключу API (`apiKey`) или по токену (`token`).
Сервис приложения обычно держит одно подключение по ключу и действует от имени пользователей через `as()`:

<!-- run: guide -->
```ts
// сервис: ключ API обменивается на сессию сервиса
const svc = await connect({ dsn: APP, schema: r.schema, apiKey: r.serviceKey! })
// вход: сервис проверяет пароль и действует от имени пользователя в арендаторе
const login = await svc.auth.verifyPassword({ identifier: 'anna@shop.ru', password: 'Ромашка-2026!' })
const db = await svc.as(login!.account, { tenant: SHOP })
// своё подключение по токену сессии — например, в другом процессе
const anna = await connect({ dsn: APP, schema: r.schema, token: r.tenant!.token! })
```

| Опция `connect()` | Что делает |
|---|---|
| `dsn` или `sql` | строка подключения или готовый пул postgres.js |
| `schema` | полное имя установки: `'v2.shop'` (удобно брать `r.schema`) |
| `token`, `apiKey` | токен сессии или ключ API (`service` — синоним `apiKey`) |
| `models` | модели `letopis/model` — только для типов цепочек ([раздел 4](#4-модель-данных)) |
| `max` | размер пула (по умолчанию 10) |
| `listen` | слушать сигналы базы (по умолчанию да; `false` — для PgBouncer в режиме транзакций) |
| `cache` | кэш результатов: `{ ttl, max, ttlOnly }` или `false` ([раздел 12](#12-подписка-на-изменения-и-кэш)) |
| `maintain` | запускать `maintain()` по расписанию: `'1h'`, `'15m'` или миллисекунды |
| `onQuery`, `slowMs` | хук на каждый запрос цепочки и порог медленного запроса |
| `refreshSession` | продлевать сессию раз в минуту работы (по умолчанию да) |
| `notifyIntervalMs` | интервал отправки отложенных сигналов (100 мс) |
| `allowBypassRls`, `owner` | разрешить роль в обход RLS (администраторское подключение); имя роли-владельца |

У подключения есть `db.schema`, `db.token`, `db.tenant` (арендатор сессии) и `db.close()`. Подключения,
полученные через `as()`, делят пул с исходным: закрывать нужно исходное.

### Администраторское подключение

Загрузчику, проекторам и `rebuildAggregates` нужно подключение роли, которая может стать владельцем, с
`allowBypassRls: true`. `verify()` и
`maintain()` работают и на нём, и у системного администратора по обычному подключению. Администраторское
подключение печатает предупреждение «RLS не действует» — так и должно быть. Сессия задаёт арендатора, с которым
оно работает. Отдельному процессу загрузки удобнее ключ сервиса: `connect({ dsn: ADMIN, schema, apiKey,
allowBypassRls: true })`, а арендатора строк задаёт опция `load(…, { tenant })`. В примере — сессия из `up()`:

<!-- run: guide -->
```ts
const adm = await connect({ dsn: ADMIN, schema: r.schema, token: r.tenant!.token!, allowBypassRls: true })
```

### Один процесс

Малому приложению не обязательно держать два процесса. `up({ login })` заводит роль приложения и отдаёт её строку
подключения (`r.login.dsn`), а `connect({ dsn, admin, token })` при первом администраторском вызове открывает второй
пул — не больше двух соединений — строкой администратора. Через него идут только `load`, `projector`,
`rebuildAggregates`, `verify`, `maintain` и `syncModels`, с той же сессией; цепочки и `db.sql` остаются в пуле
приложения под RLS. Роль строки `admin` — суперпользователь или роль с `SET` на роль-владельца, иначе `admin_required`.
Пароль администратора в процессе приложения — только для малых приложений: взломанный процесс получит и его.

<!-- run: guide -->
```ts
const soloUp = await up({ dsn: ADMIN, schema: r.schema, login: { user: 'shop_app', password: 'app-secret' } })
const solo = await connect({ dsn: soloUp.login!.dsn!, admin: ADMIN, schema: r.schema, token: r.tenant!.token! })
const soloCheck = await solo.verify()        // администраторским пулом, с сессией Анны: { ok: true, … }
const soloMembers = await solo.member().count()  // пулом приложения, под RLS: только своего арендатора
await solo.close()                           // закрывает оба пула
```

### Обновление пакета и схемы

У схемы есть ревизия движка (сейчас 7). Если новая версия пакета принесла новую ревизию, `connect()` только
предупредит и назовёт команду. Отказывает `up()`: на отставшую схему без `upgrade: true` и на схему новее пакета.
К схеме новее пакета (её уже обновил более новый пакет, а старые экземпляры приложения ещё работают) `connect()`
подключается с предупреждением «движок схемы … ревизии N новее библиотеки (она знает M) — обновите пакет letopis».
Поэтому скрипт запуска, который вызывает `up()` при каждом старте, после обновления пакета остановится, пока не
получит `upgrade: true`. `up({ dsn, schema, upgrade: true })` применяет миграции из `sql/migrate/` и повторно
накатывает функции; данные сохраняются. Ревизия 7 (1.4.1) добавляет внешний ключ `secret.account`: миграция `0007`
сначала стирает строки `secret`, чьих аккаунтов уже нет (креды удалённых раньше аккаунтов хранились с пометкой
`deleted_at`), и ставит ключ.

Ревизия меняется не с каждой версией: у 1.1–1.4.0 она одна (6), а функции разные. Поэтому `up()` пишет в комментарий
схемы ещё и штамп движка: версию пакета и хэш его файлов SQL. Если штамп не совпадает с файлами пакета, `connect()`
предупреждает. Когда схему накатила более старая версия (или версия до 1.4, у которой штампа нет), он советует
`up({ schema })`. Когда схему уже обновила более новая версия, он советует обновить пакет: `up()` старой версией вернул
бы прежние функции. Новая версия пакета без правок SQL штамп не меняет, и предупреждения нет.

Первый `up()` после перехода на 1.2 строит индекс журнала `log_class_tenant_at (class, tenant, at)` вместо
`log_class_at`: срез `asOf` и `withDeleted` по классу больше не читает журнал других арендаторов с тем же именем
класса. Пока индекс строится, запись в журнал ждёт. На большой установке постройте его заранее, не останавливая
записи: `create index concurrently log_class_tenant_at on "v2.<схема>".log (class, tenant, at)` от роли владельца, —
тогда `up()` только снимет прежний.

Обновление схем 1.4.1, 1.1.0 и 1.0.1 проверяет тест `upgrade`; каждый выпуск проверяет обновление с предыдущего
выпуска. Схему ставит прежний пакет, данные пишет прежний движок, затем
вызывается `up()` текущей версии. После него версии и хэши прежнего движка на месте, `verify({ data: true })` чист, а
каталог схемы совпадает с чистой установкой. Схема 1.4.1 той же ревизии 7 обновляется обычным `up()`, без миграций;
1.1.0 (ревизия 6) и 1.0.1 (ревизия 5) — через `up({ upgrade: true })`: миграцией `0007` и миграциями `0006` и `0007`.

### Версии и совместимость

Версии letopis следуют semver. Что обещает каждый шаг версии:

- **Патч** (1.4.1 → 1.4.2) — только исправления. Ревизия движка та же: исправленные функции накатывает обычный
  `up({ schema })`, миграций нет; до наката `connect()` предупреждает о расхождении штампа. Работающий код не получает
  новых отказов, методы, опции, экспорты и коды ошибок не исчезают.
- **Минор** (1.4 → 1.5) — новые возможности: методы, опции, коды ошибок; изменения поведения, которые не ломают
  работающий код; новая ревизия движка. Новую ревизию накатывает `up({ schema, upgrade: true })`. Удалённого и
  переименованного нет.
- **Мажор** (1.x → 2.0) — удаление и переименование методов, опций, экспортов и кодов ошибок, смена сигнатур и типов,
  новые отказы для всех. Что менять в коде, описывает `MIGRATION.md`.

Текст сообщения об ошибке в API не входит: в патче он может стать точнее. Полагайтесь на `err.code`.

Шаг версии перед каждым выпуском сверяет сценарий `check:semver`: он сравнивает контракт API (`docs/api-contract.json`)
и ревизию движка с прошлым выпуском и требует шаг не меньше нужного. Каждый выпуск проверяет обновление схемы с
предыдущего выпуска (тест `upgrade`).

### Разработка без PostgreSQL: PGlite

`up({ pglite: true })` поднимает PGlite (PostgreSQL 18 на WebAssembly) с pgcrypto и сокетом на свободном порту.
Нужны пакеты `@electric-sql/pglite` и `@electric-sql/pglite-socket`. Соединение одно, поэтому:

```ts
const dev = await up({ schema: 'dev', pglite: true })
const local = await connect({ dsn: dev.pglite!.dsn, schema: dev.schema, apiKey: dev.serviceKey!,
  listen: false, max: 1, allowBypassRls: true })
// … работа …
await local.close()
await dev.pglite!.close()
```

Подключение к PGlite — суперпользователь, поэтому нужно `allowBypassRls: true`, а RLS на нём не действует: изоляцию
арендаторов и права на PGlite не проверить. Для гонок и CI он тоже не годится: соединение одно, `LISTEN` нет.

## 4. Модель данных

Классы описываются моделями на Zod из подпути `letopis/model` и записываются в базу. В базе хранится
нормализованная JSON Schema, и данные проверяет при каждой записи сама база.

### Хабы и связи

`hub()` описывает объект, `link()` — связь со своими данными. У обоих две формы:

- короткая: `hub(имя, поля, опции)` — поля объектом типов Zod, опции третьим аргументом;
- полная: `hub(имя, { fields, ends, key, extends, … })` — нужна, например, для наследования (`extends`), чтобы
  TypeScript вывел типы данных потомка.

Модель магазина, на которой построены дальнейшие примеры:

<!-- run: guide -->
```ts
import { z } from 'zod'
import { hub, link, one, many } from 'letopis/model'
import { syncModels } from 'letopis'

const Shop = hub('Shop', { name: z.string(), city: z.string().optional() }, { key: ['name'] })
const Category = hub('Category', { name: z.string() }, {
  key: ['name'],
  ends: { Parent: one('Category').optional().onDelete('unset') },   // дерево: ссылка на родителя
})
const Product = hub('Product', {
  sku: z.string(), title: z.string(), price: z.number().int().min(0), views: z.number().int().optional(),
}, {
  ends: { Shop, Category: many(Category, { max: 5, onDelete: 'unset' }) },
  key: ['Shop', 'sku'],
  meta: { title: 'Товар', icon: 'mdi:package-variant' },
})
const Customer = hub('Customer', { name: z.string(), email: z.string() }, {})   // без ключа: id выдаёт база
const Vip = hub('Vip', { extends: Customer, fields: { discount: z.number().int().min(0).max(50) } })
const Order = hub('Order', {
  number: z.string(), status: z.enum(['new', 'paid', 'cancelled']).default('new'),
}, { ends: { Customer, Shop }, key: ['Shop', 'number'] })
const line = link('line', { qty: z.number().int().min(1), price: z.number().int().min(0) }, {
  ends: { Order: one(Order).onDelete('cascade'), Product },
  key: ['Order', 'Product'],
})
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0).default(0) },
  { ends: { Customer }, key: ['number'] })
const Movement = link('Movement', {
  opId: z.string(), kind: z.enum(['topup', 'debit', 'adjust']), amount: z.number().int(), target: z.number().int().optional(),
}, { ends: { Wallet }, key: ['Wallet', 'opId'] })

const models = [Shop, Category, Product, Customer, Vip, Order, line, Wallet, Movement]
const plan = await syncModels(db, models)                     // сухой прогон: что будет создано и изменено
const applied = await syncModels(db, models, { apply: true }) // { applied: true, created: ['Shop', …], … }
```

### Поля

Поля — типы Zod: строки, числа (`int`, `min`, `max`), логические значения, перечисления (`z.enum`), даты и время
(`z.iso.date()`, `z.iso.datetime()`), вложенные объекты любой глубины, массивы и `z.record`. `.optional()` делает
поле необязательным, `.default(…)` — задаёт умолчание, которое база подставит при вставке. Пометки `.meta()` у поля
(`title`, `description`, свои ключи) база хранит, но на проверку данных они не влияют.

Правила `refine`, `superRefine` и `transform` в JSON Schema не выражаются, и база их не исполняет. `syncModels`
возвращает их в `lost`: проверяйте такие правила в приложении. Описание с ключевым словом JSON Schema, которого
база не знает, отклоняется — ни одно правило не пропадёт молча. Шаблоны `pattern` — ограниченное подмножество
регулярных выражений, общее для Zod, валидатора и базы.

### Концы

- `ends: { Shop }` — то же, что `one(Shop)`: одиночный обязательный конец с ролью `Shop`.
- `one(A, B)` — союз: конец принимает строки нескольких классов. `one('Category')` — цель по имени: так класс
  ссылается сам на себя.
- `.optional()` — необязательный конец.
- `many(X, { min, max, onDelete })` — множественный конец: список целей в одном конце.
- `.onDelete(…)` — что делать, когда удаляют цель: `restrict` (по умолчанию — удаление цели запрещено), `cascade`
  (удалить и эту строку), `unset` (снять ссылку; только для необязательного одиночного конца и множественного без
  `min`).

Цели проверяет база: цель существует, принадлежит тому же арендатору или System и относится к объявленному классу
или его потомку. Имя роли однозначно указывает на класс во всей схеме. Поэтому роли `User` и `Tenant` (ведут на
`Account`), `Group` и `Object` (ведут на `Resource`) заняты системными классами: свой конец с таким именем возможен
только с той же целью. В строке ответа одиночный конец — id цели (`row.links.Shop`), множественный — список id.

### Ключ и id

Ключ — обязательные строковые поля и обязательные одиночные концы. Числа, логические значения, объекты,
необязательные поля и множественные концы в ключ не входят. id класса с ключом — UUID версии 5 от арендатора,
класса и значений ключа. Значения берутся как есть, без нормализации: email в разном регистре даёт разные id.
Нужный формат ключевого поля задайте в модели, и база будет его проверять.

- id не передают: база вычисляет его сама. Чужой id — `id_mismatch`, id для класса без ключа — `id_from_db`.
- Заранее id вычисляет `db.idOf(класс, ключ)`, например `db.idOf('Shop', { name: 'Ромашка' })`.
- Класс без ключа (`Customer` выше) получает id от случайной части; узнать его можно из ответа записи.
- Ключевое поле обычной правкой не меняется (`immutable_key`): новый ключ — новый id, это `rekey`
  ([раздел 5](#5-запись)).

Если уникальным должно быть что-то кроме ключа, сделайте это отдельным классом. Например, email — ключ хаба
`Email`, а связь человека с ним — ключ `['Email']`. Персональные данные лучше не делать ключом самого человека:
id из email подбирается перебором и остаётся в ссылках и журнале.

### Наследование и алиасы

`extends` — потомок получает поля, концы и ключ предка. Своё поле с тем же именем заменяет поле предка целиком.
`abstract: true` — у класса не бывает своих строк. Шаг цепочки по классу отдаёт и строки потомков: `db.Customer()`
найдёт и `Vip`, а `.exact()` оставит только сам класс. `alias` — второе имя класса для шага цепочки, например
по-русски.

### Настройки класса

- `history: false` — журнал для класса не ведётся: нет версий, среза на дату, восстановления и событий подписки.
  Политика хранения — `history: { all: '1 day', daily: '3 months', … }` ([раздел 11](#11-история-и-срезы-на-дату)).
  Сменить `history` у существующего класса может только тот, у кого есть право `READ` и `DELETE` без условий на все
  строки класса и его потомков: по политике `maintain()` прореживает журнал, а `false` его выключает.
- `ownerDefault: 'actor'` — владелец новых строк — сам пользователь, а не арендатор (по умолчанию `'tenant'`).
  Пригодится для правила «каждый видит свои записи».
- `cache: { ttl }` — чтения только этого класса кэшируются без `.cache()` ([раздел 12](#12-подписка-на-изменения-и-кэш)).
- `meta` — свободные метаданные для приложения: название, иконка, цвет, порядок в меню. До 64 КБ, наследуются по
  ключам (`null` убирает унаследованное значение), видны всем, у кого есть сессия. У конца — `.meta()`.
- `derivedBy: 'имя-проектора'` — производный класс: его строки пишет только этот проектор ([«Проекторы»](#проекторы)).
  Имя — строчные латинские буквы, цифры и `_.:-` (первый знак — буква или цифра), до 64 символов. Опция
  наследуется, потомок её не меняет. Концы производного класса — только `onDelete: 'cascade'` или `'unset'`:
  производная строка не мешает удалять цель. На строки производного класса не ссылаются. Приложение, сырой SQL и
  загрузчик в такой класс не пишут: запись, правка и удаление его строк — `derived_class`. Сам производный класс
  (свой или унаследованный) заводит, меняет и удаляет только администратор — администраторское подключение или
  аккаунт с правом System `letopis.projector`; у сессии приложения это `acl_denied` ([«Проекторы»](#проекторы)).
- `aggregate: { поле: { sum | count, of, via, where } }` — агрегат в базе: сумму или счётчик строк источника держит
  сама база ([«Агрегаты в базе»](#агрегаты-в-базе)).

### Агрегаты в базе

Агрегат — поле, которое держит сама база: сумма поля или число живых строк класса-источника, чей конец ведёт на
строку. Он нужен там, где итог обязан совпадать с источником и для сырого SQL: баланс кошелька, число позиций заказа.

```ts
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0), deposits: z.number().int().optional() }, {
  key: ['number'],
  aggregate: {
    balance: { sum: 'amount', of: 'Movement', via: 'Wallet' },                                        // сумма операций
    deposits: { count: true, of: 'Movement', via: 'Wallet', where: { properties: { amount: { minimum: 1 } } } },  // число пополнений
  },
})
const Movement = link('Movement', { amount: z.number().int() }, { ends: { Wallet } })
```

- `sum: 'поле'` — сумма числового поля источника, `count: true` — число строк. `of` — класс-источник (имя или
  модель) вместе с потомками, `via` — его одиночный конец, который ведёт на строку-цель. `where` — JSON Schema над
  данными источника: строки, которые её не проходят, в агрегат не входят.
- Считаются только живые строки того же арендатора, что и цель. Ссылка на строку System в агрегат не входит: общий
  справочник не считает данные всех арендаторов. Агрегат класса арендатора, в том числе унаследованный от класса
  System, считает только классы своего арендатора: класс System с именем `of` в него не входит, а свой потомок класса
  System входит. Агрегат класса System считает классы System и классы арендатора строки-цели.
- Поле пересчитывает триггер после каждого оператора: запись библиотеки, сырой SQL, каскад удаления, `restore`,
  `reclass`, `rekey`, загрузчик, удаление аккаунта. Операции одного оператора складываются в одно приращение цели, а
  правило класса (`min(0)`) проверяется над итогом: операция, которая увела бы баланс в минус, отклоняется с
  `invalid_data`. Каждое изменение цели — её новая версия с автором и причиной операции.
- Поле пишет только база. Значение в `create`, `update`, `upsert`, `rekey`, `reclass` или в сыром SQL — ошибка
  `aggregate_field`. Новая строка получает итог уже существующих источников, обычно 0. Замена данных целиком без
  поля сохраняет прежнее значение. Загрузчик переданное значение не пишет. Права на запись в цель не нужно:
  достаточно права на запись в источник.
- Описание проверяет база (`invalid_class`): поле есть в схеме, оно числовое и не входит в ключ; конец `via` —
  одиночный и принимает класс цели; поле `sum` — число; агрегаты не образуют цикл; цель и источник — не системные и
  не производные классы. Класс-источник описывают раньше агрегата: агрегат над классом, которого ещё нет, отклоняется.
  У класса арендатора источник ищут среди классов арендатора. `syncModels` сам описывает источники раньше целей, а
  модели по кругу (агрегат над собственным потомком, цикл агрегатов) отклоняет до записи (`invalid_class` с кругом).
  Класс `of` не удаляется, пока его называет агрегат класса того же арендатора: сначала агрегат убирают из описания цели.
- Строки попадают в агрегат только с ведома того, кто читает их все: поле считает и строки, которые автору не видны.
  Описать или изменить агрегат может только тот, кто без условий читает все строки источника и его потомков. Сделать
  класс источником (новый потомок источника, смена `parent`) может только тот, кто без условий читает все
  строки этого класса и его потомков — и до правки, и после. Иначе `acl_denied`.
- Новый источник проверяется и по тому, кто описал агрегат: он тоже должен без условий читать все строки класса.
  Описавший — автор версии строки `Class` цели, с которой описание агрегата стало нынешним. Если он их не читает, класс
  источником не станет (`acl_denied`), пока агрегат не опишет заново тот, кто читает. У агрегата класса System
  описавший проверяется по классам System, как и при описании. Класс арендатора под агрегатом System проверяется
  только у того, кто его заводит.
- Опция наследуется, потомок заменяет её целиком. Добавить или изменить агрегат — ужесточение: запись в цель и в
  источники ждёт, пока поле пересчитывается у всех строк.
- `db.rebuildAggregates(класс)` пересчитывает поле из текущих строк — для ремонта. Версия пишется только там, где
  значение изменилось. Расхождения показывает `db.verify({ data: true })`. Нужно администраторское подключение.
- Сырой `INSERT … ON CONFLICT DO UPDATE SET data = excluded.data` для цели отклоняется: поле в `excluded.data` уже
  поставил триггер вставки. Пишите `excluded.data - array['balance']`, и поле останется прежним; `upsert` библиотеки
  делает так сам.

### Записать модель в базу

`syncModels(db, модели)` без `apply` — сухой прогон, с `{ apply: true }` — применение. Результат:
`{ applied, created, updated, unchanged, skipped, lost }`; в `skipped` — классы System, их меняет только установка.
`syncModels` трогает только переданные классы и ничего не удаляет. Безопасные изменения — новое необязательное поле или
конец, метаданные, алиас — применяются сразу. Всё остальное, в том числе любая правка условий `anyOf` и `oneOf`, —
ужесточение: оно проверяет все строки семейства, и если им мешают строки, приходит `tightening_conflict` со списком. Классы пишутся в арендатора сессии, и другие арендаторы их не видят.
Классы, общие для всех, лежат в System: их ставит сид установки или импорт.

То же из командной строки:

```sh
npx letopis sync ./models.js --dsn "$APP" --schema v2.shop --token "$TOKEN"            # сухой прогон
npx letopis sync ./models.js --dsn "$APP" --schema v2.shop --token "$TOKEN" --apply    # применить
npx letopis types --dsn "$APP" --schema v2.shop --token "$TOKEN" --out types.ts       # типы классов из базы
```

### Типы цепочек

`connect({ …, models })` даёт типы шагов, строк и фильтров по моделям. Описания классов библиотека всё равно берёт
из базы, модели нужны только TypeScript. Тип данных строки — `Infer<typeof Product>`, концов —
`InferLinks<typeof Product>`. Своё описание `meta` типизируется расширением интерфейса `ClassMeta`.

### Имена классов

Шаг цепочки называется именем класса, его алиасом или именем роли. Имена методов цепочки и корня (`count`, `sort`,
`set`, `sql`, `auth` и другие) там, где такой метод есть, библиотека разбирает раньше классов: класс `count` доступен
первым шагом `db.count(…)`, но не после другого шага. Связь с таким именем база не примет. Не давайте классам эти
имена; полный список — в разделе
[«Зарезервированные имена»](#зарезервированные-имена).

## 5. Запись

Глаголы записи — `create`, `update`, `upsert`, `delete`, `anonymize`, `reclass`, `rekey`, `restore`, `purge` —
звенья плана. Сам по себе глагол ничего не делает: план исполняет терминал (`rows`, `first`, `ids`, `count`), и весь
план — одна транзакция.

### Создать: `create`

<!-- run: guide -->
```ts
import { LetopisError } from 'letopis'

const [shop] = await db.Shop().create({ name: 'Ромашка', city: 'Казань' }).rows()
const [tea] = await db.Category().create({ name: 'Чай' }).rows()
const [green] = await db.Category().create({ name: 'Зелёный чай' }).Parent.set(tea).rows()
const [kettle] = await db.Shop(shop).Product().create({ sku: 'K-1', title: 'Чайник', price: 2500 }).rows()
const [sencha] = await db.Shop(shop).Product()
  .create({ sku: 'T-7', title: 'Сенча', price: 900 }).Category.add(green).rows()
const [olga] = await db.Customer().create({ name: 'Ольга', email: 'olga@mail.ru' }).rows()

try {
  await db.Shop().create({ name: 'Ромашка' }).rows()
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'exists') throw e   // e.detail.id === shop.id: такой магазин уже есть
}
```

- `create` только создаёт. Занятый ключ — ошибка `exists` с `detail.id`: id библиотека вычисляет сама. Поэтому у
  класса с ключом повтор после сбоя сети сразу показывает, что первая попытка прошла. Класс без ключа так не
  защищён: повтор создаст второй объект.
- Теги новой строки задаёт `.tags([…])` перед глаголом, владельца — `.owner(id)`; явного владельца должны разрешать
  права.
- Удалённый объект можно создать снова тем же ключом: история продолжится.
- Ответ — строки созданных объектов со всеми колонками ([раздел 15](#15-справочник-api), «Строка ответа»).

### Изменить: `update`

<!-- run: guide -->
```ts
import { gte } from 'letopis'

await db.Product(kettle).update({ title: 'Чайник стеклянный' }).rows()
await db.Shop(shop).Product({ price: gte(2000) }).update({ title: 'Чайник стеклянный, 1 л' }).rows()
```

`update` правит каждую цель шага и никогда не создаёт. Патч сливается с данными внутри оператора: вложенные
объекты — рекурсивно, а массивы, скаляры и `null` заменяются. Поэтому параллельные правки разных полей не теряются.
Если у шага нет своего фильтра, цель берётся из `data.id` патча, а без `data.id` правятся все сущности шага:
`db.Product().update(…)` правит все товары арендатора. Шаг ничего не нашёл — ответ пустой и ошибки нет, поэтому
проверяйте длину ответа. Если `update` затронул меньше строк, чем нашёл шаг, весь план откатывается: строку успели
удалить — `target_not_found`, строка видна, но править её нельзя — `acl_denied`. Модификатор `.tags(…)` перед
`update` отбирает строки; строка или список ещё и заменяют их теги целиком, а оператор (`has`, `hasAny`, `hasAll`)
только отбирает — теги не меняются.

### Создать или заменить: `upsert`

<!-- run: guide -->
```ts
const [kept] = await db.Shop().upsert({ name: 'Ромашка', city: 'Казань' }).rows()    // kept.$upsert: 'unchanged'
const [moved] = await db.Shop().upsert({ name: 'Ромашка', city: 'Уфа' }).rows()      // moved.$upsert: 'updated'
```

`upsert` создаёт объект, а если объект с этим ключом уже есть — заменяет его данные, концы и теги целиком. Это
один оператор `INSERT … ON CONFLICT`, поэтому гонки «проверил, что нет, — создал» не бывает. Правила:

- только класс с ключом, иначе `no_key` без обращения к базе;
- объект передаётся целиком: поля, которых нет в переданном объекте, пропадают;
- ответ несёт `$upsert`: `created`, `updated` или `unchanged`;
- приращать `upsert` не умеет и затирает параллельные приращения — для денег он не годится;
- для синхронизации больших справочников дешевле загрузчик с `existing: 'update'` ([раздел 9](#9-массовая-загрузка)).

### Концы: из пути и слоты

Концы создаваемой строки берутся из пути цепочки: `db.Shop(shop).Product().create(…)` ссылается на `shop`. Если
подходит несколько ролей, выбирается роль без занятого слота, затем роль с именем класса шага; иначе —
`invalid_query`. Явно конец задаёт слот после глагола: `.Роль.set(значение)` и `.Роль.unset()`, а у множественного
конца — `.add()` и `.remove()`. Значение — id, список id, строка ответа или вложенная цепочка. Слоты меняют
`links` атомарно, без чтения списка:

<!-- run: guide -->
```ts
await db.Product(sencha).update({}).Category.add(tea).rows()      // ещё одна категория
await db.Product(sencha).update({}).Category.remove(tea).rows()
await db.Category(green).update({}).Parent.unset().rows()         // категория стала корневой
await db.Category(green).update({}).Parent.set(tea).rows()        // и снова внутри «Чая»
```

### Числа и счётчики: `inc`

<!-- run: guide -->
```ts
import { inc } from 'letopis'

await db.Product(kettle).update({ price: inc(-500) }).rows()               // цена уменьшилась на 500
await db.Product(kettle).update({ views: inc(1, { start: 0 }) }).rows()    // поля ещё нет — начать с 0
```

`inc(n)` прибавляет величину внутри оператора `UPDATE` над свежей заблокированной строкой. Поэтому параллельные
приращения не теряются, а правило класса вроде `min(0)` проверяется над итогом: уход в минус отклоняется с
`invalid_data`, без чтения и блокировок в приложении. Правила:

- только в `update`; маркер в `create`, `upsert`, загрузчике и внутри массива — `invalid_data` до отправки;
- поле должно уже быть числом; если его нет — `invalid_data` или `start`. `null` и нечисло — ошибка даже со `start`;
- путь идёт только через существующие объекты;
- маркер `inc` нельзя получить из JSON: `{ "$inc": 5 }`, пришедший из сети, остаётся данными;
- деньги храните целым числом мелких единиц (копеек) не больше 2^53 − 1.

Счётчик, который обязан совпадать с источником и для сырого SQL, удобнее держать агрегатом
([«Агрегаты в базе»](#агрегаты-в-базе)): его пересчитывает сама база, и забыть `inc` нельзя. Цена у агрегата и `inc`
одна: операции одного объекта идут друг за другом под блокировкой его строки, и каждая пишет его версию. На машине
замеров один объект так принимал 150–190 операций в секунду, сколько бы писателей его ни ждало
([раздел 17](#17-производительность)). Для более горячих счётчиков берите проектор со свёрткой пачкой
([«Проекторы»](#проекторы)): итог отстаёт от источника, зато писатели не ждут друг друга.

### Защита от параллельной правки: `{ rev }`

<!-- run: guide -->
```ts
const cur = await db.Product(kettle).first()
await db.Product(kettle).update({ price: 1900 }, { rev: cur!.rev }).rows()       // версия совпала — записано
try {
  await db.Product(kettle).update({ price: 1800 }, { rev: cur!.rev }).rows()     // версия уже другая
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'conflict') throw e          // перечитать и решить заново
}
```

Строгий режим нужен, когда новое значение вычислено из прочитанного: если строку успели изменить, приходит
`conflict`, и ничего не записывается. Режим работает при одной цели шага (иначе `rev_ambiguous`). `conflict`
библиотека сама не повторяет: что делать с изменившимися данными, решает приложение. Другой способ — чтение с
блокировкой `forUpdate()` ([раздел 8](#8-транзакции-батчи-и-деньги)).

### Сменить ключ или класс

<!-- run: guide -->
```ts
const [mug] = await db.Shop(shop).Product().create({ sku: 'M-1', title: 'Кружка', price: 400 }).rows()
const [mug2] = await db.Product(mug).rekey({ sku: 'M-100' }).rows()     // новый ключ — новый id, ссылки переведены
const [vip] = await db.Customer(olga).reclass('Vip', { name: 'Ольга', email: 'olga@mail.ru', discount: 10 }).rows()
```

- `rekey(патч)` — новое значение ключа: строка с новым id, все ссылки переведены, старая строка удалена. Если
  ссылающаяся строка включает этот конец в свой ключ, её id тоже меняется, и перевод идёт дальше. Журнал связывает
  старый и новый id (`moved`).
- `db.rekeyClass(класс, ключ)` — новый ключ для всех строк семейства, одной транзакцией. У производного класса и
  у класса с производным потомком — `derived_class`: строки производного класса пишет только проектор.
- `reclass(класс, данные)` — смена класса; данные необязательны, а если переданы — задаются целиком. Строка уходит из
  прежнего класса, поэтому нужно право `DELETE` на неё, `WRITE` — на новый класс и на каждую строку, чьи ссылки
  переписывает перевод, на любой глубине. Если у нового класса нет ключа, id сохраняется (как у `vip` выше); если
  есть — id вычисляется заново, а ссылки переводятся.
  Роли ссылающихся строк должны принимать новый класс, иначе `reclass_denied`. Сырой `UPDATE … SET class`
  проходит, только если ключа нет ни у старого, ни у нового класса (иначе `use_reclass`).
- Удаление, смена класса и смена ключа работают только в `read committed`: транзакции библиотеки всегда открываются
  на этом уровне.

### Обезличить: `anonymize`

<!-- run: guide -->
```ts
await db.Customer(olga).anonymize(['email']).rows()     // email → '[erased]', тег anonymized
```

`anonymize(поля)` затирает строковые поля новой версией и помечает строку тегом `anonymized`. Прежние версии
остаются в журнале. Для полного забвения дальше идут обрезка истории ([раздел 11](#11-история-и-срезы-на-дату)),
затем удаление и `purge` ([раздел 7](#7-удаление-и-восстановление)).

### Как исполняется план

Один план может создать несколько связанных объектов. Продолжение после глагола идёт от его результата: после
`create` и `upsert` — от созданной строки, после остальных глаголов — от всех строк.

<!-- run: guide -->
```ts
const [l1] = await db.Customer(olga).Order()
  .create({ number: 'A-1' }).Shop.set(shop)          // заказ: Customer — из пути, Shop — слотом
  .line().create({ qty: 2, price: 2000 }).Product.set(kettle)   // строка заказа: Order — из пути
  .rows()                                            // строки последнего шага — строка заказа
const order = l1.links.Order as string
await db.Order(order).line().create({ qty: 1, price: 900 }).Product.set(sencha).rows()
```

- Весь план — одна транзакция уровня `read committed`. При взаимной блокировке (`40P01`), ошибке сериализации
  (`40001`) и конфликте журнала библиотека повторяет план целиком, до трёх раз.
- Ошибка любого звена откатывает весь план. `exists` и `conflict` не повторяются: это ответы для приложения.
- Модификаторы до глагола (`limit`, `offset`, `sort`) сужают его цели.
- Модификатор после глагола относится к тому, что идёт за ним: к шагу класса, к `versions()`, `diff()`, `blame()` и
  агрегатам или к целям следующего глагола. Если за ним сразу терминал `rows`, `first`, `ids`, `count` или `paths`,
  сужать уже нечего — глагол прошёл по всем целям шага, — поэтому `db.Product().update(…).limit(1).rows()` даёт
  `invalid_query` и ничего не пишет. В батче так же отказывает `run()`.
- Глагол сразу после глагола пишет в те же сущности.
- Строки ответа глагола идут в порядке его целей: по `sort()` до глагола, без него — по id; `first()` после глагола —
  первая по этому порядку.

## 6. Чтение

### Шаги и переходы

Цепочка начинается с класса: `db.Shop()` — все магазины, `db.Shop(shop)` — один. Следующий шаг — класс, алиас
или роль конца. Переход идёт по концам: шаг-роль — своим концом, иначе — концами всех классов обоих семейств.
От объекта к тем, кто на него ссылается, — назад, к цели ссылки — вперёд, к тому же классу — к детям.

<!-- run: guide -->
```ts
const products = await db.Shop(shop).Product().rows()          // товары магазина: назад по концу Shop
const shopOf = await db.Product(kettle).Shop().first()         // магазин товара: вперёд
const inOrder = await db.Order(order).line().Product().rows()  // товары заказа: хаб → связь → хаб
const parent = await db.Category(green).Parent().first()       // шаг-роль: родительская категория
const allCustomers = await db.Customer().rows()                // вместе с потомками (Vip)
const onlyCustomer = await db.Customer().exact().rows()        // только сам класс
```

### Фильтры

Фильтр шага — id, список id, строка ответа, объект полей или `or(…)`. Объект полей может быть любой глубины.
Простое значение — равенство через вхождение в `data`, без приведения типов: `{ price: 900 }` не найдёт запись с
ценой `"900"`. Список как значение поля — «массив содержит все элементы». Операторы приводят своё значение к типу
поля из JSON Schema. Роль конца в фильтре — id цели или `null`.

<!-- run: guide -->
```ts
import { lt, ilike, between, or, not } from 'letopis'

const cheap = await db.Product({ price: lt(1000) }).rows()
const teaCount = await db.Product({ title: ilike('%чай%'), price: between(500, 3000) }).count()
const twoIds = await db.Product(or({ sku: 'K-1' }, { sku: 'T-7' })).ids()
const active = await db.Order({ status: not('cancelled') }).rows()
const ofShop = await db.Product({ Shop: shop.id }).rows()
const roots = await db.Category({ Parent: null }).rows()       // корневые категории
```

| Оператор | Условие |
|---|---|
| `ne(v)`, `gt(v)`, `gte(v)`, `lt(v)`, `lte(v)` | ≠ (с учётом `null`), >, ≥, <, ≤ |
| `between(a, b)`, `inList([…])` | a ≤ x ≤ b; значение из списка |
| `like(s)`, `ilike(s)`, `starts(s)`, `ends(s)` | шаблон с `%` и `_`; без учёта регистра; начинается с; заканчивается на |
| `has(v)`, `hasAny([…])`, `hasAll([…])` | поле-массив содержит значение; хотя бы одно; все (`hasAll([])` подходит любой строке, `hasAny([])` — никакой) |
| `exists(true \| false)`, `isNull()` | поле есть или нет; поле `null` или отсутствует |
| `not(v)` | отрицание оператора; скаляр — «не равно» |
| `or(f1, f2, …)` | любой из фильтров шага |

Теги и владелец строки — модификаторы `.tags(…)` и `.owner(…)`.

### Терминалы и строка ответа

| Терминал | Что отдаёт |
|---|---|
| `rows()` | строки сущностей последнего шага, без повторов |
| `first()` | первую строку или `null` |
| `ids()` | id сущностей последнего шага |
| `count()` | число сущностей последнего шага; `count({ paths: true })` — число путей |
| `paths()` | пути: `[{ Шаг: Row, … }]` — узел на каждый шаг |
| `versions()` | все версии сущностей последнего шага ([раздел 11](#11-история-и-срезы-на-дату)) |
| `sum`, `avg`, `min`, `max`, `countBy` | агрегаты по полю `'data.<путь>'`; на пустом множестве — `null`, у `countBy` — `{}` |

Строка ответа: `id`, `class`, `rev` (номер версии), `tenant`, `owner`, `links` (концы), `data` (поля), `tags`,
`at` (время версии), `author`, `op` (вид операции) и, если есть, `agent`, `reason`, `moved`. Служебные поля
начинаются с `$`: `$deleted`, `$depth`, `$upsert`, `$action`, `$versions`, `$purged`.

### Сортировка и постраничный вывод

<!-- run: guide -->
```ts
import { cursorOf } from 'letopis'

const page1 = await db.Product().sort('data.price', 'desc').limit(2).rows()
const page2 = await db.Product().sort('data.price', 'desc')
  .after(cursorOf(page1.at(-1)!, 'data.price')).limit(2).rows()   // строго после последней строки страницы
```

`sort(поле, 'asc' | 'desc')` — по `'at'`, `'rev'`, `'id'` или `'data.<путь>'`. `after(cursorOf(строка, поле))` —
постраничный вывод «после такой-то строки»; он требует `sort()`. Такой вывод устойчив к вставкам и удалениям между
страницами, но строка, у которой изменилось поле сортировки, может выпасть или повториться. Курсор — объект
`{ v, id, rev }` (значение поля, id и номер версии строки): он переживает JSON, и его можно отдать клиенту. Поле в `cursorOf` должно
совпадать с полем `sort`. Значение курсора проверяется по типу поля `sort` до запроса, неверное — `invalid_query`:
числовому полю нужно конечное число, `rev` — целое, логическому — `true` или `false`, текстовому — строка, uuid и
`id` — uuid, времени и `at` — строка ISO с поясом, дате — `ГГГГ-ММ-ДД`, полю без описания — строка, число или
`true`/`false`. `null` подходит только полям данных, `id` курсора — всегда uuid. Курсор того же типа, снятый
с другого поля, проверка не отличит. `limit` и `offset` тоже есть.

`after()` листает и `versions()`: курсор версии несёт её `rev`, поэтому версии одного объекта с равным полем
сортировки не теряются. В `paths()` курсор даёт `cursorOf(путь, поле)`: поле и id — последнего узла пути, а в `path`
— id всех узлов, поэтому не теряются пути к одному узлу. Курсор `cursorOf(путь.Узел, поле)` с одного узла пропустит
остальные пути к этому узлу. `count()`, агрегаты, `diff()` и `blame()` курсор не учитывают.

Поле данных бывает `null` или отсутствует. Такие строки `sort` ставит, как `order by` в PostgreSQL: при
возрастании — в конце, при убывании — в начале, а `after()` считает `null` значением после всех прочих (по
возрастанию) или перед ними (по убыванию). Поэтому страницы проходят такие строки без пропусков и повторов, а
курсор со значением `null` даёт следующую страницу.

### Деревья: `deep`

<!-- run: guide -->
```ts
const subtree = await db.Category(tea).Category().deep().rows()   // подкатегории любой глубины; $depth — уровень
```

`deep(max)` повторяет переход к тому же классу до глубины `max` (по умолчанию 32 уровня). Фильтр, теги и владелец
шага отбирают узлы любого уровня, но обход не обрывают. Обрывает его только узел, невидимый по правам: он скрывает и
своё поддерево.

### Агрегаты

<!-- run: guide -->
```ts
const total = await db.Order(order).line().sum('data.price')       // сумма строк заказа
const avgPrice = await db.Shop(shop).Product().avg('data.price')
const byStatus = await db.Order().countBy('data.status')          // { new: 1 }
```

Агрегаты считает база, по сущностям последнего шага. `limit(n)` и `offset(n)` перед `countBy()` относятся к группам:
`db.Order().limit(3).countBy('data.status')` — три самых частых значения. У логического поля `min()` — `false`, если
есть хоть одно `false` (все ли значения `true`), а `max()` — `true`, если есть хоть одно `true`; `sum()` и `avg()`
логическое поле не считают — PostgreSQL отвечает ошибкой.

### Пути

<!-- run: guide -->
```ts
const orderPaths = await db.Order(order).line().Product().paths()   // [{ Order: Row, line: Row, Product: Row }, …]
```

`paths()` отдаёт узлы каждого варианта пути; ключ узла — имя шага или имя из `.alias(имя)`. Ключи идут в порядке
шагов; если цепочка кончается возвратом к прежнему узлу, этот узел — последний. Повтор связи в
цепочке возвращает к её узлу: так из одной связи можно пройти в несколько сторон. `db.entity(строка | цепочка)`
вставляет готовый узел в путь.

## 7. Удаление и восстановление

### Превью и удаление

<!-- run: guide -->
```ts
const preview = await db.Order(order).delete().rows()     // ничего не удаляет: заказ и его строки, $action каждой
await db.Order(order).delete({ confirm: true }).rows()    // удалено: надгробия с $deleted: true

const blockers = (await db.Shop(shop).delete().rows()).filter((x) => x.$action === 'restrict')
try {
  await db.Shop(shop).delete({ confirm: true }).rows()   // магазину мешают товары: конец Shop — restrict
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'delete_restricted') throw e
}
```

`delete()` без `{ confirm: true }` — только превью: всё замыкание каскада. В каждой строке превью `$action`:
`delete`, `unset` или `restrict`, и `$depth` — уровень каскада (0 — сама цель; у строк `unset` и `restrict` его
нет). С подтверждением удаляются все цели шага одним оператором, а каскад применяет правила концов. Итог —
надгробия по уровням каскада, внутри уровня по id (в таком порядке они и в журнале); цели классов без журнала
(`history: false`) — в конце. Превью не учитывает права: строка с `$action: 'delete'` может не удалиться у
пользователя без права (`acl_denied`), поэтому интерфейсу стоит спросить `acl.checkData(класс, 'DELETE')`.
Правила концов:

- `restrict` — удаление запрещено, пока на цель ссылаются (`delete_restricted` со списком видимых строк и числом
  остальных);
- `cascade` — ссылающиеся строки удаляются вместе с целью (строки заказа выше);
- `unset` — ссылка снимается.

Каскад требует права на удаление каждой удаляемой строки, снятие ссылки — права на запись. Сырой
`DELETE … WHERE id IN (…)` любого набора связанных строк работает так же.

### Восстановить: `restore`

<!-- run: guide -->
```ts
await db.Order(order).restore().rows()                       // заказ — последним снимком, id прежний
await db.Order(order).line().withDeleted().restore().rows()  // и его строки, удалённые каскадом
```

`restore()` возвращает последний снимок удалённого объекта новой версией и перепроверяет его по текущему описанию
класса. Восстанавливаются только цели шага, а не весь каскад. Живой объект — `not_deleted`.

### Стереть историю: `purge`

<!-- run: guide -->
```ts
const [temp] = await db.Customer().create({ name: 'Тест', email: 'test@example.com' }).rows()
await db.Customer(temp).delete({ confirm: true }).rows()
const before = await db.Customer(temp).purge().rows()          // превью: $versions — сколько версий в журнале
await db.Customer(temp).purge({ confirm: true }).rows()        // история стёрта; в журнале — запись purge
```

`purge` работает только для удалённых объектов (живой — `not_deleted`) и стирает их историю целиком; на месте
версии 1 остаётся запись `purge` с числом стёртых версий. История системных классов не стирается. Пока проектор,
чьи источники `from` включают класс объекта ([«Проекторы»](#проекторы)), не прочёл удаление, `purge` отказывает
(`projector_pending`): стёртое надгробие проектор не увидел бы, и вклад объекта остался бы в итогах. Удаление и
`purge` одной транзакцией в таком классе поэтому не проходят. Так же `db.trimHistory` отказывает, пока проектор не
прочёл первую оставшуюся версию: прошлую версию для `before` он бы уже не нашёл. Удалить аккаунт — `db.auth.purgeAccount`
([раздел 10](#10-пользователи-вход-и-права)).

## 8. Транзакции, батчи и деньги

### Каждая операция — транзакция

Каждый терминал цепочки — своя транзакция уровня `read committed`, какой бы уровень ни стоял в базе по умолчанию.
На этом уровне приращение и каскад видят свежие строки. Взаимную блокировку, ошибку сериализации и конфликт журнала
библиотека повторяет сама. Если связь оборвалась во время `COMMIT`, она не повторяет и бросает `commit_unknown`:
транзакция могла и зафиксироваться. Исход выясняет повтор той же операции с тем же ключом — `exists` значит
«уже записано».

### Явная транзакция: `db.begin()`

<!-- run: guide -->
```ts
const tr = await db.begin()
try {
  const [o2] = await tr.Customer(olga).Order().create({ number: 'A-2' }).Shop.set(shop).rows()
  await tr.Order(o2).line().create({ qty: 1, price: 2000 }).Product.set(kettle).rows()
  await tr.commit()
} catch (e) {
  await tr.rollback()
  throw e
}
```

- Внутри — те же цепочки, `db.sql`, `forUpdate()`, `lock()`, `commit()` и `rollback()`.
- Ошибка любого запроса ломает транзакцию: каждый следующий вызов и `commit()` бросают исходную ошибку,
  `commit()` при этом откатывает. `rollback()` проходит. Если ошибку перехватили внутри `tr.transaction(fn)` и
  библиотека о ней не знает, PostgreSQL молча отвечает `ROLLBACK` на `COMMIT`, а библиотека превращает это в ошибку
  `tx_rolled_back`.
- Повторов внутри `db.begin()` нет: на `40P01` повторите весь блок.
- `lock(...ключи)` — advisory-блокировка до конца транзакции. Она защищает, только если её берут все, кто правит
  эти данные.

### Батч

<!-- run: guide -->
```ts
const b = db.batch('витрина')
b.Shop(shop).Product().create({ sku: 'C-1', title: 'Чашка', price: 300 })
b.Shop(shop).Product().create({ sku: 'C-2', title: 'Блюдце', price: 200 })
const results = await b.run()       // Row[][] — по массиву строк на каждый план, одной транзакцией
```

Батч копит планы, а `run()` исполняет их одной транзакцией. Подряд идущие простые `create` и `upsert` класса с
ключом склеиваются в один многострочный оператор. `b.size()` — сколько планов в очереди, `b.discard()` —
очистить. Терминал на плане из очереди — `invalid_query`: исполняет только `run()`. Имя — ключ очереди фасада: у
корня подключения, у каждого `db.as()` и у каждой `db.begin()` очереди свои. План исполняется от имени того фасада,
который поставил его в очередь (актор, арендатор, владелец, транзакция), и чужих планов `run()` не исполняет.
Копите планы через один и тот же объект фасада.

### Рецепт: кошелёк

Баланс — поле `balance` хаба `Wallet` (целые копейки, `min(0)`), операции — связь `Movement` с ключом
`[Wallet, opId]` ([раздел 4](#4-модель-данных)). Операцию не правят и не удаляют, а отменяют встречной операцией с
новым `opId`. Ключ делает операцию идемпотентной: повтор после потери ответа получает `exists`, и рецепт сверяет,
тот ли это запрос.

<!-- run: guide -->
```ts
import { inc, type Db } from 'letopis'

type Kind = 'topup' | 'debit' | 'adjust'

/** Операция: запись Movement и приращение баланса — один план, одна транзакция. */
async function operate(db: Db, wallet: string, opId: string, kind: 'topup' | 'debit', amount: number) {
  try {
    await db.Wallet(wallet).Movement().create({ opId, kind, amount })
      .Wallet().update({ balance: inc(kind === 'topup' ? amount : -amount) }).rows()
    return 'done'
  } catch (e) {
    if (e instanceof LetopisError && e.code === 'exists') return same(db, wallet, opId, kind, amount)   // повтор
    throw e                                        // invalid_data — не хватает средств (min(0))
  }
}

/** Отпечаток повтора: тот ли запрос уже записан под этим opId. */
async function same(db: Db, wallet: string, opId: string, kind: Kind, value: number) {
  const m = await db.Movement(db.idOf('Movement', { Wallet: wallet, opId })).first()
  if (!m || m.data.kind !== kind || (kind === 'adjust' ? m.data.target : m.data.amount) !== value)
    throw new Error(`ключ операции ${opId} уже использован другим запросом`)
  return 'repeat'
}

/** Корректировка «баланс = target»: операция adjust на разницу, итог — под { rev }. */
async function adjust(db: Db, wallet: string, opId: string, target: number) {
  for (;;) {
    if (await db.Movement(db.idOf('Movement', { Wallet: wallet, opId })).first()) return same(db, wallet, opId, 'adjust', target)
    const cur = (await db.Wallet(wallet).first())!
    try {
      await db.Wallet(wallet).Movement().create({ opId, kind: 'adjust', amount: target - (cur.data.balance as number), target })
        .Wallet().update({ balance: target }, { rev: cur.rev }).rows()
      return 'done'
    } catch (e) {
      if (e instanceof LetopisError && e.code === 'conflict') continue     // кошелёк изменился — перечитать
      if (e instanceof LetopisError && e.code === 'exists') return same(db, wallet, opId, 'adjust', target)
      throw e
    }
  }
}

const [wallet] = await db.Customer(olga).Wallet().create({ number: 'W-1' }).rows()
await operate(db, wallet.id, 'op-1', 'topup', 10_000)    // 'done': баланс 10 000
await operate(db, wallet.id, 'op-1', 'topup', 10_000)    // 'repeat': повтор после потери ответа, баланс тот же
await operate(db, wallet.id, 'op-2', 'debit', 3_000)     // баланс 7 000
await adjust(db, wallet.id, 'op-3', 5_000)               // корректировка: adjust на −2 000, баланс 5 000
```

Тот же итог можно записать под чтением с блокировкой — без повторов при `conflict`:

<!-- run: guide -->
```ts
const [wallet2] = await db.Customer(olga).Wallet().create({ number: 'W-2' }).rows()
const tx = await db.begin()
try {
  const w = (await tx.Wallet(wallet2).forUpdate().first())!     // строка кошелька заблокирована до commit
  await tx.Wallet(wallet2).Movement()
    .create({ opId: 'op-1', kind: 'adjust', amount: 6_000 - (w.data.balance as number), target: 6_000 })
    .Wallet().update({ balance: 6_000 }).rows()
  await tx.commit()
} catch (e) {
  await tx.rollback()
  throw e
}
```

- `inc` прибавляет внутри оператора над заблокированной строкой: параллельные списания не теряются, а `min(0)`
  отклоняет списание сверх баланса.
- Обычный `update({ balance: 700 })` записывает значение, а не прибавляет. Итог, вычисленный из прочитанного,
  без `{ rev }` или `forUpdate()` теряет параллельные списания. Advisory `lock()` не спасает, если его берут не все
  писатели. `upsert` затирает приращения.
- `forUpdate()` — только внутри `db.begin()` (иначе `tx_required`) и только с `rows`, `first`, `ids` (иначе
  `lock_unsupported`). Строки блокируются в порядке id; строка, которая перестала подходить под условия шага, в ответ
  не попадает.
- Для одного кошелька выберите один путь: под `{ rev }` и под `forUpdate()` кошелёк и ключ операции блокируются в
  разном порядке, и смешение в параллельных запросах даёт `40P01`. Внутри блока с `forUpdate()` не ждите внешних
  вызовов: кошелёк ждут все писатели (помогут `lock_timeout` и `idle_in_transaction_session_timeout`).
- Перевод — две операции в одной `db.begin()`, кошельки правятся в порядке id: тогда взаимных блокировок нет.
- Нехватку средств отличают от других ошибок данных по `e.issues`: поле `balance`, правило `minimum`.

### Рецепт: баланс агрегатом

Тот же кошелёк, только баланс держит сама база: `balance` — агрегат, сумма `amount` живых операций
([«Агрегаты в базе»](#агрегаты-в-базе)). Операция — одна запись `Movement`, приращения `inc` в коде нет, и забыть его
нельзя. Баланс остаётся верным, даже когда операции пишет сырой SQL или загрузчик, а удаляет каскад.

```ts
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0) }, {
  ends: { Customer }, key: ['number'],
  aggregate: { balance: { sum: 'amount', of: 'Movement', via: 'Wallet' } },   // баланс — сумма живых операций
})
const Movement = link('Movement', { opId: z.string(), amount: z.number().int() },
  { ends: { Wallet }, key: ['Wallet', 'opId'] })                             // ключ операции — идемпотентность

/** Операция: amount больше нуля — пополнение, меньше — списание. База пересчитает баланс в той же транзакции. */
async function operate(db: Db, wallet: string, opId: string, amount: number) {
  try {
    await db.Wallet(wallet).Movement().create({ opId, amount }).rows()
    return 'done'
  } catch (e) {
    if (e instanceof LetopisError && e.code === 'exists') return 'repeat'   // повтор после потери ответа
    throw e                                        // invalid_data — баланс ушёл бы в минус (min(0))
  }
}

/** Корректировка «баланс = target»: операция на разницу, кошелёк заблокирован до commit. */
async function adjust(db: Db, wallet: string, opId: string, target: number) {
  const tx = await db.begin()
  try {
    const w = (await tx.Wallet(wallet).forUpdate().first())!
    await tx.Wallet(wallet).Movement().create({ opId, amount: target - (w.data.balance as number) }).rows()
    await tx.commit()
    return 'done'
  } catch (e) {
    await tx.rollback()
    if (e instanceof LetopisError && e.code === 'exists') return 'repeat'   // корректировка с этим opId уже записана
    throw e
  }
}

const [wallet] = await db.Customer(olga).Wallet().create({ number: 'W-1' }).rows()   // balance — 0: его ставит база
await operate(db, wallet.id, 'op-1', 10_000)    // баланс 10 000
await operate(db, wallet.id, 'op-2', -3_000)    // баланс 7 000
await adjust(db, wallet.id, 'op-3', 5_000)      // операция на −2 000, баланс 5 000
```

- Модель здесь своя, и блок в программу примера не входит: там баланс растёт через `inc`, а агрегатное поле так не
  меняется.
- `balance` не передают ни в `create`, ни в `update` (`aggregate_field`), поэтому корректировка — тоже операция, а не
  `update` под `{ rev }`. Чтобы записать операцию, право на запись в кошелёк не нужно: хватает права на запись в
  `Movement`.
- Нехватка средств — `invalid_data`, как и с `inc`: в `e.issues` поле `balance` и правило `minimum`. Повтор сверяйте,
  как `same()` в рецепте выше: `exists` говорит только о том, что операция с этим `opId` уже есть.
- Правка и удаление операции тоже меняют баланс: база вычтет прежнее значение. Отменять операцию всё равно лучше
  встречной операцией, тогда история кошелька остаётся полной.
- Каждая операция блокирует строку кошелька и пишет его версию, поэтому операции одного кошелька идут друг за другом,
  как и с `inc`: на машине замеров — около 150 в секунду ([раздел 17](#17-производительность)). Если один объект
  получает больше, итог лучше считать проектором ([«Рецепт: дневная выручка»](#рецепт-дневная-выручка)).

## 9. Массовая загрузка

### Когда нужен загрузчик

Загрузчик — путь для импорта, засевки и синхронизации больших справочников. Он проверяет строки в коде библиотеки
тем же валидатором, что и база, и пишет их командой `COPY` от роли владельца, без триггеров и RLS. На бенче это
около 6 400 строк в секунду против 130 у построчного `create` ([раздел 17](#17-производительность)). Работает
только на администраторском подключении (`allowBypassRls` и право стать владельцем), иначе — `admin_required`.

### `db.load()`

<!-- run: guide -->
```ts
const rep = await adm.load({
  Shop: [{ name: 'Василёк', city: 'Пермь' }],
  Product: [
    { sku: 'V-1', title: 'Кружка', price: 450, Shop: { $key: ['Василёк'] } },
    { sku: 'V-2', title: 'Ложка', price: 150, Shop: { $key: ['Василёк'] }, $tags: ['новинка'] },
  ],
  Customer: [{ name: 'Пётр', email: 'petr@mail.ru', $ext: 'crm:1001' }],
})
// rep: { rows: 4, loaded: 4, updated: 0, skipped: 0, duplicates: 0, byClass: { Shop: 1, Product: 2, Customer: 1 }, … }
```

- Вход — объект «класс → строки», массив или поток строк с полем `$class`.
- Строка — поля и роли концов на верхнем уровне. Служебные ключи: `$class` — класс строки, `$ext` — внешний ключ
  класса без ключа (повторная загрузка того же файла даёт те же id), `$tags` — теги, `$owner` — владелец.
- Ссылка — id цели, ключ `{ $key: [...] }` или внешний ключ `{ $ext: '…' }`; у полиморфного конца — с `$class`
  цели. Порядок строк и классов не важен, ссылки по кругу допустимы.
- Ключи на `$` внутри данных — обычные данные.
- Строки идут в арендатора сессии (или `tenant`). Загрузка — одна транзакция: ошибка в любой строке отменяет всё.
  Подписки видят строки после фиксации.

### Повторы и существующие объекты

<!-- run: guide -->
```ts
const again = await adm.load({ Shop: [{ name: 'Василёк', city: 'Пермь' }] }, { existing: 'skip' })      // skipped: 1
const changed = await adm.load({ Shop: [{ name: 'Василёк', city: 'Самара' }] }, { existing: 'update' }) // updated: 1
```

| Опция | Значения |
|---|---|
| `duplicates` — повтор id внутри загрузки | `'error'` (по умолчанию) — отменить; `'first'` или `'last'` — оставить первую или последнюю строку |
| `existing` — объект уже есть в базе | `'error'` (по умолчанию) — отменить; `'skip'` — пропустить, удалённые не воскрешать; `'update'` — новая версия, если содержимое отличается (неизменённые считаются в `skipped`), удалённые — создать заново; объект другого класса с тем же id (класс без ключа после `reclass`) — `exists` |

### Порции, история и проверка

- `commitEvery: N` — фиксировать порциями примерно по N строк. Порции идут по классам в порядке зависимостей,
  классы из одного цикла — в одной порции. Ошибка отменяет только текущую порцию, а повтор с `existing: 'skip'`
  дописывает остальное.
- `withHistory: true` — строки — это версии с `$rev`, `$at` и `$op`; так импорт переносит историю.
- `verify: true` — в конце перепроверить загруженные строки проверкой базы.
- `batch` (строк в пачке `COPY`, 10 000), `class` (класс строк без `$class`), `tenant`, `agent` (агент версий).

### Загрузка от имени пользователя

<!-- run: guide -->
```ts
await adm.load({ Category: [{ name: 'Посуда' }] }, { as: ANNA, tenant: SHOP })
```

С `as` автором версий становится пользователь, а загрузчик проверяет то же, что база при обычной записи:
арендатор ему доступен, право записи в каждый класс, условия прав на строки, видимость целей ссылок, владелец по
`ownerDefault`. Без `tenant` строки идут в собственного арендатора пользователя. Так процесс загрузки принимает
файлы, присланные пользователями.

### Первая заливка

```ts
const r = await adm.load(rows, { initial: true })   // пустая схема: одна транзакция, индексы и триггеры — в конце
```

`db.load(rows, { initial: true })` (`letopis load --initial`) заливает данные в пустую схему быстрее обычного
загрузчика — на миллионе объектов примерно в 2,2 раза: всё идёт одной транзакцией, на время загрузки таблицы закрыты
для чтения и записи, индексы, ограничения и триггеры сняты и строятся заново в конце, строки пишутся `COPY … FREEZE`.
Пустая — значит, кроме строк системных классов (описания классов, аккаунты, членства, ресурсы, правила) и записей
`reset`, в схеме ничего нет; иначе — `not_empty` до любых изменений. Режим несовместим с `commitEvery`, `existing`
(кроме `'error'`) и `{ as }`; ошибка любой строки откатывает всё, вместе с индексами и триггерами.
`letopis import --initial` проводит так весь импорт: одной транзакцией, без `--update` и `--commit-every`. WAL пишется
и здесь (без него — только при `wal_level = minimal`), но индексы строятся один раз, и его почти втрое меньше; после
`FREEZE` первое чтение и первая очистка таблицу не переписывают.

### Командная строка

```sh
npx letopis load shops.ndjson products.ndjson --dsn "$ADMIN" --schema v2.shop --token "$TOKEN" \
  [--class Product] [--duplicates first] [--existing skip] [--commit-every 100000] [--verify]
# shops.ndjson:    {"$class":"Shop","name":"Юг"}
# products.ndjson: {"$class":"Product","sku":"Y-1","title":"Ваза","price":800,"Shop":{"$key":["Юг"]}}
```

Файлы NDJSON — объект на строку; все файлы — одна загрузка.

### Отчёт и ошибки

Отчёт: `rows`, `loaded`, `updated`, `skipped`, `duplicates`, `byClass`, `external` (сколько целей вне загрузки
сверено запросом в конце), `portions`, `ms`. Ошибка — `LetopisError` с кодом первой проблемы. Её `detail`:
`rows` — первые 100 нарушений с номером строки, кодом и подробностями (`line`, `code`, `message`, `id`, `class`,
`issues`), `total` — сколько нарушений найдено, `truncated` — список обрезан, `limit` — предел списка (100),
`complete` — проверки, нашедшие нарушения, прошли все строки. Коды строк: коды проверок базы, а также `duplicate`
(повтор id), `exists` (объект уже есть), `deleted` (объект с этим id жил раньше) и `class_not_loadable` (строки
`Class` загрузчик не принимает: классы задаёт `syncModels`). Строки производных классов и ссылки на них загрузчик
отклоняет с кодом `derived_class`: такие строки пишет только проектор.

Нарушения ищутся поэтапно: разбор строк (классы, id, повторы), права на классы (`load({ as })`), данные и концы
пачками, в конце порции — цели вне загрузки, владельцы и арендатор. Загрузка отменяется после первого этапа,
нашедшего нарушения, и `total` считает нарушения этого этапа. Цель вне загрузки — одно нарушение на цель (строка —
первая, что на неё ссылается). «(и ещё N)» в тексте ошибки — точное число остальных нарушений. Если проверены не все
строки, `complete` — `false`, а текст говорит «(и ещё не меньше N: причины)» или, если найдено одно нарушение,
«(возможно, не единственная: причины)». Причины: следующие порции `commitEvery` не проверялись; условия ACL
следующих пачек не проверялись (`load({ as })`); проверка базы (`verify: true`) называет не больше 100 строк.

## 10. Пользователи, вход и права

### Аккаунты, арендаторы и членство

Аккаунт — строка класса `Account` в System: имя, категории (`User`, `Service` и свои), признак `enabled`. Каждый
аккаунт — сам себе арендатор. Работать в чужом арендаторе позволяет членство `member` — связь пользователя
(`User`) с арендатором (`Tenant`) с ролями в данных. Аккаунты и их категории правит системный администратор —
член System с ролью `admin`. Отдельного метода, чтобы назначить его, нет: членство в System с ролью `admin` кладёт
свой сид установки или загрузчик на администраторском подключении (строка `member` с `tenant: <id System>`).
Новых пользователей арендатора удобно заводить `createTenant`
([раздел 3](#3-установка-и-подключение)).

### Сервис и ключи API

Сервис — аккаунт категории `Service` с ключом API. Ключ установки выдаёт `up()`. Сервис проверяет пароли и коды,
выпускает сессии и действует от имени пользователей. Ключи обычных пользователей он выпускает и отзывает сам (право
`auth.credential`), как ниже для Бориса. Свои ключи API и пары «ключ + секрет» сервис тоже выпускает и отзывает сам —
по сессии, открытой своим ключом (`connect({ apiKey })`, `verifyApiKey`, `verifyKeySecret`). Прочие свои креды,
ключи других сервисов, System и системных администраторов выпускает и отзывает только системный администратор;
новый ключ сервиса регистрирует и `up({ serviceKey })`.

Ключей может быть несколько. Сессия, открытая ключом, помнит его, и отзыв ключа гасит только его сессии: подключения
по другим ключам работают дальше. Поэтому ротация идёт без простоя: сервис выпускает себе новый ключ
(`issueApiKey({ account: <id сервиса> })`), переводит процессы на него и отзывает старый (`revokeCredential(id)`).
Текущую сессию отзыв оставляет, `keepCurrent: false` гасит и её. Последний действующий ключ сервиса не отзывается:
`acl_denied` «последний действующий ключ сервиса не отзывается: сначала выпустите новый». Отключить сервис —
`enabled: false` у его аккаунта.

<!-- run: guide -->
```ts
const { key, id: keyId } = await svc.auth.issueApiKey({ account: BORIS, name: 'интеграция' })   // ключ отдаётся один раз
const viaKey = await svc.auth.verifyApiKey(key)                    // { account, token } | null
await svc.auth.revokeCredential(keyId)
```

Пара «ключ + секрет» — `issueKeySecret({ account, name })` и `verifyKeySecret(key, secret)`.

### Пароли

<!-- run: guide -->
```ts
await svc.auth.setPassword({ account: BORIS, identifier: 'boris@lutik.ru', password: 'Новый-пароль-2026', confirmed: true })
const failed = await svc.auth.verifyPassword({ identifier: 'boris@lutik.ru', password: 'Лютик-2026!' })   // null: пароль сменён
```

- Пароль хранится хэшем scrypt; проверяет его сервис, время ответа для несуществующего логина выровнено.
- Идентификатор сравнивается без учёта регистра: `Anna@Shop.ru` и `anna@shop.ru` — один вход.
- Смена пароля гасит остальные сессии аккаунта (`keepCurrent` — оставить текущую).
- По умолчанию вход — только по подтверждённому креду, иначе `null`; `requireConfirmed: false` пускает и по
  неподтверждённому. Подтверждает кред сервис: `confirmed: true` в `setPassword` или `setFlags`.
- Второй фактор — опция `totp`: `verifyPassword({ identifier, password, totp })` после верного пароля проверяет код
  TOTP аккаунта и выдаёт сессию со способами `[вид, 'TOTP']`, по умолчанию `['PASSWORD', 'TOTP']` (см. ниже). Без
  `totp` вход код не проверяет: требовать ли второй фактор, решает сервис.

### Одноразовые коды и TOTP

<!-- run: guide -->
```ts
import { totpCode } from 'letopis'

const { code } = await svc.auth.issueOtp({ account: BORIS, identifier: 'boris@lutik.ru', ttl: 300 })   // сервис отправит код письмом
const byCode = await svc.auth.verifyOtp({ identifier: 'boris@lutik.ru', code })                        // { account, token } | null
const { secret, uri } = await svc.auth.enrollTotp({ account: BORIS, issuer: 'Лютик' })              // uri — для QR-кода
const totpOk = await svc.auth.verifyTotp({ account: BORIS, code: totpCode(secret) })                // первая проверка включает фактор
```

Код одноразовый: успешная проверка и перебор (по умолчанию 5 попыток) его сжигают. Счётчики попыток откатываются
вместе с транзакцией вызывающего, поэтому частоту попыток ограничивает сервис. Повтор того же шага TOTP
отклоняется. `totpCode(secret)` — помощник для тестов и сервисов.

Вход со вторым фактором — `verifyPassword({ …, totp })` и `lookup({ …, totp })`. Код проверяется только после
верного пароля или найденной учётной записи, той же проверкой, что `verifyTotp`: нужно право `auth.totp`, окно —
шаг в каждую сторону, счётчик неудач общий (пять подряд закрывают проверку на 5 минут). Верный код даёт сессию со
способами `[вид, 'TOTP']` и включает ещё не подтверждённый фактор; неверный или повторный код, как и код у аккаунта
без TOTP, — `null`. По такой сессии пользователь с TOTP 10 минут меняет свои креды сам.

### Внешние учётные записи

`link({ account, kind, identifier, confirmed })` привязывает внешнюю учётную запись (Telegram, Google, SSO): её
токен проверяет сервис, а база хранит связку. `lookup({ kind, identifier })` — вход по ней (с опцией `totp` — и по
коду TOTP, как `verifyPassword`):

<!-- run: guide -->
```ts
await svc.auth.link({ account: BORIS, kind: 'TELEGRAM', identifier: '100500', confirmed: true })
const viaTelegram = await svc.auth.lookup({ kind: 'TELEGRAM', identifier: '100500' })   // { account, token } | null
```

Свои креды пользователь привязывает сам только после недавнего входа (10 минут; ключ API, пара «ключ + секрет» и
сессия от сервиса не в счёт) и не подтверждает их сам. При включённом TOTP база требует сессию с пройденным TOTP:
её выдают `verifyPassword` и `lookup` с опцией `totp`. Если идентификатор занят, привязка отвечает тем же
`acl_denied`, что и без недавнего входа. Но пользователь с недавним входом по такому отказу поймёт, что
идентификатор занят ([раздел 18](#18-ограничения)).

### Сессии

<!-- run: guide -->
```ts
const shortToken = await svc.auth.sessionFor(BORIS, { ttl: 600 })   // сессия на 10 минут простоя — для другого процесса
const whose = await svc.auth.session(shortToken)                     // { account, tenant, member, expiresAt, loginAt, methods }
const boris = await connect({ dsn: APP, schema: r.schema, token: shortToken })
await boris.auth.revoke()                                            // выход: сессия погашена
const ended = await svc.auth.session(shortToken)                     // null
await boris.close()
```

Токен — 256 случайных бит; база хранит только его sha256. Срок по умолчанию — 7 суток. `refresh()` продлевает
текущую сессию: новый срок отсчитывается от текущего момента, но не больше срока, выданного при входе; возвращает
он новое время истечения. `connect()` продлевает сессию сам раз в минуту работы (`refreshSession`), поэтому сессия,
которой пользуются, не истекает: срок — это время простоя. `revoke()` — выход, `revokeAll()` — выход везде.
Сессии гаснут при отключении аккаунта, смене пароля, удалении креда и удалении аккаунта. Удаление креда гасит
остальные сессии аккаунта, а отзыв ключа API или пары «ключ + секрет» — только сессии, открытые этим ключом (и
старые сессии того же вида входа без отметки ключа); текущая сессия остаётся, если не передать
`keepCurrent: false`.

Сервис, у которого есть токен пользователя (например, в cookie), узнаёт о сессии через `svc.auth.session(token)`:
подключение по этому токену не открывается, срок сессии не продлевается. Ответ — чья сессия (`account`), в каком
арендаторе она работает (`tenant`: выбранный `auth.switch()` или собственный арендатор аккаунта), цело ли там членство
(`member`; в собственном арендаторе — всегда `true`), когда она истечёт (`expiresAt`), когда и как был вход
(`loginAt`, `methods`: `PASSWORD`, `APIKEY`, `SERVICE`, `TOTP` …). Неверный, погашенный или истёкший токен и
отключённый аккаунт — `null`, причина не различается. Так веб-сервис проверяет сессию в начале каждого запроса:
чтение по погашенной сессии ошибки не даёт, ответы просто пустые. Вызывает метод сервис или системный администратор
(право `auth.session`); пользователю отвечают `acl_denied`.

### Работа в другом арендаторе

Сервис действует от имени пользователя через `svc.as(account, { tenant, owner })`. База проверяет право сервиса
`auth.impersonate` (по правилам System), что пользователь существует и включён и что арендатор ему доступен —
собственный или по членству. От имени System, сервисов, системных администраторов и отключённых аккаунтов
действовать нельзя. Видимость пользователя по правилам доступа не проверяется. В журнале `author` — пользователь,
`agent` — сервис. Реестр классов `db.as()` — один на арендатора, подключение держит их не больше 1000: давно не
нужный вытесняется, а фасад, чей реестр вытеснен, продолжает работать — реестр перечитывается. Подключение
пользователя по своему токену переключается между арендаторами так:

<!-- run: guide -->
```ts
const mine = await anna.auth.tenants()     // [{ tenant, roles }]: собственный арендатор и магазин по членству
await anna.auth.switch(SHOP)               // арендатор сессии — магазин
```

### Права

Права включены всегда и по умолчанию запрещают. Правило связывает группу с объектом:

- **группа** — строка `Resource` категории `ACCOUNT`: аккаунты по категориям (`{ categories: '{User}' }`) или
  участники по ролям членства (`{ roles: '{staff}' }`);
- **объект** — строка `Resource` категории `API` (эндпоинт по маске, `{ endpoint: 'shop.reports.*' }`) или `READ`,
  `WRITE`, `DELETE` (строки класса по маске с потомками, `{ class: 'Product' }`, и условие на колонки `id`,
  `owner`, `tenant`, `tags`, `data`, `links` со значениями `$actor` и `$tenant`);
- **правило** — связь `rule` группа → объект: `permission` (`allow` или `deny`) и `weight`.

Решает ровно одно правило: наибольший вес, при равном весе запрет сильнее разрешения. Вес правила арендатора больше
999 урезается до 999, поэтому правила System с весом от 1000 — административный слой, который арендатор не
перевесит. Правила
арендатора действуют на его строки, правила System — везде. Права действуют и на сырой SQL: строки без права не
видны, правка — пусто или `acl_denied`.

Маска класса в объекте `READ`, `WRITE` или `DELETE` совпадает и с потомками класса — по именам предков и их алиасам.
Поэтому правка класса, которая меняет `parent`, `alias` или `derivedBy`, требует права `READ`, `WRITE` и `DELETE` без
условий на все строки класса и каждого его потомка, иначе `acl_denied`: одного права `WRITE` на `Class` мало, чтобы
подставить строки класса под чужие правила. Алиас не совпадает с именем другого класса (в том числе `Class` и
системных) и с чужим алиасом арендатора и System, а имя нового класса — с чужим алиасом: иначе правило, написанное
для одного класса, действовало бы и на строки другого. Нарушение — `invalid_class`.

По тем же именам правила находят и старые версии строк в журнале. Поэтому класс удаляется, только когда у него нет
строк, потомков и истории строк: историю удалённых строк сначала стирает `purge()`. Для класса System не в счёт
строки, потомки и история арендатора, у которого есть свой класс с тем же именем: они относятся к его классу. Класс,
удалённый с историей раньше, создаётся заново только с прежними `parent`, `alias`, `derivedBy` и `history` — иначе
`invalid_class`: старые версии его строк попали бы под чужие правила или другое прореживание. Правила находят старые
версии и по алиасам предков. Поэтому, пока удалённые потомки класса хранят историю строк, класс не меняет алиас
(`invalid_class`), а удалённым создаётся заново только с прежним описанием. Если журнал хранит строки класса с этим
именем, но не его надгробие (например, строки класса System, удалённого в 1.1), класс с этим именем не создаётся, пока
историю не сотрёт `purge()`.

Производный класс (`derivedBy`) заводит, меняет и удаляет только администратор: администраторское подключение или
аккаунт с правом System `letopis.projector` (у системного администратора оно есть по маске `letopis.*`). Проектор
пишет в такой класс итоги по всем строкам источников арендатора, без прав чтения, поэтому пользователь, заведя его
сам, читал бы итоги по строкам, которые ему читать запрещено. Класс, у которого есть производные потомки, тоже
правит только администратор: правка предка меняет описание потомка (поля, ключ, `history`). Пометку `aggregatedBy`
(класс стал источником агрегата) база ставит и производному классу сама: полей и ключа она не меняет.

### Выдать право

Пример: Олег — сотрудник магазина с ролью `staff`, и сотрудникам нельзя удалять товары.

<!-- run: guide -->
```ts
const pg2 = postgres(ADMIN)
const OLEG = (await createTenant(pg2, r.schema, {          // тот же магазин: создаётся только пользователь
  name: 'Ромашка', user: { name: 'Олег', login: 'oleg@shop.ru', password: 'Олег-2026!' } })).user!
await pg2.end()
await db.acl.roles(OLEG, ['staff'])                         // роли Олега в текущем арендаторе (строка member)

await db.acl.deny({ role: 'staff', delete: 'Product' })     // вес 50 — сильнее «можно всё» (10)
await db.acl.grant({ role: 'staff', api: 'shop.reports.*' })

const asOleg = await svc.as(OLEG, { tenant: SHOP })
const canDelete = await asOleg.acl.checkData('Product', 'DELETE')   // { allow: false }
const canRead = await asOleg.acl.checkData('Product', 'READ')       // { allow: true }
const canReport = await asOleg.acl.check('shop.reports.daily')      // { allow: true, rule: { weight: 50, … } }
```

- `db.acl.grant` и `db.acl.deny` принимают роль и цели: `read`, `write`, `delete` — класс (с потомками), `'*'` — все
  классы или класс с условием на строки (`{ class: 'Ticket', owner: '$actor' }`); `api` — маска эндпоинта; списком —
  несколько. На каждую операцию и цель — одно правило с весом `weight` (по умолчанию 50, от 1 до 999). Под капотом —
  те же строки `Resource` (`role:staff:ACCOUNT`, `class:Product:DELETE`, `api:shop.reports.*:API`) и `rule` текущего
  арендатора, ключ правила — пара группа и объект: повтор ничего не меняет, а `grant` после `deny` той же роли и цели
  заменяет запрет разрешением. Внутри `db.begin()` — в её транзакции. Писать правила может тот, у кого есть `WRITE` на
  `Resource` и `rule` (после `createTenant` — любой участник по правилу «можно всё»; закрыть — `deny` с
  `write: ['Resource', 'rule', 'member']`). Неверный вызов — `invalid_data` до записи.
- `db.acl.revoke({ role, … })` снимает правила роли — разрешения и запреты — для этих целей и отвечает числом снятых.
  `db.acl.roles(аккаунт)` — роли в текущем арендаторе (`null` — не член), `db.acl.roles(аккаунт, ['staff'])` — заменить
  их (членство заводится), `db.acl.roles(аккаунт, null)` — снять членство. `db.acl.list()` — правила арендатора
  `{ role, group, op, target, condition, permission, weight }`, свои и «можно всё» от `createTenant`.
- `acl.check(эндпоинт)` → `{ allow, rule, code, message }`: свой отказ эндпоинта задают поля `code` и `message`
  запрещающего правила.
- `acl.checkData(класс, 'READ' | 'WRITE' | 'DELETE')` → `{ allow, filter }`: `filter` — условие на строки.
- Права пересчитываются базой сами. Правила можно писать и цепочками `Resource` и `rule` напрямую — поля ниже.
- Библиотека один раз берёт у базы подписанный план прав актора — пропуск прав — и передаёт его в каждой
  транзакции, поэтому проверка прав стоит десятки микросекунд. Сырой SQL без пропуска платит 0,3–1,3 мс на запрос.
- На вопрос «у кого был доступ на дату» отвечает срез `asOf` по классам `rule`, `member` и `Resource`.

Поля системных классов прав:

- `member` — концы `User` и `Tenant`, поле `roles` (список ролей);
- `Resource` — `alias` (уникальное имя ресурса и его ключ; это не алиас класса), `category` (`ACCOUNT`, `API`,
  `READ`, `WRITE`, `DELETE`) и `pattern` — маска. У группы маска `categories` или `roles` — только строка: `'{staff}'`,
  `'{a,b}'`, отрицание — `'!{a}'`. У объекта — `endpoint` или `class` (тоже только строки) и условия на колонки.
  **Маску не строкой (например, массив `['staff']`, число или `null`) база отклоняет** с `invalid_data` — при записи
  библиотекой, сырым SQL и загрузчиком. Старые строки с такой маской (записанные до этой проверки или в обход
  неё) разрешений не дают, а запрет по ним действует на всех: по группе — на все аккаунты, по маске `class` — на все
  классы (маска `endpoint` не строкой, как и прежде, не совпадает ни с одним эндпоинтом). Проверку при записи несёт
  описание класса `Resource`: оно приходит со свежей установкой и после `reset({ all })`; в существующей схеме
  исправленное сопоставление действует после повторного `up()`;
- `rule` — концы `Group` и `Object` (строки `Resource`), поля `permission` (`allow` или `deny`), `weight`, а для
  своего отказа эндпоинта — `code` и `message`.

### Удалить аккаунт

`db.auth.purgeAccount(аккаунт)` удаляет аккаунт и данные его арендатора. Вызывать может системный администратор или
владелец его арендатора; себя и последнего владельца арендатора удалить нельзя. Владение строками в чужих
арендаторах переходит этим арендаторам, сессии гаснут, креды удаляются. Владелец может стереть и арендатора, в
котором сейчас работает: его сессия вернётся в личный арендатор.

Системный администратор может удалить и саму строку аккаунта — `db.Account(id).delete({ confirm: true })` в
арендаторе System; данные арендатора аккаунта при этом остаются. Любой путь сразу стирает строки аккаунта в `secret`:
сессии, хэши паролей и ключей, секреты TOTP, внешние учётные записи (внешний ключ `secret.account` с каскадом,
ревизия 7). Сессии гаснут до этого с сигналом, и процессы сбрасывают кэш ответов этих сессий. Аккаунт System
не удаляется (`acl_denied`): ему принадлежат служебные строки установки в `secret`.

## 11. История и срезы на дату

### Версии

<!-- run: guide -->
```ts
const versions = await db.Product(kettle).versions()              // все версии: op, rev, author, at, data
const followed = await db.Product(mug2).versions({ follow: true }) // и через смену id (rekey, reclass)
```

У каждой версии — автор, агент, время, номер, вид операции (`create`, `update`, `delete`, `reclass`, `rekey`,
`restore`, `purge`, `trim`, `reset`) и причина (`reason`). Причину задаёт опция `reason` глагола (`update(patch, { reason })`, `create(data, { reason })`,
`delete({ confirm, reason })` и других), для всех операций блока — `db.begin({ reason })` и
`db.batch(имя, { reason })`; сырой SQL — настройка `letopis.reason` транзакции. Версия удаления — с `$deleted`.

Без `sort()` версии идут по id и номеру версии (с `follow` — по времени). `sort()` задаёт порядок и версиям, а
`limit()` ограничивает их в самом запросе: `db.Product(kettle).sort('at', 'desc').limit(5).versions()` — пять
последних версий, новые первыми.

`follow: true` отдаёт историю объекта на всех его id: до переноса — версии прежнего id, после — нового. Объект,
который потом завели на прежнем id (тот же ключ после `rekey`), — другой, и его версий в этой истории нет; его
собственная история с `follow` начинается с его создания. Так же идут `diff({ follow: true })` и `blame()`. Без
`follow` `versions()` отдаёт все версии id, чьи бы они ни были.

### Срез на дату

<!-- run: guide -->
```ts
const createdAt = versions[0].at
const atCreation = await db.Product(kettle).asOf(createdAt).first()  // цена в момент создания — 2500
const assortment = await db.Shop(shop).Product().asOf(createdAt).rows()
```

`asOf(момент)` — состояние «как было» по журналу; момент — строка ISO или `Date`. Срез работает на любом шаге
цепочки, в том числе с `deep()`. Дёшево только текущее состояние: срез восстанавливается из журнала. Время версии
`at` хранит микросекунды, а `Date` — только миллисекунды: передавайте в `asOf` строку `at` как есть, иначе срез на
момент версии может её не застать.

### Удалённые

```ts
const withGone = await db.Customer().withDeleted().rows()   // живые и удалённые; у удалённых $deleted: true
```

### Политика хранения

Без политики журнал хранит каждую версию. Политика задаёт, сколько хранить старые версии и с какой подробностью:

```ts
history: { all: '1 day', daily: '1 week', weekly: '1 month', monthly: '1 year', yearly: 'forever', tz: 'Europe/Moscow' }
```

Это значит: все версии за последние сутки; за неделю — по одной на день; за месяц — по одной на неделю; за год —
по одной на месяц; старше — по одной на год, бессрочно. От периода остаётся его последняя версия. Неделя
начинается с понедельника, границы периодов — в поясе `tz` (по умолчанию UTC).

- Политику задают у класса (потомки наследуют) или для всех классов без своей — `up({ history })`.
- Если у последнего яруса задан срок, а не `'forever'`, история старше срока удаляется: `{ all: '30 days' }`.
- Пока история объекта жива, не удаляются текущая версия, версия 1 и версии особых видов (`create`, `delete`,
  `reclass`, `rekey`, `restore`, `purge`, `reset`, `trim`). Если надгробие удалённого объекта старше последнего яруса
  со сроком, его история стирается целиком. История системных классов не прореживается.
- Прореживает `maintain()` пачками по 10 000 версий ([раздел 13](#13-эксплуатация)).
- В прореженной части срез показывает последнюю сохранённую версию до момента, то есть его точность равна
  периоду яруса. Подписчик, отставший дольше яруса `all`, получает `cursor_expired`.

### Что изменилось и кто: `diff` и `blame`

```ts
const [d] = await db.Order(id).diff()                       // предыдущая версия → последняя
await db.Order(id).diff({ from: 3, to: 7 })                 // по номерам версий
await db.Order(id).diff({ from: '2026-10-01' })             // состояние на момент → последнее
await db.Order(id).diff({ follow: true })                   // через смену id (reclass, rekey)
const [b] = await db.Order(id).blame()                      // каждое поле последней версии
await db.Order(id).blame({ at: '2026-10-01', limit: 200 })  // версия на момент; просмотреть 200 версий
```

Оба терминала отдают массив — по элементу на объект шага. Так выглядят ответы для чайника, которому снизили цену с
причиной:

```ts
import type { BlameResult, DiffResult } from 'letopis'

// db.Product(kettle).blame(): цену изменила версия 2, остальные листья — с создания (версия 1)
const blamed: BlameResult = {
  id: '6f1c…', class: 'Product', rev: 2, complete: true,
  fields: [                                     // по порядку пути
    { path: ['class'], rev: 1, at: '2026-10-27T09:15:02.118204+00:00', author: '<id Анны>', agent: '<id сервиса>',
      op: 'create', exact: true },
    { path: ['data', 'price'], rev: 2, at: '2026-10-27T09:20:41.502617+00:00', author: '<id Анны>', agent: '<id сервиса>',
      op: 'update', reason: 'скидка к акции', exact: true },
    // ['data', 'sku'], ['data', 'title'], ['links', 'Shop'], ['owner'] — тоже версия 1, как ['class']
  ],
}
// db.Product(kettle).diff(): предыдущая версия → последняя
const diffed: DiffResult = {
  id: '6f1c…', class: 'Product',
  from: { rev: 1, at: '2026-10-27T09:15:02.118204+00:00' },
  to: { rev: 2, at: '2026-10-27T09:20:41.502617+00:00' },
  changes: [{ path: ['data', 'price'], kind: 'changed', before: 2500, after: 2000 }],
}
```

`agent` здесь — сервис, который пишет от имени Анны (`db = await svc.as(…)`); у записи без имперсонации его нет.

- `diff()` — массив `DiffResult`: `{ id, class, from, to, changes }`. `from` и `to` — сравниваемые версии
  `{ rev, at }`. В них есть `id`, если версия принадлежит другому id (`follow: true` через `reclass` или `rekey`), а у
  `to` — `deleted: true`, если на этот момент объект удалён; тогда `changes` пуст. `from` равен `null`, если объекта
  тогда ещё не было: все пути — `added`. Если версии нет вовсе, `class` и `to` тоже `null`.
- Изменение `DiffChange` — `{ path, kind, before, after }`. `path` — массив сегментов, а не строка с точками; первый
  сегмент — раздел строки: `data`, `links`, `tags`, `owner`, `class`. `kind` — `added` (значения не было), `removed`
  (не стало) или `changed`. Пустое значение опускается: у `added` нет `before`, у `removed` — `after`. Объекты данных
  сравниваются по ключам, массивы — целиком. Множественный конец и теги — множества: по изменению на каждый id или
  тег, путь — `['links', роль]` или `['tags']`, а сам id или тег — в `before` или `after`.
- `blame()` — массив `BlameResult`: `{ id, class, rev, complete, fields }` и `deleted: true`, если эта версия —
  надгробие. Объект без версий на этот момент элемента не даёт. `fields` — массив `BlameField`, по элементу на лист
  версии, упорядоченный по пути: `{ path, rev, at, author, op, exact }` и, если есть, `agent`, `reason`, `id`. Лист —
  скаляр или массив в данных, пустой объект, роль одиночного конца, каждый id множественного конца
  (`['links', роль, id]`), каждый тег (`['tags', тег]`), `owner` и `class`. `rev`, `at`, `author`, `agent`, `op` и
  `reason` — от версии, которая последней изменила лист. Пустые `agent` и `reason` опускаются; `id` есть, только если
  это версия прежнего id (история прошла через `reclass` или `rekey`). Версии другого объекта на том же id — того,
  что жил там до переноса или заведён после, — `blame()` не смотрит.
- `exact: false` — между текущей версией и найденной есть пропуски (история прорежена, обрезана или часть версий не
  видна): лист мог менять и выпавшая версия. `complete: true` — история просмотрена целиком и без пропусков; по
  умолчанию просматривается не больше 1000 последних версий.
- Считает база с правами вызывающего: сырой SQL получает то же — `select "v2.shop".blame('<id>')`,
  `select "v2.shop".diff_versions('<id>')`.
- Колонка журнала `changed` (пути изменения версии, по ним `blame` работает быстро) приложению не выдана: пути
  описывают разницу с предыдущей версией, а её читатель может не видеть. Поэтому `select * from log` от приложения
  не работает — колонки перечисляются явно; `blame` берёт пути функцией базы, только когда видны обе версии.

### Обрезка истории

<!-- run: guide -->
```ts
const trimmed = await db.trimHistory(kettle, new Date())     // стереть версии чайника до этого момента
```

`db.trimHistory(цель, момент)` сразу стирает историю до момента: класса с потомками (по имени), id, списка id или
строк. Это средний шаг «права на забвение»: `anonymize` → обрезка истории → удаление и `purge`. На месте версии 1
остаётся запись `trim` с её временем, поэтому срез знает, когда объект появился.

### Проверка целостности

<!-- run: guide -->
```ts
const audit = await adm.verify({ data: true })     // { ok, issues, anchor }
```

`verify()` пересчитывает цепочки хэшей всех версий и возвращает якорь — хэш всех голов цепочек. Храните якорь вне
базы: подмену последних версий выдаст его расхождение. `{ data: true }` вдобавок перепроверяет данные, концы,
арендаторов, владельцев и id всех строк. Вызывать может системный администратор или администраторское подключение;
из командной строки — `letopis verify [--data]` (код выхода 1 при находках). Законные разрывы — записи `trim` и
`purge`, прореживание и `reset` — ошибкой не считаются.

## 12. Подписка на изменения и кэш

### Подписка

<!-- run: guide -->
```ts
const sub = db.watch({ from: 'start', classes: ['Product'] })   // весь журнал класса, затем новые события
await db.Product(kettle).update({ price: 2100 }).rows()
let cursor = ''
for await (const ev of sub) {             // ev: { cursor, row, id, class, op, rev, at }
  cursor = sub.cursor!                    // курсор подписки: watch({ from: cursor }) продолжит после этого события
  if (ev.id === kettle.id && ev.row.data.price === 2100) break   // break (или sub.close()) — остановить
}
```

- `from` — `'now'` (по умолчанию: только изменения после подписки), `'start'` (весь журнал) или сохранённый курсор.
  `db.watch()` возвращается сразу, а момент «now» подписка берёт первым запросом к базе: запись, сделанная сразу
  после `db.watch()`, может зафиксироваться раньше и в поток не попасть. `await sub.ready()` дожидается этого момента:
  запись после него в поток придёт. Пример выше читает с `'start'`.
- Вызовы `sub.next()` идут по очереди: параллельные получают разные события. Вызов, брошенный по таймауту
  (`Promise.race`), всё равно получит своё событие — держите его обещание и ждите его снова.
- `classes` — только эти классы с потомками; `pollMs` — запасной опрос (1000 мс). Строка, ушедшая из этих классов
  сменой класса без смены id, приходит событием удаления в прежнем классе (`op: 'delete'`, `row` — прежняя версия с
  `$deleted`), даже если новый класс подписчику не виден. Событие приходит, если прежнюю версию подписчик видел.
- События идут без потерь и повторов, под правами читателя, в порядке номеров транзакций, а внутри транзакции — в
  порядке записи. Это не порядок фиксации: версии одного объекта сверяйте по `rev`.
- Долгая пишущая транзакция в любой базе кластера задерживает поток: `await sub.lag()` показывает отставание в мс.
- Курсор старше яруса `all` политики хранения — `cursor_expired`: перечитайте текущее состояние и подпишитесь
  с `'now'`. Время в курсоре подписки `sub.cursor` — время последнего события, а когда подписка догнала журнал, —
  время опроса, поэтому подписка, к которой сутки не было событий, не устаревает. Курсор события `ev.cursor` хранит
  время самого события.
- Без `LISTEN` (`connect({ listen: false })`) подписка опрашивает журнал.
- Подписка без потерь — это сохранённый курсор: обработав событие, храните `sub.cursor` (позиция после последнего
  выданного события) и продолжайте с него после перезапуска. С `ev.cursor` поток тоже продолжится, но после затишья
  дольше яруса `all` такой курсор старше яруса, и продолжение с него — `cursor_expired`.

### Проекторы

Проектор строит строки производных классов из журнала: сводки, денормализованные карточки и всё, что можно считать
с отставанием от записи. Классы-источники (`from`) пишет приложение, а строки классов `into` — только проектор.
Каждый класс `into` помечен опцией `derivedBy` с именем проектора ([«Настройки класса»](#настройки-класса)).
Производные классы заводит только администратор: синхронизируйте их администраторским подключением с сессией
арендатора — `adm` из раздела 3 (`connect({ dsn: ADMIN, schema, token, allowBypassRls: true })`) или `as()` сервиса
на таком подключении, в CLI — `letopis sync` с `--dsn` роли администратора. У сессии приложения это `acl_denied`. В примере ниже проектор
считает продажи товаров по строкам заказов `line`.

```ts
const ProductSales = hub('ProductSales', { qty: z.number().int(), revenue: z.number().int() }, {
  ends: { Product: one(Product).onDelete('cascade') }, key: ['Product'], derivedBy: 'product-sales', history: false,
})                                               // производный класс — в модели; syncModels — администраторским подключением

const sales = adm.projector('product-sales', {   // adm — администраторское подключение
  from: ['line'],                                // классы-источники с потомками; у них должен быть журнал
  into: ['ProductSales'],                        // производные классы этого проектора
  version: 1,                                    // логика handle изменилась — новая версия и перестройка
  withBefore: true,                              // c.before — прошлая версия объекта или null
  handle(changes, out) {
    for (const c of changes) {
      if (c.op === 'purge' || c.op === 'trim' || c.op === 'reset') continue   // служебные изменения, не версии
      const was = c.before                       // прошлая версия строки заказа — вычесть
      const now = c.row.$deleted ? null : c.row  // новая версия — прибавить; у удаления её нет
      if (was) out.inc('ProductSales', { Product: was.links.Product },
        { qty: -Number(was.data.qty), revenue: -Number(was.data.qty) * Number(was.data.price) }, { tenant: c.tenant })
      if (now) out.inc('ProductSales', { Product: now.links.Product },
        { qty: Number(now.data.qty), revenue: Number(now.data.qty) * Number(now.data.price) }, { tenant: c.tenant })
    }
  },
})
const report = await sales.run({ once: true })  // догнать журнал: { batches, changes, created, updated, … }
const state = await sales.status()               // { name, state, version, cursor, at, lag, failed, rebuildingTenants }
await sales.rebuild()                            // перестроить с текущего состояния; { chunked: true } — пачками
await sales.rebuild({ tenant: tenantId })        // перестроить одного арендатора — например, выбывшего (failed)
await sales.rebuild({ tenant: tenantId, chunked: true })   // его же пачками: хвост журнала тем временем идёт для всех
sales.run().catch((err) => console.error('проектор остановлен', err))   // следовать за журналом до stop()
sales.close()                                    // stop() после текущей пачки и отписка от сигналов
```

- Проектору нужно администраторское подключение: `connect({ allowBypassRls: true })` роли, которая может стать
  владельцем схемы. Иначе — `admin_required`, внутри `db.begin()` — `invalid_query`. Проектор читает журнал всех
  арендаторов.
- Первый запуск `run()` перестраивает проекцию с текущего состояния: журнал прорежен политикой хранения и обрезан
  `purge`, поэтому собрать проекцию с начала журнала нельзя.
- Каждая пачка — одна транзакция: изменения журнала, `handle`, запись результатов и сдвиг курсора фиксируются
  вместе. Обрыв посреди пачки откатывает её целиком, а повтор начинается с того же курсора, поэтому каждое
  изменение применяется ровно один раз. Писатель у проектора один: второй процесс того же проектора пропускает пачку
  (счётчик `skipped` в отчёте), а `rebuild()`, начатая, пока другой процесс пишет пачку, — `projector_busy`.
- Пачка делится по арендаторам: `handle` получает изменения одного арендатора, и запись его результатов идёт под
  своей точкой сохранения. Если база отклоняет запись результатов арендатора (данные не проходят описание его
  производного класса, цель конца не найдена и т. п.) или `out` отклоняет строку или приращение, построенные по его
  данным (приращение — не число), откатываются только его изменения: арендатор выбывает, а остальные записываются в
  той же пачке. Выбывший попадает в `status().failed` — `{ [id арендатора]: { cursor, code, message } }`, `message`
  называет арендатора и id строки, — и его изменения пропускаются, пока его не перестроят. Производные строки
  выбывшего больше не меняются: выбывший в `run()` сохраняет их такими, какими они были до пачки с ошибкой, а выбывший
  посреди перестройки остаётся без них — частично построенные строки удаляются. Исключение из `handle`, нарушение
  границ `out` и сбой окружения (взаимная блокировка, отмена запроса, обрыв связи) откатывают пачку целиком, а
  `run()` отклоняется. Поэтому `run()` без `once` ловите (`catch`): после ошибки он остановлен.
- Изменение (`ProjectorChange`) — это `cursor`, `id`, `class`, `tenant`, `op`, `rev`, `at`, `author`, `agent`,
  `reason`, `moved` и `row` — версия из журнала (у удаления — надгробие с `$deleted`). При перестройке изменения —
  строки текущего состояния: `rebuild: true`, `op` — `create`, `cursor` пустой.
- Смена класса без смены id (у классов без ключа: сырой `UPDATE … SET class` и `reclass()`) журнал пишет версией уже
  нового класса. Если она уводит строку из семейства `from`, проектор получает удаление: `op` — `delete`, `row` —
  последняя версия строки в семействе с `$deleted`, `rev`, `at` и автор — смены класса. Строка, вошедшая так в
  семейство, приходит изменением `reclass` с `before` = `null`.
- С `withBefore` у изменения есть `before` — прошлая версия того же id. `before` равен `null`, если прошлой версии нет
  (создание и первая версия нового id после `reclass` и `rekey`), если прошлая версия — удаление (так бывает после
  `restore`) или вне семейства `from`, и у всех изменений перестройки. При `reclass` и `rekey` прежние данные
  вычитает надгробие прежнего id: оно приходит изменением с `$deleted`, его `before` — последняя версия прежнего id,
  а `moved` обоих изменений указывает на другой id. Поэтому свёртка из примера после `rekey` даёт ту же сумму. У
  служебных изменений `purge`, `trim` и `reset` поля `before` нет совсем. Поэтому вычитайте `before`, только проверив
  его на `null`, как в примере выше.
- Служебные записи журнала `purge`, `trim` и `reset` тоже приходят изменениями, и у них `rev` равен 1. Поэтому
  сначала разберите `op`, а уже потом сравнивайте `rev`.
- `out.upsert(класс, строка, { tenant })` создаёт строку или заменяет её целиком по ключу класса.
  `out.inc(класс, строка, приращения, { tenant })` создаёт строку или дополняет её и прибавляет числа, не читая
  строку (поля, которых нет, считаются от 0). `out.delete(класс, ключ или id, { tenant })` удаляет строку, а если её
  нет, ничего не делает. `await out.get(класс, ключ или id, { tenant })` читает текущую строку вместе с записями
  пачки. Строку класса с ключом `delete` и `get` находят по полям ключа (`{ day: '2026-10-29' }`), а по id (строкой
  или `{ $id }`) — только строку класса без ключа; один id у класса с ключом — `invalid_data`, и пачка откатывается.
  `out` пишет только в классы `into` и только в арендатора изменений, переданных в `handle`; иначе —
  `derived_class` или `tenant_denied`, и пачка откатывается.
- Приращения строки, заданной одними полями ключа (или одним `$id`), `out` складывает до отправки в базу, пока между
  ними нет `upsert`, `delete` или `get`: на строку — одна правка за пачку, а правило класса проверяется над итогом её
  приращений. Строку с другими полями (данными, `$tags`, `$owner`) `inc` не складывает: её поля правят строку, и
  порядок таких правок сохраняется.
- Строка для `out` — в формате загрузчика: поля и роли концов на верхнем уровне, служебные `$tags`, `$owner` и
  `$id` (`$id` нужен только классу без ключа). Значение роли — id цели. Правка, которая ничего не меняет, версии не
  даёт. Версии производных строк пишутся от System с агентом `letopis projector <имя>`; журнал ведётся по
  `history` класса, а сигнал об изменении уходит всегда.
- `rebuild()` перестраивает проекцию атомарно, одной транзакцией: до её фиксации читатели видят прежние строки, но
  горизонт подписок стоит. `rebuild({ chunked: true })` идёт пачками: производные строки удаляются сразу, и до
  конца перестройки данные неполные, а `status().state` — `'rebuilding'`. Прерванную перестройку пачками
  продолжает следующий запуск. Сам `run()` — первый запуск новой проекции и `onExpired: 'rebuild'` — перестраивает
  пачками: горизонт подписок кластера стоит не дольше пачки. Второй процесс того же проектора тем временем ждёт или
  продолжает ту же перестройку, а не начинает её заново. Перестройка удаляет строки только участников и только
  классов их семейств `into` и начинает всех участников заново: отметки выбывших снимаются, а арендатор, чьи данные
  снова не проходят, выбывает снова.
- `rebuild({ tenant: id })` перестраивает одного арендатора одной транзакцией: удаляет его производные строки, строит
  их из его текущих строк источников и снимает отметку в `status().failed`; изменения, уже учтённые перестройкой,
  проектор потом не применяет второй раз. Исправьте данные или описание класса арендатора, затем перестройте его. Если
  база снова отклоняет запись, перестройка откатывается с этой ошибкой, и арендатор остаётся выбывшим. Проекции ещё
  нет или идёт перестройка пачками — `rebuild_required`; арендатор не участник — `tenant_denied`. С `chunked: true` —
  пачками, каждая своей транзакцией со своим снимком, пока хвост журнала идёт для всех: изменения арендатора выше
  последней пачки хвост пропускает (их прочтёт пачка), в пройденной — если транзакция видна в её снимке. Производные
  строки арендатора удаляются сразу и до конца перестройки неполны (`status().rebuildingTenants`); блокировку,
  занятую `run()` другого процесса, перестройка пережидает. Прерванную перестройку (процесс остановился) продолжает
  `run()` любого процесса — с `onExpired` и без него.
- `status().state` описывает проекцию в базе, а не процесс: `'new'` — проекции ещё нет, её построит первый `run()`
  или `rebuild()`; `'running'` — проекция построена и ведётся по журналу (это не значит, что какой-то процесс сейчас
  выполняет `run()`); `'rebuilding'` — идёт или прервана перестройка пачками.
- `version` — версия логики `handle`. Если проекция построена другой версией, `run()` бросает `rebuild_required`, и
  нужна перестройка `rebuild()`.
- Если курсор старше яруса `all` политики хранения источников и после него есть изменения, часть изменений могла
  проредиться. Ярус у каждого арендатора свой — это описание его классов. Курсор старше яруса у всех участников —
  `run()` бросает `cursor_expired`, а с `onExpired: 'rebuild'` проектор перестраивается целиком, пачками. Старше
  яруса только у части — выбывают они (`status().failed`, код `cursor_expired`), остальные идут дальше, а с
  `onExpired: 'rebuild'` выбывшие перестраиваются сами, пачками: состояние перестройки лежит в чекпоинте, и её
  продолжает `run()` любого процесса; блокировка, занятая другим процессом, — только повтор на следующем проходе, а
  ошибка данных выводит арендатора с её кодом, без повторов. Ярус перестроенного арендатора отсчитывается от начала
  его перестройки, пока курсор её не догнал: отстающий проектор не выводит его снова. Проектор без новых изменений не
  истекает. `status().lag` — возраст самого старого необработанного изменения в мс.
- Проектор работает с арендаторами, у которых каждый класс `into` помечен его `derivedBy`; изменения остальных
  арендаторов он пропускает, поэтому одноимённый класс без пометки у другого арендатора ему не мешает. Нет ни одного
  такого арендатора — `derived_class`. Пометить классы арендатора может только администратор, поэтому участников
  выбирает он: пользователь арендатора сам к проектору не подключится. Опция
  `tenants: [id, …]` — явный список участников: проектор работает только с этими арендаторами (их классы `into` тоже
  должны быть помечены), а пометку у остальных не учитывает. Источники — семейства `from` у этих арендаторов; класс
  из `into` источником не бывает, даже если попадает в `from`: свои результаты проектор не читает. Изменений класса
  с `history: false` проектор не видит: журнала у него нет. Поэтому арендатор, у которого такой класс среди
  источников, выбывает с кодом `invalid_class`, и его производных строк проектор не строит. Включите журнал класса и перестройте арендатора `rebuild({ tenant })`.
- Арендатор, который стал участником после первой проекции (администратор пометил его классы позже), получает
  начальную перестройку пачками: в проекцию попадают и строки, заведённые до вступления. Состав участников проектор
  перечитывает по сигналу классов, а на подключении без LISTEN (`listen: false`) — в начале `run()` и не реже раза
  в 5 секунд.
- `batch` — сколько изменений в пачке (500), `pollMs` — запасной опрос (1000 мс): сигналы источников будят
  проектор раньше.
- `lockTimeout` — сколько транзакция проектора ждёт чужую блокировку строки (5000 мс; 0 — без предела). Транзакция
  любого арендатора, которая держит строку итога или цель конца, иначе держала бы пачку всех арендаторов. Дольше —
  пачка откатывается, курсор остаётся, `run()` не отклоняется, а пропускает проход (`skipped`) и повторяет его. Отчёт
  называет арендатора, на чьей строке встала пачка (`locked`). `rebuild({ tenant, chunked: true })` такую блокировку
  пережидает.
- `lockRetries` — сколько проходов подряд запись одного арендатора может упираться в `lockTimeout`, прежде чем он
  выбудет (по умолчанию 0 — не выбывает). Выбывший получает код `55P03`, и пачка идёт для остальных; его изменения
  пропускаются до `rebuild({ tenant })`. Счёт ведёт процесс, удачная запись арендатора его сбрасывает. Учтите: долгая
  исключительная блокировка семейства класса System (ужесточение описания) упрётся в каждого арендатора по очереди.
- Каждая правка, которую `out` отправляет в базу, — отдельная правка строки, и скорость проектора задаёт число
  правок, а не число изменений. Свёртка `inc` сводит правки строки к одной за пачку, поэтому handle из примера выше
  (`out.inc` на каждое изменение) на машине замеров догонял 6 тысяч изменений в секунду при `batch` 500 и 33 тысячи
  при `batch` 2000 ([раздел 17](#17-производительность)): чем больше пачка, тем больше приращений одной строки
  складывается в одну правку.

### Рецепт: дневная выручка

Агрегат в базе и проектор решают похожие задачи по-разному:

| | Агрегат в базе | Проектор |
|---|---|---|
| когда считается | в той же транзакции, что и запись источника | после фиксации, с отставанием (`status().lag`) |
| что считает | сумму поля или число строк источника для одной строки-цели | что угодно: сводки по дням и группам, денормализованные карточки |
| совпадает с источником | всегда, в том числе для сырого SQL | когда проектор догнал журнал |
| цена записи | каждая операция блокирует строку цели и пишет её версию, поэтому писатели одной цели идут по очереди | писатели не ждут друг друга: проектор применяет изменения пачками после фиксации |
| правило над итогом | `min(0)` отклоняет операцию, которая увела бы итог за правило | итог не мешает записи: ошибка данных выводит арендатора из проекции |
| что запустить | ничего: поле держит база | процесс на администраторском подключении |

Баланс кошелька, который не должен уйти в минус, — агрегат ([«Рецепт: баланс агрегатом»](#рецепт-баланс-агрегатом)).
Выручка магазина по дням — итог по многим продажам, которому можно немного отставать, — работа для проектора:

```ts
const Sale = hub('Sale', { day: z.iso.date(), amount: z.number().int().min(0) }, { ends: { Shop } })   // продажа: день и сумма
const DayRevenue = hub('DayRevenue', { day: z.iso.date(), revenue: z.number().int(), sales: z.number().int() }, {
  ends: { Shop: one(Shop).onDelete('cascade') }, key: ['Shop', 'day'], derivedBy: 'day-revenue', history: false,
})
await syncModels(db, [Sale], { apply: true })
await syncModels(adm, [DayRevenue], { apply: true })   // производный класс заводит администратор: adm — с сессией арендатора

const revenue = adm.projector('day-revenue', {
  from: ['Sale'], into: ['DayRevenue'], version: 1, withBefore: true,
  handle(changes, out) {
    for (const c of changes) {
      if (c.op === 'purge' || c.op === 'trim' || c.op === 'reset') continue   // служебные изменения
      const was = c.before                          // прошлая версия продажи — вычесть из её дня
      const now = c.row.$deleted ? null : c.row     // новая — прибавить к её дню; у удаления её нет
      if (was) out.inc('DayRevenue', { Shop: was.links.Shop, day: was.data.day },
        { revenue: -Number(was.data.amount), sales: -1 }, { tenant: c.tenant })
      if (now) out.inc('DayRevenue', { Shop: now.links.Shop, day: now.data.day },
        { revenue: Number(now.data.amount), sales: 1 }, { tenant: c.tenant })
    }
  },
})
revenue.run().catch((err) => console.error('проектор выручки остановлен', err))   // следует за журналом до stop()
const week = await db.Shop(shop).DayRevenue().sort('data.day', 'desc').limit(7).rows()   // семь последних дней
```

- День — поле продажи, а не время версии `at`: со временем версии правка, `restore` или `rekey` переносили бы сумму
  продажи в свой день.
- `out.inc` прибавляет, не читая строку, поэтому итог не зависит от порядка изменений: журнал отдаёт транзакции в
  порядке первой записи, а не фиксации. Правка продажи вычитает прежнюю сумму из прежнего дня и прибавляет новую к
  новому, удаление только вычитает. День, в котором продаж не осталось, остаётся строкой с нулями. Приращения одного
  дня в пачке `out` складывает в одну правку.
- У `DayRevenue` — `history: false`: производные строки не удваивают журнал, а перестройка соберёт их и без истории.
  У `Sale` журнал нужен: изменений класса с `history: false` проектор не видит.
- Строки `DayRevenue` приложение читает, как любой класс, а пишет их только проектор: `create` или `update` такой
  строки — `derived_class`. Итог отстаёт от продаж до следующей пачки: проектор будят сигналы записи, а без них —
  опрос раз в `pollMs`.

### Кэш результатов

<!-- run: guide -->
```ts
const cached = await db.Product().cache({ ttl: 30 }).rows()   // ответ хранится в памяти процесса 30 с
const stats = db.cache.stats()                                 // { size, hits, misses, stores, raced, … }
```

Кэш включается только явно: `.cache()` в цепочке или `cache: { ttl }` у класса в модели. Как он остаётся верным:

- в ключе ответа — запрос, параметры, сессия, актор и арендатор, поэтому один пользователь не получит ответ другого;
- свои записи сбрасывают ответы изменённых классов сразу после фиксации (с классами каскада), чужие — по сигналу
  базы. В режимах `tenant` и `opaque` процесс с ключом сигналов сбрасывает класс только в арендаторе записи (строки
  System — во всех); процесс без ключа — во всех арендаторах, а в режиме `opaque` любой сигнал сбрасывает у него
  весь кэш;
- изменение прав и классов, запись через `db.sql`, погашенная сессия и переподключение слушателя сбрасывают весь
  кэш или ответы сессии;
- срок по умолчанию — 60 секунд; внутри `db.begin()` кэш не работает;
- без `LISTEN` и в режиме `none` кэш выключен, а `connect({ cache: { ttlOnly: true } })` включает его: ответ живёт до
  конца срока, если его не сбросит запись этого подключения;
- `db.load()`, проектор и `db.rebuildAggregates()` сбрасывают кэш, даже этого подключения, только сигналом базы.

Реестр классов процесс перечитывает по сигналу об изменении классов сразу (одно перечитывание за раз), а реестр и
ключ сигналов по `*`, по незнакомому токену и по нагрузке не своего режима (а без ключа в режиме `opaque` — по любому
сигналу) — не чаще раза в 5 секунд: поток сигналов, в том числе поддельных, не превращается в поток запросов. В режиме `none` реестр раз в 5 секунд сверяет отпечаток классов, а подписка
опрашивает журнал. Подписка просыпается только от своих классов и своего арендатора, а без ключа — от любого
сигнала; события она в любом случае читает из журнала, поэтому ничего не теряет.

Между процессами кэш устаревает на интервал отправки сигналов (`notifyIntervalMs`, 100 мс) плюс доставку;
`db.flushSignals()` отправляет накопленные сигналы сразу. `db.cache.clear()` очищает кэш.

## 13. Эксплуатация

### Обслуживание: `maintain()`

<!-- run: guide -->
```ts
const report = await adm.maintain()     // { sessions, codes, thinned, batches, more, queue, skipped }
```

`maintain()` удаляет из таблицы `secret` сессии и одноразовые коды всех видов (`OTP` и свои `OTP_<ИМЯ>` из
`issueOtp({ kind })`) — истёкшие, а также погашенные сессии и коды, которые уже использованы, заменены новым или
исчерпали попытки, — и строки-замки удалённых классов (по две на класс; строку, которую держит транзакция, — следующим
вызовом), прореживает журнал по политике хранения
и проверяет очередь сигналов PostgreSQL: заполнение больше половины — предупреждение. Строки удалённого аккаунта
`maintain()` ждать не нужно: их стирает само удаление ([«Удалить аккаунт»](#удалить-аккаунт)). Вызывать может системный
администратор, роль с правом `letopis.maintain` или администраторское подключение. Запускает его внешний
планировщик (`letopis maintain`) или сама библиотека: `connect({ maintain: '1h' })`. Интервал — число миллисекунд или
строка (`'500ms'`, `'30s'`, `'15m'`, `'1h'`, `'1d'`) от 1 мс до 2³¹−1 мс (около 24 суток): другое значение, в том
числе ноль, отрицательное или `NaN`, `connect()` отклоняет с `invalid_data`, не открывая соединений. `close()` ждёт
идущий по расписанию запуск: он доделывает текущую пачку и следующую не начинает. Из нескольких процессов работает один:
каждая пачка — своя транзакция, и первым делом она берёт блокировку обслуживания — строку таблицы `secret`, которую
ни прикладная, ни посторонняя роль базы не займёт; блокировка снимается с фиксацией пачки. Если блокировку держит
другой процесс, вызов до первой пачки отвечает `skipped: true`, а между пачками останавливается (продолжит тот
процесс) и отчитывается о сделанном с `more: true`. Сеансовой блокировки нет, поэтому `maintain()` работает за любым
пулом, в том числе за PgBouncer в режиме транзакций.

### Сброс: `reset()`

```ts
await adm.reset({ level: 'tenant', confirm: 'v2.shop', tenant: SHOP })   // sessions | tenant | all
```

Сброс нужен тестам и стендам. Он работает, только если установка поставлена с `up({ allowReset: true })` (иначе
`reset_disabled` даже для System), у вызывающего есть право `letopis.reset`, а `confirm` совпадает с именем схемы
(`confirm_mismatch`). Уровни: `sessions` — все сессии, кроме текущей; `tenant` — данные арендатора; `all` — всё, с заново
положенным системным сидом и новым ключом сервиса. Первая запись журнала после сброса — `reset`.

### Описание модели для людей и ИИ

```ts

const modelText = describeText(model) // то же текстом — для llms.txt приложения или подсказки ИИ-агенту
```

`db.describe()` отдаёт описание классов, доступных сессии: поля, концы, ключи, политики и метаданные, а также

### Агенты и MCP

Агент — Claude, Cursor или свой — работает с данными через инструменты MCP: узнаёт модель, читает цепочкой, смотрит
историю, а если разрешено — пишет. Сервер MCP действует от имени одного пользователя и только с его правами: каждый
вызов — цепочка под его сессией, права и арендаторов проверяет база. Сырого SQL у агента нет.

| Инструмент | Что делает |
|---|---|
| `letopis_model` | модель: классы, поля (JSON Schema), условия `anyOf` и `oneOf`, концы, ключи, алиасы, метаданные; с `class` — подробно один класс |
| `letopis_query` | чтение JSON-цепочкой: старт `class` и `filter`, `id` или `ids`; `steps` — переходы по ролям и классам; `asOf`, `withDeleted`, `sort`, `limit`, `cursor`; терминал `rows`, `first`, `ids`, `count`, `sum`, `avg`, `min`, `max`, `countBy` |
| `letopis_history` | `versions`, `diff` или `blame` одного объекта |
| `letopis_write` | `create`, `update` (только с `rev`), `upsert`, `delete` — только при `write: true` (`letopis mcp --write`) |

Запрос `letopis_query` — та же цепочка, что `db.Product({ price: lt(1000) }).Shop().sort('data.name').rows()`, только записанная JSON:

```json
{ "class": "Product", "filter": { "price": { "$lt": 1000 } }, "steps": [{ "step": "Shop" }], "sort": { "field": "data.name" } }
```

Значение фильтра — равенство, вложенный объект — поля вложенных объектов, `{ "Роль": id }` — конец. Операторы:
`$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$between`, `$in`, `$like`, `$ilike`, `$starts`, `$ends`, `$has`, `$hasAny`,
`$hasAll`, `$exists`, `$isNull`, `$not`; ИЛИ — `{ "$or": [фильтр, …] }`. Неизвестный класс, роль, параметр или
оператор — ответ `isError` с подсказкой похожих имён. Шагов `steps` — не больше 16, условий в `$or` одного фильтра —
не больше 64; иначе `invalid_query`. Время запроса эти пределы не ограничивают: задайте `statement_timeout` роли базы,
под которой подключается сервер MCP (`alter role … set statement_timeout = '5s'`).

Ответ — `structuredContent` и его текстовый дубль. `structuredContent` — `{ notice, data }`: `notice` — постоянный
текст пакета о том, что в `data` данные базы, а не инструкции, `data` — сам ответ. Форма `data` у `letopis_query`
зависит от терминала:

| Терминал | `structuredContent.data` |
|---|---|
| `rows` (по умолчанию) | `{ rows, count, more, cursor? }` |
| `ids` | `{ ids, count, more, cursor? }` |
| `first` | `{ row }` — строка или `null` |
| `count` | `{ count }` |
| `countBy` | `{ counts, truncated? }` |
| `sum`, `avg`, `min`, `max` | `{ value }` |

У `rows` и `ids` `count` — число строк на этой странице, а не всего. Страница — не больше `limit`, `maxRows` строк
(100) и `maxBytes` байт JSON строк (50 000); строка, которая сама больше `maxBytes`, приходит на странице одна.
`more: true` — есть ещё строки, и тогда `cursor` с тем же запросом отдаёт следующую страницу. `counts` —
`{ значение: число }`, самые частые значения; если группы не поместились в пределы, приходит `truncated: true`. Из
базы `countBy` читает не больше `maxRows` + 1 групп. Поле агрегата и `countBy` —
`field: 'data.<путь>'`. Сортировка — `sort: { field, dir }`: `field` — `at`, `rev`, `id` или `data.<путь>`, `dir` —
`'asc'` (по умолчанию) или `'desc'`; без `sort` строки идут по `id`. `sort`, `limit` и `cursor` — только у `rows`,
`first` и `ids`.

`letopis_model` без `class` отвечает (в `data`) `{ schema, tenant, classes }` — классы те же, что в `db.describe()`. Если такая
модель больше `maxBytes`, приходит краткая: `brief: true`, а у классов — только имена полей и концов; подробно каждый
класс отдаёт `letopis_model` с `class`. `letopis_history` принимает `class`, `id` и `kind`. `versions` отвечает
`{ versions, more }` — последние версии в пределах ответа, от старой к новой; `diff` с `from` и `to` (номер версии или
момент) — `{ diff }`; `blame` с `at` и `limit` — `{ blame }`. Если изменения или листья не поместились, ответ
обрезан, и в нём есть `truncated: true` и `total`. `follow` работает у `versions` и `diff`.

Отказ инструмента — `isError: true` и `structuredContent` вида `{ notice, error }`, где `error` — `{ code, message }`, а также `similar` (похожие
имена), `detail` (подробности) и `sqlstate` (код PostgreSQL у ошибки не из letopis), если они есть. Параметр не по
входной схеме инструмента (не тот тип, значение не из перечня, нет обязательного) отклоняет SDK ещё до letopis: тогда
`isError: true` и только текст, без `structuredContent`.

В тексте ответа всё, что пришло из базы, — строки, имена и описания классов, тексты ошибок, подсказки — стоит внутри
`<untrusted-data-…>` со случайным суффиксом и пояснением, что это данные, а не инструкции. Описания инструментов и
`instructions` сервера — постоянный текст пакета: `meta` классов пишут арендаторы, поэтому она попадает только в
результаты.

Запись. Без `write` инструмента `letopis_write` нет в списке инструментов, а его вызов — ошибка протокола SDK
(`Tool letopis_write not found`), а не ответ инструмента с `isError`. Концы записи задаёт
`links: { Роль: id | [id] | null }`, а `create`, `update` и `upsert` отвечают `{ rows }`. `update` принимает только
`rev` прочитанной версии: чужая версия — `conflict`, потерянной правки нет. `delete` без `confirm` возвращает превью
каскада и код операции: `{ preview, operation }`. С `confirm: true` удаление подтверждает человек в клиенте через
elicitation (в ревизии протокола 2025 — запросом клиенту, в 2026-07-28 — ответом `input_required`), подтверждение
привязано к хэшу операции, а ответ — `{ deleted, operation }`. В ревизии 2026-07-28 подпись `requestState`, с которой
клиент повторяет вызов, привязана ещё к пользователю сервера и действует 10 минут: подпись сервера другого
пользователя и устаревшая — отказ `confirmation_required`. Окно подтверждения показывает каноническое имя класса и
id целей (первые 10, дальше — «и ещё K»); алиас и `meta` класса пишет арендатор, поэтому в окно они не попадают. Код
операции, присланный агентом, подтверждением не считается; клиент без elicitation получает отказ
`confirmation_required`. Причина каждой записи — `mcp: letopis_write`, её показывает `blame()`. Классы прав — `rule`,
`Resource`, `member`, `Account`, `Class` и их потомков (правила, членства, описания классов) — `letopis_write` по
умолчанию не пишет, не правит и не удаляет: отказ `acl_denied`. Агент под инъекцией в данных выдал бы постороннему
членство или правило без подтверждения человека. Разрешает это только опция `allowAclWrite: true`.

**stdio.** `letopis mcp` — сервер по stdio для клиентов MCP. Нужен пакет SDK: `npm i @modelcontextprotocol/server`
(необязательная peer-зависимость). Строку подключения, схему и токен клиент передаёт флагами или переменными
`LETOPIS_DSN`, `LETOPIS_SCHEMA`, `LETOPIS_TOKEN`; `--write` включает запись. Принимается только токен сессии
пользователя — его выпускает приложение: `svc.auth.sessionFor(пользователь, { ttl })`, а рабочий арендатор сессии
задаёт `auth.switch(арендатор)`. Ключ сервиса (`--api-key`) команда отклоняет: он даёт все права `auth.*` и лежал бы на
машине агента. Без токена и с `--api-key` команда завершается с кодом 2 и пишет причину в stderr. Токен сессии в
арендаторе System (так работает системный администратор) команда тоже отклоняет: опций `allowSystemAdmin` и
`allowAclWrite` у неё нет. Конфигурация клиента (Claude Desktop, Claude Code, Cursor):

```json
{
  "mcpServers": {
    "letopis": {
      "command": "npx",
      "args": ["letopis", "mcp"],
      "env": {
        "LETOPIS_DSN": "postgres://shop_app:app-secret@localhost:5432/shop",
        "LETOPIS_SCHEMA": "v2.shop",
        "LETOPIS_TOKEN": "<токен сессии пользователя>"
      }
    }
  }
}
```

**HTTP.** Встроенного HTTP-сервера нет. `createMcpServer(db, { write, maxRows, maxBytes })` из `letopis/mcp` отдаёт
сервер MCP, а приложение подключает его к своему обработчику `createMcpHandler` из SDK со своей авторизацией
OAuth 2.1: токен запроса проверяет приложение и находит по нему пользователя letopis. Подключение — сессия
пользователя (`connect({ token })`) или фасад `svc.as(пользователь)`: ключ сервиса остаётся в процессе приложения.
Подключение в обход RLS получает отказ `bypass_rls`, корень сервиса без `as()` и подключение без сессии —
`user_session_required`, фасад явной транзакции `db.begin()` — `invalid_query`. Сессию в арендаторе System — так
работает системный администратор: его роль `admin` даёт права на аккаунты, членства и правила установки — сервер тоже
отклоняет с `user_session_required`, если не передана опция `allowSystemAdmin: true`.

<!-- run: mcp -->
```ts
import { up, connect } from 'letopis'
import { createMcpServer } from 'letopis/mcp'
import { createMcpHandler } from '@modelcontextprotocol/server'

const ADMIN = 'postgres://postgres:secret@localhost:5432/shop'
const APP = 'postgres://shop_app:app-secret@localhost:5432/shop'
const r = await up({ dsn: ADMIN, schema: 'shop', quiet: true,
  tenant: { name: 'Ромашка', user: { name: 'Анна', login: 'anna@shop.ru', password: 'Ромашка-2026!' } } })
const svc = await connect({ dsn: APP, schema: r.schema, apiKey: r.serviceKey! })

// authInfo — итог проверки токена запроса приложением; в extra оно кладёт id аккаунта letopis
const mcp = createMcpHandler(async ({ authInfo }) =>
  createMcpServer(await svc.as(String(authInfo?.extra?.account), { tenant: r.tenant!.tenant })))
// в HTTP-обработчике приложения, после проверки токена: return mcp.fetch(request, { authInfo })
```

Фабрику обработчик вызывает на каждый запрос HTTP, поэтому `createMcpServer` проверяет подключение каждый раз (один
запрос к базе).

Проверить обработчик можно без сети: клиент SDK из пакета `@modelcontextprotocol/client` ходит в него через `fetch`
приложения — `new StreamableHTTPClientTransport(new URL('http://localhost/mcp'), { fetch: (url, init) =>
mcp.fetch(new Request(url, init), { authInfo }) })`. Так пример выше проверяет тест `docs` (сценарий `mcp` в
`lib/test/docs.test.ts` репозитория): без `write` клиент видит три инструмента, а `letopis_model` отвечает от имени
Анны в магазине.

### Сырой SQL

<!-- run: guide -->
```ts
const [{ n }] = await db.sql`select count(*)::int as n from "v2.shop".entity where class = 'Product'`
```

`` db.sql`…` `` выполняет запрос одной транзакцией под сессией подключения и RLS: видны те же строки, что и
цепочкам. `db.transaction(fn)` даёт соединение postgres.js на всю транзакцию. При взаимной блокировке и ошибке
сериализации запрос и `fn` повторяются до трёх раз, поэтому `fn` должна выдерживать повтор. Писать сырым SQL тоже
можно — те же триггеры проверят данные, а функции базы `merge` и `inc` доступны приложению.

### Командная строка

```sh
letopis sync <модуль> --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--apply]
letopis types --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--out <файл>]
letopis load <файлы…> --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--class <Класс>]
  [--duplicates error|first|last] [--existing error|skip|update] [--commit-every <N>] [--verify] [--initial]
letopis verify --dsn <строка> --schema <v2.имя> [--token <токен> | --api-key <ключ>] [--data]
letopis maintain --dsn <строка> --schema <v2.имя> [--token <токен> | --api-key <ключ>] [--batches <N>]
letopis describe --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--format json|text] [--out <файл>]
letopis import --from <строка 0.21> --from-schema <v1.имя> --dsn <строка> --schema <v2.имя> [--tenant <имя>] [--keyless <Класс>]…
  [--rename <Старое>=<Новое>]… [--update] [--commit-every <N>] [--partition <имя>] [--initial]

  (или LETOPIS_DSN, LETOPIS_SCHEMA, LETOPIS_TOKEN; ключ сервиса --api-key не принимается)
```

`letopis types` и `letopis describe` строят результат по классам сессии, поэтому без действующей сессии (токен истёк,
погашен, неверен или не задан, ключ API неверен) выходят с кодом 1 и ошибкой `no_session`, а файл `--out` не трогают.

### Наблюдение

- `connect({ onQuery, slowMs })`: хук получает на каждый запрос цепочки режим, классы, длительность, число строк и
  признак медленного запроса; без хука медленный запрос печатает предупреждение.
- `sub.lag()` — отставание подписки; отчёт `maintain()` — заполнение очереди сигналов.
- Горячие цели ссылок (организация, на которую ссылается почти всё) копят блокировки `for key share` и MultiXact,
  как при обычных внешних ключах. Это стоит мониторить.

### Пулы соединений и PgBouncer

С PgBouncer в режиме транзакций `LISTEN` недоступен: `connect({ listen: false })`. Тогда реестр перечитывается через
`db.refresh()`, подписка опрашивает журнал, а кэш результатов выключен или работает по сроку. Подготовленные
операторы работают с PgBouncer 1.21 и новее; со старыми передайте свой пул postgres.js с `prepare: false` в
`connect({ sql })`. `maintain()` берёт транзакционную блокировку в каждой пачке и работает за таким пулом.

## 14. Переход с 0.21

1.0 — новая реализация, а не продолжение 0.21: схема 0.21 не обновляется на месте. 1.0 ставится в новую схему,
данные переносит команда `letopis import`, а код переводится по таблице замен из [MIGRATION.md](MIGRATION.md).
Главные отличия в поведении: `create` не перезаписывает (занятый ключ — `exists`), `count()` считает сущности,
пути — `paths()`, права и изоляция арендаторов включены всегда.

```sh
npx letopis import --from postgres://…/old --from-schema v1.salon --dsn postgres://…/new --schema v2.salon \
  --tenant salon [--keyless booking] [--rename link=link_] [--update] [--commit-every 100000]
```

- Схема 1.0 ставится заранее (`up()`), оба подключения — администраторские. Источник — таблицы 0.21 (`Schema`,
  `Entity`, `Account`, `Credential`, `Resource`, `Rule`) любой базы: PostgreSQL 17 с TimescaleDB или дамп обычных
  таблиц. Пишут загрузчик (режим истории, `existing: 'skip'`, агент `letopis import`) и функции владельца.
- Классы становятся строками `Class` в System. Правила fastest-validator переводятся в JSON Schema (`optional`
  пропускает `null`, `$$strict` → `additionalProperties: false`, `record` → `propertyNames`). Концы — роли по
  имени класса цели, союз всех потомков класса — полиморфный конец. Корни `Entity` и `link` опускаются;
  `description`, `appearance`, `order` переходят в `meta`. Имена, занятые методами 1.0, — `--rename` (по умолчанию
  имя с `_`).
- id: у класса с ключом (правило v5 из 0.21) — v5 от ключа, у класса без ключа — v5 от старого id. Данные System
  переходят в арендатора `--tenant`, аккаунты — в строки `Account`, креды — в `secret` как есть (scrypt, ключи);
  одноразовые коды не переносятся. Ресурсы и правила — в System.
- До первой записи импорт останавливается, если два объекта 0.21 дают один id 1.0 (данные нарушают ключ —
  `--keyless <Класс>`), если ключ менялся между версиями или ссылается на отсутствующий объект. Висячая ссылка
  живой строки — `target_not_found` с объектом 0.21.
- Если загрузчик отклонил данные, ошибка начинается с `import: арендатор …`, а её `detail` — как у загрузчика
  ([«Отчёт и ошибки»](#отчёт-и-ошибки)), только строки названы объектами 0.21: `rows` — нарушения с `class`, `id`
  и `rev` объекта 0.21, `code` и `message`; `total`, `truncated`, `limit` и `complete` — как в отчёте загрузчика;
  `notes` — непереведённые правила.
- Повтор дописывает недостающее без дублей, `--update` — ещё и новые версии изменившихся объектов. Отчёт — JSON в
  конце вывода: объекты и версии по классам в 0.21 и в 1.0, `verify()`, непереведённые правила, классы без ключа и
  uuid в `data`, совпадающие со старыми id (их импорт не переписывает). Код выхода 1, если `verify()` нашёл
  расхождения.

Проверку паролей, кодов и TOTP, выпуск сессий, сведения о сессии по токену и подтверждение кредов вызывает сервис
(права `auth.*`); обычному пользователю отвечают `acl_denied`. Креды System, сервисов и системных администраторов
меняет только сам аккаунт после недавнего интерактивного входа или системный администратор. Исключение — ключи
сервиса: свои ключи API и пары «ключ + секрет» сервис выпускает и отзывает сам по сессии своего ключа, прочие свои
креды — нет; последний действующий ключ сервиса не отзывается никем (`acl_denied`). С `totp` вход `verifyPassword` и
`lookup` проверяет ещё и код TOTP (право `auth.totp`) и выдаёт сессию со способом `TOTP`.
Вид креда `kind` — `^[A-Z][A-Z0-9_]{1,31}$` (`PASSWORD`, `EMAIL`, `TELEGRAM` …); `SESSION`, `APIKEY`, `KEYSECRET`,
`OTP`, `TOTP`, `KEY`, `PROJECTOR` и `LOCK` заняты. То же правило — у вида пароля `user.kind` в `createTenant` и
`up({ tenant })`.

### Проектор

`db.projector(имя, опции)` работает только на администраторском подключении ([«Проекторы»](#проекторы)). Имя —
строчные латинские буквы, цифры и `_.:-`, до 64 символов; оно же — `derivedBy` производных классов. Неверные опции —
`invalid_data`.

| Член | Что делает |
|---|---|
| опции `ProjectorOptions` | `from`, `into` — классы с потомками; `version` — целое от 1; `handle(changes, out)`; `withBefore`; `onExpired: 'rebuild' \| 'error'` (`'rebuild'` — пачками); `batch` — изменений в пачке (500, от 1 до 10 000); `pollMs` — запасной опрос (1000 мс); `lockTimeout` — ожидание чужой блокировки строки (5000 мс, 0 — без предела); `lockRetries` — проходов подряд до выбывания арендатора с чужой блокировкой (0 — не выбывает); `tenants` — id арендаторов-участников |
| `run({ once })` | догнать журнал (`once`) или следовать за ним до `stop()` → `ProjectorReport` |
| `rebuild({ chunked, tenant })` | перестроить с текущего состояния: атомарно, пачками или одного арендатора → `ProjectorReport` |
| `status()` | → `ProjectorStatus`: `{ name, state, version, cursor, at, lag, failed, rebuildingTenants }`; `failed` — `{ [id арендатора]: ProjectorFailure }`, где `ProjectorFailure` — `{ cursor, code, message }` |
| `stop()`, `close()` | остановить `run()` после текущей пачки; то же и отписаться от сигналов |
| `ProjectorReport` | `{ batches, changes, created, updated, deleted, unchanged, skipped, rebuilds, locked }` |
| `ProjectorChange` | `{ cursor, id, class, tenant, op, rev, at, author, row }` и, если есть, `agent`, `reason`, `moved`, `before`, `rebuild` |
| `ProjectorOut` | `upsert(класс, строка, { tenant })`, `inc(класс, строка, приращения, { tenant })`, `delete(класс, ключ или id, { tenant })`, `get(класс, ключ или id, { tenant })` → `Row \| null`; строка — `ProjectorRow` в формате загрузчика; у класса с ключом `delete` и `get` — по ключу, id — только у класса без ключа |

### Строка ответа

| Поле | Что значит |
|---|---|
| `id`, `class`, `rev` | id, класс, номер версии (для `update(патч, { rev })`) |
| `tenant`, `owner` | арендатор и владелец строки |
| `links`, `data`, `tags` | концы, поля, теги |
| `at`, `author`, `agent`, `op`, `reason` | время версии (ISO, UTC, микросекунды), автор, агент (сервис при имперсонации), вид операции, причина |
| `moved` | связь со старым или новым id после `reclass` и `rekey` |
| `$deleted` | надгробие: удалённая сущность или версия удаления |
| `$depth` | глубина узла в `deep()`; уровень каскада в превью удаления |
| `$upsert`, `$action`, `$versions`, `$purged` | что сделал `upsert`; что сделает удаление; число версий в `purge`; история стёрта |

### Зарезервированные имена

Имя метода закрывает класс только там, где этот метод есть: после шага — методы цепочки, у корня `db` — его методы,
у батча — его. Поэтому хаб с именем метода только цепочки (например, `count`) доступен первым шагом `db.count(…)`, а
после другого шага недостижим; хаб с именем метода корня первым шагом не вызвать. Связь с любым из этих имён база не
примет (`reserved_names()`; список подставляет установщик из `RESERVED_CLASS_NAMES`). Не давайте классам эти имена.

- методы цепочки: `then`, `entity`, `paths`, `rows`, `first`, `ids`, `count`, `limit`, `offset`, `sort`, `asOf`,
  `withDeleted`, `deep`, `exact`, `sum`, `avg`, `min`, `max`, `countBy`, `after`, `versions`, `create`, `update`,
  `upsert`, `set`, `unset`, `add`, `remove`, `delete`, `anonymize`, `reclass`, `restore`, `purge`, `alias`, `tags`,
  `owner`, `forUpdate`, `cache`, `rekey`, `diff`, `blame`; охранники снесённого API — `run`, `execute`, `account`;
- корень `db`: `as`, `begin`, `commit`, `rollback`, `lock`, `batch`, `watch`, `close`, `registry`, `sql`, `load`,
  `verify`, `maintain`, `reset`, `describe`, `auth`, `acl`, `idOf`, `refresh`, `transaction`, `flushSignals`,
  `schema`, `token`, `tenant`, `trimHistory`, `rekeyClass`, `cache`, `projector`, `rebuildAggregates`; охранники — `reloadSchema`,
  `accounts`, `credentials`, `resources`, `rules`, `compact`;
- батч: `discard`, `size`.

## 16. Ошибки

Текст ошибки — `letopis: <код>: <сообщение>`. Код — в `err.code`, подробности — в `err.detail`. Ошибки — объекты
`LetopisError`, у ошибок данных — `ValidationError` с `err.issues: [{ path, keyword, message }]`.

Коды базы. Их получает и сырой SQL: SQLSTATE класса `LT`, подробности — JSON в `DETAIL`.

| `projector_busy` | перестройку не начать: проектор сейчас работает в другом процессе |
| `not_empty` | первая заливка (`initial`) — только в пустую схему |

Отказ PostgreSQL в праве (`42501`) приходит, например, при `upsert` поверх чужой строки, которую нельзя править.

## 18. Ограничения

Здесь собрано то, что letopis 1.4 сознательно не делает или делает с оговорками, и где за поведением нужно следить.

**Платформа**

- Нужен PostgreSQL 18 или новее; обходных путей для 15–17 нет. AWS RDS, Google Cloud SQL, Azure Flexible Server
  и Neon поддерживают 18, а Supabase на октябрь 2026 года — только 15 и 17, поэтому там letopis не заработает.
- База — в кодировке UTF8 (`casefold()` и коллация `pg_unicode_fast`). Если новая основная версия PostgreSQL
  обновит таблицы Unicode, уникальный индекс идентификаторов кредов перестраивается командой `reindex`.
- PGlite — одно соединение суперпользователя: без параллельных писателей и `LISTEN`, RLS не действует
  (`allowBypassRls: true`); не замена `postgres:18` для прав, гонок и CI.
- Пул в режиме транзакций (PgBouncer): `LISTEN` недоступен — `connect({ listen: false })`, подписка опрашивает журнал,
  кэш результатов выключен; подготовленные операторы работают с PgBouncer 1.21, со старыми — пул postgres.js
  с `prepare: false` в `connect({ sql })`.
- Символ NUL (`\u0000`) в строках данных невозможен: PostgreSQL не хранит его в `jsonb`; такие данные
  отклоняются ещё при разборе JSON (официальный набор JSON-Schema-Test-Suite, группы «nul characters», пропущены).
- На PostgreSQL до 18.6 параллельная сборка индекса GIN могла записать в статистику таблицы (`pg_class.reltuples`)
  неверное число строк, после чего автоочистка переставала её обрабатывать. Первая заливка поэтому всегда
  заканчивается `ANALYZE`, но сервер лучше обновить до 18.6 или новее.

**Запись и целостность**

- Построчная запись дороже простой вставки: каждую строку проверяют триггеры (данные, концы, id, журнал, хэш, RLS).
  Построчный `create` медленнее 0.21 на 12–18 % ([раздел 17](#17-производительность)); для массовой записи есть
  загрузчик.
- Удаление, смена класса и смена ключа работают только в `read committed` (`isolation_level`); транзакции
  библиотеки всегда открываются на этом уровне.
- `COPY` в таблицы под RLS PostgreSQL не выполняет; массовая загрузка — только загрузчиком на администраторском
  подключении.
- Первая заливка закрывает таблицы схемы на всё время загрузки — и для записи, и для чтения: она для пустой схемы
  (засевка, перенос, импорт), а не для работающей системы. Выигрыш у неё — в базе (индексы и ограничения строятся
  один раз); подготовку строк в загрузчике она не ускоряет, а только ведёт одновременно с `COPY`, поэтому на миллионе
  объектов она быстрее обычной загрузки примерно в 2,2 раза.
- Загрузчику база доверяет: данные, концы и id загруженных строк проверяет код библиотеки (валидатор на TypeScript),
  а не триггеры; база сверяет только цели вне загрузки, арендаторов и владельцев одним запросом в конце.
  Защита — загрузчик только у администратора, дифференциальные тесты валидатора против базы, `load({ verify: true })`
  и `db.verify({ data: true })`. Администраторское подключение держит отдельный процесс загрузки, а не
  веб-приложение: SQL-инъекция в нём получила бы права владельца.
- Владелец схемы и суперпользователь могут отключить триггеры и изменить что угодно. letopis это не предотвращает,
  а обнаруживает: `verify()` пересчитывает цепочки хэшей, `verify({ data: true })` перепроверяет строки, а якорь
  (хэш всех голов цепочек) стоит хранить вне базы.
- В базе проверяется подмножество JSON Schema: `refine`, `superRefine` и `transform` Zod работают только
  в библиотеке, описание с неизвестным ключевым словом база не примет; `pattern` — ограниченное подмножество
  регулярных выражений, общее для Zod, валидатора и базы. Вывод `z.toJSONSchema()` меняется между версиями Zod:
  в базе хранится уже нормализованная схема, а сухой прогон `syncModels` показывает разницу до применения.
- Ключ — единственный способ уникальности: id вычисляется из значений ключа без нормализации, поэтому одно
  значение в разной записи (email в разном регистре, время с миллисекундами и без) даёт разные id. Формат
  ключевого поля задаёт модель, и база его проверяет.
- Частая смена значения ключа (email, телефон) требует `rekey`. Изменчивые и персональные значения лучше выносить
  в отдельный хаб со связью: id из email подбирается перебором и остаётся в ссылках и журнале даже после
  `anonymize`, а отдельный хаб удаляется вместе со связью через `purge`.
- `create` занятого ключа отвечает `exists` с id, `upsert` без права на существующую строку — отказом `42501`:
  так раскрывается, что ключ занят, но только внутри своего арендатора — у других арендаторов те же ключи дают
  другие id.
- Смена класса и ключа переписывает все входящие ссылки (и рекурсивно — связи, в ключ которых входит этот конец),
  поэтому её цена пропорциональна числу ссылок. Ужесточение описания класса и `rekeyClass` на время проверки или
  переноса приостанавливают запись в семейство.
- `rekeyClass` переносит строки одной транзакцией под исключительной блокировкой семейства, а не пачками:
  между пачками строки со старыми id нарушали бы правило «id — v5 от ключа».
- id v5 ложатся в индекс первичного ключа вразброс; на очень больших таблицах с интенсивной вставкой это заметнее,
  чем с последовательными id.
- Горячие цели ссылок (организация, на которую ссылается почти всё) копят блокировки `for key share` и MultiXact,
  как при обычных внешних ключах; это нужно мониторить. Операции одного кошелька идут друг за другом под
  блокировкой его строки ([раздел 8](#8-транзакции-батчи-и-деньги), «Рецепт: кошелёк»).
- Связь не может называться зарезервированным именем, а хаб с таким именем доступен не везде: например, `count` —
  только первым шагом ([«Зарезервированные имена»](#зарезервированные-имена)).

**Доступ**

- Сервисный ключ — корень доверия: его компрометация позволяет действовать от имени любого включённого пользователя
  установки, кроме System, сервисов и системных администраторов; правила доступа этот круг не сужают. Ключ
  перевыпускает (`db.auth.issueApiKey`) и отзывает (`db.auth.revokeCredential`) сам сервис по сессии своего ключа или
  системный администратор; своим ключом сервис выпускает себе и новые ключи, поэтому после утечки отзовите все его
  ключи, кроме нового (их список — `credentials`). Последний действующий ключ сервиса не отзывается никем: отключить
  сервис — `enabled: false` у его аккаунта. Один пароль от базы без токена не даёт ничего.
- Пропуск прав открывает клиенту его собственный план (классы и условия правил, которые к нему применимы).
- Сырой SQL без пропуска прав платит за план прав на каждый запрос: 0,3–1,3 мс в зависимости от числа правил.
- Имена концов `User`, `Tenant` (членство), `Group`, `Object` (правило) заняты системными классами во всей схеме.
- Счётчики попыток OTP и TOTP откатываются вместе с транзакцией вызывающего: частоту попыток ограничивает сервис.
- Самостоятельная привязка занятого идентификатора отвечает `acl_denied` — пользователь с недавним входом так
  узнаёт, что идентификатор занят. Изменения прав во всех арендаторах упорядочены одной строкой счётчика.
- Тексты отказов называют класс, роль и id ссылающейся строки, только если актор её видит: каскад удаления, снятие
  конца, перевод ссылок при смене класса и ключа, конфликт смены `parent` (`tightening_conflict`). Число невидимых строк, мешающих удалению или смене класса
  (`reclass_denied`), и существование аккаунта по id (как цели ссылки) не скрываются.
- Ужесточение описания класса и `rekeyClass` проверяют все строки семейства, поэтому требуют права `READ` без условий
  на все строки класса и его потомков: иначе пробное ужесточение (`maximum`, `enum`, `pattern`) отвечало бы числом
  невидимых строк, которые ему не соответствуют. Системный администратор, ужесточая класс System, получает число
  нарушающих строк других арендаторов (`others`): это уровень установки.
- Метаданные классов (`meta`) видны всем, у кого есть сессия: строки `Class` читает любой. Секретам там не место.
- Прикладная роль может замедлить установку для всех: `LOCK TABLE entity`, advisory-блокировки с ключами `lock()`
  приложения, поддельные сигналы `NOTIFY` (лишь сбрасывают кэш), частая смена прав (одна строка счётчика на
  установку). По глобальному номеру журнала видна общая активность записи. Внутренние блокировки — семейства
  классов, проектора и обслуживания — строки таблицы `secret`, а не advisory: ни прикладная, ни посторонняя роль базы
  их не займёт. Писатель семейства проходит шлюз ужесточения в подтранзакции — одной на первую запись в семейство за
  транзакцию.

**История, сигналы, кэш**

- Срез `asOf` восстанавливается из журнала; дёшево только текущее состояние. В прореженной части журнала срез
  показывает последнюю сохранённую версию до момента: его точность там равна периоду яруса — дню, неделе, месяцу
  или году. Импорт истории в класс с политикой прореживается сразу, и подписчик может не увидеть старые версии.
- Прореженная часть журнала не доказывает ни полноты истории, ни подлинности старых версий: подмену версии
  старше яруса `all` у класса с политикой `verify()` не отличит от прореживания.
- Журнал без партиций: прореживание удаляет версии пачками, файл таблицы сам не уменьшается (место занимают новые
  версии после autovacuum); вернуть место системе — `VACUUM FULL` или `pg_repack` в окно обслуживания.
- Сигналы раскрывают активность: слушать канал PostgreSQL разрешает любой роли. В режиме `class` видно, когда и в
  какие классы пишут; `tenant` добавляет псевдонимы арендаторов; `opaque` прячет, что записано, но не когда: время и
  частоту записи по псевдониму видно, а детерминированный токен — основа частотных атак. Время записи видно и без
  сигналов: `pg_stat_all_tables` и `pg_locks` открыты для PUBLIC. Режим `none` убирает сигналы, но тогда отзыв
  сессии действует в кэше других процессов только по сроку, а новый класс появляется в их реестре в течение
  5 секунд. Настоящая защита от посторонних ролей — отдельная база. Поддельный сигнал лишь сбросит кэш лишний раз:
  по `*` и незнакомым токенам реестр перечитывается не чаще раза в 5 секунд, а поддельный сигнал изменения классов
  перечитывает его, как настоящий, но не больше одного перечитывания одновременно.
- Режим сигналов меняется `up({ signals })`, и после этого нужно перезапустить процессы: режим и ключ сигналов
  процесс читает при подключении (нагрузку другого режима он считает чужой и сбрасывает весь кэш).
- PostgreSQL ниже 18.2 мог усечь CLOG, который ещё нужен непрочитанным сигналам: `up()` предупреждает об этом.
- Очередь `NOTIFY` (8 ГБ) общая для кластера: зависший слушатель её переполняет, и тогда транзакции с `NOTIFY`
  падают при фиксации. Библиотека читает сигналы сразу, `maintain()` предупреждает о заполнении больше чем
  наполовину.
- Транзакции с `NOTIFY` PostgreSQL фиксирует по одной: общую для кластера блокировку очереди сигналов фиксация держит
  вместе с записью на диск. Запись сырым SQL на своём соединении шлёт сигнал из триггера в той же транзакции, поэтому
  параллельные писатели сырым SQL фиксируются по очереди: на машине замеров 20 таких писателей делали около 520
  вставок в секунду. Транзакции библиотеки, в том числе `db.sql` и `db.transaction()`, фиксируют данные без `NOTIFY` и
  отправляют сигналы потом, отдельно, поэтому их писатели этой очереди не ждут: 20 писателей библиотеки делали около
  2 000 операций в секунду.
- Горизонт подписки общий для кластера: долгая пишущая транзакция задерживает события всех подписчиков
  (`sub.lag()`); длинные операции лучше вести пачками.
- Кэш результатов между процессами устаревает на интервал отправки сигналов (100 мс) плюс доставку и на время
  переподключения слушателя: обрыв соединения слушателя postgres.js не сообщает, поэтому до переподключения кэш
  работает, а после — сбрасывается целиком. Срок `ttl` — предохранитель.
- Курсор подписки «с этого момента» несёт снимок момента подписки, пока не пройдёт его границу: такой
  курсор длиннее обычного.

**Проекторы**

- Проектор — процесс администратора: он работает только на администраторском подключении, читает журнал всех
  арендаторов в обход RLS и пишет результаты от роли владельца. Держите его в отдельном процессе, как загрузчик.
  Участник проектора — арендатор, у которого все классы `into` помечены его `derivedBy`; пометить класс может только
  администратор (право `letopis.projector`).
- Итоги производного класса видит каждый, кому правила арендатора дают `READ` на него, — даже тот, кто не читает
  строки источников: решайте, кому его читать, правилами на сам производный класс. С `history: true` его журнал
  показывает изменение каждой пачки, то есть и вклад отдельных строк источников.
- Строки производных классов пишет только их проектор: приложение, сырой SQL и загрузчик получают `derived_class`, а
  ссылаться на такие строки концами нельзя.
- Атомарная перестройка — одна долгая пишущая транзакция: пока она идёт, горизонт подписок стоит, и события
  задерживаются у подписчиков и проекторов всех процессов. На машине замеров перестройка 75 тысяч строк шла 13 с, и
  до её конца подписчик не получил ни одного события. Поэтому сам `run()` перестраивает пачками, а атомарную
  перестройку запускает только явный `rebuild()`.
- Перестройка пачками держит горизонт только на время пачки (в тех же замерах события задерживались до 0,2 с), но
  до её конца производные данные неполные: строки удалены сразу и появляются по мере перестройки.
- Проектор видит только изменения из журнала, поэтому класс с `history: false` источником быть не может: арендатор
  с таким источником выбывает из проектора (`invalid_class`), пока журнал класса не включат и арендатора не
  перестроят.
- Прореживание журнала старше яруса `all` ведёт к перестройке: проектор, отставший больше чем на этот ярус,
  получает `cursor_expired` или, с `onExpired: 'rebuild'`, перестраивается сам. Ярус — по арендатору: истёк только у
  части участников — выбывают и перестраиваются только они.
- Проектор работает только на схеме той ревизии движка, которую ждёт библиотека; на схеме другой ревизии он
  отвечает `invalid_data`.
- `purge()` ждёт проекторов: пока проектор, чьи источники включают класс объекта, а у арендатора объекта есть его
  производный класс, не прочёл удаление, `purge` отвечает `projector_pending`. Проектор, который больше не запускают,
  держит `purge` своих источников, пока у арендатора есть его производные классы: запустите его или удалите их.
  Так же ждёт `trimHistory`: пока проектор не прочёл первую оставшуюся версию, обрезка отвечает `projector_pending`.

**Агрегаты в базе**

- Агрегат выстраивает писателей одного объекта в очередь: каждая операция блокирует строку цели и пишет её версию.
  На машине замеров 20 писателей одного кошелька с агрегатом делали 152 операции в секунду (p95 — 0,47 с), без
  агрегата — 1 987. Для горячих счётчиков берите проектор со свёрткой пачкой.
- `reclass` и `rekey` копят вклады до конца переноса, а каскад удаления и загрузчик применяют их по операторам:
  правило класса проверяется на итоге каждого оператора каскада и каждой пачки загрузчика. Поэтому загрузка, где
  списания идут пачкой раньше пополнений, получит `invalid_data`, хотя итог всей загрузки допустим. Каждая пачка,
  задевшая цель, пишет её версию.
- Агрегат арендатора не считает строки класса System, а поле строки System считает только источники System.

**Агенты и MCP**

- Обёртка `<untrusted-data-…>` — смягчение, а не защита: модель может последовать тексту внутри неё. Защищают права
  базы: агент читает и пишет только то, что разрешено его пользователю. В `structuredContent` данные базы лежат в
  `data` и `error` рядом с пояснением `notice`, без меток: клиент, который отдаёт модели его, а не текст, передаёт
  данные с пояснением, но без случайной метки.
- По умолчанию сервер только читает; запись — `write: true` (`--write`); удаление — только с подтверждением человека.
  Классы прав сервер пишет только с `allowAclWrite`, сессию в арендаторе System принимает только с
  `allowSystemAdmin`; `create`, `update` и `upsert` остальных классов подтверждения человека не требуют.
- Обработчик HTTP в ревизии 2025 работает без состояния: экземпляр на запрос не знает возможностей клиента, поэтому
  удаление по нему отклоняется (`confirmation_required`). Удаляйте по stdio или в ревизии 2026-07-28.
- Подтверждение в ревизии 2026-07-28 подписано ключом процесса: повтор вызова, попавший в другой процесс приложения
  (несколько экземпляров за балансировщиком), получает отказ `confirmation_required`.
- `versions` отдаёт последние версии в пределах `maxRows` и `maxBytes` (из базы — не больше `maxRows` + 1 версий) и
  `more`; более ранние — `diff` и `blame` с `from`, `to`, `at`. Режим, в котором агент пишет код против API (code
  mode), в пакет не входит.

**Импорт из 0.21**

- 1.0 — новая major-версия, а не продолжение 0.21: `count()`, `paths()`, `create`, роли, множественные концы
  и `reclass` ведут себя по-новому, данные переносятся импортом ([MIGRATION.md](MIGRATION.md)).
- Импорт: шаги (классы, аккаунты, креды, права, данные каждого арендатора) — отдельные транзакции, источник
  читается в память целиком; владелец строки, не найденный среди аккаунтов, становится арендатором; правила доступа
  0.21 переносятся в System и действуют во всех арендаторах; `onDelete` концов — `cascade`, как удаляла 0.21.

## 19. Тесты

Раздел — для тех, кто развивает сам letopis. Запуск: `cd lib && npm test`. Обвязка сама поднимает контейнер `letopis-pg18` (`postgres:18`,
порт 15433), если база не отвечает; каждый тестовый файл работает в своей схеме `v2.t_<имя>`.
