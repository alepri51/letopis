# letopis 1.0

letopis — хранилище версионированных сущностей на PostgreSQL 18. Целостность, история,
изоляция арендаторов и права проверяет сама база: триггеры и политики RLS действуют и для
библиотеки, и для сырого SQL. Поверх базы — цепочки вида `db.Staff(vasya).booking().rows()`.

- Требования: PostgreSQL 18 или новее с расширением pgcrypto, база в кодировке UTF8, Node 22 или новее.
- Рантайм-зависимость одна — `postgres`. Zod 4 — необязательная peer-зависимость: он нужен только
  подпути `letopis/model`, `import { connect } from 'letopis'` работает и без него.
- Переход с 0.21 — `lib/MIGRATION.md` (импорт данных и таблица замен API), решения по версиям — `lib/CHANGELOG.md`.
  Документация 0.21 — в теге `v0.21.0`: `git show v0.21.0:lib/README.md`.

## 1. Быстрый старт

```sh
npm install letopis zod
```

```ts
import { up, connect, inc, gte, syncModels } from 'letopis'
import { hub, link, one } from 'letopis/model'
import { z } from 'zod'

// 1. Установка — от администраторской роли. Повторный вызов безопасен: повторный накат той же ревизии.
const r = await up({ dsn: 'postgres://admin@localhost/app', schema: 'shop' })    // схема v2.shop
// r.serviceKey — ключ сервиса; выдаётся только при первой установке, его нужно сохранить

// 2. Подключение сервиса — от роли приложения (член letopis_app): ключ обменивается на сессию.
const svc = await connect({ dsn: 'postgres://app@localhost/app', schema: 'v2.shop', apiKey: r.serviceKey! })

// 3. Вход пользователя и работа от его имени в его арендаторе (имперсонацию проверяет база).
const login = await svc.auth.verifyPassword({ identifier: 'anna@shop.ru', password })   // { account, token } | null
const db = await svc.as(login!.account, { tenant: org })

// 4. Модель на Zod: хаб с ключом и связь. sync сверяет описания с базой и применяет изменения.
const Product = hub('Product', { name: z.string(), price: z.number().int().min(0) }, { key: ['name'] })
const review = link('review', { ends: { Product: one(Product) }, fields: { text: z.string(), stars: z.number().int() } })
await syncModels(db, [Product, review], { apply: true })        // или CLI: letopis sync ./models.js --apply

// 5. Запись и чтение цепочками.
const [p] = await db.Product().create({ name: 'Чайник', price: 2500 }).rows()   // id — v5 от ключа
await db.Product(p.id).review().create({ text: 'Хорош', stars: 5 }).rows()      // конец Product — из пути
await db.Product(p.id).update({ price: inc(-500) }).rows()                     // приращение внутри оператора
await db.Product({ price: gte(1000) }).review().count()
await db.Product(p.id).versions()                                              // история из журнала
```

Аккаунты, членства в арендаторах и правила доступа — строки системных
классов `Account`, `member`, `Resource` и `rule`; их пишет системный администратор (член System с ролью `admin`)
теми же цепочками, а креды — `db.auth` (§11, «Доступ»). Права по умолчанию запрещают всё, поэтому арендатору
нужны правила, разрешающие работу с его классами. Для разработки без PostgreSQL — `up({ pglite: true })` (§11).

## 2. Устройство

**Три таблицы.** `entity` — текущее состояние: одна строка на живую сущность, включая строки системных классов
(`Class`, `Account`, `Resource`, `member`, `rule`). `log` — журнал: полный снимок каждой версии с автором,
временем, видом операции и хэшем. `secret` — креды и сессии; приложение не видит в ней ни одной строки, с ней
работают только функции входа. Классы — тоже сущности: описание класса лежит в строке `Class`, наследование
и скомпилированную проверку данных база хранит в той же строке.

**Две роли.** `letopis_owner` владеет схемой, таблицами и функциями; `letopis_app` — роль приложения, его
LOGIN-роль состоит только в ней. Всё, что выполняет приложение, — и библиотека, и сырой SQL, — проходит через
триггеры и RLS. Обходит их только код от имени владельца: функции владельца (`security definer`, фиксированный
`search_path`) и загрузчик на администраторском подключении. `connect()` отказывает роли, которая обходит RLS
(суперпользователь, `BYPASSRLS`, член `letopis_owner`), если не указано `allowBypassRls: true`.

**Триггеры.** На вставке триггер вычисляет id (v5 от арендатора, класса и значений ключа, у класса без ключа —
от случайной части), подставляет умолчания, проверяет данные по JSON Schema класса (скомпилированной в
jsonpath), концы и их цели, заполняет служебные колонки и пишет версию в журнал. Правка сливает патч внутри
оператора (`merge`, `inc`), удаление после оператора применяет `restrict`, `cascade` и `unset` и пишет
надгробия. Хэш версии — генерируемая колонка: sha256 от хэша прошлой версии и снимка строки.

**RLS и права.** Политики RLS изолируют арендаторов и применяют правила ACL: в начале запроса база один раз
строит план прав актора (`acl_plan()`), а на строку остаётся дешёвая проверка `acl_ok`. Контекст запроса —
настройки транзакции `letopis.token`, `letopis.account` (имперсонация) и `letopis.reason`; сессию база ищет
по sha256 токена.

**Чтение.** Под RLS индексы по `data` и обратным ссылкам недоступны политике напрямую, поэтому id для шагов
цепочки находят функции владельца `find_ids()`, `find_hop()` и `find_deep()` — с теми же условиями арендатора
и прав, что у политики, — а сами строки читаются по первичному ключу под RLS. Срез `asOf` строится по журналу.

**Сигналы.** Запись сообщает об изменённых классах через `NOTIFY`: сырой SQL — из триггера вместе с
фиксацией, транзакции библиотеки — отложенно, нотификатор процесса раз в 100 мс (`notifyIntervalMs`).
В сигнале только имя класса или начало хэша токена погашенной сессии. По сигналам перечитывается реестр
классов, сбрасывается кэш результатов и будится подписка.

## 3. Имена

### Модели и подключение

```ts
import { hub, link, one, many } from 'letopis/model'
const Org = hub('Org', { fields: { name: z.string() }, key: ['name'], meta: { title: 'Организация', icon: 'mdi:domain' } })
const Staff = hub('Staff', { ends: { Org }, fields: { name: z.string() }, key: ['Org', 'name'], alias: 'Мастер' })
const booking = link('booking', { ends: { Staff: one(Staff), Customer: one(Customer).optional().onDelete('unset') },
  fields: { start: z.iso.datetime() }, key: ['Staff', 'start'], history: { all: '1 day', daily: '3 months' } })
await syncModels(db, [Org, Staff, booking])                 // сухой прогон: created, updated, unchanged, lost
await syncModels(db, [Org, Staff, booking], { apply: true })
const db = await connect({ dsn, schema: 'v2.salon', token, models: [Org, Staff, booking] })
```

- `hub` — объект, `link` — связь со своими данными; описание: `fields` (Zod; короткая форма — поля вторым
  аргументом), `ends` (`one(X)`, `one(A, B)` — союз, `many(X, { min, max })`, `.optional()`, `.onDelete()`),
  `key`, `extends`, `abstract`, `alias`, `history` (`false` или политика хранения), `ownerDefault`, `cache: { ttl }`,
  `meta`. Потомок заменяет поле предка целиком, как в 0.21. В ключ входят только обязательные строковые поля
  и обязательные одиночные концы; класс без ключа получает id от случайной части.
- В базу уходит нормализованная JSON Schema (`z.toJSONSchema`); `refine`, `superRefine` и `transform` база не
  исполняет — `syncModels` возвращает их в `lost`. Ужесточение описания, которому мешают строки, —
  `tightening_conflict` со списком строк. CLI: `letopis sync <модуль> [--apply]`, `letopis types` — типы по базе.
- `connect({ dsn | sql, schema, token | apiKey, allowBypassRls, max, models, listen, cache, maintain,
  notifyIntervalMs, onQuery, slowMs, refreshSession })`. `models` — только для типов шагов, строк и фильтров;
  описания классов библиотека берёт из базы и перечитывает по сигналу (`db.refresh()` — вручную).
- Корень `db`: `registry` (`resolve(класс)`, в том числе `.meta`), `idOf(класс, ключ)`, `` sql`select …` `` — сырой SQL под
  сессией и RLS, `transaction(fn)`, `entity(строка | цепочка)`, `describe()`, `close()`.

### Чтение

```ts
const db = await connect({ dsn, schema: 'v2.salon', token, models: BOOKING })   // models — только для типов
await db.Org(org).Staff({ specialization: 'барбер' }).skill().Service().rows()  // хаб → хаб → связь → хаб
await db.Folder(f).Parent().rows()                 // шаг-роль: родительская папка
await db.Person(p).booking().count()               // базовый класс: записи, где p — мастер или клиент
await db.Staff(v).booking().Customer().booking().Item().paths()  // повтор связи — возврат к её узлу
await db.Folder(root).Folder().deep().rows()       // дети любой глубины, $depth
await db.Service(s).asOf('2026-10-07T10:00:00Z').first()        // срез по журналу
await db.Service().withDeleted().rows()            // с удалёнными ($deleted)
await db.Service().sort('data.duration', 'desc').after(cursorOf(last, 'data.duration')).limit(20).rows()
```

- Фильтр шага: id, список id, строка ответа, `or(…)`, объект полей любой глубины с операторами (`gt`, `between`,
  `inList`, `like`, `has`, `exists`, `not`, …) и роли концов: `{ Customer: id }`, `{ Customer: null }`.
- Модификаторы: `limit`, `offset`, `sort('at' | 'rev' | 'id' | 'data.<путь>', dir)`, `after(cursor)`, `asOf`,
  `withDeleted`, `deep(max)`, `exact`, `alias`, `tags`, `owner`, `entity(цепочка | строка)`.
- Терминалы: `rows`, `first`, `ids`, `count` (сущности; `{ paths: true }` — пути), `paths`, `versions`, `sum`, `avg`,
  `min`, `max`, `countBy`. Строка ответа: `id`, `class`, `rev`, `tenant`, `owner`, `links`, `data`, `tags`, `at`,
  `author`, `op` и, если есть, `agent`, `reason`, `moved`, `$deleted`, `$depth`.
- Переход: шаг-роль идёт своим концом; иначе — концами всех классов обоих семейств: в своём семействе — к детям,
  хаб → связь — назад, связь → хаб и хаб → хаб — вперёд. Под RLS id находят функции владельца `find_ids()`,
  `find_hop()`, `find_deep()` (индексы GIN), строки читаются по первичному ключу.

### Запись, транзакции, батч, загрузчик

```ts
await db.Org(org).Staff().create({ name: 'Вася', phone: '+7 900' }).rows()     // концы из пути: { Org }
await db.Staff(s).booking().create({ start_datetime, end_datetime })
  .Customer.set(c).Item.set(svc).Location.set(loc).Schedule.set(sch).rows()    // слоты концов
await db.Customer(c).booking({ notes: 'x' }).update({ notes: 'y' }).rows()     // слияние патча в базе
await db.Wallet(w).update({ balance: inc(-300) }).first()                       // приращение, без чтения
await db.Wallet(w).update({ balance: 700 }, { rev: 3 }).first()                 // строгий режим: conflict
await db.Service().upsert({ Org: org, name: 'Стрижка', duration: 45 } as never).first()  // $upsert
await db.Service(s).delete().rows()                // превью: $action delete | unset | restrict
await db.Service(s).delete({ confirm: true }).rows()                            // удалённое: $deleted
const tr = await db.begin()                        // явная транзакция read committed
await tr.Wallet(w).forUpdate().first()             // чтение с блокировкой
await tr.commit()
const b = db.batch('импорт'); b.Service().create({ … }); await b.run()          // одна транзакция
await adm.load({ Org: orgs, Staff: staff })        // загрузчик: администраторское подключение
```

- Глаголы — звенья плана: `create`, `update(patch, { rev })`, `upsert`, `delete({ confirm })`, `anonymize(поля)`,
  `reclass(класс, данные)`. Терминал исполняет весь план одной транзакцией; продолжение после глагола идёт от его
  результата (create и upsert — по строке, остальные — от всех строк), глагол сразу после глагола пишет в те же
  сущности; ошибка любого сегмента откатывает план. Модификаторы до глагола (`limit`, `sort`) сужают его цели.
- `create` только создаёт: занятый ключ — `exists` с id (вычисляет `idOf`); замена целиком — `upsert` (класс с ключом,
  иначе `no_key`); `update` никогда не создаёт; `data.id` — цель `update`, если у шага нет фильтра.
- Концы создаваемой строки — из пути (шаг, на который она ссылается) и слотов `.Роль.set/unset/add/remove`.
  Из нескольких подходящих ролей — без занятых слотами, затем роль с именем класса шага, иначе `invalid_query`.
- `inc(n, { start })` — маркер, который не получить из JSON; база прибавляет величину функцией `inc` внутри оператора.
  Поля нет — ошибка (или `start`); маркер в create, upsert, загрузчике и массиве — `invalid_data` до отправки.
- Если `update`, `delete` или `anonymize` затронули меньше строк, чем шаг нашёл, план откатывается: невидимые —
  `target_not_found`, видимые с другим `rev` в строгом режиме — `conflict`, остальные — `acl_denied`. `{ rev }` —
  только при одной цели (`rev_ambiguous`).
- `db.begin()`: ошибка любого запроса ломает транзакцию — каждый следующий вызов и `commit()` бросают исходную
  ошибку, `rollback()` проходит; `lock(...ключи)` — advisory до конца транзакции; 40P01 — с подсказкой повторить
  весь блок; обрыв связи во время `COMMIT` — `commit_unknown` (и в операциях из пула), без повтора.
- `forUpdate()` — только в `db.begin()` (`tx_required`), с `rows`, `first`, `ids` (`lock_unsupported`): блокировка
  `for no key update` в порядке id; строка, переставшая подходить под условия шага, в ответ не попадает.
- Батч: подряд простые `create`/`upsert` класса с ключом — одна многострочная вставка (повтор id в upsert режет
  группу), `create` класса без ключа — конвейер однострочных; терминал на плане из очереди — `invalid_query`.
- `db.as(аккаунт, { owner })` — тот же пул с `letopis.account` (имперсонацию проверяет база — этап 5) и владельцем
  новых строк.
- Загрузчик `db.load(вход, { duplicates, existing, commitEvery, withHistory, verify, class, tenant })` и
  `letopis load <файлы NDJSON…>`: только администраторское подключение (`allowBypassRls` и право стать владельцем,
  иначе `admin_required`); проверки в коде валидатором на TypeScript, `COPY` от роли владельца, один запрос по целям
  вне загрузки с `for key share`; строка — поля и роли на верхнем уровне, `$class`, `$ext`; ссылка — id,
  `{ $key: […] }` или `{ $ext }` (полиморфная — с `$class`). Ошибка — код первой проблемы и `detail.rows`
  (номер строки, код, нарушения). Режима доверия нет (решение 2 точки А).

### Рецепт: кошелёк (баланс без потерь)

Модель (как в наборе `balance`): хаб `Wallet` с ключом `[number]` и полем `balance` — целое число мелких единиц
с `minimum: 0` и умолчанием 0; связь `Movement` с концом `Wallet` (`onDelete: 'restrict'`), ключом `[Wallet, opId]`
и полями `opId`, `kind` (`topup` | `debit` | `adjust`), `amount`, `target`. Операции не правят и не удаляют —
это запрещают права; отмена — встречная операция с новым `opId`.

```ts
// операция: запись Movement и приращение баланса — один план, одна транзакция
async function operate(db, w, opId, kind, amount) {
  try {
    await db.Wallet(w).Movement().create({ opId, kind, amount })
      .Wallet().update({ balance: inc(kind === 'topup' ? amount : -amount) }).rows()
    return 'done'
  } catch (err) {
    if (err.code === 'exists') return same(db, w, opId, kind, amount)   // повтор: сверить отпечаток
    throw err                                                            // invalid_data — не хватает средств
  }
}
// отпечаток повтора: тот же ли это запрос
async function same(db, w, opId, kind, value) {
  const m = await db.Movement(db.idOf('Movement', { Wallet: w, opId })).first()
  if (!m || m.data.kind !== kind || (kind === 'adjust' ? m.data.target : m.data.amount) !== value)
    throw new Error(`ключ операции ${opId} уже использован другим запросом`)
  return 'repeat'
}
// корректировка «баланс = X»: операция adjust на разницу, итог — под { rev }
async function adjust(db, w, opId, target) {
  for (;;) {
    if (await db.Movement(db.idOf('Movement', { Wallet: w, opId })).first()) return same(db, w, opId, 'adjust', target)
    const cur = await db.Wallet(w).first()
    try {
      await db.Wallet(w).Movement().create({ opId, kind: 'adjust', amount: target - cur.data.balance, target })
        .Wallet().update({ balance: target }, { rev: cur.rev }).rows()
      return 'done'
    } catch (err) {
      if (err.code === 'conflict') continue                              // кошелёк изменился — перечитать
      if (err.code === 'exists') return same(db, w, opId, 'adjust', target)
      throw err
    }
  }
}
```

- Ключ `[Wallet, opId]` делает операцию идемпотентной: повтор после потери ответа (в том числе после
  `commit_unknown`) получает `exists`, и рецепт сверяет отпечаток. Неудачная операция ключ не расходует — план
  откатился целиком.
- `inc` прибавляет внутри оператора над заблокированной строкой, поэтому параллельные списания не теряются,
  а правило `minimum: 0` отклоняет списание сверх баланса (`invalid_data`) без чтения и блокировок в приложении.
- Обычный `update({ balance: 700 })` записывает значение, а не прибавляет: итог, вычисленный из прочитанного,
  без `{ rev }` или `forUpdate()` теряет параллельные списания, и advisory `lock()` не спасает, если его берут
  не все писатели. `upsert` заменяет объект целиком и затирает приращения — для денег он не годится.
- Для горячего кошелька корректировку можно делать в `db.begin()`: `tr.Wallet(w).forUpdate().first()`, затем тот же
  план без `{ rev }` и `commit()`. Для одного кошелька приложение выбирает один путь: под `{ rev }` и под
  `forUpdate()` кошелёк и ключ операции блокируются в разном порядке, и смешение даёт `40P01`. Внутри такого блока
  не стоит ждать внешних вызовов: кошелёк ждут все писатели (`lock_timeout`, `idle_in_transaction_session_timeout`).
- Перевод — две операции в одной `db.begin()`, кошельки — в порядке id: тогда взаимных блокировок нет.

### Доступ

```ts
const svc = await connect({ dsn, schema: 'v2.salon', apiKey: SERVICE_KEY })      // сервис: ключ → сессия
const r = await svc.auth.verifyPassword({ identifier: 'anna@salon.ru', password })  // { account, token } | null
const user = await svc.as(r.account, { tenant: org })     // имперсонация: база проверяет право auth.impersonate
await user.booking().create({ start }).rows()             // author — пользователь, agent — сервис
await user.acl.check('booking.create')                    // { allow, rule, code, message }
await user.acl.checkData('booking', 'READ')               // { allow, filter }
const tok = await svc.auth.sessionFor(r.account, { ttl: 600 })   // короткая сессия для другого процесса
```

- Права включены всегда и по умолчанию запрещают. Правила — строки `Resource` (группа `ACCOUNT` по категориям
  аккаунта или ролям членства, эндпоинт `API`, объект строк `READ`, `WRITE`, `DELETE` — маска класса с предками
  и условие на колонки `id`, `owner`, `tenant`, `tags`, `data`, `links`, значения `$actor` и `$tenant`) и `rule`
  (группа → объект, `allow` | `deny`, вес). Решение — ровно одно правило: наибольший вес, при равном запрет
  сильнее, из равных — объект с меньшим alias. Вес правила арендатора — не больше 999: правила System с весом от
  1000 — административный слой, который арендатор не перевесит. Правила арендатора действуют на его строки, правила System — везде;
  группа по ролям совпадает только в правилах того арендатора, где у пользователя роль.
- Строки видят и правят только по плану прав (политики RLS) — и библиотека, и сырой SQL; без права строка не
  видна, правка — пусто или `acl_denied`, новые значения вне условия — `acl_denied`. Каскад удаления требует
  права `DELETE` на каждую удаляемую строку, снятие конца — `WRITE`; цель ссылки должна быть видна.
- Аккаунты лежат в System, их категории правит только системный администратор (член System с ролью `admin`).
  Права `auth.*` (имперсонация, выпуск сессий, креды) и `letopis.*` (`verify`, `reset`, `maintain`) решают
  только правила System.
- `db.auth`: `setPassword`, `verifyPassword`, `issueApiKey`, `verifyApiKey`, `issueKeySecret`,
  `verifyKeySecret`, `enrollTotp`, `verifyTotp`, `totpEnabled`, `issueOtp`, `verifyOtp`, `link`, `lookup`,
  `credentials`, `revokeCredential`, `setFlags`, `sessionFor`, `refresh`, `revoke`, `revokeAll`, `switch`,
  `tenants`. Свои креды аккаунт привязывает сам только после недавнего интерактивного входа (10 минут; ключ API
  и сессия от сервиса не в счёт, при включённом TOTP — с пройденным TOTP) и не подтверждает их сам; креды
  System, сервисов и системных администраторов меняет только сам аккаунт или системный администратор.
  Вход по одноразовому коду и проверку TOTP вызывает сервис (права `auth.otp`, `auth.totp`): счётчики попыток
  транзакционные, частоту ограничивает сервис. Продление сессии — не дольше срока, выданного при входе.
- Пропуск прав: библиотека один раз берёт у базы подписанный план прав актора (`acl_token()`) и передаёт его в
  каждой транзакции (`letopis.acl`) — проверка прав стоит десятки микросекунд вместо сотен. Устаревший пропуск
  база не принимает и считает план сама.
- Загрузчик от имени пользователя: `db.load(rows, { as: account, tenant })` — право `WRITE` на класс, условия
  ACL на строки, видимость целей, владелец по `ownerDefault`, автор — пользователь.

### История, хранение, события, эксплуатация

```ts
await db.Note(id).withDeleted().versions({ follow: true })   // все версии и через смену id (reclass, rekey)
await db.Note(id).restore().rows()                           // удалённый — последним снимком, id прежний
await db.Note(id).purge().rows()                             // превью: $versions; purge({ confirm: true }) — стереть
await db.trimHistory('Note', '2026-01-01')                   // обрезка истории класса, id или строк до момента
await db.Master(id).rekey({ name: 'Василий' }).rows()        // новый ключ — новый id, ссылки переведены
await db.rekeyClass('Room', ['floor', 'code'])               // новый ключ класса для всех строк семейства
for await (const ev of db.watch({ from: cursor, classes: ['booking'] })) save(ev.cursor)
await db.Price().cache({ ttl: 300 }).rows()                  // кэш результатов; класс с cache в модели — без .cache()
await admin.verify({ data: true })                           // цепочки хэшей, якорь; данные, концы, арендаторы, id
await admin.maintain()                                       // сессии, коды, прореживание журнала, очередь сигналов
await admin.reset({ level: 'tenant', confirm: 'v2.salon', tenant })   // sessions | tenant | all
const r = await up({ dsn, schema: 'salon', seeds: ['booking'], history: { all: '1 day', daily: '1 month' } })
```

- У id, у которого в журнале есть запись, номер версии 1 всегда занят: `purge` и обрезка истории кладут на его
  место свою запись (`purge` — число стёртых версий и последний хэш; `trim` — время прежней версии 1). Эти записи
  видны в `versions()`, но не в срезах `asOf` и не в `withDeleted`. `purge` — только для удалённых
  (`not_deleted`), история системных классов не стирается и не обрезается.
- Политика хранения — `history: { all, daily, weekly, monthly, yearly, tz }` у класса (наследуется) или
  `up({ history })` для всех классов без своей: все версии моложе `all`, дальше — последняя версия периода
  (день, неделя с понедельника, месяц, год в поясе `tz`) текущего яруса или любого более крупного; ярус —
  календарно. Не удаляются версия 1, текущая и версии `create`, `delete`, `reclass`, `rekey`, `restore`,
  `purge`, `reset`, `trim`; история удалённого объекта, надгробие которого старше последнего яруса со сроком,
  стирается целиком. Прореживает `maintain()` пачками по 10 000 версий (каждая — своя транзакция).
- `maintain()` — системный администратор, роль с правом `letopis.maintain` или администраторское подключение;
  из нескольких процессов работает один (advisory-блокировка), `connect({ maintain: '1h' })` — по расписанию.
- Подписка `db.watch({ from: 'now' | 'start' | курсор, classes, pollMs })` — асинхронный итератор событий
  `{ cursor, row, id, class, op, rev, at }`: события ниже горизонта завершённых транзакций — без потерь и повторов,
  под RLS журнала; долгая пишущая транзакция задерживает поток (`sub.lag()`); курсор старше яруса `all` —
  `cursor_expired`. Без LISTEN (`connect({ listen: false })`) — опрос.
- Кэш результатов: ключ — запрос, параметры, сессия, актор и арендатор; свои записи сбрасывают ответы сразу
  после фиксации (с классами каскада), чужие — по сигналу базы; права, схема, `db.sql`-запись, погашенная сессия
  и переподключение слушателя — весь кэш или ответы сессии; срок по умолчанию 60 с; в `db.begin()` не работает;
  без LISTEN — выключен (`cache: { ttlOnly: true }` — по сроку). `db.cache.clear()`, `db.cache.stats()`.
- `reset`: флаг `up({ allowReset: true })` (по умолчанию выключен — `reset_disabled` даже для System), право
  `letopis.reset`, подтверждение именем схемы (`confirm_mismatch`); первая запись журнала после сброса — `reset`;
  `all` возвращает новый ключ сервиса.
- `db.verify({ data })` и `letopis verify [--data]` (код 1 при находках): законные разрывы — после записи `trim`
  (стык по её хэшу) и прореживание (пропуск после версии старше яруса `all` класса с политикой); якорь — хэш всех
  голов цепочек, его стоит хранить вне базы.
- `db.auth.purgeAccount(аккаунт)` — удаление аккаунта: системный администратор или владелец его арендатора;
  себя и последнего владельца арендатора нельзя; данные арендатора стираются, владение строками в чужих
  арендаторах переходит им.
- `up()`: ждёт и создаёт базу, проверяет PostgreSQL 18+ и UTF8, `fresh`, `upgrade` (миграции `sql/migrate/`),
  свои сиды (имена или пути), свой ключ сервиса, `ANALYZE` только без статистики; `up({ pglite: true })` —
  база для разработки без PostgreSQL (одно соединение: `connect({ dsn: r.pglite.dsn, listen: false, max: 1 })`).
  `connect()` предупреждает, если ревизия схемы отстала. `db.describe()` и `describeText()` (`letopis describe
  --format text` — llms.txt) — описание модели с метаданными.

### Импорт из 0.21

```sh
letopis import --from postgres://…/letopis --from-schema v1.salon --dsn postgres://…/app --schema v2.salon   --tenant salon [--keyless booking] [--rename link=link_] [--update] [--commit-every 100000]
```

- Схема 1.0 ставится заранее (`up()`); подключения — администраторские. Читаются таблицы 0.21 (`Schema`,
  `Entity`, `Account`, `Credential`, `Resource`, `Rule`) любой базы — PostgreSQL 17 с TimescaleDB или дамп
  обычных таблиц; пишут загрузчик (режим истории, `existing: 'skip'`, агент `letopis import`) и функции владельца.
- Классы — строки `Class` арендатора System: правила fastest-validator → JSON Schema (`optional` пропускает
  `null`, `$$strict` → `additionalProperties: false`, `record` → `propertyNames`), концы — роли по имени класса
  цели, союз всех потомков класса — полиморфный конец; корни `Entity` и `link` опускаются; `description`,
  `appearance`, `order` → `meta`; имена методов 1.0 — `--rename` (по умолчанию имя + `_`).
- id: класс с ключом (правило v5 0.21) — v5 от ключа, без ключа — v5 от старого id; данные System — в
  арендатора `--tenant`; аккаунты — строки `Account`, креды — в `secret` как есть (scrypt, ключи), одноразовые
  коды не переносятся; ресурсы и правила — в System.
- До первой записи импорт останавливается, если два объекта 0.21 дают один id 1.0 (данные нарушают ключ —
  `--keyless <Класс>`), если ключ менялся между версиями или ссылается на отсутствующий объект; висячую ссылку
  живой строки — `target_not_found` с объектом 0.21. Повтор дописывает недостающее без дублей; `--update` —
  новые версии изменившихся объектов. Отчёт: объекты и версии по классам в 0.21 и в 1.0, `verify()`,
  непереведённые правила, классы без ключа, uuid в `data`, совпадающие со старыми id (их импорт не переписывает).
- Загрузчик: `$tags` — теги строки, `$owner` — владелец (аккаунт; не с `{ as }`); в режиме истории
  `existing: 'skip'` пропускает объект со всей историей (`'update'` — только без истории).

## 12. Ошибки

Текст ошибки — `letopis: <код>: <сообщение>`, код — в `err.code`. Коды базы (SQLSTATE класса `LT`, детали — JSON):

| Код | Когда |
|---|---|
| `no_session` | нет действующей сессии (запись, функции владельца) |
| `target_not_found` | цель не найдена — одинаково для несуществующей, чужой и невидимой |
| `invalid_data` | данные не проходят описание класса; `err.issues` — путь, ключевое слово, сообщение |
| `undeclared_end` | конец не объявлен в классе |
| `tenant_denied` | чужой арендатор или нет членства |
| `acl_denied` | отказ по правилам доступа |
| `id_mismatch`, `id_from_db` | id не равен v5 от ключа; id класса без ключа выдаёт база |
| `immutable_key` | ключевое поле, id, арендатор, владелец не меняются (смена ключа — `rekey`) |
| `invalid_class` | описание класса отклонено, класс не найден или абстрактный |
| `use_reclass`, `reclass_denied` | класс с ключом меняется `reclass()`; роли ссылающихся строк не принимают класс |
| `tightening_conflict` | ужесточению описания мешают строки |
| `isolation_level` | удаление, смена класса и ключа — только в `read committed` |
| `recreated_in_statement` | id удалён и создан заново одним оператором |
| `delete_restricted` | удалению мешают ссылающиеся строки (`onDelete: restrict`) |
| `cursor_expired` | курсор подписки старше яруса `all` политики хранения |
| `not_deleted` | `restore` и `purge` — только для удалённых |
| `reset_disabled` | сброс выключен в установке (`allowReset`) |
| `confirm_mismatch` | подтверждение сброса не совпадает с именем схемы |

Коды библиотеки: `exists` (объект уже существует, `detail.id`), `conflict` (`{ rev }` разошёлся), `rev_ambiguous`,
`tx_required`, `lock_unsupported`, `commit_unknown`, `tx_rolled_back`, `no_key`, `admin_required`,
`class_not_loadable`, `invalid_query`, `no_path` (между классами шагов нет перехода), `bypass_rls`, `removed` (снесённое API 0.21 с заменой). Полный машинный
каталог — `docs/api-contract.json`.

## 15. Ограничения

Здесь собрано то, что letopis 1.0 сознательно не делает или делает с оговорками, и где за поведением нужно следить.

**Платформа**

- Нужен PostgreSQL 18 или новее; обходных путей для 15–17 нет. AWS RDS, Google Cloud SQL, Azure Flexible Server
  и Neon поддерживают 18, а Supabase на октябрь 2026 года — только 15 и 17, поэтому там 1.0 не заработает.
- База — в кодировке UTF8 (`casefold()` и коллация `pg_unicode_fast`). Если новая основная версия PostgreSQL
  обновит таблицы Unicode, уникальный индекс идентификаторов кредов перестраивается командой `reindex`.
- PGlite — одно соединение: без параллельных писателей и LISTEN; не замена `postgres:18` для гонок и CI.
- Пул в режиме транзакций (PgBouncer): `LISTEN` недоступен — `connect({ listen: false })`, подписка опрашивает журнал,
  кэш результатов выключен; подготовленные операторы работают с PgBouncer 1.21, со старыми — пул postgres.js
  с `prepare: false` в `connect({ sql })`.
- символ NUL (` `) в строках данных невозможен: PostgreSQL не хранит его в `jsonb`; такие данные
  отклоняются ещё при разборе JSON (официальный набор JSON-Schema-Test-Suite, группы «nul characters», пропущены).

**Запись и целостность**

- Построчная запись дороже простой вставки: каждую строку проверяют триггеры (данные, концы, id, журнал, хэш, RLS).
  Построчный `create` медленнее 0.21 на 12–18 % (§14); для массовой записи есть загрузчик.
- Удаление, смена класса и смена ключа работают только в `read committed` (`isolation_level`); транзакции
  библиотеки всегда открываются на этом уровне.
- `COPY` в таблицы под RLS PostgreSQL не выполняет; массовая загрузка — только загрузчиком на администраторском
  подключении.
- Загрузчику база доверяет: данные, концы и id загруженных строк проверяет код библиотеки (валидатор на TypeScript),
  а не триггеры; база сверяет только цели вне загрузки, арендаторов и владельцев одним запросом в конце.
  Защита — загрузчик только у администратора, дифференциальные тесты валидатора против базы, `load({ verify: true })`
  и `db.verify({ data: true })`. Администраторское подключение держит отдельный процесс загрузки, а не
  веб-приложение: SQL-инъекция в нём получила бы права владельца.
- Владелец схемы и суперпользователь могут отключить триггеры и изменить что угодно. letopis это не предотвращает,
  а обнаруживает: `verify()` пересчитывает цепочки хэшей, `verify({ data: true })` перепроверяет строки, а якорь
  (хэш всех голов цепочек) стоит хранить вне базы.
- В базе проверяется подмножество JSON Schema: `refine`, `superRefine` и `transform` Zod работают только
  в библиотеке, описание с неизвестным ключевым словом база не примет; `pattern` — ограниченное подмножество
  регулярных выражений, общее для Zod, валидатора и базы. Вывод `z.toJSONSchema()` меняется между версиями Zod:
  в базе хранится уже нормализованная схема, а сухой прогон `syncModels` показывает разницу до применения.
- Ключ — единственный способ уникальности: id вычисляется из значений ключа без нормализации, поэтому одно
  значение в разной записи (email в разном регистре, время с миллисекундами и без) даёт разные id. Формат
  ключевого поля задаёт модель, и база его проверяет.
- Частая смена значения ключа (email, телефон) требует `rekey`. Изменчивые и персональные значения лучше выносить
  в отдельный хаб со связью: id из email подбирается перебором и остаётся в ссылках и журнале даже после
  `anonymize`, а отдельный хаб удаляется вместе со связью через `purge`.
- `create` занятого ключа отвечает `exists` с id, `upsert` без права на существующую строку — отказом `42501`:
  так раскрывается, что ключ занят, но только внутри своего арендатора — у других арендаторов те же ключи дают
  другие id.
- Смена класса и ключа переписывает все входящие ссылки (и рекурсивно — связи, в ключ которых входит этот конец),
  поэтому её цена пропорциональна числу ссылок. Ужесточение описания класса и `rekey` на время проверки или
  переноса приостанавливают запись в семейство.
- `rekeyClass` переносит строки одной транзакцией под исключительной блокировкой семейства, а не пачками:
  между пачками строки со старыми id нарушали бы правило «id — v5 от ключа».
- id v5 ложатся в индекс первичного ключа вразброс; на очень больших таблицах с интенсивной вставкой это заметнее,
  чем с последовательными id.
- Горячие цели ссылок (организация, на которую ссылается почти всё) копят блокировки `for key share` и MultiXact,
  как при обычных внешних ключах; это нужно мониторить. Операции одного кошелька идут друг за другом под
  блокировкой его строки (§11, «Рецепт: кошелёк»).
- Имя связи или класса не может совпасть с зарезервированным именем (§3).

**Доступ**

- Сервисный ключ — корень доверия: его компрометация позволяет действовать от имени любого пользователя, которого
  сервис видит по правилам ACL. Права ограничивают круг; ключ перевыпускается (`db.auth.issueApiKey`) и отзывается
  (`db.auth.revokeCredential`). Один пароль от базы без токена не даёт ничего.
- Пропуск прав открывает клиенту его собственный план (классы и условия правил, которые к нему применимы).
- Сырой SQL без пропуска прав платит за план прав на каждый запрос: 0,3–1,3 мс в зависимости от числа правил.
- Имена концов `User`, `Tenant` (членство), `Group`, `Object` (правило) заняты системными классами во всей схеме.
- Счётчики попыток OTP и TOTP откатываются вместе с транзакцией вызывающего: частоту попыток ограничивает сервис.
- Самостоятельная привязка занятого идентификатора отвечает `acl_denied` — пользователь с недавним входом так
  узнаёт, что идентификатор занят. Изменения прав во всех арендаторах упорядочены одной строкой счётчика.
- Число невидимых строк, мешающих удалению, и существование аккаунта по id (как цели ссылки) не скрываются.
- Метаданные классов (`meta`) видны всем, у кого есть сессия: строки `Class` читает любой. Секретам там не место.

**История, сигналы, кэш**

- Срез `asOf` восстанавливается из журнала; дёшево только текущее состояние. В прореженной части журнала срез
  показывает последнюю сохранённую версию до момента: его точность там равна периоду яруса — дню, неделе, месяцу
  или году. Импорт истории в класс с политикой прореживается сразу, и подписчик может не увидеть старые версии.
- Прореженная часть журнала не доказывает ни полноты истории, ни подлинности старых версий: подмену версии
  старше яруса `all` у класса с политикой `verify()` не отличит от прореживания.
- Журнал без партиций: прореживание удаляет версии пачками, файл таблицы сам не уменьшается (место занимают новые
  версии после autovacuum); вернуть место системе — `VACUUM FULL` или `pg_repack` в окно обслуживания.
- Сигналы раскрывают активность: слушать канал PostgreSQL разрешает любой роли, и по именам классов в сигналах
  видно, когда и в какие классы пишут (ни id, ни арендатора, ни данных в сигнале нет). Поддельный сигнал лишь
  сбросит кэш лишний раз.
- Очередь `NOTIFY` (8 ГБ) общая для кластера: зависший слушатель её переполняет, и тогда транзакции с `NOTIFY`
  падают при фиксации. Библиотека читает сигналы сразу, `maintain()` предупреждает о заполнении больше чем
  наполовину.
- Горизонт подписки общий для кластера: долгая пишущая транзакция задерживает события всех подписчиков
  (`sub.lag()`); длинные операции лучше вести пачками.
- Кэш результатов между процессами устаревает на время доставки сигнала (миллисекунды) и переподключения
  слушателя (десятки миллисекунд); срок `ttl` — предохранитель.
- Курсор подписки «с этого момента» несёт снимок момента подписки, пока не пройдёт его границу: такой
  курсор длиннее обычного.

**Импорт из 0.21**

- 1.0 — новая major-версия, а не продолжение 0.21: `count()`, `paths()`, `create`, роли, множественные концы
  и `reclass` ведут себя по-новому, данные переносятся импортом (`lib/MIGRATION.md`).
- Импорт: шаги (классы, аккаунты, креды, права, данные каждого арендатора) — отдельные транзакции, источник
  читается в память целиком; владелец строки, не найденный среди аккаунтов, становится арендатором; правила ACL
  0.21 переносятся в System и действуют во всех арендаторах; `onDelete` концов — `cascade`, как удаляла 0.21.
