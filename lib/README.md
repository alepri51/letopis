# letopis 1.0

**letopis** — библиотека для Node.js, хранилище версионированных сущностей на PostgreSQL 18. Каждое изменение
сохраняется версией в журнале. Поэтому у любого объекта есть история, состояние на любую дату и подписка на
изменения. Целостность данных, изоляцию арендаторов и права доступа проверяет сама база — триггерами и политиками
RLS. Правила одинаково действуют и для библиотеки, и для сырого SQL. Данные читают и пишут цепочками:
`db.Shop(shop).Product({ price: lt(1000) }).rows()`.

[English version](README.en.md) · [Шпаргалка для ИИ-агента](AGENT-CHEATSHEET.md) · [Переход с 0.21](MIGRATION.md) ·
[Изменения по версиям](CHANGELOG.md) · [llms.txt](llms.txt)

Что умеет letopis:

- **Модели на Zod** хранятся в базе как классы: хабы (объекты) и связи (отношения со своими данными) — [раздел 4](#4-модель-данных).
- **Запись цепочками**: `create`, `update` со слиянием, `upsert`, удаление с превью и каскадом, приращение `inc`
  для денег и счётчиков — [разделы 5](#5-запись), [7](#7-удаление-и-восстановление) и [8](#8-транзакции-батчи-и-деньги).
- **Чтение цепочками**: переходы по связям, фильтры, деревья, агрегаты, постраничный вывод — [раздел 6](#6-чтение).
- **История**: версии, срез на дату, восстановление удалённого, политика хранения, проверка цепочки хэшей —
  [раздел 11](#11-история-и-срезы-на-дату).
- **Арендаторы, вход и права** — в самой базе: пароли, ключи API, одноразовые коды, TOTP, сессии, имперсонация,
  правила доступа — [раздел 10](#10-пользователи-вход-и-права).
- **Подписка на изменения** по курсору без потерь и **кэш результатов** — [раздел 12](#12-подписка-на-изменения-и-кэш).
- **Массовая загрузка** миллионов строк и **импорт из 0.21** — [разделы 9](#9-массовая-загрузка) и [14](#14-переход-с-021).

Требования:

- PostgreSQL 18 или новее с расширением pgcrypto (оно входит в стандартную поставку), база в кодировке UTF8.
- Node.js 22 или новее; пакет — модуль ES.
- Рантайм-зависимость одна — `postgres`. Zod 4 — необязательная peer-зависимость: он нужен только подпути
  `letopis/model`, а `import { connect } from 'letopis'` работает и без него. Для разработки без PostgreSQL —
  необязательные `@electric-sql/pglite` и `@electric-sql/pglite-socket`.

## 1. Быстрый старт

Нужен PostgreSQL 18 и роль администратора: суперпользователь или роль с правом `CREATEROLE`. Установите пакет:

```sh
npm install letopis zod postgres    # postgres — для createTenant и своих SQL-запросов
```

Приложение подключается к базе отдельной ролью, которая состоит в `letopis_app`. Роль `letopis_app` создаёт установка.
Поэтому после первой установки один раз создайте роль приложения:

```sql
create role shop_app login password 'app-secret';
grant letopis_app to shop_app;
```

Пример ставит схему, заводит магазин с первым пользователем, описывает два класса и работает с ними:

<!-- run: quickstart -->
```ts
import { up, connect, syncModels, inc, gte } from 'letopis'
import { hub } from 'letopis/model'
import { z } from 'zod'

const ADMIN = 'postgres://postgres:secret@localhost:5432/shop'    // администратор: ставит схему
const APP = 'postgres://shop_app:app-secret@localhost:5432/shop'  // приложение: член letopis_app

// 1. Установка схемы v2.shop. tenant — первый арендатор (магазин) и его пользователь Анна.
const r = await up({ dsn: ADMIN, schema: 'shop',
  tenant: { name: 'Ромашка', user: { name: 'Анна', login: 'anna@shop.ru', password: 'Ромашка-2026!' } } })
// r.serviceKey — ключ сервиса приложения: выдаётся при первой установке, сохраните его

// 2. Сервис приложения входит по ключу, проверяет пароль Анны и работает от её имени в магазине.
const svc = await connect({ dsn: APP, schema: r.schema, apiKey: r.serviceKey! })
const login = await svc.auth.verifyPassword({ identifier: 'anna@shop.ru', password: 'Ромашка-2026!' })
const db = await svc.as(login!.account, { tenant: r.tenant!.tenant })

// 3. Модель: магазин и товар. syncModels записывает описания классов в базу.
const Shop = hub('Shop', { name: z.string() }, { key: ['name'] })
const Product = hub('Product', { sku: z.string(), title: z.string(), price: z.number().int().min(0) },
  { ends: { Shop }, key: ['Shop', 'sku'] })
await syncModels(db, [Shop, Product], { apply: true })

// 4. Запись и чтение цепочками.
const [shop] = await db.Shop().create({ name: 'Ромашка' }).rows()
const [kettle] = await db.Shop(shop).Product().create({ sku: 'K-1', title: 'Чайник', price: 2500 }).rows()
await db.Product(kettle).update({ price: inc(-500) }).rows()      // скидка: база вычитает внутри оператора
const expensive = await db.Shop(shop).Product({ price: gte(1000) }).rows()
const history = await db.Product(kettle).versions()               // две версии: создание и правка

await svc.close()
```

Что здесь произошло:

- `up()` поставил в базу схему `v2.shop`: три таблицы, триггеры, политики RLS, функции и системный сид. Опция
  `tenant` завела арендатора «Ромашка» с правилом «аутентифицированным можно всё» и пользователя Анну с ролью
  `owner` в нём.
- `connect({ apiKey })` обменял ключ сервиса на сессию. `verifyPassword` вернул `{ account, token }` (или `null`,
  если пароль неверный). `svc.as(account, { tenant })` — тот же пул соединений, но от имени Анны в магазине;
  право сервиса на это проверяет база.
- `hub('Product', поля, опции)` описал класс-объект. `ends: { Shop }` — обязательная ссылка на магазин.
  `key: ['Shop', 'sku']` — ключ: id товара вычисляется из магазина и артикула, а второй товар с тем же ключом база
  не примет.
- `db.Shop(shop).Product().create(…)` создал товар, и ссылку на магазин взял из пути цепочки. `inc(-500)`
  уменьшил цену внутри оператора `UPDATE`, без предварительного чтения. `versions()` прочитал историю из журнала.

Повторный вызов `up()` безопасен: он повторно накатывает ту же ревизию и данные не трогает, а ключ сервиса снова не
выдаёт, пока в установке есть действующий ключ API. Дальше раздел 2 объясняет устройство, а разделы 3–13 разбирают задачи по порядку.

## 2. Как устроен letopis

### Основные понятия

| Понятие | Что это |
|---|---|
| установка | схема PostgreSQL `v2.<имя>` с таблицами и функциями letopis; в одной базе их может быть несколько |
| класс | тип данных: имя, поля (JSON Schema), концы и ключ. Описание класса — тоже строка в базе (класс `Class`) |
| хаб | класс-объект: магазин, товар, клиент |
| связь | класс-отношение между объектами со своими данными: строка заказа, навык мастера |
| конец (роль) | ссылка строки на другую строку. У конца есть имя — роль: `Shop`, `Parent`. Концы лежат в `row.links`, поля — в `row.data` |
| ключ | поля и концы, которые определяют объект внутри класса и арендатора. Из них вычисляется id, поэтому уникальность — это ключ |
| id | UUID версии 5: хэш от арендатора, класса и значений ключа; у класса без ключа — от случайной части |
| аккаунт | пользователь, сервис или организация — строка класса `Account` |
| арендатор | аккаунт, в чьих данных идёт работа. Данные разных арендаторов изолированы |
| членство | связь `member` «пользователь — арендатор» с ролями; даёт работать в чужом арендаторе |
| сессия | токен, по которому база узнаёт аккаунт и арендатора. Сервис получает её по ключу API, пользователь — входом |
| версия, журнал | каждое изменение строки — версия в журнале `log` с автором, временем и хэшем |
| надгробие | версия «удалено» с последним снимком объекта |
| цепочка | запрос вида `db.Shop(shop).Product().rows()`: шаги, модификаторы, глаголы записи и терминал |
| терминал | метод, который исполняет цепочку: `rows`, `first`, `ids`, `count`, `paths`, агрегаты |

### Что хранится в базе

Таблиц три. `entity` — текущее состояние: одна строка на каждую живую сущность, включая строки системных классов
(`Class`, `Account`, `Resource`, `member`, `rule`). `log` — журнал: полный снимок каждой версии с автором,
временем, видом операции и хэшем. `secret` — креды и сессии: приложение не видит в ней ни одной строки, с ней
работают только функции входа.

Классы — тоже сущности. Описание класса лежит в строке `Class`; там же база хранит развёрнутое описание с учётом
предков и скомпилированную проверку данных. Хэш версии — генерируемая колонка: sha256 от хэша прошлой версии и
снимка строки. Поэтому подмену версии выдаёт следующая версия, а у последней — якорь вне базы ([раздел 11](#11-история-и-срезы-на-дату)).

### Кто проверяет данные

Ролей две. `letopis_owner` владеет схемой, таблицами и функциями. `letopis_app` — роль приложения: его
LOGIN-роль состоит только в ней. Всё, что выполняет приложение, — и библиотека, и сырой SQL, — проходит через
триггеры и RLS.

- **Триггеры.** При вставке триггер вычисляет id, подставляет умолчания и проверяет данные по JSON Schema класса
  (схема скомпилирована в jsonpath). Он проверяет концы и их цели, заполняет служебные колонки и пишет версию в
  журнал. Правка сливает патч внутри оператора (`merge`, `inc`). После удаления триггер применяет правила
  `restrict`, `cascade` и `unset` и пишет надгробия.
- **RLS и права.** Политики изолируют арендаторов и применяют правила доступа. В начале запроса база один раз
  строит план прав актора (`acl_plan()`), а на каждую строку остаётся дешёвая проверка `acl_ok`.
- **Контекст запроса** — настройки транзакции: `letopis.token` (сессия), `letopis.tenant` и `letopis.account`
  (арендатор и имперсонация), `letopis.reason` (причина изменения) и `letopis.acl` (пропуск прав, см.
  [раздел 10](#10-пользователи-вход-и-права)). Сессию база ищет по sha256 токена, поэтому без настоящего токена
  настройки ничего не дают.
- **Обход проверок** есть только у кода от имени владельца: у функций владельца (`security definer` с
  фиксированным `search_path`) и у загрузчика на администраторском подключении. `connect()` отказывает роли,
  которая обходит RLS (суперпользователь, `BYPASSRLS`, член `letopis_owner`), если не указано
  `allowBypassRls: true`.

### Как идёт чтение

Под RLS индексы по `data` и по обратным ссылкам политике напрямую недоступны. Поэтому id для шагов цепочки
находят функции владельца `find_ids()`, `find_hop()` и `find_deep()`. Они применяют те же условия арендатора и
прав, что и политика. Сами строки затем читаются по первичному ключу под RLS. Срез на дату строится по журналу.

### Сигналы

Запись сообщает об изменённых классах через `NOTIFY`. Сырой SQL шлёт сигнал из триггера, и PostgreSQL доставляет
его при фиксации. Транзакции библиотеки шлют сигналы отложенно: нотификатор процесса отправляет их раз в 100 мс
(`notifyIntervalMs`). В сигнале только имя класса или начало хэша токена погашенной сессии — ни id, ни данных.
По сигналам перечитывается реестр классов, сбрасывается кэш результатов и будится подписка.

## 3. Установка и подключение

### Установка: `up()`

`up()` ждёт базу и создаёт её, если её нет. Он проверяет PostgreSQL 18 и кодировку UTF8, ставит роли
`letopis_owner` и `letopis_app`, расширение pgcrypto и схему `v2.<имя>` со всеми функциями и системным сидом.
При первой установке он выдаёт ключ сервиса. Вызывайте его от администраторской роли.

| Опция | Что делает |
|---|---|
| `dsn` или `sql` | администраторская строка подключения или готовый пул postgres.js |
| `schema` | имя установки: `'shop'` даёт схему `v2.shop`; можно сразу `'v2.shop'` |
| `tenant` | первый арендатор и его пользователь (см. ниже) |
| `seeds` | сиды после ядра: `'booking'` — демо-домен салона, или пути к своим файлам `.sql` |
| `history` | политика хранения истории для классов без своей ([раздел 11](#11-история-и-срезы-на-дату)) |
| `serviceKey` | свой ключ сервиса вместо случайного: `lts_` и 32–128 шестнадцатеричных знаков |
| `allowReset` | разрешить `db.reset()` ([раздел 13](#13-эксплуатация)); по умолчанию выключено |
| `fresh` | удалить схему и поставить заново — **данные схемы теряются** |
| `upgrade` | обновить схему старой ревизии: миграции и повторный накат |
| `pglite` | база для разработки без PostgreSQL (см. ниже) |
| `quiet`, `waitTimeoutMs` | без сообщений в консоль; сколько ждать базу (по умолчанию 60 000 мс) |
| `owner`, `app` | имена ролей владельца и приложения (по умолчанию `letopis_owner`, `letopis_app`) |

Результат: `schema` (полное имя), `serviceKey` (при первой установке и при накате, когда в установке не осталось ни
одного действующего ключа API; иначе `null`), `created`,
`upgraded`, `revision`, `migrations`, `analyzed`, `owner`, `app`, а также `tenant` и `pglite`, если их просили.

<!-- run: guide -->
```ts
import { up, connect } from 'letopis'

const ADMIN = 'postgres://postgres:secret@localhost:5432/shop'
const APP = 'postgres://shop_app:app-secret@localhost:5432/shop'

const r = await up({ dsn: ADMIN, schema: 'shop',
  tenant: { name: 'Ромашка', user: { name: 'Анна', login: 'anna@shop.ru', password: 'Ромашка-2026!' } } })
const SHOP = r.tenant!.tenant      // арендатор — магазин «Ромашка»
const ANNA = r.tenant!.user!       // его первый пользователь
```

### Роль приложения

Приложение работает от LOGIN-роли, которая состоит только в `letopis_app`:
`create role shop_app login password '…'; grant letopis_app to shop_app;`. Тогда на него действуют RLS и
триггеры, как и на любой сырой SQL от этой роли. Роль, которая обходит RLS, `connect()` отклоняет с ошибкой
`bypass_rls`. Администраторское подключение (`allowBypassRls: true`) нужно только загрузчику, проверке и
обслуживанию; держите его в отдельном процессе, а не в веб-приложении.

### Первый арендатор и пользователь

Права в letopis включены всегда и по умолчанию запрещают всё. Поэтому новому арендатору нужны правила. Опция
`up({ tenant })` и функция `createTenant(sql, schema, opts)` делают это одной транзакцией:

- арендатор — аккаунт в System с id из имени («tenant:<имя>»);
- правило «аутентифицированным можно всё» в этом арендаторе (`grantAll`, по умолчанию да, вес 10);
- пользователь (id из логина) с членством в арендаторе с ролями `user.roles` (по умолчанию `['owner']`), паролем и
  сессией в арендаторе.

Повтор с теми же именем и логином ничего не дублирует и пароль не меняет, только выдаёт новую сессию. Логин входит в
id как есть: `Anna@shop.ru` и `anna@shop.ru` дали бы два аккаунта, и у второго не было бы пароля, — пишите логин в
одном регистре. Поле `created` в ответе — создан ли арендатор этим вызовом: для существующего арендатора с новым
пользователем оно `false`. Роли задаёт `user.roles` — непустой список имён (не масок), иначе `invalid_data`. Роли
уже существующего членства повтор не меняет: их меняет правка членства ([«Выдать право»](#выдать-право)).
Удалённое повтор не воскрешает: если арендатор, аккаунт пользователя или членство удалены (строки нет, а история в
журнале есть), `createTenant` отвечает `invalid_data` и не записывает ничего. Текст ошибки называет удалённое и
советует вернуть его `restore()`: аккаунт — `db.Account(id).restore()` от имени системного администратора,
членство — `db.member(id).restore()` в этом арендаторе; другой выход — другое имя или логин. Сессия
из `createTenant` — без способа входа, поэтому свой пароль по ней не сменить: для этого пользователь входит по
паролю. `createTenant` нужен администраторский пул postgres.js:

<!-- run: guide -->
```ts
import postgres from 'postgres'
import { createTenant } from 'letopis'

const pg = postgres(ADMIN)
const lutik = await createTenant(pg, r.schema, {
  name: 'Лютик', user: { name: 'Борис', login: 'boris@lutik.ru', password: 'Лютик-2026!' } })
await pg.end()
const BORIS = lutik.user!          // lutik: { tenant, user, token, created: true }
```

### Подключение: `connect()`

Подключение получает сессию одним из двух способов: по ключу API (`apiKey`) или по токену (`token`).
Сервис приложения обычно держит одно подключение по ключу и действует от имени пользователей через `as()`:

<!-- run: guide -->
```ts
// сервис: ключ API обменивается на сессию сервиса
const svc = await connect({ dsn: APP, schema: r.schema, apiKey: r.serviceKey! })
// вход: сервис проверяет пароль и действует от имени пользователя в арендаторе
const login = await svc.auth.verifyPassword({ identifier: 'anna@shop.ru', password: 'Ромашка-2026!' })
const db = await svc.as(login!.account, { tenant: SHOP })
// своё подключение по токену сессии — например, в другом процессе
const anna = await connect({ dsn: APP, schema: r.schema, token: r.tenant!.token! })
```

| Опция `connect()` | Что делает |
|---|---|
| `dsn` или `sql` | строка подключения или готовый пул postgres.js |
| `schema` | полное имя установки: `'v2.shop'` (удобно брать `r.schema`) |
| `token`, `apiKey` | токен сессии или ключ API (`service` — синоним `apiKey`) |
| `models` | модели `letopis/model` — только для типов цепочек ([раздел 4](#4-модель-данных)) |
| `max` | размер пула (по умолчанию 10) |
| `listen` | слушать сигналы базы (по умолчанию да; `false` — для PgBouncer в режиме транзакций) |
| `cache` | кэш результатов: `{ ttl, max, ttlOnly }` или `false` ([раздел 12](#12-подписка-на-изменения-и-кэш)) |
| `maintain` | запускать `maintain()` по расписанию: `'1h'`, `'15m'` или миллисекунды |
| `onQuery`, `slowMs` | хук на каждый запрос цепочки и порог медленного запроса |
| `refreshSession` | продлевать сессию раз в минуту работы (по умолчанию да) |
| `notifyIntervalMs` | интервал отправки отложенных сигналов (100 мс) |
| `allowBypassRls`, `owner` | разрешить роль в обход RLS (администраторское подключение); имя роли-владельца |

У подключения есть `db.schema`, `db.token`, `db.tenant` (арендатор сессии) и `db.close()`. Подключения,
полученные через `as()`, делят пул с исходным: закрывать нужно исходное.

### Администраторское подключение

Загрузчику нужно подключение роли, которая может стать владельцем, с `allowBypassRls: true`. `verify()` и
`maintain()` работают и на нём, и у системного администратора по обычному подключению. Администраторское
подключение печатает предупреждение «RLS не действует» — так и должно быть. Сессия задаёт арендатора, с которым
оно работает. Отдельному процессу загрузки удобнее ключ сервиса: `connect({ dsn: ADMIN, schema, apiKey,
allowBypassRls: true })`, а арендатора строк задаёт опция `load(…, { tenant })`. В примере — сессия из `up()`:

<!-- run: guide -->
```ts
const adm = await connect({ dsn: ADMIN, schema: r.schema, token: r.tenant!.token!, allowBypassRls: true })
```

### Обновление пакета и схемы

У схемы есть ревизия движка (сейчас 5). Если новая версия пакета принесла новую ревизию, `connect()` только
предупредит и назовёт команду. Отказывает `up()`: на отставшую схему без `upgrade: true` и на схему новее пакета.
Поэтому скрипт запуска, который вызывает `up()` при каждом старте, после обновления пакета остановится, пока не
получит `upgrade: true`. `up({ dsn, schema, upgrade: true })` применяет миграции из `sql/migrate/` и повторно
накатывает функции; данные сохраняются.

### Разработка без PostgreSQL: PGlite

`up({ pglite: true })` поднимает PGlite (PostgreSQL 18 на WebAssembly) с pgcrypto и сокетом на свободном порту.
Нужны пакеты `@electric-sql/pglite` и `@electric-sql/pglite-socket`. Соединение одно, поэтому:

```ts
const dev = await up({ schema: 'dev', pglite: true })
const local = await connect({ dsn: dev.pglite!.dsn, schema: dev.schema, apiKey: dev.serviceKey!,
  listen: false, max: 1, allowBypassRls: true })
// … работа …
await local.close()
await dev.pglite!.close()
```

Подключение к PGlite — суперпользователь, поэтому нужно `allowBypassRls: true`, а RLS на нём не действует: изоляцию
арендаторов и права на PGlite не проверить. Для гонок и CI он тоже не годится: соединение одно, `LISTEN` нет.

## 4. Модель данных

Классы описываются моделями на Zod из подпути `letopis/model` и записываются в базу. В базе хранится
нормализованная JSON Schema, и данные проверяет при каждой записи сама база.

### Хабы и связи

`hub()` описывает объект, `link()` — связь со своими данными. У обоих две формы:

- короткая: `hub(имя, поля, опции)` — поля объектом типов Zod, опции третьим аргументом;
- полная: `hub(имя, { fields, ends, key, extends, … })` — нужна, например, для наследования (`extends`), чтобы
  TypeScript вывел типы данных потомка.

Модель магазина, на которой построены дальнейшие примеры:

<!-- run: guide -->
```ts
import { z } from 'zod'
import { hub, link, one, many } from 'letopis/model'
import { syncModels } from 'letopis'

const Shop = hub('Shop', { name: z.string(), city: z.string().optional() }, { key: ['name'] })
const Category = hub('Category', { name: z.string() }, {
  key: ['name'],
  ends: { Parent: one('Category').optional().onDelete('unset') },   // дерево: ссылка на родителя
})
const Product = hub('Product', {
  sku: z.string(), title: z.string(), price: z.number().int().min(0), views: z.number().int().optional(),
}, {
  ends: { Shop, Category: many(Category, { max: 5, onDelete: 'unset' }) },
  key: ['Shop', 'sku'],
  meta: { title: 'Товар', icon: 'mdi:package-variant' },
})
const Customer = hub('Customer', { name: z.string(), email: z.string() }, {})   // без ключа: id выдаёт база
const Vip = hub('Vip', { extends: Customer, fields: { discount: z.number().int().min(0).max(50) } })
const Order = hub('Order', {
  number: z.string(), status: z.enum(['new', 'paid', 'cancelled']).default('new'),
}, { ends: { Customer, Shop }, key: ['Shop', 'number'] })
const line = link('line', { qty: z.number().int().min(1), price: z.number().int().min(0) }, {
  ends: { Order: one(Order).onDelete('cascade'), Product },
  key: ['Order', 'Product'],
})
const Wallet = hub('Wallet', { number: z.string(), balance: z.number().int().min(0).default(0) },
  { ends: { Customer }, key: ['number'] })
const Movement = link('Movement', {
  opId: z.string(), kind: z.enum(['topup', 'debit', 'adjust']), amount: z.number().int(), target: z.number().int().optional(),
}, { ends: { Wallet }, key: ['Wallet', 'opId'] })

const models = [Shop, Category, Product, Customer, Vip, Order, line, Wallet, Movement]
const plan = await syncModels(db, models)                     // сухой прогон: что будет создано и изменено
const applied = await syncModels(db, models, { apply: true }) // { applied: true, created: ['Shop', …], … }
```

### Поля

Поля — типы Zod: строки, числа (`int`, `min`, `max`), логические значения, перечисления (`z.enum`), даты и время
(`z.iso.date()`, `z.iso.datetime()`), вложенные объекты любой глубины, массивы и `z.record`. `.optional()` делает
поле необязательным, `.default(…)` — задаёт умолчание, которое база подставит при вставке. Пометки `.meta()` у поля
(`title`, `description`, свои ключи) база хранит, но на проверку данных они не влияют.

Правила `refine`, `superRefine` и `transform` в JSON Schema не выражаются, и база их не исполняет. `syncModels`
возвращает их в `lost`: проверяйте такие правила в приложении. Описание с ключевым словом JSON Schema, которого
база не знает, отклоняется — ни одно правило не пропадёт молча. Шаблоны `pattern` — ограниченное подмножество
регулярных выражений, общее для Zod, валидатора и базы.

### Концы

- `ends: { Shop }` — то же, что `one(Shop)`: одиночный обязательный конец с ролью `Shop`.
- `one(A, B)` — союз: конец принимает строки нескольких классов. `one('Category')` — цель по имени: так класс
  ссылается сам на себя.
- `.optional()` — необязательный конец.
- `many(X, { min, max, onDelete })` — множественный конец: список целей в одном конце.
- `.onDelete(…)` — что делать, когда удаляют цель: `restrict` (по умолчанию — удаление цели запрещено), `cascade`
  (удалить и эту строку), `unset` (снять ссылку; только для необязательного одиночного конца и множественного без
  `min`).

Цели проверяет база: цель существует, принадлежит тому же арендатору или System и относится к объявленному классу
или его потомку. Имя роли однозначно указывает на класс во всей схеме. Поэтому роли `User` и `Tenant` (ведут на
`Account`), `Group` и `Object` (ведут на `Resource`) заняты системными классами: свой конец с таким именем возможен
только с той же целью. В строке ответа одиночный конец — id цели (`row.links.Shop`), множественный — список id.

### Ключ и id

Ключ — обязательные строковые поля и обязательные одиночные концы. Числа, логические значения, объекты,
необязательные поля и множественные концы в ключ не входят. id класса с ключом — UUID версии 5 от арендатора,
класса и значений ключа. Значения берутся как есть, без нормализации: email в разном регистре даёт разные id.
Нужный формат ключевого поля задайте в модели, и база будет его проверять.

- id не передают: база вычисляет его сама. Чужой id — `id_mismatch`, id для класса без ключа — `id_from_db`.
- Заранее id вычисляет `db.idOf(класс, ключ)`, например `db.idOf('Shop', { name: 'Ромашка' })`.
- Класс без ключа (`Customer` выше) получает id от случайной части; узнать его можно из ответа записи.
- Ключевое поле обычной правкой не меняется (`immutable_key`): новый ключ — новый id, это `rekey`
  ([раздел 5](#5-запись)).

Если уникальным должно быть что-то кроме ключа, сделайте это отдельным классом. Например, email — ключ хаба
`Email`, а связь человека с ним — ключ `['Email']`. Персональные данные лучше не делать ключом самого человека:
id из email подбирается перебором и остаётся в ссылках и журнале.

### Наследование и алиасы

`extends` — потомок получает поля, концы и ключ предка. Своё поле с тем же именем заменяет поле предка целиком.
`abstract: true` — у класса не бывает своих строк. Шаг цепочки по классу отдаёт и строки потомков: `db.Customer()`
найдёт и `Vip`, а `.exact()` оставит только сам класс. `alias` — второе имя класса для шага цепочки, например
по-русски.

### Настройки класса

- `history: false` — журнал для класса не ведётся: нет версий, среза на дату, восстановления и событий подписки.
  Политика хранения — `history: { all: '1 day', daily: '3 months', … }` ([раздел 11](#11-история-и-срезы-на-дату)).
- `ownerDefault: 'actor'` — владелец новых строк — сам пользователь, а не арендатор (по умолчанию `'tenant'`).
  Пригодится для правила «каждый видит свои записи».
- `cache: { ttl }` — чтения только этого класса кэшируются без `.cache()` ([раздел 12](#12-подписка-на-изменения-и-кэш)).
- `meta` — свободные метаданные для приложения: название, иконка, цвет, порядок в меню. До 64 КБ, наследуются по
  ключам (`null` убирает унаследованное значение), видны всем, у кого есть сессия. У конца — `.meta()`.

### Записать модель в базу

`syncModels(db, модели)` без `apply` — сухой прогон, с `{ apply: true }` — применение. Результат:
`{ applied, created, updated, unchanged, skipped, lost }`; в `skipped` — классы System, их меняет только установка.
`syncModels` трогает только переданные классы и ничего не удаляет. Безопасные изменения — новое необязательное поле или
конец, метаданные, алиас — применяются сразу. Ужесточение проверяет все строки семейства, и если им мешают строки,
приходит `tightening_conflict` со списком. Классы пишутся в арендатора сессии, и другие арендаторы их не видят.
Классы, общие для всех, лежат в System: их ставит сид установки или импорт.

То же из командной строки:

```sh
npx letopis sync ./models.js --dsn "$APP" --schema v2.shop --token "$TOKEN"            # сухой прогон
npx letopis sync ./models.js --dsn "$APP" --schema v2.shop --token "$TOKEN" --apply    # применить
npx letopis types --dsn "$APP" --schema v2.shop --token "$TOKEN" --out types.ts       # типы классов из базы
```

### Типы цепочек

`connect({ …, models })` даёт типы шагов, строк и фильтров по моделям. Описания классов библиотека всё равно берёт
из базы, модели нужны только TypeScript. Тип данных строки — `Infer<typeof Product>`, концов —
`InferLinks<typeof Product>`. Своё описание `meta` типизируется расширением интерфейса `ClassMeta`.

### Имена классов

Шаг цепочки называется именем класса, его алиасом или именем роли. Имена методов цепочки и корня (`count`, `sort`,
`set`, `sql`, `auth` и другие) Proxy разбирает раньше классов. Поэтому класс с таким именем недостижим как шаг, а
связь с таким именем база не примет. Полный список — в разделе
[«Зарезервированные имена»](#зарезервированные-имена).

## 5. Запись

Глаголы записи — `create`, `update`, `upsert`, `delete`, `anonymize`, `reclass`, `rekey`, `restore`, `purge` —
звенья плана. Сам по себе глагол ничего не делает: план исполняет терминал (`rows`, `first`, `ids`, `count`), и весь
план — одна транзакция.

### Создать: `create`

<!-- run: guide -->
```ts
import { LetopisError } from 'letopis'

const [shop] = await db.Shop().create({ name: 'Ромашка', city: 'Казань' }).rows()
const [tea] = await db.Category().create({ name: 'Чай' }).rows()
const [green] = await db.Category().create({ name: 'Зелёный чай' }).Parent.set(tea).rows()
const [kettle] = await db.Shop(shop).Product().create({ sku: 'K-1', title: 'Чайник', price: 2500 }).rows()
const [sencha] = await db.Shop(shop).Product()
  .create({ sku: 'T-7', title: 'Сенча', price: 900 }).Category.add(green).rows()
const [olga] = await db.Customer().create({ name: 'Ольга', email: 'olga@mail.ru' }).rows()

try {
  await db.Shop().create({ name: 'Ромашка' }).rows()
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'exists') throw e   // e.detail.id === shop.id: такой магазин уже есть
}
```

- `create` только создаёт. Занятый ключ — ошибка `exists` с `detail.id`: id библиотека вычисляет сама. Поэтому у
  класса с ключом повтор после сбоя сети сразу показывает, что первая попытка прошла. Класс без ключа так не
  защищён: повтор создаст второй объект.
- Теги новой строки задаёт `.tags([…])` перед глаголом, владельца — `.owner(id)`; явного владельца должны разрешать
  права.
- Удалённый объект можно создать снова тем же ключом: история продолжится.
- Ответ — строки созданных объектов со всеми колонками ([раздел 15](#15-справочник-api), «Строка ответа»).

### Изменить: `update`

<!-- run: guide -->
```ts
import { gte } from 'letopis'

await db.Product(kettle).update({ title: 'Чайник стеклянный' }).rows()
await db.Shop(shop).Product({ price: gte(2000) }).update({ title: 'Чайник стеклянный, 1 л' }).rows()
```

`update` правит каждую цель шага и никогда не создаёт. Патч сливается с данными внутри оператора: вложенные
объекты — рекурсивно, а массивы, скаляры и `null` заменяются. Поэтому параллельные правки разных полей не теряются.
Если у шага нет своего фильтра, цель берётся из `data.id` патча, а без `data.id` правятся все сущности шага:
`db.Product().update(…)` правит все товары арендатора. Шаг ничего не нашёл — ответ пустой и ошибки нет, поэтому
проверяйте длину ответа. Если `update` затронул меньше строк, чем нашёл шаг, весь план откатывается: строку успели
удалить — `target_not_found`, строка видна, но править её нельзя — `acl_denied`. Модификатор `.tags(…)` перед
`update` и отбирает строки, и заменяет их теги целиком.

### Создать или заменить: `upsert`

<!-- run: guide -->
```ts
const [kept] = await db.Shop().upsert({ name: 'Ромашка', city: 'Казань' }).rows()    // kept.$upsert: 'unchanged'
const [moved] = await db.Shop().upsert({ name: 'Ромашка', city: 'Уфа' }).rows()      // moved.$upsert: 'updated'
```

`upsert` создаёт объект, а если объект с этим ключом уже есть — заменяет его данные, концы и теги целиком. Это
один оператор `INSERT … ON CONFLICT`, поэтому гонки «проверил, что нет, — создал» не бывает. Правила:

- только класс с ключом, иначе `no_key` без обращения к базе;
- объект передаётся целиком: поля, которых нет в переданном объекте, пропадают;
- ответ несёт `$upsert`: `created`, `updated` или `unchanged`;
- приращать `upsert` не умеет и затирает параллельные приращения — для денег он не годится;
- для синхронизации больших справочников дешевле загрузчик с `existing: 'update'` ([раздел 9](#9-массовая-загрузка)).

### Концы: из пути и слоты

Концы создаваемой строки берутся из пути цепочки: `db.Shop(shop).Product().create(…)` ссылается на `shop`. Если
подходит несколько ролей, выбирается роль без занятого слота, затем роль с именем класса шага; иначе —
`invalid_query`. Явно конец задаёт слот после глагола: `.Роль.set(значение)` и `.Роль.unset()`, а у множественного
конца — `.add()` и `.remove()`. Значение — id, список id, строка ответа или вложенная цепочка. Слоты меняют
`links` атомарно, без чтения списка:

<!-- run: guide -->
```ts
await db.Product(sencha).update({}).Category.add(tea).rows()      // ещё одна категория
await db.Product(sencha).update({}).Category.remove(tea).rows()
await db.Category(green).update({}).Parent.unset().rows()         // категория стала корневой
await db.Category(green).update({}).Parent.set(tea).rows()        // и снова внутри «Чая»
```

### Числа и счётчики: `inc`

<!-- run: guide -->
```ts
import { inc } from 'letopis'

await db.Product(kettle).update({ price: inc(-500) }).rows()               // цена уменьшилась на 500
await db.Product(kettle).update({ views: inc(1, { start: 0 }) }).rows()    // поля ещё нет — начать с 0
```

`inc(n)` прибавляет величину внутри оператора `UPDATE` над свежей заблокированной строкой. Поэтому параллельные
приращения не теряются, а правило класса вроде `min(0)` проверяется над итогом: уход в минус отклоняется с
`invalid_data`, без чтения и блокировок в приложении. Правила:

- только в `update`; маркер в `create`, `upsert`, загрузчике и внутри массива — `invalid_data` до отправки;
- поле должно уже быть числом; если его нет — `invalid_data` или `start`. `null` и нечисло — ошибка даже со `start`;
- путь идёт только через существующие объекты;
- маркер `inc` нельзя получить из JSON: `{ "$inc": 5 }`, пришедший из сети, остаётся данными;
- деньги храните целым числом мелких единиц (копеек) не больше 2^53 − 1.

### Защита от параллельной правки: `{ rev }`

<!-- run: guide -->
```ts
const cur = await db.Product(kettle).first()
await db.Product(kettle).update({ price: 1900 }, { rev: cur!.rev }).rows()       // версия совпала — записано
try {
  await db.Product(kettle).update({ price: 1800 }, { rev: cur!.rev }).rows()     // версия уже другая
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'conflict') throw e          // перечитать и решить заново
}
```

Строгий режим нужен, когда новое значение вычислено из прочитанного: если строку успели изменить, приходит
`conflict`, и ничего не записывается. Режим работает при одной цели шага (иначе `rev_ambiguous`). `conflict`
библиотека сама не повторяет: что делать с изменившимися данными, решает приложение. Другой способ — чтение с
блокировкой `forUpdate()` ([раздел 8](#8-транзакции-батчи-и-деньги)).

### Сменить ключ или класс

<!-- run: guide -->
```ts
const [mug] = await db.Shop(shop).Product().create({ sku: 'M-1', title: 'Кружка', price: 400 }).rows()
const [mug2] = await db.Product(mug).rekey({ sku: 'M-100' }).rows()     // новый ключ — новый id, ссылки переведены
const [vip] = await db.Customer(olga).reclass('Vip', { name: 'Ольга', email: 'olga@mail.ru', discount: 10 }).rows()
```

- `rekey(патч)` — новое значение ключа: строка с новым id, все ссылки переведены, старая строка удалена. Если
  ссылающаяся строка включает этот конец в свой ключ, её id тоже меняется, и перевод идёт дальше. Журнал связывает
  старый и новый id (`moved`).
- `db.rekeyClass(класс, ключ)` — новый ключ для всех строк семейства, одной транзакцией.
- `reclass(класс, данные)` — смена класса; данные необязательны, а если переданы — задаются целиком. Если у нового
  класса нет ключа, id сохраняется (как у `vip` выше); если есть — id вычисляется заново, а ссылки переводятся.
  Роли ссылающихся строк должны принимать новый класс, иначе `reclass_denied`. Сырой `UPDATE … SET class`
  проходит, только если ключа нет ни у старого, ни у нового класса (иначе `use_reclass`).
- Удаление, смена класса и смена ключа работают только в `read committed`: транзакции библиотеки всегда открываются
  на этом уровне.

### Обезличить: `anonymize`

<!-- run: guide -->
```ts
await db.Customer(olga).anonymize(['email']).rows()     // email → '[erased]', тег anonymized
```

`anonymize(поля)` затирает строковые поля новой версией и помечает строку тегом `anonymized`. Прежние версии
остаются в журнале. Для полного забвения дальше идут обрезка истории ([раздел 11](#11-история-и-срезы-на-дату)),
затем удаление и `purge` ([раздел 7](#7-удаление-и-восстановление)).

### Как исполняется план

Один план может создать несколько связанных объектов. Продолжение после глагола идёт от его результата: после
`create` и `upsert` — от созданной строки, после остальных глаголов — от всех строк.

<!-- run: guide -->
```ts
const [l1] = await db.Customer(olga).Order()
  .create({ number: 'A-1' }).Shop.set(shop)          // заказ: Customer — из пути, Shop — слотом
  .line().create({ qty: 2, price: 2000 }).Product.set(kettle)   // строка заказа: Order — из пути
  .rows()                                            // строки последнего шага — строка заказа
const order = l1.links.Order as string
await db.Order(order).line().create({ qty: 1, price: 900 }).Product.set(sencha).rows()
```

- Весь план — одна транзакция уровня `read committed`. При взаимной блокировке (`40P01`), ошибке сериализации
  (`40001`) и конфликте журнала библиотека повторяет план целиком, до трёх раз.
- Ошибка любого звена откатывает весь план. `exists` и `conflict` не повторяются: это ответы для приложения.
- Модификаторы до глагола (`limit`, `sort`) сужают его цели.
- Глагол сразу после глагола пишет в те же сущности.

## 6. Чтение

### Шаги и переходы

Цепочка начинается с класса: `db.Shop()` — все магазины, `db.Shop(shop)` — один. Следующий шаг — класс, алиас
или роль конца. Переход идёт по концам: шаг-роль — своим концом, иначе — концами всех классов обоих семейств.
От объекта к тем, кто на него ссылается, — назад, к цели ссылки — вперёд, к тому же классу — к детям.

<!-- run: guide -->
```ts
const products = await db.Shop(shop).Product().rows()          // товары магазина: назад по концу Shop
const shopOf = await db.Product(kettle).Shop().first()         // магазин товара: вперёд
const inOrder = await db.Order(order).line().Product().rows()  // товары заказа: хаб → связь → хаб
const parent = await db.Category(green).Parent().first()       // шаг-роль: родительская категория
const allCustomers = await db.Customer().rows()                // вместе с потомками (Vip)
const onlyCustomer = await db.Customer().exact().rows()        // только сам класс
```

### Фильтры

Фильтр шага — id, список id, строка ответа, объект полей или `or(…)`. Объект полей может быть любой глубины.
Простое значение — равенство через вхождение в `data`, без приведения типов: `{ price: 900 }` не найдёт запись с
ценой `"900"`. Список как значение поля — «массив содержит все элементы». Операторы приводят своё значение к типу
поля из JSON Schema. Роль конца в фильтре — id цели или `null`.

<!-- run: guide -->
```ts
import { lt, ilike, between, or, not } from 'letopis'

const cheap = await db.Product({ price: lt(1000) }).rows()
const teaCount = await db.Product({ title: ilike('%чай%'), price: between(500, 3000) }).count()
const twoIds = await db.Product(or({ sku: 'K-1' }, { sku: 'T-7' })).ids()
const active = await db.Order({ status: not('cancelled') }).rows()
const ofShop = await db.Product({ Shop: shop.id }).rows()
const roots = await db.Category({ Parent: null }).rows()       // корневые категории
```

| Оператор | Условие |
|---|---|
| `ne(v)`, `gt(v)`, `gte(v)`, `lt(v)`, `lte(v)` | ≠ (с учётом `null`), >, ≥, <, ≤ |
| `between(a, b)`, `inList([…])` | a ≤ x ≤ b; значение из списка |
| `like(s)`, `ilike(s)`, `starts(s)`, `ends(s)` | шаблон с `%` и `_`; без учёта регистра; начинается с; заканчивается на |
| `has(v)`, `hasAny([…])`, `hasAll([…])` | поле-массив содержит значение; хотя бы одно; все |
| `exists(true \| false)`, `isNull()` | поле есть или нет; поле `null` или отсутствует |
| `not(v)` | отрицание оператора; скаляр — «не равно» |
| `or(f1, f2, …)` | любой из фильтров шага |

Теги и владелец строки — модификаторы `.tags(…)` и `.owner(…)`.

### Терминалы и строка ответа

| Терминал | Что отдаёт |
|---|---|
| `rows()` | строки сущностей последнего шага, без повторов |
| `first()` | первую строку или `null` |
| `ids()` | id сущностей последнего шага |
| `count()` | число сущностей последнего шага; `count({ paths: true })` — число путей |
| `paths()` | пути: `[{ Шаг: Row, … }]` — узел на каждый шаг |
| `versions()` | все версии сущностей последнего шага ([раздел 11](#11-история-и-срезы-на-дату)) |
| `sum`, `avg`, `min`, `max`, `countBy` | агрегаты по полю `'data.<путь>'`; на пустом множестве — `null`, у `countBy` — `{}` |

Строка ответа: `id`, `class`, `rev` (номер версии), `tenant`, `owner`, `links` (концы), `data` (поля), `tags`,
`at` (время версии), `author`, `op` (вид операции) и, если есть, `agent`, `reason`, `moved`. Служебные поля
начинаются с `$`: `$deleted`, `$depth`, `$upsert`, `$action`, `$versions`, `$purged`.

### Сортировка и постраничный вывод

<!-- run: guide -->
```ts
import { cursorOf } from 'letopis'

const page1 = await db.Product().sort('data.price', 'desc').limit(2).rows()
const page2 = await db.Product().sort('data.price', 'desc')
  .after(cursorOf(page1.at(-1)!, 'data.price')).limit(2).rows()   // строго после последней строки страницы
```

`sort(поле, 'asc' | 'desc')` — по `'at'`, `'rev'`, `'id'` или `'data.<путь>'`. `after(cursorOf(строка, поле))` —
постраничный вывод «после такой-то строки»; он требует `sort()`. Такой вывод устойчив к вставкам и удалениям между
страницами, но строка, у которой изменилось поле сортировки, может выпасть или повториться. Курсор — объект
`{ v, id }` (значение поля и id строки): он переживает JSON, и его можно отдать клиенту. Поле в `cursorOf` должно
совпадать с полем `sort`. Значение курсора проверяется по типу поля `sort` до запроса, неверное — `invalid_query`:
числовому полю нужно конечное число, `rev` — целое, логическому — `true` или `false`, текстовому — строка, uuid и
`id` — uuid, времени и `at` — строка ISO с поясом, дате — `ГГГГ-ММ-ДД`, полю без описания — строка, число или
`true`/`false`. `null` подходит только полям данных, `id` курсора — всегда uuid. Курсор того же типа, снятый
с другого поля, проверка не отличит. `limit` и `offset` тоже есть.

Поле данных бывает `null` или отсутствует. Такие строки `sort` ставит, как `order by` в PostgreSQL: при
возрастании — в конце, при убывании — в начале, а `after()` считает `null` значением после всех прочих (по
возрастанию) или перед ними (по убыванию). Поэтому страницы проходят такие строки без пропусков и повторов, а
курсор со значением `null` даёт следующую страницу.

### Деревья: `deep`

<!-- run: guide -->
```ts
const subtree = await db.Category(tea).Category().deep().rows()   // подкатегории любой глубины; $depth — уровень
```

`deep(max)` повторяет переход к тому же классу до глубины `max` (по умолчанию 32 уровня). Фильтр, теги и владелец
шага отбирают узлы любого уровня, но обход не обрывают. Обрывает его только узел, невидимый по правам: он скрывает и
своё поддерево.

### Агрегаты

<!-- run: guide -->
```ts
const total = await db.Order(order).line().sum('data.price')       // сумма строк заказа
const avgPrice = await db.Shop(shop).Product().avg('data.price')
const byStatus = await db.Order().countBy('data.status')          // { new: 1 }
```

Агрегаты считает база, по сущностям последнего шага.

### Пути

<!-- run: guide -->
```ts
const orderPaths = await db.Order(order).line().Product().paths()   // [{ Order: Row, line: Row, Product: Row }, …]
```

`paths()` отдаёт узлы каждого варианта пути; ключ узла — имя шага или имя из `.alias(имя)`. Повтор связи в
цепочке возвращает к её узлу: так из одной связи можно пройти в несколько сторон. `db.entity(строка | цепочка)`
вставляет готовый узел в путь.

## 7. Удаление и восстановление

### Превью и удаление

<!-- run: guide -->
```ts
const preview = await db.Order(order).delete().rows()     // ничего не удаляет: заказ и его строки, $action каждой
await db.Order(order).delete({ confirm: true }).rows()    // удалено: надгробия с $deleted: true

const blockers = (await db.Shop(shop).delete().rows()).filter((x) => x.$action === 'restrict')
try {
  await db.Shop(shop).delete({ confirm: true }).rows()   // магазину мешают товары: конец Shop — restrict
} catch (e) {
  if (!(e instanceof LetopisError) || e.code !== 'delete_restricted') throw e
}
```

`delete()` без `{ confirm: true }` — только превью: всё замыкание каскада. В каждой строке превью `$action`:
`delete`, `unset` или `restrict`, и `$depth` — уровень каскада (0 — сама цель; у строк `unset` и `restrict` его
нет). С подтверждением удаляются все цели
шага одним оператором, а каскад применяет правила концов. Превью не учитывает права: строка с `$action: 'delete'`
может не удалиться у пользователя без права (`acl_denied`), поэтому интерфейсу стоит спросить
`acl.checkData(класс, 'DELETE')`. Правила концов:

- `restrict` — удаление запрещено, пока на цель ссылаются (`delete_restricted` со списком видимых строк и числом
  остальных);
- `cascade` — ссылающиеся строки удаляются вместе с целью (строки заказа выше);
- `unset` — ссылка снимается.

Каскад требует права на удаление каждой удаляемой строки, снятие ссылки — права на запись. Сырой
`DELETE … WHERE id IN (…)` любого набора связанных строк работает так же.

### Восстановить: `restore`

<!-- run: guide -->
```ts
await db.Order(order).restore().rows()                       // заказ — последним снимком, id прежний
await db.Order(order).line().withDeleted().restore().rows()  // и его строки, удалённые каскадом
```

`restore()` возвращает последний снимок удалённого объекта новой версией и перепроверяет его по текущему описанию
класса. Восстанавливаются только цели шага, а не весь каскад. Живой объект — `not_deleted`.

### Стереть историю: `purge`

<!-- run: guide -->
```ts
const [temp] = await db.Customer().create({ name: 'Тест', email: 'test@example.com' }).rows()
await db.Customer(temp).delete({ confirm: true }).rows()
const before = await db.Customer(temp).purge().rows()          // превью: $versions — сколько версий в журнале
await db.Customer(temp).purge({ confirm: true }).rows()        // история стёрта; в журнале — запись purge
```

`purge` работает только для удалённых объектов (живой — `not_deleted`) и стирает их историю целиком; на месте
версии 1 остаётся запись `purge` с числом стёртых версий. История системных классов не стирается. Удалить аккаунт —
`db.auth.purgeAccount` ([раздел 10](#10-пользователи-вход-и-права)).

## 8. Транзакции, батчи и деньги

### Каждая операция — транзакция

Каждый терминал цепочки — своя транзакция уровня `read committed`, какой бы уровень ни стоял в базе по умолчанию.
На этом уровне приращение и каскад видят свежие строки. Взаимную блокировку, ошибку сериализации и конфликт журнала
библиотека повторяет сама. Если связь оборвалась во время `COMMIT`, она не повторяет и бросает `commit_unknown`:
транзакция могла и зафиксироваться. Исход выясняет повтор той же операции с тем же ключом — `exists` значит
«уже записано».

### Явная транзакция: `db.begin()`

<!-- run: guide -->
```ts
const tr = await db.begin()
try {
  const [o2] = await tr.Customer(olga).Order().create({ number: 'A-2' }).Shop.set(shop).rows()
  await tr.Order(o2).line().create({ qty: 1, price: 2000 }).Product.set(kettle).rows()
  await tr.commit()
} catch (e) {
  await tr.rollback()
  throw e
}
```

- Внутри — те же цепочки, `db.sql`, `forUpdate()`, `lock()`, `commit()` и `rollback()`.
- Ошибка любого запроса ломает транзакцию: каждый следующий вызов и `commit()` бросают исходную ошибку,
  `commit()` при этом откатывает. `rollback()` проходит. Если ошибку перехватили внутри `tr.transaction(fn)` и
  библиотека о ней не знает, PostgreSQL молча отвечает `ROLLBACK` на `COMMIT`, а библиотека превращает это в ошибку
  `tx_rolled_back`.
- Повторов внутри `db.begin()` нет: на `40P01` повторите весь блок.
- `lock(...ключи)` — advisory-блокировка до конца транзакции. Она защищает, только если её берут все, кто правит
  эти данные.

### Батч

<!-- run: guide -->
```ts
const b = db.batch('витрина')
b.Shop(shop).Product().create({ sku: 'C-1', title: 'Чашка', price: 300 })
b.Shop(shop).Product().create({ sku: 'C-2', title: 'Блюдце', price: 200 })
const results = await b.run()       // Row[][] — по массиву строк на каждый план, одной транзакцией
```

Батч копит планы, а `run()` исполняет их одной транзакцией. Подряд идущие простые `create` и `upsert` класса с
ключом склеиваются в один многострочный оператор. `b.size()` — сколько планов в очереди, `b.discard()` —
очистить. Терминал на плане из очереди — `invalid_query`: исполняет только `run()`. Имя — ключ очереди фасада: у
корня подключения, у каждого `db.as()` и у каждой `db.begin()` очереди свои. План исполняется от имени того фасада,
который поставил его в очередь (актор, арендатор, владелец, транзакция), и чужих планов `run()` не исполняет.
Копите планы через один и тот же объект фасада.

### Рецепт: кошелёк

Баланс — поле `balance` хаба `Wallet` (целые копейки, `min(0)`), операции — связь `Movement` с ключом
`[Wallet, opId]` ([раздел 4](#4-модель-данных)). Операцию не правят и не удаляют, а отменяют встречной операцией с
новым `opId`. Ключ делает операцию идемпотентной: повтор после потери ответа получает `exists`, и рецепт сверяет,
тот ли это запрос.

<!-- run: guide -->
```ts
import { inc, type Db } from 'letopis'

type Kind = 'topup' | 'debit' | 'adjust'

/** Операция: запись Movement и приращение баланса — один план, одна транзакция. */
async function operate(db: Db, wallet: string, opId: string, kind: 'topup' | 'debit', amount: number) {
  try {
    await db.Wallet(wallet).Movement().create({ opId, kind, amount })
      .Wallet().update({ balance: inc(kind === 'topup' ? amount : -amount) }).rows()
    return 'done'
  } catch (e) {
    if (e instanceof LetopisError && e.code === 'exists') return same(db, wallet, opId, kind, amount)   // повтор
    throw e                                        // invalid_data — не хватает средств (min(0))
  }
}

/** Отпечаток повтора: тот ли запрос уже записан под этим opId. */
async function same(db: Db, wallet: string, opId: string, kind: Kind, value: number) {
  const m = await db.Movement(db.idOf('Movement', { Wallet: wallet, opId })).first()
  if (!m || m.data.kind !== kind || (kind === 'adjust' ? m.data.target : m.data.amount) !== value)
    throw new Error(`ключ операции ${opId} уже использован другим запросом`)
  return 'repeat'
}

/** Корректировка «баланс = target»: операция adjust на разницу, итог — под { rev }. */
async function adjust(db: Db, wallet: string, opId: string, target: number) {
  for (;;) {
    if (await db.Movement(db.idOf('Movement', { Wallet: wallet, opId })).first()) return same(db, wallet, opId, 'adjust', target)
    const cur = (await db.Wallet(wallet).first())!
    try {
      await db.Wallet(wallet).Movement().create({ opId, kind: 'adjust', amount: target - (cur.data.balance as number), target })
        .Wallet().update({ balance: target }, { rev: cur.rev }).rows()
      return 'done'
    } catch (e) {
      if (e instanceof LetopisError && e.code === 'conflict') continue     // кошелёк изменился — перечитать
      if (e instanceof LetopisError && e.code === 'exists') return same(db, wallet, opId, 'adjust', target)
      throw e
    }
  }
}

const [wallet] = await db.Customer(olga).Wallet().create({ number: 'W-1' }).rows()
await operate(db, wallet.id, 'op-1', 'topup', 10_000)    // 'done': баланс 10 000
await operate(db, wallet.id, 'op-1', 'topup', 10_000)    // 'repeat': повтор после потери ответа, баланс тот же
await operate(db, wallet.id, 'op-2', 'debit', 3_000)     // баланс 7 000
await adjust(db, wallet.id, 'op-3', 5_000)               // корректировка: adjust на −2 000, баланс 5 000
```

Тот же итог можно записать под чтением с блокировкой — без повторов при `conflict`:

<!-- run: guide -->
```ts
const [wallet2] = await db.Customer(olga).Wallet().create({ number: 'W-2' }).rows()
const tx = await db.begin()
try {
  const w = (await tx.Wallet(wallet2).forUpdate().first())!     // строка кошелька заблокирована до commit
  await tx.Wallet(wallet2).Movement()
    .create({ opId: 'op-1', kind: 'adjust', amount: 6_000 - (w.data.balance as number), target: 6_000 })
    .Wallet().update({ balance: 6_000 }).rows()
  await tx.commit()
} catch (e) {
  await tx.rollback()
  throw e
}
```

- `inc` прибавляет внутри оператора над заблокированной строкой: параллельные списания не теряются, а `min(0)`
  отклоняет списание сверх баланса.
- Обычный `update({ balance: 700 })` записывает значение, а не прибавляет. Итог, вычисленный из прочитанного,
  без `{ rev }` или `forUpdate()` теряет параллельные списания. Advisory `lock()` не спасает, если его берут не все
  писатели. `upsert` затирает приращения.
- `forUpdate()` — только внутри `db.begin()` (иначе `tx_required`) и только с `rows`, `first`, `ids` (иначе
  `lock_unsupported`). Строки блокируются в порядке id; строка, которая перестала подходить под условия шага, в ответ
  не попадает.
- Для одного кошелька выберите один путь: под `{ rev }` и под `forUpdate()` кошелёк и ключ операции блокируются в
  разном порядке, и смешение в параллельных запросах даёт `40P01`. Внутри блока с `forUpdate()` не ждите внешних
  вызовов: кошелёк ждут все писатели (помогут `lock_timeout` и `idle_in_transaction_session_timeout`).
- Перевод — две операции в одной `db.begin()`, кошельки правятся в порядке id: тогда взаимных блокировок нет.
- Нехватку средств отличают от других ошибок данных по `e.issues`: поле `balance`, правило `minimum`.

## 9. Массовая загрузка

### Когда нужен загрузчик

Загрузчик — путь для импорта, засевки и синхронизации больших справочников. Он проверяет строки в коде библиотеки
тем же валидатором, что и база, и пишет их командой `COPY` от роли владельца, без триггеров и RLS. На бенче это
около 6 400 строк в секунду против 130 у построчного `create` ([раздел 17](#17-производительность)). Работает
только на администраторском подключении (`allowBypassRls` и право стать владельцем), иначе — `admin_required`.

### `db.load()`

<!-- run: guide -->
```ts
const rep = await adm.load({
  Shop: [{ name: 'Василёк', city: 'Пермь' }],
  Product: [
    { sku: 'V-1', title: 'Кружка', price: 450, Shop: { $key: ['Василёк'] } },
    { sku: 'V-2', title: 'Ложка', price: 150, Shop: { $key: ['Василёк'] }, $tags: ['новинка'] },
  ],
  Customer: [{ name: 'Пётр', email: 'petr@mail.ru', $ext: 'crm:1001' }],
})
// rep: { rows: 4, loaded: 4, updated: 0, skipped: 0, duplicates: 0, byClass: { Shop: 1, Product: 2, Customer: 1 }, … }
```

- Вход — объект «класс → строки», массив или поток строк с полем `$class`.
- Строка — поля и роли концов на верхнем уровне. Служебные ключи: `$class` — класс строки, `$ext` — внешний ключ
  класса без ключа (повторная загрузка того же файла даёт те же id), `$tags` — теги, `$owner` — владелец.
- Ссылка — id цели, ключ `{ $key: [...] }` или внешний ключ `{ $ext: '…' }`; у полиморфного конца — с `$class`
  цели. Порядок строк и классов не важен, ссылки по кругу допустимы.
- Ключи на `$` внутри данных — обычные данные.
- Строки идут в арендатора сессии (или `tenant`). Загрузка — одна транзакция: ошибка в любой строке отменяет всё.
  Подписки видят строки после фиксации.

### Повторы и существующие объекты

<!-- run: guide -->
```ts
const again = await adm.load({ Shop: [{ name: 'Василёк', city: 'Пермь' }] }, { existing: 'skip' })      // skipped: 1
const changed = await adm.load({ Shop: [{ name: 'Василёк', city: 'Самара' }] }, { existing: 'update' }) // updated: 1
```

| Опция | Значения |
|---|---|
| `duplicates` — повтор id внутри загрузки | `'error'` (по умолчанию) — отменить; `'first'` или `'last'` — оставить первую или последнюю строку |
| `existing` — объект уже есть в базе | `'error'` (по умолчанию) — отменить; `'skip'` — пропустить, удалённые не воскрешать; `'update'` — новая версия, если содержимое отличается (неизменённые считаются в `skipped`), удалённые — создать заново |

### Порции, история и проверка

- `commitEvery: N` — фиксировать порциями примерно по N строк. Порции идут по классам в порядке зависимостей,
  классы из одного цикла — в одной порции. Ошибка отменяет только текущую порцию, а повтор с `existing: 'skip'`
  дописывает остальное.
- `withHistory: true` — строки — это версии с `$rev`, `$at` и `$op`; так импорт переносит историю.
- `verify: true` — в конце перепроверить загруженные строки проверкой базы.
- `batch` (строк в пачке `COPY`, 10 000), `class` (класс строк без `$class`), `tenant`, `agent` (агент версий).

### Загрузка от имени пользователя

<!-- run: guide -->
```ts
await adm.load({ Category: [{ name: 'Посуда' }] }, { as: ANNA, tenant: SHOP })
```

С `as` автором версий становится пользователь, а загрузчик проверяет то же, что база при обычной записи:
арендатор ему доступен, право записи в каждый класс, условия прав на строки, видимость целей ссылок, владелец по
`ownerDefault`. Без `tenant` строки идут в собственного арендатора пользователя. Так процесс загрузки принимает
файлы, присланные пользователями.

### Командная строка

```sh
npx letopis load shops.ndjson products.ndjson --dsn "$ADMIN" --schema v2.shop --token "$TOKEN" \
  [--class Product] [--duplicates first] [--existing skip] [--commit-every 100000] [--verify]
# shops.ndjson:    {"$class":"Shop","name":"Юг"}
# products.ndjson: {"$class":"Product","sku":"Y-1","title":"Ваза","price":800,"Shop":{"$key":["Юг"]}}
```

Файлы NDJSON — объект на строку; все файлы — одна загрузка.

### Отчёт и ошибки

Отчёт: `rows`, `loaded`, `updated`, `skipped`, `duplicates`, `byClass`, `external` (сколько целей вне загрузки
сверено запросом в конце), `portions`, `ms`. Ошибка — `LetopisError` с кодом первой проблемы. Её `detail`:
`rows` — первые 100 нарушений с номером строки, кодом и подробностями (`line`, `code`, `message`, `id`, `class`,
`issues`), `total` — сколько нарушений найдено, `truncated` — список обрезан, `limit` — предел списка (100),
`complete` — проверки, нашедшие нарушения, прошли все строки. Коды строк: коды проверок базы, а также `duplicate`
(повтор id), `exists` (объект уже есть), `deleted` (объект с этим id жил раньше) и `class_not_loadable` (строки
`Class` загрузчик не принимает: классы задаёт `syncModels`).

Нарушения ищутся поэтапно: разбор строк (классы, id, повторы), права на классы (`load({ as })`), данные и концы
пачками, в конце порции — цели вне загрузки, владельцы и арендатор. Загрузка отменяется после первого этапа,
нашедшего нарушения, и `total` считает нарушения этого этапа. Цель вне загрузки — одно нарушение на цель (строка —
первая, что на неё ссылается). «(и ещё N)» в тексте ошибки — точное число остальных нарушений. Если проверены не все
строки, `complete` — `false`, а текст говорит «(и ещё не меньше N: причины)» или, если найдено одно нарушение,
«(возможно, не единственная: причины)». Причины: следующие порции `commitEvery` не проверялись; условия ACL
следующих пачек не проверялись (`load({ as })`); проверка базы (`verify: true`) называет не больше 100 строк.

## 10. Пользователи, вход и права

### Аккаунты, арендаторы и членство

Аккаунт — строка класса `Account` в System: имя, категории (`User`, `Service` и свои), признак `enabled`. Каждый
аккаунт — сам себе арендатор. Работать в чужом арендаторе позволяет членство `member` — связь пользователя
(`User`) с арендатором (`Tenant`) с ролями в данных. Аккаунты и их категории правит системный администратор —
член System с ролью `admin`. Отдельного метода, чтобы назначить его, нет: членство в System с ролью `admin` кладёт
свой сид установки или загрузчик на администраторском подключении (строка `member` с `tenant: <id System>`).
Новых пользователей арендатора удобно заводить `createTenant`
([раздел 3](#3-установка-и-подключение)).

### Сервис и ключи API

Сервис — аккаунт категории `Service` с ключом API. Ключ установки выдаёт `up()`. Сервис проверяет пароли и коды,
выпускает сессии и действует от имени пользователей. Ключи обычных пользователей он выпускает и отзывает сам (право
`auth.credential`), как ниже для Бориса. Свои ключи API и пары «ключ + секрет» сервис тоже выпускает и отзывает сам —
по сессии, открытой своим ключом (`connect({ apiKey })`, `verifyApiKey`, `verifyKeySecret`). Прочие свои креды,
ключи других сервисов, System и системных администраторов выпускает и отзывает только системный администратор;
новый ключ сервиса регистрирует и `up({ serviceKey })`.

Ключей может быть несколько. Сессия, открытая ключом, помнит его, и отзыв ключа гасит только его сессии: подключения
по другим ключам работают дальше. Поэтому ротация идёт без простоя: сервис выпускает себе новый ключ
(`issueApiKey({ account: <id сервиса> })`), переводит процессы на него и отзывает старый (`revokeCredential(id)`).
Текущую сессию отзыв оставляет, `keepCurrent: false` гасит и её. Последний действующий ключ сервиса не отзывается:
`acl_denied` «последний действующий ключ сервиса не отзывается: сначала выпустите новый». Отключить сервис —
`enabled: false` у его аккаунта.

<!-- run: guide -->
```ts
const { key, id: keyId } = await svc.auth.issueApiKey({ account: BORIS, name: 'интеграция' })   // ключ отдаётся один раз
const viaKey = await svc.auth.verifyApiKey(key)                    // { account, token } | null
await svc.auth.revokeCredential(keyId)
```

Пара «ключ + секрет» — `issueKeySecret({ account, name })` и `verifyKeySecret(key, secret)`.

### Пароли

<!-- run: guide -->
```ts
await svc.auth.setPassword({ account: BORIS, identifier: 'boris@lutik.ru', password: 'Новый-пароль-2026', confirmed: true })
const failed = await svc.auth.verifyPassword({ identifier: 'boris@lutik.ru', password: 'Лютик-2026!' })   // null: пароль сменён
```

- Пароль хранится хэшем scrypt; проверяет его сервис, время ответа для несуществующего логина выровнено.
- Идентификатор сравнивается без учёта регистра: `Anna@Shop.ru` и `anna@shop.ru` — один вход.
- Смена пароля гасит остальные сессии аккаунта (`keepCurrent` — оставить текущую).
- По умолчанию вход — только по подтверждённому креду, иначе `null`; `requireConfirmed: false` пускает и по
  неподтверждённому. Подтверждает кред сервис: `confirmed: true` в `setPassword` или `setFlags`.
- Второй фактор — опция `totp`: `verifyPassword({ identifier, password, totp })` после верного пароля проверяет код
  TOTP аккаунта и выдаёт сессию со способами `[вид, 'TOTP']`, по умолчанию `['PASSWORD', 'TOTP']` (см. ниже). Без
  `totp` вход код не проверяет: требовать ли второй фактор, решает сервис.

### Одноразовые коды и TOTP

<!-- run: guide -->
```ts
import { totpCode } from 'letopis'

const { code } = await svc.auth.issueOtp({ account: BORIS, identifier: 'boris@lutik.ru', ttl: 300 })   // сервис отправит код письмом
const byCode = await svc.auth.verifyOtp({ identifier: 'boris@lutik.ru', code })                        // { account, token } | null
const { secret, uri } = await svc.auth.enrollTotp({ account: BORIS, issuer: 'Лютик' })              // uri — для QR-кода
const totpOk = await svc.auth.verifyTotp({ account: BORIS, code: totpCode(secret) })                // первая проверка включает фактор
```

Код одноразовый: успешная проверка и перебор (по умолчанию 5 попыток) его сжигают. Счётчики попыток откатываются
вместе с транзакцией вызывающего, поэтому частоту попыток ограничивает сервис. Повтор того же шага TOTP
отклоняется. `totpCode(secret)` — помощник для тестов и сервисов.

Вход со вторым фактором — `verifyPassword({ …, totp })` и `lookup({ …, totp })`. Код проверяется только после
верного пароля или найденной учётной записи, той же проверкой, что `verifyTotp`: нужно право `auth.totp`, окно —
шаг в каждую сторону, счётчик неудач общий (пять подряд закрывают проверку на 5 минут). Верный код даёт сессию со
способами `[вид, 'TOTP']` и включает ещё не подтверждённый фактор; неверный или повторный код, как и код у аккаунта
без TOTP, — `null`. По такой сессии пользователь с TOTP 10 минут меняет свои креды сам.

### Внешние учётные записи

`link({ account, kind, identifier, confirmed })` привязывает внешнюю учётную запись (Telegram, Google, SSO): её
токен проверяет сервис, а база хранит связку. `lookup({ kind, identifier })` — вход по ней (с опцией `totp` — и по
коду TOTP, как `verifyPassword`):

<!-- run: guide -->
```ts
await svc.auth.link({ account: BORIS, kind: 'TELEGRAM', identifier: '100500', confirmed: true })
const viaTelegram = await svc.auth.lookup({ kind: 'TELEGRAM', identifier: '100500' })   // { account, token } | null
```

Свои креды пользователь привязывает сам только после недавнего входа (10 минут; ключ API, пара «ключ + секрет» и
сессия от сервиса не в счёт) и не подтверждает их сам. При включённом TOTP база требует сессию с пройденным TOTP:
её выдают `verifyPassword` и `lookup` с опцией `totp`. Если идентификатор занят, привязка отвечает тем же
`acl_denied`, что и без недавнего входа. Но пользователь с недавним входом по такому отказу поймёт, что
идентификатор занят ([раздел 18](#18-ограничения)).

### Сессии

<!-- run: guide -->
```ts
const shortToken = await svc.auth.sessionFor(BORIS, { ttl: 600 })   // сессия на 10 минут простоя — для другого процесса
const boris = await connect({ dsn: APP, schema: r.schema, token: shortToken })
await boris.auth.revoke()                                            // выход: сессия погашена
await boris.close()
```

Токен — 256 случайных бит; база хранит только его sha256. Срок по умолчанию — 7 суток. `refresh()` продлевает
текущую сессию: новый срок отсчитывается от текущего момента, но не больше срока, выданного при входе; возвращает
он новое время истечения. `connect()` продлевает сессию сам раз в минуту работы (`refreshSession`), поэтому сессия,
которой пользуются, не истекает: срок — это время простоя. `revoke()` — выход, `revokeAll()` — выход везде.
Сессии гаснут при отключении аккаунта, смене пароля, удалении креда и удалении аккаунта. Удаление креда гасит
остальные сессии аккаунта, а отзыв ключа API или пары «ключ + секрет» — только сессии, открытые этим ключом (и
старые сессии того же вида входа без отметки ключа); текущая сессия остаётся, если не передать
`keepCurrent: false`.

### Работа в другом арендаторе

Сервис действует от имени пользователя через `svc.as(account, { tenant, owner })`. База проверяет право сервиса
`auth.impersonate` (по правилам System), что пользователь существует и включён и что арендатор ему доступен —
собственный или по членству. От имени System, сервисов, системных администраторов и отключённых аккаунтов
действовать нельзя. Видимость пользователя по правилам доступа не проверяется. В журнале `author` — пользователь,
`agent` — сервис. Подключение
пользователя по своему токену переключается между арендаторами так:

<!-- run: guide -->
```ts
const mine = await anna.auth.tenants()     // [{ tenant, roles }]: собственный арендатор и магазин по членству
await anna.auth.switch(SHOP)               // арендатор сессии — магазин
```

### Права

Права включены всегда и по умолчанию запрещают. Правило связывает группу с объектом:

- **группа** — строка `Resource` категории `ACCOUNT`: аккаунты по категориям (`{ categories: '{User}' }`) или
  участники по ролям членства (`{ roles: '{staff}' }`);
- **объект** — строка `Resource` категории `API` (эндпоинт по маске, `{ endpoint: 'shop.reports.*' }`) или `READ`,
  `WRITE`, `DELETE` (строки класса по маске с потомками, `{ class: 'Product' }`, и условие на колонки `id`,
  `owner`, `tenant`, `tags`, `data`, `links` со значениями `$actor` и `$tenant`);
- **правило** — связь `rule` группа → объект: `permission` (`allow` или `deny`) и `weight`.

Решает ровно одно правило: наибольший вес, при равном весе запрет сильнее разрешения. Вес правила арендатора больше
999 урезается до 999, поэтому правила System с весом от 1000 — административный слой, который арендатор не
перевесит. Правила
арендатора действуют на его строки, правила System — везде. Права действуют и на сырой SQL: строки без права не
видны, правка — пусто или `acl_denied`.

### Выдать право

Пример: Олег — сотрудник магазина с ролью `staff`, и сотрудникам нельзя удалять товары.

<!-- run: guide -->
```ts
const pg2 = postgres(ADMIN)
const OLEG = (await createTenant(pg2, r.schema, {          // тот же магазин: создаётся только пользователь
  name: 'Ромашка', user: { name: 'Олег', login: 'oleg@shop.ru', password: 'Олег-2026!' } })).user!
await pg2.end()
await db.member(db.idOf('member', { User: OLEG, Tenant: SHOP })).update({ roles: ['staff'] }).rows()

const [staff] = await db.Resource().create({ alias: 'staff:ACCOUNT', category: 'ACCOUNT', pattern: { roles: '{staff}' } }).rows()
const [delProduct] = await db.Resource().create({ alias: 'product:DELETE', category: 'DELETE', pattern: { class: 'Product' } }).rows()
await db.rule().create({ permission: 'deny', weight: 50 }).Group.set(staff).Object.set(delProduct).rows()   // сильнее «можно всё» (10)
const [reports] = await db.Resource().create({ alias: 'reports:API', category: 'API', pattern: { endpoint: 'shop.reports.*' } }).rows()
await db.rule().create({ permission: 'allow', weight: 50 }).Group.set(staff).Object.set(reports).rows()

const asOleg = await svc.as(OLEG, { tenant: SHOP })
const canDelete = await asOleg.acl.checkData('Product', 'DELETE')   // { allow: false }
const canRead = await asOleg.acl.checkData('Product', 'READ')       // { allow: true }
const canReport = await asOleg.acl.check('shop.reports.daily')      // { allow: true, rule: { weight: 50, … } }
```

- `acl.check(эндпоинт)` → `{ allow, rule, code, message }`: свой отказ эндпоинта задают поля `code` и `message`
  запрещающего правила.
- `acl.checkData(класс, 'READ' | 'WRITE' | 'DELETE')` → `{ allow, filter }`: `filter` — условие на строки.
- Права пересчитываются базой сами. Убрать право — удалить правило: `db.rule(id).delete({ confirm: true })`.
- Библиотека один раз берёт у базы подписанный план прав актора — пропуск прав — и передаёт его в каждой
  транзакции, поэтому проверка прав стоит десятки микросекунд. Сырой SQL без пропуска платит 0,3–1,3 мс на запрос.
- На вопрос «у кого был доступ на дату» отвечает срез `asOf` по классам `rule`, `member` и `Resource`.

Поля системных классов прав:

- `member` — концы `User` и `Tenant`, поле `roles` (список ролей);
- `Resource` — `alias` (уникальное имя ресурса и его ключ; это не алиас класса), `category` (`ACCOUNT`, `API`,
  `READ`, `WRITE`, `DELETE`) и `pattern` — маска. У группы маска `categories` или `roles` — только строка: `'{staff}'`,
  `'{a,b}'`, отрицание — `'!{a}'`. У объекта — `endpoint` или `class` (тоже только строки) и условия на колонки.
  **Маску не строкой (например, массив `['staff']`, число или `null`) база отклоняет** с `invalid_data` — при записи
  библиотекой, сырым SQL и загрузчиком. Старые строки с такой маской (записанные до этой проверки или в обход
  неё) разрешений не дают, а запрет по ним действует на всех: по группе — на все аккаунты, по маске `class` — на все
  классы (маска `endpoint` не строкой, как и прежде, не совпадает ни с одним эндпоинтом). Проверку при записи несёт
  описание класса `Resource`: оно приходит со свежей установкой и после `reset({ all })`; в существующей схеме
  исправленное сопоставление действует после повторного `up()`;
- `rule` — концы `Group` и `Object` (строки `Resource`), поля `permission` (`allow` или `deny`), `weight`, а для
  своего отказа эндпоинта — `code` и `message`.

### Удалить аккаунт

`db.auth.purgeAccount(аккаунт)` удаляет аккаунт и данные его арендатора. Вызывать может системный администратор или
владелец его арендатора; себя и последнего владельца арендатора удалить нельзя. Владение строками в чужих
арендаторах переходит этим арендаторам, сессии гаснут, креды удаляются.

## 11. История и срезы на дату

### Версии

<!-- run: guide -->
```ts
const versions = await db.Product(kettle).versions()              // все версии: op, rev, author, at, data
const followed = await db.Product(mug2).versions({ follow: true }) // и через смену id (rekey, reclass)
```

У каждой версии — автор, агент, время, номер, вид операции (`create`, `update`, `delete`, `reclass`, `rekey`,
`restore`, `purge`, `trim`, `reset`) и причина (`reason`) — если её задала настройка `letopis.reason` транзакции;
отдельного API для причины нет. Версия удаления — с `$deleted`.

### Срез на дату

<!-- run: guide -->
```ts
const createdAt = versions[0].at
const atCreation = await db.Product(kettle).asOf(createdAt).first()  // цена в момент создания — 2500
const assortment = await db.Shop(shop).Product().asOf(createdAt).rows()
```

`asOf(момент)` — состояние «как было» по журналу; момент — строка ISO или `Date`. Срез работает на любом шаге
цепочки, в том числе с `deep()`. Дёшево только текущее состояние: срез восстанавливается из журнала. Время версии
`at` хранит микросекунды, а `Date` — только миллисекунды: передавайте в `asOf` строку `at` как есть, иначе срез на
момент версии может её не застать.

### Удалённые

<!-- run: guide -->
```ts
const withGone = await db.Customer().withDeleted().rows()   // живые и удалённые; у удалённых $deleted: true
```

### Политика хранения

Без политики журнал хранит каждую версию. Политика задаёт, сколько хранить старые версии и с какой подробностью:

```ts
history: { all: '1 day', daily: '1 week', weekly: '1 month', monthly: '1 year', yearly: 'forever', tz: 'Europe/Moscow' }
```

Это значит: все версии за последние сутки; за неделю — по одной на день; за месяц — по одной на неделю; за год —
по одной на месяц; старше — по одной на год, бессрочно. От периода остаётся его последняя версия. Неделя
начинается с понедельника, границы периодов — в поясе `tz` (по умолчанию UTC).

- Политику задают у класса (потомки наследуют) или для всех классов без своей — `up({ history })`.
- Если у последнего яруса задан срок, а не `'forever'`, история старше срока удаляется: `{ all: '30 days' }`.
- Пока история объекта жива, не удаляются текущая версия, версия 1 и версии особых видов (`create`, `delete`,
  `reclass`, `rekey`, `restore`, `purge`, `reset`, `trim`). Если надгробие удалённого объекта старше последнего яруса
  со сроком, его история стирается целиком. История системных классов не прореживается.
- Прореживает `maintain()` пачками по 10 000 версий ([раздел 13](#13-эксплуатация)).
- В прореженной части срез показывает последнюю сохранённую версию до момента, то есть его точность равна
  периоду яруса. Подписчик, отставший дольше яруса `all`, получает `cursor_expired`.

### Обрезка истории

<!-- run: guide -->
```ts
const trimmed = await db.trimHistory(kettle, new Date())     // стереть версии чайника до этого момента
```

`db.trimHistory(цель, момент)` сразу стирает историю до момента: класса с потомками (по имени), id, списка id или
строк. Это средний шаг «права на забвение»: `anonymize` → обрезка истории → удаление и `purge`. На месте версии 1
остаётся запись `trim` с её временем, поэтому срез знает, когда объект появился.

### Проверка целостности

<!-- run: guide -->
```ts
const audit = await adm.verify({ data: true })     // { ok, issues, anchor }
```

`verify()` пересчитывает цепочки хэшей всех версий и возвращает якорь — хэш всех голов цепочек. Храните якорь вне
базы: подмену последних версий выдаст его расхождение. `{ data: true }` вдобавок перепроверяет данные, концы,
арендаторов, владельцев и id всех строк. Вызывать может системный администратор или администраторское подключение;
из командной строки — `letopis verify [--data]` (код выхода 1 при находках). Законные разрывы — записи `trim` и
`purge`, прореживание и `reset` — ошибкой не считаются.

## 12. Подписка на изменения и кэш

### Подписка

<!-- run: guide -->
```ts
const sub = db.watch({ from: 'start', classes: ['Product'] })   // весь журнал класса, затем новые события
await db.Product(kettle).update({ price: 2100 }).rows()
let cursor = ''
for await (const ev of sub) {             // ev: { cursor, row, id, class, op, rev, at }
  cursor = ev.cursor                      // сохраните курсор: watch({ from: cursor }) продолжит после него
  if (ev.id === kettle.id && ev.row.data.price === 2100) break   // break (или sub.close()) — остановить
}
```

- `from` — `'now'` (по умолчанию: только изменения после подписки), `'start'` (весь журнал) или сохранённый курсор.
  `db.watch()` возвращается сразу, а момент «now» подписка берёт первым запросом к базе: запись, сделанная сразу
  после `db.watch()`, может зафиксироваться раньше и в поток не попасть. Поэтому пример выше читает с `'start'`.
- `classes` — только эти классы с потомками; `pollMs` — запасной опрос (1000 мс).
- События идут без потерь и повторов, под правами читателя, в порядке номеров транзакций, а внутри транзакции — в
  порядке записи. Это не порядок фиксации: версии одного объекта сверяйте по `rev`.
- Долгая пишущая транзакция в любой базе кластера задерживает поток: `await sub.lag()` показывает отставание в мс.
- Курсор старше яруса `all` политики хранения — `cursor_expired`: перечитайте текущее состояние и подпишитесь
  с `'now'`.
- Без `LISTEN` (`connect({ listen: false })`) подписка опрашивает журнал.
- Подписка без потерь — это сохранённый курсор: храните `ev.cursor` последнего обработанного события и продолжайте
  с него после перезапуска.

### Кэш результатов

<!-- run: guide -->
```ts
const cached = await db.Product().cache({ ttl: 30 }).rows()   // ответ хранится в памяти процесса 30 с
const stats = db.cache.stats()                                 // { size, hits, misses, stores, raced, … }
```

Кэш включается только явно: `.cache()` в цепочке или `cache: { ttl }` у класса в модели. Как он остаётся верным:

- в ключе ответа — запрос, параметры, сессия, актор и арендатор, поэтому один пользователь не получит ответ другого;
- свои записи сбрасывают ответы изменённых классов сразу после фиксации (с классами каскада), чужие — по сигналу
  базы;
- изменение прав и классов, запись через `db.sql`, погашенная сессия и переподключение слушателя сбрасывают весь
  кэш или ответы сессии;
- срок по умолчанию — 60 секунд; внутри `db.begin()` кэш не работает;
- без `LISTEN` кэш выключен, а `connect({ cache: { ttlOnly: true } })` включает его только по сроку.

Между процессами кэш устаревает на интервал отправки сигналов (`notifyIntervalMs`, 100 мс) плюс доставку;
`db.flushSignals()` отправляет накопленные сигналы сразу. `db.cache.clear()` очищает кэш.

## 13. Эксплуатация

### Обслуживание: `maintain()`

<!-- run: guide -->
```ts
const report = await adm.maintain()     // { sessions, codes, thinned, batches, more, queue, skipped }
```

`maintain()` удаляет истёкшие сессии и одноразовые коды, прореживает журнал по политике хранения и проверяет
очередь сигналов PostgreSQL: заполнение больше половины — предупреждение. Вызывать может системный администратор,
роль с правом `letopis.maintain` или администраторское подключение. Запускает его внешний планировщик
(`letopis maintain`) или сама библиотека: `connect({ maintain: '1h' })`. Из нескольких процессов работает один:
каждая пачка — своя транзакция, и первым делом она берёт транзакционную advisory-блокировку
(`pg_try_advisory_xact_lock`), которая снимается с фиксацией пачки. Если блокировку держит другой процесс, вызов до
первой пачки отвечает `skipped: true`, а между пачками останавливается (продолжит тот процесс) и отчитывается о
сделанном с `more: true`. Сеансовой блокировки нет, поэтому `maintain()` работает за любым пулом, в том числе за
PgBouncer в режиме транзакций.

### Сброс: `reset()`

```ts
await adm.reset({ level: 'tenant', confirm: 'v2.shop', tenant: SHOP })   // sessions | tenant | all
```

Сброс нужен тестам и стендам. Он работает, только если установка поставлена с `up({ allowReset: true })` (иначе
`reset_disabled` даже для System), у вызывающего есть право `letopis.reset`, а `confirm` совпадает с именем схемы
(`confirm_mismatch`). Уровни: `sessions` — все сессии, кроме текущей; `tenant` — данные арендатора; `all` — всё, с заново
положенным системным сидом и новым ключом сервиса. Первая запись журнала после сброса — `reset`.

### Описание модели для людей и ИИ

<!-- run: guide -->
```ts
import { describeText } from 'letopis'

const model = db.describe()           // { schema, tenant, classes: [...], methods }
const modelText = describeText(model) // то же текстом — для llms.txt приложения или подсказки ИИ-агенту
```

`db.describe()` отдаёт описание классов, доступных сессии: поля, концы, ключи, политики и метаданные. Из
командной строки — `letopis describe --format text --out llms.txt`.

### Сырой SQL

<!-- run: guide -->
```ts
const [{ n }] = await db.sql`select count(*)::int as n from "v2.shop".entity where class = 'Product'`
```

`` db.sql`…` `` выполняет запрос одной транзакцией под сессией подключения и RLS: видны те же строки, что и
цепочкам. `db.transaction(fn)` даёт соединение postgres.js на всю транзакцию. При взаимной блокировке и ошибке
сериализации запрос и `fn` повторяются до трёх раз, поэтому `fn` должна выдерживать повтор. Писать сырым SQL тоже
можно — те же триггеры проверят данные, а функции базы `merge` и `inc` доступны приложению.

### Командная строка

```sh
letopis sync <модуль> --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--apply]
letopis types --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--out <файл>]
letopis load <файлы…> --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--class <Класс>]
  [--duplicates error|first|last] [--existing error|skip|update] [--commit-every <N>] [--verify]
letopis verify --dsn <строка> --schema <v2.имя> [--token <токен> | --api-key <ключ>] [--data]
letopis maintain --dsn <строка> --schema <v2.имя> [--token <токен> | --api-key <ключ>] [--batches <N>]
letopis describe --dsn <строка> --schema <v2.имя> (--token <токен> | --api-key <ключ>) [--format json|text] [--out <файл>]
letopis import --from <строка 0.21> --from-schema <v1.имя> --dsn <строка> --schema <v2.имя> [--tenant <имя>] [--keyless <Класс>]…
  [--rename <Старое>=<Новое>]… [--update] [--commit-every <N>] [--partition <имя>]
```

### Наблюдение

- `connect({ onQuery, slowMs })`: хук получает на каждый запрос цепочки режим, классы, длительность, число строк и
  признак медленного запроса; без хука медленный запрос печатает предупреждение.
- `sub.lag()` — отставание подписки; отчёт `maintain()` — заполнение очереди сигналов.
- Горячие цели ссылок (организация, на которую ссылается почти всё) копят блокировки `for key share` и MultiXact,
  как при обычных внешних ключах. Это стоит мониторить.

### Пулы соединений и PgBouncer

С PgBouncer в режиме транзакций `LISTEN` недоступен: `connect({ listen: false })`. Тогда реестр перечитывается через
`db.refresh()`, подписка опрашивает журнал, а кэш результатов выключен или работает по сроку. Подготовленные
операторы работают с PgBouncer 1.21 и новее; со старыми передайте свой пул postgres.js с `prepare: false` в
`connect({ sql })`. `maintain()` берёт транзакционную блокировку в каждой пачке и работает за таким пулом.

<!-- run: guide -->
```ts
await adm.close()
await anna.close()
await svc.close()      // и подключения, полученные через svc.as()
```

## 14. Переход с 0.21

1.0 — новая реализация, а не продолжение 0.21: схема 0.21 не обновляется на месте. 1.0 ставится в новую схему,
данные переносит команда `letopis import`, а код переводится по таблице замен из [MIGRATION.md](MIGRATION.md).
Главные отличия в поведении: `create` не перезаписывает (занятый ключ — `exists`), `count()` считает сущности,
пути — `paths()`, права и изоляция арендаторов включены всегда.

```sh
npx letopis import --from postgres://…/old --from-schema v1.salon --dsn postgres://…/new --schema v2.salon \
  --tenant salon [--keyless booking] [--rename link=link_] [--update] [--commit-every 100000]
```

- Схема 1.0 ставится заранее (`up()`), оба подключения — администраторские. Источник — таблицы 0.21 (`Schema`,
  `Entity`, `Account`, `Credential`, `Resource`, `Rule`) любой базы: PostgreSQL 17 с TimescaleDB или дамп обычных
  таблиц. Пишут загрузчик (режим истории, `existing: 'skip'`, агент `letopis import`) и функции владельца.
- Классы становятся строками `Class` в System. Правила fastest-validator переводятся в JSON Schema (`optional`
  пропускает `null`, `$$strict` → `additionalProperties: false`, `record` → `propertyNames`). Концы — роли по
  имени класса цели, союз всех потомков класса — полиморфный конец. Корни `Entity` и `link` опускаются;
  `description`, `appearance`, `order` переходят в `meta`. Имена, занятые методами 1.0, — `--rename` (по умолчанию
  имя с `_`).
- id: у класса с ключом (правило v5 из 0.21) — v5 от ключа, у класса без ключа — v5 от старого id. Данные System
  переходят в арендатора `--tenant`, аккаунты — в строки `Account`, креды — в `secret` как есть (scrypt, ключи);
  одноразовые коды не переносятся. Ресурсы и правила — в System.
- До первой записи импорт останавливается, если два объекта 0.21 дают один id 1.0 (данные нарушают ключ —
  `--keyless <Класс>`), если ключ менялся между версиями или ссылается на отсутствующий объект. Висячая ссылка
  живой строки — `target_not_found` с объектом 0.21.
- Если загрузчик отклонил данные, ошибка начинается с `import: арендатор …`, а её `detail` — как у загрузчика
  ([«Отчёт и ошибки»](#отчёт-и-ошибки)), только строки названы объектами 0.21: `rows` — нарушения с `class`, `id`
  и `rev` объекта 0.21, `code` и `message`; `total`, `truncated`, `limit` и `complete` — как в отчёте загрузчика;
  `notes` — непереведённые правила.
- Повтор дописывает недостающее без дублей, `--update` — ещё и новые версии изменившихся объектов. Отчёт — JSON в
  конце вывода: объекты и версии по классам в 0.21 и в 1.0, `verify()`, непереведённые правила, классы без ключа и
  uuid в `data`, совпадающие со старыми id (их импорт не переписывает). Код выхода 1, если `verify()` нашёл
  расхождения.

## 18. Ограничения

Здесь собрано то, что letopis 1.0 сознательно не делает или делает с оговорками, и где за поведением нужно следить.

**Платформа**

- Нужен PostgreSQL 18 или новее; обходных путей для 15–17 нет. AWS RDS, Google Cloud SQL, Azure Flexible Server
  и Neon поддерживают 18, а Supabase на октябрь 2026 года — только 15 и 17, поэтому там 1.0 не заработает.
- База — в кодировке UTF8 (`casefold()` и коллация `pg_unicode_fast`). Если новая основная версия PostgreSQL
  обновит таблицы Unicode, уникальный индекс идентификаторов кредов перестраивается командой `reindex`.
- PGlite — одно соединение суперпользователя: без параллельных писателей и `LISTEN`, RLS не действует
  (`allowBypassRls: true`); не замена `postgres:18` для прав, гонок и CI.
- Пул в режиме транзакций (PgBouncer): `LISTEN` недоступен — `connect({ listen: false })`, подписка опрашивает журнал,
  кэш результатов выключен; подготовленные операторы работают с PgBouncer 1.21, со старыми — пул postgres.js
  с `prepare: false` в `connect({ sql })`.
- Символ NUL (`\u0000`) в строках данных невозможен: PostgreSQL не хранит его в `jsonb`; такие данные
  отклоняются ещё при разборе JSON (официальный набор JSON-Schema-Test-Suite, группы «nul characters», пропущены).

**Запись и целостность**

- Построчная запись дороже простой вставки: каждую строку проверяют триггеры (данные, концы, id, журнал, хэш, RLS).
  Построчный `create` медленнее 0.21 на 12–18 % ([раздел 17](#17-производительность)); для массовой записи есть
  загрузчик.
- Удаление, смена класса и смена ключа работают только в `read committed` (`isolation_level`); транзакции
  библиотеки всегда открываются на этом уровне.
- `COPY` в таблицы под RLS PostgreSQL не выполняет; массовая загрузка — только загрузчиком на администраторском
  подключении.
- Загрузчику база доверяет: данные, концы и id загруженных строк проверяет код библиотеки (валидатор на TypeScript),
  а не триггеры; база сверяет только цели вне загрузки, арендаторов и владельцев одним запросом в конце.
  Защита — загрузчик только у администратора, дифференциальные тесты валидатора против базы, `load({ verify: true })`
  и `db.verify({ data: true })`. Администраторское подключение держит отдельный процесс загрузки, а не
  веб-приложение: SQL-инъекция в нём получила бы права владельца.
- Владелец схемы и суперпользователь могут отключить триггеры и изменить что угодно. letopis это не предотвращает,
  а обнаруживает: `verify()` пересчитывает цепочки хэшей, `verify({ data: true })` перепроверяет строки, а якорь
  (хэш всех голов цепочек) стоит хранить вне базы.
- В базе проверяется подмножество JSON Schema: `refine`, `superRefine` и `transform` Zod работают только
  в библиотеке, описание с неизвестным ключевым словом база не примет; `pattern` — ограниченное подмножество
  регулярных выражений, общее для Zod, валидатора и базы. Вывод `z.toJSONSchema()` меняется между версиями Zod:
  в базе хранится уже нормализованная схема, а сухой прогон `syncModels` показывает разницу до применения.
- Ключ — единственный способ уникальности: id вычисляется из значений ключа без нормализации, поэтому одно
  значение в разной записи (email в разном регистре, время с миллисекундами и без) даёт разные id. Формат
  ключевого поля задаёт модель, и база его проверяет.
- Частая смена значения ключа (email, телефон) требует `rekey`. Изменчивые и персональные значения лучше выносить
  в отдельный хаб со связью: id из email подбирается перебором и остаётся в ссылках и журнале даже после
  `anonymize`, а отдельный хаб удаляется вместе со связью через `purge`.
- `create` занятого ключа отвечает `exists` с id, `upsert` без права на существующую строку — отказом `42501`:
  так раскрывается, что ключ занят, но только внутри своего арендатора — у других арендаторов те же ключи дают
  другие id.
- Смена класса и ключа переписывает все входящие ссылки (и рекурсивно — связи, в ключ которых входит этот конец),
  поэтому её цена пропорциональна числу ссылок. Ужесточение описания класса и `rekeyClass` на время проверки или
  переноса приостанавливают запись в семейство.
- `rekeyClass` переносит строки одной транзакцией под исключительной блокировкой семейства, а не пачками:
  между пачками строки со старыми id нарушали бы правило «id — v5 от ключа».
- id v5 ложатся в индекс первичного ключа вразброс; на очень больших таблицах с интенсивной вставкой это заметнее,
  чем с последовательными id.
- Горячие цели ссылок (организация, на которую ссылается почти всё) копят блокировки `for key share` и MultiXact,
  как при обычных внешних ключах; это нужно мониторить. Операции одного кошелька идут друг за другом под
  блокировкой его строки ([раздел 8](#8-транзакции-батчи-и-деньги), «Рецепт: кошелёк»).
- Связь не может называться зарезервированным именем, а хаб с таким именем недостижим как шаг
  ([«Зарезервированные имена»](#зарезервированные-имена)).

**Доступ**

- Сервисный ключ — корень доверия: его компрометация позволяет действовать от имени любого включённого пользователя
  установки, кроме System, сервисов и системных администраторов; правила доступа этот круг не сужают. Ключ
  перевыпускает (`db.auth.issueApiKey`) и отзывает (`db.auth.revokeCredential`) сам сервис по сессии своего ключа или
  системный администратор; своим ключом сервис выпускает себе и новые ключи, поэтому после утечки отзовите все его
  ключи, кроме нового (их список — `credentials`). Последний действующий ключ сервиса не отзывается никем: отключить
  сервис — `enabled: false` у его аккаунта. Один пароль от базы без токена не даёт ничего.
- Пропуск прав открывает клиенту его собственный план (классы и условия правил, которые к нему применимы).
- Сырой SQL без пропуска прав платит за план прав на каждый запрос: 0,3–1,3 мс в зависимости от числа правил.
- Имена концов `User`, `Tenant` (членство), `Group`, `Object` (правило) заняты системными классами во всей схеме.
- Счётчики попыток OTP и TOTP откатываются вместе с транзакцией вызывающего: частоту попыток ограничивает сервис.
- Самостоятельная привязка занятого идентификатора отвечает `acl_denied` — пользователь с недавним входом так
  узнаёт, что идентификатор занят. Изменения прав во всех арендаторах упорядочены одной строкой счётчика.
- Число невидимых строк, мешающих удалению, и существование аккаунта по id (как цели ссылки) не скрываются.
- Метаданные классов (`meta`) видны всем, у кого есть сессия: строки `Class` читает любой. Секретам там не место.
- Прикладная роль может замедлить установку для всех: `LOCK TABLE entity`, advisory-блокировки с предсказуемыми
  ключами, поддельные сигналы `NOTIFY` (лишь сбрасывают кэш), частая смена прав (одна строка счётчика на
  установку). По глобальному номеру журнала видна общая активность записи.

**История, сигналы, кэш**

- Срез `asOf` восстанавливается из журнала; дёшево только текущее состояние. В прореженной части журнала срез
  показывает последнюю сохранённую версию до момента: его точность там равна периоду яруса — дню, неделе, месяцу
  или году. Импорт истории в класс с политикой прореживается сразу, и подписчик может не увидеть старые версии.
- Прореженная часть журнала не доказывает ни полноты истории, ни подлинности старых версий: подмену версии
  старше яруса `all` у класса с политикой `verify()` не отличит от прореживания.
- Журнал без партиций: прореживание удаляет версии пачками, файл таблицы сам не уменьшается (место занимают новые
  версии после autovacuum); вернуть место системе — `VACUUM FULL` или `pg_repack` в окно обслуживания.
- Сигналы раскрывают активность: слушать канал PostgreSQL разрешает любой роли, и по именам классов в сигналах
  видно, когда и в какие классы пишут (ни id, ни арендатора, ни данных в сигнале нет). Поддельный сигнал лишь
  сбросит кэш лишний раз.
- Очередь `NOTIFY` (8 ГБ) общая для кластера: зависший слушатель её переполняет, и тогда транзакции с `NOTIFY`
  падают при фиксации. Библиотека читает сигналы сразу, `maintain()` предупреждает о заполнении больше чем
  наполовину.
- Горизонт подписки общий для кластера: долгая пишущая транзакция задерживает события всех подписчиков
  (`sub.lag()`); длинные операции лучше вести пачками.
- Кэш результатов между процессами устаревает на интервал отправки сигналов (100 мс) плюс доставку и на время
  переподключения слушателя; срок `ttl` — предохранитель.
- Курсор подписки «с этого момента» несёт снимок момента подписки, пока не пройдёт его границу: такой
  курсор длиннее обычного.

**Импорт из 0.21**

- 1.0 — новая major-версия, а не продолжение 0.21: `count()`, `paths()`, `create`, роли, множественные концы
  и `reclass` ведут себя по-новому, данные переносятся импортом ([MIGRATION.md](MIGRATION.md)).
- Импорт: шаги (классы, аккаунты, креды, права, данные каждого арендатора) — отдельные транзакции, источник
  читается в память целиком; владелец строки, не найденный среди аккаунтов, становится арендатором; правила доступа
  0.21 переносятся в System и действуют во всех арендаторах; `onDelete` концов — `cascade`, как удаляла 0.21.
