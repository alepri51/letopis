# Changelog

Формат: [Keep a Changelog](https://keepachangelog.com/), версии — semver.

## [1.2.0-alpha.0] — 2026-10-26

Начало работы над letopis 1.2 по плану `reports/PLAN-LETOPIS-1.1.md` (этапы 4–6): проекторы, агрегаты в базе, MCP.
Версия не публикуется; итоговая запись — `[1.2.0]`.

### Added — этап 4а (проекторы)
- `db.projector(имя, { from, into, version, handle, withBefore, onExpired, batch, pollMs })` — проектор из журнала
  (`lib/src/project.ts`): строит строки производных классов из изменений классов-источников. `run()` догоняет
  журнал и следует за ним до `stop()`, `run({ once: true })` только догоняет; `rebuild()` и `rebuild({ chunked: true })`
  перестраивают проекцию с текущего состояния; `status()` отдаёт состояние, версию, курсор и отставание; `close()`
  останавливает проектор и отписывает его от сигналов. Каждая пачка — одна транзакция: блокировка проектора,
  чекпоинт, изменения журнала, `handle(changes, out)`, запись результатов и сдвиг курсора. Каждое изменение
  применяется ровно один раз, писатель у проектора один. Только на администраторском подключении (иначе
  `admin_required`).
- Опция класса `derivedBy: 'имя-проектора'`: строки класса пишет только этот проектор. Опция наследуется, потомок её
  не меняет; концы производного класса — только `onDelete: 'cascade'` или `'unset'`; системный класс производным не
  бывает; концы других классов на производный класс не ведут. Опцию показывают реестр, `db.describe()` и
  `describeText()`.
- Функции базы `lib/sql/88-derived.sql` (только для роли владельца): `projector_state` (чекпоинт — строка `secret`
  вида `PROJECTOR`), `projector_advance` (сдвиг чекпоинта, только если курсор не изменился), `derived_split`,
  `derived_id`, `derived_apply` (запись результатов пачки: `upsert`, `inc`, `delete`), `derived_clear` (удаление
  строк проектора перед перестройкой).
- Код ошибки базы `LT021` `derived_class`: строку производного класса пишет, правит или удаляет не его проектор,
  либо конец ведёт на такую строку.
- Коды библиотеки `rebuild_required` (проекция построена другой версией проектора) и `projector_busy` (перестройку
  не начать: проектор сейчас работает в другом процессе).
- Зарезервированное имя корня `projector`; типы `Projector`, `ProjectorOptions`, `ProjectorChange`, `ProjectorOut`,
  `ProjectorRow`, `ProjectorReport`, `ProjectorStatus`.

### Changed — этап 4а
- Функции кредов (`auth_credentials`, `auth_revoke_credential`, `auth_set_flags`) не видят вид `PROJECTOR`, а
  `auth_kind_ok` не принимает его как вид кредов.
- `targets_bad` отличает производную цель: возвращает `!роль`, и триггеры записи, `check_links` и проверка базы в
  загрузчике отвечают `derived_class`, а не `target_not_found`.
- Загрузчик (`db.load()` и первая заливка) отклоняет строки производных классов и ссылки на их строки —
  `derived_class` в отчёте.
- `restore`, `reclass`, `rekey` и `rekeyClass` строк производного класса — `derived_class`.
- Ревью коммита: проектор работает с арендаторами, у которых каждый класс `into` помечен его `derivedBy`, и
  пропускает изменения остальных — одноимённый класс без пометки у другого арендатора больше не останавливает его для
  всех; класс System, который становится производным, сверяется со ссылками всех арендаторов; описание со ссылкой и
  пометка `derivedBy` идут под блокировками семейства и не проходят параллельно мимо друг друга; источники и
  результаты проектора — свои у каждого арендатора: имя класса одного арендатора не меняет набор источников другого.
- Правка `derivedBy` в описании класса — не безопасное изменение (`class_change_safe`): её проверяют как ужесточение.

### Added — этап 4б (агрегаты в базе)
- Опция класса `aggregate: { поле: { sum: 'поле' | count: true, of: 'Класс', via: 'роль', where?: JSON Schema } }`:
  поле держит сама база — сумма поля или число живых строк класса-источника (с потомками) того же арендатора, чей
  одиночный конец `via` ведёт на строку и чьи данные проходят `where`. Строка System в агрегат не входит. Опция
  наследуется, потомок заменяет её целиком; её показывают реестр (`ClassInfo.aggregate`), `db.describe()` и
  `describeText()`; в `letopis/model` — `ClassDef.aggregate` и тип `AggregateDef`, экспорт типа `AggregateInfo`.
- Триггеры `entity_total_ai`, `entity_total_au`, `entity_total_ad` (`lib/sql/88-derived.sql`): после оператора, с
  переходными таблицами, без условия `WHEN` — срабатывают и для владельца (каскад удаления, `restore`, `reclass`,
  `rekey`, удаление аккаунта, загрузчик), `enable always`. Вклады строк оператора складываются по цели, цели
  блокируются в порядке id, итог проверяет описание класса цели (`minimum: 0` → `invalid_data`), версия цели —
  `sys_update` с автором и причиной операции. Новая цель оператора (вставка, `restore`, смена класса) считается
  целиком из живых источников в ту же версию. Перенос строки (`move_row`) копит вклады до своего конца и применяет их
  одним итогом — промежуточная сумма не выходит за правило класса.
- Проверки описания агрегата (`invalid_class`): поле есть в схеме, числовое и не в ключе; ровно одно из `sum` и
  `count`; конец `via` источника одиночный и принимает класс цели; поле `sum` — число; нет цикла агрегатов; цель и
  источник не системные и не производные; агрегат арендатора не считает классы System. Источник, описанный после
  цели, сверяется при появлении; его класс получает метку `resolved.aggregatedBy`.
- `db.rebuildAggregates(класс)` — ремонт: поле класса и его потомков во всех арендаторах заново из живых источников
  под исключительными блокировками, версия только у исправленных; возвращает их число. Только администраторское
  подключение (иначе `admin_required`); функция владельца `rebuild_aggregates`. Зарезервированное имя корня
  `rebuildAggregates`.
- `verify({ data: true })` сообщает расхождения агрегатов: `{ id, class, field, stored, expected, problem }`.
- Код ошибки базы `LT022` `aggregate_field`: приложение передало или изменило агрегатное поле.

### Changed — этап 4б
- Агрегатное поле пишет только база: `trg_entity_bi` отклоняет переданное значение и ставит 0 до умолчаний и
  проверки, `trg_entity_bu` отклоняет изменённое, а при замене данных целиком без поля возвращает прежнее значение;
  `reclass()` и `rekey()` отклоняют его в данных. Библиотека отвечает `aggregate_field` до отправки (`create`,
  `upsert`, `update`, `reclass`, `rekey`), а `upsert` заменяет данные без агрегатных полей
  (`excluded.data - поля`).
- Добавить или изменить агрегат — ужесточение (`class_change_safe`): исключительные блокировки семейства цели и
  семейств источников, пересчёт поля у всех целей (`class_evolve`), метки источников заново (`agg_mark`).
- Загрузчик ставит агрегатные поля в 0 (поле посчитает триггер), при `existing: 'update'` сохраняет прежние значения
  (`agg_keep`) и пишет журнал пачки раньше строк: новая цель получает итог в ту же версию. Первая заливка считает
  поле функцией `agg_fill` — одним оператором на агрегат до перестройки индексов, в ту же версию в `entity` и `log`.
- `restore()` и `sys_update` со сменой класса пишут в журнал строку таблицы, а не `returning`: агрегатные поля
  досчитаны триггером; `sys_create` пишет журнал раньше строки. `reset({ level: 'tenant' })` агрегаты не
  пересчитывает: строки арендатора уходят вместе с целями.
- Ревью коммита этапа 4б: агрегат считают функции владельца по всем строкам источника, без прав чтения, и описание с
  `where` выдавало суммы и счётчики по строкам, которые автору не видны. Теперь строки попадают в агрегат только с
  ведома того, кто читает их все. Описать или изменить агрегат может только тот, у кого право READ без условий на все
  строки каждого класса-источника (класс `of` и его потомки) — и свой агрегат, и унаследованный (новый потомок цели,
  смена `parent`); неизменённый агрегат при правке описания не проверяется. Сделать класс источником (новый класс, смена `parent`, источник после цели) можно только с таким правом
  на этот класс и его потомков — до правки, по прежним предкам, и после. Иначе `acl_denied` (`class_admit`, а для
  нового класса и новых предков — `agg_source_admit` в триггерах после оператора и в `class_evolve`). Агрегат класса
  арендатора считает только классы своего арендатора — везде одинаково (`agg_prepare`, `agg_classes`, `agg_compute`,
  `agg_apply`, `agg_fill`, `agg_cycle`): класс System с именем `of` его источником не бывает. Поэтому такой агрегат
  больше не останавливает установку и правку классов System (`agg_source` его пропускает, а не отвечает
  `invalid_class`), не расходится с `verify` и `rebuildAggregates` и не мешает арендатору править цель.

### Tests — этап 4б

## [1.1.0] — 2026-10-11

letopis 1.1 по плану `reports/PLAN-LETOPIS-1.1.md` (редакция 5, этапы 0–3 и контрольная точка А): `diff` и `blame`
по журналу с причиной изменения, режимы сигналов, первая заливка; ревью безопасности №1. Совместимость с 1.0 не
сохраняется: процессам 1.0 и 1.1 не нужно работать с одной схемой; обновление схемы 1.0.1 (`up({ upgrade: true })`,
миграция `0006`) тестом не проверяется.

### Changed — этап 0 (подготовка)
- Версия `1.1.0` (во время работы — `1.1.0-alpha.0`, не публиковалась).
- `db.describe()` и `describeText()` отдают условия класса по нескольким полям `anyOf` и `oneOf` (из
  `resolved.schema`, с учётом наследования). Раньше агент, читавший описание, их не видел.

- Бенч против 1.0.1 (`bench/vs-101.bench.mjs`, dev-зависимость `letopis-1` = `npm:letopis@1.0.1`): засевка полигона
  salon, загрузка без истории, построчный `create`, чтение по ключу, цепочка, `asOf`, двадцать писателей,

- Карта: заготовки карточек модулей M-DERIVED и M-MCP (этапы 4 и 5 плана 1.1).

### Added — этап 1 (`diff`, `blame`, причина изменения)
- Терминалы `diff({ from, to, follow })` и `blame({ at, limit })`: что изменилось между двумя версиями или моментами
  и кто, когда и почему последним менял каждое поле. Пути — массивы с разделом строки в начале (`data`, `links`,
  `tags`, `owner`, `class`); объекты данных — по ключам, массивы — целиком, множественные концы и теги — по
  элементам. `exact: false` и `complete: false` — история неполная (прореживание, обрезка, невидимые версии,
  предел `limit`, по умолчанию 1000 версий).
- Функции базы `jsonb_changes`, `version_changes`, `version_leaves`, `diff_versions`, `blame`
  (`lib/sql/75-history.sql`) с правами вызывающего: сырой SQL получает то же под RLS журнала.
- Причина изменения из библиотеки: опция `reason` у `create`, `update`, `upsert`, `delete`, `anonymize`, `reclass`,
  `restore`, `purge`, `rekey`; `db.begin({ reason })` и `db.batch(имя, { reason })` — для всех операций блока.
  В 1.0 причину мог задать только сырой SQL настройкой `letopis.reason`.
- Зарезервированные имена `diff` и `blame`.
- Замер `bench/history.bench.mjs` (`docs/checkpoint-1.1.md`): `blame` по 1000 версиям — около 0,26–0,29 с, по
  10 000 — 1,5 с; `diff` — 4–12 мс.

### Added — этап 1б (колонка изменённых путей, ревизия движка 6)
- Колонка журнала `changed`: пути изменения каждой версии против предыдущей. `blame` берёт их вместо сравнения
  соседних версий; версии без путей (создание, загрузчик, импорт) досчитывает сравнением. Миграция

- `blame` и `diff_versions` — без JIT (`set jit = off`), соседние версии — окном `lead()`: `blame` по 1000 версиям —
  13,5 мс вместо 264, по 10 000 — 0,12 с вместо 1,5 (`docs/checkpoint-1.1.md`).

### Tests — этап 1

  `roles` — новые функции приложения в белом списке.

### Added — этап 2 (режимы сигналов)
- Режим сигналов установки `up({ signals })`: `class` (по умолчанию, как в 1.0) — имя класса, `tenant` — имя класса
  и токен арендатора, `opaque` — только токены, `none` — сигналов нет. Токен — первые 96 бит HMAC-SHA256 на ключе
  сигналов, выведенном из ключа строки `secret` с id System: без ключа псевдоним не сопоставить с именем, а
  одинаковые сигналы транзакции PostgreSQL по-прежнему склеивает. Режим хранится в схеме (`meta` строки ключа):
  повторный `up()` без опции его не меняет, `reset({ all })` сохраняет.
- Ключ сигналов — функция владельца `signal_key()` и право `letopis.signals` (системный сид выдаёт его сервисам:
  ресурс `signals:API`, правило для `service:ACCOUNT`). Процесс с ключом сбрасывает кэш с точностью до арендатора
  (строки System — во всех) и узнаёт классы по токенам; процесс без ключа сбрасывает класс во всех арендаторах, а в
  режиме `opaque` — весь кэш на любой сигнал. Реестр, ключ и пропуска прав по `*`, незнакомым токенам, нагрузке не
  своего режима (и у процесса без ключа в `opaque` — по любому сигналу) перечитываются не чаще раза в 5 с.
- Режим `none`: без LISTEN и без отправки сигналов, кэш только по сроку (`ttlOnly`), подписка опрашивает журнал,
  реестр раз в 5 с сверяет отпечаток классов `class_stamp()`.
- Подписка просыпается только от своих классов и своего арендатора; без ключа — от любого сигнала, кроме сессий.
- `UpResult.signals`, `UpResult.warnings`, `InstallResult.signals`; `up()` предупреждает о PostgreSQL ниже 18.2
  (сервер мог усечь CLOG, который ещё нужен непрочитанным сигналам), `checkServer()` возвращает предупреждения.
  Тип `SignalMode`.
- Функции базы `signal(классы, арендаторы)` вместо `signal(классы)`, `signal_raw()`, `signal_token()`,
  `signal_mode()`, `signal_key()`, `class_stamp()`; маркер установщика `@SIGNALS@`.
- Замер `bench/signals.bench.mjs` (`docs/checkpoint-1.1.md`): цены режима в скорости записи не видно на фоне шума;
  `signal()` в режимах `tenant` и `opaque` дороже на 15 и 26 мкс на оператор; при записи одного арендатора ответы
  другого остаются в кэше процесса с ключом (100 % попаданий против 0 % в режиме `class`).

### Changed — этап 2

  импорт больше не зовут `pg_notify` сами); сессии и сброс — `signal_raw()`. `reset({ all })` шлёт `*` и

  пришедший во время обрыва, потерян. Перечитывания реестра по сигналу `Class` не идут одновременно: сигналы во
  время перечитывания сливаются в одно следующее.
- Общий список классов прав — `ACL_CLASS_NAMES` в `types.ts` (был продублирован в `cache.ts` и `load.ts`).
- Бенчи `core-concurrency`, `core-write`, `core-notify`, `core-load` — на `signal_raw()` и новую `signal()`. Заодно
  `core-concurrency` и `core-write` снова запускаются: их подмены `targets_bad` искали сигнатуру с двумя параметрами,
  а замена `trg_entity_ai` в `core-write` была без `security definer` (сломались ещё до выпуска 1.0.0).

### Fixed — этап 2

## [1.0.0] — 2026-10-09

letopis 1.0 — новая реализация хранилища по плану `reports/PLAN-LETOPIS-1.0.md` (редакция 8), основанному на
предложении «Свод» (`reports/PROPOSAL-SVOD.md`). Целостность, история, изоляция арендаторов и права проверяет
сама база — и для библиотеки, и для сырого SQL. Переход с 0.21 — [MIGRATION.md](MIGRATION.md): импорт данных
командой `letopis import` и таблица замен API. Подробная запись по этапам — ниже, в `[1.0.0-alpha.0]`.

### BREAKING — платформа и хранение
- PostgreSQL 18 и новее, Node 22 и новее. TimescaleDB, Redis и Docker не нужны; рантайм-зависимость одна —
  `postgres`; fastest-validator заменён JSON Schema, модели на Zod 4 — необязательная peer-зависимость
  (подпуть `letopis/model`).
- Три таблицы: `entity` (текущие версии), `log` (журнал) и приватная `secret` (креды и сессии) вместо `Schema`,
  `Entity`, `Account`, `Credential`, `Resource`, `Rule`. Классы, аккаунты, ресурсы и правила — строки системных
  классов. Колонки `partition` нет: отдельные пространства — отдельные схемы `v2.<имя>`. Схема 0.21 на месте не
  обновляется — данные переносит `letopis import`.
- Журнал без партиций и политик TimescaleDB; хранение истории — политика «все версии — по дню — по неделе — по
  месяцу — по году» (`history: { all, daily, weekly, monthly, yearly, tz }`), прореживает `maintain()`.
  `compact()` снят: обрезка — `db.trimHistory()`, отказ от истории — `history: false`, который теперь отключает
  и `versions`, `asOf`, `restore`, события подписки.
- `up()` без Docker и без сидов по умолчанию: демо-домен — только `seeds: ['booking']`; схема — `v2.<имя>`.

### BREAKING — идентификаторы и уникальность
- Только v5: id объекта класса с ключом — v5 от имени класса и значений ключа как есть в пространстве арендатора
  (`idOf`); у класса без ключа id выдаёт база. v4 и v7, `generate` и `from` ушли; `uuidv7()` и `LETOPIS_NS` —
  охранники `removed`. Переданный id должен совпасть с вычисленным (`id_mismatch`); класс без ключа id не
  принимает (`id_from_db`).
- Уникальность — только ключ, правил `unique` нет; неявного ключа связи по её концам нет.
- Ключевые поля, id, арендатор и владелец обычной правкой не меняются (`immutable_key`): новый ключ — `rekey()`
  или `db.rekeyClass()`, оба выдают новые id и переводят ссылки. В 0.21 правка ключа проходила, но id переставал
  ему соответствовать.
- Смена класса — глагол `reclass()`: у класса без ключа id сохраняется, у класса с ключом вычисляется заново,
  ссылки переводятся; правка класса обычной записью — `use_reclass`.

### BREAKING — запись и транзакции
- `create` — обычная вставка: занятый ключ — `exists` (`detail.id`), а не идемпотентный PUT. Замена целиком —
  отдельный глагол `upsert`, только для класса с ключом (`no_key`) и только целым объектом.
- `update` по-прежнему не создаёт; затронуто меньше строк, чем нашёл шаг, — откат плана с `target_not_found`,
  `conflict` или `acl_denied`.
- Ошибка любого запроса в `db.begin()` ломает транзакцию (в том числе `exists` и `conflict`): следующие вызовы и
  `commit()` бросают исходную ошибку, `rollback()` проходит; обрыв связи во время `COMMIT` — `commit_unknown`.
  В 0.21 повторный `commit` после ошибки молча проходил.
- Каскад удаления — в триггере после оператора; удаление и создание одного id одним оператором —
  `recreated_in_statement`; удаление, смена класса и ключа — только в `read committed` (`isolation_level`).
- `db.as()` асинхронный и принимает арендатора: `await db.as(аккаунт, { tenant, owner })`.
- `batch.execute()` — охранник с заменой `batch.run()`.

### BREAKING — чтение
- `count()` и агрегаты считают сущности последнего шага, а не пути; пути — `count({ paths: true })`; `run()` и
  `execute()` сняты — пути отдаёт `paths()`.
- `account()` снят: арендатор — свойство сессии (`connect({ token | apiKey })`, `db.as(…, { tenant })`,
  `db.auth.switch()`).
- Строка ответа: `tenant` вместо `account`, `at` вместо `updated`; новые поля `rev`, `author`, `op`, `agent`,
  `reason`, `moved`.

### BREAKING — доступ
- Изоляция арендаторов и права действуют всегда — политиками RLS, для библиотеки и сырого SQL; права по умолчанию
  запрещают. Опции `connect()` `partition`, `enforceAccount`, `enforceAcl`, `container`, `image`, `dataDir`,
  `redisPort`, `version` — охранники `removed`. Роль, обходящая RLS, подключается только с `allowBypassRls`
  (иначе `bypass_rls`).
- Сессии — в PostgreSQL: `db.auth.sessions(store)` снят (`sessionFor`, `refresh`, `revoke`, `revokeAll`);
  `enabled: false` гасит и живые сессии.
- Фасады `db.accounts`, `db.credentials`, `db.resources`, `db.rules` сняты — системные классы `Account`,
  `Resource`, `rule`, `member` и `db.auth`; `accounts.purge` — `db.auth.purgeAccount()`. `db.reloadSchema()` и
  `db.acl.reload()` сняты: реестр и права обновляются сами по сигналу базы (принудительно — `db.refresh()`).
- Системный сид — только общие группы и системные права; ресурсы продуктов (`chrono`, `payment`, `billing`,
  `geo`, `shop`) в библиотеку не входят.

### BREAKING — события, классы, ошибки
- `watch(cb)` и `watch(класс, cb)` сняты: `db.watch({ from, classes })` — асинхронный итератор с курсором, без
  потерь и повторов.
- Классы описываются моделями на Zod (`hub`, `link`, `one`, `many`) или строками `Class` с JSON Schema;
  `db.schema.define()` и CLI `schema-sync`, `gen-types` заменены `letopis sync` и `letopis types`; `db.schema` —
  имя схемы.
- Зарезервированы только имена методов цепочки и корня (`RESERVED_CLASS_NAMES`), а не 52 имени 0.21.
- Ошибки — `LetopisError`, текст `letopis: <код>: <сообщение>`, строчный код в `err.code`; ошибки базы —
  SQLSTATE `LT001`–`LT020` (`error_catalog()`).

### Отличия от предложения «Свод» (§3 плана)
PostgreSQL 18 вместо 15; одна приватная таблица `secret` вместо `credential` и `session`; журнал без партиций с
политикой хранения; v5 — класс и значения ключа как есть, без канонизации и неявного ключа связи; только ключ
вместо правил `unique`; `create` и `upsert` — разные глаголы; `rekey` для ключевых полей; приращение `inc`;
`{ rev }` с кодом `conflict` и правилом одной цели; сломанная транзакция и `commit_unknown`; `forUpdate()`;
загрузчик через `COPY` от роли владельца; индексы под RLS и срезы `asOf` через функции владельца `find_ids()`;
план прав вместо таблицы-снимка; журнал защищён правами, а не триггерами; каскад после оператора; хэш —
генерируемая колонка; проверка данных компиляцией JSON Schema в jsonpath; `NOTIFY` с именем класса; кэш плана и
результатов; свободный объект `meta`; имперсонация через `letopis.account`; продление сессии отдельным вызовом;
выпуск — letopis 1.0.0, а не новый пакет.

### Added — после этапа 8 (решение владельца на точке В)
- `up({ tenant })` и `createTenant(sql, schema, { name, grantAll, user })`: первый арендатор (аккаунт в System, правило «аутентифицированным можно всё») и его пользователь (членство с ролью `owner`, пароль, сессия в арендаторе) без своего сида; повтор ничего не дублирует (id — v5 от имени и логина).

После верного пароля или найденной учётной записи база проверяет код той же функцией, что `verifyTotp` (`auth_verify_totp`: право `auth.totp`, окно — шаг в каждую сторону, повтор шага отклоняется, счётчик неудач и блокировка общие), и выдаёт сессию со способами `[вид, 'TOTP']` — по ней пользователь с TOTP меняет свои креды сам. ### Fixed — после этапа 8 (код)
- Подмена актора в `db.batch()`: очередь была общей для всех фасадов подключения, и `run()` одного фасада исполнял от своего имени планы, поставленные другим (`db.as()`, `db.begin()`). Теперь очередь своя у каждого фасада, и план исполняется от имени поставившего.
- Курсор `after()` проверяется по типу поля `sort` до запроса: значение не того типа, курсор без `v` или `id` не uuid — `invalid_query`. Раньше курсор без `v` вешал соединение, а логический курсор по полю без описания давал ошибку сервера.
- Ошибка загрузчика называет точное число нарушений («и ещё N»; «не меньше N» с причинами, если проверены не все строки), а в `detail` к первым 100 нарушениям в `rows` добавлены `total`, `truncated`, `limit` и `complete`.
- Маска шаблона `Resource` не строкой (`categories`, `roles`, `endpoint`, `class`) совпадала со всеми, как в 0.21: группа `{ roles: ['staff'] }` с разрешающим правилом давала право любому аккаунту, маска `class` не строкой — на все классы. Теперь описание класса `Resource` требует строки, и маску не строкой отклоняет `invalid_data` — при записи библиотекой, сырым SQL и загрузчиком, в том числе при импорте. Строка, записанная в обход проверки, разрешений не даёт, а запрет по ней действует на всех: `acl_set_ok` и `acl_class_ok` на не строку отвечают null, `acl_rules` и `acl_plan_for` отбрасывают по ней разрешение. Новое описание попадает в свежую установку и после `reset({ all })`; в существующей схеме исправленное сопоставление действует после повторного `up()`.
- Ключи сервиса: по сессии своего ключа сервис не мог ни выпустить себе новый ключ, ни отозвать старый (только системный администратор), а отзыв любого креда гасил все сессии аккаунта — ротация без простоя не получалась. Теперь свои `APIKEY` и `KEYSECRET` сервис выпускает и отзывает сам по сессии своего ключа (`auth_service_self`); сессия по ключу помнит его id (`meta.cred`), и отзыв ключа гасит только его сессии и старые сессии того же вида без отметки (`auth_kill_cred`), `keepCurrent` — как у прочих кредов. Последний действующий ключ сервиса не отзывается никем — `acl_denied` «последний действующий ключ сервиса не отзывается: сначала выпустите новый»; отключить сервис — `enabled: false`.
- TOTP: пользователю с включённым TOTP свои креды было не сменить — база требует сессию с пройденным TOTP, а библиотека такую не выдавала. Теперь её выдают `verifyPassword` и `lookup` с `totp` (см. «Added — после этапа 8»).
- `maintain()` за пулом в режиме транзакций (PgBouncer) молча вставал: сеансовая advisory-блокировка оставалась на серверном соединении, которое пул отдаёт другим клиентам, — `skipped` у всех. Теперь каждая пачка в своей транзакции первым делом берёт транзакционную блокировку (`pg_try_advisory_xact_lock`), её снимает фиксация пачки; блокировка занята до первой пачки — `skipped`, между пачками — остановка с `more: true`.
- `after()` по полю данных терял строки с `null` или без поля: сравнение с `null` не проходило, а после строки с `null` следующая страница была пустой. Теперь `null` — после всех значений при возрастании и перед ними при убывании, как в `order by`; курсор `null` работает.
- `letopis import`: ошибка загрузчика в данных арендатора теряла `total`, `truncated`, `limit` и `complete` отчёта загрузчика — теперь они доходят вместе со строками 0.21 в `rows` и `notes`.
- `createTenant` и `up({ tenant })` после удаления арендатора, аккаунта пользователя или членства падали с `23505` (`log_id_rev`): `sys_create` пишет версию 1, а её занимает история. Теперь — `invalid_data` с объяснением и советом вернуть строку `restore()`, транзакция откатывается целиком; повтор удалённое не воскрешает.

### Fixed — документация
- В `README.md` стоял байт NUL: grep и поисковые инструменты считали файл двоичным и пропускали его.
- Примеры шпаргалки, которые в прежнем виде падали: строгий режим `{ rev }` с устаревшим номером версии, создание уже существующего членства (теперь — правка ролей), подписка без условия выхода и неопределённые переменные.
- Утверждения прежних README и шпаргалки, которые расходились с кодом (ревизия против кода и тестов): имперсонация не проверяет видимость пользователя по правилам доступа; `deep()` по умолчанию — 32 уровня; `refresh()` возвращает новое время истечения, а не токен; `verifyPassword` по умолчанию пускает только по подтверждённому креду; подписка отдаёт события в порядке номеров транзакций, а не фиксации; подключение к PGlite требует `allowBypassRls`; `update`, не нашедший целей, отвечает пустым списком, а не `target_not_found`; вес правила арендатора больше 999 урезается, а не отклоняется.
- Маска группы (`Resource` категории `ACCOUNT`) задаётся только строкой; маску не строкой теперь отклоняет база (см. «Fixed — после этапа 8 (код)»).

### Security — итоговое ревью безопасности (этап 8)
- Блокировка семейства классов (`family_lock`) — по арендатору корневого класса: ужесточение класса или `rekeyClass` в одном арендаторе больше не останавливает запись в одноимённый класс других арендаторов.
- `account_purge` проверяет право до поиска аккаунта: без права ответ всегда `acl_denied` — существование аккаунта не раскрывается.
- `restore` и `purge` блокируют запись журнала только своего арендатора: чужой id нельзя ни заблокировать, ни заметить по ожиданию.
- Маска `Resource` не строкой больше не открывает права всем: такую строку база не записывает (`invalid_data`), а записанная в обход проверки разрешений не даёт (см. «Fixed — после этапа 8 (код)»).
- Тест `security-final`.

## [0.21.0] — 2026-08-23

### Added — no-history классы: `meta.history: false` (DDL_REVISION 2)

Класс, помеченный в `Schema.meta` флагом `history: false`, хранит **одну актуальную строку
на id**: новый AFTER INSERT триггер `entity_collapse` после каждой вставки физически удаляет
более старые версии этого id. Дефолт (`history` отсутствует или `true`) — прежнее поведение,
все версии копятся; фича строго opt-in, существующие схемы и сервисы не затронуты.

Зачем: у мутабельных статус-сущностей (очереди, outbox — статус живёт в `data`) история
версий делает jsonb-фильтры неселективными: GIN по `data` матчит каждую версию, что
когда-либо была в искомом статусе, и сканы растут O(вся история). Под `history:false`
фильтр матчит только актуальные строки — скан остаётся O(активных) при любом росте данных.

Механика:
- `entity_collapse` — AFTER INSERT (как `entity_notify`; collapse по алфавиту раньше —
  один NOTIFY на выжившую строку). In-place UPDATE не годится: Entity — гипертаблица по
  `updated` (перенос между чанками), а `entity_notify` слушает только INSERT.
- DELETE старых версий идёт под `letopis.purge='on'` (save+restore флага):
  `entity_delete` пропущен — без tombstone и каскада. Advisory-lock тем же ключом,
  что `entity_delete`/`purge`, сериализует конкурентные вставки одного id.
- `.delete()` под no-history оставляет один tombstone (его `updated` строго больше),
  `purge()` работает как прежде.
- Новая серверная функция `compact(partition, class) → bigint` — разовая чистка УЖЕ
  накопленной истории при переводе класса на `history:false` (оставить последнюю версию
  каждого id, вернуть число удалённых). Идемпотентна. После вызова — `ANALYZE "Entity"`.
- `ClassDef.history` в реестре; `.versions()`/`.asOf()` по no-history классу предупреждают
  в console.warn (один раз на класс+метод за процесс) — результат не отражает историю.

Накат на существующие схемы: `up({ upgrade: true })` или `node db/apply.mjs --upgrade`
(файл идемпотентен, данные целы); до наката `connect()` предупредит о ревизии (1 → 2).

- `test/no-history.test.ts` — 7 сцен: реестр, схлопывание, соседний history-класс,
  NOTIFY, tombstone, `compact()`, warning; суммарно 205 тестов.

### Fixed — `ANALYZE` при накате схемы: чтения были медленнее на порядок

`up()` и `db/apply.mjs` теперь вызывают `ANALYZE "<схема>"."Entity"` после наката DDL и сидов.

`Entity` — гипертаблица: строки лежат в чанках, у родительской таблицы своих строк нет. Пока
`ANALYZE` по ней не прошёл, планировщик берёт дефолт «200 уникальных `id`». Ядро всех чтений
либы — semi-join с подзапросом кандидатов (`e.id IN (SELECT c.id FROM Entity c WHERE …)`), и на
такой оценке он выбирает `Nested Loop` вместо `Merge Semi Join`, с уходом хеша и сортировки на
диск. Замерено на полигоне 980k строк:

| Сцена | без статистики | после `ANALYZE` | |
|---|---|---|---|
| `count()` класса под изоляцией арендатора | 57.6 s | 3.2 s | ×18 |
| фильтр `rows` limit 100 по 440k | 1371 ms | 11 ms | ×126 |
| `count()` класса без фильтра | 2981 ms | 1373 ms | ×2.2 |

Тайминги README §14 и §9.2 перемерены на проанализированной базе. Своя массовая вставка
(`COPY`, миграция, генератор) требует `ANALYZE` вручную — это отдельная грабля в
`AGENT-CHEATSHEET.md` (#17) и новая секция README §14.1.

Заодно вычищен доковый дрейф в §14: строка «обход `запись→Мастер` по всему классу» показывала
≈6 с с версии 0.17.0, где полигон был 250 000 записей / 613 тыс. строк, и переезд на
440 006 / 980 328 её не обновил — настоящее значение ≈30 с. Стоимость этой сцены = `строки
внешнего шага × чанки` (одна проба — 0.924 мс / 80 буферов при 13 чанках), потому что
forward-hop идёт коррелированным `JOIN LATERAL` с пробой по всем чанкам. Первое объяснение
в §14 («планировщик недооценивает внешнюю сторону и не ставит `Memoize`») **снято как
неверное**: подстановка класса литералом и `SET enable_nestloop = off` план не меняют, дело в
самой форме — корреляция внутри подзапроса с `DISTINCT ON` не раскоррелируется и не
мемоизируется. Некоррелированный join измерен и хуже в 18 раз (561 с), так что форма
оставлена как есть; лечится стороной старта цепочки — `db.запись(id).Мастер()` 7.5 мс и
`db.Мастер(id).запись()` 11.7 мс против 30 с у обхода всего класса.

Попутно исправлен `bench/acl.bench.mjs`: его колонки были несравнимы — `base` шёл без изоляции
арендатора, а ACL-хендлы с ней, из-за чего бенч приписывал авторизации до 18× чужой цены.
Теперь все три режима с `enforceAccount: false`, и видно настоящее: **ACL бесплатен на всех
сценах** (отличия в пределах шума). Цена изоляции измеряется отдельно и зависит от доли
арендатора в классе — на 10-арендаторном полигоне она ускоряет чтение до 27× (README §10.6).

### BREAKING — арендатор стал свойством ВЫЗОВА: `db.as(account)`, опции `connect({ account })` больше нет

Из `ConnectOpts` **удалены `account` и `owner`**. Аккаунт на подключении — это модель
«одно соединение = один тенант», а для веб-приложения она неверна: пул общий, арендатор
меняется от запроса к запросу. Теперь подключение безличное, а идентичность даёт хендл:

```ts
const db = await connect({ dsn, schema })     // было: connect({ …, account: X })
const t  = await db.as(accountId)             // стало: имя вызова, хендл того же пула
await t.Клиент().rows()
```

`db.as(account, { owner? })` клонирует контекст на **том же пуле** (нового соединения не
открывает, SQL не шлёт), поэтому его нормально создавать на каждый HTTP-запрос. `close()`
по-прежнему один на пул. Батчи с корня в scope не наследуются: очередь планов, общая для
разных арендаторов, была бы утечкой записи.

Под `enforceAcl` **правила компилятся под субъекта scope** — у каждого `db.as()` свой
энфорсер. Это не оптимизация, а требование корректности: ключ memo в `acl.ts` — «класс +
операция», без аккаунта, так что переиспользование одного энфорсера двумя арендаторами
отдало бы второму решения первого. Закреплено тестом (`acl.test.ts`, «memo энфорсера не
течёт между scope одного пула»); проверено негативно — с общим энфорсером тест падает.

`enforceAccount` — **`true`** по умолчанию: чтения фильтруются по `account` scope-хендла,
записи к нему пришпилены. Забыть флаг было слишком легко, а цена забывчивости — чужие
строки в выдаче без всякой ошибки. Теперь и забыть `db.as()` нельзя: с безличного корня
чтение/запись бросают

```
letopis: enforceAccount is on — call db.as(account) to name the tenant of this call,
or connect({ enforceAccount: false }) for admin access
```

Админским и сервисным подключениям (миграции, отчёты по всем арендаторам, дев-скрипты)
нужен явный `connect({ …, enforceAccount: false })` — там колонку `account` закрывает
System-аккаунт схемы, как раньше.

Смысл модификатора `.account()` не изменился: это точечный фильтр/значение одного шага;
на scope-хендле чужое значение — ошибка `pinned`.

`enforceAcl` остаётся **`false`** (opt-in): включённый по умолчанию deny-by-default без
настроенных `Resource`/`Rule` давал бы пустые выборки. Вместо смены дефолта `connect()`
печатает предупреждение один раз на процесс: авторизация не проверяется — это должно быть
шумно, а не молча.

**Миграция.** `connect({ …, account: X })` → `(await connect({ … })).as(X)`;
`connect({ …, account: X, owner: Y })` → `.as(X, { owner: Y })`; подключения, которые
работали без `account` и должны видеть всё, — `connect({ …, enforceAccount: false })`.
`accounts.purge(id)` требует scoped-хендла: `(await db.as(caller)).accounts.purge(id)`.

### BREAKING — снят охранник `.link()`

`case 'link'` в цепочке удалён. Он затенял **реальный класс схемы**: в демо-домене `link`
(алиас `связь`) — абстрактный корень всех связок, и `db.Клиент(c).link()` падал
migration-ошибкой вместо обхода, хотя `db.link()` с корня работал. Теперь имя `link`
резолвится как класс на всех уровнях; зарезервированных имён 52 (`link` ушло, `as` пришло).
Совместимость со снесённым в 0.15.0 методом `.link()` принесена в жертву достижимости
класса — при обращении к нему теперь будет обычная ошибка пути, а не подсказка миграции.
Остальные migration-охранники (`execute()`, `set(data)`, слот `.delete()`,
`batch.execute()`) не тронуты: они не затеняют классов.

### BREAKING — чтение стало полиморфным по иерархии классов

Шаг цепочки по родительскому классу теперь отдаёт **объединение с потомками любой глубины**
(как и права ACL наследуются по иерархии). Раньше фильтр шёл по точной колонке `class`,
поэтому abstract-классы молча возвращали пусто, а родитель не видел потомков:

- `db.Контрагент()` (`Person`, abstract): было `0` → стало `Мастер` + `Клиент`;
- `db.связь()` (`link`, abstract): было `0` → стало все классы-связки;
- `db.окно()` (`slot`, конкретный, потомок `booking`): в демо-полигоне было `54 005` →
  стало `494 008`.

**Что нужно проверить в своём коде.** Если наследование у вас — переиспользование
`attributes`, а не «is-a» для выборки, добавьте **`.exact()`** на шаг: он возвращает
одиночный класс. Ровно этот случай в демо-домене — `запись` наследует `окно` (интервал и
правило v5-id), но смена ≠ бронь, поэтому «смены мастера» теперь
`db.Мастер(id).окно().exact()`. На классе без потомков `.exact()` — no-op.

- **Идентичность сущности в полиморфной выборке — пара `(class, id)`**: `DISTINCT ON`,
  подзапрос кандидатов и join истории в `versions()` переведены на неё; `Row.class`
  показывает конкретный класс строки.
- **Ключи `Entity.links` конкретны**, поэтому обходы (forward/reverse/`deep`) берут ключ
  из колонки `class` строки, а не из литерала родителя.
- **ACL решается по конкретному классу каждой строки.** `deny` на потомке больше не
  обходится шагом по родителю: запрещённые классы выпадают из выборки, у каждого
  разрешённого действует его собственный row-предикат; отказ шага целиком — только если
  запрещено всё семейство. Покрыто `test/acl.test.ts` (2 новых теста).
- **Запись полиморфной не бывает**: `create()` пишет строго в свой класс (в abstract —
  `class "X" is abstract`); `update()`/`delete()`/`purge()` работают со строками в их
  собственных классах.
- `exact` добавлено в зарезервированные имена классов (52).

Ревизия документации на пригодность для ИИ-агента: устранён дрейф между доками и кодом,
добавлен агентский слой и автопроверки, чтобы дрейф не возвращался.

## [0.19.0] — 2026-07-14

### Added — физический purge (hard-erase) + живой подхват правок схемы

- **`.purge({ confirm })`** — необратимый физический снос уже логически удалённой (tombstone)
  сущности + всего поддерева по `links` (все версии). Двухфазно: живую не трогает (сначала
  `.delete()`); без `confirm` — dry-превью замыкания. Внутри — серверная `purge()`:
  `SET LOCAL letopis.purge='on'` отключает append-only-триггер через `WHEN`-условие → плоский
  `DELETE` (детерминированно, без `TM_SelfModified`).

## [0.16.0] — 2026-07-12

### Changed — BREAKING: глаголы записи create/update, слот unset, id считает Schema

- **`set()` разбит на `create()` / `update()`** — мина «`Класс()` → INSERT,
  `Класс({})` → UPDATE всех» мертва, намерение всегда явное:
  - **`create(data?)`** — INSERT; известный id (шаг `Класс(id)`, `data.id` или
    вычисленный v5) уже существует → новая версия (идемпотентный create,
    REST-PUT семантика). Фильтр-объект перед create — ошибка ПОСТРОЕНИЯ
    (`create() takes no filter`); create на pivot-шаге — ошибка.
  - **`update(data?)`** — новая версия КАЖДОГО найденного путём;
    `Класс()` ≡ `Класс({})` — «все в границах контекста»; не найдено → `[]`,
    update НИКОГДА не создаёт.
  - `set()` бросает подсказку `set() split into create()/update() (0.16.0)`.
- **Слот-снятие переименовано: `.Класс.delete()` → `.Класс.unset()`** — развели
  «удалить сущность» (`delete()`) и «снять конец связи» (`unset()`); старое имя
  бросает подсказку. Слот теперь требует глагол записи ПЕРЕД собой:
  `…create(…).Класс.set(x)` / `…update(…).Класс.unset()`; слот без операции —
  ошибка `link slot needs a write` (раньше слот молча создавал `set({})`).
- **Генерация id по Schema** — `attributes.id`:
  - `"uuid"` / `{type:'uuid'}` → **v4** (random, как раньше — дефолт);
  - `{type:'uuid', generate: 7}` → **v7** (unix-время в старших битах — вставки
    ложатся в хвост btree-индекса);
  - `{type:'uuid', generate: 5, from:[…]}` → **v5, детерминированный**:
    `uuidv5("pgSchema:partition:класс:значения from")`; `from` — имена
    ОБЯЗАТЕЛЬНЫХ концов `Schema.links` (класс или полное имя союза
    `'Service|Complex'`; значение — id конца) и/или скалярных полей `data`.
    Явный id у v5-класса запрещён (`computes id`). Свойства: **create
    идемпотентен** (та же комбинация → та же сущность, дубль невозможен даже в
    гонке — двойная бронь мертва на уровне схемы) и **id известен ДО создания**
    (формула открыта; namespace letopis `c7a2f9d4-3b61-4e8a-9f05-8d2c1e6b7a90`).
  - Батч: multi-VALUES-склейка для v5-классов отключена (id нужны концы) —
    такие планы исполняются поштучно, семантика та же.
- **Наследование attributes по иерархии Schema**: при загрузке реестра attributes
  класса собираются по цепочке `ancestor` — потомок ПОВЕРХ предка, переопределение
  поля = замена правила целиком (не слияние). Правило `id` (генерация) наследуется

- **Демо-схема booking целиком на generate** — с наследованием: `Entity` и `link`

  `"v<version>.<schema>"` из шаблонов пакета (маркер `"<SCHEMA-NAME>"`) → сквозной
  `connect()`. Идемпотентно на каждом шаге; `fresh: true` — дроп схемы и накат заново;
  `seeds: string[] | false` — свои сиды вместо демо. Живые тайминги: с нуля
  (build+initdb+apply) 7.4 s, `docker start` 1.2 s, всё готово ~110 ms.
- **Данные PG — на хосте**: контейнер поднимается с named volume **`letopis-pgdata`**
  (кроссплатформенно, переживает пересоздание контейнера; физически — внутри
  docker-диска WSL2/ext4), `dataDir: '/path'` — bind mount папки (на Windows/NTFS —
  на свой риск). Redis без персиста — сессии эфемерны.
- SQL-шаблоны и Dockerfile теперь **пакуются в npm** (`lib/sql/`, `lib/docker/`,

## [0.11.0] — 2026-07-11

### Changed — BREAKING: цепочка = план, операции = звенья
- **`.set(data?)` / `.delete(opts?)` / `.anonymize(fields)` возвращают ЦЕПОЧКУ** (Chain),
  а не исполняются сами: операция применяется к шагу, к которому приклеена точкой;
  **исполняет терминал** (`rows/first/ids/count/run/versions/агрегации`) — весь план
  **одной транзакцией** (deny/валидация любого сегмента откатывает всё). Голый
  `await …set(…)` без терминала больше НЕ пишет (цепочка не thenable). Миграция:
  `await db.X(id).set({…})` → `await db.X(id).set({…}).rows()`.
- **Продолжение цепочки — от результата операции** (fan-out по строкам):
  `db.Клиент({vip: true}).set({bonus: 500}).Запись().delete({confirm: true}).rows()` —
  обновить всех vip и снести записи каждого. Повторная операция без шага — к тем же
  строкам: `X(id).set({a}).set({b}).rows()` — две версии подряд.
- **`execute()` → `run()`** (пути; то же у батча: `batch.execute()` → `batch.run()`);
  старые имена бросают понятную ошибку.
- **`delete({ confirm: true })` — удалить; БЕЗ confirm — превью**: терминал возвращает
  кандидатов (цели + каскад), БД не тронута.
- **Пост-довесы связей удалены** (`set({}).Окно(w)`, z-форма, тип `SetChain`): имя класса
  после операции — переход-шаг. Связи — контекст-шагами до операции; для значения связи
  БЕЗ участия в фильтре целей — новый модификатор **`.link(Класс, target)`**:
  `tr.Запись(b).позиция({}).link('Сотрудник', новый).set({}).rows()`.
- Ошибки записи (ValidationError, abstract, context step, acl) летят из терминала (async).
- В батче `await …set(…)` больше не возвращает номер очереди (план в очереди; Chain).
- Модификатор шага сразу после операции — ошибка `step modifier after set()`.
