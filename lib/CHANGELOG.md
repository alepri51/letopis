## [0.20.1] — 2026-07-31

### Fixed — движок схемы больше не отстаёт молча

`ddl.sql` растёт аддитивно внутри одной версии движка (в 0.19.0 так появились
`purge`/`purge_closure`/`purge_account`), а существующая схема этих правок **не получала**:
приложение обновляло пакет и падало сырым
`PostgresError: function "v1.booking".purge(...) does not exist`. Обнаружено смоук-тестом
опубликованного пакета на схеме, накатанной до 0.19.0.

- Последняя строка `ddl.sql` штампует метку `COMMENT ON SCHEMA … IS 'letopis ddl_revision=N'`
  (последней — чтобы метка не встала при частично применённом файле). `connect()` сверяет её
  с новой константой `DDL_REVISION` и **один раз на схему за процесс** предупреждает, называя
  команду апгрейда. Предупреждение, а не отказ: правки аддитивны.
- Апгрейд движка на месте: `up({ upgrade: true })` и `node db/apply.mjs … --upgrade`
  перекатывают **только** `ddl.sql` (сиды не трогаются). Безопасно, потому что файл
  идемпотентен — `CREATE OR REPLACE` у функций, `DROP IF EXISTS` + `CREATE` у триггеров,
  `IF NOT EXISTS` у таблиц/индексов. Механизм существовал, но был недостижим: `applySchema`
  при существующей схеме молча выходил.
- Ревизия ≠ версия схемы: несовместимая правка структуры таблиц по-прежнему означает смену
  `version` в имени схемы (`v1` → `v2`). README § 10.8a, грабля #18 в шпаргалке.

### Fixed — под `enforceAcl` каждый `db.as()` делал три SELECT вместо одного

Словарь `Resource`/`Rule` одинаков для всех субъектов, но снимался на каждый scope — то есть
в вебе (scope на HTTP-запрос) два лишних запроса к БД на каждый запрос приложения. Теперь
снимок берётся один раз на подключение и переиспользуется; per-scope остались чтение своего
аккаунта и компиляция энфорсера (один энфорсер = один субъект — иначе memo отдаст чужое
решение). Снимок сбрасывает `db.reloadSchema()`. Провал чтения не кэшируется.

### Added — проверки и воспроизводимость

- `check:docs` — десятая проверка: маркер `-- DDL_REVISION:` в `ddl.sql`, штамп `COMMENT` и
  константа в `types.ts` обязаны совпадать, а штамп — быть последним выражением файла.
- `release.yml` — смоук **артефакта** после публикации: пакет ставится из реестра в чистую
  папку, проверяются ESM-импорт, ключевые экспорты и наличие `dist`/`sql`/`scripts` в тарболе.
  Тесты гоняют `lib/src`, а в npm уезжает сборка — сломанные `exports`/`files` иначе
  обнаружил бы первый пользователь.
- `bench/tenants-seed.mjs` + `bench/isolation.bench.mjs` — многоарендаторный полигон
  (10 аккаунтов, перекос 50 %…0.3 %, 1 млн строк) и цена изоляции. Таблица README § 10.6
  была измерена временным скриптом; попутно из неё убрана колонка «без сужения» — это форма
  SQL, которой в публичном API нет.
- Тайминги README § 11 перенесены с проанализированного полигона точным сопоставлением по
  коду вызова (151 из 208; остальные — иллюстративные фрагменты, у них добавлена оговорка).
- Тесты: 198 (было 193 на 0.20.0). Новые — ревизия движка и апгрейд, `ANALYZE` при накате,
  кэш словаря ACL. Каждый проверен негативно.

### Changed — на каждое событие ровно одно действие в Actions

Тесты гонялись трижды на одном и том же коммите: прогон от push в `dev`, второй от
`pull_request` при открытии релизного PR и третий от push в `main` при merge. Причём на merge
`ci` и `tag` стартовали **одновременно** — тег мог встать раньше, чем закончатся тесты.

Контур приведён к одному действию на событие:

```
push dev            →  ci  (typecheck + check:docs + 198 тестов)
merge dev→main      →  tag (аннотированный тег из lib/package.json)
publish Release     →  release (описание из PR + npm publish + смоук артефакта)
```

- `ci.yml` — только `push: dev`. Ни `pull_request`, ни `push: main`: релизный PR и сам merge
  несут ТОТ ЖЕ коммит, что уже проверен на `dev` (ветка всегда пушится до PR). `concurrency` —
  быстрые последовательные пуши в `dev` отменяют предыдущий прогон.
- `tag.yml` — `push: main`, тегирует сразу: ждать нечего, тесты прошли на `dev`.
- убраны шаги `npm run build` + `npm pack` с выгрузкой артефакта: тарбол никто не забирал —
  `release.yml` публикует сам (`prepublishOnly` гоняет typecheck + build), а результат
  проверяется смоуком уже из реестра; компиляция дублировала шаг Typecheck. CI — 7 шагов.

**Остаётся настройкой репозитория:** branch protection на `main` с обязательной проверкой
`test`. Без неё запрет «не мерджить на красном» держится на дисциплине: у PR своей проверки
нет, гарантию даёт зелёный прогон того же SHA на `dev`.

### Changed — флоу релиза: тег с историей, заметки из PR, без сторонних экшенов

`tag.yml` ставит **аннотированный** тег: в сообщении — список коммитов от предыдущего тега,
поэтому `git show <tag>` и GitHub → Tags показывают состав версии без GitHub Release.

`release.yml` при публикации ставит в тело релиза **описание релизного PR** `dev→main`: оно
писалось осмысленно (что и почему, с замерами), в отличие от списка заголовков коммитов. PR
находится по коммиту, на который указывает тег; если PR не нашёлся или пуст — тело не трогается.

Источник версии — `lib/package.json`: тег обязан равняться тому, что уедет в npm. Забытый бамп
виден сразу — тег такой версии уже существует, шаг пропускается, релиза нет.

`git-cliff` и `cliff.toml` (заводились по образцу VP) удалены: после перехода на заметки из PR
от них оставались только аннотация тега и подсказка про bump — первое даёт обычный `git log`,
второе избыточно. Побочно ушла и зависимость от стороннего экшена в job, который публикует в npm.

## [0.20.0] — 2026-07-29

### Fixed — `ANALYZE` при накате схемы: чтения были медленнее на порядок

`up()` и `db/apply.mjs` теперь вызывают `ANALYZE "<схема>"."Entity"` после наката DDL и сидов.

`Entity` — гипертаблица: строки лежат в чанках, у родительской таблицы своих строк нет. Пока
`ANALYZE` по ней не прошёл, планировщик берёт дефолт «200 уникальных `id`». Ядро всех чтений
либы — semi-join с подзапросом кандидатов (`e.id IN (SELECT c.id FROM Entity c WHERE …)`), и на
такой оценке он выбирает `Nested Loop` вместо `Merge Semi Join`, с уходом хеша и сортировки на
диск. Замерено на полигоне 980k строк:

| Сцена | без статистики | после `ANALYZE` | |
|---|---|---|---|
| `count()` класса под изоляцией арендатора | 57.6 s | 3.2 s | ×18 |
| фильтр `rows` limit 100 по 440k | 1371 ms | 11 ms | ×126 |
| `count()` класса без фильтра | 2981 ms | 1373 ms | ×2.2 |

Тайминги README §14 и §9.2 перемерены на проанализированной базе. Своя массовая вставка
(`COPY`, миграция, генератор) требует `ANALYZE` вручную — это отдельная грабля в
`AGENT-CHEATSHEET.md` (#17) и новая секция README §14.1.

Заодно вычищен доковый дрейф в §14: строка «обход `запись→Мастер` по всему классу» показывала
≈6 с с версии 0.17.0, где полигон был 250 000 записей / 613 тыс. строк, и переезд на
440 006 / 980 328 её не обновил — настоящее значение ≈30 с. Стоимость этой сцены = `строки
внешнего шага × чанки` (одна проба — 0.924 мс / 80 буферов при 13 чанках), потому что
forward-hop идёт коррелированным `JOIN LATERAL` с пробой по всем чанкам. Первое объяснение
в §14 («планировщик недооценивает внешнюю сторону и не ставит `Memoize`») **снято как
неверное**: подстановка класса литералом и `SET enable_nestloop = off` план не меняют, дело в
самой форме — корреляция внутри подзапроса с `DISTINCT ON` не раскоррелируется и не
мемоизируется. Некоррелированный join измерен и хуже в 18 раз (561 с), так что форма
оставлена как есть; лечится стороной старта цепочки — `db.запись(id).Мастер()` 7.5 мс и
`db.Мастер(id).запись()` 11.7 мс против 30 с у обхода всего класса.

Попутно исправлен `bench/acl.bench.mjs`: его колонки были несравнимы — `base` шёл без изоляции
арендатора, а ACL-хендлы с ней, из-за чего бенч приписывал авторизации до 18× чужой цены.
Теперь все три режима с `enforceAccount: false`, и видно настоящее: **ACL бесплатен на всех
сценах** (отличия в пределах шума). Цена изоляции измеряется отдельно и зависит от доли
арендатора в классе — на 10-арендаторном полигоне она ускоряет чтение до 27× (README §10.6).

### BREAKING — арендатор стал свойством ВЫЗОВА: `db.as(account)`, опции `connect({ account })` больше нет

Из `ConnectOpts` **удалены `account` и `owner`**. Аккаунт на подключении — это модель
«одно соединение = один тенант», а для веб-приложения она неверна: пул общий, арендатор
меняется от запроса к запросу. Теперь подключение безличное, а идентичность даёт хендл:

```ts
const db = await connect({ dsn, schema })     // было: connect({ …, account: X })
const t  = await db.as(accountId)             // стало: имя вызова, хендл того же пула
await t.Клиент().rows()
```

`db.as(account, { owner? })` клонирует контекст на **том же пуле** (нового соединения не
открывает, SQL не шлёт), поэтому его нормально создавать на каждый HTTP-запрос. `close()`
по-прежнему один на пул. Батчи с корня в scope не наследуются: очередь планов, общая для
разных арендаторов, была бы утечкой записи.

Под `enforceAcl` **правила компилятся под субъекта scope** — у каждого `db.as()` свой
энфорсер. Это не оптимизация, а требование корректности: ключ memo в `acl.ts` — «класс +
операция», без аккаунта, так что переиспользование одного энфорсера двумя арендаторами
отдало бы второму решения первого. Закреплено тестом (`acl.test.ts`, «memo энфорсера не
течёт между scope одного пула»); проверено негативно — с общим энфорсером тест падает.

`enforceAccount` — **`true`** по умолчанию: чтения фильтруются по `account` scope-хендла,
записи к нему пришпилены. Забыть флаг было слишком легко, а цена забывчивости — чужие
строки в выдаче без всякой ошибки. Теперь и забыть `db.as()` нельзя: с безличного корня
чтение/запись бросают

```
letopis: enforceAccount is on — call db.as(account) to name the tenant of this call,
or connect({ enforceAccount: false }) for admin access
```

Админским и сервисным подключениям (миграции, отчёты по всем арендаторам, дев-скрипты)
нужен явный `connect({ …, enforceAccount: false })` — там колонку `account` закрывает
System-аккаунт схемы, как раньше.

Смысл модификатора `.account()` не изменился: это точечный фильтр/значение одного шага;
на scope-хендле чужое значение — ошибка `pinned`.

`enforceAcl` остаётся **`false`** (opt-in): включённый по умолчанию deny-by-default без
настроенных `Resource`/`Rule` давал бы пустые выборки. Вместо смены дефолта `connect()`
печатает предупреждение один раз на процесс: авторизация не проверяется — это должно быть
шумно, а не молча.

**Миграция.** `connect({ …, account: X })` → `(await connect({ … })).as(X)`;
`connect({ …, account: X, owner: Y })` → `.as(X, { owner: Y })`; подключения, которые
работали без `account` и должны видеть всё, — `connect({ …, enforceAccount: false })`.
`accounts.purge(id)` требует scoped-хендла: `(await db.as(caller)).accounts.purge(id)`.

### BREAKING — снят охранник `.link()`

`case 'link'` в цепочке удалён. Он затенял **реальный класс схемы**: в демо-домене `link`
(алиас `связь`) — абстрактный корень всех связок, и `db.Клиент(c).link()` падал
migration-ошибкой вместо обхода, хотя `db.link()` с корня работал. Теперь имя `link`
резолвится как класс на всех уровнях; зарезервированных имён 52 (`link` ушло, `as` пришло).
Совместимость со снесённым в 0.15.0 методом `.link()` принесена в жертву достижимости
класса — при обращении к нему теперь будет обычная ошибка пути, а не подсказка миграции.
Остальные migration-охранники (`execute()`, `set(data)`, слот `.delete()`,
`batch.execute()`) не тронуты: они не затеняют классов.

### Added — тест паритета клиент ↔ триггер БД

`test/parity.test.ts`: правило концов связей реализовано дважды — в plpgsql
(`entity_check`) и в TypeScript (`write.validate`), и до сих пор ничто не проверяло, что
реализации не разошлись. Теперь каждый кейс исполняется двумя путями (через либу и голым
`INSERT` в `Entity`), и утверждается одинаковое решение: abstract-класс, неизвестный
класс, отсутствующий обязательный конец, посторонняя связь, ключ `links` не-класс,
союз ролей, отсутствие optional-конца. Тест не привязан к схеме потребителя — проверяется
само правило, одно для всех схем.

Отдельным кейсом закреплена **известная асимметрия**: валидация данных по `attributes`
живёт только в либе (fastest-validator нельзя запустить в plpgsql), поэтому голый SQL
структурный мусор в `data` принимает. Если это изменится — тест упадёт и потребует
поправить README §2.

### BREAKING — чтение стало полиморфным по иерархии классов

Шаг цепочки по родительскому классу теперь отдаёт **объединение с потомками любой глубины**
(как и права ACL наследуются по иерархии). Раньше фильтр шёл по точной колонке `class`,
поэтому abstract-классы молча возвращали пусто, а родитель не видел потомков:

- `db.Контрагент()` (`Person`, abstract): было `0` → стало `Мастер` + `Клиент`;
- `db.связь()` (`link`, abstract): было `0` → стало все классы-связки;
- `db.окно()` (`slot`, конкретный, потомок `booking`): в демо-полигоне было `54 005` →
  стало `494 008`.

**Что нужно проверить в своём коде.** Если наследование у вас — переиспользование
`attributes`, а не «is-a» для выборки, добавьте **`.exact()`** на шаг: он возвращает
одиночный класс. Ровно этот случай в демо-домене — `запись` наследует `окно` (интервал и
правило v5-id), но смена ≠ бронь, поэтому «смены мастера» теперь
`db.Мастер(id).окно().exact()`. На классе без потомков `.exact()` — no-op.

- **Идентичность сущности в полиморфной выборке — пара `(class, id)`**: `DISTINCT ON`,
  подзапрос кандидатов и join истории в `versions()` переведены на неё; `Row.class`
  показывает конкретный класс строки.
- **Ключи `Entity.links` конкретны**, поэтому обходы (forward/reverse/`deep`) берут ключ
  из колонки `class` строки, а не из литерала родителя.
- **ACL решается по конкретному классу каждой строки.** `deny` на потомке больше не
  обходится шагом по родителю: запрещённые классы выпадают из выборки, у каждого
  разрешённого действует его собственный row-предикат; отказ шага целиком — только если
  запрещено всё семейство. Покрыто `test/acl.test.ts` (2 новых теста).
- **Запись полиморфной не бывает**: `create()` пишет строго в свой класс (в abstract —
  `class "X" is abstract`); `update()`/`delete()`/`purge()` работают со строками в их
  собственных классах.
- `exact` добавлено в зарезервированные имена классов (52).

Ревизия документации на пригодность для ИИ-агента: устранён дрейф между доками и кодом,
добавлен агентский слой и автопроверки, чтобы дрейф не возвращался.

- Гвард: `test/wave2.test.ts` проверяет форму фасада, отсутствие снесённых имён и

### Added — зарезервированные имена классов

- **52 имени** разбирается Proxy до резолва класса, причём в двух формах: `case`-метки
  switch'ей (`count`, `sort`, `account`, `as`, `set`, `size`, …) **и** ранние `if (prop === …)`
  — гашение `then` во всех трёх Proxy и фасады корня `db` (`schema`, `auth`, `acl`, `accounts`,
  `credentials`, `resources`, `rules`). Класс с таким `id`/`alias` недостижим как шаг под этим
  именем; раньше это нигде не было записано, хотя коллизия живёт в самом демо-сиде (класс `link`).
- `RESERVED_CLASS_NAMES` / `reservedNamesOf()` в `types.ts`; `db.schema.define()` **отказывает**
  на таком имени; `loadRegistry` предупреждает (один раз на схему+класс за процесс, не throw —
  иначе демо-сид ронял бы `up()`); `gen-types` не выдаёт таких шагов; таблица в README §3.

### Added — агентский слой и автопроверки

## [0.16.0] — 2026-07-12

### Changed — BREAKING: глаголы записи create/update, слот unset, id считает Schema

- **`set()` разбит на `create()` / `update()`** — мина «`Класс()` → INSERT,
  `Класс({})` → UPDATE всех» мертва, намерение всегда явное:
  - **`create(data?)`** — INSERT; известный id (шаг `Класс(id)`, `data.id` или
    вычисленный v5) уже существует → новая версия (идемпотентный create,
    REST-PUT семантика). Фильтр-объект перед create — ошибка ПОСТРОЕНИЯ
    (`create() takes no filter`); create на pivot-шаге — ошибка.
  - **`update(data?)`** — новая версия КАЖДОГО найденного путём;
    `Класс()` ≡ `Класс({})` — «все в границах контекста»; не найдено → `[]`,
    update НИКОГДА не создаёт.

- **Слот-снятие переименовано: `.Класс.delete()` → `.Класс.unset()`** — развели
  «удалить сущность» (`delete()`) и «снять конец связи» (`unset()`); старое имя
  бросает подсказку. Слот теперь требует глагол записи ПЕРЕД собой:
  `…create(…).Класс.set(x)` / `…update(…).Класс.unset()`; слот без операции —
  ошибка `link slot needs a write` (раньше слот молча создавал `set({})`).
- **Генерация id по Schema** — `attributes.id`:

## [0.11.0] — 2026-07-11

### Changed — BREAKING: цепочка = план, операции = звенья
- **`.set(data?)` / `.delete(opts?)` / `.anonymize(fields)` возвращают ЦЕПОЧКУ** (Chain),
  а не исполняются сами: операция применяется к шагу, к которому приклеена точкой;
  **исполняет терминал** (`rows/first/ids/count/run/versions/агрегации`) — весь план
  **одной транзакцией** (deny/валидация любого сегмента откатывает всё). Голый
  `await …set(…)` без терминала больше НЕ пишет (цепочка не thenable). Миграция:
  `await db.X(id).set({…})` → `await db.X(id).set({…}).rows()`.
- **Продолжение цепочки — от результата операции** (fan-out по строкам):
  `db.Клиент({vip: true}).set({bonus: 500}).Запись().delete({confirm: true}).rows()` —
  обновить всех vip и снести записи каждого. Повторная операция без шага — к тем же
  строкам: `X(id).set({a}).set({b}).rows()` — две версии подряд.
- **`execute()` → `run()`** (пути; то же у батча: `batch.execute()` → `batch.run()`);
  старые имена бросают понятную ошибку.
- **`delete({ confirm: true })` — удалить; БЕЗ confirm — превью**: терминал возвращает
  кандидатов (цели + каскад), БД не тронута.
- **Пост-довесы связей удалены** (`set({}).Окно(w)`, z-форма, тип `SetChain`): имя класса
  после операции — переход-шаг. Связи — контекст-шагами до операции; для значения связи
  БЕЗ участия в фильтре целей — новый модификатор **`.link(Класс, target)`**:
  `tr.Запись(b).позиция({}).link('Сотрудник', новый).set({}).rows()`.
- Ошибки записи (ValidationError, abstract, context step, acl) летят из терминала (async).
- В батче `await …set(…)` больше не возвращает номер очереди (план в очереди; Chain).
- Модификатор шага сразу после операции — ошибка `step modifier after set()`.

- `connect({enforceAccount})` — жёсткая изоляция арендатора (чтение и запись).
- `.anonymize(fields)` — GDPR-затирание string-полей + тег `anonymized` (история сохраняется).
- Операторы `or(...)`/`not(...)`; агрегации `.sum/.avg/.min/.max/.countBy` (считает БД).
- `.deep(max)` — рекурсивный обход детей (self-hop) одним запросом, `$depth` в Row.
- `db.watch()` — realtime-события версий (триггер `entity_notify` → LISTEN/NOTIFY).
