## [0.17.0] — 2026-07-12

### Changed — BREAKING: демо-домен booking переделан (позитивная доступность)

Библиотека не изменилась — переделан демо-домен booking (19 классов вместо 16;
источник правды — сид `lib/sql/seed.booking.sql`) и всё, что на нём стоит:
тесты, бенчи, полигоны, доки. Промежуточные дизайн-файлы `schema.booking.v2.*`
удалены из корня; `gen-seed.mjs` упразднён (сид редактируется напрямую).

- **Новые HUB**: `Person·Контрагент` (абстракт: `name`+`phone`, наследуют
  Мастер/Клиент), `Location·Локация`, `Element·Элемент` (абстрактная каталожная
  единица: `name`/`price` + правило `id = v5(Org, name)` объявлены ОДИН раз,
  наследуются Услугой/Товаром/Комплексом), `Product·Товар`.
- **Смена категории**: Окно и Запись из HUB стали LINK:
  - `slot·окно [Staff, Location, Schedule] {start_datetime, end_datetime}` —
    интервал доступности мастера (смена), `id = v5(Staff, start_datetime)`;
  - `booking·запись` — **наследник окна** (`ancestor: slot`): интервал и
    v5-правило id приходят по наследству, свои концы — предмет-союз
    `Service|Product|Complex` + `Customer?`. Двойная бронь мертва самим id
    записи; окно и запись на одно время сосуществуют (classId в формуле).
- **Инверсия модели доступности**: негативная (Slot-сетка + busy off/hold/booking
  + shift-ростер) → **позитивная** (окно есть = мастер доступен; свободно =
  внутри окна и нет пересекающейся записи). Классы `busy`, `shift`, `item`,
  HUB `Slot`/`Booking` — удалены.
- **Запись самодостаточна**: сама несёт интервал (длинная услуга = один интервал,
  мульти-окна не нужны), предмет и клиента. «4 руки» = две записи. Перенос =
  пересоздание (id жёстко держит пару мастер+старт). Отмена = tombstone-delete;
  повторная бронь пары воскрешает id с историей. Статусы
  (created/…/no_show), source, total, qty и снимок цены — удалены: история —
  версии, цена — из предмета (`asOf` для задним числом).
- **Каталог**: принадлежность папке — LINK `content·содержимое [Folder, союз]`
  (M:N + order) вместо Folder-конца; состав комплекса `compo·состав` принимает
  союз `Service|Product`; вложенность папок осталась HUB-концом `Folder⤴`.
  `skill·навык` сужен до `[Staff, Service]` (+`level`) — умение комплекса
  вычислимо по составу. Новый `address·адрес [Staff, Location]`.
- **Упрощения атрибутов**: `price` — число (record по валютам удалён),
  `Schedule {name, year, month}` (месячная модель), у Мастера/Клиента общие
  поля уехали в Контрагента; `Complex` переопределяет унаследованный `price`
  в `optional` (демонстрация «замена правила целиком»).
- Тесты переписаны под модель (**167 тестов**, было 165): `idgen.test.ts` —
  наследование v5-правила через два уровня (booking→slot→link, DeluxeBooking),
  v5 из пары концов (адрес) и конца+поля (запись); `real-life.test.ts` — сцены
  переноса-пересоздания, воскрешения id, no-show пометкой; `salon.test.ts` —
  21 акт на новой модели; has/hasAny/hasAll переехали на колонку tags
  (массивов в data демо-схемы больше нет).
- Полигоны `v1.salondemo` (~1M строк) и `v1.article` пересеяны генераторами
  новой модели; SALON.md, README §3, TESTPLAN.md — перегнаны с живых прогонов.

## [0.16.0] — 2026-07-12

### Changed — BREAKING: глаголы записи create/update, слот unset, id считает Schema

- **`set()` разбит на `create()` / `update()`** — мина «`Класс()` → INSERT,
  `Класс({})` → UPDATE всех» мертва, намерение всегда явное:
  - **`create(data?)`** — INSERT; известный id (шаг `Класс(id)`, `data.id` или
    вычисленный v5) уже существует → новая версия (идемпотентный create,
    REST-PUT семантика). Фильтр-объект перед create — ошибка ПОСТРОЕНИЯ
    (`create() takes no filter`); create на pivot-шаге — ошибка.
  - **`update(data?)`** — новая версия КАЖДОГО найденного путём;
    `Класс()` ≡ `Класс({})` — «все в границах контекста»; не найдено → `[]`,
    update НИКОГДА не создаёт.
  - `set()` бросает подсказку `set() split into create()/update() (0.16.0)`.
- **Слот-снятие переименовано: `.Класс.delete()` → `.Класс.unset()`** — развели
  «удалить сущность» (`delete()`) и «снять конец связи» (`unset()`); старое имя
  бросает подсказку. Слот теперь требует глагол записи ПЕРЕД собой:
  `…create(…).Класс.set(x)` / `…update(…).Класс.unset()`; слот без операции —
  ошибка `link slot needs a write` (раньше слот молча создавал `set({})`).
- **Генерация id по Schema** — `attributes.id`:
  - `"uuid"` / `{type:'uuid'}` → **v4** (random, как раньше — дефолт);
  - `{type:'uuid', generate: 7}` → **v7** (unix-время в старших битах — вставки
    ложатся в хвост btree-индекса);
  - `{type:'uuid', generate: 5, from:[…]}` → **v5, детерминированный**:
    `uuidv5("pgSchema:partition:класс:значения from")`; `from` — имена
    ОБЯЗАТЕЛЬНЫХ концов `Schema.links` (класс или полное имя союза
    `'Service|Complex'`; значение — id конца) и/или скалярных полей `data`.
    Явный id у v5-класса запрещён (`computes id`). Свойства: **create
    идемпотентен** (та же комбинация → та же сущность, дубль невозможен даже в
    гонке — двойная бронь мертва на уровне схемы) и **id известен ДО создания**
    (формула открыта; namespace letopis `c7a2f9d4-3b61-4e8a-9f05-8d2c1e6b7a90`).
  - Батч: multi-VALUES-склейка для v5-классов отключена (id нужны концы) —
    такие планы исполняются поштучно, семантика та же.
- **Наследование attributes по иерархии Schema**: при загрузке реестра attributes
  класса собираются по цепочке `ancestor` — потомок ПОВЕРХ предка, переопределение
  поля = замена правила целиком (не слияние). Правило `id` (генерация) наследуется
  так же; `links` НЕ наследуются (концы объявляются каждым классом). Валидатор и
  fieldTypes компилируются из слитых attributes.
- **Демо-схема booking целиком на generate** — с наследованием: `Entity` и `link`
  объявляют дефолт `{generate: 7}`, v7-классы (Org/Staff/Folder/Customer/Schedule/
  Booking/item) наследуют его без собственного правила; v5-классы переопределяют:
  `busy ← v5(Slot, Staff)`; `skill ← v5(Staff, Service|Complex)`;
  `shift ← v5(Schedule, Staff)`; `compo ← v5(Complex, Service)`;
  `Slot ← v5(Schedule, data.start)`; `Service`/`Complex` ← `v5(Org, data.name)`
  (имя уникально в организации). Полигоны `v1.salondemo`/`v1.article` обновлены
  на месте (UPDATE Schema; данные нетронуты).
- Тесты мигрированы (все `set`→`create`/`update`, слот `.delete`→`.unset`,
  фикс-id v5-классов → вычисляемые); новый **`test/idgen.test.ts`** — генерация
  id на боевых классах Schema (v4/v7/v5 из поля и концов, гонка без локов,
  наследование attributes/id-правила, схема-гарды). SALON.md и демо-полигон
  перегнаны на 0.16.0. Итого **165 тестов**.

## [0.15.0] — 2026-07-12

### Changed — BREAKING: единый закон пути, слоты связей, pivot, entity()
- **Один закон навигации для чтения И записи**: цепочка всегда подчиняется переходам
  `Schema.links`; недопустимый переход — ошибка СИНХРОННО при построении (не в терминале).
  Мультиродительский «контекст-сбор» через невалидные HUB→HUB прыжки удалён.
- **Слоты связей** вместо `.link()`: конец связки задаётся `.Класс.set(target)` ПОСЛЕ
  `.set(данные)` — свойство-класс БЕЗ вызова. Владелец создаваемой связки — из валидного
  пути, прочие концы — слотами. `target` = id | Row | **вложенная цепочка** (исполняется в
  той же транзакции, обязана дать ровно одну сущность класса конца — «создать И привязать»).
  `.Класс.delete()` снимает optional-конец; союз-конец `[A|B]` замещается слотом целиком.
  **`.link()` УДАЛЁН** (бросает подсказку).
- **pivot**: повтор LINK-класса в пути — возврат к тому же узлу (ветвление к другому концу
  + дофильтровка AND). `db.Запись(з).позиция().Услуга(у).позиция().Сотрудник(вася)` —
  «позиции записи з с услугой у у мастера вася» одной цепочкой.
- **`entity(x)`** (Chain и db): вставить узел-переменную/паттерн (`db.позиция()`) или Row в
  путь; та же переменная повторно — явный pivot; `db.entity(row).…` — старт с готовой строки.
- Тесты мигрированы на слоты; **`test/salon.test.ts`** — тест-план «работа салона»
  (21 акт), покрывающий ВСЕ 145 публичных точек API + матрица покрытия. Итого 153 теста.

## [0.13.0] — 2026-07-11

### Added — `up()`: одна точка входа
- **`up(opts): Promise<EntityDb>`** — от пустой машины до готового `db` одной функцией:
  probe `dsn` (живой postgres — docker пропускается: CI-сервисы, внешние БД) → docker
  ensure через CLI (`inspect`/`build` из пакованного Dockerfile/`run`/`start`) → ожидание
  готовности PG + Redis → автосоздание базы из `dsn` (3D000) → версионная схема
  `"v<version>.<schema>"` из шаблонов пакета (маркер `"<SCHEMA-NAME>"`) → сквозной
  `connect()`. Идемпотентно на каждом шаге; `fresh: true` — дроп схемы и накат заново;
  `seeds: string[] | false` — свои сиды вместо демо. Живые тайминги: с нуля
  (build+initdb+apply) 7.4 s, `docker start` 1.2 s, всё готово ~110 ms.
- **Данные PG — на хосте**: контейнер поднимается с named volume **`letopis-pgdata`**
  (кроссплатформенно, переживает пересоздание контейнера; физически — внутри
  docker-диска WSL2/ext4), `dataDir: '/path'` — bind mount папки (на Windows/NTFS —
  на свой риск). Redis без персиста — сессии эфемерны.
- SQL-шаблоны и Dockerfile теперь **пакуются в npm** (`lib/sql/`, `lib/docker/`,
  `files += sql, docker`) — `up()` работает у любого потребителя пакета из коробки.

### Changed
- Dev-контейнер переименован: образ `clockz-db` → **`letopis-db`**, контейнер
  `clockz-timescale` → **`letopis-timescale`** (данные перенесены дампом, полигон
  `v1.article` 1 112 952 строк цел).
- Шаблоны переехали `db/*.sql` → `lib/sql/`, докер-файлы `db/docker/` → `lib/docker/`;
  `db/apply.mjs` остался CLI-обёрткой и читает шаблоны из `lib/sql/`.

### Changed — BREAKING: шаблон SQL + версия движка в имени схемы
- **SQL-шаблоны (`db/ddl.sql`, сиды) держат маркер `"<SCHEMA-NAME>"`** вместо реального

  `v1.plan`, `v1.wave4`, `v1.bench`; безверсионные дропнуты.

## [0.11.0] — 2026-07-11

### Changed — BREAKING: цепочка = план, операции = звенья
- **`.set(data?)` / `.delete(opts?)` / `.anonymize(fields)` возвращают ЦЕПОЧКУ** (Chain),
  а не исполняются сами: операция применяется к шагу, к которому приклеена точкой;
  **исполняет терминал** (`rows/first/ids/count/run/versions/агрегации`) — весь план
  **одной транзакцией** (deny/валидация любого сегмента откатывает всё). Голый
  `await …set(…)` без терминала больше НЕ пишет (цепочка не thenable). Миграция:
  `await db.X(id).set({…})` → `await db.X(id).set({…}).rows()`.
- **Продолжение цепочки — от результата операции** (fan-out по строкам):
  `db.Клиент({vip: true}).set({bonus: 500}).Запись().delete({confirm: true}).rows()` —
  обновить всех vip и снести записи каждого. Повторная операция без шага — к тем же
  строкам: `X(id).set({a}).set({b}).rows()` — две версии подряд.
- **`execute()` → `run()`** (пути; то же у батча: `batch.execute()` → `batch.run()`);
  старые имена бросают понятную ошибку.
- **`delete({ confirm: true })` — удалить; БЕЗ confirm — превью**: терминал возвращает
  кандидатов (цели + каскад), БД не тронута.
- **Пост-довесы связей удалены** (`set({}).Окно(w)`, z-форма, тип `SetChain`): имя класса
  после операции — переход-шаг. Связи — контекст-шагами до операции; для значения связи
  БЕЗ участия в фильтре целей — новый модификатор **`.link(Класс, target)`**:
  `tr.Запись(b).позиция({}).link('Сотрудник', новый).set({}).rows()`.
- Ошибки записи (ValidationError, abstract, context step, acl) летят из терминала (async).
- В батче `await …set(…)` больше не возвращает номер очереди (план в очереди; Chain).
- Модификатор шага сразу после операции — ошибка `step modifier after set()`.

## [0.10.0] — 2026-07-11

### Added
- **ACL по Resource/Rule** (формат согласован повторно, закрыт последний гэп RESEARCH.md):
  - `db.acl.check(account, endpoint)` — legacy-семантика 1:1: субъект-группы по
    `Account.categories` (`{A,B}` / `!{A,B}` / NULL), маски эндпоинтов (`*`, `{a,b}`),
    победа ровно одного правила (max weight, при равенстве deny), без правил — deny.
  - **Операции над данными = категории ресурсов `READ`/`WRITE`/`DELETE`**; pattern —
    **шаблон строки Entity**: реальные колонки (`class`, `owner`, `account`, `tags`,
    `data`, `links`…) с литералами или `"$account"` (подставляется динамически);
    `class`-маска действует на потомков (lineage). Никаких выдуманных полей.
  - `db.acl.checkData(account, class, op)` → `{allow, filter?}` — filter = остаточный
    шаблон строк победившего правила с подставленным `$account`.
  - **`connect({ account, enforceAcl: true })`**: READ на каждый шаг цепочки, WRITE на
    `set()`/anonymize/батчи, DELETE на цели и все классы каскадного замыкания (deny
    откатывает транзакцию). **Предикат вливается в SQL до сортировки/лимита** — пагинация,
    count, keyset честные. INSERT пришпиливает `$account`-колонки; upsert по явному id
    НЕ перехватывает существующую недоступную сущность. `watch()` отдаёт события только
    безусловных allow-классов. Deny-by-default; правила фиксируются на connect.
  - `bench/acl.bench.mjs` (1.1M): безусловное правило — бесплатно; предикат в worst-case
    (100% строк) +33–99% на full-scan; в реальности предикат сужает выборку — дешевле базы.
  - `test/acl.test.ts` — 9 сцен; суммарно 114 тестов. Сид не менялся.

    через `meta.lastStep`, первая успешная проверка активирует фактор), `totpEnabled`;
    хелпер `totpCode(secret, atMs?)` экспортирован (тесты/серверная генерация).
  - **Одноразовые коды** (email/SMS/сброс — доставка на приложении): `issueOtp` (в БД
    только sha256 + expires + attempts; повторный выпуск затирает старый код),
    `verifyOtp` (успех сжигает код; 5 неудач сжигают; истёкший TTL сжигает).
- `test/auth.test.ts`: +2 сцены (TOTP: enroll/verify/replay/окно/re-enroll; OTP:
  одноразовость/лимит/TTL/перевыпуск); суммарно 105 тестов.

## [0.8.0] — 2026-07-11

### Added
- **Устойчивость к сбоям** (§ 10.12 README):
  - transient-ошибки PG (deadlock `40P01`, serialization `40001`) ретраятся там, где
    повтор безопасен: чтения в автокоммите (до 3 попыток, backoff 40–160 ms), `insertOne`
    (плюс прежний 23505), внутренние транзакции delete-каскада и батчей — повтор целиком;
  - внутри `db.begin()` повтор невозможен (транзакция aborted) — ошибка уходит сразу
    с подсказкой `retry the whole db.begin() block`; `tr.lock()` при deadlock — та же подсказка;
  - ретрай 23505/transient в `insertOne` больше не срабатывает внутри транзакции
    (раньше повтор в aborted-транзакции маскировал исходную ошибку кодом 25P02).
- **`watch(…, { onReconnect })`** — LISTEN-соединение и так переживает обрывы
  (postgres.js: reconnect + повторный LISTEN), но NOTIFY за время разрыва потеряны;
  `onReconnect` зовётся после каждого восстановления — точка дочитать пропущенное.
  Типы `WatchEvent`/`WatchOpts` экспортированы.
- `test/resilience.test.ts` — юнит-ретраи, настоящий deadlock двух транзакций
  (встречные `lock()`), обрыв LISTEN через `pg_terminate_backend` (reconnect ~0.4 s);
  суммарно 103 теста.
