# Changelog

Формат: [Keep a Changelog](https://keepachangelog.com/), версии — semver. Что обещают патч, минор и мажор, — раздел
«Версии и совместимость» в README; шаг версии сверяет `npm run check:semver`. С 1.4.2 у правки ядра (библиотеки и SQL)
в конце пункта указан источник находки: «Источник: тест», «пример», «сервис», «ревью», «soak» или «внедрение».

## [1.4.2-alpha.0] — 2026-11-01

План 2.0 (`reports/PLAN-LETOPIS-2.0.md`): правила версий, проверка перед выпуском, исправления.

### Добавлено
- Правила версий — подраздел «Версии и совместимость» в README (обе версии): патч — только исправления без новой
  ревизии движка и без новых отказов; минор — новые возможности и новая ревизия с `up({ upgrade: true })`; мажор —
  удаление, переименование, смена сигнатур и новые отказы.
- `npm run check:semver` (`scripts/check-semver.mjs`): контракт API и ревизия движка текущего дерева против тега
  прошлого выпуска — исчезло → мажор, появилось или выросла ревизия → минор, тексты ошибок → патч; шаг версии обязан
  быть не меньше. Входит в `check:docs` (в CI checkout с полной историей) и в `release.yml` до публикации. Сборка
  контракта вынесена в `scripts/contract.mjs`; в `docs/api-contract.json` появилось поле `codes` — коды ошибок.
- `npm run prerelease` (`scripts/prerelease.mjs`) — полная локальная проверка одной командой, строго по очереди:
  typecheck, сверка документов, весь `npm test`, примеры сайта со снимками, ER-схемы, покрытие, сборка сайта,
  песочница, сценарии четырёх сервисов, проверка пакета с живым прогоном. Первый красный шаг останавливает прогон;
  итог — таблица в `docs/checkpoint-<x.y.z>.md`. Тесты в CI не гоняются (решение владельца 01.11.2026).
- Метрика стабилизации: у правки ядра в CHANGELOG — источник находки, `release-notes.mjs` считает их в теле релиза.
- Тест `upgrade` №3: накат схемы 1.4.1 (dev-зависимость `letopis-141`) обычным `up()` без миграций; правило — каждый
  выпуск проверяет накат с предыдущего. Тесты `semver` и `prerelease` проверяют сами сценарии (план 2.0, 7.8).
- `CONTRIBUTING.md` (и английская версия), шаблон issue об ошибке, форма отчёта о внедрении
  `docs/adoption/TEMPLATE.md`.

### Исправлено
- `maintain()` мог безвозвратно стереть историю: если класс System заводили позже одноимённого класса арендатора,
  строки журнала арендатора попадали в отбор дважды, и промежуточные версии ярусов стирались. Теперь политику выбирают
  прореживание, `verify` и срок курсора подписки так же, как класс строки: свой класс арендатора, иначе System
  (план 2.0, 7.3 №1). Источник: ревью.
- История удалённого объекта стирается целиком и тогда, когда до `reclass` он был в классе без политики: версии
  прежнего класса больше не остаются и не показывают объект живым в срезе (7.3 №2). Источник: ревью.
- Стирание истории удалённого ждёт `restore()`, начатый в другой транзакции, и после него историю не трогает: раньше
  цепочка восстановленного объекта начиналась не с версии 1 (7.3 №3). Источник: ревью.
- `maintain()` чистит истёкшие сессии и коды один раз за вызов, в первой пачке, а не в каждой из пачек (до 100):
  у функции базы `maintain` третий аргумент `p_cleanup`; схема, которую ещё не обновил `up()`, получает прежний
  вызов (7.3 №4). Источник: ревью.

- Два `create` одного ключа в батче проходили молча: обе строки ответа были одной и той же строкой. Теперь повтор —
  `exists`, и батч откатывается целиком (7.2 №1). Источник: ревью.
- Строки ответа `reclass`, `restore` и `rekey` — в порядке целей (`sort()` до глагола, иначе id), как обещает README;
  в 1.4.1 так стало только у `update` и `anonymize` (7.2 №2). Источник: ревью.
- Цепочка с глаголом и читающим хвостом в значении слота (`.Cat.add(db.Cat().create(…).Parent())`) падала с
  `TypeError`; вложенный план не проходил проверки до базы. Теперь работает, а модификатор сразу после её глагола —
  `invalid_query`, как у терминала (7.2 №3). Источник: ревью.
- Кэш результатов отдавал общие объекты: правка `rows[0].data` у ответа `.cache()` портила следующие ответы. Теперь
  кэш хранит и отдаёт копии (7.2 №5). Источник: ревью.

- Подписка без событий опрашивала журнал сериями по 40 коротких повторов на каждый тик таймера — около 4 запросов в
  секунду вместо одного за `pollMs`. Теперь короткие повторы идут только после сигнала (7.4 №1). Источник: ревью.
- `close()` подключения не закрывал живые подписки: с чужим пулом (`connect({ sql })`) они опрашивали журнал и после
  `close()`. Теперь подписки закрываются, ожидающий `next()` получает `done: true` (7.4 №8). Источник: ревью.

- `reclass` класса без ключа (id тот же) сигналил только новый класс: ответы кэша и подписки прежнего класса не
  сбрасывались и отдавали строку, которая из него ушла. Теперь сигнал идёт по обоим классам, как у пути через
  триггер (7.4 №4). Источник: ревью.

- `letopis types` падал на кириллическом имени класса (`invalid_class`, хотя такой идентификатор в TypeScript допустим),
  а для класса без полей, класса с `anyOf`/`oneOf` и открытой схемы выдавал неверный TypeScript
  (`export interface XData Record<string, unknown>`). Теперь имена — буквы Unicode, не-объекты — `export type`, ветки
  `anyOf` из одних `required` у класса с полями — условие, а не форма (7.5 №1). Источник: ревью.
- `hub('X', { fields: z.object(…) })` без других ключей описания читался как короткая форма — класс с единственным
  полем `fields`. Теперь это полная форма (7.5 №2). Источник: ревью.
- Понятные ошибки вместо сырых: `connect({ owner })` с ролью, которой нет, — `invalid_data`; `anonymize(['опечатка'])` —
  «поля нет в классе»; `up()` на готовой роли владельца без ADMIN OPTION — объяснение, что нужно; `auth.switch` при
  имперсонации сырым SQL — `acl_denied` из каталога, а не неизвестный код; `--trust` — `LetopisError` (7.5 №3).
  Источник: ревью.
- CLI: `letopis <команда> --help` возвращает код 0, неизвестная команда — справку с кодом 2 ещё до подключения к базе
  (7.5 №4). Источник: ревью.
- Сравнение имени проектора в `88-derived.sql` — той же коллацией, что индекс `secret_kind_ident` (7.5 №5). Источник:
  ревью.

- Срез `asOf` по классу и по концам показывал объект в классе, из которого он уже ушёл (`reclass` класса без ключа
  сохраняет id): последняя версия выбиралась среди версий классов шага. Теперь она выбирается среди всех версий id, и
  класс проверяется у неё — как уже делала ветка по id; то же в `trimHistory` по классам (7.1 №1). Источник: ревью.

- Имя поля, в котором есть `@S@` (например, `a@S@b`), портилось в запросе цепочки: построитель подставлял на это место
  имя схемы, и фильтр, `sort()` или агрегат по такому полю ничего не находили (7.1 №5). Источник: ревью.

### Изменено

## [1.4.1] — 2026-11-01

Исправления, найденные прогоном примеров документации для людей (`guide/`).

По правилам версий, введённым в 1.4.2, часть изменений этого выпуска требовала минора (ревизия движка 7 с миграцией
`0007`, новый метод `auth.session`), а новые отказы (`invalid_query` для модификатора после глагола, `acl_denied` для
удаления `Account` System, код 1 у `letopis types` и `letopis describe` без сессии) и убранный код `not_implemented` —
мажора.

### Добавлено
- `db.auth.session(token)` — сведения о сессии по её токену для сервиса: чья сессия (`account`), в каком арендаторе
  она работает (`tenant`), цело ли там членство (`member`; в собственном арендаторе — всегда `true`), когда она
  истечёт (`expiresAt`), когда и как был вход (`loginAt`, `methods`). Подключение по этому токену не открывается,
  срок сессии не продлевается. Неверный, погашенный или истёкший токен и отключённый аккаунт — `null`, причина не
  различается. Вызывает сервис или системный администратор (право `auth.session`, как у `sessionFor`); пользователю
  отвечают `acl_denied`, вызову без сессии — `no_session`. В базе — функция владельца `auth_session_info(text)`, в
  пакете — новый тип `SessionInfo`; в схеме метод появляется после повторного `up()`. Пробел нашли сервисы-примеры
  сайта (салон, helpdesk). Helpdesk теперь проверяет сессию в начале каждого запроса через `svc.auth.session(token)`,
  а не вызовом `auth.tenants()` по подключению пользователя.

### Исправлено
- `db.auth.purgeAccount(арендатор)` из сессии, которая работает в этом же арендаторе, откатывался с
  `tenant_denied` («нет членства в арендаторе»): функция стирала членство вызывающего вместе с данными, а
  надгробия и передача владения дальше перечитывали контекст. Теперь после проверки прав остаток операции идёт в
  личном арендаторе вызывающего, его сессия больше не указывает на стёртого арендатора, а корень подключения
  перечитывает арендатора и реестр. Подтверждает пример `guide/examples/auth/02-sessions-tenants.ts` (шаг 8):
  без исправления он падает.
- `commit()` явной транзакции (`db.begin()`), в которой ошибку поймали и проглотили, бросал сырую ошибку
  PostgreSQL `25P02` вместо обещанного README `tx_rolled_back`: чтение `letopis.changed` в одном конвейере с
  COMMIT падало раньше, чем COMMIT отвечал ROLLBACK. Теперь на `25P02` библиотека дожидается ответа COMMIT и
  бросает `tx_rolled_back`. Подтверждает пример `guide/examples/errors/01-api-errors.ts` (шаг 7): без исправления
  он падает с `25P02`.
- Порядок надгробий одного уровня каскада в журнале (`seq`, время `at`) и строк итога
  `delete({ confirm: true })` зависел от плана запроса и менялся от прогона к прогону: триггер удаления писал
  надгробия вставкой без `order by`, а превью при этом шло по id. Теперь надгробия каждого уровня пишутся в порядке
  id, итог — по уровням каскада, внутри уровня по id (README, раздел 7); цели классов без журнала — в конце, тоже по
  id. Подтверждают примеры `guide/examples/delete/01-delete-cascade.ts` и `02-restore-purge.ts`: без исправления их
  снимки то и дело расходятся порядком строк заказа.

- Порядок записей журнала у остальных массовых операций тоже определён, а не зависит от плана запроса: пакетная
  вставка — в порядке входа, правка многих строк, перестройка проектора, загрузчик с `existing: 'update'` — по id;
  смена владельца при выходе из членства и `purgeAccount` идут по арендаторам по порядку; глаголы по списку целей без
  `sort` (`restore`, `purge`, `reclass`, `rekey`) обходят цели по id.
- Подписка, к которой больше суток (яруса `all` политики хранения её классов) не было событий, получала ложный
  `cursor_expired`, хотя ничего не пропустила: время курсора оставалось временем последнего события, а база проверяет
  его на каждом опросе. Теперь подписка, догнав журнал, ставит в свой курсор время опроса — «сейчас», но не позже самой
  старой записи её классов, которая уже зафиксирована, а горизонт ещё не прошла; курсор события `ev.cursor` по-прежнему
  хранит время события. `sub.cursor` больше не обгоняет события, прочитанные в запас: он стоит после последнего
  события, которое отдал `next()`, поэтому продолжать после перезапуска нужно с него (README, раздел 12 «Подписка»).
  Подтверждает пример `guide/examples/watch/02-quiet-cursor.ts`: без исправления шаг 3 падает с `cursor_expired`.
- `connect({ maintain })` не проверял интервал: ноль, отрицательное число, `NaN`, `Infinity` или интервал длиннее
  2³¹−1 мс (`'25d'`, `'30d'`) таймер Node.js превращал в 1 мс, и обслуживание шло без перерыва, а `null` и `true`
  давали `TypeError`. Теперь интервал — число или строка, конечный, от 1 мс до 2³¹−1 мс (около 24 суток), иначе
  `invalid_data`; проверка идёт до открытия пула и таймеров. `close()` ждёт идущий по расписанию запуск: он доделывает
  текущую пачку и следующую не начинает, а пул закрывается после него. Подтверждает пример
  `guide/examples/install/03-connect-options.ts` (шаг 6): без исправления подключения с такими интервалами открывались.
- `createTenant` и `up({ tenant })` принимали любой `user.kind`: вид в другом регистре (`password`), пустой или
  служебный (`SESSION`, `TOTP` …). По такому паролю нельзя было войти, а служебным видом пароль выдавал себя за другой
  кред: с видом `TOTP` аккаунт выглядел так, будто у него включён второй фактор (`totpEnabled: true`), с видом
  `SESSION` пароль пропадал из `auth.credentials()`. Теперь вид проверяется по правилу функций кредов (`^[A-Z][A-Z0-9_]{1,31}$`, не `SESSION`, `APIKEY`,
  `KEYSECRET`, `OTP`, `TOTP`, `KEY`, `PROJECTOR`, `LOCK`), иначе `invalid_data` до записи. Подтверждает пример
  `guide/examples/install/01-up-and-connect.ts` (шаг 4): без исправления арендатор создавался.
- Параллельные `up()` разных схем одной базы падали с `tuple concurrently updated` (`XX000`): общую часть
  установки — роли `letopis_owner` и `letopis_app`, членство установщика, pgcrypto и право владельца на схему pgcrypto —
  каждый `up()` менял одновременно с другими, а `grant usage on schema` переписывает строку схемы в каталоге, даже если
  право уже выдано. На чистой базе так же столкнулись бы `create role` и `create extension`. Теперь общая часть — одна
  транзакция под advisory-блокировкой: следующий `up()` ждёт, пока предыдущий её зафиксирует. Блокировка действует в
  пределах базы, а роли общие для кластера, поэтому роль или членство, которые одновременно создал `up()` в другой
  базе, считаются уже созданными. Нашёл стенд сайта (`services/compose.yaml`): helpdesk падал при одновременном
  запуске четырёх сервисов; без исправления 4 из 8 параллельных `up()` падали в каждом круге.
- Одновременные `up()` одной и той же схемы (несколько экземпляров сервиса при запуске) падали: второй
  `create schema` — на уникальном индексе каталога (`23505`), второй `create or replace function` или `comment` —
  `tuple concurrently updated` (`XX000`), а `up({ tenant })` дважды вставлял того же арендатора. Ревизию, от которой
  считаются миграции, `up()` читал до наката, поэтому второй `upgrade` повторил бы миграции, уже накатанные первым.
  Теперь накат схемы — `fresh`, чтение ревизии, `create schema`, миграции, ядро, сиды и ключ сервиса — одна транзакция
  под advisory-блокировкой схемы (ключ — её имя), и `createTenant` берёт ту же блокировку. Следующий `up()` ждёт
  предыдущий и делает повторный накат по готовой схеме: `created` и `upgraded` он считает по ревизии, которую увидел
  под блокировкой. `up()` разных схем друг друга не ждут. Подтверждает пример
  `guide/examples/install/02-up-options.ts` (шаг 6): без исправления он падал 5 раз из 5.
- `out.delete` и `out.get` проектора у производного класса с ключом, получив один id (строкой или `{ $id }`), искали
  строку с пустым ключом: `get` отвечал `null`, а `delete` выводил арендатора с `id_mismatch`. Теперь это сразу
  `invalid_data` с перечнем полей ключа — ошибка кода `handle`, пачка откатывается целиком; строку класса с ключом
  называют полями ключа, id — только у класса без ключа (README, раздел 12 «Проекторы»). Подтверждает пример
  `guide/examples/derived/03-projector-options.ts` (шаги 3 и 4): без исправления `get` по id отвечал `null`, а
  `run()` проходил без ошибки.
- Строки `secret` удалённого аккаунта хранились вечно: удаление строки `Account` гасило сессии и ставило способам
  входа `deleted_at`, а `maintain()` физически убирает только сессии и коды вида `OTP` — хэши паролей и ключей,
  секреты TOTP и внешние учётные записи удалённого аккаунта оставались в базе. Теперь их уносит внешний ключ
  `secret.account → entity(id) on delete cascade` в том же операторе удаления. Сессии гаснут с сигналом
  `session:<хэш>` раньше каскада — в новом триггере `entity_bd_account` (до удаления, для всех ролей, в том числе
  владельца: аккаунты удаляют и каскад `trg_entity_ad`, и `purgeAccount`), поэтому процессы по-прежнему сбрасывают кэш
  ответов этих сессий; пометка `deleted_at` в триггере удаления снята. Первая заливка снимает внешний ключ до `TRUNCATE`
  и возвращает его после первичного ключа `entity`; `letopis import` пропускает креды аккаунтов, которых нет в
  `Account` версии 0.21 (считает их в `skipped`). Подтверждает пример `guide/examples/auth/03-delete-account.ts`: без
  исправления шаг 3 находит в `secret` три строки удалённого аккаунта, а шаг 4 не получает `acl_denied`.
- Описание `maintain()` в README расходилось с кодом и JSDoc: он удаляет не только истёкшие сессии и коды, но и
  погашенные сессии и использованные, заменённые или исчерпавшие попытки коды вида `OTP`. В README перечислены и
  занятые виды кредов `PROJECTOR` и `LOCK`.
- `.tags(has(…))`, `.tags(hasAny(…))` и `.tags(hasAll(…))` перед `update()` падали сырой ошибкой Node.js
  `ERR_INVALID_ARG_TYPE`: оператор отбора библиотека пыталась записать в колонку тегов. Теперь оператор перед
  `update()` только отбирает строки, а их теги не меняются; строка или список, как и раньше, и отбирают строки, и
  заменяют их теги целиком. Подтверждает пример `guide/examples/write/05-batch-tags-reason.ts` (шаг 6): без
  исправления он падает.

- Срез `asOf()` и надгробия `withDeleted()` на обратном переходе отдавали объект столько раз, на сколько объектов
  прошлого шага он ссылается: товар в двух категориях на шаге `db.Category().Product().asOf(t)` приходил в `rows()`
  дважды, `count()` и итоги его удваивали. Без среза повторы отбрасывались, а пары переходов среза журнала шли в узел
  как есть. Теперь узел — одна строка на объект, `paths()` по-прежнему отдаёт путь на каждую ссылку. Подтверждает
  пример `guide/examples/history/01-versions-asof-diff-blame.ts` (шаг 6): без исправления он падает.
- Строки ответа `update()` и `anonymize()` шли в порядке обхода таблицы, а не целей, поэтому `first()` после глагола
  отдавал случайную из исправленных строк. Теперь ответ — в порядке целей: по `sort()` до глагола, без него — по id.
  Подтверждает пример `guide/examples/write/01-create-update-upsert.ts` (шаг 7): без исправления он падает.
- `maintain()` удалял только одноразовые коды вида `OTP`, а использованные и истёкшие коды своих видов `OTP_<ИМЯ>`
  (`auth.issueOtp({ kind })`) оставались в `secret` навсегда. Теперь он удаляет коды всех видов, которые выпускает
  `issueOtp`. Подтверждает пример `guide/examples/auth/01-login-factors.ts` (шаг 6): без исправления он падает.
- `min()` и `max()` по логическому полю падали сырой ошибкой PostgreSQL (у `boolean` нет `min` и `max`). Теперь
  `false` меньше `true`: `min` — `false`, если есть хоть одно `false`, `max` — `true`, если есть хоть одно `true`.
  Подтверждает пример `guide/examples/read/03-sort-pages-aggregates.ts` (шаг 7).
- `verifyHash()` и вход `auth.verifyPassword()` по хэшу scrypt, которому нужно больше 64 МБ памяти или с
  недопустимыми N, r, p, бросали сырую ошибку Node.js; теперь — `invalid_data` с объяснением. `compileValidator()` с
  шаблоном `pattern`, неверным для JavaScript, бросал `SyntaxError`; теперь — `invalid_class` с путём поля.
  Подтверждает пример `guide/examples/models/06-exports.ts` (шаги 3 и 5).

### Изменено
- `letopis types` и `letopis describe` без действующей сессии (токен истёк, погашен, неверен или не задан) выдавали
  пустой результат с кодом 0, а с `--out` затирали им файл. Теперь они выходят с кодом 1 и ошибкой `no_session`, файл
  не трогают. Подтверждает пример `guide/examples/ops/04-cli.ts` (шаг 5).
- `connect()` на схеме, ревизия которой новее пакета (её обновил более новый пакет), молчал; теперь он подключается и
  предупреждает «обновите пакет letopis», как предупреждает об отставшей схеме. Подтверждает пример
  `guide/examples/install/05-engine-stamp.ts` (шаг 4).
- Описания методов (JSDoc), которые справочник сайта показывал непонятными, переписаны простыми словами: цепочка и
  операторы фильтра, `db.as`, `db.verify`, `db.reset`, `db.trimHistory`, способы входа, подписка, проектор, загрузчик,

  новый ключ сервиса выпускается на любом накате, где не осталось ни одного неотозванного ключа API.
- README: ключ сервиса `up()` выдаёт, когда не осталось ни одного ключа API, кроме отозванных (истёкший или
  выключенный ключ тоже в счёт), — было «действующего»; класс из `into` проектора источником не бывает, даже если
  попадает в `from`, — было «не может быть одновременно источником и результатом», будто это запрет.
- Модификатор выборки (`limit`, `offset`, `sort`, `after`, `asOf`, `withDeleted`, `cache`) сразу после глагола, за

  остальные молча пропускались, а у `ids` и `count` — и `limit`. Цели глагола сужают модификаторы до него. В батче
  так же отказывает `run()`. После глагола модификатор по-прежнему действует на чтение за ним (шаг класса,

  `guide/examples/write/01-create-update-upsert.ts` (шаг 8) и `guide/examples/write/05-batch-tags-reason.ts`

- Ревизия движка 7: внешний ключ `secret.account` (миграция `0007` сначала стирает строки `secret`, чьих аккаунтов уже

- Убран код ошибки `not_implemented` (охранник `notYet`): в 1.4 его не бросал ни один метод.
- Тексты для людей:
  - ошибка снятой опции `connect()` согласована по роду: «опция connect({ … }) снята в 1.0.0»;

letopis 1.4 — доработки после выпуска 1.3.0. Вошли:

Версия `1.4.0` (во время работы — `1.4.0-alpha.0`, не публиковалась). Схема 1.3.0 обновляется повторным `up()`:
ревизия движка прежняя (6), функции накатываются заново. До наката `connect()` новой версии предупреждает о схеме без
штампа и советует `up({ schema })`. Новое в API:
- опция проектора `lockRetries` и поле отчёта `ProjectorReport.locked`;
- штамп движка в комментарии схемы и предупреждение `connect()` о схеме другой версии.

Поведение, которое стоит проверить при обновлении:
- на подключении, где роль приложения поставлена поверх привилегированной роли входа (`SET ROLE`, параметр запуска
  `role`), пользователи больше не получают права `letopis.*`;
- новый источник агрегата должен без условий читать и тот, кто описал агрегат, иначе `acl_denied`; агрегат можно
  описать заново от того, кто читает;
- предки и алиас класса System больше не дают прав на строки одноимённого класса арендатора;
- запись, дождавшаяся удаления своего класса, получает `invalid_class` «класс … удалён».

### Added — проектор: изоляция арендаторов при чужой блокировке
- Опция проектора `lockRetries` (решение владельца, кандидат 6 из 10 «`lockTimeout` не изолирует арендаторов»). Задаёт,
  сколько проходов подряд запись одного арендатора может упираться в `lockTimeout`. Дальше арендатор выбывает с кодом
  `55P03`, и пачка идёт для остальных; его изменения пропускаются до `rebuild({ tenant })`. По умолчанию 0: арендатор
  не выбывает, и проход повторяется для всех, как раньше. Счёт ведёт процесс, удачная запись арендатора его
  сбрасывает.
- Отчёт `run()` называет арендаторов, на чьей строке вставала пачка: новое поле `ProjectorReport.locked`.
- `rebuild({ tenant, chunked: true })` пережидает чужую блокировку строки арендатора (кандидат 5 из 10). Раньше
  `startTenant` отдавал вызывающему сырую ошибку 55P03, хотя состояние не портилось. Так же ведёт себя чтение
  чекпоинта в конце перестройки, а пропущенные из-за блокировки проходы идут в `skipped`.

### Added — штамп движка в схеме
- `up()` пишет в комментарий схемы, кроме ревизии, штамп движка: версию пакета и 16 знаков sha256 исходного текста
  файлов `sql/NN-*.sql` (`'letopis ddl_revision=6 engine=1.4.0 sql=…'`). Ревизия у 1.1–1.4 одна, а функции разные, и
  `connect()` раньше не замечал схему, которую после обновления пакета не накатили (так было при 1.1 → 1.2).
- `connect()` при той же ревизии сверяет штамп с файлами своего пакета и при расхождении предупреждает
  (`console.warn`). Схема без штампа (до 1.4) или со штампом более старой версии — совет `up({ schema })`. Штамп более
  новой версии — совет обновить пакет: `up()` старой версией вернул бы прежние функции. Новая версия пакета без правок
  SQL штамп не меняет. Если файлов SQL рядом со сборкой нет, сверка молча пропускается.

### Security — хвост ревью безопасности доработок после 1.2.0
- `purge` и `trimHistory` проверяют, прочёл ли проектор источника каждую версию строки, а не одну (кандидат 5 из 10).
  Раньше `purge` смотрел только надгробие, а обрезка — самую позднюю по `(tx, seq)` версию у стыка. Но у более поздней
  версии бывает меньший xid, а снимок перестройки учитывает транзакции, зафиксированные до него. Поэтому непрочитанной
  могла остаться версия, которую проверка пропускала, и `purge` или обрезка стирали её. Проверку делает функция
  владельца `projector_unread(uuid, uuid, int)`, прежняя `projector_behind` удаляется при накате.
- Удаление класса больше не расходится с параллельной записью (кандидат 5 из 10, «гонка смены алиаса и удаления
  потомка»). Удаление проверяет, что у класса нет строк, потомков и истории, но раньше проверка не видела строку, которую
  писатель ещё не зафиксировал: строка оставалась без класса, а вместе с ней появлялась история удалённого класса, от
  которой зависит запрет смены алиаса предка. Теперь так:
  - удаление класса берёт исключительную блокировку его семейства, поэтому ждёт писателей и видит их строки;
  - создание класса и смена `parent` берут разделяемую блокировку семейства родителя, поэтому родитель не удаляется мимо
    нового потомка;
  - писатель, дождавшийся блокировки, проверяет, что класс ещё есть (`invalid_class`, «класс … удалён»). Так делают
    вставка, правка, `reclass`, `restore`, `rekey` и запись проектора.
- План прав берёт один класс на имя — тот, что находит `class_row`: свой класс арендатора, иначе класс System (замечание
  `/security-review` ниже порога). Раньше в план попадали оба одноимённых класса, и побеждало разрешение любого из них.
  Поэтому предки и алиас класса System, заведённого после класса арендатора, давали права на строки класса арендатора.
- Правка класса System без права `letopis.projector` больше не упирается в производных потомков у арендаторов со своим
  одноимённым классом (кандидат 5 из 10, лишняя строгость): их потомки наследуют класс арендатора, а не класс System.
- Подписка подключения в обход RLS получает события ухода строки из классов подписки (кандидат 6 из 10). Раньше без
  сессии `watch_leaving` их не отдавал (`acl_actor` — null), хотя `watch_read` такому подключению отдаёт журнал всех
  арендаторов. Теперь роль сеанса (суперпользователь, `BYPASSRLS`, член роли-владельца) видит все события ухода, с
  автором.
- Администратором и подключением в обход RLS база считает действующую роль сеанса, а не роль входа (находка
  автоматического ревью коммита). Внутри функции владельца `session_user` — роль входа, даже если поверх неё поставлена
  роль приложения (`SET ROLE` или параметр запуска `role`). Так бывает у пула с одной привилегированной ролью входа: там
  `connect()` видит роль приложения, а `admin_role()` с 1.0 видела суперпользователя. Поэтому любой пользователь
  арендатора на таком подключении получал права `letopis.*` (`verify`, `reset`, `letopis.projector` и другие), а
  подписка — события ухода чужих арендаторов. Новая функция владельца `session_role()` берёт роль `SET ROLE`, иначе роль
  входа; через неё работают `admin_role()` и `watch_leaving`.
- Новый источник агрегата проверяется и по тому, кто описал агрегат (кандидат 6 из 10, решение владельца). Раньше право
  `READ` проверялось только у того, кто заводит потомка источника (или переносит класс под него сменой `parent`). Тот,
  кто описал агрегат без права на строки будущего потомка, читал бы в истории цели вклад каждой из них. Теперь
  описавший тоже должен без условий читать все строки нового источника, иначе `acl_denied`; агрегат можно описать
  заново от того, кто их читает. Описавший — автор версии строки `Class` цели, с которой описание агрегата (своё или
  унаследованное) стало нынешним; журнал строк `Class` не стирается. Объём проверки — как при описании: у агрегата
  класса арендатора — классы арендатора, у агрегата класса System — классы System; класс арендатора под агрегатом System
  проверяет только заводящий.

### Fixed — хвост ревью безопасности доработок после 1.2.0
- `syncModels` отклоняет модели по кругу до записи: `invalid_class` называет круг (кандидат 4 из 10). Пример — агрегат
  над собственным потомком: потомок ждёт родителя, а цель ждёт источник агрегата. Раньше обход молча ставил потомка
  раньше предка, и база отвечала «предок … не найден». В два шага такой агрегат отклоняет уже база: потомок наследует
  агрегат над самим собой, и выходит «цикл агрегатов».

  Класс выбирает новая функция владельца `visible_class(jsonb)`. Атака №47.
- Класс System и одноимённые классы арендаторов (кандидат 6 из 10). Раньше `class_has_history` и проверка «есть строки
  или потомки» при удалении класса System считали журнал, строки и потомков любого арендатора по имени. Поэтому
  арендатор с собственным классом `Invoice` и историей его строк не давал администратору создать или удалить System
  `Invoice`. Теперь строки, потомки и история арендатора со своим одноимённым классом не в счёт: так их резолвит
  `class_row`. Строки класса System у арендатора без своего класса по-прежнему мешают. Атака №48.
- Надгробие класса (кандидат 5 из 10). Класс, удалённый с историей строк, создаётся заново только с прежней
  политикой хранения `history` вместе с прежними `parent`, `alias` и `derivedBy`. Иначе `maintain()` прореживал бы его
  старые версии по другой политике.

  Алиасы предков в надгробии не записаны, поэтому дыра закрыта со стороны предка. Пока удалённые потомки класса
  хранят историю строк, класс не меняет алиас (`invalid_class`). Удалённый, он создаётся заново только с описанием из
  своего надгробия, даже без собственной истории. Удалённых потомков находит новая функция владельца
  `class_orphan_history(text, uuid)`. Атака №49.
- Производный класс через непроизводного предка (кандидат 5 из 10). Правка предка пересчитывает описание потомка
  (`class_evolve`): поля, ключ и `history`. Поэтому класс, у которого есть производные потомки, теперь тоже правит
  только администратор, с правом `letopis.projector`. Потомки учитываются своего арендатора, у класса System — всех.
  Иначе `acl_denied`. Атака №50.
- `family_conflicts` (кандидат 4 из 10). Конфликт смены `parent` (`tightening_conflict`) раньше называл роль невидимой
  ссылающейся строки. Теперь о ней в тексте нет ни роли, ни id. Видимые ссылающиеся строки идут первыми, затем по id:
  раньше бралась первая попавшаяся. Атака №51.
- Агрегат над ещё не созданным классом источника (`/security-review`, кандидат 5 из 10). Раньше `class_admit`
  проверял право READ описывающего агрегат только по уже существующим классам `of`. Пока класса не было, проверять
  было нечего. Когда источник потом заводил пользователь с полным READ, проверялись только его права, и описавший
  агрегат читал в истории цели вклад каждой строки источника.

  Теперь новый или изменённый агрегат, у которого нет ни класса `of`, ни его потомков, отклоняется
  (`invalid_class`, «класс-источник описывают раньше агрегата»). У класса арендатора они ищутся среди классов
  арендатора, у класса System — среди классов System. `syncModels` (`letopis sync`) теперь описывает класс-источник
  раньше цели, в каком бы порядке ни пришли модели. Атака №52, тест `sync`.

  Класс `of` проверяется только при описании агрегата. Поэтому класс-источник теперь не удаляется, пока его называет
  агрегат класса того же арендатора (`invalid_class`): иначе пустой класс удалили бы, а класс с этим именем завёл бы
  заново другой пользователь, например под другим `parent`. Это нашло автоматическое ревью коммита. Агрегаты
  классов System описывает системный администратор, он и так читает всё. Атака №53.
- Прерванная `rebuild({ tenant, chunked: true })` (кандидат 6 из 10). Раньше её продолжал только `run()` с
  `onExpired: 'rebuild'`. Без этой опции хвост бессрочно пропускал изменения арендатора с id выше последней пачки.

  Теперь начатую перестройку арендатора продвигает `run()` любого процесса. Запуск перестройки выбывших по ярусу
  по-прежнему только с `onExpired`. Если блокировку проектора держит другой процесс (`busy`), `run()` перестройку
  не трогает и чекпоинт не читает: иначе второй процесс ждал бы пачку первого. Тест `projector`.
- Нет `lock_timeout` у транзакций проектора (кандидат 6 из 10). Пачка всех арендаторов ждала блокировку строки,
  которую держит транзакция любого арендатора. Новая опция `ProjectorOptions.lockTimeout`: сколько ждать, по
  умолчанию 5000 мс, 0 — без предела. Её ставит `set local lock_timeout` в каждой транзакции проектора.

  На 55P03 пачка откатывается, курсор остаётся, арендатор не выбывает. `run()` не отклоняется, а считает проход
  пропущенным (`skipped`) и повторяет его; `rebuild({ tenant, chunked: true })` повторяет пачку. Держащая
  транзакция и так держит горизонт подписок, поэтому ждать имеет смысл только запись, зафиксированную раньше неё.
  Тест `projector`.
- `trimHistory` версий, которые проектор ещё не прочёл (кандидат 5 из 10). Первая оставшаяся версия пришла бы
  проектору с `before` = `null`, и свёртка прибавила бы её, не вычитая прежнюю. Теперь `trim_history` отказывает
  `projector_pending`, пока проектор источника не прочёл первую оставшуюся версию. Класс проверяется у обеих версий
  стыка, потому что строка могла уйти из семейства источников сменой класса.

  Проверку `purge` и обрезки делает общая функция владельца `projector_behind(uuid, text[], xid8, bigint)`.
  `rebuild({ tenant, chunked: true })` засчитывает завершённую перестройку, даже если последнюю пачку записал `run()`
  другого процесса. Тест `projector`.
- `as()` арендатора корня (кандидат 5 из 10). Фасад `db.as()` того же арендатора, что и корень, получал сам реестр
  корня. После `auth.switch()` корня он видел классы нового арендатора. Теперь у фасада свой реестр из кэша
  арендатора. Тест `impersonation`.
- Пустой реестр `as()` (кандидат 4 из 10). Если на первой загрузке контекст сессии уже ушёл из арендатора (сменился
  или кончился), пустой реестр кэшировался и не перечитывался. Теперь он не кэшируется: `as()` читает контекст
  заново, не больше трёх раз, затем отказывает `no_session`. Тест `impersonation`.
- Подписка и смена класса без смены id. Раньше `db.watch()` по классам не видел ухода строки из класса: версия
  пишется уже с новым классом. Теперь такой уход приходит событием удаления в прежнем классе (`op: 'delete'`, `row` —
  прежняя версия с `$deleted`, автор и время — версии смены класса). Событие приходит, даже если новый класс
  подписчику не виден, но только если прежнюю версию он видел.

  Уход находит новая функция владельца `watch_leaving`, выданная приложению. Окно у неё то же, что у `watch_read`, и
  ограничено полной пачкой, поэтому догонка с `'start'` не читает журнал заново на каждой пачке. Подписка сливает
  оба потока по `(tx, seq)`. Тесты `watch` (уход в видимый и в невидимый класс, уход в чужом арендаторе, вход в
  класс) и `roles`.

  Ревью безопасности доработок нашло ошибку в подписке, исправлена до выпуска. `watch_read` и `watch_leaving` идут
  одним оператором с общим снимком: двумя запросами с разными горизонтами курсор мог перескочить событие,
  зафиксированное между ними. Если новую версию подписчик не видит, надгробие приходит при любых классах подписки и
  без автора: иначе перебором классов он узнал бы новый класс.
- Обрезка истории проверяет курсор проектора по самой поздней по `(tx, seq)` версии у стыка: у более поздней версии
  бывает меньший xid.

### Changed
- Порядок описания агрегата: класс-источник — раньше цели (раньше источник можно было описать позже, и он
  сверялся при появлении). Классы с концом на ещё не созданный класс по-прежнему описываются, поэтому пара «цель —
  источник с концом на цель» описывается в порядке «источник, цель». Тесты `aggregate` и бенч `derived` описывают
  классы в этом порядке.

### Added — этап 4а (проекторы)
- `db.projector(имя, { from, into, version, handle, withBefore, onExpired, batch, pollMs })` — проектор из журнала
  (`lib/src/project.ts`): строит строки производных классов из изменений классов-источников. `run()` догоняет
  журнал и следует за ним до `stop()`, `run({ once: true })` только догоняет; `rebuild()` и `rebuild({ chunked: true })`

  не начать: проектор сейчас работает в другом процессе).

### Added — этап 4б (агрегаты в базе)
- Опция класса `aggregate: { поле: { sum: 'поле' | count: true, of: 'Класс', via: 'роль', where?: JSON Schema } }`:
  поле держит сама база — сумма поля или число живых строк класса-источника (с потомками) того же арендатора, чей
  одиночный конец `via` ведёт на строку и чьи данные проходят `where`. Строка System в агрегат не входит. Опция
  наследуется, потомок заменяет её целиком; её показывают реестр (`ClassInfo.aggregate`), `db.describe()` и
  `describeText()`; в `letopis/model` — `ClassDef.aggregate` и тип `AggregateDef`, экспорт типа `AggregateInfo`.
- Триггеры `entity_total_ai`, `entity_total_au`, `entity_total_ad` (`lib/sql/88-derived.sql`): после оператора, с
  переходными таблицами, без условия `WHEN` — срабатывают и для владельца (каскад удаления, `restore`, `reclass`,
  `rekey`, удаление аккаунта, загрузчик), `enable always`. Вклады строк оператора складываются по цели, цели
  блокируются в порядке id, итог проверяет описание класса цели (`minimum: 0` → `invalid_data`), версия цели —
  `sys_update` с автором и причиной операции. Новая цель оператора (вставка, `restore`, смена класса) считается
  целиком из живых источников в ту же версию. Перенос строки (`move_row`) копит вклады до своего конца и применяет их
  одним итогом — промежуточная сумма не выходит за правило класса.
- Проверки описания агрегата (`invalid_class`): поле есть в схеме, числовое и не в ключе; ровно одно из `sum` и
  `count`; конец `via` источника одиночный и принимает класс цели; поле `sum` — число; нет цикла агрегатов; цель и
  источник не системные и не производные; агрегат арендатора не считает классы System. Источник, описанный после
  цели, сверяется при появлении; его класс получает метку `resolved.aggregatedBy`.
- `db.rebuildAggregates(класс)` — ремонт: поле класса и его потомков во всех арендаторах заново из живых источников
  под исключительными блокировками, версия только у исправленных; возвращает их число. Только администраторское
  подключение (иначе `admin_required`); функция владельца `rebuild_aggregates`. Зарезервированное имя корня
  `rebuildAggregates`.
- `verify({ data: true })` сообщает расхождения агрегатов: `{ id, class, field, stored, expected, problem }`.
- Код ошибки базы `LT022` `aggregate_field`: приложение передало или изменило агрегатное поле.

  пересчитывает: строки арендатора уходят вместе с целями.
- Ревью коммита этапа 4б: агрегат считают функции владельца по всем строкам источника, без прав чтения, и описание с
  `where` выдавало суммы и счётчики по строкам, которые автору не видны. Теперь строки попадают в агрегат только с
  ведома того, кто читает их все. Описать или изменить агрегат может только тот, у кого право READ без условий на все
  строки каждого класса-источника (класс `of` и его потомки) — и свой агрегат, и унаследованный (новый потомок цели,
  смена `parent`); неизменённый агрегат при правке описания не проверяется. Сделать класс источником (новый класс, смена `parent`, источник после цели) можно только с таким правом
  на этот класс и его потомков — до правки, по прежним предкам, и после. Иначе `acl_denied` (`class_admit`, а для
  нового класса и новых предков — `agg_source_admit` в триггерах после оператора и в `class_evolve`). Агрегат класса
  арендатора считает только классы своего арендатора — везде одинаково (`agg_prepare`, `agg_classes`, `agg_compute`,
  `agg_apply`, `agg_fill`, `agg_cycle`): класс System с именем `of` его источником не бывает. Поэтому такой агрегат
  больше не останавливает установку и правку классов System (`agg_source` его пропускает, а не отвечает
  `invalid_class`), не расходится с `verify` и `rebuildAggregates` и не мешает арендатору править цель.

### Security — ревью безопасности №2
- Н1 (проекторы, отказ в обслуживании между арендаторами). Участником проектора становится любой арендатор, который
  пометит свои классы его `derivedBy`, а пачка всех арендаторов была одной транзакцией и одним `derived_apply`: ошибка
  данных одного (например, `DayTotal` с `maximum: 0`) откатывала пачку, курсор стоял, `rebuild()` падал, перестройка
  пачками успевала стереть производные строки всех и оставалась в `rebuilding`, а `status()` молчал. Теперь
  (`lib/src/project.ts`: `apply`, `atomic`, `chunked`) пачка делится по арендаторам: `handle` получает изменения одного
  арендатора, запись его результатов идёт под точкой сохранения. Ошибка данных арендатора — отказ базы при записи его
  результатов (коды letopis, неверные значения, пределы размера) или отказ `out` по его строке или приращению —
  откатывает только его группу: арендатор выбывает — `meta.failed[арендатор] = { cursor, code, message }` пишется в
  чекпоинт в той же транзакции — и пропускается до `rebuild({ tenant: id })`, а остальные записываются. `status()`
  отдаёт `failed`. Производные строки выбывшего больше не меняются: выбывший в `run()` сохраняет их на момент до
  пачки с ошибкой, а выбывший посреди перестройки остаётся без них (частично построенные удаляются). Новая опция
  `rebuild({ tenant })` перестраивает одного арендатора одной транзакцией: удаляет его производные строки, строит их из
  его текущих строк источников и снимает отметку; снимок перестройки встаёт в чекпоинт (`meta.resync`), и хвост
  журнала не применяет учтённые изменения второй раз. Полная перестройка начинает всех участников заново. Текст ошибки
  `derived_apply` называет проектор, арендатора и id строки, а `fromDbError` сохраняет у `ValidationError` текст базы
  целиком. Опция `tenants` в `ProjectorOptions` — явный список участников. Исключение `handle`, нарушение границ `out`
  и сбой окружения (взаимная блокировка, отмена запроса, обрыв связи) по-прежнему откатывают пачку целиком: это не
  данные арендатора, и выводить его из проекции не за что. Тип `ProjectorFailure`.
- Н1, продолжение: ярус журнала и журнал источников — по арендатору. Тем же путём арендатор останавливал проектор
  описанием своих классов: предел `cursor_expired` был общим — самый короткий ярус `all` политики хранения источников
  всех участников, и ярус в одну секунду у классов одного арендатора ронял `run()` для всех (а при
  `onExpired: 'rebuild'` зацикливал полные перестройки). Теперь ярус — по арендатору (`resolve`, `step`): курсор старше
  яруса у всех участников — `cursor_expired`, как прежде; у части — выбывают они с кодом `cursor_expired`, а с
  `onExpired: 'rebuild'` перестраиваются сами, каждый своей транзакцией (`rebuild({ tenant })`). Источник без журнала
  (`history: false`) проектор принимал молча: изменений такого класса он не видит, и проекция арендатора расходилась с
  данными. Теперь такой арендатор выбывает с кодом `invalid_class` (и при перестройке, атомарной и пачками), его
  производных строк нет, а `rebuild({ tenant })` отказывает, пока журнал класса не включат.
- Н2 (известна с 1.0). Право WRITE на `Class` позволяло сменить у класса `parent` или `alias`, и его строки попадали
  под правила READ, WRITE и DELETE нового предка или алиаса: план прав берёт для класса имена предков и их алиасы.
  Теперь `class_admit` при правке, которая меняет `resolved.ancestors`, `alias` или `resolved.derivedBy`, зовёт функцию
  владельца `class_acl_admit` (`lib/sql/60-write.sql`, по образцу `agg_source_admit`): для самого класса и каждого его
  потомка своего арендатора `acl_check_data` по READ, WRITE и DELETE должна разрешать без условий, иначе `acl_denied`;
  потомки класса System у арендаторов пропускаются, как у агрегатов. Проверка идёт после проверок агрегатов. Алиас не
  совпадает с именем другого класса (в том числе `Class` и системных) и с чужим алиасом арендатора и System —
  `invalid_class`, и у нового класса тоже. И наоборот: имя класса не совпадает с чужим алиасом арендатора и System
  (автоматическое ревью коммита `6c66d02`): иначе правило, написанное для нового класса, действовало бы и на строки
  класса с этим алиасом. `class_acl_admit` — не `security definer`: приложению она не выдана, словарь
  негативных тестов `roles` №4 не изменился.
- О1. Чекпоинт проектора искался по виду `PROJECTOR` и имени, без аккаунта. Теперь `projector_state`,
  `projector_advance` и `status()` берут только строку System. Накат помечает удалёнными строки `PROJECTOR` других

  уникальный индекс `secret_kind_ident` не дал бы записать свою.
- О2. `derived_clear` удалял строки всех классов с пометкой проектора во всех арендаторах. Теперь
  `derived_clear(имя, арендаторы[], классы[])` удаляет только пары «арендатор, класс», которые передаёт проектор

- Ревью безопасности №3, №2 (было до 1.2): внутренние блокировки — семейства классов (`family_lock`), проектора и
  обслуживания — больше не advisory, а строки-замки: строки вида `LOCK` таблицы `secret`, которой у приложения нет
  (`lock_row`, `lock_try`). Advisory-блокировку берёт любая роль базы, а её ключ виден всем в `pg_locks`: посторонняя
  роль занимала блокировку с ключом из `hashtext` открытого имени (или подсмотренным) и останавливала запись
  семейства, проектор или обслуживание для всех. Писатели берут строку-замок семейства `for key share`, ужесточение и
  `rekeyClass` — `for update`. Строковые блокировки очереди не держат — поток записей не дал бы ужесточению случиться
  никогда, — поэтому ужесточение сначала занимает шлюз семейства (вторую строку-замок), и новые писатели ждут у него.
  Писатель проходит шлюз в подтранзакции один раз за транзакцию: справка о взятых блокировках
  (`letopis.family_locks`) пропускает только шлюз, а строку-замок функция берёт на каждую строку — повторно взятая
  своя блокировка не ждёт. Справку клиент выставляет сам, и в первой редакции, где по ней пропускалась и блокировка,
  запись с подделанной справкой шла мимо ужесточения (автоматическое ревью коммита 1bc6584). Строки-замки заводятся
  заранее — при записи строки `Class` и в `seed_system()` (установка, `up()` после обновления, `reset({ all })`).
  Блокировку обслуживания берёт сама функция `maintain()`. Цена — строковая блокировка на строку записи и
  подтранзакция на первую запись в семейство за транзакцию; замер (`bench/family-lock.bench.mjs`, медиана трёх
  кругов) — в пределах шума против advisory 1.1: построчная запись 159 и 157 строк/с, 20 писателей 576
  и 544 строк/с, 1000 строк одним оператором 303 и 300 мс (`bench/results/family-lock.md`). id строки-замка —
  `lock_id`: первые 16 байт `sha256` имени (с `v5_id` вставка 1000 строк одним оператором стоила 352 мс против 321).

- `blame` и `diff_versions` — без JIT (`set jit = off`), соседние версии — окном `lead()`: `blame` по 1000 версиям —
  13,5 мс вместо 264, по 10 000 — 0,12 с вместо 1,5 (`docs/checkpoint-1.1.md`).

### Tests — этап 1

### Added — этап 2 (режимы сигналов)
- Режим сигналов установки `up({ signals })`: `class` (по умолчанию, как в 1.0) — имя класса, `tenant` — имя класса
  и токен арендатора, `opaque` — только токены, `none` — сигналов нет. Токен — первые 96 бит HMAC-SHA256 на ключе
  сигналов, выведенном из ключа строки `secret` с id System: без ключа псевдоним не сопоставить с именем, а
  одинаковые сигналы транзакции PostgreSQL по-прежнему склеивает. Режим хранится в схеме (`meta` строки ключа):
  повторный `up()` без опции его не меняет, `reset({ all })` сохраняет.
- Ключ сигналов — функция владельца `signal_key()` и право `letopis.signals` (системный сид выдаёт его сервисам:
  ресурс `signals:API`, правило для `service:ACCOUNT`). Процесс с ключом сбрасывает кэш с точностью до арендатора
  (строки System — во всех) и узнаёт классы по токенам; процесс без ключа сбрасывает класс во всех арендаторах, а в
  режиме `opaque` — весь кэш на любой сигнал. Реестр, ключ и пропуска прав по `*`, незнакомым токенам, нагрузке не
  своего режима (и у процесса без ключа в `opaque` — по любому сигналу) перечитываются не чаще раза в 5 с.
- Режим `none`: без LISTEN и без отправки сигналов, кэш только по сроку (`ttlOnly`), подписка опрашивает журнал,
  реестр раз в 5 с сверяет отпечаток классов `class_stamp()`.
- Подписка просыпается только от своих классов и своего арендатора; без ключа — от любого сигнала, кроме сессий.
- `UpResult.signals`, `UpResult.warnings`, `InstallResult.signals`; `up()` предупреждает о PostgreSQL ниже 18.2
  (сервер мог усечь CLOG, который ещё нужен непрочитанным сигналам), `checkServer()` возвращает предупреждения.
  Тип `SignalMode`.
- Функции базы `signal(классы, арендаторы)` вместо `signal(классы)`, `signal_raw()`, `signal_token()`,
  `signal_mode()`, `signal_key()`, `class_stamp()`; маркер установщика `@SIGNALS@`.
- Замер `bench/signals.bench.mjs` (`docs/checkpoint-1.1.md`): цены режима в скорости записи не видно на фоне шума;
  `signal()` в режимах `tenant` и `opaque` дороже на 15 и 26 мкс на оператор; при записи одного арендатора ответы
  другого остаются в кэше процесса с ключом (100 % попаданий против 0 % в режиме `class`).

### Changed — этап 2

## [1.0.0] — 2026-10-09

letopis 1.0 — новая реализация хранилища по плану `reports/PLAN-LETOPIS-1.0.md` (редакция 8), основанному на
предложении «Свод» (`reports/PROPOSAL-SVOD.md`). Целостность, история, изоляция арендаторов и права проверяет
сама база — и для библиотеки, и для сырого SQL. Переход с 0.21 — [MIGRATION.md](MIGRATION.md): импорт данных
командой `letopis import` и таблица замен API. Подробная запись по этапам — ниже, в `[1.0.0-alpha.0]`.

### BREAKING — платформа и хранение
- PostgreSQL 18 и новее, Node 22 и новее. TimescaleDB, Redis и Docker не нужны; рантайм-зависимость одна —
  `postgres`; fastest-validator заменён JSON Schema, модели на Zod 4 — необязательная peer-зависимость
  (подпуть `letopis/model`).
- Три таблицы: `entity` (текущие версии), `log` (журнал) и приватная `secret` (креды и сессии) вместо `Schema`,
  `Entity`, `Account`, `Credential`, `Resource`, `Rule`. Классы, аккаунты, ресурсы и правила — строки системных
  классов. Колонки `partition` нет: отдельные пространства — отдельные схемы `v2.<имя>`. Схема 0.21 на месте не
  обновляется — данные переносит `letopis import`.
- Журнал без партиций и политик TimescaleDB; хранение истории — политика «все версии — по дню — по неделе — по
  месяцу — по году» (`history: { all, daily, weekly, monthly, yearly, tz }`), прореживает `maintain()`.
  `compact()` снят: обрезка — `db.trimHistory()`, отказ от истории — `history: false`, который теперь отключает
  и `versions`, `asOf`, `restore`, события подписки.
- `up()` без Docker и без сидов по умолчанию: демо-домен — только `seeds: ['booking']`; схема — `v2.<имя>`.

### BREAKING — идентификаторы и уникальность
- Только v5: id объекта класса с ключом — v5 от имени класса и значений ключа как есть в пространстве арендатора
  (`idOf`); у класса без ключа id выдаёт база. v4 и v7, `generate` и `from` ушли; `uuidv7()` и `LETOPIS_NS` —
  охранники `removed`. Переданный id должен совпасть с вычисленным (`id_mismatch`); класс без ключа id не
  принимает (`id_from_db`).
- Уникальность — только ключ, правил `unique` нет; неявного ключа связи по её концам нет.
- Ключевые поля, id, арендатор и владелец обычной правкой не меняются (`immutable_key`): новый ключ — `rekey()`
  или `db.rekeyClass()`, оба выдают новые id и переводят ссылки. В 0.21 правка ключа проходила, но id переставал
  ему соответствовать.
- Смена класса — глагол `reclass()`: у класса без ключа id сохраняется, у класса с ключом вычисляется заново,
  ссылки переводятся; правка класса обычной записью — `use_reclass`.

### BREAKING — запись и транзакции
- `create` — обычная вставка: занятый ключ — `exists` (`detail.id`), а не идемпотентный PUT. Замена целиком —
  отдельный глагол `upsert`, только для класса с ключом (`no_key`) и только целым объектом.
- `update` по-прежнему не создаёт; затронуто меньше строк, чем нашёл шаг, — откат плана с `target_not_found`,
  `conflict` или `acl_denied`.
- Ошибка любого запроса в `db.begin()` ломает транзакцию (в том числе `exists` и `conflict`): следующие вызовы и
  `commit()` бросают исходную ошибку, `rollback()` проходит; обрыв связи во время `COMMIT` — `commit_unknown`.
  В 0.21 повторный `commit` после ошибки молча проходил.
- Каскад удаления — в триггере после оператора; удаление и создание одного id одним оператором —
  `recreated_in_statement`; удаление, смена класса и ключа — только в `read committed` (`isolation_level`).
- `db.as()` асинхронный и принимает арендатора: `await db.as(аккаунт, { tenant, owner })`.
- `batch.execute()` — охранник с заменой `batch.run()`.

### BREAKING — чтение
- `count()` и агрегаты считают сущности последнего шага, а не пути; пути — `count({ paths: true })`; `run()` и
  `execute()` сняты — пути отдаёт `paths()`.
- `account()` снят: арендатор — свойство сессии (`connect({ token | apiKey })`, `db.as(…, { tenant })`,
  `db.auth.switch()`).
- Строка ответа: `tenant` вместо `account`, `at` вместо `updated`; новые поля `rev`, `author`, `op`, `agent`,
  `reason`, `moved`.

### BREAKING — доступ
- Изоляция арендаторов и права действуют всегда — политиками RLS, для библиотеки и сырого SQL; права по умолчанию
  запрещают. Опции `connect()` `partition`, `enforceAccount`, `enforceAcl`, `container`, `image`, `dataDir`,
  `redisPort`, `version` — охранники `removed`. Роль, обходящая RLS, подключается только с `allowBypassRls`
  (иначе `bypass_rls`).
- Сессии — в PostgreSQL: `db.auth.sessions(store)` снят (`sessionFor`, `refresh`, `revoke`, `revokeAll`);
  `enabled: false` гасит и живые сессии.
- Фасады `db.accounts`, `db.credentials`, `db.resources`, `db.rules` сняты — системные классы `Account`,
  `Resource`, `rule`, `member` и `db.auth`; `accounts.purge` — `db.auth.purgeAccount()`. `db.reloadSchema()` и
  `db.acl.reload()` сняты: реестр и права обновляются сами по сигналу базы (принудительно — `db.refresh()`).
- Системный сид — только общие группы и системные права; ресурсы продуктов (`chrono`, `payment`, `billing`,
  `geo`, `shop`) в библиотеку не входят.

### BREAKING — события, классы, ошибки
- `watch(cb)` и `watch(класс, cb)` сняты: `db.watch({ from, classes })` — асинхронный итератор с курсором, без
  потерь и повторов.
- Классы описываются моделями на Zod (`hub`, `link`, `one`, `many`) или строками `Class` с JSON Schema;
  `db.schema.define()` и CLI `schema-sync`, `gen-types` заменены `letopis sync` и `letopis types`; `db.schema` —
  имя схемы.

### Отличия от предложения «Свод» (§3 плана)
PostgreSQL 18 вместо 15; одна приватная таблица `secret` вместо `credential` и `session`; журнал без партиций с
политикой хранения; v5 — класс и значения ключа как есть, без канонизации и неявного ключа связи; только ключ
вместо правил `unique`; `create` и `upsert` — разные глаголы; `rekey` для ключевых полей; приращение `inc`;
`{ rev }` с кодом `conflict` и правилом одной цели; сломанная транзакция и `commit_unknown`; `forUpdate()`;
загрузчик через `COPY` от роли владельца; индексы под RLS и срезы `asOf` через функции владельца `find_ids()`;
план прав вместо таблицы-снимка; журнал защищён правами, а не триггерами; каскад после оператора; хэш —
генерируемая колонка; проверка данных компиляцией JSON Schema в jsonpath; `NOTIFY` с именем класса; кэш плана и
результатов; свободный объект `meta`; имперсонация через `letopis.account`; продление сессии отдельным вызовом;
выпуск — letopis 1.0.0, а не новый пакет.

### Fixed — после этапа 8 (код)
- Подмена актора в `db.batch()`: очередь была общей для всех фасадов подключения, и `run()` одного фасада исполнял от своего имени планы, поставленные другим (`db.as()`, `db.begin()`). Теперь очередь своя у каждого фасада, и план исполняется от имени поставившего.
- Курсор `after()` проверяется по типу поля `sort` до запроса: значение не того типа, курсор без `v` или `id` не uuid — `invalid_query`. Раньше курсор без `v` вешал соединение, а логический курсор по полю без описания давал ошибку сервера.
- Ошибка загрузчика называет точное число нарушений («и ещё N»; «не меньше N» с причинами, если проверены не все строки), а в `detail` к первым 100 нарушениям в `rows` добавлены `total`, `truncated`, `limit` и `complete`.
- Маска шаблона `Resource` не строкой (`categories`, `roles`, `endpoint`, `class`) совпадала со всеми, как в 0.21: группа `{ roles: ['staff'] }` с разрешающим правилом давала право любому аккаунту, маска `class` не строкой — на все классы. Теперь описание класса `Resource` требует строки, и маску не строкой отклоняет `invalid_data` — при записи библиотекой, сырым SQL и загрузчиком, в том числе при импорте. Строка, записанная в обход проверки, разрешений не даёт, а запрет по ней действует на всех: `acl_set_ok` и `acl_class_ok` на не строку отвечают null, `acl_rules` и `acl_plan_for` отбрасывают по ней разрешение. Новое описание попадает в свежую установку и после `reset({ all })`; в существующей схеме исправленное сопоставление действует после повторного `up()`.
- Ключи сервиса: по сессии своего ключа сервис не мог ни выпустить себе новый ключ, ни отозвать старый (только системный администратор), а отзыв любого креда гасил все сессии аккаунта — ротация без простоя не получалась. Теперь свои `APIKEY` и `KEYSECRET` сервис выпускает и отзывает сам по сессии своего ключа (`auth_service_self`); сессия по ключу помнит его id (`meta.cred`), и отзыв ключа гасит только его сессии и старые сессии того же вида без отметки (`auth_kill_cred`), `keepCurrent` — как у прочих кредов. Последний действующий ключ сервиса не отзывается никем — `acl_denied` «последний действующий ключ сервиса не отзывается: сначала выпустите новый»; отключить сервис — `enabled: false`.
- TOTP: пользователю с включённым TOTP свои креды было не сменить — база требует сессию с пройденным TOTP, а библиотека такую не выдавала. Теперь её выдают `verifyPassword` и `lookup` с `totp` (см. «Added — после этапа 8»).
- `maintain()` за пулом в режиме транзакций (PgBouncer) молча вставал: сеансовая advisory-блокировка оставалась на серверном соединении, которое пул отдаёт другим клиентам, — `skipped` у всех. Теперь каждая пачка в своей транзакции первым делом берёт транзакционную блокировку (`pg_try_advisory_xact_lock`), её снимает фиксация пачки; блокировка занята до первой пачки — `skipped`, между пачками — остановка с `more: true`.
- `after()` по полю данных терял строки с `null` или без поля: сравнение с `null` не проходило, а после строки с `null` следующая страница была пустой. Теперь `null` — после всех значений при возрастании и перед ними при убывании, как в `order by`; курсор `null` работает.
- `letopis import`: ошибка загрузчика в данных арендатора теряла `total`, `truncated`, `limit` и `complete` отчёта загрузчика — теперь они доходят вместе со строками 0.21 в `rows` и `notes`.
- `createTenant` и `up({ tenant })` после удаления арендатора, аккаунта пользователя или членства падали с `23505` (`log_id_rev`): `sys_create` пишет версию 1, а её занимает история. Теперь — `invalid_data` с объяснением и советом вернуть строку `restore()`, транзакция откатывается целиком; повтор удалённое не воскрешает.

### Fixed — документация
- В `README.md` стоял байт NUL: grep и поисковые инструменты считали файл двоичным и пропускали его.
- Примеры шпаргалки, которые в прежнем виде падали: строгий режим `{ rev }` с устаревшим номером версии, создание уже существующего членства (теперь — правка ролей), подписка без условия выхода и неопределённые переменные.
- Утверждения прежних README и шпаргалки, которые расходились с кодом (ревизия против кода и тестов): имперсонация не проверяет видимость пользователя по правилам доступа; `deep()` по умолчанию — 32 уровня; `refresh()` возвращает новое время истечения, а не токен; `verifyPassword` по умолчанию пускает только по подтверждённому креду; подписка отдаёт события в порядке номеров транзакций, а не фиксации; подключение к PGlite требует `allowBypassRls`; `update`, не нашедший целей, отвечает пустым списком, а не `target_not_found`; вес правила арендатора больше 999 урезается, а не отклоняется.
- Маска группы (`Resource` категории `ACCOUNT`) задаётся только строкой; маску не строкой теперь отклоняет база (см. «Fixed — после этапа 8 (код)»).

### Security — итоговое ревью безопасности (этап 8)
- Блокировка семейства классов (`family_lock`) — по арендатору корневого класса: ужесточение класса или `rekeyClass` в одном арендаторе больше не останавливает запись в одноимённый класс других арендаторов.
- `account_purge` проверяет право до поиска аккаунта: без права ответ всегда `acl_denied` — существование аккаунта не раскрывается.
- `restore` и `purge` блокируют запись журнала только своего арендатора: чужой id нельзя ни заблокировать, ни заметить по ожиданию.
- Маска `Resource` не строкой больше не открывает права всем: такую строку база не записывает (`invalid_data`), а записанная в обход проверки разрешений не даёт (см. «Fixed — после этапа 8 (код)»).
- Тест `security-final`.

## [0.21.0] — 2026-08-23

### Added — no-history классы: `meta.history: false` (DDL_REVISION 2)

Класс, помеченный в `Schema.meta` флагом `history: false`, хранит **одну актуальную строку
на id**: новый AFTER INSERT триггер `entity_collapse` после каждой вставки физически удаляет
более старые версии этого id. Дефолт (`history` отсутствует или `true`) — прежнее поведение,
все версии копятся; фича строго opt-in, существующие схемы и сервисы не затронуты.

Зачем: у мутабельных статус-сущностей (очереди, outbox — статус живёт в `data`) история
версий делает jsonb-фильтры неселективными: GIN по `data` матчит каждую версию, что
когда-либо была в искомом статусе, и сканы растут O(вся история). Под `history:false`
фильтр матчит только актуальные строки — скан остаётся O(активных) при любом росте данных.

Механика:
- `entity_collapse` — AFTER INSERT (как `entity_notify`; collapse по алфавиту раньше —
  один NOTIFY на выжившую строку). In-place UPDATE не годится: Entity — гипертаблица по
  `updated` (перенос между чанками), а `entity_notify` слушает только INSERT.
- DELETE старых версий идёт под `letopis.purge='on'` (save+restore флага):
  `entity_delete` пропущен — без tombstone и каскада. Advisory-lock тем же ключом,
  что `entity_delete`/`purge`, сериализует конкурентные вставки одного id.
- `.delete()` под no-history оставляет один tombstone (его `updated` строго больше),
  `purge()` работает как прежде.
- Новая серверная функция `compact(partition, class) → bigint` — разовая чистка УЖЕ
  накопленной истории при переводе класса на `history:false` (оставить последнюю версию
  каждого id, вернуть число удалённых). Идемпотентна. После вызова — `ANALYZE "Entity"`.
- `ClassDef.history` в реестре; `.versions()`/`.asOf()` по no-history классу предупреждают
  в console.warn (один раз на класс+метод за процесс) — результат не отражает историю.

Накат на существующие схемы: `up({ upgrade: true })` или `node db/apply.mjs --upgrade`
(файл идемпотентен, данные целы); до наката `connect()` предупредит о ревизии (1 → 2).

- `test/no-history.test.ts` — 7 сцен: реестр, схлопывание, соседний history-класс,
  NOTIFY, tombstone, `compact()`, warning; суммарно 205 тестов.

### Fixed — релиз доезжает до npm

### Changed — на каждое событие ровно одно действие в Actions

Тесты гонялись трижды на одном и том же коммите: прогон от push в `dev`, второй от
`pull_request` при открытии релизного PR и третий от push в `main` при merge. Причём на merge
`ci` и `tag` стартовали **одновременно** — тег мог встать раньше, чем закончатся тесты.

Контур приведён к одному действию на событие:

```
push dev            →  ci  (typecheck + check:docs + 198 тестов)
merge dev→main      →  tag (аннотированный тег из lib/package.json)
publish Release     →  release (описание из PR + npm publish + смоук артефакта)
```

- `ci.yml` — только `push: dev`. Ни `pull_request`, ни `push: main`: релизный PR и сам merge
  несут ТОТ ЖЕ коммит, что уже проверен на `dev` (ветка всегда пушится до PR). `concurrency` —
  быстрые последовательные пуши в `dev` отменяют предыдущий прогон.
- `tag.yml` — `push: main`, тегирует сразу: ждать нечего, тесты прошли на `dev`.
- убраны шаги `npm run build` + `npm pack` с выгрузкой артефакта: тарбол никто не забирал —
  `release.yml` публикует сам (`prepublishOnly` гоняет typecheck + build), а результат
  проверяется смоуком уже из реестра; компиляция дублировала шаг Typecheck. CI — 7 шагов.

**Остаётся настройкой репозитория:** branch protection на `main` с обязательной проверкой
`test`. Без неё запрет «не мерджить на красном» держится на дисциплине: у PR своей проверки
нет, гарантию даёт зелёный прогон того же SHA на `dev`.

### Changed — флоу релиза: тег с историей, заметки из PR, без сторонних экшенов

`tag.yml` ставит **аннотированный** тег: в сообщении — список коммитов от предыдущего тега,

### Fixed — `ANALYZE` при накате схемы: чтения были медленнее на порядок

`up()` и `db/apply.mjs` теперь вызывают `ANALYZE "<схема>"."Entity"` после наката DDL и сидов.

`Entity` — гипертаблица: строки лежат в чанках, у родительской таблицы своих строк нет. Пока
`ANALYZE` по ней не прошёл, планировщик берёт дефолт «200 уникальных `id`». Ядро всех чтений
либы — semi-join с подзапросом кандидатов (`e.id IN (SELECT c.id FROM Entity c WHERE …)`), и на
такой оценке он выбирает `Nested Loop` вместо `Merge Semi Join`, с уходом хеша и сортировки на
диск. Замерено на полигоне 980k строк:

| Сцена | без статистики | после `ANALYZE` | |
|---|---|---|---|
| `count()` класса под изоляцией арендатора | 57.6 s | 3.2 s | ×18 |
| фильтр `rows` limit 100 по 440k | 1371 ms | 11 ms | ×126 |
| `count()` класса без фильтра | 2981 ms | 1373 ms | ×2.2 |

Тайминги README §14 и §9.2 перемерены на проанализированной базе. Своя массовая вставка
(`COPY`, миграция, генератор) требует `ANALYZE` вручную — это отдельная грабля в
`AGENT-CHEATSHEET.md` (#17) и новая секция README §14.1.

Заодно вычищен доковый дрейф в §14: строка «обход `запись→Мастер` по всему классу» показывала
≈6 с с версии 0.17.0, где полигон был 250 000 записей / 613 тыс. строк, и переезд на
440 006 / 980 328 её не обновил — настоящее значение ≈30 с. Стоимость этой сцены = `строки
внешнего шага × чанки` (одна проба — 0.924 мс / 80 буферов при 13 чанках), потому что
forward-hop идёт коррелированным `JOIN LATERAL` с пробой по всем чанкам. Первое объяснение
в §14 («планировщик недооценивает внешнюю сторону и не ставит `Memoize`») **снято как
неверное**: подстановка класса литералом и `SET enable_nestloop = off` план не меняют, дело в
самой форме — корреляция внутри подзапроса с `DISTINCT ON` не раскоррелируется и не
мемоизируется. Некоррелированный join измерен и хуже в 18 раз (561 с), так что форма
оставлена как есть; лечится стороной старта цепочки — `db.запись(id).Мастер()` 7.5 мс и
`db.Мастер(id).запись()` 11.7 мс против 30 с у обхода всего класса.

Попутно исправлен `bench/acl.bench.mjs`: его колонки были несравнимы — `base` шёл без изоляции
арендатора, а ACL-хендлы с ней, из-за чего бенч приписывал авторизации до 18× чужой цены.
Теперь все три режима с `enforceAccount: false`, и видно настоящее: **ACL бесплатен на всех
сценах** (отличия в пределах шума). Цена изоляции измеряется отдельно и зависит от доли
арендатора в классе — на 10-арендаторном полигоне она ускоряет чтение до 27× (README §10.6).

### BREAKING — арендатор стал свойством ВЫЗОВА: `db.as(account)`, опции `connect({ account })` больше нет

Из `ConnectOpts` **удалены `account` и `owner`**. Аккаунт на подключении — это модель
«одно соединение = один тенант», а для веб-приложения она неверна: пул общий, арендатор
меняется от запроса к запросу. Теперь подключение безличное, а идентичность даёт хендл:

```ts
const db = await connect({ dsn, schema })     // было: connect({ …, account: X })
const t  = await db.as(accountId)             // стало: имя вызова, хендл того же пула
await t.Клиент().rows()
```

`db.as(account, { owner? })` клонирует контекст на **том же пуле** (нового соединения не
открывает, SQL не шлёт), поэтому его нормально создавать на каждый HTTP-запрос. `close()`
по-прежнему один на пул. Батчи с корня в scope не наследуются: очередь планов, общая для
разных арендаторов, была бы утечкой записи.

Под `enforceAcl` **правила компилятся под субъекта scope** — у каждого `db.as()` свой
энфорсер. Это не оптимизация, а требование корректности: ключ memo в `acl.ts` — «класс +
операция», без аккаунта, так что переиспользование одного энфорсера двумя арендаторами
отдало бы второму решения первого. Закреплено тестом (`acl.test.ts`, «memo энфорсера не
течёт между scope одного пула»); проверено негативно — с общим энфорсером тест падает.

`enforceAccount` — **`true`** по умолчанию: чтения фильтруются по `account` scope-хендла,
записи к нему пришпилены. Забыть флаг было слишком легко, а цена забывчивости — чужие
строки в выдаче без всякой ошибки. Теперь и забыть `db.as()` нельзя: с безличного корня
чтение/запись бросают

```
letopis: enforceAccount is on — call db.as(account) to name the tenant of this call,
or connect({ enforceAccount: false }) for admin access
```

Админским и сервисным подключениям (миграции, отчёты по всем арендаторам, дев-скрипты)
нужен явный `connect({ …, enforceAccount: false })` — там колонку `account` закрывает
System-аккаунт схемы, как раньше.

Смысл модификатора `.account()` не изменился: это точечный фильтр/значение одного шага;
на scope-хендле чужое значение — ошибка `pinned`.

`enforceAcl` остаётся **`false`** (opt-in): включённый по умолчанию deny-by-default без
настроенных `Resource`/`Rule` давал бы пустые выборки. Вместо смены дефолта `connect()`
печатает предупреждение один раз на процесс: авторизация не проверяется — это должно быть
шумно, а не молча.

**Миграция.** `connect({ …, account: X })` → `(await connect({ … })).as(X)`;
`connect({ …, account: X, owner: Y })` → `.as(X, { owner: Y })`; подключения, которые
работали без `account` и должны видеть всё, — `connect({ …, enforceAccount: false })`.
`accounts.purge(id)` требует scoped-хендла: `(await db.as(caller)).accounts.purge(id)`.

### BREAKING — снят охранник `.link()`

`case 'link'` в цепочке удалён. Он затенял **реальный класс схемы**: в демо-домене `link`
(алиас `связь`) — абстрактный корень всех связок, и `db.Клиент(c).link()` падал
migration-ошибкой вместо обхода, хотя `db.link()` с корня работал. Теперь имя `link`
резолвится как класс на всех уровнях; зарезервированных имён 52 (`link` ушло, `as` пришло).
Совместимость со снесённым в 0.15.0 методом `.link()` принесена в жертву достижимости
класса — при обращении к нему теперь будет обычная ошибка пути, а не подсказка миграции.
Остальные migration-охранники (`execute()`, `set(data)`, слот `.delete()`,
`batch.execute()`) не тронуты: они не затеняют классов.

### BREAKING — чтение стало полиморфным по иерархии классов

Шаг цепочки по родительскому классу теперь отдаёт **объединение с потомками любой глубины**
(как и права ACL наследуются по иерархии). Раньше фильтр шёл по точной колонке `class`,
поэтому abstract-классы молча возвращали пусто, а родитель не видел потомков:

- `db.Контрагент()` (`Person`, abstract): было `0` → стало `Мастер` + `Клиент`;
- `db.связь()` (`link`, abstract): было `0` → стало все классы-связки;
- `db.окно()` (`slot`, конкретный, потомок `booking`): в демо-полигоне было `54 005` →
  стало `494 008`.

**Что нужно проверить в своём коде.** Если наследование у вас — переиспользование
`attributes`, а не «is-a» для выборки, добавьте **`.exact()`** на шаг: он возвращает
одиночный класс. Ровно этот случай в демо-домене — `запись` наследует `окно` (интервал и
правило v5-id), но смена ≠ бронь, поэтому «смены мастера» теперь
`db.Мастер(id).окно().exact()`. На классе без потомков `.exact()` — no-op.

- **Идентичность сущности в полиморфной выборке — пара `(class, id)`**: `DISTINCT ON`,
  подзапрос кандидатов и join истории в `versions()` переведены на неё; `Row.class`
  показывает конкретный класс строки.
- **Ключи `Entity.links` конкретны**, поэтому обходы (forward/reverse/`deep`) берут ключ
  из колонки `class` строки, а не из литерала родителя.
- **ACL решается по конкретному классу каждой строки.** `deny` на потомке больше не
  обходится шагом по родителю: запрещённые классы выпадают из выборки, у каждого
  разрешённого действует его собственный row-предикат; отказ шага целиком — только если
  запрещено всё семейство. Покрыто `test/acl.test.ts` (2 новых теста).
- **Запись полиморфной не бывает**: `create()` пишет строго в свой класс (в abstract —
  `class "X" is abstract`); `update()`/`delete()`/`purge()` работают со строками в их
  собственных классах.
- `exact` добавлено в зарезервированные имена классов (52).

Ревизия документации на пригодность для ИИ-агента: устранён дрейф между доками и кодом,
добавлен агентский слой и автопроверки, чтобы дрейф не возвращался.

## [0.16.0] — 2026-07-12

### Changed — BREAKING: глаголы записи create/update, слот unset, id считает Schema

- **`set()` разбит на `create()` / `update()`** — мина «`Класс()` → INSERT,
  `Класс({})` → UPDATE всех» мертва, намерение всегда явное:
  - **`create(data?)`** — INSERT; известный id (шаг `Класс(id)`, `data.id` или
    вычисленный v5) уже существует → новая версия (идемпотентный create,
    REST-PUT семантика). Фильтр-объект перед create — ошибка ПОСТРОЕНИЯ
    (`create() takes no filter`); create на pivot-шаге — ошибка.
  - **`update(data?)`** — новая версия КАЖДОГО найденного путём;
    `Класс()` ≡ `Класс({})` — «все в границах контекста»; не найдено → `[]`,
    update НИКОГДА не создаёт.
  - `set()` бросает подсказку `set() split into create()/update() (0.16.0)`.
- **Слот-снятие переименовано: `.Класс.delete()` → `.Класс.unset()`** — развели
  «удалить сущность» (`delete()`) и «снять конец связи» (`unset()`); старое имя
  бросает подсказку. Слот теперь требует глагол записи ПЕРЕД собой:
  `…create(…).Класс.set(x)` / `…update(…).Класс.unset()`; слот без операции —
  ошибка `link slot needs a write` (раньше слот молча создавал `set({})`).
- **Генерация id по Schema** — `attributes.id`:
  - `"uuid"` / `{type:'uuid'}` → **v4** (random, как раньше — дефолт);
  - `{type:'uuid', generate: 7}` → **v7** (unix-время в старших битах — вставки
    ложатся в хвост btree-индекса);
  - `{type:'uuid', generate: 5, from:[…]}` → **v5, детерминированный**:
    `uuidv5("pgSchema:partition:класс:значения from")`; `from` — имена
    ОБЯЗАТЕЛЬНЫХ концов `Schema.links` (класс или полное имя союза
    `'Service|Complex'`; значение — id конца) и/или скалярных полей `data`.
    Явный id у v5-класса запрещён (`computes id`). Свойства: **create
    идемпотентен** (та же комбинация → та же сущность, дубль невозможен даже в
    гонке — двойная бронь мертва на уровне схемы) и **id известен ДО создания**

  - Батч: multi-VALUES-склейка для v5-классов отключена (id нужны концы) —
    такие планы исполняются поштучно, семантика та же.
- **Наследование attributes по иерархии Schema**: при загрузке реестра attributes
  класса собираются по цепочке `ancestor` — потомок ПОВЕРХ предка, переопределение
  поля = замена правила целиком (не слияние). Правило `id` (генерация) наследуется

## [0.11.0] — 2026-07-11

### Changed — BREAKING: цепочка = план, операции = звенья
- **`.set(data?)` / `.delete(opts?)` / `.anonymize(fields)` возвращают ЦЕПОЧКУ** (Chain),
  а не исполняются сами: операция применяется к шагу, к которому приклеена точкой;
  **исполняет терминал** (`rows/first/ids/count/run/versions/агрегации`) — весь план
  **одной транзакцией** (deny/валидация любого сегмента откатывает всё). Голый
  `await …set(…)` без терминала больше НЕ пишет (цепочка не thenable). Миграция:
  `await db.X(id).set({…})` → `await db.X(id).set({…}).rows()`.
- **Продолжение цепочки — от результата операции** (fan-out по строкам):
  `db.Клиент({vip: true}).set({bonus: 500}).Запись().delete({confirm: true}).rows()` —
  обновить всех vip и снести записи каждого. Повторная операция без шага — к тем же
  строкам: `X(id).set({a}).set({b}).rows()` — две версии подряд.
- **`execute()` → `run()`** (пути; то же у батча: `batch.execute()` → `batch.run()`);
  старые имена бросают понятную ошибку.
- **`delete({ confirm: true })` — удалить; БЕЗ confirm — превью**: терминал возвращает
  кандидатов (цели + каскад), БД не тронута.
- **Пост-довесы связей удалены** (`set({}).Окно(w)`, z-форма, тип `SetChain`): имя класса
  после операции — переход-шаг. Связи — контекст-шагами до операции; для значения связи
  БЕЗ участия в фильтре целей — новый модификатор **`.link(Класс, target)`**:
  `tr.Запись(b).позиция({}).link('Сотрудник', новый).set({}).rows()`.
- Ошибки записи (ValidationError, abstract, context step, acl) летят из терминала (async).
- В батче `await …set(…)` больше не возвращает номер очереди (план в очереди; Chain).
- Модификатор шага сразу после операции — ошибка `step modifier after set()`.
