# letopis на живом полигоне: один день сети салонов

Это не референс и не README — это **прогон**. Мы засеяли под миллион строк по доменной
схеме сети салонов красоты и провели сквозь неё один рабочий день: открыли салон,
собрали каталог, наняли мастеров, приняли брони, переставили предмет, перенесли и
отменили запись, посчитали отчёты, пустили клиентов по паролю и токену, раздали права.
Каждый вызов API ниже — **реальный**, с ответом прямо из PostgreSQL и временем на живой БД.

Воспроизвести целиком:

```bash
node lib/bench/salon-seed.mjs          # засеять полигон v1.salondemo (~980k строк, ~8 мин)
node lib/bench/salon-article-demo.mjs  # снять все ответы этой статьи
```

Тест-план, по которому построен рассказ, — `lib/TESTPLAN.md` (21 акт, 145 точек API);
исполняемая версия — `lib/test/salon.test.ts`.

## Полигон

`salon-seed.mjs` детерминированным генератором (`mulberry32`) наполняет схему
`v1.salondemo` за год «истории» — 30 салонов, локации, каталоги, мастера, 40 000
клиентов, 440 000 записей с двумя версиями каждая, окна-смены, навыки. Bulk-INSERT
напрямую в `Entity`; каждая строка проходит серверный триггер целостности `entity_check` —
то есть **весь миллион валиден по схеме `Schema.links` v2** (иначе INSERT бы отклонился).

Распределение классов (`SELECT class, count(*) … GROUP BY class`):

| Класс | Строк | | Класс | Строк |
|---|--:|---|---|--:|
| `booking` (запись) | 880 000 | | `price` (цена) | 1 620 |
| `slot` (окно) | 54 000 | | `Service` (Услуга) | 600 |
| `Customer` (Клиент) | 40 000 | | `content` (содержимое) | 750 |
| `skill` (навык) | 1 260 | | `compo` (состав) | 360 |
| `Staff`/`address` | 360 + 360 | | `Location` (Локация) | 60 |

**Итого 980 180 строк.** `booking` — половина полигона: у каждой записи две версии
(создана → подтверждена накануне), append-only хранит их обе, актуальная — с
максимальным `updated`.

### Доменная схема (`Schema.links` v2) — позитивная доступность

Связи объявлены не строками, а объектами-концами — с союзами ролей и опциональностью:

```
адрес       [Staff, Location]                              ← мастер закреплён за локацией
окно        [Staff, Location, Schedule]                    ← СМЕНА: интервал доступности мастера
запись      [Staff, Location, Schedule, Service|Product|Complex, Customer?]  ← НАСЛЕДНИК окна
содержимое  [Folder, Service|Product|Complex]              ← наполнение папки-каталога
состав      [Complex, Service|Product]                     ← состав комплекса
навык       [Staff, Service]                               ← мастер умеет услугу
цена        [Service|Product|Complex]                      ← вариант цены: note + amounts (мультивалюта)
```

`Service|Product|Complex` — «ровно один из»: предмет записи — либо услуга, либо товар,
либо комплекс, никогда несколько. `Customer?` — клиент необязателен (ручная бронь «на
имя», имя в `notes`). Модель **позитивная**: доступность мастера — это факт наличия
окна-смены, а не отсутствие блокировок; нет отдельных `busy`/`shift`/сетки часовых
слотов. Свободно = внутри окна и нет пересекающейся записи. Триггер БД валидирует концы
на каждой вставке, даже в обход библиотеки.

### id считает схема (`attributes.id`)

В `attributes.id` объявлено, **как рождается id** — и это правило, как и любые
attributes, **наследуется по иерархии классов** (потомок поверх предка, переопределение
поля — замена правила целиком; концы `links` не наследуются — они у каждого свои):

```jsonc
// корни иерархий объявляют дефолт ОДИН раз:
"Entity": { "id": { "type": "uuid", "generate": 7 } }   // v7: время в старших битах
"link":   { "id": { "type": "uuid", "generate": 7 } }
// абстрактный Элемент — правило v5 ОДИН раз, наследуют Услуга/Товар/Комплекс:
"Element": { "id": { "type": "uuid", "generate": 5, "from": ["Org","name"] } }
// окно объявляет v5, а запись НАСЛЕДУЕТ его правило (ancestor: slot):
"slot":    { "id": { "type": "uuid", "generate": 5, "from": ["Staff","start_datetime"] } }
```

В полигоне это разложено так:

| generate | Классы | Формула id |
|---|---|---|
| **v7** (time-ordered) | Org, Staff, Customer, Location, Schedule, Folder — своего правила НЕ имеют, наследуют от `Entity`; `address` — от `link` | время + random — вставки ложатся в хвост индекса |
| **v5** (детерминированный) | `Element` → наследуют `Service`/`Product`/`Complex` | `uuidv5(Org, name)` — имя уникально в салоне (classId различает классы) |
| | `slot` → наследует `booking` | `uuidv5(Staff, start_datetime)` — пара (мастер, старт) |
| | `skill` | `uuidv5(Staff, Service)` |
| | `compo` | `uuidv5(Complex, Service\|Product)` |
| | `content` | `uuidv5(Folder, Service\|Product\|Complex)` |
| | `цена (price)` | `uuidv5(элемент, note)` — `note` не задан ⇒ дефолт `'базовая'` (генератор берёт default из Schema) |

v5-формула открыта: `uuidv5("схема:партиция:класс:значения from")` — функция
экспортируется пакетом (`import { uuidv5 } from 'letopis'`). Это даёт два свойства,
которые дальше играют весь день: **create идемпотентен** (повторный вызов с теми же
данными — новая версия той же сущности, не дубль) и **id известен заранее** (проверка
«занято ли время мастера» — до создания чего-либо). Ключевой трюк наследования:
`запись` берёт правило id у `окна`, но `classId` в формуле у неё свой — поэтому окно и
запись на одно и то же время у одного мастера сосуществуют, а вот две записи на пару
(мастер, старт) слиться в одну неизбежно. Явный id у v5-класса запрещён — его всегда
считает схема.

### Грамматика в трёх правилах

Весь язык letopis держится на трёх формах свойства-класса:

```ts
Класс(фильтр?)            // ВЫЗОВ — навигация по пути; повтор LINK-класса = возврат к узлу (pivot)
Класс                     // СЛОТ  — конец связи: .Класс.set(x) записать, .Класс.unset() снять
create / update / delete  // ГЛАГОЛ — операция; исполняет ТЕРМИНАЛ (rows/first/count/run/…)
```

Глаголы не перепутать: `create` **вставляет** (или версионирует по известному id),
`update` **правит найденное путём** и никогда не создаёт, `delete` показывает превью,
пока не сказали `confirm`. Слот приклеивается только к глаголу записи. Путь всегда
подчиняется переходам схемы — и при чтении, и при записи.

## Акт 1. Открытие: создание сущностей и батч

Заводим салон, зал и двух мастериц. `create()` — звено плана; исполняет терминал `.rows()`:

```ts
const [org] = await db.Организация()
  .create({ name: 'Салон «Пример»', phone: '+7 495 0000000', timezone: 'Europe/Moscow' }).rows()
```
```jsonc
// [44.3 ms] → defaults (active, timezone) подставлены из Schema
{ "id": "…0010", "class": "Org",
  "data": { "name": "Салон «Пример»", "phone": "+7 495 0000000", "active": true, "timezone": "Europe/Moscow" },
  "links": {} }
```

Двух мастеров — батчем. `batch` копит планы и шлёт одной транзакцией:

```ts
const b = db.batch('setup')
b.Организация(org).Мастер().create({ name: 'Ольга', phone: '+7 900 222', specialization: 'парикмахер' })
b.Организация(org).Мастер().create({ name: 'Ирина', phone: '+7 900 333', specialization: 'барбер' })
b.size()            // → 2
await b.run()       // [31.6 ms]
```
```jsonc
[ { "id": "…0011", "class": "Staff", "data": { "name": "Ольга", "phone": "+7 900 222", "specialization": "парикмахер" },
    "links": { "Org": "…0010" } },
  { "id": "…0012", "class": "Staff", "data": { "name": "Ирина", "phone": "+7 900 333", "specialization": "барбер" },
    "links": { "Org": "…0010" } } ]
```

Имя и телефон — от абстрактного `Контрагента` (наследуются), `specialization` — своё поле
Мастера. Владелец `Org` попал в `links` мастера **из пути** — `Организация(org)` первым
шагом. Это ключевой принцип: владельца связки задаёт путь, прочие концы — слотами. Мастер
привязывается к локации связью `адрес` (`Мастер(m).адрес().create().Локация.set(зал)`).

## Акт 2. `up()`: вход одной функцией

Второй способ подключиться — `up()`: на живой БД он пропускает docker и просто
подключается к той же схеме.

```ts
const db = await up({ schema: 'salondemo', version: 1 })   // [153.3 ms]
await db.Организация().count()                              // → 31  (30 полигона + наш «Пример»)
```

## Акт 3. Каталог: дерево папок, услуги, товар, комплекс, содержимое

Услуга — прямо в организации, id вычисляет схема из пары (салон, имя):

```ts
const [стрижка] = await db.Организация(org).Услуга()
  .create({ name: 'Стрижка', duration: 60 }).rows()
```
```jsonc
// [17.2 ms] — конец Org из пути; id вычислен схемой: uuidv5(Org, "Стрижка")
{ "id": "…65ae", "class": "Service",
  "data": { "name": "Стрижка", "duration": 60 },
  "links": { "Org": "…0010" } }
// проверка формулы: стрижка.id === uuidv5(`v1.salondemo:entity:Service:${org.id}:Стрижка`)  → true
```

Никакого id в вызове нет — «Стрижка» в этом салоне может существовать только одна,
и её id вытекает из этого факта. Повторный `create` той же пары (салон, имя) не создаст
дубль — добавит версию.

**Цена — отдельная связь `цена`** (вариант по пожеланиям + мультивалюта). У услуги может
быть несколько вариантов (`note` их различает); `note` не задан → дефолт «базовая», и id
варианта считается стабильно из (услуга, note):

```ts
const [цена] = await db.Услуга(стрижка).цена().create({ amounts: { RUB: 1500, USD: 18 } }).rows()
```
```jsonc
// [14.9 ms] — note подставлен дефолтом, id = uuidv5(услуга, "базовая")
{ "id": "…", "class": "price", "note": "базовая", "amounts": { "RUB": 1500, "USD": 18 },
  "links": { "Service": "…65ae" } }
// цена.id === uuidv5(`v1.salondemo:entity:price:${стрижка.id}:базовая`)  → true
await db.Услуга(стрижка).цена().create({ note: 'с дизайном', amounts: { RUB: 2000 } }).rows()  // второй вариант
await db.Услуга(стрижка).цена().rows()   // [6.7 ms] → [{note:'базовая',…}, {note:'с дизайном',…}]
```

Почему цена не поле-число и не массив: варианты правят по одному (`db.цена(id).update({amounts:{RUB:…}})`
меняет лишь одну валюту — record мержится по ключам), по цене ищут
(`db.цена({amounts:{RUB:lte(2000)}}).Услуга()`) и ведут историю каждого варианта. Массив в
`data` при update заменялся бы целиком — точечно не поправить, гонки теряют правки.

Комплекс «Образ» и его состав. Владелец состава (`Комплекс`) — из пути, предмет
(`Услуга`/`Товар` — союзный конец) — **слотом**; в состав входят и услуги, и товар:

```ts
await db.Комплекс(набор).состав().create({ quantity: 1, order: 1 }).Услуга.set(стрижка).rows()   // [17.6 ms]
await db.Комплекс(набор).состав().create({ quantity: 1, order: 2 }).Услуга.set(укладка).rows()
await db.Комплекс(набор).состав().create({ quantity: 1, order: 3 }).Товар.set(шампунь).rows()

await db.Комплекс(набор).состав().Услуга().rows()   // [12.4 ms] → ["Укладка", "Стрижка"]
```

Наполнение папки — отдельная связь `содержимое` (M:N + порядок): один элемент может лежать
в нескольких папках.

```ts
await db.Папка(волосы).содержимое().create({ order: 1 }).Услуга.set(стрижка).rows()
await db.Папка(волосы).содержимое().Услуга().rows()             // [15.2 ms] → ["Укладка", "Стрижка"]
await db.Организация(org).Папка(корень).Папка().deep().rows()   // [23.1 ms] вся ветка → ["Волосы"]
```

`deep()` — рекурсивный обход детей того же класса (вложенность папок — HUB-концом `Folder⤴`).

## Акт 4. Навыки: слоты, вычислимое умение комплекса

Мастер умеет услуги — `навык [Staff, Service]` (+уровень). id навыка вычисляется из пары
(мастер, услуга): один навык дважды не завести.

```ts
await db.Мастер(ольга).навык().create({ level: 'expert' }).Услуга.set(стрижка).rows()

await db.Мастер(ольга).навык().Услуга().rows()   // [14.6 ms] → ["Укладка", "Стрижка"]
```

«Умеет ли Ирина бороду?» — обычный путь с фильтром на предмете, счёт по нему же:

```ts
await db.Мастер(ирина).навык().Услуга(борода).count()    // [12.6 ms] → 1  (умеет)
await db.Мастер(ирина).навык().Услуга(укладка).count()   //          → 0  (не умеет)
```

Умение **комплекса** теперь вычислимо, отдельной связи не нужно: мастер делает комплекс,
если покрывает навыком все услуги его состава.

```ts
const услуги = await db.Комплекс(набор).состав().Услуга().ids()
;(await db.Мастер(ольга).навык().Услуга(услуги).count()) === услуги.length   // Ольга → true
;(await db.Мастер(ирина).навык().Услуга(услуги).count()) === услуги.length   // Ирина → false
```

## Акт 5. Расписание: смены мастеров окнами

Месячное расписание `{name, year, month}`, смены мастеров — окна батчем. Окно — интервал
доступности (у Ольги 10:00–18:00, у Ирины 10:00–17:00). id окна — `uuidv5(Мастер, старт)`:

```ts
wb.Мастер(ольга).окно().create({ start_datetime: iso(10), end_datetime: iso(18) }).Локация.set(зал).Расписание.set(расп)
wb.Мастер(ирина).окно().create({ start_datetime: iso(10), end_datetime: iso(17) }).Локация.set(зал).Расписание.set(расп)
await wb.run()   // [30.6 ms] → 2 смены;  смены[0].id === uuidv5(Мастер, "…T10:00:00+03:00") → true

await db.Расписание(расп).окно().Мастер().rows()   // [12.1 ms] ростер дня → ["Ольга", "Ирина"]
```

Выходной час не пишется вовсе: нет окна на это время — мастер недоступен. Никаких
off-блокировок задним числом.

## Акт 6. Первая бронь: транзакция + advisory-lock

Аня записывается к Ольге на 10:00. Всё в одной транзакции с межпроцессным локом на пару
(мастер, старт). id записи **известен до создания** — `uuidv5(мастер, старт)` по открытой
формуле — поэтому «занято?» проверяется точечным `first()`:

```ts
const bid = uuidv5(`v1.salondemo:entity:booking:${ольга.id}:${iso(10)}`)

const tr = await db.begin()
await tr.lock('booking', ольга.id, iso(10))
await tr.запись(bid).first()                                    // → null: время свободно
await tr.Мастер(ольга).запись()
  .create({ start_datetime: iso(10), end_datetime: iso(11) })
  .Локация.set(зал).Расписание.set(расп).Услуга.set(стрижка).Клиент.set(аня).rows()
await tr.commit()                                               // [25.1 ms] весь блок
```
```jsonc
// запись — наследник окна: сама несёт интервал, предмет и клиента одной строкой:
{ "id": "…4e52", "class": "booking",
  "data": { "start_datetime": "2026-08-01T07:00:00.000Z", "end_datetime": "2026-08-01T08:00:00.000Z" },
  "links": { "Staff": "…0011", "Service": "…65ae", "Customer": "…0110", "Location": "…0015", "Schedule": "…0070" } }
// id записи = v5(мастер, старт) → true (двойная бронь мертва самим id)
```

Пять концов, и каждый пришёл своим путём: `Staff` из шага `Мастер(ольга)`, остальные —
слотами. id детерминирован: даже если два процесса одновременно создадут «Ольга × 10:00»,
это будет **одна и та же запись** (вторая вставка станет её версией) — повторный `create`
дал тот же id и вторую версию. Двойная бронь невозможна на уровне схемы.

## Акт 8. «Четыре руки»: два мастера в один час

Стрижка у Ольги и борода у Ирины в 12:00 — две **записи** одной клиентки (мульти-мастер
= несколько записей, не одна с придатками):

```ts
await db.Мастер(ольга).запись().create({ start_datetime: iso(12), end_datetime: iso(13) })
  .Локация.set(зал).Расписание.set(расп).Услуга.set(укладка).Клиент.set(аня).rows()
await db.Мастер(ирина).запись().create({ start_datetime: iso(12), end_datetime: iso(13) })
  .Локация.set(зал).Расписание.set(расп).Услуга.set(борода).Клиент.set(аня).rows()

await db.Клиент(аня).запись({ start_datetime: between(iso(12), iso(12)) }).count()   // → 2
await db.запись({ start_datetime: between(iso(12), iso(12)) }).Мастер().rows()       // [6140.6 ms] → ["Ольга", "Ирина"]
```

Шесть секунд на «кто занят в 12:00» — честный full-scan 880 000 версий записей с
фильтром по дате-полю (равенство момента задаётся `between(t, t)` — скалярный eq по date
это строковый containment). Это цена вопроса «по всему полигону»; точечные пути (акты
выше) — единицы миллисекунд.

## Акт 9. Операции дня: союз-замена, снятие клиента, перенос

Клиент передумал и берёт вместо услуги комплекс. Предмет — союзный конец
`Service|Product|Complex`, слот замещает его **целиком** (старый класс снимается сам):

```ts
await db.запись(bid12).update().Комплекс.set(набор).rows()   // [15.9 ms]
// links → { Staff, Complex, Customer, Location, Schedule }   (Service снят!)
```

Клиент не представился — делаем бронь ручной: отвязываем `Customer` (optional-конец) и
кладём имя в `notes`:

```ts
await db.запись(bid12).update({ notes: 'бронь по телефону: Аня' }).Клиент.unset().rows()   // [17.9 ms]
// links → { Staff, Service, Location, Schedule }   (Customer убран)
```

Перенос на другое время — это **пересоздание**: id жёстко держит пару (мастер, старт),
поэтому старую запись сносим, новую создаём, всё одной транзакцией:

```ts
const tr = await db.begin()
await tr.запись(bid10).delete({ confirm: true }).rows()        // старый (мастер, 10:00) свободен
await tr.Мастер(ольга).запись().create({ start_datetime: iso(15), end_datetime: iso(16) })
  .Локация.set(зал).Расписание.set(расп).Услуга.set(стрижка).Клиент.set(аня).rows()
await tr.commit()                                              // [60.9 ms]
// 10:00 свободно → true | 15:00 занято → true
```

## Акт 10. Отмена: сначала превью, потом удаление

`delete()` без подтверждения — **превью**: показывает, что уйдёт, но БД не трогает:

```ts
await db.запись(bid).delete().rows()                 // [16.7 ms] — БД НЕ тронута
// → [{ class: "booking" }]   $deleted отсутствует

await db.запись(bid).delete({ confirm: true }).rows()   // [32.9 ms] — tombstone
await db.запись(bid).count()                         // → 0
await db.запись(bid).versions().length               // → 2  (история цела: жизнь + tombstone)
```

Повторная бронь той же пары (мастер, старт) **воскресит** id с полной историей.

## Акт 11. `entity()`: узел из переменной

Готовую строку можно вставить в путь как узел:

```ts
await db.entity(текАни).Услуга().first()   // [8.2 ms] → "Стрижка"
```

## Акты 12–13. Отчёты на миллионе строк

Здесь чтения идут по **всему полигону** — 1 200 версий услуг, 880 000 версий записей.
Тайминги живые.

**Операторы фильтра** (`count()` на классе `Услуга`, ~600 уникальных):

```ts
db.Услуга({ duration: ne(60) }).count()               // [10.2 ms] → 454
db.Услуга({ duration: between(30, 45) }).count()                 // → 303
db.Услуга({ name: ilike('массаж 7') }).count()                  // → 30
db.Локация({ coordinates: { lat: gte(55.5) } }).count()         // [5.4 ms] → 27  (вложенный путь)
db.цена({ amounts: { RUB: gte(2000) } }).Услуга().count()       // [38.9 ms] → 391  (поиск по цене через класс)
db.Услуга({ description: isNull() }).count()                    // → 392
db.Услуга(or({ name: 'Стрижка 0' }, { duration: lt(40) })).count()   // → 153
```

Полный список отработал: `ne` 454, `gt(45)` 301, `gte(45)` 452, `lt(45)` 152,
`between` 303, `inList` 60, `like` 61, `starts('Спа')` 60, `not(ilike)` 544,
`exists(description)` 393. Массивов в данных новой схемы нет — `has/hasAny/hasAll` живут
на колонке `tags` (`db.Клиент().tags(has('vip')).count()` → 401). GIN-индексы по `data`/
`tags` держат это в единицах миллисекунд.

**Агрегации** — считает БД, не приложение:

```ts
db.Услуга().count()                    // [2.5 ms] → 605   (уникальные сущности)
db.цена().sum('data.amounts.RUB')      // [13.9 ms] → 2 286 100  (сумма всех вариантов, record-лист)
db.Услуга().avg('data.duration')       //         → 52.4
db.Услуга().min('data.duration')       // → 20    max → 75
db.Услуга().countBy('data.duration')   // [7.7 ms] → { "30": 152, "45": 150, "60": 151, "75": 150 }
```

Агрегация берёт **актуальные** версии, старые версии цен в сумму не попадают —
append-only не искажает отчёт.

Самый тяжёлый запрос дня — пересчёт всех записей:

```ts
db.запись().count()   // [5589.4 ms] → 440 002
```

Пять с половиной секунд на 880 000 версий-строк — честный full-scan класса с вычислением
актуальной версии каждой из 440 000 записей. Дорого стоит только «посчитать вообще всё».

**Keyset-пагинация** — страница за страницей по возрастанию цены (класс `цена`), без `OFFSET`:

```ts
const p1 = await db.цена().sort('data.amounts.RUB').limit(3).rows()   // [22.6 ms]
// → base 300, base 300, base 300 (варианты цены по возрастанию RUB)
const cur = cursorOf(p1[p1.length - 1], 'data.amounts.RUB')
const p2 = await db.цена().sort('data.amounts.RUB').after(cur).limit(3).rows()   // [26.1 ms]
// следующая тройка — строго после курсора, без пропусков и дублей на границе
```

## Акт 14. Машина времени

Вариант цены «Бороды» дорожает с 800 до 1000 ₽ — правим одну валюту, обе версии в истории:

```ts
const [цБорода] = await db.Услуга(борода).цена().rows()      // вариант «базовая»
await db.цена(цБорода.id).update({ amounts: { RUB: 1000 } }).rows()   // record-merge: меняется лишь RUB
db.цена(цБорода.id).first()                     // сейчас → { RUB: 1000 }
db.цена(цБорода.id).asOf(доПодорожания).first() // тогда → { RUB: 800 }
db.цена(цБорода.id).versions()                  // [6.1 ms]
// → [ { RUB: 800, updated: "…20:43:23" }, { RUB: 1000, updated: "…20:43:37" } ]
```

## Акт 16. Приватность (GDPR)

`anonymize()` затирает персональные поля новой версией и метит тегом — но **история
цела**, старая версия хранит настоящее имя (для аудита это важно):

```ts
await db.Клиент(id).anonymize(['name', 'phone']).rows()   // [19.2 ms]
// data → { name: "[erased]", phone: "[erased]", preferred_contact: "phone" }, tags → ["anonymized"]
db.Клиент(id).versions()[0].data.name   // → "Пётр Удаляев"  (первая версия нетронута)
```

## Акт 17. Вход: способы аутентификации

Все механики `db.auth` на живых scrypt/sha256/TOTP/OTP:

```ts
await db.auth.setPassword({ account, identifier: 'olga@salon.ru', password: 'Secr3t!' })
await db.auth.verifyPassword({ identifier: 'olga@salon.ru', password: 'Secr3t!' })   // [114.5 ms] → account
await db.auth.verifyPassword({ identifier: 'olga@salon.ru', password: 'x' })         //          → null

const { key } = await db.auth.issueApiKey({ account, name: 'касса' })   // → lts_14bf5ba9…
await db.auth.verifyApiKey(key)                                         // → account (в БД только sha256)

const totp = await db.auth.enrollTotp({ account, issuer: 'Пример' })
db.auth.totpEnabled(account)                              // → false (до первой проверки)
db.auth.verifyTotp({ account, code: totpCode(totp.secret) })   // → true → фактор активирован

const otp = await db.auth.issueOtp({ account, identifier: '+7 900 111' })
db.auth.verifyOtp({ identifier: '+7 900 111', code: otp.code })   // → account
db.auth.verifyOtp({ identifier: '+7 900 111', code: otp.code })   // → null (одноразовый, погашен)
```

scrypt намеренно медленный (~114 мс) — это защита пароля, не тормоз. API-ключ в БД лежит
только хэшем: даже дамп базы не выдаёт ключ.

## Акт 18. Сессии в Redis

```ts
const sessions = db.auth.sessions(redis)
const token = await sessions.start(account, { ttlSec: 3600, meta: { ip: '10.0.0.1' } })   // [2.8 ms]
await sessions.check(token)     // → { account, meta: { ip: "10.0.0.1" }, created: "…" }
await sessions.revoke(token)    // → true;  check после → null
await sessions.revokeAll(account)   // → 2  (погасили обе оставшиеся сессии)
```

Токен отдаётся один раз; в Redis лежит его sha256 — дамп Redis не раскрывает действующие
токены.

## Акт 19. Права доступа (ACL)

Ресурс-субъект (маска категорий) + ресурс-объект + правило между ними:

```ts
await db.resources.set({ alias: 'salonStaff:ACCOUNT', category: 'ACCOUNT', pattern: { categories: '{Staff}' } })
await db.resources.set({ alias: 'salon.book:API', category: 'API', pattern: { endpoint: 'salon.book' } })
await db.rules.set({ account: 'salonStaff:ACCOUNT', resource: 'salon.book:API', permission: 'allow', weight: 50 })

await db.acl.check(account, 'salon.book')   // [42.0 ms]
// → { allow: true, rule: { account: "salonStaff:ACCOUNT", resource: "salon.book:API", permission: "allow", weight: 50 } }
await db.acl.checkData(account, 'booking', 'READ')   // → true
```

## Акт 20. Изоляция арендатора и наблюдаемость

`enforceAccount` пришпиливает каждое чтение и запись к аккаунту — арендатор видит только
своё среди миллиона чужих строк:

```ts
const iso = await connect({ dsn, schema, account: tenant, owner: tenant, enforceAccount: true })
const [своя] = await iso.Организация().create({ name: 'Частная' }).rows()
своя.account === tenant     // → true
await iso.Организация().count()   // → 1   (только своя, 30 полигонных невидимы)
```

`onQuery` даёт метрику на каждый запрос — здесь порог `slowMs: 0` пометил всё медленным:

```ts
// onQuery → { mode: "count", classes: ["Service"], ms: 27.0, rows: 1, slow: true }
```

## Акт 21. Гарды: чего сделать нельзя

Библиотека ловит ошибки рано и с понятным текстом — многие ещё **при построении
цепочки**, до похода в БД:

```ts
db.Организация(org).Услуга().create({ name: 'X', duration: -1 }).rows()
// → validation failed for "Service": duration — …  (на терминале)

db.Мастер(ольга).запись().create({ start_datetime, end_datetime }).Локация.set(зал).Расписание.set(расп).rows()
// → link "booking" requires end "Service|Product|Complex"   (нет предмета — союз обязателен)
db.Мастер(ольга).навык().create().rows()   // → id (uuid v5) of "skill" needs end "Service"
db.Услуга('…').create({ name: 'Y' })  // → class "Service" computes id (uuid v5 from Org, name)

db.Локация(зал).Клиент()             // → no path Location → Customer  (СИНХРОННО, до БД)
db.запись().навык()                  // → LINK → LINK traversal is not supported (booking → skill)
db.Услуга({ name: 'X' }).create({})  // → create() takes no filter — searching is update()
db.Услуга().set({ name: 'X' })       // → set() split into create()/update() (0.16.0)
db.запись('x').Клиент.set('x')       // → link slot "Клиент" needs a write — add .create(…)/.update(…)
db.запись('x').update().Клиент.delete()   // → slot .delete() renamed to .unset() (0.16.0)
db.запись('…').update().Папка.set('x')    // → "Folder" is not a link end of "booking"
db.Мастер.set('x')                   // → slot "Мастер" needs an owner step
db.Услуга().link('X', 'y')           // → .link() removed (0.15.0) — use the link slot
db.Услуга().execute()                // → execute() renamed to run() (0.11.0)
```

Путь `Локация→Клиент` невозможен по схеме — и это ошибка сразу, а не пустой результат на
терминале.

## Что показал прогон

За один сквозной день салона задействованы **все публичные точки API** — от
`connect`/`up` до `anonymize`, сессий и ACL (полная матрица — в `lib/TESTPLAN.md`).
Четыре наблюдения, ради которых стоило гонять живой миллион:

1. **Одна грамматика на чтение и запись.** Путь по `Schema.links` работает одинаково;
   `create`/`update`/`delete` не перепутать, слот `.Класс.set()`/`.unset()` пишет связь,
   `pivot` возвращает к узлу. Ни строк-литералов классов, ни «магических» словарей.
2. **id рождается из данных и наследуется.** v7 — время для потоковых классов; v5 —
   `uuidv5` из концов/полей, объявленный ОДИН раз на абстрактном предке (`Element`, `slot`)
   и унаследованный: двойная бронь и дубль каталога мертвы на уровне схемы, create
   идемпотентен, id известен до создания.
3. **Позитивная доступность проще негативной.** Окно-смена = факт доступности; запись —
   самодостаточная строка (интервал + предмет + клиент). Ни `busy`, ни `shift`, ни сетки
   часовых слотов — половину классов старой модели сняли, а сценарии остались те же.
4. **История бесплатна и честна; дорого — только «посчитать всё».** 880 000 версий
   записей не мешают отчётам: агрегации берут актуальные версии, `asOf`/`versions`
   открывают прошлое; точечные пути — единицы-десятки мс, полный `count()` класса — секунды.

Полигон и оба скрипта в репозитории — числа выше можно перепроверить одной командой.
