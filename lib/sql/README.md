# SQL ядра letopis

Файлы ядра накатывает установщик (`lib/src/up.ts`, функция `install`; её зовёт `setup()`) по возрастанию номера; каждый
можно применить повторно — повторный накат той же ревизии данных не трогает. Миграций нет: дом другой ревизии движка
`setup()` не обновляет — его сносит `demolish()`, и `setup()` строит его заново.

## Подстановки при накате

| Маркер | Что подставляется |
|---|---|
| `@SCHEMA@` | имя схемы дома в кавычках идентификатора, например `"v2.salon"` |
| `@SCHEMA_NAME@` | имя схемы без кавычек идентификатора — для строковых литералов, например `v2.salon` |
| `@OWNER@` | роль-владелец схемы в кавычках идентификатора, по умолчанию `"letopis_owner"` |
| `@OWNER_NAME@` | имя роли-владельца без кавычек идентификатора, например `letopis_owner` (условия триггеров, `pg_has_role`) |
| `@APP@` | служебная роль дома в кавычках идентификатора: у каждого дома своя — `setup()` передаёт `"letopis_a_<имя>"` (длинное имя — хэш, как у роли консьержа `letopis_c_<имя>`); в неё входит роль консьержа этого дома, ей выданы функции и права на таблицы схемы. |
| `@APP_NAME@` | имя служебной роли без кавычек идентификатора, например `letopis_a_salon` |
| `@PGCRYPTO@` | схема, где установлен pgcrypto (`pg_extension.extnamespace`), в кавычках идентификатора |
| `@SYSTEM@` | id System — общих классов, аккаунтов и квартир дома: `2eba6d0a-1edd-4bb6-a85a-a703dab49035` |
| `@RESERVED_NAMES@` | методы цепочки, корня `db` и батча — `RESERVED_CLASS_NAMES` из `lib/src/types.ts`, литералами через запятую |
| `@MESSAGES@` | каталог сообщений базы — разделы `sql-*` каталога `lib/src/messages`: строковый литерал с JSON «ключ → `{ name, ru }`» для `message_catalog()` в `15-errors.sql` |
| `@SIGNALS@` | режим сигналов `class`, `tenant`, `opaque` или `none`: опция `setup({ signals })`, иначе сохранённый в `meta.signals` строки `secret` вида `KEY`, иначе `class` |
| `@ENGINE_VERSION@` | версия пакета (`lib/package.json`) — штамп движка в комментарии схемы (`99-revision.sql`) |
| `@ENGINE_SQL@` | 16 знаков sha256 исходного текста файлов `NN-*.sql` до подстановок (переводы строк — LF) и разделов `sql-*` каталога сообщений: `connect()` сверяет его с файлами своего пакета |

Маркер заменяется во всём тексте файла, в том числе в комментариях; неизвестный маркер — отказ `boot.unknown_marker`.
Те же маркеры действуют в своих сидах (`setup({ seeds: ['путь/к/файлу.sql'] })`).

## Колонки версии

Одинаковы в `entity` и `log`: `id`, `rev`, `class`, `cv`, `tenant`, `owner`, `links`, `data`, `tags`, `at` (время
версии), `author`, `agent`, `op`, `reason`. У `entity` ещё `ends` (генерируемая: все цели концов),
`created_at` и `validator` (у строк `Class`), у `log` — `seq` и `tx` (курсор подписки).

## Коды ошибок

Собственный класс SQLSTATE `LT`; текст — `letopis: <имя>: <сообщение>`, детали — JSON в `DETAIL`.
Источник истины — функция `error_catalog()` в `15-errors.sql`.

Тексты — по ключам каталога сообщений: `lt_fail(ключ, параметры jsonb, detail jsonb)` берёт имя
ошибки и русский шаблон из `message_catalog()` (`{имя}` — параметр, подставляет `lt_text()`), а в `DETAIL` кладёт поля
`detail` и ещё `key`, `params` — библиотека переносит их в `err.key` и `err.params`; текст тот же, что видит сырой SQL.
`LetopisError.detail`: без `detail` — `{}`; с `p_detail => 'null'` в `DETAIL` — признак `nodetail`, и у ошибки `detail` нет.
Свой SQLSTATE — `lt_raise(код, ключ, параметры, detail)`. Функции, которые исполняет служебная роль дома (`@APP@`)
(`inc`, `links_patch`), бросают `raise` сами: текст — `lt_text(ключ, параметры)`, она и `message_catalog()` выданы
этой роли; `DETAIL` без своих полей — с `'nodetail', true`. Все места бросают ошибки по ключам: перегрузки
`lt_fail(имя, текст, detail)` и `lt_raise(код, имя, текст, detail)` — сам механизм, вне `15-errors.sql` их не зовут
(`lt_raise` с текстом — единственный `raise`). Внутренняя ошибка — `lt_raise('XX000', ключ, …)` с кодом `internal`;
строки отказа ужесточения и нарушения данных несут `key` и `params`, а текст `problem` и `message` собирает `lt_text`.
Литеральный текст в `raise` и в `problem` ловит `check:docs` (`literals`).

| Код | Имя | Когда |
|---|---|---|
| LT001 | `no_session` | нет действующей сессии |
| LT002 | `target_not_found` | цель конца не найдена (одинаково для несуществующей и чужой) |
| LT003 | `invalid_data` | данные не проходят описание класса; в деталях `issues` — путь, ключевое слово, сообщение |
| LT004 | `undeclared_end` | конец не объявлен в классе |
| LT005 | `tenant_denied` | чужая квартира: запись в неё, работа вне квартиры ключа или без прописки |
| LT006 | `acl_denied` | отказ по правилам доступа |
| LT007 | `id_mismatch` | id не равен v5 от ключа; в деталях `expected` |
| LT008 | `id_from_db` | id класса без ключа выдаёт база |
| LT009 | `immutable_key` | ключевое поле, класс, id, квартиру, владельца менять нельзя |
| LT010 | `invalid_class` | описание класса отклонено, класс не найден или абстрактный |
| LT013 | `tightening_conflict` | ужесточению мешают строки; в деталях `rows`, `others` |
| LT014 | `isolation_level` | удаление — только в `read committed` |
| LT015 | `recreated_in_statement` | id удалён и создан заново одним оператором |
| LT017 | `delete_restricted` | удалению мешают ссылающиеся строки (`onDelete: restrict`); в деталях `rows`, `others` |
| LT018 | `not_deleted` | `restore` — только для удалённых объектов |
| LT019 | `acl_ambiguous` | правила с равным счётом спорят: одно разрешает, другое запрещает; в деталях `rules` |
| LT020 | `last_owner` | квартира осталась бы без owner: прописка потеряла метку owner любым путём — выписка, правка меток, удаление прописки, удаление аккаунта, жильцом или консьержем (триггер `entity_member_owner`); удаление квартиры не проверяется. В тексте — имя квартиры, в деталях `tenant` (id) и `name` |
| LT021 | `exists` | уже есть: имя квартиры занято, внешний id открывает другую квартиру |
| LT022 | `auth_failed` | ключ не подошёл (причина не раскрывается) |

## Порядок файлов

`10-core` → `15-errors` → `20-context` → `30-validate` → `40-class` → `50-acl` → `60-write` → `70-read` → `80-auth` →
`90-time` → `95-seed.system` → `99-revision`. Файл ядра — имя вида `NN-имя.sql`: только такие установщик накатывает и
считает в хэш штампа. Сиды `seed.<имя>.sql` (например `seed.booking.sql` — его генерирует `npm run seed:booking`)
накатываются после ядра только по опции `setup({ seeds })` и в штамп не входят.

Файлы описывают только нынешнюю ревизию (`ddl_revision` в `99-revision.sql` = `DDL_REVISION` в `lib/src/types.ts`):
`drop … if exists` в них — лишь там, где без него не пройдёт повторный накат той же ревизии (политики RLS в
`50-acl.sql`: у `create policy` нет `or replace`). Смена сигнатуры функции в пределах ревизии — `drop function if
exists` старой сигнатуры в том же файле, иначе повторный накат оставит лишнюю перегрузку.
