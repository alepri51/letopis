# Фоновые задачи консьержа

## Зачем

Не всё в приложении делает человек. Ночная очистка, рассылка, отчёт по расписанию, перенос данных — это задачи без входа: ключа жильца у них нет. Их выполняет консьерж. У него два способа зайти в квартиру:

- **`db.in('Мир')`** — консьерж сам. Ему можно всё.
- **`db.as(аккаунт, 'Мир')`** — консьерж от имени жильца. Ему можно ровно то, что можно этому жильцу.

Оба вызова отдают корень квартиры: от него идут те же цепочки, что и у жильца.

## Что выбрать

| Вопрос | `db.in(квартира)` | `db.as(аккаунт, квартира)` |
|---|---|---|
| чьи права | консьержа: полный доступ к квартире | прописанного жильца: его правила матрицы |
| кто автор версии в журнале | консьерж | жилец; исполнитель (`agent`) — консьерж |
| когда брать | задача самого приложения: очистка, пересчёт, перенос, служебные правила | задача, которую поставил человек: отчёт, выгрузка, отложенное действие |
| квартира | имя или id | имя или id |
| если не вышло | квартиры нет — `target_not_found` | аккаунт не прописан в квартире — `acl_denied`; аккаунта нет — `target_not_found` |

Простое правило: если у задачи есть «заказчик» среди жильцов — берите `db.as`. Тогда задача не увидит и не изменит больше, чем мог бы он сам, а в истории останется его имя.

## Задача приложения: `db.in`

Пример: раз в сутки отменить заказы, которые неделю висят неоплаченными. В модели у заказа есть поля `status` и `date`.

```ts
import { connect, lt } from 'letopis'

const db = await connect(process.env.LETOPIS_PASS!)       // консьерж: пропуск из окружения
const weekAgo = new Date(Date.now() - 7 * 24 * 3600 * 1000).toISOString()

for (const t of await db.tenants()) {                     // все квартиры дома: { id, name }
  const flat = await db.in(t.id)                          // консьерж в квартире
  const cancelled = await flat.Order({ status: 'new', date: lt(weekAgo) })
    .update({ status: 'cancelled' }, { reason: 'не оплачен за неделю' })
    .rows()
  console.log(`${t.name}: отменено заказов — ${cancelled.length}`)
}

await db.close()
```

Что здесь важно:

- `db.tenants()` отдаёт все квартиры дома. Консьерж обходит их по очереди: у каждой квартиры свой корень и свои данные.
- У правки есть фильтр, поэтому она задевает только подходящие заказы. Править все строки шага можно только явно — `update(…, { all: true })`.
- Причина (`reason`) попадёт в журнал рядом с версией. По ней потом видно, что заказ отменила ночная задача, а не человек.
- Автор этих версий в журнале — консьерж.

## Задача от имени жильца: `db.as`

Пример: Аня попросила прислать ей отчёт к утру. Приложение запомнило, кто попросил и в какой квартире, а ночью собирает отчёт её правами.

```ts
import { connect } from 'letopis'

const db = await connect(process.env.LETOPIS_PASS!)

// когда Аня ставит задачу, приложение сохраняет её аккаунт и квартиру:
//   { account: me.account, tenant: me.tenant }
const job = { account: '…id аккаунта Ани…', tenant: '…id квартиры «Мир»…' }

const anya = await db.as(job.account, job.tenant)         // консьерж с правами Ани
const orders = await anya.Order({ status: 'paid' }).rows()    // только то, что видит Аня
await anya.Report().create({ title: 'Оплаченные заказы', count: orders.length }).rows()

await db.close()
```

Что здесь важно:

- Задача видит только то, что видит Аня. Если матрица не даёт ей читать заказы — ответ пустой.
- Запись — два разных случая. У Ани нет права писать класс `Report` — отказ `acl_denied`. Право на класс есть, но именно эту строку Аня не видит (чужая строка, правило с условием) — правка возвращает **0 строк, без ошибки**: для неё такой строки нет. Проверяйте длину ответа.
- Автор версии отчёта в журнале — Аня, исполнитель (`agent`) — консьерж. Так в истории видно и «чьё это», и «кто сделал».
- Аню выписали из квартиры — `db.as` ответит `acl_denied`. Её аккаунт удалён — `target_not_found`. Задачу тогда нужно снять, а не повторять.
- id аккаунта жильца — `me.account` в его корне квартиры. Сохраните его вместе с задачей.

## Что приложение может от лица человека {#от-лица-человека}

Корень `db.as(аккаунт, 'Мир')` — это консьерж, который работает от лица жильца. Данные он видит и меняет как этот жилец. А то, чем человек подтверждает, что он — это он, остаётся только у самого человека.

| Что | Через `db.as` | Пояснение |
|---|---|---|
| читать и писать данные: цепочки, `begin()`, `acl.check`, `acl.checkData` | да | по правам этого жильца; автор версии — жилец, исполнитель (`agent`) — консьерж |
| звать людей: `invite`, `invites`, `revokeInvite` | да | с ролями, которые этому жильцу можно выдавать; в письме `from` — этот жилец |
| список людей: `acl.people()` | да | те же, кого видит этот жилец |
| сменить имя: `changeName(имя)` | да | меняется имя этого человека; недавний вход не нужен — за человека ручается приложение. Так поддержка исправляет опечатку в имени |
| ключи и пароль: `keys.*` | нет | `invalid_query`, ключ `api.resident_only` |
| сменить контакт: `changeContact` | нет | `invalid_query`, ключ `api.resident_only` |
| выписаться, удалить аккаунт, выйти везде: `leave`, `deleteAccount`, `closeAll` | нет | `invalid_query`, ключ `api.resident_only` |
| сервер MCP: `createMcpServer(корень)` | нет | `user_session_required` (ключ `mcp.resident_required`): помощнику нужен вход самого жильца |

```ts
// поддержка исправляет опечатку в имени: приложение — от лица человека
const anya = await db.as(account, 'Мир')
await anya.changeName('Анна Петрова')          // { name: 'Анна Петрова' } — видно во всех её квартирах
```

У корня `db.in('Мир')` — консьерж сам — все строки «нет» тоже закрыты, и `changeName` тоже: у консьержа нет имени человека (`api.resident_only`). Зато людей и приглашения квартиры он видит все.

Отличить корень консьержа от корня жильца можно по свойству `concierge`: у корней `db.in()` и `db.as()` оно `true`, у корня жильца — `false`.

## Запуск по расписанию

letopis сам задачи не запускает. Расписание — дело приложения или внешнего планировщика: cron, задача Kubernetes, таймер в самом процессе.

- **Отдельный скрипт.** Подключился, сделал работу, закрыл консьержа (`db.close()`). Так устроены оба примера выше.
- **Таймер в веб-сервисе.** Консьерж у процесса уже есть — берите его же, второй `connect()` не нужен.
- **Несколько экземпляров сервиса.** Одну и ту же задачу могут запустить два процесса сразу. Пишите задачу так, чтобы повтор не навредил: правка с фильтром по состоянию (`{ status: 'new' }`) второй раз ничего не найдёт, а запись с ключом второй раз ответит `exists`.

Обслуживание самого дома — чистка истёкших сессий, кодов и приглашений — тоже может идти по таймеру сервиса: `await db.maintain()`. То же делает команда `letopis maintain` мастер-ключом: [«Эксплуатация»](../ops/#обслуживание-letopis-maintain).

## Подводные камни

- **`db.in` — полный доступ.** Ошибка в фильтре заденет чужие строки квартиры, и матрица её не остановит. Где можно — берите `db.as`.
- **Правила, которые завёл консьерж, жилец не снимет.** Правила, которые жильцы не должны трогать, пишите через `db.in`: [«Квартиры и права»](../access/).
- **В сохранённой задаче держите id квартиры, а не имя.** `db.in()` и `db.as()` принимают и имя, и id. Но квартиру могут удалить и завести другую с тем же именем — тогда имя приведёт в новую. id квартиры — `me.tenant`, имя — `me.tenantName`.
- **Пустой ответ — не ошибка.** Правка, которая ничего не нашла — или нашла строку, которой жильцу не видно, — возвращает пустой список, а не `acl_denied`. Проверяйте длину ответа, если от неё зависит следующий шаг.
- **Помощнику MCP корень консьержа не отдать.** Сервер MCP работает только с корнем жильца: [«ИИ-агенты: MCP»](../mcp/).

## Где это в сервисах

В [документах с аудитом](../services/documents) демо-черновики пишет консьерж от имени юриста и руководителя (`db.as`): автор версии — человек, исполнитель — консьерж. В [Helpdesk](../services/helpdesk) режим «работать от имени» устроен так же.
