# Первые 15 минут

От пустой базы до первых данных — четыре шага в одном процессе Node:

1. `up({ tenant, login })` от администратора базы — схема, арендатор с первым пользователем и роль приложения;
2. `connect({ dsn: r.login.dsn, admin, token })` — приложение подключается этой ролью от имени пользователя;
3. модель на `letopis/model` и `syncModels` — описания классов в базе, **в каждом арендаторе отдельно**;
4. цепочки — запись и чтение данных.

Хотите сначала понять, как letopis устроен, — начните с главы [«Что такое letopis»](../basics/what-is). Кто такие аккаунт, арендатор, сессия и сервис и как они связаны — на [карте понятий](../concepts/).

## Что нужно

- Node 22 или новее;
- PostgreSQL 18 и роль администратора (суперпользователь или `CREATEROLE`). Нет своей базы — запустите ту, на которой работают примеры этого сайта:
  ```sh
  docker compose -f services/compose.yaml up -d pg     # PostgreSQL 18 на 127.0.0.1:15440
  ```
- пакеты:
  ```sh
  npm install letopis zod
  ```

::: warning Несколько арендаторов — модель в каждом
Классы, которые записал `syncModels`, принадлежат **арендатору сессии**. Второй арендатор (второй клуб, салон, компания) их не видит и на первом же обращении к классу получает `invalid_class`. Вызывайте `syncModels` для каждого арендатора — на подключении с сессией этого арендатора, например при запуске приложения:

```ts
for (const t of tenants) {   // t — результат createTenant: { tenant, user, … }
  const db = await svc.as(t.user, { tenant: t.tenant })
  await syncModels(db, models, { apply: true })   // повтор безопасен: неизменённые классы не трогаются
}
```

Новый арендатор, заведённый позже, тоже получает модель отдельным вызовом. Почему так — [«Арендаторы и права»](../access/).
:::

## Один процесс — для малых приложений

С `admin` администраторские вызовы — `syncModels`, `load` и `maintain` — идут вторым пулом с той же сессией, а цепочки — всегда ролью приложения под правами базы. Цена — пароль администратора в процессе приложения: взломанный процесс получит и его. Большому приложению подойдёт путь из [«Старта с нуля»](../start/): веб-приложение подключается по ключу сервиса без пароля администратора, а администраторская работа идёт в отдельном процессе.

## Десять главных нюансов

Ловушки, на которых чаще всего спотыкаются в первый день, — по порядку шагов выше. У каждого — живой пример. Все нюансы по темам — на странице [«Все нюансы»](../nuances/).

<!-- nuances:top -->
1. Ключ сервиса up() выдаёт только при первой установке или когда не осталось ни одного ключа API, кроме отозванных: истёкший или выключенный ключ тоже в счёт, нового не будет. [Пример](../install/#ex-install-01-up-and-connect)
2. syncModels без apply — сухой прогон: ничего не пишет, отвечает, что будет создано и изменено. [Пример](../models/#ex-models-01-shop-model)
3. Классы, записанные syncModels, принадлежат арендатору: другой арендатор не видит даже класса (invalid_class). [Пример](../access/#ex-access-01-rules)
4. Значения ключа берутся как есть: email в разном регистре даёт разные id. [Пример](../models/#ex-models-02-keys-and-ids)
5. У цепочки нет метода then: await db.Класс(…) отдаёт саму цепочку и ничего не читает — запрос выполняет терминал (rows, first, count…). [Пример](../write/#ex-write-06-link-verbs)
6. upsert заменяет данные целиком: поля, которых нет в объекте, пропадают; затирает параллельные приращения. [Пример](../write/#ex-write-01-create-update-upsert)
7. update без найденных строк возвращает пустой список без ошибки — проверяйте длину ответа. От гонки это не защищает: условие фильтра при параллельной записи не перепроверяется — берите forUpdate(), { rev } или ключ. [Пример](../write/#ex-write-01-create-update-upsert)
8. delete() без { confirm: true } ничего не удаляет — возвращает предпросмотр: что удалится и с каким действием ($action). [Пример](../basics/what-is#ex-basics-01-first-object)
9. Права включены всегда и по умолчанию запрещают всё; createTenant даёт правило «своим можно всё» (вес 10). [Пример](../access/#ex-access-01-rules)
10. Отозванная или истёкшая сессия при чтении не даёт ошибки: запросы просто возвращают пустой результат. no_session бросают функции входа (auth.*) и connect() с неверным ключом — сервис проверяет сессию в начале каждого запроса. [Пример](../auth/#ex-auth-02-sessions-tenants)
