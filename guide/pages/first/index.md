# Первые 15 минут: один процесс

От пустой базы до первых данных — четыре шага в одном процессе Node (так устроено малое приложение; веб-сервис с ключом сервиса и отдельной установкой — [«Старт с нуля»](../start/)):

1. `up({ tenant, login })` от администратора базы — схема, арендатор с первым пользователем и роль приложения;
2. `connect({ dsn: r.login.dsn, admin, token })` — приложение подключается этой ролью от имени пользователя (зачем здесь `admin` — в [сводке значений](#сводка-значений));
3. модель на `letopis/model` и `syncModels` — описания классов в базе, **в каждом арендаторе отдельно**;
4. цепочки — запись и чтение данных.

Потом — [удаление и возврат](#удалить-и-вернуть-только-по-expect) так, как их делают в настоящем приложении, и [прокат целиком](#прокат-целиком-ключ-удаление-и-возврат-одним-фрагментом) одним фрагментом. Хотите сначала понять, как letopis устроен, — глава [«Что такое letopis»](../basics/what-is); кто такие аккаунт, арендатор, сессия и сервис — [карта понятий](../concepts/).

## Что нужно

- Node 22 или новее;
- PostgreSQL 18 и роль-установщик: суперпользователь или роль с `CREATEROLE` и правом `CREATE` на базе ([какие права нужны](../install/#права-установщика)). Нет своей базы — запустите PostgreSQL 18 в Docker и дождитесь готовности (репозиторий не нужен):
  ```sh
  docker run -d --name pg18 -e POSTGRES_PASSWORD=guide -e POSTGRES_DB=letopis -p 127.0.0.1:15440:5432 postgres:18
  until docker exec pg18 pg_isready -h 127.0.0.1 -U postgres -d letopis; do sleep 1; done
  ```
  Строка подключения администратора — `postgres://postgres:guide@127.0.0.1:15440/letopis`. Пароль `guide` стоит в двух местах — в `POSTGRES_PASSWORD=guide` команды `docker run` и в строке подключения: меняете — меняйте в обоих. Порт 15440 занят — возьмите свободный, тоже в двух местах: первое число в `-p 127.0.0.1:15440:5432` и порт в строке (`-p 127.0.0.1:15441:5432` → `…@127.0.0.1:15441/letopis`). Остановить — `docker stop pg18`, запустить снова — `docker start pg18`. PowerShell — ожидание так: `do { Start-Sleep 1; docker exec pg18 pg_isready -h 127.0.0.1 -U postgres -d letopis } until ($LASTEXITCODE -eq 0)`.
- пакеты — в пустой папке проекта (`type=module` нужен для `await` на верхнем уровне; `tsx` запускает TypeScript):
  ```sh
  npm init -y && npm pkg set type=module && npm i letopis@3 zod postgres@3 && npm i -D tsx
  ```
  `postgres@3` — драйвер той же основной версии, на которой работает letopis: пул администратора из него передают в `createTenant`.
- запуск примера: скопируйте скрипт кнопкой «Копировать», сохраните под именем над ним (здесь — `first-15.ts`) и запустите:
  ```sh
  ADMIN_DSN=postgres://postgres:guide@127.0.0.1:15440/letopis npx tsx first-15.ts
  ```
  PowerShell: `$env:ADMIN_DSN = 'postgres://postgres:guide@127.0.0.1:15440/letopis'; npx tsx first-15.ts`. Роль приложения скрипт заводит сам (`up({ login })`); вывод сравните с блоком «Ожидаемый вывод» под скриптом.

Это самостоятельная программа: скопируйте её кнопкой «Копировать» и запустите по рецепту выше. Что после каждого шага лежит в таблицах `entity` (текущее состояние объектов) и `log` (журнал версий) — в пошаговом показе под программой («Пошагово: что происходит в базе»); служебные строки установки там свёрнуты — их показывает кнопка над таблицей.

Ваш вывод совпадёт с ожидаемым не во всём. **id будут те же**: они не случайные (uuid версии 5) — id арендатора вычисляется из его имени («Ромашка»), id пользователя — из логина, id объекта класса с ключом (`key`) — из id арендатора, имени класса и значений ключа. Поэтому одинаковые имя арендатора, логин и ключи дают одинаковые id в любой базе и схеме; случайный id получает только объект класса без ключа. **Свои будут** время (`at`), токены сессий, ключ сервиса, если его выдал `up()`, и хэши паролей.

::: warning Несколько арендаторов — модель в каждом
Классы, которые записал `syncModels`, принадлежат **арендатору сессии**: второй арендатор (второй клуб, салон, компания) их не видит и получает `invalid_class`. Второго арендатора заводит [`createTenant(admin, schema, { name, user })`](../reference/setup#export-createtenant) — `admin` здесь пул `postgres(ADMIN_DSN)`, а не строка, `schema` — та же схема, что у `up()`; затем `syncModels` на подключении с сессией его пользователя.

Продолжение программы `first-15.ts` выше: `ADMIN_DSN`, `r`, `connect`, `syncModels`, `Shop` и `Product` в ней уже есть. Добавьте `createTenant` в импорт из `letopis` и допишите перед последней строкой `process.exit(0)`:

```ts
const admin = postgres(ADMIN_DSN)                                     // пул администратора, не строка
const t = await createTenant(admin, r.schema, {                       // та же схема, что у up()
  name: 'Василёк', user: { name: 'Борис', login: 'boris@vasilek.ru', password: 'Василёк-2026!' },
})
await admin.end()
const db2 = await connect({ dsn: r.login!.dsn!, admin: ADMIN_DSN, schema: r.schema, token: t.token! })   // Борис в «Васильке»
await syncModels(db2, [Shop, Product], { apply: true })               // своя копия модели; повтор безопасен
console.log(await db2.Shop().rows())                                  // [] — магазины «Ромашки» Борису не видны
```

Почему так — [«Арендаторы и права»](../access/).
:::

## Сводка значений

Какие строки подключения, ключи и токены встречаются в примерах, откуда они берутся и кому нужны.

| Значение | Откуда берётся | Кому нужно | Где хранить |
|---|---|---|---|
| `ADMIN_DSN` — строка подключения администратора базы | задаёте вы: роль-установщик — суперпользователь или роль с `CREATEROLE` и правом `CREATE` на базе ([какие права нужны](../install/#права-установщика)) | установке и администраторской работе: `up()`, `createTenant(postgres(ADMIN_DSN), …)`, массовой загрузке `db.load`; в одном процессе — опции `connect({ admin })` | только у процесса установки и обслуживания (скрипт, CI); в веб-приложение не кладут — кроме малого приложения «одним процессом», как на этой странице |
| `APP_DSN` — строка подключения роли приложения | `up({ login: { user, password } })` заводит роль (член группы `letopis_app`) и возвращает её строку `r.login.dsn` — тот же адрес и база, что у `ADMIN_DSN`, но имя и пароль роли; или вручную: `create role … login password …` и `grant letopis_app to …` | приложению: `connect({ dsn: APP_DSN, … })` — под этой ролью база сама проверяет права (RLS) | в настройках приложения (переменная окружения) |
| `serviceKey` — ключ сервиса `lts_…` | `up()` возвращает `r.serviceKey` при первой установке; надёжнее задать свой заранее — `up({ serviceKey })` ([как](../start/#service-key)) | серверной части: `connect({ dsn: APP_DSN, schema, apiKey })` — подключение сервиса `svc`; через него вход пользователей (`svc.auth.verifyPassword`) и работа от их имени (`svc.as`) | секрет: файл с правами только владельца или хранилище секретов; в базе лежит только хэш, второй раз ключ не выдаётся |
| `tenant` — id арендатора | `createTenant()` → `t.tenant`, `up({ tenant })` → `r.tenant.tenant`; вычисляется из имени арендатора | `svc.as(аккаунт, { tenant })` — в каком арендаторе работать | не секрет: можно держать в настройках или в своей таблице |
| `token` — токен сессии пользователя | вход: `svc.auth.verifyPassword({ identifier, password })` → `{ account, token }`; `svc.auth.sessionFor(аккаунт, { ttl })` — сессия для другого процесса (`ttl` в секундах, по умолчанию 7 суток); `createTenant()` и `up({ tenant })` — сессия первого пользователя в новом арендаторе (`t.token`, `r.tenant.token`) | `connect({ dsn: APP_DSN, schema, token })` — подключение от имени пользователя; `svc.auth.session(token)` — чья это сессия | секрет пользователя (например, cookie); гасит `auth.revoke(token)` |

«Токена арендатора» нет: `token`, который возвращают `createTenant()` и `up({ tenant })`, — сессия первого пользователя в этом арендаторе. Сессия обычного входа (`verifyPassword`) начинается в личном арендаторе пользователя; в нужный переходят `db.auth.switch(tenant)` или работают через `svc.as(аккаунт, { tenant })`.

**Имя схемы.** `schema: 'myapp'` и `schema: 'v2.myapp'` — одно и то же: имя без точки `up()`, `connect()` и `createTenant()` дополняют префиксом `v2.` — это версия структуры таблиц letopis. В PostgreSQL схема так и называется — `v2.myapp`, с точкой внутри имени, поэтому в своём SQL её пишут в кавычках: `select * from "v2.myapp".entity`. Полное имя возвращает `up()` в `r.schema`.

**Почему у приложения нет `ADMIN_DSN`.** Администратор базы — суперпользователь или член роли-владельца схемы — обходит правила доступа (RLS): под ним база не проверяет права и видны данные всех арендаторов. Поэтому `connect()` с такой ролью без `allowBypassRls: true` отказывает (`bypass_rls`), а с этой опцией печатает предупреждение «letopis: администраторское подключение — RLS не действует, данные всех арендаторов видны». Приложение ходит ролью приложения: каждый запрос база проверяет сама, и ошибка в коде приложения не откроет чужие данные.

**Зачем `admin` в `connect()` на этой странице.** Здесь всё приложение — один процесс. Цепочки и `db.sql` идут ролью приложения (`r.login.dsn`) под правами базы, а `admin` — строка администратора: по ней при первой надобности открывается второй пул (не больше двух соединений) с той же сессией, только для администраторских вызовов — `load` (без администратора — отказ `admin_required`), `maintain` и `syncModels` (правка класса, у которого уже есть строки, может требовать прав, которых у роли приложения нет). Цена — пароль администратора в процессе приложения: взломанный процесс получит и его. Большому приложению подойдёт путь из [«Старта с нуля»](../start/): веб-сервис подключается по ключу сервиса без пароля администратора, а администраторская работа идёт отдельным процессом.

## Удалить и вернуть: только по expect

Удаление в letopis — два шага, и второй всегда со сверкой: удаляется **ровно то, что человек видел**.

```ts
const preview = await db.Member(member).delete().rows()       // 1. ничего не удаляет: что удалится ($action, $depth)
// 2. показать preview пользователю; он нажал «Удалить»
const gone = await db.Member(member)
  .delete({ confirm: true, expect: preview, reason: 'удаление участника (op-17)' }).rows()   // 3. ровно показанное
```

- **Без `expect` подтверждение не пройдёт.** `delete({ confirm: true })` — отказ `invalid_query` (ключ `write.confirm_without_expect`), ничего не удалено: между показом и нажатием в каскад могла добавиться строка, и она ушла бы без спроса.
- **Изменилось — `conflict`.** Если состав удаления за это время поменялся, ничего не удаляется, а новый предпросмотр — в `err.detail.preview`: покажите его и подтверждайте уже с ним.
- **Ответ — надгробия.** `gone` — цель и весь каскад с `id` и `rev`. Сохраните его: по нему удаление и возвращают.

```ts
await db.Member(member).restore({ expect: gone.filter((r) => r.class === 'Member') }).rows()   // сам участник
const loans = gone.filter((r) => r.class === 'OpenLoan')                       // его выдачи из того же удаления
const back = await db.OpenLoan(loans.map((r) => r.id)).restore({ expect: loans, partial: true }).rows()
const lost = back.filter((r) => r.$action === 'skip')                          // не вернулись — причина в r.$why
```

- **Без `expect` возврат не пройдёт.** `restore()` — отказ `invalid_query` (ключ `write.restore_without_expect`): последний снимок объекта может быть уже чужим — вещь после удаления выдавали другому.
- **`partial: true`** — вернуть то, что можно; остальное приходит строками-пропусками `$action: 'skip'` с причиной `$why`.
- Осознанно, без сверки — `delete({ confirm: true, all: true })` и `restore({ all: true })`. В приложении для людей так не делают.

Подробно — [«Удаление и восстановление»](../delete/).

## Прокат целиком: ключ, удаление и возврат одним фрагментом

Клуб выдаёт вещи участникам. Пример ниже держит все три правила, на которых спотыкаются в первый день, — скопируйте его кнопкой «Копировать» и запустите на своей базе.

<Example id="first/01-rental" />

Что в нём и зачем:

1. **Одна открытая выдача на вещь — ключом.** Открытая выдача — отдельная связь с ключом только из вещи: `link('OpenLoan', { … }, { ends: { Item: one(Item), Member: one(Member).onDelete('cascade') }, key: ['Item'] })`. id выдачи вычисляется из вещи, поэтому вторая выдача той же вещи — отказ `exists` при любом числе процессов. Проверка «есть ли выдача» в коде этого не удержит: два запроса проверят одновременно и оба выдадут. Вернули вещь — удаляют эту строку; следующая выдача продолжает её историю.
2. **Удаление — по `expect`.** Предпросмотр показывают человеку, подтверждение идёт с ним: удаляется ровно показанное, а не то, что успело добавиться.
3. **Возврат — по надгробиям этого удаления, с `partial`.** Участника удалили — его выдача ушла каскадом; вещь тем временем выдали другому. Возврат по надгробиям удаления (`restore({ expect, partial: true })`) вернёт участника, но не оживит его выдачу поверх чужой: она придёт пропуском `reissued`, а если вещь успели и вернуть — `changed`.
4. **`$why` — в текст для человека:**

| `$why` | Что случилось | Что сказать |
|---|---|---|
| `changed` | после удаления строку пересоздавали, правили или удалили снова — вещь выдавали другому | «выдача не вернулась: вещь после удаления выдавали другому» |
| `reissued` | id занят живой строкой с тем же ключом — вещь сейчас у другого | «вещь сейчас выдана другому» |
| `restored` | строку уже вернули | «уже возвращено» |

::: details Как превратить ошибку letopis в текст для человека
По `err.code` программа решает, что делать, по `err.key` — что именно случилось; `err.message` — для журнала, а не для пользователя.

```ts
import { LetopisError } from 'letopis'

function say(e: unknown): string {
  if (!(e instanceof LetopisError)) throw e
  switch (e.code) {
    case 'exists': return 'такая запись уже есть'                       // ключ занят: вещь уже выдана
    case 'conflict': return 'данные изменились — посмотрите ещё раз'    // устарел предпросмотр или версия
    case 'target_not_found': return 'не найдено: объект удалили или он вам не виден'
    case 'invalid_data': return 'проверьте введённые данные'            // подробности — e.issues
    case 'acl_denied': return 'недостаточно прав'
    default: throw e                                                    // ошибка в коде — в журнал, не пользователю
  }
}
```

Все коды и ключи — глава [«Ошибки»](../errors/).
:::

## Десять главных нюансов

Ловушки, на которых чаще всего спотыкаются в первый день, — по порядку шагов выше. У каждого — живой пример. Все нюансы по темам — на странице [«Все нюансы»](../nuances/).

<!-- nuances:top -->
1. Ключ сервиса up() выдаёт только при первой установке или когда не осталось ни одного ключа API, кроме отозванных: истёкший или выключенный ключ тоже в счёт, нового не будет. [Пример](../install/#ex-install-01-up-and-connect)
2. syncModels без apply — сухой прогон: ничего не пишет, отвечает, что будет создано и изменено. [Пример](../models/#ex-models-01-shop-model)
3. Классы, записанные syncModels, принадлежат арендатору: другой арендатор не видит даже класса (invalid_class). [Пример](../access/#ex-access-01-rules)
4. Значения ключа берутся как есть: email в разном регистре даёт разные id. [Пример](../models/#ex-models-02-keys-and-ids)
5. У цепочки нет метода then: await db.Класс(…) отдаёт саму цепочку и ничего не читает — запрос выполняет терминал (rows, first, count…). [Пример](../write/#ex-write-06-link-verbs)
6. upsert заменяет данные целиком: поля, которых нет в объекте, пропадают; затирает параллельные приращения. [Пример](../write/#ex-write-01-create-update-upsert)
7. update без найденных строк возвращает пустой список без ошибки — проверяйте длину ответа. Фильтр по данным при гонке перепроверяется под блокировкой: из двух одновременных правок одной строки пройдёт одна, вторая получит пустой ответ. Правило «одна открытая запись на объект» так не удержать — его держит ключ; «прочитал — посчитал — записал» — forUpdate() в db.begin() или { rev }. [Пример](../write/#ex-write-01-create-update-upsert)
8. delete() без { confirm: true } ничего не удаляет — возвращает предпросмотр: что удалится и с каким действием ($action). [Пример](../basics/what-is#ex-basics-01-first-object)
9. Права включены всегда и по умолчанию запрещают всё; createTenant даёт правило «своим можно всё» (вес 10). [Пример](../access/#ex-access-01-rules)
10. Отозванная или истёкшая сессия при чтении не даёт ошибки: запросы просто возвращают пустой результат. no_session бросают функции входа (auth.*) и connect() с неверным ключом или погашенным токеном — сервис проверяет сессию в начале каждого запроса. [Пример](../auth/#ex-auth-02-sessions-tenants)
<!-- /nuances:top -->

::: details Транзакция db.begin() — форма вызова (к нюансу 7)
`begin()` открывает транзакцию, закрывают её `tr.commit()` или `tr.rollback()`; ошибка — откатить и пробросить. Функцию `begin()` не принимает: `db.begin(async (tr) => …)` — отказ `invalid_query` ([пример](../errors/#ex-errors-01-api-errors)).

Продолжение программы `first-15.ts` выше (`db` и модель товара `Product` — из неё): «прочитал — посчитал — записал» — поднять цену товара на `percent` процентов так, чтобы одновременная правка той же строки не потерялась.

```ts
async function raisePrice(sku: string, percent: number) {
  const tr = await db.begin({ reason: 'наценка' })
  try {
    const p = await tr.Product({ sku }).forUpdate().first()          // строка заблокирована до конца транзакции
    if (!p) {
      await tr.rollback()
      return null                                                    // такого товара нет
    }
    const price = Math.round(Number(p.data.price) * (1 + percent / 100))
    const [row] = await tr.Product(p).update({ price }).rows()
    await tr.commit()
    return row
  } catch (e) {
    await tr.rollback()   // после commit() или rollback() ничего не делает
    throw e
  }
}

console.log((await raisePrice('M-1', 10))?.data)                     // { sku: 'M-1', price: 440, title: 'Кружка' }
```
