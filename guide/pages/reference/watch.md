# Подписка и кэш

Подписка читает журнал изменений по курсору и будит ожидание по сигналам базы. Кэш результатов хранит ответы цепочек в памяти процесса.

## Подписка

### db.watch() {#db-watch}

```ts
watch(opts?: WatchOptions): Subscription
```

Подписка по курсору: for await (const ev of db.watch({ from })) …; sub.cursor — откуда продолжить.

Каждое событие — одна версия объекта из журнала: `ev.row` — сама версия (у удаления — надгробие с `$deleted`), `ev.id`, `ev.class`, `ev.op` — вид операции, `ev.rev` — номер версии, `ev.at` — время версии, `ev.cursor` — курсор события. Обработав событие, сохраняйте курсор подписки `sub.cursor`: `db.watch({ from: cursor })` продолжит сразу после этого события, без потерь и повторов. События идут в порядке номеров транзакций, а внутри транзакции — в порядке записи. Это не порядок фиксации, поэтому версии одного объекта сверяйте по `rev`. Служебные записи журнала тоже приходят событиями: `purge` (стёрта история удалённого объекта) и `trim` (обрезана старая история) — в классе объекта, а запись сброса арендатора (`op` — `reset`, класс `#reset`) — только подписке без `classes`. Подписка видит только то, что разрешено её сессии: права и арендатора проверяет база. Долгая пишущая транзакция в любой базе того же кластера PostgreSQL задерживает поток: события транзакций, начавших запись позже неё, ждут её конца. Насколько поток задержан, показывает `sub.lag()`. Остановить подписку — `break` в цикле или `sub.close()`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `WatchOptions` | `{}` | Опции подписки — таблица ниже. |

**Опции `WatchOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="watch-from"></span>`from` | `string` | `'now'` | Откуда: курсор (sub.cursor или курсор события), 'now' (по умолчанию — изменения после подписки) или 'start' (весь журнал). С курсором подписка начнёт сразу после него. С `'now'` момент подписки запоминает отдельный запрос к базе: чтобы запись, сделанная сразу после `db.watch()`, попала в поток, сначала дождитесь `await sub.ready()`.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) |
| <span id="watch-classes"></span>`classes` | `string[]` | все классы | Только эти классы (с потомками). Потомков подписка берёт из реестра классов подключения в момент вызова `db.watch()`: класс, описанный позже, в неё не попадёт. Строка, которая ушла из этих классов сменой класса с прежним id (например, `reclass` в класс без ключа), приходит событием удаления в прежнем классе: `op: 'delete'`, `row` — прежняя версия с `$deleted`. Такое событие приходит, если прежнюю версию подписчик видел.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) |
| <span id="watch-batch"></span>`batch` | `number` | `500` | Событий за запрос (по умолчанию 500).<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |
| <span id="watch-pollms"></span>`pollMs` | `number` | `1000` | Запасной опрос, мс (по умолчанию 1000; без LISTEN — единственный способ узнать о событиях). Запасной опрос — проверка журнала по таймеру, даже если сигнала не было: так подписка находит события, сигнал о которых потерялся. `LISTEN` — команда PostgreSQL, которой подключение слушает сигналы базы; её нет при `connect({ listen: false })` и в установке с `up({ signals: 'none' })`.<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |

**Возвращает:** `Subscription` ([Subscription](./types#type-subscription)) — Подписку: события из неё берут циклом `for await (const ev of sub)` или вызовом `await sub.next()`. `db.watch()` возвращается сразу, не дожидаясь базы; события подписка читает при первом `next()`.

**Ошибки** ([все коды](../errors/)):

- `invalid_class` — класса из `classes` нет в реестре классов подключения.
- `invalid_query` — `from` — не `'now'`, не `'start'` и не курсор.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору)

### sub.cursor {#subscription-cursor}

```ts
readonly cursor: string | null
```

Курсор подписки: позиция после последнего выданного события (или начальная точка). Догнав журнал, подписка обновляет в нём время и на пустых опросах, поэтому его, а не курсор события, сохраняют, чтобы продолжить после перезапуска: курсор события хранит время события, и когда оно выйдет за ярус all политики хранения, продолжение с него — cursor_expired.

Подписка читает события из базы пачками (опция `batch`), но события, прочитанные в запас и ещё не отданные `next()`, курсор не учитывает. Время в курсоре нужно для проверки срока: продолжение с курсора старше яруса `all` политики хранения (срока, в течение которого журнал хранит все версии; не меньше суток) отклоняется с `cursor_expired`. При `from: 'now'` курсор — `null`, пока подписка не запомнила момент «сейчас» (`await sub.ready()` или первый `next()`).

**Примеры:** [Курсор подписки: подписка без событий не устаревает](../watch/#пример-курсор-подписки-без-событии-не-устаревает)

### sub.ready() {#subscription-ready}

```ts
ready(): Promise<void>
```

Начальная точка взята: у from: 'now' — горизонт и снимок момента подписки (watch_head()); у 'start' и курсора — сразу. Запись после await sub.ready() придёт в поток; ошибка начальной точки — отказ.

При `from: 'now'` подписка запоминает момент «сейчас» отдельным запросом к базе (`watch_head()`). Горизонт — граница, до которой все пишущие транзакции кластера уже завершены: с неё подписка начнёт читать журнал. Снимок — какие транзакции к этому моменту уже зафиксированы: их записи подписка не отдаёт. `db.watch()` этого запроса не ждёт, поэтому запись, сделанная сразу после `db.watch()`, может зафиксироваться раньше него и в поток не попасть.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки: подписка без событий не устаревает](../watch/#пример-курсор-подписки-без-событии-не-устаревает)

### sub.next() {#subscription-next}

```ts
next(): Promise<IteratorResult<WatchEvent>>
```

Следующее событие. Вызовы идут по очереди: параллельные next() получают разные события, без двойных. Вызов, брошенный по таймауту (Promise.race), всё равно получит своё событие — держите его обещание.

Пока событий нет, промис ждёт: подписку будит сигнал базы о записи в её классы, а без сигнала — запасной опрос раз в `pollMs`. «Держите обещание» значит: дождитесь промиса такого вызова, иначе его событие пропадёт — следующий `next()` отдаст уже следующее. Ошибка чтения журнала закрывает подписку: каждый следующий `next()` бросает её снова, и нужна новая подписка.

**Возвращает:** `Promise<IteratorResult<WatchEvent>>` — `{ value: событие, done: false }`, где событие — `{ cursor, row, id, class, op, rev, at }`; `{ value: undefined, done: true }` — подписка закрыта и событий, прочитанных в запас, не осталось.

**Ошибки** ([все коды](../errors/)):

- `cursor_expired` — курсор старше яруса `all` политики хранения классов подписки: события после него могли проредиться. Курсор подписки, догнавшей журнал, не стареет, а курсор события (`ev.cursor`) стареет вместе с событием. Перечитайте текущее состояние и подпишитесь заново с `'now'`.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### sub.lag() {#subscription-lag}

```ts
lag(): Promise<number>
```

Отставание, мс: сколько ждёт самое старое событие, которое уже зафиксировано, но ещё не ушло за горизонт (его держит более старая открытая транзакция); 0 — ждать нечего.

Это не отставание вашего обработчика: события, которые уже можно читать, но вы их ещё не забрали, сюда не входят. `lag()` показывает, насколько поток задерживает долгая пишущая транзакция в кластере PostgreSQL. Считается по классам подписки и по тому, что видит её сессия.

**Возвращает:** `Promise<number>` — Число миллисекунд.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору)

### sub.close() {#subscription-close}

```ts
close(): void
```

Останавливает подписку: она перестаёт слушать сигналы базы и опрашивать журнал, а ожидающий вызов `next()` сразу завершается. События, которые подписка уже прочла из базы в запас, `next()` ещё отдаст, а затем вернёт `{ done: true }`; новых запросов к базе не будет. Повторный вызов ничего не делает. Выход из цикла `for await` (`break`) закрывает подписку сам.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### sub.return() {#subscription-return}

```ts
return(): Promise<IteratorResult<WatchEvent>>
```

Служебный метод протокола асинхронного итератора: его вызывает сам цикл `for await`, когда из него выходят раньше конца (`break`, `return` или исключение). Закрывает подписку так же, как `close()`. Вызывать его самому не нужно: чтобы остановить подписку, есть `close()`.

**Возвращает:** `Promise<IteratorResult<WatchEvent>>` — `{ value: undefined, done: true }` — признак конца перебора.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору)

### for await (const ev of sub) {#subscription-asynciterator}

```ts
[Symbol.asyncIterator](): AsyncIterator<WatchEvent>
```

Служебный метод протокола асинхронного итератора: благодаря ему подписку перебирают циклом `for await (const ev of sub)`. Его вызывает сам цикл, вызывать его самому не нужно. Цикл берёт события методом `next()` и ждёт новых, пока подписку не закроют. Ошибку чтения журнала (например, `cursor_expired`) цикл бросает наружу, а выход из цикла (`break`) закрывает подписку.

**Возвращает:** `AsyncIterator<WatchEvent>` — Саму подписку: её метод `next()` отдаёт события циклу.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору)

## Кэш результатов

### db.cache {#db-cache}

```ts
readonly cache: { clear(): void; stats(): CacheStats }
```

Кэш результатов подключения.

Опции из таблицы ниже задают при подключении: `connect({ cache: { ttl, ttlOnly, max } })`, а `connect({ cache: false })` выключает кэш совсем. В кэш попадают только ответы цепочек с `.cache()` и цепочек, у которых все читаемые классы помечены `cache` в модели. Кэш лежит в памяти процесса и один на подключение: он общий для `db` и всех `db.as()`, а цепочки внутри `db.begin()` его не используют. В ключе ответа — запрос, сессия, аккаунт и арендатор, поэтому один пользователь не получит ответ другого. Записи этого подключения сбрасывают ответы изменённых классов сразу после фиксации, записи других процессов — по сигналу базы.

**Опции `CacheOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="cache-ttl"></span>`ttl` | `number` | `60` | Срок ответа по умолчанию, секунды (60). Действует для `.cache()` без `ttl` и для классов с пометкой `cache` без своего срока; `.cache({ ttl })` и `cache: { ttl }` у класса задают свой. Ответ сессии, срок которой истёк, из кэша не берётся.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="cache-ttlonly"></span>`ttlOnly` | `boolean` | `false` | Работать без слушателя сигналов — только по сроку (пул в режиме транзакций). Слушатель сигналов — соединение, которым подключение ждёт сигналы базы (`LISTEN`). Его нет при `connect({ listen: false })` (например, за PgBouncer в режиме транзакций) и в установке с `up({ signals: 'none' })`: тогда кэш выключен, а с `ttlOnly: true` работает. Записи других процессов такой ответ не сбрасывают: он живёт до конца срока. Записи этого подключения сбрасывают его, как обычно.<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |
| <span id="cache-max"></span>`max` | `number` | `10000` | Не больше ответов в памяти (10 000): старые вытесняются. Когда места нет, новый ответ вытесняет тот, что положен в кэш раньше всех, даже если его часто читают.<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |

**Примеры:** [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect)

### db.cache.clear() {#dbcache-clear}

```ts
clear(): void
```

Очищает кэш результатов подключения: все ответы удаляются, а запросы, которые выполняются в этот момент, своих ответов в кэш уже не положат. Кэш других процессов не меняется. Если кэш выключен (`connect({ cache: false })`), ничего не делает.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### db.cache.stats() {#dbcache-stats}

```ts
stats(): CacheStats
```

Возвращает счётчики кэша результатов подключения — для метрик и отладки.

**Возвращает:** `CacheStats` ([CacheStats](./types#type-cachestats)) — Объект `{ size, hits, misses, stores, raced, signals, listens, enabled }`: `size` — ответов в памяти сейчас; `hits` — ответов, взятых из кэша; `misses` — запросов, которые искали ответ в кэше и не нашли (его нет или срок вышел); `stores` — сколько ответов положено в кэш; `raced` — сколько ответов не положено, потому что за время запроса их классы или сессию сбросили (сигнал базы, своя запись или `clear()`); `signals` — получено сигналов базы; `listens` — подключений и переподключений слушателя сигналов; `enabled` — кэш работает: слушатель сигналов на месте или включён `ttlOnly`. У подключения с `cache: false` — нули и `enabled: false`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)
