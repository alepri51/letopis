# Подписка и кэш

Подписка читает журнал изменений по курсору и будит ожидание по сигналам базы. Кэш результатов хранит ответы цепочек в памяти процесса.

**Что здесь:** [Подписка](#подписка) · [Кэш результатов](#кэш-результатов). У каждого пункта — сигнатура с типами, что делает, параметры и опции (тип, значение по умолчанию), что возвращает, коды ошибок и переходы к живым примерам сайта.

## Подписка

### me.watch() {#db-watch}

```ts
watch(opts?: WatchOptions): Subscription
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Подписка по курсору: `for await (const ev of me.watch({ from })) …`; `sub.cursor` — откуда продолжить.

Каждое событие — одна версия объекта из журнала: `ev.row` — сама версия (у удаления — надгробие с `$deleted`), `ev.id`, `ev.class`, `ev.op` — вид операции, `ev.rev` — номер версии, `ev.at` — время версии, `ev.cursor` — курсор события. Обработав событие, сохраняйте курсор подписки `sub.cursor`: `me.watch({ from: cursor })` продолжит сразу после этого события, без потерь и повторов. События идут в порядке номеров транзакций, а внутри транзакции — в порядке записи. Это не порядок фиксации, поэтому версии одного объекта сверяйте по `rev`. Подписка видит только то, что разрешено её сессии: права и квартиру проверяет база. Долгая пишущая транзакция в любой базе того же кластера PostgreSQL задерживает поток: события транзакций, начавших запись позже неё, ждут её конца. Насколько поток задержан, показывает `sub.lag()`. Остановить подписку — `break` в цикле или `sub.close()`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `WatchOptions` | `{}` | Опции подписки — таблица ниже. |

**Опции `WatchOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="watch-from"></span>`from` | `string` | `'now'` | Откуда: курсор (sub.cursor или курсор события), 'now' (по умолчанию — изменения после подписки) или 'start' (весь журнал). С курсором подписка начнёт сразу после него. С `'now'` момент подписки запоминает отдельный запрос к базе: чтобы запись, сделанная сразу после `me.watch()`, попала в поток, сначала дождитесь `await sub.ready()`.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает) · [Живой экран: подписка, снимок и переподключение по курсору](../watch/#рецепт-живои-экран) |
| <span id="watch-classes"></span>`classes` | `string[]` | все классы | Только эти классы (с потомками). Потомков подписка берёт из реестра классов корня в момент вызова `me.watch()`: класс, описанный позже, в неё не попадёт. Класс строки неизменен, поэтому строка не уходит из классов подписки и не приходит в них.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) |
| <span id="watch-batch"></span>`batch` | `number` | `500` | Событий за запрос (по умолчанию 500).<br>Примеры: [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы) |
| <span id="watch-pollms"></span>`pollMs` | `number` | `1000` | Как часто подписка сама проверяет журнал, мс (по умолчанию 1000): так она находит события, даже если сигнал базы не пришёл. Без сигналов (`connect(pass, { listen: false })` или дом с `setup({ signals: 'none' })`) новые события она узнаёт только так.<br>Примеры: [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы) |

**Возвращает:** `Subscription` ([Subscription](./types-watch#type-subscription)) — Подписку: события из неё берут циклом `for await (const ev of sub)` или вызовом `await sub.next()`. `me.watch()` возвращается сразу, не дожидаясь базы; события подписка читает при первом `next()`.

**Ошибки** ([все коды](../errors/)):

- `invalid_class` — класса из `classes` нет в реестре классов корня.
- `invalid_query` — `from` — не `'now'`, не `'start'` и не курсор.
- `invalid_data` — неизвестная опция — с похожими именами в `err.params.similar`.

### sub.cursor {#subscription-cursor}

```ts
readonly cursor: string | null
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Курсор подписки: позиция после последнего выданного события (или начальная точка) — с неё продолжают после перезапуска.

Подписка читает события из базы пачками (опция `batch`), но события, прочитанные в запас и ещё не отданные `next()`, курсор не учитывает. Курсор не устаревает: журнал хранит каждую версию, поэтому продолжить можно с любого сохранённого курсора, сколько бы времени ни прошло. При `from: 'now'` курсор — `null`, пока подписка не запомнила момент «сейчас» (`await sub.ready()` или первый `next()`).

**Примеры:** [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает)

### sub.ready() {#subscription-ready}

```ts
ready(): Promise<void>
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Промис выполняется, когда подписка запомнила начальную точку: запись, сделанная после этого, придёт в поток. У `from: 'now'` точку запоминает отдельный запрос к базе, у `'start'` и курсора промис выполняется сразу; если запрос не удался, промис отклоняется с его ошибкой.

Момент «сейчас» — это граница, до которой все пишущие транзакции кластера уже завершены (с неё подписка начнёт читать журнал), и список транзакций, зафиксированных к этому моменту (их записи подписка не отдаёт). `me.watch()` этого запроса не ждёт, поэтому запись, сделанная сразу после `me.watch()`, может зафиксироваться раньше него и в поток не попасть.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает) · [Живой экран: подписка, снимок и переподключение по курсору](../watch/#рецепт-живои-экран)

### sub.next() {#subscription-next}

```ts
next(): Promise<IteratorResult<WatchEvent>>
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Следующее событие. Вызовы идут по очереди: параллельные next() получают разные события, без двойных. Вызов, брошенный по таймауту (Promise.race), всё равно получит своё событие — держите его обещание.

Пока событий нет, промис ждёт: подписку будит сигнал базы о записи в её классы, а без сигнала она сама проверяет журнал раз в `pollMs`. «Держите обещание» значит: дождитесь промиса такого вызова, иначе его событие пропадёт — следующий `next()` отдаст уже следующее. Ошибка чтения журнала закрывает подписку: каждый следующий `next()` бросает её снова, и нужна новая подписка.

**Возвращает:** `Promise<IteratorResult<WatchEvent>>` — `{ value: событие, done: false }`, где событие — `{ cursor, row, id, class, op, rev, at }`; `{ value: undefined, done: true }` — подписка закрыта и событий, прочитанных в запас, не осталось.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает) · [Живой экран: подписка, снимок и переподключение по курсору](../watch/#рецепт-живои-экран) · [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы)

### sub.lag() {#subscription-lag}

```ts
lag(): Promise<number>
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Отставание, мс: сколько ждёт самое старое событие, которое уже зафиксировано, но ещё не ушло за горизонт (его держит более старая открытая транзакция); 0 — ждать нечего.

Это не отставание вашего обработчика: события, которые уже можно читать, но вы их ещё не забрали, сюда не входят. `lag()` показывает, насколько поток задерживает долгая пишущая транзакция в кластере PostgreSQL. Считается по классам подписки и по тому, что видит её сессия.

**Возвращает:** `Promise<number>` — Число миллисекунд.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает) · [Живой экран: подписка, снимок и переподключение по курсору](../watch/#рецепт-живои-экран)

### sub.close() {#subscription-close}

```ts
close(): void
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Останавливает подписку: она перестаёт слушать сигналы базы и опрашивать журнал, а ожидающий вызов `next()` сразу завершается. События, которые подписка уже прочла из базы в запас, `next()` ещё отдаст, а затем вернёт `{ done: true }`; новых запросов к базе не будет. Повторный вызов ничего не делает. Выход из цикла `for await` (`break`) закрывает подписку сам.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Курсор подписки не устаревает](../watch/#пример-курсор-подписки-не-устаревает) · [Живой экран: подписка, снимок и переподключение по курсору](../watch/#рецепт-живои-экран) · [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы)

### for await (const ev of sub) {#subscription-asynciterator}

```ts
[Symbol.asyncIterator](): AsyncIterator<WatchEvent>
```

**Откуда:** `sub` — из `me.watch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

**Возвращает:** `AsyncIterator<WatchEvent>` — Саму подписку: её метод `next()` отдаёт события циклу.

**Ошибки:** собственных кодов нет.

## Кэш результатов

### me.cache {#db-cache}

```ts
readonly cache: { clear(): void; stats(): CacheStats }
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Кэш результатов подключения.

Опции из таблицы ниже задают при подключении консьержа: `connect(pass, { cache: { ttl, ttlOnly, max } })`, а `connect(pass, { cache: false })` выключает кэш совсем. В кэш попадают только ответы цепочек с `.cache()` и цепочек, у которых все читаемые классы помечены `cache` в модели. Кэш лежит в памяти процесса и один на консьержа: он общий для всех корней квартир, а цепочки внутри `me.begin()` его не используют. В ключе ответа — запрос, сессия, аккаунт и квартира, поэтому один жилец не получит ответ другого. Записи через корни этого консьержа — цепочками, батчем, в `me.begin()` и `me.transaction()` — сбрасывают ответы изменённых классов (с классами каскада) сразу после фиксации, а запись через `me.sql` — весь кэш. Загрузка `letopis load` и записи других процессов сбрасывают кэш сигналом базы.

**Опции `CacheOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="cache-ttl"></span>`ttl` | `number` | `60` | Срок ответа по умолчанию, секунды (60). Действует для `.cache()` без `ttl` и для классов с пометкой `cache` без своего срока; `.cache({ ttl })` и `cache: { ttl }` у класса задают свой. Ответ сессии, срок которой истёк, из кэша не берётся.<br>Примеры: [Опции connect(pass): наблюдение за запросами, пул, сигналы, кэш](../install/#опции-connect) |
| <span id="cache-ttlonly"></span>`ttlOnly` | `boolean` | `false` | Включает кэш, даже когда подключение не слушает сигналы базы: `connect(pass, { listen: false })` (например, за PgBouncer в режиме транзакций) или дом с `setup({ signals: 'none' })`; без опции кэш тогда выключен. Такой ответ живёт до конца срока: записи других процессов его не сбрасывают, записи этого подключения — сбрасывают. Если консьерж сигналы слушает, опция ничего не меняет: сигналы базы сбрасывают кэш и с ней. Без сигналов ответ не узнаёт о записях других процессов и загрузке `letopis load`: он доживает свой срок или до `me.cache.clear()`.<br>Примеры: [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы) |
| <span id="cache-max"></span>`max` | `number` | `10000` | Не больше ответов в памяти (10 000): старые вытесняются. Когда места нет, новый ответ вытесняет тот, что положен в кэш раньше всех, даже если его часто читают.<br>Примеры: [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы) |

**Примеры:** [Опции connect(pass): наблюдение за запросами, пул, сигналы, кэш](../install/#опции-connect) · [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы)

### me.cache.clear() {#dbcache-clear}

```ts
clear(): void
```

### me.cache.stats() {#dbcache-stats}

```ts
stats(): CacheStats
```

**Откуда:** `me.cache`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Возвращает счётчики кэша результатов консьержа — для метрик и отладки.

**Возвращает:** `CacheStats` ([CacheStats](./types-watch#type-cachestats)) — Объект `{ size, hits, misses, stores, raced, signals, listens, enabled }`: `size` — ответов в памяти сейчас; `hits` — ответов, взятых из кэша; `misses` — запросов, которые искали ответ в кэше и не нашли (его нет или срок вышел); `stores` — сколько ответов положено в кэш; `raced` — сколько ответов не положено, потому что за время запроса их классы или сессию сбросили (сигнал базы, своя запись или `clear()`); `signals` — получено сигналов базы; `listens` — подключений и переподключений слушателя сигналов; `enabled` — кэш работает: слушатель сигналов на месте или включён `ttlOnly`. У консьержа с `cache: false` — нули и `enabled: false`.

**Ошибки:** собственных кодов нет.
