# Подписка и кэш

Подписка читает журнал изменений по курсору и будит ожидание по сигналам базы. Кэш результатов хранит ответы цепочек в памяти процесса.

## Подписка

### db.watch() {#db-watch}

```ts
watch(opts?: WatchOptions): Subscription
```

Подписка по курсору: for await (const ev of db.watch({ from })) …; ev.cursor — откуда продолжить.

Каждое событие — одна версия объекта из журнала: `ev.row` (у удаления — надгробие с `$deleted`), `ev.id`, `ev.class`, `ev.op`, `ev.rev`, `ev.at` и курсор `ev.cursor`. Сохраняйте курсор последнего обработанного события: `db.watch({ from: cursor })` продолжит сразу после него, без потерь и повторов. События идут в порядке номеров транзакций, а внутри транзакции — в порядке записи. Это не порядок фиксации, поэтому версии одного объекта сверяйте по `rev`. Служебные записи журнала тоже приходят событиями: `purge` и `trim` — в классе объекта, а запись сброса арендатора (`op` — `reset`, класс `#reset`) — только подписке без `classes`. Подписка видит только то, что разрешено сессии подключения: права и арендатора проверяет база. Долгая пишущая транзакция в любой базе того же кластера PostgreSQL задерживает поток: события транзакций, начавших запись позже неё, ждут её конца. Насколько поток задержан, показывает `sub.lag()`. Остановить подписку — `break` в цикле или `sub.close()`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `WatchOptions` | `{}` | Опции подписки — таблица ниже. |

**Опции `WatchOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="watch-from"></span>`from` | `string` | `'now'` | Откуда: курсор события, 'now' (по умолчанию — изменения после подписки) или 'start' (весь журнал). Курсор — значение `ev.cursor` из события: подписка продолжит сразу после него. С `'now'` момент подписки берётся первым запросом к базе: если запись сразу после `db.watch()` должна попасть в поток, дождитесь `await sub.ready()`.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) |
| <span id="watch-classes"></span>`classes` | `string[]` | все классы | Только эти классы (с потомками). Потомков подписка берёт из реестра классов подключения в момент вызова `db.watch()`: класс, описанный позже, в неё не попадёт. Строка, ушедшая из этих классов сменой класса без смены id, приходит событием удаления в прежнем классе (`op: 'delete'`, `row` — прежняя версия с `$deleted`), если прежнюю версию подписчик видел.<br>Примеры: [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) |
| <span id="watch-batch"></span>`batch` | `number` | `500` | Событий за запрос (по умолчанию 500).<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |
| <span id="watch-pollms"></span>`pollMs` | `number` | `1000` | Запасной опрос, мс (по умолчанию 1000; без LISTEN — единственный способ узнать о событиях).<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |

**Возвращает:** `Subscription` ([Subscription](./types#type-subscription)) — подписку: события из неё берут циклом `for await (const ev of sub)` или вызовом `await sub.next()`. Вызов возвращается сразу, не дожидаясь базы, а события подписка читает при первом `next()`.

**Ошибки** ([все коды](../errors/)):

- `invalid_class` — класса из `classes` нет в реестре классов подключения.
- `invalid_query` — `from` — не `'now'`, не `'start'` и не курсор события.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору)

### sub.cursor {#subscription-cursor}

```ts
readonly cursor: string | null
```

Курсор последнего выданного события (или начальной точки).

Курсор сдвигается, когда подписка читает события из базы, а читает она пачками (опция `batch`). Поэтому `sub.cursor` может опережать события, которые вы уже получили: он указывает на последнее событие, прочитанное в запас. Чтобы продолжить без потерь, сохраняйте `ev.cursor` последнего обработанного события. До первого события `sub.cursor` — начальная точка подписки, а при `from: 'now'` — `null`, пока подписка не запомнила момент «сейчас» (`await sub.ready()` или первый `next()`).

**Примеры:** живого примера пока нет.

### sub.ready() {#subscription-ready}

```ts
ready(): Promise<void>
```

Начальная точка взята: у from: 'now' — горизонт и снимок момента подписки (watch_head()); у 'start' и курсора — сразу. Запись после await sub.ready() придёт в поток; ошибка начальной точки — отказ.

Нужен только при `from: 'now'`. `db.watch()` возвращается сразу, а момент «сейчас» подписка запоминает отдельным запросом к базе. Запись, сделанная сразу после `db.watch()`, может зафиксироваться раньше этого запроса и в поток не попасть. Когда `await sub.ready()` выполнился, момент запомнен: всё, что зафиксировано позже, подписка отдаст. Если запрос к базе не удался, промис отклоняется с его ошибкой.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** живого примера пока нет.

### sub.next() {#subscription-next}

```ts
next(): Promise<IteratorResult<WatchEvent>>
```

Следующее событие. Вызовы идут по очереди: параллельные next() получают разные события, без двойных. Вызов, брошенный по таймауту (Promise.race), всё равно получит своё событие — держите его обещание.

Пока событий нет, промис ждёт: подписку будит сигнал базы о записи в её классы, а без сигнала — запасной опрос раз в `pollMs`. «Держите обещание» — не теряйте промис вызова, брошенного по таймауту: событие достанется ему, а следующий `next()` получит уже следующее. Ошибка чтения журнала закрывает подписку: каждый следующий `next()` бросает её снова, и нужна новая подписка.

**Возвращает:** `Promise<IteratorResult<WatchEvent>>` — `{ value: событие, done: false }`, где событие — `{ cursor, row, id, class, op, rev, at }`; `{ value: undefined, done: true }` — подписка закрыта и событий, прочитанных в запас, не осталось.

**Ошибки** ([все коды](../errors/)):

- `cursor_expired` — курсор старше яруса `all` политики хранения классов подписки: события после него могли проредиться. Возраст курсора считается по времени события, на котором он стоит. Перечитайте текущее состояние и подпишитесь заново с `'now'`.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### sub.lag() {#subscription-lag}

```ts
lag(): Promise<number>
```

Отставание, мс: сколько ждёт самое старое событие, которое уже зафиксировано, но ещё не ушло за горизонт (его держит более старая открытая транзакция); 0 — ждать нечего.

Это не отставание вашего обработчика: события, которые уже можно читать, но вы их ещё не забрали, сюда не входят. `lag()` показывает, насколько поток задерживает долгая пишущая транзакция в кластере PostgreSQL. Считается по классам подписки и по тому, что видит её сессия.

**Возвращает:** `Promise<number>` — отставание в миллисекундах; `0` — задержанных событий нет.

**Ошибки:** собственных кодов нет.

**Примеры:** живого примера пока нет.

### sub.close() {#subscription-close}

```ts
close(): void
```

Останавливает подписку: отписывает её от сигналов базы и запасного опроса и будит ожидающий `next()`. События, которые подписка уже прочла из базы в запас, `next()` ещё отдаст, а затем вернёт `{ done: true }`; новых запросов к базе не будет. Повторный вызов ничего не делает. Выход из цикла `for await` (`break`) закрывает подписку сам.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** [Подписка на изменения: по курсору, без потерь и повторов](../watch/#пример-подписка-по-курсору) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### sub.return() {#subscription-return}

```ts
return(): Promise<IteratorResult<WatchEvent>>
```

Служебный метод протокола асинхронного итератора: его вызывает сам цикл `for await`, когда из него выходят раньше конца (`break`, `return` или исключение). Закрывает подписку так же, как `close()`. Вызывать его самому не нужно: чтобы остановить подписку, есть `close()`.

**Возвращает:** `Promise<IteratorResult<WatchEvent>>` — `{ value: undefined, done: true }` — признак конца перебора.

**Ошибки:** собственных кодов нет.

**Примеры:** живого примера пока нет.

### for await (const ev of sub) {#subscription-asynciterator}

```ts
[Symbol.asyncIterator](): AsyncIterator<WatchEvent>
```

Служебный метод протокола: благодаря ему подписку перебирают циклом `for await (const ev of sub)`. Его вызывает сам цикл, вызывать его самому не нужно. Цикл берёт события методом `next()` и ждёт новых, пока подписку не закроют. Ошибку чтения журнала (например, `cursor_expired`) цикл бросает наружу, а выход из цикла (`break`) закрывает подписку.

**Возвращает:** `AsyncIterator<WatchEvent>` — саму подписку: её метод `next()` отдаёт события циклу.

**Ошибки:** собственных кодов нет.

**Примеры:** живого примера пока нет.

## Кэш результатов

### db.cache {#db-cache}

```ts
readonly cache: { clear(): void; stats(): CacheStats }
```

Кэш результатов подключения.

Опции из таблицы ниже задают при подключении: `connect({ cache: { ttl, ttlOnly, max } })`; `connect({ cache: false })` выключает кэш совсем. Какие ответы кэшировать, решает цепочка (`.cache()`, `.cache({ ttl })`) или пометка класса `cache: { ttl }` в модели: без них ответы в кэш не попадают. Кэш лежит в памяти процесса и общий для `db`, `db.as()` и `db.begin()` одного подключения. В ключе ответа — запрос, сессия, актор и арендатор, поэтому один пользователь не получит ответ другого. Свои записи сбрасывают ответы изменённых классов сразу после фиксации, чужие — по сигналу базы. Внутри `db.begin()` кэш не работает.

**Опции `CacheOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="cache-ttl"></span>`ttl` | `number` | `60` | Срок ответа по умолчанию, секунды (60). Действует для `.cache()` без `ttl` и для классов с пометкой `cache` без своего срока; `.cache({ ttl })` и `cache: { ttl }` у класса задают свой. Ответ сессии, срок которой истёк, из кэша не берётся.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="cache-ttlonly"></span>`ttlOnly` | `boolean` | `false` | Работать без слушателя сигналов — только по сроку (пул в режиме транзакций). Без слушателя сигналов (`connect({ listen: false })` — например, за PgBouncer в режиме транзакций — или режим сигналов `none`) кэш выключен, а с `ttlOnly: true` работает и тогда. Без слушателя записи других процессов ответ не сбрасывают: он живёт до конца срока. Свои записи подключения сбрасывают его, как обычно.<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |
| <span id="cache-max"></span>`max` | `number` | `10000` | Не больше ответов в памяти (10 000): старые вытесняются. Когда ответов больше, удаляется ответ, положенный в кэш раньше остальных.<br>Примеры: [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы) |

**Примеры:** [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect)

### db.cache.clear() {#dbcache-clear}

```ts
clear(): void
```

Очищает кэш результатов подключения: все ответы удаляются, а запросы, которые выполняются в этот момент, своих ответов в кэш уже не положат. Кэш других процессов не меняется. Если кэш выключен (`connect({ cache: false })`), ничего не делает.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** живого примера пока нет.

### db.cache.stats() {#dbcache-stats}

```ts
stats(): CacheStats
```

Возвращает счётчики кэша результатов подключения — для наблюдения: сколько ответов в памяти, сколько раз ответ взят из кэша и работает ли кэш.

**Возвращает:** `CacheStats` ([CacheStats](./types#type-cachestats)) — объект `{ size, hits, misses, stores, raced, signals, listens, enabled }`: `size` — ответов в памяти сейчас; `hits` — ответов, взятых из кэша; `misses` — запросов, которые искали ответ в кэше и не нашли (его нет или срок вышел); `stores` — сколько ответов положено в кэш; `raced` — сколько не положено, потому что во время запроса пришёл сигнал о его классах или сессии; `signals` — получено сигналов базы; `listens` — подключений и переподключений слушателя сигналов; `enabled` — кэш работает: слушатель сигналов на месте или включён `ttlOnly`. У подключения с `cache: false` — нули и `enabled: false`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) · [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)
