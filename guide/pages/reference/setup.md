# Установка и подключение

`up()` ставит или обновляет схему, `connect()` открывает подключение, `createTenant()` заводит арендатора с первым пользователем.

## Функции

### up() {#export-up}

```ts
up(opts: UpOptions): Promise<UpResult>
```

Поставить или обновить установку letopis. Схема есть и её ревизия совпадает — повторный накат (идемпотентный); ревизия отстала — только с upgrade: true; новее библиотеки — отказ.

Если задан `dsn`, `up()` сначала ждёт ответа сервера и создаёт базу, когда её нет. Затем проверяет, что сервер — PostgreSQL 18 или новее, а база — в кодировке UTF8. Создаёт роли владельца и приложения и расширение pgcrypto. Создаёт схему `v2.<имя>` и одной транзакцией ставит в неё таблицы, функции, проверки, политики доступа, системные классы и сиды. Если в установке нет ни одного ключа API, кроме отозванных, выпускает ключ сервиса. Сервис — служебный аккаунт: с его ключом приложение подключается (`connect({ apiKey })`), проверяет пароли и действует от имени пользователей. Собирает статистику PostgreSQL для таблиц, у которых её ещё нет. Повторный вызов на схеме той же ревизии (повторный накат) заново ставит функции и не трогает данные, поэтому `up()` можно вызывать при каждом запуске приложения. Вызывают его от администратора базы.

На PostgreSQL ниже 18.2 `up()` предупреждает: такой сервер мог удалить служебные данные, которые ещё нужны непрочитанным сигналам, — его лучше обновить.

Отказы `up()` — обычные ошибки `Error` с текстом `letopis.up: …`, без кода: нет ни `dsn`, ни `sql`, ни `pglite`; не установлены пакеты PGlite; неверное имя схемы или роли; сервер ниже PostgreSQL 18 или база не в UTF8; сервер не ответил за `waitTimeoutMs`; ревизия схемы новее пакета или старше пакета без `upgrade: true`; неверные `serviceKey`, `signals`, `history` или имя сида; ошибка в файле SQL (текст называет файл). Ошибки подключения, например неверный пароль, приходят от PostgreSQL как есть.

Если самая первая установка схемы оборвалась ошибкой (например, в своём сиде), в базе остаётся пустая схема без ревизии. Повторный `up()` принимает её за схему старой ревизии и без `upgrade: true` отказывает. Схема пустая, поэтому её можно поставить заново: `up({ schema, fresh: true })`.

Без опции случайный ключ выпускается, только когда в установке нет ни одного ключа API, кроме отозванных: при первой установке или после отзыва всех ключей.<br>Примеры: [Опции up(): сиды, режим сигналов, свой ключ, история, обновление, установка заново](../install/#опции-up) |

Режим хранится в схеме: накат без опции его не меняет, reset({ all }) — сохраняет. Сигналы — короткие уведомления базы (`NOTIFY`), по которым процессы приложения будят подписки и сбрасывают кэш. Их может читать любая роль, которая подключается к базе, поэтому режим решает, что в них видно. Токен — псевдоним вместо имени класса или id арендатора: раскрыть его может только процесс с ключом сигналов, а ключ выдают сервисам с правом `letopis.signals`. Узнав арендатора записи, такой процесс сбрасывает кэш только в нём. В режиме `'none'` подписки опрашивают журнал, а кэш результатов выключен или работает только по сроку. После смены режима перезапустите процессы приложения: режим читается при подключении. Неизвестное значение — ошибка `up()`.<br>Примеры: [Опции up(): сиды, режим сигналов, свой ключ, история, обновление, установка заново](../install/#опции-up) |

**Возвращает:** `Promise<UpResult>` ([UpResult](./types#type-upresult)) — Итог установки: полное имя схемы (`schema`); поставлена ли она впервые или обновлена со старой ревизии (`created`, `upgraded`); ревизия движка (`revision`); новый ключ сервиса (`serviceKey`, если ключ не выпускался — `null`); применённые миграции (`migrations`); таблицы, для которых собрана статистика (`analyzed`); имена ролей (`owner`, `app`); режим сигналов (`signals`); предупреждения (`warnings`). С опцией `tenant` — ещё арендатор с сессией пользователя (`tenant`), с опцией `pglite` — запущенный PGlite (`pglite`).

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — опция `tenant` не прошла проверку, как у `createTenant()`: неверные `user.roles` или `user.kind` (это проверяется ещё до подключения к базе) либо удалены арендатор, аккаунт пользователя или членство (тогда схема к этому моменту уже поставлена).

### connect() {#export-connect}

```ts
connect<const M extends readonly AnyModelLike[]>(opts: ConnectOptions & { models: M }): Promise<TypedDb<M>>
connect(opts: ConnectOptions): Promise<Db>
```

Открывает подключение к установке letopis и возвращает объект `db`, с которого начинаются цепочки: `db.Класс(фильтр)`. Сначала `connect()` проверяет роль подключения: роль, которая обходит RLS, он пускает только с опцией `allowBypassRls`. Затем получает сессию — по токену `token` или в обмен на ключ API `apiKey`, загружает описания классов арендатора сессии и System и начинает слушать сигналы базы (если не задан `listen: false` и сигналы в установке не выключены).

О трёх случаях `connect()` только предупреждает в консоли, а не отказывает: подключение администраторское; ревизия схемы старше пакета (он называет команду `up({ schema, upgrade: true })`); схему той же ревизии ставила другая версия пакета — не совпал штамп движка (он называет, что обновить: схему или пакет). Пул, который `connect()` создал по `dsn`, закрывает `db.close()`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `ConnectOptions` | обязательный | Опции подключения — таблица `ConnectOptions` ниже. Обязательны `schema` и одно из `dsn` или `sql`; сессию даёт `token` или `apiKey`. |

**Опции `ConnectOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="connect-dsn"></span>`dsn` | `string` | нет — нужен `dsn` или `sql` | Строка подключения; либо готовый пул postgres.js в `sql`. По строке `connect()` создаёт свой пул на `max` соединений и закрывает его в `db.close()`. В строке — роль приложения, то есть член `letopis_app`; роль, которая обходит RLS, `connect()` пускает только с `allowBypassRls`.<br>Примеры: [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход) |

| <span id="connect-schema"></span>`schema` | `string` | обязательная | Схема установки, например `v2.salon`. Только полное имя с версией: короткое имя, которое понимает `up()`, здесь не подходит (`invalid_data`). Удобно брать `r.schema` из результата `up()`.<br>Примеры: [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход) |
| <span id="connect-token"></span>`token` | `string` | нет | Токен сессии; либо ключ APIKEY в `apiKey` (он же `service` — ключ сервиса) — его обменяют на сессию. Если заданы и `token`, и `apiKey`, используется `token`. Токен при подключении не проверяется: с неверным или истёкшим токеном `connect()` всё равно вернёт подключение, но без сессии — `db.tenant` равен `null`, а роль приложения не увидит ни классов, ни строк. Без `token` и `apiKey` подключение тоже работает без сессии; так имеет смысл только администраторское подключение, например для `verify()` и `maintain()`.<br>Примеры: [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход) |
| <span id="connect-apikey"></span>`apiKey` | `string` | нет | Ключ API вида `lts_…` — например, ключ сервиса `r.serviceKey` из `up()` или ключ, выпущенный `db.auth.issueApiKey()`. `connect()` сразу обменивает его на новую сессию аккаунта этого ключа сроком 7 дней.<br>Примеры: [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход) |
| <span id="connect-service"></span>`service` | `string` | нет | То же, что `apiKey`: ключ API, который `connect()` обменивает на сессию. Если заданы оба, берётся `apiKey`.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-refreshsession"></span>`refreshSession` | `boolean` | `true` | Продлевать сессию раз в минуту работы (по умолчанию да). После успешного запроса, если с прошлого продления прошла минута, подключение отдельным запросом продлевает сессию — снова на срок, выданный при входе, но не больше 7 дней. Ошибка продления (например, база только для чтения) работе не мешает. С `false` сессия истечёт в свой срок.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-allowbypassrls"></span>`allowBypassRls` | `boolean` | `false` | Разрешить роль, которая обходит RLS (суперпользователь, BYPASSRLS, член роли-владельца), — администраторское подключение. Без опции такую роль `connect()` отклоняет (`bypass_rls`), с опцией — пускает и печатает предупреждение: права и изоляция арендаторов на таком подключении не действуют. Загрузчику, проекторам и ремонту агрегатов (`db.rebuildAggregates()`) нужна роль, которая может стать владельцем схемы: суперпользователь или член роли-владельца с правом `SET`. Держите такое подключение в отдельном процессе, а не в веб-приложении.<br>Примеры: [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход) |
| <span id="connect-owner"></span>`owner` | `string` | `'letopis_owner'` | Имя роли-владельца (по умолчанию letopis_owner). Нужна, только если установку поставили с другим именем роли (`up({ owner })`). По членству в этой роли `connect()` узнаёт администраторское подключение; от неё работают загрузчик, проекторы и ремонт агрегатов. Если роли с таким именем нет, `connect()` падает с ошибкой PostgreSQL.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-notifyintervalms"></span>`notifyIntervalMs` | `number` | `100` | Интервал отправки отложенного сигнала, мс (по умолчанию 100). Записи через библиотеку (цепочки, `db.sql`, `db.transaction()`) не шлют сигнал сразу: подключение копит сигналы своих транзакций и отправляет их пачкой раз в этот интервал, а неотправленные из-за ошибки повторяет. Чем больше интервал, тем дольше другие процессы видят устаревший кэш и тем позже просыпаются их подписки. Отправить сразу — `db.flushSignals()`.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-max"></span>`max` | `number` | `10` | Размер пула, если подключение создаёт сам connect(). С опцией `sql` не действует: размер своего пула задают при его создании.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-onquery"></span>`onQuery` | `(e: QueryEvent) => void` | нет | Хук на каждый запрос цепочки (метрики, лог). Хук получает событие `{ mode, classes, ms, rows, slow }`: вид запроса (`rows`, `ids`, `count`, `paths`, `versions`, `agg`, `diff`, `blame`), классы шагов, длительность в миллисекундах, число строк ответа и признак медленного запроса (дольше `slowMs`). Хук вызывается после каждого терминала цепочки, который обратился к базе, в том числе после записи. Ответы из кэша, `db.sql` и методы `db.auth` событий не дают. Вызов синхронный: исключение из хука получит код, который вызвал терминал.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-slowms"></span>`slowMs` | `number` | нет: запросы не отмечаются медленными | Порог медленного запроса, мс: событие получает slow; без onQuery — console.warn. Признак — поле `slow: true` в событии хука `onQuery`. Предупреждение в консоли называет длительность, вид и классы запроса.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-models"></span>`models` | `readonly AnyModelLike[]` | нет: `db` без типов моделей | Модели letopis/model — только для типов цепочек (TypedDb); описания классов берутся из базы. Чтобы классы появились в базе, модели записывают `syncModels()`.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-listen"></span>`listen` | `boolean` | `true` | Слушать сигналы базы (LISTEN, по умолчанию да). false — пул в режиме транзакций (PgBouncer): реестр перечитывается через db.refresh(), подписка опрашивает журнал, кэш результатов выключен (с cache: { ttlOnly: true } — работает только по сроку). В установке с up({ signals: 'none' }) слушателя нет всегда, а реестр раз в 5 с сверяет отпечаток классов. В режиме транзакций PgBouncer после каждой транзакции отдаёт соединение другому клиенту, поэтому `LISTEN` там не работает. Если сигналы в установке есть, с `false` реестр классов сам не обновляется: новые и изменённые классы подключение увидит после `db.refresh()`. Подписка `watch()` тогда опрашивает журнал раз в `pollMs` (по умолчанию раз в секунду).<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-cache"></span>`cache` | `CacheOptions \| false` | включён: срок 60 с, до 10 000 ответов | Кэш результатов: срок по умолчанию, размер, ttlOnly; false — выключен. Кэш хранит ответы только тех цепочек, где вызван `.cache()`, и чтения классов с `cache` в модели. Поля: `ttl` — срок ответа по умолчанию в секундах (60); `max` — сколько ответов держать в памяти (10 000, при переполнении вытесняются самые старые); `ttlOnly` — работать без сигналов базы, только по сроку. Без слушателя сигналов (`listen: false` или режим сигналов `none`) кэш работает только с `ttlOnly`, иначе он выключен. С `false` вызов `.cache()` в цепочках ничего не делает.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |
| <span id="connect-maintain"></span>`maintain` | `string \| number` | нет: по расписанию не запускается | Запускать maintain() по расписанию ('1h', '15m', мс) под блокировкой обслуживания: работает один процесс. Интервал — от 1 мс до 2³¹−1 мс (около 24 суток), иначе connect() отказывает invalid_data, не открывая соединений; close() ждёт идущий запуск (он доделывает текущую пачку). Интервал — число миллисекунд или строка с единицей: `'500ms'`, `'30s'`, `'15m'`, `'1h'`, `'1d'`; другой формат — тоже `invalid_data`. Предел нужен потому, что интервал вне его таймер Node.js превратил бы в 1 мс, и обслуживание шло бы без перерыва. Первый запуск — через один интервал, а не сразу; пока прошлый запуск не закончился, следующий пропускается. Обслуживание идёт в одном процессе: запуск, который застал его в другом, ничего не делает. Ошибки (например, у подключения нет права на обслуживание) печатаются предупреждением в консоль. Запускать `maintain()` может системный администратор, аккаунт с правом `letopis.maintain` или администраторское подключение. После `db.close()` новые запуски и пачки не начинаются.<br>Примеры: [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect) |

**Возвращает:** `Promise<Db>` ([Db](./types#type-db)) — Подключение `db`; его служебные методы и свойства — на странице [Корень db](./db). С опцией `models` — то же подключение, но с типами шагов, строк и фильтров по моделям.

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — имя схемы не полное (нужно `v<N>.<имя>`); не задан ни `dsn`, ни `sql`; схемы с таким именем в базе нет (при входе по `apiKey` об этом раньше сообщит ошибка PostgreSQL); у `maintain` неверный интервал.
- `bypass_rls` — роль подключения обходит RLS (суперпользователь, `BYPASSRLS` или член роли-владельца), а `allowBypassRls` не задан.
- `no_session` — ключ из `apiKey` (или `service`) неверен, отозван, отключён или истёк либо отключён аккаунт ключа.
- `tenant_denied` — сессия работает в чужом арендаторе, а членства в нём больше нет или арендатор отключён.

### createTenant() {#export-createtenant}

```ts
createTenant(
  sql: postgres.Sql,
  schema: string,
  opts: TenantOptions,
  owner?: string,
): Promise<TenantResult>
```

Арендатор и его первый пользователь — то, что раньше делал свой сид функциями владельца (sys_create, sys_grant_all). Нужно администраторское подключение (роль может стать владельцем); всё — одной транзакцией от владельца. Повтор с тем же именем и логином ничего не дублирует: id — v5 от имени и логина, существующие строки пропускаются (пароль и роли членства не меняются), сессия выдаётся заново. Удалённые арендатор, аккаунт пользователя или членство (строки нет, а журнал id есть) — отказ invalid_data, транзакция откатывается целиком: повтор не воскрешает то, что удалил администратор (up({ tenant }) идёт при каждом запуске), а sys_create пишет только версию 1 — её занимает история; вернуть строку — restore() цепочкой.

Функция заводит арендатора — аккаунт в System — и по умолчанию разрешает пользователям арендатора читать, писать и удалять его данные (`grantAll`). Если задан `user`, она заводит и пользователя: аккаунт, пароль, членство в арендаторе и новую сессию. Всё делается одной транзакцией: при ошибке не записывается ничего. Повторный вызов с тем же именем и логином находит уже созданное: ничего не дублирует, не меняет пароль и роли, а только выдаёт новую сессию. Удалённое повтор не воскрешает: арендатора или пользователя возвращает `db.Account(id).restore()` от имени системного администратора, членство — `db.member(id).restore()` в этом арендаторе. Сессия из `createTenant` не помнит способа входа, поэтому сменить по ней свой пароль нельзя: для этого пользователь входит по паролю.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `sql` | `postgres.Sql` | обязательный | Администраторский пул postgres.js: его роль должна уметь стать владельцем схемы (`set role` на роль-владельца). Закрывает его вызывающий код. |
| `schema` | `string` | обязательный | Полное имя схемы установки: `v2.<имя>`. Удобно брать `r.schema` из результата `up()`. |
| `opts` | `TenantOptions` | обязательный | Арендатор и, по желанию, его первый пользователь — таблица `TenantOptions` ниже. |
| `owner` | `string` | `'letopis_owner'` | Имя роли-владельца — то же, что в `up({ owner })`. |

**Опции `TenantOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="tenant-name"></span>`name` | `string` | обязательная | Имя арендатора (аккаунт в System; id — v5 от «tenant:&lt;имя&gt;»). id вычисляется из имени, поэтому повтор с тем же именем находит уже созданного арендатора. Пустое имя — ошибка `Error` без кода. |
| <span id="tenant-grantall"></span>`grantAll` | `boolean` | `true` | Правило арендатора «аутентифицированным можно всё» (READ, WRITE, DELETE; по умолчанию да). Правило ставится только при создании арендатора; повторный вызов его не добавляет и не снимает. По нему все вошедшие аккаунты, которые работают в этом арендаторе по членству, могут читать, писать и удалять его строки; вес правила — 10. С `false` арендатор остаётся без правил, а права в letopis запрещают всё, что не разрешено явно, — их нужно выдать самим. |
| <span id="tenant-user"></span>`user` | `{ name: string; login: string; password: string; kind?: string; ttl?: string; roles?: string[]; }` | нет: только арендатор | Первый пользователь: аккаунт, членство в арендаторе с ролями roles, пароль и сессия в арендаторе. Поля: `name` — имя в аккаунте; `login` — логин для входа по паролю (из него вычисляется id аккаунта, поэтому пишите логин в одном регистре); `password` — пароль, в базе хранится только его хэш; `kind` — вид пароля, по умолчанию `'PASSWORD'` (тот же вид потом передают в `verifyPassword`); `ttl` — срок сессии интервалом PostgreSQL, по умолчанию `'7 days'`; `roles` — роли членства, по умолчанию `['owner']`. Вид пароля — по тому же правилу, что у `setPassword()`: заглавная латинская буква, затем заглавные буквы, цифры и `_`, всего 2–32 знака, и не служебный вид (`SESSION`, `APIKEY`, `KEYSECRET`, `OTP`, `TOTP`, `KEY`, `PROJECTOR`, `LOCK`), иначе `invalid_data`. Если такой логин уже занят другим аккаунтом (например, записан в другом регистре), пароль новому аккаунту не ставится. |

**Возвращает:** `Promise<TenantResult>` ([TenantResult](./types#type-tenantresult)) — Объект `{ tenant, user, token, created }`: `tenant` — id арендатора; `user` — id пользователя (без `user` в опциях — `null`); `token` — токен новой сессии пользователя в арендаторе, его передают в `connect({ token })` (без пользователя — `null`); `created` — арендатор создан этим вызовом (`false`, если он уже был).

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — список ролей `user.roles` пуст (или это не список), в нём не строка, пустая роль, роль с пробелами по краям, с запятой, фигурными скобками или «!» в начале, или роли повторяются; неверный вид пароля `user.kind` (правило — у опции `user` ниже); удалены арендатор, аккаунт пользователя или членство (строки нет, а история в журнале есть) — тогда не записывается ничего, а текст ошибки говорит, как вернуть удалённое.

**Примеры:** [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход)
