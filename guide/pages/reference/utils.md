# Служебные экспорты

Функции и константы пакета `letopis`, которые не относятся к подключению: операторы фильтров, id, ошибки, проверка данных, пароли.

## Операторы фильтров

Оператор ставится значением поля в фильтре шага, простое значение — равенство. Колонка MCP — ключи JSON-фильтра инструмента `letopis_query`; `$or` ставится вместо всего фильтра.

| TypeScript | MCP | Смысл |
|---|---|---|
| `ne(v)` | `{ "$ne": v }` | Не равно. Подходят и строки без поля или с `null`; `ne(null)` — строки, где у поля есть значение |
| `gt(v)` | `{ "$gt": v }` | Больше. Сравнение — по типу поля из описания класса (числа — как числа, даты — как даты), поле без описания — как текст; строки без поля не подходят |
| `gte(v)` | `{ "$gte": v }` | Больше или равно; сравнение — как у `gt` |
| `lt(v)` | `{ "$lt": v }` | Меньше; сравнение — как у `gt` |
| `lte(v)` | `{ "$lte": v }` | Меньше или равно; сравнение — как у `gt` |
| `between(a, b)` | `{ "$between": [a, b] }` | От `a` до `b` включительно; сравнение — как у `gt`. Если `a` больше `b`, не подходит ничего |
| `inList([v, …])` | `{ "$in": [v, …] }` | Одно из значений списка. Пустой список не находит ничего; `null` в списке не находит строк без значения — для них `isNull` |
| `like(s)` | `{ "$like": "s" }` | Текст по шаблону с учётом регистра: `%` — любые символы, в том числе ни одного, `_` — ровно один; буквальные `%` и `_` — с обратной косой чертой |
| `ilike(s)` | `{ "$ilike": "s" }` | Как `like`, но без учёта регистра |
| `starts(s)` | `{ "$starts": "s" }` | Текст начинается с `s`, с учётом регистра. Это `like(s + '%')`: `%` и `_` внутри `s` не экранируются и работают как в шаблоне |
| `ends(s)` | `{ "$ends": "s" }` | Текст заканчивается на `s`, с учётом регистра. Это `like('%' + s)`: `%` и `_` внутри `s` не экранируются и работают как в шаблоне |
| `has(v)` | `{ "$has": v }` | Поле-массив содержит элемент `v`. Тип важен: `has(5)` найдёт число 5, но не строку `'5'` |
| `hasAny([v, …])` | `{ "$hasAny": [v, …] }` | Поле-массив содержит хотя бы один элемент списка. Находит только строковые элементы; пустой список не находит ничего |
| `hasAll([v, …])` | `{ "$hasAll": [v, …] }` | Поле-массив содержит все элементы списка, в любом порядке. Тип важен, как у `has`; пустой список подходит любой строке, даже без поля |
| `exists(b = true)` | `{ "$exists": b }` | Поле есть в данных (`true`, по умолчанию) или его нет (`false`); значение не важно — поле с `null` тоже есть |
| `isNull()` | `{ "$isNull": true }` | В поле `null` или поля нет совсем; отличить одно от другого помогает `exists` |
| `not(x)` | `{ "$not": x }` | Отрицание: `x` — оператор (`not(gte(1000))` — меньше 1000 или поля нет) или простое значение — тогда это «не равно», как `ne` |
| `or(f1, f2, …)` | `{ "$or": [f1, f2, …] }` | Хотя бы один из фильтров. Ставится вместо всего фильтра шага, а не значением поля; условия внутри одного фильтра соединяются через «и» |

### ne() {#export-ne}

```ts
ne(v: Scalar): Op
```

Значение приводится к типу поля из описания класса.

### like() {#export-like}

```ts

```

### hasAll() {#export-hasall}

```ts
hasAll(vs: Scalar[]): Op
```

Поле-массив содержит все элементы списка, в любом порядке: `db.Product({ labels: hasAll(['хит', 'стекло']) })`. Тип элементов важен, как у `has()`; пустой список подходит любой строке, даже без этого поля.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `vs` | `Scalar[]` | обязательный | Элементы, которые все должны быть в массиве. |

**Возвращает:** `Op` ([Op](./types#type-op)) — Оператор фильтра: его ставят значением поля в фильтре шага.

### not() {#export-not}

```ts
not(v: Scalar | Op): Op
```

Отрицание оператора: `db.Product({ price: not(gte(1000)) })` — цена меньше 1000 или поля нет. Простое значение вместо оператора значит «не равно», как `ne()`: `db.Order({ status: not('cancelled') })`.

Строки без поля подходят, потому что для них исходное условие не выполнено. `or(…)` внутри `not()` даёт `invalid_query` при выполнении цепочки.

| `v` | `Scalar \| Op` | обязательный | Оператор фильтра, который нужно отрицать, или простое значение. |

**Возвращает:** `Op` ([Op](./types#type-op)) — Оператор фильтра: его ставят значением поля в фильтре шага.

### or() {#export-or}

```ts
or<F extends object>(...filters: NoInfer<F>[]): OrOp<F>
```

Хотя бы один из фильтров: `db.Product(or({ sku: 'K-1' }, { price: lt(500) }))` — товар K-1 или дешевле 500. Ставится вместо всего фильтра шага, а не значением поля; условия внутри одного фильтра соединяются через «и». В шаге подключения с моделями (`TypedDb`) фильтры внутри — поля и роли класса шага: тип им даёт шаг. Та же фабрика, что в реестре операторов (ops.ts), — другой у неё только тип.

На месте значения поля `or(…)` даёт `invalid_query` при выполнении цепочки — как и любой другой оператор вместо всего фильтра. `or()` без фильтров не находит ничего.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `...filters` | `NoInfer<F>[]` | обязательный | Фильтры шага: объекты полей, как в `db.Класс({ … })`, со значениями и операторами. |

**Возвращает:** `OrOp<F>` — Оператор фильтра: его ставят вместо всего фильтра шага.

**Ошибки:** собственных кодов нет.

**Примеры:** [Фильтры: все 18 операторов](../read/#фильтры)

### isOp() {#export-isop}

```ts
isOp(v: unknown): v is Op
```

Проверяет, оператор ли перед вами: результат `gt()`, `like()`, `or()` и других функций этого раздела. Оператор помечен особым символом, поэтому его нельзя получить из JSON: фильтр, пришедший по сети, остаётся обычными данными и сравнивается на равенство. Оператор, созданный другой копией пакета в том же процессе, тоже узнаётся.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `v` | `unknown` | обязательный | Любое значение. |

**Возвращает:** `v is Op` — `true`, если `v` — оператор фильтра, иначе `false`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Фильтры: все 18 операторов](../read/#фильтры)

## Приращение и курсор

### inc() {#export-inc}

```ts
inc(by: number, opts?: { start?: number }): IncMarker
```

Приращение числового поля в `update()`: `db.Wallet(w).update({ balance: inc(-300) })`. Сложение делает база над текущим значением поля в момент записи, поэтому одновременные приращения не теряются. Если поля ещё нет, `{ start }` задаёт, с чего начать (поле получит `start + by`), а без него — ошибка `invalid_data`.

Работает только в `update()`. Правило класса вроде `min(0)` проверяется над итогом. Поле во вложенном объекте — `update({ stats: { views: inc(1) } })`; все объекты на пути к полю должны уже быть в данных. Сама функция ничего не проверяет. Ошибка `invalid_data` приходит при выполнении цепочки, если: маркер стоит в `create()`, `upsert()`, загрузчике или внутри массива; величина — не конечное число; поля нет, а `start` не задан; в поле `null` или не число (даже со `start`); итог нарушает описание класса.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `by` | `number` | обязательный | Сколько прибавить; отрицательное число вычитает. Деньги храните целым числом мелких единиц (копеек). |
| `opts` | `{ start?: number }` | `{}` | Настройки приращения. |
| `opts.start` | `number` | нет | Начальное значение, если поля ещё нет: поле получит `start + by`. Без `start` отсутствующее поле — ошибка `invalid_data`. |

**Возвращает:** `IncMarker` ([IncMarker](./types#type-incmarker)) — Маркер приращения для `update()`: замороженный объект, из JSON его не получить.

**Ошибки:** собственных кодов нет.

**Примеры:** [Счётчики inc и защита от параллельной правки { rev }](../write/#числа-счетчики-и-защита-от-параллельнои-правки)

### cursorOf() {#export-cursorof}

```ts
cursorOf(row: Row | Path, field: string): Cursor
```

Курсор постраничного вывода для `after()`: значение поля сортировки, id и номер версии последней строки страницы. Поле — то же, что в `sort()`; если его нет в данных строки, `v` — `null`. Для пути из `paths()` — то же по его последнему узлу (узлу последнего шага) и id всех узлов: курсор отделяет пути с общим последним узлом.

Пример: `db.Product().sort('data.price', 'desc').after(cursorOf(page.at(-1), 'data.price')).limit(20).rows()`. Направление берётся из `sort()`. Курсор можно отдать клиенту в JSON и принять обратно. `after()` проверяет значение курсора по типу поля до запроса и на неподходящее отвечает `invalid_query`, но курсор того же типа, снятый с другого поля, эта проверка не заметит.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `row` | `Row \| Path` | обязательный | Последняя строка страницы — строка ответа (или версия из `versions()`) с `id` и тем полем, по которому идёт сортировка, либо последний путь из `paths()`: тогда поле и `id` берутся у его последнего узла. |
| `field` | `string` | обязательный | Поле сортировки, как в `sort()`: `'at'`, `'rev'`, `'id'` или `'data.<путь>'`, например `'data.price'`. |

**Возвращает:** `Cursor` ([Cursor](./types#type-cursor)) — Курсор `{ v, id, rev }` для `after()`; у пути — `{ v, id, path }`, где `path` — id всех узлов.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — поле не `at`, `rev`, `id` и не начинается с `data.`.

**Примеры:** [Сортировка, страницы и итоги](../read/#сортировка-страницы-и-итоги)

## id объектов

### idOf() {#export-idof}

```ts
idOf(cls: KeyedClass, key: Readonly<Record<string, unknown>>, opts: { tenant: string }): string
```

id объекта класса с ключом: `idOf(класс, { поле: значение, Роль: id }, { tenant })`. Значения ключевых полей — строки как есть (база их не нормализует), значения концов — id целей. Для класса без ключа id выдаёт база — ошибка `no_key`.

Вычисляет id без запроса к базе — тот же, что база даст объекту при создании: UUID версии 5 из арендатора, имени класса и значений ключа в порядке, в котором ключ объявлен. Регистр важен: «Anna@x.ru» и «anna@x.ru» дают разные id. Подключение делает то же короче: `db.idOf('Shop', { name: 'Ромашка' })` берёт описание класса из реестра и арендатора сессии.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `cls` | `KeyedClass` | обязательный | Описание класса: `{ name, key, ends }` — имя класса, части ключа в объявленном порядке и имена концов класса. Для класса из базы подходит `db.registry.resolve(имя)` с `ends: Object.keys(класс.ends)`. |
| `key` | `Readonly<Record<string, unknown>>` | обязательный | Значения частей ключа: у поля — строка, у конца — id цели. id цели можно писать в любом регистре: он приводится к строчным буквам. |
| `opts` | `{ tenant: string }` | обязательный | Настройки вычисления: `{ tenant }`. |
| `opts.tenant` | `string` | обязательный | id арендатора, которому принадлежит объект. |

**Возвращает:** `string` — id объекта: UUID версии 5 в нижнем регистре.

**Ошибки** ([все коды](../errors/)):

- `no_key` — у класса нет ключа.
- `invalid_data` — часть ключа не передана или не строка, значение конца — не uuid, `opts.tenant` — не uuid.

**Примеры:** [Служебные экспорты: id из ключа, пароли, валидатор, типы, строгие типы, зарезервированные имена](../models/#служебные-функции-пакета)

## Ошибки

### LetopisError {#export-letopiserror}

```ts
class LetopisError extends Error {
  constructor(
    code: string,
    message: string,
    detail?: unknown,
    msg?: { key: string; params?: Params },
  );
  readonly code: string;
  readonly detail: unknown;
  declare readonly key?: string;
  declare readonly params?: Params;
  declare readonly hint?: string;
  declare readonly docs?: string;
}
```

Класс ошибок letopis: все ошибки библиотеки и переведённые ошибки базы — его объекты. Код — в `err.code`, подробности — в `err.detail`, а текст ошибки имеет вид `letopis: <код>: <сообщение>`. Ловят так: `if (e instanceof LetopisError && e.code === 'conflict') …`. Все коды — в главе «Ошибки».

**Параметры конструктора**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `code` | `string` | обязательный | Код ошибки, например `'conflict'` или `'invalid_data'`. |
| `message` | `string` | обязательный | Сообщение для человека; в `err.message` к нему спереди добавляется `letopis: <код>: `. |
| `detail` | `unknown` | нет (`undefined`) | Подробности для программы, например `{ id, rev, expected }` у `conflict`. |
| `msg` | `{ key: string; params?: Params }` | нет (`undefined`) | Ключ каталога сообщений и параметры текста — `{ key, params }`, они попадают в `err.key` и `err.params`. Так ошибку создают библиотека и `fromDbError()`; подсказка `err.hint` и адрес раздела документации `err.docs` есть и без них. |
| `msg.key` | `string` | обязательный | Ключ каталога сообщений вида `<раздел>.<имя>`, например `'api.unknown_step'`. |

### fromDbError() {#export-fromdberror}

```ts
fromDbError(e: unknown): unknown
```

Ошибка базы → LetopisError (ValidationError для invalid_data с нарушениями). Детали из DETAIL (JSON) переносятся в detail; ключ каталога и параметры из DETAIL (lt_fail(ключ, …)) — в key и params, текст — тот, что база собрала по ним из русского шаблона; без ключа — текст базы. У нарушений (issues) и строк отказа (detail.rows) key и params наружу не идут. Внутренняя ошибка базы (XX000) с ключом в DETAIL — код internal. Повторяемый конфликт (40001, 40P01) и прочие ошибки возвращаются как есть: на SQLSTATE конфликта держатся повторы (tx.ts).

Библиотека сама переводит ошибки базы, поэтому вызывать функцию нужно только для сырого SQL через свой клиент PostgreSQL. Ошибка с SQLSTATE `LT001`–`LT023` становится `LetopisError` с кодом из главы «Ошибки», а отказ RLS на новых значениях строки (SQLSTATE `42501`) — `acl_denied`. Исходная ошибка остаётся в `cause`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `e` | `unknown` | обязательный | Пойманная ошибка — обычно ошибка драйвера PostgreSQL. |

**Возвращает:** `unknown` — Переведённую ошибку или тот же объект `e`. Функция ошибку возвращает, а не бросает: `throw fromDbError(e)`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Ошибки базы: что ловят триггеры при записи в обход библиотеки](../errors/#запись-в-обход-библиотеки-что-ловит-база)

## Проверка данных

### compileValidator() {#export-compilevalidator}

```ts
compileValidator(schema: JsonSchema): Validator
```

Превращает JSON Schema данных класса в функцию проверки — ту же проверку, что выполняет база при записи, кроме `pattern` (и `anyOf`/`oneOf` с ним в ветке): шаблоны задаёт арендатор, их проверяет только база. Схема класса — `db.registry.resolve(имя).schema`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `schema` | `JsonSchema` | обязательный | JSON Schema данных класса — нормализованная, в том подмножестве, которое понимает база, как `db.registry.resolve(имя).schema`: ключевые слова `$ref`, `$defs` и `$schema` не принимаются. |

**Возвращает:** `Validator` ([Validator](./types#type-validator)) — Функцию проверки: принимает данные и возвращает список нарушений `[{ path, keyword, message }]`; пустой список — данные подходят.

**Ошибки** ([все коды](../errors/)):

- `invalid_class` — в схеме ключевое слово, тип или формат, которых база не понимает (в том числе `$ref`, `$defs`, `$schema`); шаблон `pattern`, несовместимый с PostgreSQL или неверный уже для JavaScript (например, с незакрытой скобкой); внутри `anyOf` и `oneOf` — длина строки (`minLength`, `maxLength`), `uniqueItems: true`, `minProperties` и `maxProperties`, `format` `date` и `date-time`, `enum` и `const` с объектами или массивами. В тексте ошибки — путь к узлу схемы.

### db.registry.load() {#registry-load}


## Пароли и коды

### hashPassword() {#export-hashpassword}

```ts
hashPassword(password: string): Promise<string>
```

Хэш пароля scrypt: `scrypt$N$r$p$соль$хэш`.

`db.auth.setPassword()` хэширует пароль сам, вызывать эту функцию для него не нужно. Параметры scrypt: N = 32768, r = 8, p = 1, соль — 16 случайных байт, хэш — 32 байта; соль и хэш записаны в base64. Из-за случайной соли два вызова с одним паролем дают разные строки; проверяет пароль `verifyHash()`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `password` | `string` | обязательный | Пароль открытым текстом. |

**Возвращает:** `Promise<string>` — Строку вида `scrypt$32768$8$1$<соль>$<хэш>`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Служебные экспорты: id из ключа, пароли, валидатор, типы, строгие типы, зарезервированные имена](../models/#служебные-функции-пакета)

### verifyHash() {#export-verifyhash}

```ts
verifyHash(password: string, stored: string): Promise<boolean>
```

Проверка пароля по хэшу scrypt; другие форматы не проверяются.

Параметры scrypt берутся из самой строки хэша, поэтому подходят и хэши с другими N, r, p — если им хватает 64 МБ памяти (scrypt нужно примерно 128 · N · r байт). Сравнение идёт за постоянное время, чтобы по времени ответа нельзя было подобрать хэш. Строка другого алгоритма или без части с хэшем даёт `false`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `password` | `string` | обязательный | Пароль, который ввёл пользователь. |
| `stored` | `string` | обязательный | Сохранённый хэш — строка от `hashPassword()`. |

**Возвращает:** `Promise<boolean>` — `true`, если пароль подходит к хэшу, иначе `false`.

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — хэш scrypt с недопустимыми N, r, p или такой, которому нужно больше 64 МБ памяти: «хэш пароля: параметры scrypt … недопустимы или требуют больше 64 МБ памяти».

**Примеры:** [Служебные экспорты: id из ключа, пароли, валидатор, типы, строгие типы, зарезервированные имена](../models/#служебные-функции-пакета)

### totpCode() {#export-totpcode}

```ts
totpCode(secretBase32: string, atMs?: number): string
```

Код приложения-аутентификатора для секрета на момент времени (RFC 6238; помощник для тестов и сервисов).

Код тот же, что показывает приложение-аутентификатор: шаг 30 секунд, HMAC-SHA1. Например: `db.auth.verifyTotp({ account, code: totpCode(secret) })`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `secretBase32` | `string` | обязательный | Секрет TOTP в base32 — `secret` из `db.auth.enrollTotp()`; регистр не важен, `=` в конце допускаются. |
| `atMs` | `number` | `Date.now()` | Момент времени в миллисекундах с 1970 года. |

**Возвращает:** `string` — Код из шести цифр строкой, с ведущими нулями.

**Ошибки** ([все коды](../errors/)):

## Константы

### DDL_REVISION {#export-ddl-revision}

```ts
const DDL_REVISION = 8
```

Ревизия схемы, которую знает эта версия пакета, — номер версии SQL-части letopis (таблиц и функций в схеме установки). После `up()` у схемы та же ревизия (`r.revision`); схему отставшей ревизии 2.x `up()` обновляет только с `upgrade: true`, а `connect()` о ней предупреждает. Ревизия 8 — первая у 2.0: схему letopis 1.x (ревизия 7 и ниже) `up()` не обновляет и `connect()` к ней не подключается — 2.0 ставится только заново (`up({ fresh: true })`).

`up()` записывает ревизию в комментарий схемы. Схему новее пакета `up()` не трогает и отказывает, а `connect()` подключается к ней с предупреждением: обновите пакет.

**Примеры:** [Служебные экспорты: id из ключа, пароли, валидатор, типы, строгие типы, зарезервированные имена](../models/#служебные-функции-пакета)

### RESERVED_CLASS_NAMES {#export-reserved-class-names}

```ts
const RESERVED_CLASS_NAMES: readonly string[]
```

Имена методов цепочки, корня `db` и батча. Там, где имя занято методом, библиотека не ищет его среди классов, и шаг с таким именем до класса не дойдёт. Хаб с таким именем отклоняют `hub()`, `syncModels` и база, связь (`link`) — база (`invalid_class`); хаб, заведённый мимо проверки базы, `up()` оставляет и называет в предупреждении.

Корень `db` ищет среди классов любое имя, которого нет среди его методов, а после шага цепочки имена методов цепочки — уже терминалы и модификаторы, а не классы. Поэтому хаб с именем из списка не заводится нигде, а связь с таким именем база не примет при записи модели. Правку описания хаба, заведённого мимо проверки базы (например, от роли владельца), база отклоняет.

**Примеры:** [Служебные экспорты: id из ключа, пароли, валидатор, типы, строгие типы, зарезервированные имена](../models/#служебные-функции-пакета)

### CHAIN_METHODS {#export-chain-methods}

```ts
const CHAIN_METHODS: readonly string[]
```

Имена методов цепочки: модификаторы, терминалы, глаголы записи и слоты концов, а также `then`. После шага цепочки эти имена библиотека не ищет среди классов; все они входят в `RESERVED_CLASS_NAMES`.

`then` занято, чтобы `await` без терминала не выполнял цепочку: цепочка не промис.
