# Права: me.acl

Права проверяет база по матрице: ресурсы (`Resource`) — маски «кто» и «что», правила (`rule`) связывают их. Для каждой строки, каждого действия API и каждой роли побеждает подходящее правило с наибольшим счётом: ключи маски «кто» + 1 за класс, действие или роль + поля условия + 1 у запрета + вес. Роль — тоже ресурс: выдать и снять её (позвать с ней, вписать в прописку) можно только по правилу `me.acl.grant({ role, assign })`, правило по умолчанию ролей не выдаёт. Ничья «можно» против «нельзя»: строка не видна, а `me.acl.check`, `checkData`, `checkRole` и запись спорящего правила отвечают `acl_ambiguous`; подходящих правил нет — правило по умолчанию (на свежем доме — «нельзя»). `me.acl` спрашивает решение для того, от чьего имени идёт запрос, и правит правила квартиры.

**Что здесь:** [Методы](#методы). У каждого пункта — сигнатура с типами, что делает, параметры и опции (тип, значение по умолчанию), что возвращает, коды ошибок и переходы к живым примерам сайта.

## Методы

### me.acl {#db-acl}

```ts
readonly acl: AclApi
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Права того, от чьего имени идёт запрос, — заранее, для интерфейса и проверок в приложении: `check(endpoint)` — можно ли обратиться к ресурсу приложения, `checkData(класс, операция)` — можно ли читать, менять или удалять объекты класса. Сами права база применяет при каждом запросе.

«Тот, от чьего имени идёт запрос», — жилец корня; у корня `db.as()` — жилец, переданный в `as()`; у `db.in()` — консьерж: его правила в квартире разрешают всё.

**Примеры:** [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила) · [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья)

### me.acl.check() {#acl-check}

```ts
check(endpoint: string): Promise<AclDecision>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Можно ли тому, от чьего имени идёт запрос, выполнить действие API. Решают правила System и квартиры: победитель по счёту, `score` и `rule` в ответе; подходящих нет — правило по умолчанию (`rule.default`, `score` 0). Ничья «можно» против «нельзя» — ошибка acl_ambiguous.

Действие API — именованное действие приложения, например отчёт или кнопка: строки база защищает сама, а право на такое действие приложение проверяет этим вызовом. Счёт правила действия — ключи маски «кто» (роли, категории) + 1, если у ресурса есть маска действия + 1 у запрета + вес. Маска `reports.*` подходит `reports.daily`, но не `reports`. Внутренние действия движка `letopis.*` (`letopis.signals`, `letopis.maintain`) решают только правила System: правила квартиры и правило по умолчанию их не выдают — `check()` отвечает так же, как сама база.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `endpoint` | `string` | обязательный | Имя действия, например `reports.daily`: части через точку, как в масках ресурсов `API`. |

**Возвращает:** `Promise<AclDecision>` ([AclDecision](./types-access#type-acldecision)) — `{ allow, rule, score, code?, message? }`: `allow` — можно ли; `rule` — победившее правило (`id`, `group`, `object`, `weight`, `permission`; у правила по умолчанию — ещё `default: true`); `score` — его счёт (у правила по умолчанию — 0); `code` и `message` — из запрещающего правила, если они в нём заданы (у правила по умолчанию — `code: 403`).

**Ошибки** ([все коды](../errors/)):

- `acl_ambiguous` — правила с равным наибольшим счётом спорят: одно разрешает, другое запрещает; в тексте — id обоих.
- `no_session` — у корня нет действующей сессии.

**Примеры:** [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила) · [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья)

### me.acl.checkData() {#acl-checkdata}

```ts
checkData(className: string, op: AclOp): Promise<AclDataDecision>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Можно ли тому, от чьего имени идёт запрос, выполнять операцию `op` с объектами класса: правила-кандидаты по счёту — для каждой строки побеждает первый, чьё условие ей подходит; `all` — разрешены все строки.

Подходит, чтобы заранее скрыть в интерфейсе недоступные действия и понять, почему строка не видна: права на строки база применяет при каждом запросе. Для каждой строки побеждает первый кандидат по счёту, чьё условие (`filter`) строка проходит; кандидатов ниже первого правила без условия строка не увидит. Нет ни одного правила без условия — в конце списка правило по умолчанию (`default: true`, счёт 0). Ничья «можно» против «нельзя» на строке: чтение такую строку не видит, без ошибки; `checkData` бросает `acl_ambiguous`, когда среди кандидатов есть разрешение и запрет с равным счётом, а условие одного входит в условие другого (в том числе оба без условия), — id правил в `err.detail.rules`. Без сессии или квартиры и для неизвестного класса — `{ allow: false, all: false, candidates: [] }`, без ошибки.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `className` | `string` | обязательный | Имя класса (не алиас). |
| `op` | `AclOp` | обязательный | Операция: `READ`, `WRITE` или `DELETE`. |

**Возвращает:** `Promise<AclDataDecision>` ([AclDataDecision](./types-access#type-acldatadecision)) — `{ allow, all, candidates }`: `allow` — есть хоть одно «можно» (операция затронет часть строк или все); `all` — разрешены все строки, без условий; `candidates` — правила-кандидаты по убыванию счёта (при равном — запрет первым), каждый `{ rule, score, permission, filter, default? }`: `rule` — id правила, `filter` — условие на колонки строки (`id`, `owner`, `tenant`, `tags`, `data`, `links`) с подставленными `$actor` и `$tenant`, `{}` — без условия.

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — операция не `READ`, не `WRITE` и не `DELETE` (`sql-access.acl_bad_op`).
- `acl_ambiguous` — разрешение и запрет с равным счётом спорят за одни строки (`sql-access.acl_ambiguous`).

**Примеры:** [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила) · [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья) · [Ничья правил: отказ при записи и скрытая строка при чтении](../access/#ничья)

### me.acl.checkRole() {#acl-checkrole}

```ts
checkRole(role: string): Promise<AclDecision>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Можно ли тому, от чьего имени идёт запрос, выдать и снять роль (`'*'` — любые роли): в приглашении и правкой прописки. Консьержу в квартире — всегда. Ничья — ошибка acl_ambiguous.

Роль — ресурс матрицы: правило «кто → роль» разрешает или запрещает выдать и снять её — в приглашении (`me.invite`), при его принятии (за звавшего) и правкой прописки (`me.acl.roles`, `member(id).update({ roles })`). Нет подходящего правила — нельзя: правило по умолчанию ролей не выдаёт. Консьержу в квартире (`db.in()`) — всегда можно.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `role` | `string` | обязательный | Имя роли, например `'staff'`; `'*'` — право на все роли (и на приглашение без ролей). |

**Возвращает:** `Promise<AclDecision>` ([AclDecision](./types-access#type-acldecision)) — Правило нашлось — `{ allow, score, rule: { id, group, object, weight, permission } }` (у правила обёртки `object` — `assign:<роль>:ROLE`); подходящего правила нет — `{ allow: false, score: 0, message }` без `rule`; консьержу в квартире — `{ allow: true }`.

**Ошибки** ([все коды](../errors/)):

- `acl_ambiguous` — правила с равным наибольшим счётом спорят: одно разрешает, другое запрещает.
- `no_session` — у корня нет действующей сессии.

**Примеры:** [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила) · [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья) · [Роли: кто их выдаёт — правило матрицы assign](../access/#роль-ресурс-матрицы) · [Края приглашения: повтор, отмена, потеря права, почтальон не доставил](../invites/#края-что-будет-если)

### me.acl.grant() {#acl-grant}

```ts
grant(spec: AclRuleSpec): Promise<AclRule[]>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Разрешить роли (`role`) или всем жильцам квартиры (`everyone: true`) операции с классами, действия API и выдачу ролей (`assign`) — по правилу на каждую операцию и цель, с весом `weight` (1–999, по умолчанию 50). Повтор ничего не меняет; поверх запрета той же группы и цели разрешение не пишется (rule_flip — сначала `revoke`); правило, которое при тех же масках и равном счёте спорит с действующим, — отказ rule_tie. Внутри `begin()` — в её транзакции, иначе — своей.

Правила хранятся строками `Resource` и `rule` квартиры. Правило определяют роль (или все аккаунты), операция и цель, поэтому повтор (и смена веса) ничего не ломает, а `grant` поверх `deny` той же пары «кто → что» — отказ `rule_flip`: сначала `me.acl.revoke(…)`. Ничьей с действующим правилом через обёртку не получить: те же «кто» и «что» — всегда та же пара, и обратное решение упирается в `rule_flip` (`rule_tie` бывает только у строк `Resource` и `rule`, записанных цепочкой под другими именами). Счёт правила на строки — ключи маски «кто» + 1 за класс + поля условия + вес: `grant({ role: 'staff', read: 'Order' })` — 1 + 1 + 0 + 50 = 52. `assign` — право выдавать и снимать роли: `grant({ role: 'manager', assign: 'staff' })`, `assign: '*'` — любые роли. Писать правила может тот, кому матрица разрешает запись `Resource` и `rule` (роли `owner` — по правилу `createTenant`). Владелец правила — тот, кто его завёл: менять и снимать его может только он или консьерж.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `spec` | `AclRuleSpec` | обязательный | `{ role \| everyone: true, read?, write?, delete?, api?, assign?, weight? }`: `role` — роль прописки, `everyone: true` — все аккаунты квартиры (ровно одно из двух); `read`, `write`, `delete` — класс (с потомками), `'*'` (все классы) или `{ class, …условие }` — шаблон колонок `owner`, `tenant`, `tags`, `data`, `links`, `id` со значениями `$actor` и `$tenant` (каждое поле условия прибавляет к счёту 1), списком — несколько; `api` — маски действий; `assign` — роль, список ролей или `'*'`, которые можно выдавать и снимать; `weight` — от 1 до 999, по умолчанию 50. |

**Возвращает:** `Promise<AclRule[]>` ([AclRule](./types-access#type-aclrule)) — Записанные правила `{ id, role, everyone, group, op, target, condition?, permission, weight, enabled }` — по одному на операцию и цель.

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — неизвестное поле, нет ни `role`, ни `everyone: true` или есть оба, роль с запятой, фигурными скобками, «!» в начале или пробелами по краям, цель — не имя класса, условие не на колонку, вес вне 1–999 (`access.bad_rule_weight`), нет ни одной операции; ничего не записано.
- `acl_denied` — нет права записи `Resource` или `rule`; правило той же роли и цели завёл другой (`sql-access.rule_foreign`).
- `exists` — у этой пары «кто → что» уже есть обратное правило (`sql-access.rule_flip`).

**Примеры:** [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила) · [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья) · [Роли: кто их выдаёт — правило матрицы assign](../access/#роль-ресурс-матрицы) · [Ничья правил: отказ при записи и скрытая строка при чтении](../access/#ничья) · [Края приглашения: повтор, отмена, потеря права, почтальон не доставил](../invites/#края-что-будет-если) · [С нуля: дом, пропуск, вход по ключу и второй жилец](../start/#семь-шагов-на-примере)

### me.acl.deny() {#acl-deny}

```ts
deny(spec: AclRuleSpec): Promise<AclRule[]>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Запретить — те же правила с запретом: у запрета счёт на 1 больше, чем у такого же разрешения.

То же, что `grant`, с запретом. Запрет с условием прячет только подходящие строки: после `grant({ role: 'staff', read: 'Order' })` (счёт 52) запрет `deny({ role: 'staff', read: { class: 'Order', data: { vip: true } } })` (счёт 1 + 1 + 1 + 1 + 50 = 54) скрывает от роли `staff` только VIP-заказы. `deny` поверх `grant` той же пары — отказ `rule_flip`: сначала `revoke`.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `spec` | `AclRuleSpec` | обязательный | Как у `grant`: `{ role \| everyone: true, read?, write?, delete?, api?, assign?, weight? }`. |

**Возвращает:** `Promise<AclRule[]>` ([AclRule](./types-access#type-aclrule)) — Записанные правила `{ id, role, everyone, group, op, target, condition?, permission: 'deny', weight, enabled }`.

- `invalid_data` — как у `grant`; ничего не записано.

### me.acl.revoke() {#acl-revoke}

```ts
revoke(spec: Omit<AclRuleSpec, 'weight'>): Promise<number>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Снять правила роли или всех жильцов — разрешения и запреты — для этих операций и целей; возвращает число снятых правил. Операции снимаются по очереди, и правило на несколько операций считается один раз. Чужое правило (его завёл другой аккаунт) снимает только консьерж — иначе rule_foreign.

Ресурсы остаются: без правил они ни на что не действуют. Правила консьержа и роли `owner`, которые заводит `createTenant`, завёл консьерж: жилец их не снимет.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `spec` | `Omit<AclRuleSpec, 'weight'>` | обязательный | `{ role \| everyone: true, read?, write?, delete?, api?, assign? }` — как у `grant`, без `weight`. |

**Возвращает:** `Promise<number>` — Число снятых правил; 0 — таких правил не было.

**Ошибки** ([все коды](../errors/)):

- `invalid_data` — как у `grant` (и поле `weight`); ничего не снято.
- `acl_denied` — нет права удалить `rule`; правило завёл другой жилец (`sql-access.rule_foreign`).

**Примеры:** [Счёт правил: ничья, правило по умолчанию, кто меняет правило](../access/#ничья) · [Роли: кто их выдаёт — правило матрицы assign](../access/#роль-ресурс-матрицы) · [Края приглашения: повтор, отмена, потеря права, почтальон не доставил](../invites/#края-что-будет-если) · [Несколько жильцов: owner, сотрудник и правила по ролям](../access/#пример-жильцы-роли-и-правила)

### me.acl.roles() {#acl-roles}

```ts
roles(account: string | { id: string }, roles?: readonly string[] | null): Promise<string[] | null>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Роли прописки аккаунта в квартире (строка `member`); null — не прописан. Со списком — заменить роли, с null — выписать (его ключи этой квартиры гаснут). Каждую добавленную и снятую роль должна разрешать матрица (`assign`), иначе role_denied. Прописать нового человека нельзя: только приглашением (invite, accept).

Прописка — строка `member` с концами `User` и `Tenant` в квартире; роли сверяются с масками групп правил квартиры (`{ roles: '{staff}' }`). Каждую добавленную и каждую снятую роль (при выписке — каждую роль выписываемого) должно разрешать правило `assign` тому, кто правит; консьержу (`db.in()`) — всегда. Выписка (`null`) гасит ключи и сессии жильца в этой квартире.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `account` | `string \| { id: string }` | обязательный | Аккаунт — id или строка с полем `id`. |
| `roles` | `readonly string[] \| null` | нет — прочитать роли | Новые роли: список заменяет прежние, `null` выписывает. |

**Возвращает:** `Promise<string[] | null>` — Роли аккаунта в квартире; `null` — не прописан.

**Ошибки** ([все коды](../errors/)):

- `acl_denied` — аккаунт не прописан, а роли задают списком — прописка только по приглашению (`sql-access.member_invite_only`); нет права записи `member` (для `null` — удаления); нельзя выдать или снять роль (`sql-access.role_denied`, `err.params.role`).
- `invalid_data` — роль не по правилу имён, роли повторяются, аккаунт не задан.
- `no_session` — у корня нет квартиры (`access.no_session_tenant`).

### me.acl.people() {#acl-people}

```ts
people(): Promise<AclPerson[]>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Люди этой квартиры: `[{ account, name, roles }]` по имени, затем по id аккаунта — для страницы «Команда» и подписей авторов. В ответе ровно те, чью прописку (`member`) видит тот, от чьего имени идёт запрос: хозяин (правило owner) и консьерж в квартире (`db.in`) — все; жилец без правила на чтение `member` — только он сам; с правилом — те, кого оно открывает. Контактов в ответе нет (контакт отдаёт консьерж: `db.contactOf(аккаунт)`); людей других квартир так не узнать. Чужую строку `Account` цепочкой по-прежнему не прочитать.

Видно ровно тех, чью прописку (`member`) вызывающий видит по матрице: хозяину (роль `owner`) и консьержу в квартире (`db.in()`) — всех прописанных; жильцу без правила на чтение `member` — только себя (это не отказ); с правилом `me.acl.grant({ everyone: true, read: 'member' })` — всех, с правилом с условием — себя и тех, чья прописка подходит; корню `db.as(аккаунт, квартира)` — как этому жильцу. Только эта квартира; выписанных в списке нет. Контактов в ответе нет — контакт отдаёт только консьерж: `db.contactOf(аккаунт)`. Работает и в `me.begin()`.

**Возвращает:** `Promise<AclPerson[]>` ([AclPerson](./types-access#type-aclperson)) — Массив `{ account, name, roles }` (тип `AclPerson`): id аккаунта, имя (у аккаунта без имени — пустая строка), роли прописки; по имени, затем по id аккаунта.

**Ошибки** ([все коды](../errors/)):

- `no_session` — нет действующей сессии (`sql-access.no_session`).

### me.acl.list() {#acl-list}

```ts
list(): Promise<AclRule[]>
```

**Откуда:** `me.acl`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Правила квартиры — свои, жильцов, консьержа и роли owner от createTenant. На подключении без RLS — тоже только правила этой квартиры, без правил других квартир и System.

Правила, записанные `grant()` и `deny()`, показаны по роли; правила групп не одной роли — консьержа (`service:ACCOUNT`) и своих групп — по имени группы (`role: null`); правила для всех аккаунтов — с `everyone: true`. Правило на роль — `op: 'ROLE'`, `target` — имя роли или `'*'`. В списке и правила, которые завёл `createTenant`: консьержа (вес 1 000 000) и роли `owner` (вес 100 000).

**Возвращает:** `Promise<AclRule[]>` ([AclRule](./types-access#type-aclrule)) — Массив `{ id, role, everyone, group, op, target, condition?, permission, weight, enabled }`, по операции, цели и роли; `enabled: false` — правило выключено полем `enabled` строки `rule`, база его не применяет.

**Ошибки** ([все коды](../errors/)):

- `no_session` — у корня нет квартиры (`access.no_session_tenant`).
