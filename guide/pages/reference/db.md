# Корень db

`db` — подключение, которое возвращает `connect()`. Классы модели — стартовые шаги цепочек (`db.Класс(фильтр)`), остальное — служебные методы и свойства. Транзакция `db.begin()` и подключение `db.as()` устроены так же.

## Свойства

### db.schema {#db-schema}

```ts
readonly schema: string
```

Имя схемы установки, с которой работает подключение, например `v2.shop`: то, что передали в `connect({ schema })`.

**Примеры:** [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход)

### db.token {#db-token}

```ts
readonly token: string | null
```

Токен сессии подключения: переданный в `connect({ token })` или полученный в обмен на ключ API из `connect({ apiKey })`. `null` — сессии нет: например, у администраторского подключения без токена (его роль базы обходит RLS, опция `connect({ allowBypassRls: true })`). У подключения `db.as()` токен тот же, что у исходного: работа от имени другого аккаунта новой сессии не выпускает.

**Примеры:** [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход)

### db.tenant {#db-tenant}

```ts
readonly tenant: string | null
```

Арендатор сессии.

Это id арендатора, в котором сейчас работает сессия: после входа — личный арендатор, после `auth.switch()` — выбранный. У подключения `db.as()` — арендатор, выбранный при вызове `as()`. `null` — сессии нет.

**Примеры:** [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход)

### db.registry {#db-registry}

```ts
readonly registry: Registry
```

Реестр классов подключения: описания классов System и арендатора сессии, которые подключение держит в памяти. Методы: `resolve(имя)` — описание класса по имени или алиасу (нет такого — `invalid_class`), `find(имя)` — то же или `undefined`, `has(имя)` — есть ли такой класс, `all()` — все описания, `family(имя)` — класс и все его потомки. Реестр обновляется сам по сигналу базы; обновить его сразу — `db.refresh()`.

**Примеры:** [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

## От имени другого аккаунта

### db.as() {#db-as}

```ts
as(account: string | { id: string } | null, opts?: { owner?: string; tenant?: string }): Promise<Db>
```

Подключение на том же пуле от имени другого аккаунта: запросы идут с его правами и в его арендаторе. Журнал записывает автором версий этот аккаунт, а исполнителем (`agent`) — аккаунт сессии, например сервис. Нужно право `auth.impersonate`.

Разрешает это база: от имени System, сервисов, системных администраторов и выключенных аккаунтов работать нельзя.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `account` | `string \| { id: string } \| null` | обязательный | Аккаунт, от имени которого работать: id или объект с `id`. `null` — тот же аккаунт, что у этого подключения (чтобы сменить только арендатора или владельца). |
| `opts` | `{ owner?: string; tenant?: string }` | нет | Арендатор и владелец. |
| `opts.owner` | `string` | владелец этого подключения; если его нет — по `ownerDefault` класса | Владелец новых строк: id аккаунта. Если такого аккаунта нет, запись получит `target_not_found`. |
| `opts.tenant` | `string` | личный арендатор аккаунта; при `account = null` — текущий | Арендатор, в котором работать: личный арендатор аккаунта или тот, где у аккаунта есть членство. |

**Возвращает:** `Promise<Db>` ([Db](./types#type-db)) — Подключение с тем же API, что у `db`, от имени аккаунта в выбранном арендаторе.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — вызван внутри `db.begin()`.
- `no_session` — у подключения нет действующей сессии.
- `acl_denied` — нет права `auth.impersonate`, аккаунт нельзя выбрать (System, сервис, системный администратор, выключен) или `account` — не id.
- `tenant_denied` — у аккаунта нет членства в арендаторе `tenant` или это не id арендатора.

**Примеры:** [Установка, первый арендатор и вход](../install/#пример-установка-арендатор-и-вход)

## Транзакции и сырой SQL

### db.begin() {#db-begin}

```ts
begin(opts?: { reason?: string }): Promise<DbTx>
```

Явная транзакция `read committed`: те же цепочки, `commit()`, `rollback()`, `lock()`, `forUpdate()`; `reason` — причина изменения для всех операций блока.

Транзакция уровня `read committed` на одном соединении. Внутри работают те же цепочки, `db.sql`, `forUpdate()` и `lock()`; завершает её `commit()` или `rollback()`. Ошибка любого запроса ломает транзакцию: следующие вызовы и `commit()` бросают эту ошибку, а `commit()` при этом откатывает. Библиотека не повторяет запросы внутри транзакции: при взаимной блокировке повторите весь блок.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `{ reason?: string }` | нет | Настройки транзакции. |
| `opts.reason` | `string` | нет | Причина изменения для всех записей транзакции: строка до 1000 символов. Её можно переопределить у отдельного глагола. |

**Возвращает:** `Promise<DbTx>` ([DbTx](./types#type-dbtx)) — Транзакцию — подключение с тем же API, что у `db`; все его операции идут в этой транзакции.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — вызван внутри другой `db.begin()` (вложенных транзакций нет) или `reason` — не строка до 1000 символов.

**Примеры:** [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### db.commit() {#db-commit}

```ts
commit(tr?: DbTx): Promise<void>
```

Зафиксировать транзакцию `tr` (то же, что `tr.commit()`).

Если транзакцию сломала ошибка, `commit()` откатывает её и бросает эту ошибку. Повторный вызов после успешной фиксации ничего не делает.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `tr` | `DbTx` | та, у которой вызван метод | Транзакция `db.begin()`, которую зафиксировать. |

**Возвращает:** промис без значения.

**Ошибки** ([все коды](../errors/)):

- `tx_required` — `tr` не передан, а метод вызван не у транзакции `db.begin()`.
- `tx_rolled_back` — PostgreSQL ответил на `COMMIT` откатом (`ROLLBACK`): ошибку в транзакции перехватил код внутри неё.
- `commit_unknown` — связь оборвалась во время `COMMIT`: транзакция могла и зафиксироваться.

**Примеры:** [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### db.rollback() {#db-rollback}

```ts
rollback(tr?: DbTx): Promise<void>
```

Откатить транзакцию `tr` (то же, что `tr.rollback()`).

Откат проходит и у сломанной ошибкой транзакции. Повторный вызов ничего не делает.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `tr` | `DbTx` | та, у которой вызван метод | Транзакция `db.begin()`, которую откатить. |

**Возвращает:** промис без значения.

**Ошибки** ([все коды](../errors/)):

- `tx_required` — `tr` не передан, а метод вызван не у транзакции `db.begin()`.

**Примеры:** [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### db.lock() {#db-lock}

```ts
lock(...keys: (string | number)[]): Promise<void>
```

Advisory-блокировка до конца транзакции — только в `db.begin()` (иначе `tx_required`).

Advisory-блокировка — блокировка PostgreSQL по произвольному ключу, а не по строке. Если блокировку с тем же ключом уже держит другая транзакция, вызов ждёт её конца. Защищает, только если её берут все, кто правит эти данные.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `...keys` | `(string \| number)[]` | обязательный | Части ключа: строки и числа. Они склеиваются через `\|`, поэтому `lock('a', 1)` и `lock('a\|1')` — одна блокировка. |

**Возвращает:** промис без значения.

**Ошибки** ([все коды](../errors/)):

- `tx_required` — вызван вне `db.begin()` или после её завершения.

**Примеры:** [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### db.transaction() {#db-transaction}

```ts
transaction<T>(fn: (tx: Tx) => Promise<T>): Promise<T>
```

Транзакция под сессией: `fn` получает соединение postgres.js (в `db.begin()` — ту же транзакцию).

Запросы через `tx` подчиняются RLS и триггерам, как и цепочки. Вне `db.begin()` при взаимной блокировке и ошибке сериализации вся `fn` повторяется до трёх раз, поэтому она должна выдерживать повтор. В `db.begin()` повторов нет, а ошибка внутри `fn` ломает всю транзакцию.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `fn` | `(tx: Tx) => Promise<T>` | обязательный | Асинхронная функция: получает соединение транзакции `tx` и выполняет запросы через него. |

**Возвращает:** `Promise<T>` — То, что вернула `fn`.

**Ошибки** ([все коды](../errors/)):

- `commit_unknown` — вне `db.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.
- `tx_required` — вызван у транзакции `db.begin()`, которая уже зафиксирована или откачена.

**Примеры:** [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### db.sql() {#db-sql}

```ts
sql(strings: TemplateStringsArray, ...values: unknown[]): Promise<postgres.Row[]>
```

Сырой SQL под сессией и RLS, одной транзакцией (в `db.begin()` — в ней): `` db.sql`select …` ``.

Запрос видит те же строки, что и цепочки. Писать тоже можно — данные проверят те же триггеры. Вне `db.begin()` при взаимной блокировке и ошибке сериализации библиотека повторяет запрос до трёх раз. Ошибки, которые бросает сама letopis в базе, приходят как `LetopisError` с её кодом, например `acl_denied`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `strings` | `TemplateStringsArray` | обязательный | Части текста запроса — их передаёт сам шаблон: db.sql`select …`. |
| `...values` | `unknown[]` | обязательный | Значения, подставленные в шаблон через `${…}`: уходят в базу параметрами, а не текстом запроса. |

**Возвращает:** `Promise<postgres.Row[]>` — Строки ответа запроса массивом объектов (как у postgres.js).

**Ошибки** ([все коды](../errors/)):

- `commit_unknown` — вне `db.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.
- `tx_required` — вызван у транзакции `db.begin()`, которая уже зафиксирована или откачена.

**Примеры:** [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

## Батч

### db.batch() {#db-batch}

```ts
batch(name: string, opts?: { reason?: string }): Batch
```

Именованная очередь планов фасада: `batch.Класс(…).create(…)`; `batch.run()` — одной транзакцией. У корня, у каждого `db.as()` и у каждой `db.begin()` очереди свои: план исполняется от имени фасада, который его поставил.

Планы одного батча ставьте через один и тот же фасад. Повторный `db.batch(имя)` с тем же именем у того же фасада работает с той же очередью.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `name` | `string` | обязательный | Имя очереди. |
| `opts` | `{ reason?: string }` | нет | Настройки батча. |
| `opts.reason` | `string` | нет | Причина изменения для планов, поставленных через этот объект батча: строка до 1000 символов. Её можно переопределить у отдельного глагола. |

**Возвращает:** `Batch` ([Batch](./types#type-batch)) — Батч: `batch.Класс(…)` начинает план записи, и первый глагол ставит его в очередь; `run()`, `discard()` и `size()` — ниже.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — `reason` — не строка до 1000 символов.

**Примеры:** [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина)

### batch.run() {#batch-run}

```ts
run(): Promise<Row[][]>
```

Исполняет все планы очереди одной транзакцией. Подряд идущие простые `create` одного класса с ключом склеиваются в один многострочный оператор, подряд идущие `upsert` — тоже. Ошибка любого плана откатывает весь батч; коды ошибок — те же, что у глагола этого плана. Очередь очищается в начале вызова, поэтому после ошибки планы нужно поставить заново. В `db.begin()` батч исполняется внутри этой транзакции.

**Возвращает:** `Promise<Row[][]>` — Массив результатов в порядке постановки в очередь: у каждого плана — массив записанных им строк. Пустая очередь — пустой массив.

**Ошибки** ([все коды](../errors/)):

- `exists` — `create` на ключ, который уже занят.
- `commit_unknown` — вне `db.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.

**Примеры:** [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина)

### batch.discard() {#batch-discard}

```ts
discard(): void
```

Очищает очередь: планы удаляются без исполнения.

**Возвращает:** ничего.

**Ошибки:** собственных кодов нет.

**Примеры:** [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина)

### batch.size() {#batch-size}

```ts
size(): number
```

Сколько планов ждут исполнения в очереди.

**Возвращает:** `number` — Число планов; после `run()` и `discard()` — `0`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина)

## Модель и id

### db.entity() {#db-entity}

```ts
entity(x: Chain | Row): Chain
```

Начать путь с готового узла: `db.entity(row | цепочка)`.

Узел — объект, с которого цепочка продолжает путь. Из строки ответа получается шаг её класса с её id; из цепочки чтения — её шаги целиком, и следующие шаги идут от её последнего шага.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `x` | `Chain \| Row` | обязательный | Строка ответа (нужны `id` и `class`) или цепочка чтения без глаголов записи. |

**Возвращает:** `Chain` ([Chain](./types#type-chain)) — Новую цепочку, которая начинается с этого узла.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — передана цепочка с глаголом записи или значение, которое не строка ответа и не цепочка.
- `invalid_class` — класса строки нет в реестре.

**Примеры:** [Ссылки шагами: set, unset, add, remove; entity(), cache(); await цепочки — не запрос](../write/#ссылки-из-пути-цепочки-и-вызовами-роль-set-add-remove)

### db.idOf() {#db-idof}

```ts
idOf(cls: string, key: Readonly<Record<string, unknown>>): string
```

id объекта по классу и значениям ключа — такой же, какой вычислит база в арендаторе сессии.

Вычисление идёт в приложении, без запроса к базе: так можно сослаться на объект, не читая его.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `cls` | `string` | обязательный | Имя класса или его алиас. |
| `key` | `Readonly<Record<string, unknown>>` | обязательный | Значения всех частей ключа: у поля — строка, у конца — id цели. Пример: `{ sku: 'K-1', Shop: shopId }`. |

**Возвращает:** `string` — id объекта (UUID v5).

**Ошибки** ([все коды](../errors/)):

- `no_session` — у подключения нет арендатора сессии.
- `invalid_class` — класса с таким именем или алиасом нет в реестре.
- `no_key` — у класса нет ключа: id выдаёт база при создании.
- `invalid_data` — часть ключа не строка или значение конца не uuid.

**Примеры:** [Модель магазина: классы, концы, ключи](../models/#пример-модель-магазина)

### db.describe() {#db-describe}

```ts
describe(): ModelDescription
```

Описание модели для программ и языковых моделей: классы арендатора сессии и общие классы System с полями, ключом, ссылками и метаданными `meta`. `describeText(db.describe())` превращает его в текст.

Описание берётся из реестра классов, без запроса к базе. Права реестр не фильтрует: классы своего арендатора и System видит любая сессия. У класса есть ещё обязательные поля и политика истории, а если заданы — условия `anyOf` и `oneOf`, признак производного класса `derivedBy` и агрегаты `aggregate`. В `examples` — рабочие цепочки из реестра: создать (`create`; нет у абстрактного, производного и системного класса), найти (`find`) и перейти к соседям (`neighbors`).

**Возвращает:** `ModelDescription` ([ModelDescription](./types#type-modeldescription)) — Объект `{ schema, tenant, classes, methods }`: в `classes` сначала классы приложения, затем системные, в каждой группе — по имени; `methods` — имена методов цепочки и корня `db`.

**Ошибки:** собственных кодов нет.

**Примеры:** [Настройки класса: без истории, владелец-автор, метаданные, описание модели](../models/#настроики-класса)

### db.refresh() {#db-refresh}

```ts
refresh(): Promise<void>
```

Перечитать описания классов.

Обычно реестр классов обновляется сам по сигналу базы. Вызов нужен, когда сигналов нет (`connect({ listen: false })`, например за PgBouncer в режиме транзакций) или когда новое описание класса нужно сразу, не дожидаясь сигнала. Перечитываются и реестры подключений `db.as()`.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** [Проектор: итоги из журнала, записи не ждут друг друга](../derived/#проектор-из-журнала)

### db.rekeyClass() {#db-rekeyclass}

```ts
rekeyClass(cls: string, key: string[]): Promise<number>
```

Меняет ключ класса. Объекты его семейства (сам класс и потомки), у которых по новому ключу выходит другой id, переезжают на новый id, а ссылки на них переводятся.

Новый ключ получают те классы семейства, что наследуют ключ. История переехавшей строки продолжается под новым id, а старый id остаётся надгробием со ссылкой на новый. Пока идёт перенос, запись в семейство ждёт. Работает только с собственными классами арендатора сессии. Нужны право WRITE на описание класса, право READ без условий на все строки семейства и право WRITE на переносимые строки и строки, которые на них ссылаются.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `cls` | `string` | обязательный | Имя класса или его алиас. |
| `key` | `string[]` | обязательный | Новый ключ — список имён: обязательные строковые поля и обязательные одиночные концы. |

**Возвращает:** `Promise<number>` — Сколько строк семейства получили новый id. Строки других классов, которые переехали заодно (конец на перенесённую строку входит в их ключ), не считаются.

**Ошибки** ([все коды](../errors/)):

- `no_session` — нет действующей сессии.
- `invalid_class` — класса нет, это класс System или системный класс, либо новый ключ не годится (поле не обязательная строка, конец не обязательный одиночный, такого поля или конца нет).
- `derived_class` — класс или его потомок производный: его строки пишет проектор.
- `acl_denied` — не хватает прав на класс или на строки.
- `tightening_conflict` — строки не соответствуют новому ключу; подробности — в `err.detail`.

**Примеры:** [История через смену номера и класса: versions({ follow })](../history/#смена-номера-и-класса-versions-follow)

## История и целостность

### db.trimHistory() {#db-trimhistory}

```ts
trimHistory(target: string | string[] | Row | Row[], before: string | Date): Promise<number>
```

Стирает версии, сделанные раньше момента `before`; текущая версия остаётся всегда. Вместо стёртого начала истории остаётся служебная запись `trim` со временем появления объекта.

По записи `trim` срез на момент знает, когда объект появился. Работает в арендаторе сессии; нужно право DELETE на строки. Объекты класса, которых вызывающий не видит, пропускаются. Это средний шаг «права на забвение»: `anonymize`, затем обрезка истории, затем удаление и `purge`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `target` | `string \| string[] \| Row \| Row[]` | обязательный | Что обрезать: имя класса (вместе с потомками), id объекта, список id, строка ответа или список строк. |
| `before` | `string \| Date` | обязательный | Момент: версии раньше него стираются. Строка ISO или `Date`. |

**Возвращает:** `Promise<number>` — Сколько версий стёрто.

**Ошибки** ([все коды](../errors/)):

- `no_session` — нет действующей сессии.
- `target_not_found` — заданного id нет в арендаторе сессии, он не виден или его история уже стёрта.
- `invalid_class` — цель — строка системного класса (`Class`, `Account`, `member`, `Resource`, `rule`): их история не обрезается.
- `acl_denied` — нет права DELETE на строку цели.
- `projector_pending` — проектор, который читает этот класс, ещё не обработал версии, которые нужно стереть: сначала вызовите его `run()`.

**Примеры:** [Хранение истории по ярусам: maintain, trimHistory, cursor_expired](../history/#хранение-по-ярусам)

### db.verify() {#db-verify}

```ts
verify(opts?: { data?: boolean }): Promise<VerifyResult>
```

Проверяет целостность журнала всей установки: сходится ли хэш каждой версии с хэшем предыдущей и текущая строка объекта — с его последней версией; с `{ data: true }` проверяет ещё каждую строку. Якорь в ответе — один хэш текущих версий всех объектов: храните его вне базы, тогда заметна и подмена самых свежих версий. Нужно право `letopis.verify` (по умолчанию оно у системного администратора) или администраторское подключение.

Правка журнала в обход библиотеки видна по несовпадению хэшей. Законные разрывы цепочки — обрезка истории, `purge`, прореживание и сброс — находками не считаются.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `{ data?: boolean }` | `{}` | Настройки проверки. |
| `opts.data` | `boolean` | `false` | `true` — проверить ещё каждую строку: данные по описанию класса, цели концов, арендатора, владельца, id по ключу и агрегатные поля. Такая проверка идёт дольше. |

**Возвращает:** `Promise<VerifyResult>` ([VerifyResult](./types#type-verifyresult)) — Объект `{ ok, issues, anchor }`: `ok` — находок нет, `issues` — находки (у каждой — `id`, номер версии `rev` или класс `class` и описание `problem`), `anchor` — якорь.

**Ошибки** ([все коды](../errors/)):

- `acl_denied` — нет права `letopis.verify` и подключение не администраторское.

**Примеры:** [Проверка целостности: verify() и правка журнала в обход библиотеки](../ops/#проверка-целостности)

## Обслуживание

### db.maintain() {#db-maintain}

```ts
maintain(opts?: MaintainOptions): Promise<MaintainReport>
```

Обслуживание: истёкшие сессии и коды, прореживание журнала по политике хранения, очередь сигналов.

Журнал прореживается пачками, и каждая пачка — своя транзакция, поэтому долгих блокировок нет. Из нескольких процессов работает один: если обслуживание уже идёт в другом процессе, вызов ничего не делает и отвечает `skipped: true`. Нужно право `letopis.maintain` (по умолчанию оно есть только у системного администратора) или администраторское подключение. Запускать по расписанию удобно опцией `connect({ maintain: '1h' })` или командой `letopis maintain`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `MaintainOptions` | `{}` | Настройки обслуживания (опции ниже). |

**Опции `MaintainOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="maintain-now"></span>`now` | `string \| Date` | текущее время базы | Момент «сейчас» для прореживания — только в установке с `allowReset` (тесты).<br>Примеры: [Хранение истории по ярусам: maintain, trimHistory, cursor_expired](../history/#хранение-по-ярусам) |
| <span id="maintain-batches"></span>`batches` | `number` | `100` | Сколько пачек прореживания журнала самое большее сделать за один вызов; каждая пачка — своя транзакция.<br>Примеры: [Хранение истории по ярусам: maintain, trimHistory, cursor_expired](../history/#хранение-по-ярусам) |
| <span id="maintain-limit"></span>`limit` | `number` | `10000` | Сколько версий самое большее удалить в одной пачке прореживания. Значение меньше 1 считается за 1.<br>Примеры: [Хранение истории по ярусам: maintain, trimHistory, cursor_expired](../history/#хранение-по-ярусам) |

**Возвращает:** `Promise<MaintainReport>` ([MaintainReport](./types#type-maintainreport)) — Отчёт `{ skipped, sessions, codes, thinned, batches, more, queue }`: `sessions` — сколько удалено сессий, истёкших и погашенных; `codes` — сколько удалено одноразовых кодов любого вида (`OTP` и свои `OTP_<ИМЯ>` из `issueOtp({ kind })`), которые больше не действуют: использованных, заменённых новым, исчерпавших попытки и истёкших; `thinned` — сколько версий прорежено; `batches` — сколько пачек выполнено; `more: true` — журнал прорежен не до конца, продолжит следующий вызов; `queue` — заполнение очереди сигналов PostgreSQL от 0 до 1, больше половины — предупреждение в консоль.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — вызван внутри `db.begin()`.
- `acl_denied` — нет права `letopis.maintain` и подключение не администраторское.
- `reset_disabled` — задана опция `now`, а установка поставлена без `allowReset`.

**Примеры:** [Хранение истории по ярусам: maintain, trimHistory, cursor_expired](../history/#хранение-по-ярусам)

### db.reset() {#db-reset}

```ts
reset(opts: ResetOptions): Promise<ResetResult>
```

Сбрасывает тестовую установку: сессии, данные одного арендатора или всё — смотря по `level`. Работает, только если установка поставлена с `up({ allowReset: true })`, у вызывающего есть право `letopis.reset` (или подключение администраторское), а `confirm` совпадает с именем схемы.

Сброс нужен тестам и стендам. После `level: 'all'` не действуют прежние сессии и ключи — в том числе те, с которыми работает это подключение. Первая запись журнала после сброса — запись `reset`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `ResetOptions` | обязательный | Что сбросить и подтверждение (опции ниже). |

**Опции `ResetOptions`**

| Опция | Тип | По умолчанию | Описание |
|---|---|---|---|
| <span id="reset-level"></span>`level` | `'sessions' \| 'tenant' \| 'all'` | обязательная | Что сбросить: `'sessions'` — все сессии, кроме текущей; `'tenant'` — строки и журнал арендатора; `'all'` — всё, после чего заново ставятся системные классы и выпускается новый ключ сервиса.<br>Примеры: [Сброс: reset({ level }) — сессии, данные арендатора, всё](../ops/#сброс-тестовои-установки) |
| <span id="reset-confirm"></span>`confirm` | `string` | обязательная | Подтверждение — имя схемы установки.<br>Примеры: [Сброс: reset({ level }) — сессии, данные арендатора, всё](../ops/#сброс-тестовои-установки) |
| <span id="reset-tenant"></span>`tenant` | `string` | арендатор сессии | Какого арендатора сбросить при `level: 'tenant'` — его id; на других уровнях не учитывается.<br>Примеры: [Сброс: reset({ level }) — сессии, данные арендатора, всё](../ops/#сброс-тестовои-установки) |

**Возвращает:** `Promise<ResetResult>` ([ResetResult](./types#type-resetresult)) — Отчёт о сбросе: всегда `level`; для `sessions` — `sessions`, сколько сессий удалено; для `tenant` — `tenant` (какой арендатор сброшен), `rows` и `versions` (сколько стёрто строк и версий журнала); для `all` — `serviceKey`, новый ключ сервиса.

**Ошибки** ([все коды](../errors/)):

- `reset_disabled` — установка поставлена без `allowReset`.
- `acl_denied` — нет права `letopis.reset`.
- `confirm_mismatch` — `confirm` не совпадает с именем схемы.
- `tenant_denied` — `level: 'tenant'` для System или когда арендатор не задан и у сессии его нет: System сбрасывается только целиком.
- `target_not_found` — `level: 'tenant'`: такого арендатора нет.
- `invalid_data` — неизвестный уровень `level`.
- `invalid_query` — `level: 'tenant'` внутри `db.begin()`: этот уровень работает пачками в своих транзакциях.

**Примеры:** [Сброс: reset({ level }) — сессии, данные арендатора, всё](../ops/#сброс-тестовои-установки)

### db.flushSignals() {#db-flushsignals}

```ts
flushSignals(): Promise<void>
```

Отправить накопленные сигналы сейчас.

После записи библиотека шлёт сигнал «данные изменились» не сразу: она копит сигналы и отправляет их пачкой раз в `notifyIntervalMs` (опция `connect()`, по умолчанию 100 мс). Раньше срока их отправляют, например, перед выходом из процесса или в тесте. Если отправить не удалось, сигналы остаются в очереди до следующей попытки, а промис не отклоняется.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** [Описание модели, свой SQL с правами сессии, кэш по сроку, сигналы](../ops/#описание-модели-сырои-sql-кэш-сигналы)

### db.close() {#db-close}

```ts
close(): Promise<void>
```

Закрывает подключение: останавливает обслуживание по расписанию (идущий запуск доделывает пачку) и фоновое перечитывание реестра, отправляет накопленные сигналы, перестаёт слушать сигналы базы и закрывает пул, если его создал `connect()` из `dsn`; идущим запросам даётся до 5 секунд. Пул, переданный в `connect({ sql })`, остаётся открытым. Подключения `db.as()` делят состояние с исходным: `close()` у любого из них закрывает всё подключение. У транзакции `db.begin()` `close()` — откат, как `rollback()`.

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.

**Примеры:** [Опции connect(): наблюдение за запросами, пул, сигналы, кэш, модели](../install/#опции-connect)
