# Корень квартиры

`me` — корень квартиры (тип в коде — `Room`): с него начинаются цепочки (`me.Класс(фильтр)`), остальное — служебные методы и свойства. Жильцу корень дают `db.open(ключ)`, `db.resume(токен)` и `db.accept(token)` — с правами жильца; консьержу — `db.in(квартира)` (полный доступ) и `db.as(аккаунт, квартира)` (права жильца); `db` — консьерж из `connect(pass)`. Транзакция `me.begin()` — такой же корень с цепочками, транзакциями и сырым SQL, но без приглашений, ключей и выписки. Загрузки и обслуживания у корня квартиры нет: загрузка — команда `letopis load` мастер-ключом, обслуживание — `db.maintain()` консьержа или `letopis maintain`.

**Что здесь:** [Свойства](#своиства) · [Квартира](#квартира) · [Транзакции и сырой SQL](#транзакции-и-сырои-sql) · [Батч](#батч) · [Модель и id](#модель-и-id) · [Сигналы и закрытие](#сигналы-и-закрытие). У каждого пункта — сигнатура с типами, что делает, параметры и опции (тип, значение по умолчанию), что возвращает, коды ошибок и переходы к живым примерам сайта.

## Транзакции и сырой SQL

### me.begin() {#db-begin}

```ts
begin(opts?: { reason?: string }): Promise<DbTx>
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Явная транзакция `read committed`: те же цепочки, `commit()`, `rollback()`, `lock()`, `forUpdate()`; `reason` — причина изменения для всех операций блока.

Транзакция уровня `read committed` на одном соединении. Внутри работают те же цепочки, `me.sql`, `forUpdate()` и `lock()`; завершает её `commit()` или `rollback()`. Ошибка любого запроса ломает транзакцию: следующие вызовы и `commit()` бросают эту ошибку, а `commit()` при этом откатывает. Библиотека не повторяет запросы внутри транзакции: при взаимной блокировке повторите весь блок. Приглашений, ключей жильца и выписки у транзакции нет — они у самого корня.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `opts` | `{ reason?: string }` | нет | Настройки транзакции. |
| `opts.reason` | `string` | нет | Причина изменения для всех записей транзакции: строка до 1000 символов. Её можно переопределить у отдельного глагола. |

**Возвращает:** `Promise<DbTx>` ([DbTx](./types-setup#type-dbtx)) — Транзакцию — корень с теми же цепочками, сырым SQL и батчем; все его операции идут в этой транзакции.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — вызван внутри другой `me.begin()` (вложенных транзакций нет), `reason` — не строка до 1000 символов или аргумент — не объект опций, например функция: `me.begin(async (tr) => …)` (ключ `api.begin_arg`; форма — `const tr = await me.begin(); try { …; await tr.commit() } catch (e) { await tr.rollback(); throw e }`).
- `invalid_data` — неизвестная опция (похожие имена — в `err.params.similar`).

**Примеры:** [Удаление по HTTP: предпросмотр, подтверждение, отмена](../recipes/undo#пример-сервер-с-билетами) · [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### me.commit() {#db-commit}

```ts
commit(tr?: DbTx): Promise<void>
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Зафиксировать транзакцию `tr` (то же, что `tr.commit()`).

Если транзакцию сломала ошибка, `commit()` откатывает её и бросает эту ошибку. Повторный вызов после успешной фиксации ничего не делает.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `tr` | `DbTx` | та, у которой вызван метод | Транзакция `me.begin()`, которую зафиксировать. |

**Возвращает:** промис без значения.

**Ошибки** ([все коды](../errors/)):

- `tx_required` — `tr` не передан, а метод вызван не у транзакции `me.begin()`.
- `tx_rolled_back` — PostgreSQL ответил на `COMMIT` откатом (`ROLLBACK`): ошибку в транзакции перехватил код внутри неё.
- `commit_unknown` — связь оборвалась во время `COMMIT`: транзакция могла и зафиксироваться.

**Примеры:** [Явная транзакция: всё или ничего](../money/#пример-все-или-ничего)

### me.transaction() {#db-transaction}

```ts
transaction<T>(fn: (tx: Tx) => Promise<T>): Promise<T>
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Транзакция под сессией: `fn` получает соединение postgres.js (в `me.begin()` — ту же транзакцию).

Запросы через `tx` подчиняются RLS и триггерам, как и цепочки. Таблицы — со схемой дома, как у `me.sql`: `` await me.transaction(async (tx) => tx`select count(*)::int as n from "v2.shop".entity`) ``. Вне `me.begin()` при взаимной блокировке и ошибке сериализации вся `fn` повторяется до трёх раз, поэтому она должна выдерживать повтор. В `me.begin()` повторов нет, а ошибка внутри `fn` ломает всю транзакцию.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `fn` | `(tx: Tx) => Promise<T>` | обязательный | Асинхронная функция: получает соединение транзакции `tx` и выполняет запросы через него. |

**Возвращает:** `Promise<T>` — То, что вернула `fn`.

**Ошибки** ([все коды](../errors/)):

- `commit_unknown` — вне `me.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.
- `tx_required` — вызван у транзакции `me.begin()`, которая уже зафиксирована или откачена.

**Примеры:** [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы)

### me.sql() {#db-sql}

```ts
sql(strings: TemplateStringsArray, ...values: unknown[]): Promise<postgres.Row[]>
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Сырой SQL под сессией и RLS, одной транзакцией (в `me.begin()` — в ней); права те же, что у цепочек. Путь поиска схем у запроса — по умолчанию PostgreSQL, поэтому таблицы `entity`, `log`, `secret` пишутся со схемой установки в двойных кавычках, значения — параметрами шаблона: ```ts const rows = await me.sql`select id, data->>'name' as name from "v2.shop".entity where class = ${'Shop'}`; ``` Без схемы (`from entity`) — ошибка PostgreSQL 42P01 «relation does not exist».

Запрос видит те же строки, что и цепочки (права те же). Таблицы `entity`, `log` и `secret` лежат в схеме дома (полное имя — `me.schema`, например `v2.shop`), а не в `public`: имя таблицы пишите со схемой в двойных кавычках — `` me.sql`select id, data from "v2.shop".entity where class = ${'Product'}` ``; без схемы — ошибка PostgreSQL «relation does not exist» (SQLSTATE 42P01). Имя схемы в шаблон значением не подставить — значения уходят параметрами. Писать тоже можно — данные проверят те же триггеры. Вне `me.begin()` при взаимной блокировке и ошибке сериализации библиотека повторяет запрос до трёх раз. Ошибки, которые бросает сама letopis в базе, приходят как `LetopisError` с её кодом, например `acl_denied`.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `strings` | `TemplateStringsArray` | обязательный | Части текста запроса — их передаёт сам шаблон: `` me.sql`select …` ``. |
| `...values` | `unknown[]` | обязательный | Значения, подставленные в шаблон через `${…}`: уходят в базу параметрами, а не текстом запроса. |

**Возвращает:** `Promise<postgres.Row[]>` — Строки ответа запроса массивом объектов (как у postgres.js).

**Ошибки** ([все коды](../errors/)):

- `commit_unknown` — вне `me.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.
- `tx_required` — вызван у транзакции `me.begin()`, которая уже зафиксирована или откачена.

**Примеры:** [Реестр классов, свой SQL под правами жильца, кэш по сроку, сигналы](../ops/#свои-sql-реестр-кэш-и-сигналы)

## Батч

### me.batch() {#db-batch}

```ts
batch(name: string, opts?: { reason?: string }): Batch
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Именованная очередь планов: `batch.Класс(…).create(…)`; `batch.run()` — одной транзакцией. У корня квартиры и у каждой `begin()` очереди свои: план исполняется от имени того, кто его поставил.

Планы одного батча ставьте через один и тот же корень (`me` или транзакцию `me.begin()`). Повторный `me.batch(имя)` с тем же именем у того же корня работает с той же очередью.

**Параметры**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `name` | `string` | обязательный | Имя очереди. |
| `opts` | `{ reason?: string }` | нет | Настройки батча. |
| `opts.reason` | `string` | нет | Причина изменения для планов, поставленных через этот объект батча: строка до 1000 символов. Её можно переопределить у отдельного глагола. |

**Возвращает:** `Batch` ([Batch](./types-chain#type-batch)) — Батч: `batch.Класс(…)` начинает план записи, и первый глагол ставит его в очередь; `run()`, `discard()` и `size()` — ниже.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — `reason` — не строка до 1000 символов.

**Примеры:** [С нуля: дом, пропуск, вход по ключу и второй жилец](../start/#семь-шагов-на-примере) · [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина)

### batch.run() {#batch-run}

```ts
run(): Promise<Row[][]>
```

**Откуда:** `batch` — из `me.batch()`; `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`).

Исполняет все планы очереди одной транзакцией. Подряд идущие простые `create` одного класса с ключом склеиваются в один многострочный оператор, подряд идущие `upsert` — тоже. Ошибка любого плана откатывает весь батч; коды ошибок — те же, что у глагола этого плана. Очередь очищается в начале вызова, поэтому после ошибки планы нужно поставить заново. В `me.begin()` батч исполняется внутри этой транзакции.

**Возвращает:** `Promise<Row[][]>` — Массив результатов в порядке постановки в очередь: у каждого плана — массив записанных им строк. Пустая очередь — пустой массив.

**Ошибки** ([все коды](../errors/)):

- `exists` — `create` на ключ, который уже занят.
- `invalid_query` — в плане `update()` или `delete({ confirm: true, expect })` без фильтра, id, `tags()`, `owner()` или `limit()` и без `{ all: true }`, `delete({ confirm: true })` без `expect` (`write.confirm_without_expect`), `restore()` без `expect` (`write.restore_without_expect`), или модификатор выборки сразу после глагола: отказ до записи, `run()` не пишет ни одного плана.
- `commit_unknown` — вне `me.begin()`: связь оборвалась во время `COMMIT`, исход неизвестен.

**Примеры:** [Батч, теги, владелец и причина изменения](../write/#батч-теги-владелец-причина) · [С нуля: дом, пропуск, вход по ключу и второй жилец](../start/#семь-шагов-на-примере)

entity(x: ChainRef | Row): Chain

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Начать путь с готового узла: `me.entity(row | цепочка)`.

Узел — объект, с которого цепочка продолжает путь. Из строки ответа получается шаг её класса с её id; из цепочки чтения — её шаги целиком, и следующие шаги идут от её последнего шага.

|---|---|---|---|
| `x` | `ChainRef \| Row` | обязательный | Строка ответа (нужны `id` и `class`) или цепочка чтения без глаголов записи. |

**Возвращает:** `Chain` ([Chain](./types-chain#type-chain)) — Новую цепочку, которая начинается с этого узла.

**Ошибки** ([все коды](../errors/)):

- `invalid_query` — передана цепочка с глаголом записи или значение, которое не строка ответа и не цепочка.
- `invalid_class` — класса строки нет в реестре.

### me.idOf() {#db-idof}

```ts
idOf(cls: string, key: Readonly<Record<string, unknown>>): string
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

**Ошибки** ([все коды](../errors/)):

- `no_session` — у корня нет квартиры.

### me.flushSignals() {#db-flushsignals}

### me.close() {#db-close}

```ts
close(): Promise<void>
```

**Откуда:** `me` — корень квартиры: жильцу его дают `db.open(ключ)`, `db.resume(токен)`, `db.accept(token)`, консьержу — `db.in(квартира)`, `db.as(аккаунт, квартира)`; `db` — консьерж из `connect(pass, { postman })` (`import { connect } from 'letopis'`); те же методы — у транзакции `me.begin()`.

Закрыть: в `begin()` — откат транзакции; корень квартиры жильца гасит свою сессию (пул общий с консьержем). После `close()` консьержа любой вызов его и производных от него (корни квартир, `begin()`, цепочки, созданные раньше) — `invalid_query` «подключение закрыто»; пул заново не открывается, процесс может завершиться. Повторный `close()` — без ошибки.

У корня жильца `close()` гасит его сессию: токен больше не открывает квартиру (`db.resume()` — `auth_failed`). Пул остаётся открытым — он общий с консьержем. У корня консьержа (`db.in()`, `db.as()`) `close()` ничего не делает, у транзакции `me.begin()` — откат, как `rollback()`. Пул закрывает `db.close()` консьержа: после него любой корень и его цепочки отказывают `invalid_query` (ключ `api.closed`).

**Возвращает:** промис без значения.

**Ошибки:** собственных кодов нет.
