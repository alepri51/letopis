# F-BOOT — up() → install() → connect()
Процессы: [N] Node-процесс (приложение, CLI или `db/apply.mjs`) · [P] PostgreSQL 18 (или PGlite)
Триггер: `const r = await up({ dsn, schema: 'salon', seeds: ['booking'] })` → `connect({ dsn, schema: r.schema, apiKey: r.serviceKey })`; `node db/apply.mjs --dsn=… --schema=salon [--seed=…] [--fresh] [--upgrade] [--quiet]`.

## Проба и база
1. [N] `lib/src/up.ts:up` — неизвестная опция — `invalid_data` с похожими именами (`checkOptions`, `UP_OPTIONS`); имя без версии получает `v2.` (`SCHEMA_VERSION`); проверка `SCHEMA_NAME`; опции `tenant` и `login` — до подключения. Готовый пул `opts.sql` — без пробы.
2. [N] `lib/src/up.ts:up#«opts.pglite»` — `up({ pglite })`: `lib/src/pglite.ts:startPglite` грузит необязательные `@electric-sql/pglite` (с pgcrypto) и `@electric-sql/pglite-socket` по требованию (нет пакета — ошибка с командой установки), сокет на свободном порту `127.0.0.1`; дальше — как с обычной базой через `postgres://postgres:postgres@127.0.0.1:<порт>/postgres`, одно соединение.
3. [N] `lib/src/up.ts:pgPing` — `select 1` раз в 500 мс до `waitTimeoutMs` (60 с): `3D000` → `ensureDatabase` (через базу `postgres`, `encoding 'UTF8' template template0`, гонка `42P04` — не ошибка), `57P03` и нет сервера → ждать, `28P01`/`28000` → сразу ошибка.
4. [P] `lib/src/up.ts:checkServer` — `server_version_num` не ниже 180000 и кодировка базы UTF8, иначе понятный отказ; ниже 18.2 — предупреждение (сервер мог усечь CLOG, нужный непрочитанным сигналам): `UpResult.warnings`, без `quiet` — `console.warn`.

## Ревизия
5. [P] `lib/src/up.ts:schemaRevision` — комментарий схемы `letopis ddl_revision=N engine=… sql=…`; схемы нет → `null` (свежая установка), штампа ревизии нет → 0. Это ревизия до блокировки схемы — только для ранних отказов шага 6 (с `fresh` не читается); что накатывать, решает ревизия под блокировкой (шаг 8).
6. [N] ревизия схемы новее `DDL_REVISION` — отказ «обновите пакет»; ниже `FIRST_REVISION` (8) или 0 — `lib/src/up.ts:refuse1x`: `invalid_data` (`boot.schema_1x`, подсказка `up({ fresh: true })`) до общей части `install()`, то есть до любых изменений, с `upgrade` тоже (план 2.0, 7.10 №5); отставшая ревизия (`FIRST_REVISION` ≤ N < `DDL_REVISION`) без `upgrade` — отказ с командой `up({ schema, upgrade: true })`; с `upgrade` — `migrateFrom`. Политику ревизий держит `up()`: `install()` — механизм наката.

## Накат (`install`)
7. [P] `lib/src/up.ts:install` — общая часть установки одной транзакцией под advisory-блокировкой (ключ — пара int4 `hashtext('letopis')`, `hashtext('install')`): параллельные `up()` разных схем одной базы ждут друг друга, иначе второй `grant usage on schema` падал `tuple concurrently updated`. В ней роли владельца и приложения идемпотентно (`duplicate_object` и `unique_violation` — роль уже есть); членство установщика `with inherit false, set true` в точке сохранения (`0LP01` и `23505` — не ошибка; 42501 — нет ADMIN на готовую роль владельца: `admin_required`, `boot.owner_no_admin`); `create extension if not exists pgcrypto` и `usage` владельцу на его схему, она же — в подстановку `@PGCRYPTO@`.
8. [P] одна транзакция под advisory-блокировкой схемы (`lib/src/up.ts:lockSchema`, ключ — имя схемы; одновременный `up()` той же схемы ждёт и делает повторный накат): `fresh` — `drop schema … cascade` от роли владельца (установщик без суперпользователя состоит в ней без наследования прав, план 2.0, ревью: `roles`); ревизия под блокировкой (`found`: миграции — от `max(migrateFrom, found)`, по ней же `created` и `upgraded`); `create schema` до `set role`; дальше под `set local role` владельца: миграции `lib/src/up.ts:migrationFiles` (`lib/sql/migrate/NNNN-*.sql`, номер выше ревизии схемы и не выше `DDL_REVISION`; каталога нет — миграций нет) — до функций; затем `lib/sql/NN-*.sql` по номеру через `substitute()` (`@SCHEMA@`, роли, `@SYSTEM@`, `@RESERVED_NAMES@`, `@MESSAGES@` — каталог сообщений базы, разделы sql-* каталога библиотеки `lib/src/messages` (план 2.0, этап 3, п. 3), `@SIGNALS@` — режим сигналов: опция `signals`, иначе сохранённый в `meta.signals` строки ключа `secret` (читается уже под ролью владельца), иначе `class`; `@ENGINE_VERSION@`, `@ENGINE_SQL@` — `lib/src/up.ts:engineStamp`: версия пакета и хэш исходного текста `NN-*.sql` и разделов sql-* каталога сообщений); последний — `lib/sql/99-revision.sql` ставит штамп `ddl_revision=8` (= `lib/src/types.ts:DDL_REVISION`, сверяет `check:docs`) и штамп движка. Файлы идемпотентны и описывают только нынешнюю ревизию: `drop … if exists` — лишь у политик RLS (`create policy` без `or replace`, `lib/sql/50-acl.sql`). Миграций сейчас нет: в `lib/sql/migrate/` — только README с правилом имени.
9. [P] сиды `seeds` — имя пакета (`lib/sql/seed.<имя>.sql`) или путь к своему файлу, с теми же подстановками.
10. [P] `lib/sql/95-seed.system.sql:seed_system` — системный сид: строка ключа с режимом сигналов в `meta.signals` (у существующей строки режим обновляется), ресурс `signals:API` и правило «сервисам — `letopis.signals`»; ключ сервиса — `bootstrap_service`: свой `serviceKey` регистрируется, если его sha256 ещё нет; иначе новый `lts_…` выдаётся, только если в схеме нет ни одного живого `APIKEY`.
11. [P] `lib/src/up.ts:up#«last_analyze is null»` — `ANALYZE` только таблиц схемы без статистики, транзакцией от роли владельца (`set local role`, как у загрузчика); в `analyzed` — таблицы, где статистика появилась, оставшиеся без неё — предупреждение `boot.analyze_skipped` в `warnings`. Затем `lib/src/up.ts:up#«boot.reserved_hubs»` — хабы с зарезервированными именами, заведённые мимо проверки базы (поиск — тоже от роли владельца): накат их оставляет, в `warnings` — `boot.reserved_hubs`.
12. [N] `up({ tenant })` — `lib/src/up.ts:createTenant` (под `lockSchema`); `up({ login })` — `lib/src/up.ts:ensureLogin`: роль приложения своей транзакцией под блокировкой `install`, привилегированную роль не трогает (`boot.login_privileged`). Результат: `schema`, `owner`, `app`, `revision`, `created`, `upgraded`, `migrations`, `analyzed`, `signals`, `warnings`, `serviceKey` (выпущенный или зарегистрированный этим накатом, иначе null — шаг 10), `pglite` (`dsn`, `close()`), `tenant`, `login` (`dsn` роли). Ошибка — PGlite останавливается.

## Подключение
13. [N] `lib/src/index.ts:connect` — неизвестная опция — `checkOptions` с похожими именами; пул postgres.js (`max` 10, `timestamptz` строкой ради микросекунд); `admin` — второй пул (`max` 2, соединяется при первом запросе, роль проверяет `adminReady`) — M-API.
14. [P] роль обходит RLS (суперпользователь, `BYPASSRLS`, членство в роли владельца с `USAGE` или `SET`) — `bypass_rls`, с `allowBypassRls` — предупреждение «администраторское подключение».
15. [P] схемы нет — `invalid_data` «установите её: up({ schema })»; ревизия схемы ниже 8 или штампа нет — отказ `refuse1x` (как в шаге 6) до входа по ключу; отставшая ревизия — предупреждение с командой `upgrade`, не отказ; новее — предупреждение «обновите пакет»; та же ревизия, а штамп движка не совпал с файлами пакета — предупреждение `lib/src/up.ts:stampDrift` (старее — `up()`, новее — обновить пакет, без версии в штампе — `boot.stamp_unknown`). Затем `apiKey`/`service` → `login_apikey` (ошибка базы — `fromDbError`).
16. [N] режим сигналов (`signal_mode()`) и ключ (`signal_key()`, режимы `tenant` и `opaque`) → `Signals`; `Notifier`, `AclPasses`, `ResultCache` (`cache: false` — без кэша; `onChanged` контекста → `ResultCache.changed`); реестр классов арендатора сессии и System; LISTEN на канал схемы (`listen: false` и режим none — нет) — дальше F-WATCH; `maintain: '1h'` — `lib/src/admin.ts:scheduleMaintain`.
17. [N] `lib/src/index.ts:makeDb` — фасад `db` → F-READ, F-WRITE, F-ACCESS.

Обёртка `db/apply.mjs` — в репозитории исходники через `tsx` из `lib/node_modules`, иначе `lib/dist/up.js`; печатает JSON (`schema`, `revision`, `created`, `upgraded`, `serviceKey`), ошибка — код 1, без `--dsn`/`ENTITY_DSN` и `--schema` — код 2.
Состояние: схема `v2.<имя>` с ревизией в комментарии; роли общие для кластера; ключ сервиса — только в ответе наката, который его выпустил или зарегистрировал (шаг 10).
Сбои: PostgreSQL ниже 18, база не в UTF8, схема ниже ревизии 8 или без штампа (`boot.schema_1x`), отставшая ревизия без `upgrade`, ошибка файла — сообщение с именем файла (`letopis.up: 60-write.sql: …`, `migrate/0009-…: …`). PGlite — одно соединение: `connect({ dsn: r.pglite.dsn, listen: false, max: 1, allowBypassRls: true })` (роль `postgres` — суперпользователь), без гонок и LISTEN.
Проверка: `cd lib && npx tsx --test --test-concurrency=1 --test-force-exit test/up.test.ts test/install.test.ts test/roles.test.ts test/one-process.test.ts` (up: 6.10, PGlite, 7.10 №5 — схема ниже ревизии 8, 7.10 №3 — хабы; one-process: 7.9 №4 — `up({ login })`).
