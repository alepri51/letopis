# F-WATCH — Сигналы, подписка по курсору, кэш результатов (letopis 1.0, этап 6; режимы сигналов — план 1.1, этап 2)
Процессы: [N] Node-процесс приложения · [P] PostgreSQL
Триггер: `for await (const ev of db.watch({ from: 'now' | 'start' | курсор, classes })) save(ev.cursor)`; `db.Price().cache({ ttl }).rows()`; любая запись в `entity`.

## Сигнал
1. [P] `lib/sql/60-write.sql:signal` — каждая запись (триггеры, функции владельца, загрузчик; и классы с `history: false`) передаёт пары «класс, арендатор»; нагрузка — по режиму установки `@SIGNALS@` (`up({ signals })`): `class` — имя класса, `tenant` — `класс@токен арендатора`, `opaque` — `токен класса@токен арендатора` (`signal_token`: 96 бит HMAC-SHA256 ключом сигналов — HMAC ключа строки KEY по `'letopis:signals'`), `none` — ничего. Одинаковые пары транзакции склеиваются. Готовые нагрузки — `signal_raw` (он же — для погашенных сессий): транзакции библиотеки помечены `letopis.notify = 'deferred'` (`lib/src/tx.ts:runTx`) — нагрузки копятся в `letopis.changed` (в режиме none — только для своего кэша), NOTIFY нет; сырой SQL — `pg_notify(схема, нагрузка)` сразу (в none — ничего), доставка при фиксации.
2. [N] `lib/src/tx.ts:runTx` — чтение `letopis.changed` и `COMMIT` уходят одним конвейером (порядок на соединении сохраняется, круг до базы один); операция только для чтения (`read: true`) — просто `COMMIT`. После фиксации — `Notifier.add` (нагрузки уходят отдельной транзакцией `pg_notify(...) from unnest(...)` раз в `notifyIntervalMs`, 100 мс; ошибка отправки — обратно в очередь, повтор следующим интервалом; в режиме none нотификатора у контекста нет) и `ctx.onChanged` (кэш своих записей, ниже). Явная транзакция — то же в `lib/src/tx.ts:ExplicitTx.commit`; обрыв во время `COMMIT` — `commit_unknown`, сигналов нет.
3. [P] Нагрузка, кроме сигналов записи (`signal_raw`, во всех режимах, кроме none): `session:<16 hex sha256 токена>` — погашенная сессия (`lib/sql/80-auth.sql`); служебных `*` и `session:*` сброса нет с 2.0.0 (`reset` снят). Ни id, ни данных; арендатор — только токеном (режимы `tenant`, `opaque`).
4. [N] `lib/src/index.ts:connect` — режим (`signal_mode()`; схема без функции — `class`) и в режимах `tenant`, `opaque` ключ (`signal_key()`: право `letopis.signals`, иначе процесс без ключа; сменившийся ключ — кэш целиком) → `lib/src/signals.ts:Signals` (разбор нагрузки, токены арендаторов, карта «токен → класс» по всем реестрам подключения). Одно LISTEN-соединение postgres.js на `connect()` (`#«sql.listen(opts.schema, onSignal»`): `onSignal` разбирает нагрузку — класс прав → пропуска прав; `Class` → реестр сразу (`reload`, одно перечитывание за раз); `*`, незнакомый токен, нагрузка не по режиму и (без ключа в opaque) любой сигнал → `resync` (пропуска, ключ, реестр — `throttle`: сразу и не чаще раза в 5 с); затем `cache.signal` и подписчики `Shared.signals` (разобранный сигнал). `onlisten` — `cache.listen()` (весь кэш) и `*` подпискам, при переподключении ещё `resync`. Без слушателя — `connect({ listen: false })` и режим none; в none реестр раз в 5 с сверяет `class_stamp()` (корень и реестры `db.as()`).

## Подписка
5. [N] `lib/src/index.ts:makeDb#«watch:»` — опции — `checkOptions`; классы → семейства (`registry.family`); исполнитель — пул, чтение под RLS журнала.
6. [N] `lib/src/watch.ts:Subscription` — `from: 'now'` (умолчание): запрос `watch_head()` уходит в конструкторе; `'start'` — `(0, 0)`; иначе — `decode(курсор)` (`tx:seq[~снимок]`, неверный — `invalid_query`).
7. [P] `lib/sql/90-time.sql:watch_head` — горизонт `pg_snapshot_xmin(pg_current_snapshot())`, seq 0 и сам снимок: транзакции, видимые в нём, зафиксированы до подписки и не отдаются.
8. [P] `lib/sql/90-time.sql:watch_read` — версии журнала с `(tx, seq) > курсор`, `tx < горизонт`, нужных классов, не видимые в снимке «now», по `(tx, seq)`, не больше `batch` (500). Права вызывающего — RLS журнала. Курсор не устаревает: журнал не прореживается (`cursor_expired` снят в 2.0.0).
9. [N] `Subscription.fetch` — события в буфер; курсор события несёт снимок, пока `tx` не дошёл до xmax снимка (`keepSnap`).
10. [N] `Subscription.next` — будят сигнал (`lib/src/watch.ts:wakes`: класс подписки и её арендатор — токен `WatchCtx.tenant`, сигнал System — все; незнакомый токен — только подписку на все классы; переподключение слушателя, opaque без ключа и нагрузка не по режиму — любую; сессии — нет) и запасной опрос `pollMs` (1000 мс). Сигнал без событий ниже горизонта — до 40 коротких повторов (25–250 мс), затем ждёт следующего сигнала или опроса.
11. [N] `Subscription.lag()` — сколько ждёт самое старое зафиксированное, но ещё не ушедшее за горизонт событие (мс); `close()` и `return()` — отписка и остановка таймера.

## Кэш результатов
12. [N] `lib/src/chain.ts:cacheTtl` — кэш только с `.cache({ ttl })` или когда все классы чтения помечены `cache` в модели; не в явной транзакции, не в батче, не с `forUpdate()`; выключен без слушателя (кроме `cache: { ttlOnly: true }`).
13. [N] `lib/src/chain.ts:exec` — ключ `ResultCache.key`: текст, параметры, токен, актор, арендатор. Промах: снимок счётчиков `token(классы, тег сессии, арендатор)` — класса, пары «класс, токен арендатора» (без токена — сигналов класса в любом арендаторе), сессии; запрос и `session_expires()` одной транзакцией, `set` — только если счётчики и общая эпоха не сдвинулись (иначе `raced`). Ответ помнит токен арендатора запроса; подключение в обход RLS — без токена.
14. [N] `lib/src/cache.ts:ResultCache.apply` — свои записи (`changed`: нагрузки из `letopis.changed` после фиксации — классы каскада и unset) и сигналы (`signal`): классы прав и схемы (`ACL_CLASSES`), opaque без ключа и нагрузка не по режиму — весь кэш; `session:<тег>` — ответы сессии; класс с токеном арендатора — ответы класса этого арендатора и ответы без арендатора; класс без токена (режим class, System, процесс без ключа) — во всех арендаторах; незнакомый токен — ничего. Запись через `db.sql` (`raw`) — весь кэш.
15. [N] `ResultCache.get` — ответ старше `ttl` (60 с) или истёкшей сессии не отдаётся; `db.cache.clear()`, `db.cache.stats()`.

Состояние: курсор хранит приложение (`ev.cursor`, `sub.cursor`); снимок «now» — в курсоре; кэш и счётчики — в памяти процесса.
Сбои: ошибка чтения закрывает подписку и бросается из `next()`. Долгая пишущая транзакция в любой базе кластера держит горизонт — поток стоит (`lag()`). PgBouncer в режиме транзакций — `listen: false`: подписка опросом, кэш выключен или `ttlOnly` (то же — во всех процессах установки с режимом none). Обрыв слушателя postgres.js не сообщает: до переподключения кэш включён, после — сброшен целиком. Очередь NOTIFY заполнена больше чем наполовину — предупреждение `maintain()` (`lib/src/admin.ts:queueWarning`).
Окно устаревания: кэш другого процесса — время доставки сигнала (интервал `Notifier` плюс доставка) и переподключения слушателя.
