# Агентский прогон

> План 2.0, этап 3, п. 9 (`reports/PLAN-LETOPIS-2.0.md`). Прогоны — на 1.4.2 (базовый), 1.5.0 и 2.0.0. Итоги — в
> `docs/checkpoint-<версия>.md`; каждый провал становится правкой документов.

Агент без доступа к репозиторию решает три типовые задачи по одной документации пакета. Приёмочные скрипты проверяют
результат на тестовой базе.

## Что видит решающий агент

- Только каталог задачи вне репозитория. В нём лежат `TASK.md` и установленный пакет: `node_modules/letopis`, `zod`
  и `postgres`.
- Документы:
  - `README.md` и `README.en.md`;
  - `AGENT-CHEATSHEET.md` и `AGENT-CHEATSHEET.en.md`;
  - `llms.txt` и `llms-full.txt` (в 1.4.2 этого файла нет);
  - типы `node_modules/letopis/dist/**/*.d.ts`.
- Нельзя: исходники пакета (`dist/*.js`, `sql/`), прочие его файлы, документацию других пакетов, репозиторий
  letopis, интернет.
- Агента запускают без CLAUDE.md, AGENTS.md и карточек проекта: рабочий каталог — каталог задачи. Если агент —
  субагент сессии, запрет стоит в промпте и в `TASK.md`, а нарушения ищут в транскрипте.
- Пишет агент только в свой каталог: `solution-a.mjs`, `solution-b.mjs`, `solution-c.mjs`, `REPORT.md` и
  вспомогательные `scratch-*`.

## Каталоги

Каталог прогона — вне репозитория, например временный каталог сессии `…\scratchpad\agent-run\`:

| Каталог | Пакет | Как ставится |
|---|---|---|
| `v142` | letopis 1.4.2 из npm | `npm install letopis@1.4.2 zod postgres` |
| `v150` | тарбол текущего `dev` | сборка и `npm pack` из чистой копии `HEAD:lib`, затем `npm install <тарбол> zod postgres` |
| `v200` | 2.0.0 | так же, к выпуску 2.0.0 |

Подготовка каталога `v<NNN>`:
1. Создать `package.json` с `{ "private": true, "type": "module" }`. Без него npm уходит вверх к ближайшему
   `package.json` или `node_modules` и ставит пакеты туда.
2. Поставить пакеты по таблице. `postgres` берётся последний: так его поставит и пользователь по README. letopis
   пользуется своей вложенной копией.
3. Положить `TASK.md` — копию `docs/agent-run/TASK.md`, где `{ver}` заменено на `<NNN>`:
   `sed "s/{ver}/150/g" docs/agent-run/TASK.md > <каталог>/TASK.md`.

Тарбол собирают из `git archive HEAD:lib`, а не из рабочего дерева: параллельные правки других исполнителей не
должны попасть в пакет. Копию распаковывают в `lib/.tmp/…` (каталог в `.gitignore`), там же собирают: `tsc -p
tsconfig.build.json`, типы берутся из `lib/node_modules`. Затем `npm pack --pack-destination <каталог прогона>`, и
копия удаляется.

## Три задачи

Условия — `docs/agent-run/TASK.md`. Схема агента — `v2.agent_<NNN>_<a|b|c>`, его роли — с префиксом `agent_<NNN>_`.

| Задача | Суть | Функции решения |
|---|---|---|
| А — CRUD со связями | Библиотека: `Author`, `Book` (конец `Author`, `restrict`), `Review` (конец `Book`, каскад). Создание, перевод книги к другому автору правкой, приращение, удаление с каскадом и по шагам | `run(dsn, schema)`, `report(db)` |
| Б — арендаторы и права | «Альфа» и «Бета», четыре пользователя с паролями и ролями `manager`, `staff`, `viewer`, класс `Product` в обоих арендаторах, права по ролям | `run(dsn, schema)` |
| В — история и проектор | `Product` с ценами и причинами изменений, `Sale`, производный `SkuTotal` проектора `totals` | `run(dsn, schema)`, `project(adm)`, `priceLog(db, sku)`, `priceAt(db, sku, at)` |

## Приёмка

```sh
node docs/agent-run/accept-a.mjs <каталог агента> [--solution файл] [--schema v2.имя] [--drop]
node docs/agent-run/accept-b.mjs <каталог агента>
node docs/agent-run/accept-c.mjs <каталог агента>
```

Общая часть — `docs/agent-run/_accept.mjs`:
- letopis и postgres.js приёмка берёт из каталога агента, то есть той версии, на которой он решал;
- решение ставится на пустую схему `v2.accept_<NNN>_<задача>`, а не на схему агента: так видно, что имя схемы не
  зашито. Схема остаётся для разбора; с `--drop` её удаляют;
- сначала проверяется сборка: файл есть, проходит `node --check`, импортируется и отдаёт нужные функции;
- затем приёмка вызывает `run(dsn, схема)` с тайм-аутом 10 минут. Остальные функции — с тайм-аутом 3 минуты;
  `process.exit` и `console.warn` решения при этом перехвачены;
- данные проверяются SQL суперпользователя по `entity` (живые строки) и `log` (версии, причины, удаления);
- поведение и права проверяются от имени пользователя. Он входит паролем: сессию сервиса установки выдаёт
  суперпользователь (`new_session`), сервис зовёт `auth.verifyPassword`. Затем сессия переключается
  `auth.switch`, и пользователь работает ролью `letopis_accept` (LOGIN, только `letopis_app`) без обхода RLS;
- ожидаемый отказ — операция бросила ошибку, данные не изменились. `invalid_class` отказом не считается: класса
  нет, проверять нечего.

Проверки:
- **А**, 15 проверок: авторы, книги и их концы; перевод книги правкой (версии, без удаления); переход `copies` 3 → 2
  и удаление «Войны и мира»; каскад отзывов; удаление Достоевского с книгами и отзывом; живой отзыв; вход Лизы;
  `report(db)` после книги, которую добавила приёмка; отказы `exists`, «без автора», `invalid_data` (оценка 6,
  `copies` −1), `delete_restricted`.
- **Б**, 11 проверок: арендаторы; товары по арендаторам; вход четверых паролем (неверный пароль — нет входа);
  членства `auth.tenants()` и переключение; видимость; `manager` создаёт, меняет, удаляет; `staff` не удаляет;
  `viewer` только читает; изоляция арендаторов; итог в базе.
- **В**, 12 проверок: товары; журнал `P-1` (цены и причины трёх версий); продажи (правка `S-2`, удаление `S-3`);
  итоги после `run`; вход Марии; `SkuTotal` закрыт для записи приложением; `priceLog`; `priceAt` на `P-1` и на
  товаре приёмки (10 → 20 → 30, точки — середины между версиями по часам базы); `project(adm)` после новой
  продажи, правки, переноса на другой `sku`, удаления; повторный `project(adm)` итогов не меняет.

Код выхода: 0 — сборка, `run()` и все проверки прошли; 1 — что-то не прошло; 2 — сбой самой приёмки (аргументы,
база). Последняя строка — `RESULT {json}`:
- `build`, `run` (`ok`, `ms`, `code`, `error`);
- `checks` (`id`, `ok`, `code`, `detail`), `passed`, `total`, `ok`;
- `errors` — коды неожиданных ошибок letopis;
- `refusals` — коды ожидаемых отказов (на эталоне Б — `acl_denied` ×4, `tenant_denied` ×1);
- `warnings` — сколько предупреждений библиотека напечатала в вызовах решения.

Приёмку не запускают одновременно с `npm test` и `prerelease` на той же базе.

## Метрики

| Метрика | Источник | Как считать |
|---|---|---|
| Собралось | `RESULT.build.ok` | файл есть, `node --check`, импорт, все функции задачи |
| Прошли ли приёмки | `RESULT.passed` / `RESULT.total`, `RESULT.ok` | задача решена, если `ok`; провалы — по `id` и `detail` |
| Ошибки по кодам при работе агента | транскрипт агента; раздел «ошибки» в `REPORT.md` | число строк `letopis: <код>:` в выводе инструментов по кодам; что агент сделал после каждой |
| Ошибки по кодам в приёмке | `RESULT.run.code`, `RESULT.errors`, `RESULT.checks[].code` | неожиданные ошибки решения; ожидаемые отказы (`refusals`) — не ошибки |
| К каким документам обращался | транскрипт агента; раздел «документы» в `REPORT.md` | чтения (Read, Grep, Glob, `cat`, `grep`, `sed` в Bash) по файлам из списка: число обращений, разделы (смещение или образец поиска). Чтение вне списка — нарушение, отдельной строкой |
| Дополнительно | транскрипт | время до готовности, число вызовов инструментов и токены; запускал ли агент решение на базе |

## Порядок прогона

1. Подготовить каталоги (раздел «Каталоги»). Схемы `v2.agent_<NNN>_*` и `v2.accept_<NNN>_*` должны отсутствовать.
2. Координатор запускает по одному решающему агенту на каталог с промптом ниже. Каталоги разных версий можно
   решать одновременно: схемы и роли у них разные.
3. Когда агент закончил, координатор запускает три приёмки на его каталоге и сохраняет вывод.
4. Метрики собираются из `RESULT`, транскрипта и `REPORT.md`.
5. Итоги записываются в `docs/checkpoint-<версия>.md`:
   - таблица «версия — задача — собралось — приёмки — ошибки при работе — ошибки приёмки — документы — время»;
   - по каждому провалу: `id` проверки → причина → какой документ поправить.
6. Уборка суперпользователем:
   ```sql
   do $$ declare s text; begin
     for s in select nspname from pg_namespace where nspname like 'v2.agent\_%' or nspname like 'v2.accept\_%' loop
       execute format('drop schema %I cascade', s);
     end loop;
   end $$;
   -- роли агентов: для каждой rolname like 'agent\_%' — drop owned by <роль>; drop role <роль>;
   ```

## Промпт решающего агента

Одинаковый для всех версий; `<КАТАЛОГ>` — абсолютный путь каталога задачи:

```text
Ты — решающий агент агентского прогона letopis. Твой каталог: <КАТАЛОГ>.
Прочитай <КАТАЛОГ>\TASK.md и выполни его целиком по его правилам. Главное:
- читать можно только TASK.md и документацию с типами пакета в <КАТАЛОГ>\node_modules\letopis (README.md, README.en.md, AGENT-CHEATSHEET.md, AGENT-CHEATSHEET.en.md, llms.txt, llms-full.txt, если он есть, dist/**/*.d.ts); исходники пакета, другие каталоги, репозитории и интернет — нельзя;
- если в твоём контексте уже есть сведения о репозитории letopis (CLAUDE.md, AGENTS.md, карточки, исходники), не пользуйся ими;
- писать — только в <КАТАЛОГ>: solution-a.mjs, solution-b.mjs, solution-c.mjs, REPORT.md и вспомогательные файлы scratch-*;
- проверяй решения запуском на тестовой базе из TASK.md, каждую задачу — в её схеме.
Закончив, ответь кратко: какие задачи решены, какие нет и что мешало.
```
