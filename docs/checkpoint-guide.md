# Документация для людей: сайт guide/ и сервисы-примеры

План — «документация letopis для людей», утверждён владельцем 29 октября 2026 года. Его решения:
- сайт только на русском и только локально;
- найденный баг библиотеки исправляется сразу, исправление подтверждает пример документации, который без него падает;
- новых тестов в `lib/test` нет;
- сервисы — все четыре, на блоках shadcnblocks, у каждого ручной запуск (bash и PowerShell) и Docker;
- отдельная страница «Старт с нуля».

Работа шла в ветке `dev`, от `e4119ab` (этап 0) до коммитов этого отчёта. Первая редакция отчёта (коммит `c44d666`) подвела итог этапов 0–5. После неё по решениям и указаниям владельца сделаны доработки — коммиты от `ae7d2fe` до `e1aa620`; они описаны в разделе «Доработки после первой редакции отчёта». Выпуск библиотеки не делался: в `lib/package.json` стоит версия `1.4.1-alpha.0`, тега и выпуска с ней нет.

## Доработки после первой редакции отчёта

### Сайт

**Реальные значения, «Дано», весь код примера** (`4de6b34`). Снимок с метками удобен для сверки, но не показывает, как данные выглядят в базе. Теперь рядом с каждым снимком лежит второй файл, `<id>.real.json`: тот же прогон с настоящими значениями — uuid, время, токены, ключи, хэши секретов, номер транзакции журнала. В плеере у таблиц две вкладки: «Метки» (как раньше) и «Реальная таблица». Сверка `--check` по-прежнему сравнивает только снимок с метками: настоящие значения в каждом прогоне свои.

Над кодом шага появился блок «Дано»: что шаг берёт из контекста примера и какие значения были в этом прогоне, с пояснениями — строки подключения `dsn.admin` и `dsn.app`, схема, логин и пароль Анны, ключ сервиса и арендатор. Кнопка «Весь код примера» открывает исходник целиком: с моделями, помощниками и переменными прошлых шагов. Песочница тоже отдаёт настоящие значения своего прогона.

**Справочник API** (`4de6b34`, дополнен вместе с `db.auth.session` и исправлениями библиотеки). Раздел `/reference/` — обзор и 13 страниц: цепочка, корень `db`, `db.auth`, `db.acl`, подписка и кэш, проекторы и агрегаты, загрузка, установка и подключение, `letopis/model`, служебные экспорты, `letopis/mcp`, командная строка, типы. В нём 300 пунктов, у каждого — сигнатура, что делает, параметры и поля опций, результат, ошибки и примеры. Описания берутся из JSDoc библиотеки; то, чего в JSDoc нет, дописано в `guide/coverage/api-docs.ts` и сверено с кодом и README. Страницы строит `guide/scripts/gen-api.ts`, в CI их сверяет `gen-api.ts --check` (`.github/workflows/ci.yml`).

**Переход с 0.21 убран** (`4de6b34`, указание владельца). С сайта сняты глава 18 «Переход с 0.21», пример импорта из 0.21, пример снятого API и нюанс об импорте. 34 пункта инвентаря, которые относились только к 0.21 (снятое API и команда `letopis import`), вынесены за рамки сайта: список исключений с пояснением — в `guide/scripts/coverage.ts`. Код ошибки `removed` в главе 16 остался — с примечанием, что так отвечает снятое API.

**«Действие при удалении» и «ограничение модели»** (`2c061a2`). Слово «правило» на сайте значило две разные вещи. Теперь «правило» — только правило доступа. Значения `cascade`, `restrict` и `unset` у конца связи называются «действием при удалении»: на страницах, в примерах, в нюансе, в главе 16 и в новой статье глоссария. «Правило модели» стало «ограничением модели» — в схемах процессов и на страницах агрегатов и кошелька. Переименование сделал субагент без смены модели, снимки перезаписаны и сверены с прежними версиями скриптом: изменились только тексты.

### Библиотека

Все изменения библиотеки — в записи `1.4.1-alpha.0` файла `lib/CHANGELOG.md`. Где менялось поведение, описанное в документации, обновлены README (обе версии) и справочник сайта.

**Порядок записей журнала у массовых операций** (`2f977c0`). После исправления порядка надгробий каскада (раздел «Баги библиотеки — исправлены», пункт 3) владелец решил проверить остальные массовые записи в журнал. Нашлось шесть мест, где порядок зависел от плана запроса; теперь он определён:
- пакетная вставка (`trg_entity_ai`) — по времени и id: порядок `seq` совпадает с порядком входа;
- правка многих строк одним оператором (`trg_entity_au`) — по id;
- перестройка проектора (`derived_clear` в `lib/sql/88-derived.sql`) — по id;
- загрузка с `existing: 'update'` (`lib/src/load.ts`) — по id;
- выход из членства (`trg_entity_ad`) и `purgeAccount` (`account_purge`) — арендаторы по порядку;
- цели `reclass`, `rekey`, `restore` и `purge` (`targetIds` и `deletedTargets` в `lib/src/write.ts`) — по id.

`derived_apply` не тронут: там записи идут в порядке операций проектора, и этот порядок обязателен. В примерах документации порядок и раньше не расходился, поэтому пример, который падает без исправления, показать нельзя: исправление убирает саму зависимость от плана запроса.

**`db.auth.session(token)`** (`f1ed819`). В API не было способа узнать по токену сессии, чья она. Владелец утвердил проект, метод добавлен. Сервис передаёт токен (например, из cookie) и получает `{ account, tenant, member, expiresAt, loginAt, methods }`: аккаунт, арендатора сессии, цело ли там членство, срок, время и способы входа. Подключение по этому токену не открывается, срок сессии не продлевается. Неверный, погашенный или истёкший токен и токен отключённого аккаунта дают `null`, причина не различается. Вызывать метод может сервис или системный администратор (право `auth.session`): пользователю отвечают `acl_denied`, без сессии — `no_session`. В базе это функция `auth_session_info` (`lib/sql/80-auth.sql`); она ищет только строки сессий, как и проверка контекста. На сайте — шаг 9 примера `guide/examples/auth/02-sessions-tenants.ts` и справочник; helpdesk проверяет через этот метод веб-сессию. В тесте `roles` с разрешения владельца дополнены белый список функций и негативный тест №4.

**Четыре исправления по разбору возможных ошибок** (`8fdf957`). Владелец решил исправить все четыре. Каждое подтверждает пример, который без исправления падает; это проверено откатом исправления.
1. **Молчащая подписка.** Подписка, у классов которой дольше яруса `all` политики хранения (больше суток) не было событий, получала ложный `cursor_expired`, хотя ничего не пропустила: время курсора оставалось временем последнего события, а база сверяет его с горизонтом на каждом опросе. Теперь подписка, догнав журнал, ставит в курсор время опроса, но не позже самой старой записи своих классов, которая ещё не ушла за горизонт. `sub.cursor` стоит после последнего события, отданного `next()`, и не обгоняет события, прочитанные в запас. Пример — новый `guide/examples/watch/02-quiet-cursor.ts` (без исправления шаг 3 падает с `cursor_expired`), нюанс `watch-subscription-cursor`.
2. **Интервал `maintain`.** `connect({ maintain })` не проверял интервал. Ноль, отрицательное число, `NaN`, `Infinity` и интервал длиннее 2³¹−1 мс таймер Node.js превращал в 1 мс, и обслуживание шло без перерыва, а `null` и `true` давали `TypeError`. Теперь интервал — конечное число или строка от 1 мс до 2³¹−1 мс (около 24 суток), иначе `invalid_data` ещё до открытия пула. `close()` дожидается идущего по расписанию `maintain()`. Пример — `guide/examples/install/03-connect-options.ts`, шаг 6.
3. **Вид входа в `createTenant`.** `createTenant` и `up({ tenant })` принимали любой `user.kind`: в другом регистре, пустой или служебный (`SESSION`, `TOTP` и другие). По такому паролю нельзя было войти, а с видом `TOTP` аккаунт выглядел так, будто у него включён второй фактор. Теперь вид проверяется тем же правилом, что в функциях кредов (`auth_kind_ok`), а неверный вид — `invalid_data` до записи. Пример — `guide/examples/install/01-up-and-connect.ts`, шаг 4.
4. **`out.delete` и `out.get` проектора по id.** У производного класса с ключом они, получив один id, искали строку с пустым ключом: `get` отвечал `null`, а `delete` выводил арендатора с `id_mismatch`. Теперь это сразу понятная ошибка `invalid_data` с перечнем полей ключа. Строку класса с ключом называют полями ключа, id — только строку класса без ключа. Пример — `guide/examples/derived/03-projector-options.ts`, шаги 3 и 4, нюанс `projector-out-by-key`.

**Секреты удалённого аккаунта: внешний ключ `secret.account`** (`dbadfe3`, ревизия движка 7). Раньше хэши паролей и ключей, секреты TOTP и внешние учётные записи удалённого аккаунта оставались в `secret` навсегда: удаление гасило сессии и помечало способы входа, а `maintain()` физически убирает только сессии и коды `OTP`. Решение владельца — «стирать сразу + внешний ключ», с запретом удалять аккаунт System. Сделано:
- внешний ключ `secret.account → entity(id) on delete cascade` и индекс по `secret.account` (`lib/sql/10-core.sql`). Миграция `lib/sql/migrate/0007-secret-account-fk.sql` сначала стирает строки `secret`, чьих аккаунтов уже нет, потом ставит ключ;
- новый триггер `trg_entity_bd_account` (`lib/sql/60-write.sql`, до удаления, для всех ролей) гасит сессии с сигналом раньше каскада, поэтому процессы, как и прежде, сбрасывают кэш ответов этих сессий;
- строку `Account` аккаунта System удалить нельзя — `acl_denied`. Ему принадлежат служебные строки установки в `secret` (ключ прав и сигналов, строки-замки, чекпоинты проекторов), и каскад стёр бы их. `seed_system()` создаёт аккаунт System раньше строки ключа;
- `purgeAccount` полагается на триггер и каскад; первая заливка снимает внешний ключ до очистки таблиц и возвращает после; `letopis import` пропускает креды аккаунтов, которых нет.

Схемы ревизии 6 (1.1–1.4.0) обновляются вызовом `up({ upgrade: true })`, без него `up()` отказывает. Под новое поведение подстроены существующие тесты: `upgrade` (миграция 0007), `roles` №4 и №7 и атака №19 в `engine-attacks`; новых тестов нет. Пример — `guide/examples/auth/03-delete-account.ts`: без исправления шаг 3 находит в `secret` три строки удалённого аккаунта, а шаг 4 не получает `acl_denied`. Нюанс — `account-delete-secrets`.

### Сервисы

**`up({ upgrade: true })`** (`e1aa620`). После перехода движка на ревизию 7 сервисы стенда перестали подниматься: `up()` отказывал на схемах ревизии 6, созданных прежней версией. ## Баги библиотеки — исправлены

Эти три бага нашли прогоны примеров на этапах 0–5. Все они — в записи `1.4.1-alpha.0` файла `lib/CHANGELOG.md`, и каждый подтверждает пример, который без исправления падает. Ещё пять исправлений сделаны после первой редакции отчёта по решениям владельца: порядок журнала у массовых операций, четыре ошибки из разбора и строки `secret` удалённого аккаунта. Они описаны в разделе «Доработки после первой редакции отчёта».

1. **`db.auth.purgeAccount(арендатор)` из сессии, работающей в этом арендаторе,** откатывался с `tenant_denied`: функция стирала членство вызывающего, а дальше перечитывала контекст. Исправление — в `lib/sql/90-time.sql` и `lib/src/auth.ts`. Пример — `guide/examples/auth/02-sessions-tenants.ts`, шаг 8.
2. **`commit()` транзакции, в которой ошибку поймали и проглотили,** бросал сырую `25P02` вместо обещанной README `tx_rolled_back`. Исправление — в `lib/src/tx.ts`. Пример — `guide/examples/errors/01-api-errors.ts`, шаг 7.
3. **Порядок надгробий каскада.** Надгробия одного уровня каскада триггер писал вставкой без `order by`, поэтому их порядок в журнале (`seq`, время `at`) и порядок строк итога `delete({ confirm: true })` зависел от плана запроса. Предпросмотр при этом шёл по id. Теперь надгробия каждого уровня пишутся в порядке id (`lib/sql/60-write.sql`, `trg_entity_ad`), цели классов без журнала — тоже по id (`lib/src/write.ts`). Примеры — `guide/examples/delete/01-delete-cascade.ts` и `02-restore-purge.ts`: без исправления снимок разошёлся в 5 прогонах из 5, с исправлением совпал в 10 из 10. В README (раздел 7, обе версии) — порядок итога.

## Недетерминизм примеров и раннера — исправлен

Сверка снимков в CI годится, только если повторный прогон даёт тот же снимок. Расхождения находились и устранялись:
- время в снимке — метки `t1, t2…`, одна транзакция — один момент. Сначала метка ставилась на каждое различное время версии. Две версии одной транзакции изредка совпадали до микросекунды, и это сдвигало все следующие метки: так в `start/01`, где установка идёт внутри шага — десятки строк одной транзакцией;
- метки строк («Класс·N», «·2» у одноимённых) — по первому появлению в журнале. Сначала я раздавал их по рангу id, но у класса без ключа id случайный: две строки «Пётр» в `models/02` менялись метками в половине прогонов;
- длительности `ms`, ключ пары «ключ + секрет», номер шага TOTP — метки;
- `write/06`: кэш изредка не засчитывал попадание. Сигнал о записи прошлого шага приходил во время первого чтения, и кэш, защищаясь от гонки, ответ не клал. Это верное поведение библиотеки; попадания теперь считаются на свежем подключении, а сама защита описана нюансом `cache-raced`.

Настоящие значения из второго снимка (`<id>.real.json`) сверка не сравнивает: uuid, время, токены и хэши в каждом прогоне свои.

Найдено и исправлено на сайте:
- точка с запятой в подписи Mermaid обрывает схему;
- стиль страницы VitePress (высота строки абзаца) обрезал подписи в узлах схем.

## Нюансы, найденные прогонами

Прогоны примеров и сценариев вскрыли поведение, которого не было в документации. Всё описано в главе 17 или на страницах сервисов:
- погашенная сессия на чтении даёт пустой ответ, а не ошибку;
- `refresh` не укорачивает срок сессии;
- свежая сессия работает в личном арендаторе;
- второй фактор letopis не навязывает — его требует сервис;
- `reclass` в класс с ключом даёт новый id;
- прореживание по политике — не разрыв журнала для `verify()`;
- первая заливка — только в пустую схему;
- `reset` уровня `tenant` стирает и членства;
- у цепочки нет `then`: `await db.Класс(…)` ничего не читает;
- `purge()` без `confirm` — только предпросмотр;
- `auth.tenants()` не упорядочен;
- `revokeAll` действует во всех компаниях пользователя;
- `createTenant` находит арендатора по имени, а название закрытой компании занято навсегда;
- ответ, на время чтения которого пришёл сигнал, в кэш не кладётся.

После первой редакции отчёта вместе с исправлениями библиотеки добавлены нюансы `watch-subscription-cursor` (курсор молчащей подписки), `projector-out-by-key` (строку класса с ключом проектор называет полями ключа) и `account-delete-secrets` (удаление аккаунта стирает его строки `secret`, аккаунт System удалить нельзя). Нюанс о том, что импорт из 0.21 проверяет всё до записи, снят вместе с переходом с 0.21. В главе 17 — 70 нюансов.

## Как запустить

- Весь стенд: `docker compose -f services/compose.yaml up -d --build`. Сайт с песочницей — http://127.0.0.1:8080, сервисы — 8081–8084. Схему стенда сервисы при старте обновляют сами (`up({ upgrade: true })`).
- Сайт без Docker: `cd lib && npm ci && cd ../guide && npm ci && npm run build && npm run sandbox`. Подробности и меры безопасности — страница «Песочница».
- Примеры: `cd guide && npx tsx scripts/run-examples.ts [фильтр] [--check]`. Нужна тестовая база библиотеки: 127.0.0.1:15433, при наличии Docker поднимается сама.
- Сервисы руками: README в каталоге каждого сервиса.
